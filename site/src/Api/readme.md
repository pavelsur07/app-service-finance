# Api: управление внешним доступом

Статус: backend управления ключами реализован, UI и права в работе. [План](../../../docs/tasks/api-management/plan.md), [checkpoint](../../../docs/tasks/api-management/checkpoint.md), [контракт](../../../docs/tasks/api-management/TASK.md).

Новый Bearer API отделён от старых ключей отчётов: маршруты и аутентификация не взаимозаменяемы. Предметные endpoints и финансовые изменения здесь не реализуются.

Запрос: `GET /api/external/v1/auth/check`, `Authorization: Bearer <API_KEY>`, `X-Company-Id: <public_company_id>`. ID компании публичный числовой, UUID остаётся внутренним. Ключ живёт ровно 90 суток UTC; при now >= expiresAt недействителен. Отзыв необратим, новый выпуск не отзывает старые ключи. Секрет из 32 случайных байт выдаётся один раз в no-store ответе; хранится лишь SHA-256, сравнение constant-time. Секреты не передаются в URL/flash/аудит/логи/localStorage.

Prepared scopes — конкретные выбранные права каталога. Effective scopes — пересечение prepared, подключённых возможностей и ресурсов, явно включённых владельцем. Сейчас все предметные ресурсы не подключены, effective пуст. Подключение ресурса и добавление scopes не должны автоматически наделять старые ключи правами. Connection check доступен без предметных scopes.

## Обязательный контракт будущих предметных модулей

```text
UI → Action предметного модуля
API → Facade предметного модуля → тот же Action
Другой модуль → Facade предметного модуля → тот же Action
```

- Создание, корректировка, мягкое удаление и восстановление имеют единые правила во всех каналах.
- Сервер формирует доверенный контекст: ui/api/module/system, пользователь, ID API-ключа, код модуля, ID запроса/задачи. Клиентские поля не считаются доверенным происхождением.
- Источник создания неизменяемый; источник последнего изменения отдельный; история событий сохраняется. Бизнес-изменение и аудит атомарны; повтор без изменения данных не создаёт ложного события.
- UI показывает происхождение и последнее изменение. Неизвестное происхождение исторических записей не подменяется UI.
- Существующие import source и external ID сохраняются для идемпотентности.
- Переиспользовать Shared AuditLog. Его автоматический subscriber сейчас обрабатывает только CashTransaction; полноценная поддержка каналов и других операций ещё не реализована. Явный аудит управления API-ключами не означает готовность финансового аудита.
- Техническое физическое удаление ОПиУ запрещено для пользовательского API.
- До подключения каждого ресурса: Facade → общий Action; company isolation/owner policies; scope для каждого endpoint (отсутствие policy = deny); атомарность/идемпотентность/история и UI происхождения; функциональные тесты каналов и прав; явное включение владельцем.

Подготовка финансовых модулей, финансовые endpoints, бейджи и история финансовых операций выполняются отдельным планом.

## Реализованный протокол

Токен имеет вид `vfd_<32 hex public identifier>.<64 hex secret>`. Открытая часть используется лишь для узкого bootstrap-поиска: `ApiKeyRepository::findOneByPublicIdentifier` помечен companyScopeExempt. После проверки секрета и соответствия CompanyFacade все операции используют установленный companyId. Поле createdBy не является principal и не используется для входа.

`auth/check` возвращает `company_id` (число), `key_id` (UUID), `expires_at` (UTC ISO8601), `prepared_scopes`, `effective_scopes`. Для подключения cookies не нужны. Отзыв и срок проверяются свежим чтением без долгоживущего кеша. Последнее успешное использование обновляется отдельно, не меняя версию настроек.

Ошибки имеют `Content-Type: application/problem+json`, тело `{ "type": "about:blank", "title": "Unauthorized", "status": 401, "detail": "Missing or invalid API key." }`. 401 также содержит `WWW-Authenticate: Bearer`; 403 — чужая компания/нет политики или прав; 422 — неверный обязательный X-Company-Id; 429 — лимит с Retry-After. Допускается60 запросов/минуту/ключ и20 неуспешных аутентификаций/минуту/IP. Ошибки и успешные ответы no-store. Профайлер выключен для внешнего API и страницы управления секретами; локальный Monolog маскирует новые токены и параметры SQL api_keys, Sentry использует существующий scrubber.

Даты ключей хранятся timezone-aware: TIMESTAMP WITH TIME ZONE / datetimetz_immutable. Это исключает сдвиг90-дневного срока при чтении в московской зоне приложения. Публичный номер компании выдаётся DB sequence; миграция совместима со старыми INSERT и не меняет UUID. После публикации идентификаторов rollback через перенумерацию запрещён: forward-fix.

Doctrine schema diff: DBAL считает `nextval` autoincrement, поэтому для non-PK public_id остаётся ожидаемая разница mapping/schema. Не применять автоматически сгенерированный diff этой колонки и не удалять mapping default: DB default необходим старым INSERT без public_id.
