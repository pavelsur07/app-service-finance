# Промпт: страницы «Вход» и «Регистрация», логотип и юридический блок (legacy-слой)

Работай по `AGENTS.md`, `CLAUDE.md`, `CLAUDE.frontend.md`. Начни со Stage 0 (аудит) и короткого отчёта; код — после. Правила DS — `docs/design-system/sheets/` (Tokens, Controls, Feedback), планы `docs/plan/ds-legacy-tabler-audit.md`.
Эталон — пакет: `docs/design-system/AUTH-SPEC.md` (**прочитай целиком**), `screens/Login.dc.html`, `screens/Register.dc.html`, `screens/auth-refs/*.png`, `brand/*` (логотип и `README-logo.md`), `components/auth/*` (эталонные CSS/JS/Twig). Критерии готовности — `CHECKLIST-auth-pages.md`.

## Цель
1. Страницы входа и регистрации оформляются по макету (раскладка, поля, состояния, адаптив).
2. Вместо текстового «ВФ»-квадрата везде используется настоящий логотип (SVG) + favicon.
3. На обеих страницах — юридический блок: ссылки на документы, «Сведения о компании» (реквизиты из конфигурации), оговорка о хранении ПДн в РФ, баннер cookie; на входе — строка о принятии условий; на регистрации — раздельные обязательные согласия, отдельное необязательное согласие на рассылку и юридическое примечание.

## Рамки
- Только legacy-слой: `templates/_layout/legacy.html.twig` (или текущий layout страниц авторизации), Tabler, токены `--vf-*`, `legacy-app.css/js`. Не трогать `_layout/app.html.twig`, `assets/react/**`, `site/ui-kit/`; не брать их за образец.
- Security, FormType, имена роутов и полей, CSRF, «запомнить меня», подтверждение email, сброс пароля, существующие тесты — **не менять**. Серверная валидация — источник истины. Не добавлять пользовательские данные в логи/URL.
- Схему БД/миграции — не менять без согласования. Для отдельного согласия на рассылку (SPEC §10.3) выбери безопасный вариант или вынеси вопрос в отчёт; **не придумывай** хранение молча.
- Прототипы — не код: не копируй их разметку и демо-логику (пароль `wrong`, `busy@company.ru`, таймеры, фейковые экраны «Вы вошли» и «Проверьте почту» без реального потока). Эталонные `auth.css/js`, `cookie-consent.js`, Twig — отправная точка: допустимо адаптировать под сборку проекта, но вид и поведение должны совпасть.
- Реквизиты в макете — **демо**. В коде — конфигурация (`legal.example.yaml`), настоящие значения не придумывать: оставить демо с пометкой и вынести в отчёт, что подставить.

## Stage 0 — аудит (до правок, коротко в отчёт)
1. Найди шаблоны, контроллеры, FormType, JS/CSS страниц входа и регистрации, layout авторизации, письма и экран подтверждения email. Перечисли, что реально применено сейчас.
2. Где используется логотип/название сервиса (шапка, меню, письма, `<title>`, favicon, manifest, OG). Составь список мест для замены.
3. Какие юридические страницы и роуты уже есть (`/legal/*` или иные), какие документы отсутствуют (особенно «Политика cookie»). Как сейчас хранятся согласия при регистрации (поля, дата, версия документа).
4. Какие cookie и скрипты аналитики/маркетинга грузятся и до какого момента; есть ли уже баннер cookie.
5. Найди e2e-селекторы и тесты страниц; зафиксируй, что не должно сломаться.
6. Предложи разбивку на PR; по умолчанию: **PR 1 — логотип/favicon + юридический подвал + баннер cookie (общие partial/CSS/JS)**, **PR 2 — страница входа**, **PR 3 — страница регистрации**.

## Stage 1 — логотип и общие компоненты
- Скопируй `brand/*.svg|png` в `public/brand/` (или `assets/` с версионированием), подключи favicon/apple-touch/OG по `brand/README-logo.md`; замени логотип в layout авторизации, боковом меню приложения (`logo-full-white.svg`), письмах (PNG@4x) и заголовках.
- Подключи `auth.css` (алиасы токенов к `--vf-*` в одном блоке), `auth.js`, `cookie-consent.js`; создай Twig-partials по `components/auth/*`: `_logo`, `_legal_footer`, `_cookie_banner`.
- Реквизиты — в конфиг (twig global `legal` или параметры), строки реестров скрываются при пустом значении.
- Баннер cookie: cookie `vf_cookie_consent`, аналитика/маркетинг грузятся только после «Принять все» (событие `vf:cookie-consent`); необходимые cookie работают всегда.
- Проверь, что страницы документов `/legal/*` существуют; если нет — не оставляй мёртвых ссылок: отчёт + вопрос владельцу (допустимо временное «в разработке» только по согласованию).

## Stage 2 — страница входа
- Вёрстка SPEC §2, §4: шапка с логотипом и ссылкой «Создать», карточка 440, поля Email/Пароль (глаз, «Забыли пароль?»), «Запомнить меня», кнопка «Войти» с состоянием загрузки, плашка ошибки входа, юридическая строка, переход на регистрацию, подвал и баннер.
- Ошибка входа не раскрывает, что именно неверно. Фокус на первое невалидное поле. Имена полей/роутов/CSRF — прежние.

## Stage 3 — страница регистрации
- Вёрстка SPEC §2, §5: карточка 520, компания, «Как вы продаёте?» (две карточки-радио), email, пароль + индикатор и правила, два отдельных обязательных согласия, отдельное необязательное согласие на рассылку (выключено по умолчанию), юридическое примечание, кнопка, плашка «email уже зарегистрирован».
- Правила пароля в интерфейсе **совпадают с серверными**; если серверные отличаются — приведи подсказки к серверным и отметь в отчёте. Согласия проверяются на сервере; дата и версия принятых документов сохраняются так, как сейчас (если сейчас не сохраняются — вопрос владельцу).
- Экран после отправки — по реальному потоку подтверждения email проекта (SPEC §5 «После отправки»).

## Адаптив и доступность
1440 / 1280 / 1100 / 390 (карточка на всю ширину без radius ≤560). Label у каждого поля, `role=alert` для ошибок, `fieldset/legend` для радио, фокус-кольца, `prefers-reduced-motion`, контраст ≥ 4.5:1, навигация с клавиатуры, баннер cookie доступен с клавиатуры.

## Бэкенд-правила (CLAUDE.md, обязательно)
Контроллер — только HTTP in/out; бизнес-логика не в шаблонах; `strict_types`; baseline PHPStan только уменьшается; legacy — HIGH-LOCAL, тесты минимум по правилам. Rate limit/брутфорс-защиту входа не ослаблять.
