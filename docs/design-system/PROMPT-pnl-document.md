Работай по `AGENTS.md`, `CLAUDE.md`, `CLAUDE.frontend.md`. Начни со Stage 0 (аудит) и короткого отчёта; код — после. Правила DS — `docs/design-system/sheets/` (Tokens, Controls, Table, Money, Feedback), планы `docs/plan/ds-legacy-tabler-audit.md`, `docs/plan/ds-dds-operation.md` (если есть), `docs/plan/entity-picker.md`.
Эталон — пакет: `docs/design-system/PNL-DOCUMENT-SPEC.md` (**прочитай целиком**), `screens/PnlDocument.dc.html`, `screens/PnlDocumentNew.dc.html`, `screens/pnl-refs/*.png`, `components/dds-tree-picker/*` (эталонные CSS/JS/Twig виджета дерева). Критерии готовности — `CHECKLIST-pnl-document.md`.

## Цель
Страницы «Документ ОПиУ» (редактирование) и «Новый документ ОПиУ» (создание) оформляются по макету, а также:
1. в шапку добавляются **Проект** и **ЦФО**, которые автоматически подставляются в операции документа, но в операции их можно изменить (SPEC §4.1);
2. у каждой операции документа появляется поле **«Описание»** (SPEC §5.2);
3. выпадающий список «Статья ОПиУ» заменяется виджетом **«Категория ОПиУ»** — выбор листа дерева (до 4 уровней групп) с поиском, по аналогии с «Статьёй ДДС» (SPEC §5.3).

## Рамки
- Только legacy-слой: `templates/_layout/legacy.html.twig`, Tabler, токены `--vf-*`, `legacy-app.css/js`. Не трогать `_layout/app.html.twig`, `assets/react/**`, `site/ui-kit/`; не брать их за образец.
- Роуты, имена роутов, имена полей формы, CSRF, `data-*`-хуки, существующие тесты — не менять. Серверная валидация — источник истины.
- Схему БД/миграции не менять без явной необходимости и согласия владельца. Для «Описания» операции и хранения Проекта/ЦФО шапки действуют решения SPEC §8: **не изобретай** — выбери безопасный вариант (рекомендации в SPEC) или вынеси вопрос в отчёт.
- Прототипы — не код: не копируй их разметку. Берёшь размеры, тексты, состояния, поведение. Демо-данные и нерабочие пункты («Дублировать», «Выгрузить JSON», «История») переноси только если есть бэкенд.
- Виджет дерева из пакета ДДС переиспользуй (не плодить второй). Если он ещё не в проекте — внеси его как отдельный PR 1 по `PROMPT-dds-operation-edit.md` Stage 1 либо адаптируй из `components/dds-tree-picker/*`.

## Stage 1 — виджет «Категория ОПиУ»
- Провайдер дерева статей ОПиУ (Facade/сервис модуля справочников) → `[{id,name,children}|{id,name,flow}]`; id листа == value option; один запрос на страницу; фильтрация по `company`; дерево отдаётся один раз и используется всеми строками.
- Виджет работает **в нескольких экземплярах** (строка = экземпляр), инициализируется для строк, добавленных динамически и продублированных; direction-source каждой строки — её собственный select типа операции. Поле обязательное → в select есть пустая option «Выберите категорию»; под полем виден путь выбранной категории.
- Поведение — SPEC §5.3: только листья; 4 уровня; направляющие линии; поиск; ↑ ↓ Enter Esc; фильтр по типу + «Показать все»; сброс несовместимой категории с заметкой; ARIA; без JS — обычный select.
- Тесты: адаптируй `dds-tree-picker.e2e.js` (несколько экземпляров, динамическая строка); unit-тест провайдера (вложенность, `flow`, изоляция по компании).

## Stage 2 — форма редактирования
- Вёрстка SPEC §3–§5: шапка с Проект/ЦФО, таблица операций (колонки, вторая строка «Описание»), правая колонка (сверка, история), sticky-панель, модалки, `beforeunload`.
- **Наследование Проекта/ЦФО (SPEC §4.1) — на клиенте**, без новых флагов в БД: «изменён» = значение отличается от значения шапки; смена шапки обновляет только наследующие строки; уведомление «подставлен в N из M»; ссылка «Как в шапке».
- Начальное значение шапки при открытии существующего документа — по решению SPEC §8.1.
- «Описание» операции — поле формы (имя поля по соглашению проекта), сохраняется вместе с операцией; если в модели нет — не придумывай колонку молча: отчёт + вопрос.
- Валидация/сводка/фокус; сверка с основанием; блокировка сохранения при расхождении (текущая логика).
- Адаптив 1440/1280/1100/390 (мобильная таблица-карточки — SPEC §5.5).
