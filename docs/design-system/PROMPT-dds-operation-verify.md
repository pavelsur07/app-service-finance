# Промпт приёмки: проверка готовности переноса дизайна «Операция ДДС» + «Статья ДДС»

Ты — независимый ревьюер, **код не меняешь**. Работай по `AGENTS.md`, `CLAUDE.md`. Задача: проверить, что реализация в этом репозитории соответствует эталону из `docs/design-system/` (`DDS-OPERATION-SPEC.md`, `screens/*.dc.html`, `screens/dds-refs/*.png`, `components/dds-tree-picker/*`) и закрывает `CHECKLIST-dds-operation-edit.md`.

## Как проверять
1. `git diff <base>...HEAD --stat` и список изменённых файлов: убедись, что не тронуты `_layout/app.html.twig`, `assets/react/**`, `site/ui-kit/`, роуты/имена полей/CSRF/миграции (пункты раздела A).
2. Статический обзор: Twig-шаблон страницы, partial виджета, CSS/JS, FormType, контроллер, провайдер дерева, тесты. Ищи: хардкод цветов, inline-стили с динамикой, запросы в цикле Twig, отсутствие фильтра по `company`, `innerHTML` с данными, нерабочие элементы, потерянные `data-*`-хуки.
3. Запусти приложение (или статические страницы) и сними скриншоты состояний 01–12 в 1440 и 1280, 390 для мобильного. Сравни с `dds-refs/` попиксельно «на глаз»: отступы дерева (22 px, направляющие), высоты полей (36), цвета бейджей, текст ошибок, подписи. Различия опиши с координатами/селекторами.
4. Выполни сценарии в браузере (Playwright/Chromium или вручную): выбор только листа; клик по группе не выбирает; поиск «цех» раскрывает цепочку и подсвечивает; ↑ ↓ Enter Esc; клик вне; смена направления сбрасывает статью и показывает заметку; сохранение отправляет значение select; ошибки валидации + фокус; модалка ухода; удаление; выписочный вариант; Tab-обход; `prefers-reduced-motion`.
5. Прогони гейты: `make site-stan`, `make site-cs-check`, `make site-cs-strict-types`, `make site-test-unit` / `site-test`, `npm run lint`, `npm run build`, `npm run check:ui-kit`. Для PHPStan при коде 137 повтори с `--memory-limit`; если нельзя — пиши «не прогнан».
6. Для запросов страницы сравни количество SQL «до/после» (профайлер); N+1 в дереве недопустим.

## Формат отчёта (`docs/plan/ds-dds-operation-review.md`)
1. **Вердикт**: «Готово к релизу» / «Готово с замечаниями» / «Не готово» + одна фраза почему.
2. **Таблица чек-листа**: пункт → ✅/⚠️/❌ → доказательство (файл:строка, скриншот, вывод команды).
3. **Блокеры (⛔)** отдельным списком с точным местом и предлагаемым исправлением.
4. **Расхождения с эталоном** (дизайн): элемент, ожидаемое значение из спеки, фактическое, файл/селектор.
5. **Риски и открытые вопросы** (SPEC §7) — какие решения приняты в коде и где.
6. Скриншоты «эталон vs факт» для каждого расхождения.

Правила: ничего не додумывай; если пункт нельзя проверить (нет данных, не запускается) — отметь «не проверено» и причину. Не помечай ✅ без доказательства.
