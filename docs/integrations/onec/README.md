# Интеграция с 1С:Бухгалтерией предприятия 3.0

Внешняя обработка ВФ_Обмен в базе клиента сама отправляет данные к нам по HTTPS: рукопожатие (параметры базы и справочник организаций) и части пакетов. Мы к 1С не подключаемся. Обработка «тонкая», разбор — на сервере. Контракт — [api-contract.md](api-contract.md), требования к обработке для разработчика 1С — [processor-spec.md](processor-spec.md).

Сейчас сервер принимает и хранит пакеты `kind=invoices` (счета на оплату покупателям и от поставщиков). Разбор счетов, привязка организаций к компаниям в кабинете и перепроведение — следующие этапы.

## Подключить базу

1. Владелец активной компании открывает «Компания → Подключения 1С» (`/onec/connections`) и нажимает «Подключить 1С».
2. Вводит название базы. На экране — адрес рукопожатия и токен. Токен показан один раз, хранится только его SHA-256. Оба значения вставляются в настройки ВФ_Обмен; адрес пакетов — тот же с `/packages` вместо `/handshake`.
3. Обработка выполняет рукопожатие: закрепляет `base_id` за подключением и присылает полный справочник организаций. `support.level` в ответе — совместимость; при `unsupported` пакеты отклоняются (422), пока не будет рукопожатия поддерживаемой версией. 409 — токен принадлежит другой базе.
4. Обработка отправляет пакеты. Карточка подключения показывает организации, выгрузки «частей N из parts_total», предупреждения обработки и даёт скачать каждую часть такой, как она пришла.

**Перевыпуск токена** в карточке сразу делает прежний токен недействительным (401) и показывает новый один раз. Отключённое подключение перевыпуском включается снова (статус «Ждёт рукопожатия»). **Отключение** отзывает токен: обработка получает 401. Оба действия, как и создание, пишутся в журнал аудита активной компании с ID пользователя.

Пороги версий — параметры `onec.minimum_config_version` и `onec.minimum_processor_version` в `site/config/services.yaml`. Пустое значение — порога нет. Семейство и редакция проверяются всегда.

## Как хранятся пакеты

- Каждая часть сохраняется байт-в-байт, сжатая gzip, через общий `Shared\Service\Storage\ObjectStorageInterface`. Путь — `onec/{connection_id}/{package_id}/{part}-{sha256}.json.gz`. На проде драйвер `s3` (timeweb, регион `ru-1`), локально и в тестах — `local`. Хранение бессрочное.
- Метаданные — `onec_package`: подключение, `package_id`, `part`, `parts_total`, `kind`, период, версии конфигурации на момент загрузки, версия обработки, `warnings`, число документов, путь, SHA-256 исходных байтов, размер, статус (`stored`), время приёма.
- Ключ повтора — unique `(connection_id, package_id, part)`. Повтор с теми же байтами получает прежний ответ с `duplicate: true`, с другими — 409. Сначала пишется объект (вне транзакции, путь детерминирован), затем строка через `INSERT … ON CONFLICT DO NOTHING`, поэтому одновременные повторы не дают 500.
- Тело пакета и токен не логируются: `/api/onec/v1/*` вычищается из событий GlitchTip, хранилище логирует только путь.
- Скачать часть может владелец подключения (`/onec/packages/{id}/raw`) и администратор (`/admin/onec/packages/{id}/raw`).

Код — `site/src/OneC`: `ReceivePackageAction`, `PackageEnvelope`, `HandshakeAction`, `ConnectionQuery`. Таблицы — `onec_connection`, `onec_organization`, `onec_package`.

## Владение подключением и привязка организаций (этап 2)

Подключение принадлежит **пользователю**, а не компании: `onec_connection.owner_id` — `User`. В одной базе 1С бывает несколько организаций, и каждая должна попасть в свою компанию сервиса.

Как устроен доступ к компаниям сейчас:

- У компании ровно один владелец — `Company.user`. Подключение создаёт только владелец активной компании, его ID и становится `owner_id`.
- Остальные пользователи работают в компании как `CompanyMember` (статус `ACTIVE`/`DISABLED`) с шаблоном прав `CompanyRole`: карта «модуль → уровень» (`read`/`write`). Доступ считает `ModuleAccessResolver::allowsForCompany()`: владелец компании проходит всегда, участник — по уровню шаблона, компанию в процессе удаления не проходит никто.
- Один пользователь может владеть одними компаниями и быть участником других.

Что из этого следует для привязки организаций:

1. **Куда можно привязать.** Организацию подключения пользователя A — только к компании, где A владелец либо активный участник с правом записи в модуле, к которому отнесена 1С (сейчас `admin`). Проверять через `allowsForCompany()` в момент привязки. Ответ рукопожатия сейчас раскрывает имена только действующих компаний владельца (`CompanyFacade::activeOwnedCompanyNames`) — правило нужно расширить до того же набора.
2. **Привязка не переживает потерю доступа.** Участника отключили или понизили — его подключение не должно продолжать загружать данные в чужую компанию. Нормализация проверяет доступ владельца подключения к компании при каждом проходе; без доступа документы организации пропускаются, сырьё остаётся.
3. **Кто видит подключение.** Карточку, токен и сырьё видит только владелец подключения и администратор. Владелец компании не видит подключение участника, даже привязанное к его компании; данные в компании он видит обычным образом. Общий доступ к подключению — отдельное решение (перенос владения или подключение на уровне компании).
4. **Удаление пользователя** каскадно удаляет его подключения, организации и метаданные пакетов (`ON DELETE CASCADE`); объекты в хранилище остаются. Это надо учесть до того, как нормализованные счета начнут жить в компаниях.
5. **Одна база у разных пользователей.** `base_id` уникален внутри владельца: два участника могут подключить одну базу и привязать одну организацию к одной компании — два источника одних счетов. На этапе 2 такую повторную привязку нужно запрещать.

На этапе 1 роли `CompanyMember` не проверяются: привязок в кабинете нет, `onec_organization.company_id` рукопожатие только сохраняет.

## Проверка после выпуска

Тестовое подключение → рукопожатие → часть пакета curl'ом по контракту → в бакете под `onec/{connection_id}/` лежит объект, в карточке «частей 1 из N», скачанная часть совпадает с отправленной.
