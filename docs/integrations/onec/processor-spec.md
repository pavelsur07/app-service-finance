# Техническое задание на внешнюю обработку «ВФ_Обмен» для БП 3.0

**Заказчик:** сервис «Ваш Финдир». **Исполнитель:** разработчик 1С. **Поставка:** внешняя обработка `ВФ_Обмен.epf` с исходниками для типовой российской конфигурации «Бухгалтерия предприятия», редакция 3.0. Установка и обновление обработки должны сохранять типовую конфигурацию на поддержке. [Описание формата внешних обработок на сайте 1С](https://v8.1c.ru/platforma/vneshnie-obrabotki/).

Пользователь указывает адрес и токен из кабинета «Ваш Финдир», проверяет связь, выбирает период и запускает выгрузку счетов покупателям и счетов от поставщиков. Соединение инициирует 1С по HTTPS. Обработка читает учётные данные и отправляет их в исходном виде настолько, насколько позволяет контракт. Привязками компаний, интерпретацией статусов, поиском контрагентов и перепроведением истории управляет сервер. Обработка не изменяет документы, проводки или справочники клиента.

## Этапы и результат

| Этап | Что сдаёт исполнитель | Где принимаем |
|---|---|---|
| 1. Подключение | Устанавливаемая обработка, форма настроек, постоянный идентификатор базы и рабочая команда «Проверить связь» | Действующий `POST /api/onec/v1/handshake`. Для живой проверки использовать отдельное тестовое подключение владельца |
| 2. Счета | Чтение двух видов счетов, предварительный просмотр, подготовка частей, отправка, возобновление и протокол результатов | На согласованном mock-сервере. Серверный `POST /api/onec/v1/packages` принимает и сохраняет части ([контракт](api-contract.md#приём-части-пакета)); разбор счетов — следующий этап сервера |

MVP запускается вручную. Автозапуск по расписанию, другие редакции и конфигурации, банковские выписки, касса, остатки, ДДС, ОПиУ и профиль выгрузки в поставку не входят. Конкретные релизы платформы и БП указываются по результатам испытаний.

## 1. Настройка и действия пользователя

- **Настройки подключения.** Администратор вставляет полный адрес рукопожатия из кабинета (включая путь) и вводит Bearer-токен в маскированное поле. При повторном открытии формы виден факт настройки. Секрет можно заменить. Хранение общее для подключения этой информационной базы, с ограничением доступа. Исполнитель описывает доступный в целевой поставке 1С способ защищённого хранения и необходимые права.
- **Проверить связь.** Показать серверное время, результат, уровень поддержки, пояснение и список организаций с признаком привязки и названием компании. Если организация не привязана, подсказать обратиться к владельцу кабинета. На стороне 1С сопоставление не выполняется.
- **Подготовить выгрузку.** Поля формы — начало и конец периода включительно, выбор организаций и признак «Включать открытые счета вне периода». Предпросмотр показывает количество по организации и виду счёта, границы окна, дополнительные счета вне окна и предупреждения. Он работает до публикации приёмника счетов.
- **Отправить / продолжить.** Показать отправленные и оставшиеся части, результат по каждой части, ошибки отдельных документов и итог. Отправка доступна только при настроенном приёмнике соответствующего этапа. После потери связи или перезапуска можно продолжить тот же пакет.
- Проверять сертификат HTTPS. Передавать токен только в заголовке запроса к настроенному узлу. Смена узла требует повторного ввода токена. В журнале достаточно времени, типа операции, периода, идентификатора пакета, номера части, HTTP-кода и краткого результата. Токен, полные тела запросов и персональные данные в журнал не выводить.

## 2. Постоянная идентификация базы

Один рабочий экземпляр информационной базы использует один `base_id` в формате UUID. Он одинаков для разных пользователей этой базы и сохраняется после замены EPF, изменения названия подключения и обновления релиза БП. Идентификатор счёта, организации и контрагента берётся из UUID ссылки соответствующего объекта. Из номера документа, ИНН, строки подключения или пути к файлу UUID не вычисляется.

Исполнитель демонстрирует, где хранится или откуда читается `base_id`. Отдельно описывает восстановление той же рабочей базы и создание самостоятельной копии. Полная копия может унаследовать одновременно идентификатор и токен: в таком случае сервер не отличит её по `base_id`. В инструкции для копии предусмотреть отключение обмена до первого запуска, отдельную инициализацию идентификатора и новое подключение с собственным токеном. При конфликте 409 обработка сохраняет прежние настройки и показывает причину.

## 3. Рукопожатие — действующий контракт

Источник истины для JSON, точных лимитов, кодов ошибок и примеров — [контракт API v1](api-contract.md). Отправлять UTF-8 JSON, `Content-Type: application/json`, `Authorization: Bearer <token>`. Адрес из кабинета уже содержит `/api/onec/v1/handshake`.

Передавать `base_id`, внутреннее имя конфигурации из метаданных (`БухгалтерияПредприятия` для БП), версию конфигурации, платформы и обработки, при наличии — синоним конфигурации. Номера версий — числовые компоненты через точку. В `organizations` отправлять **полный справочник организаций базы**, независимо от выбора периода и организаций в форме счетов. Для каждой записи — GUID, наименование, ИНН и КПП при наличии. Двенадцатизначный ИНН физлица исключать до формирования исходящего JSON.

Если права пользователя ограничивают видимость организаций или чтение справочника прервано, отменить отправку handshake и объяснить причину. При невозможности гарантировать полноту под ограниченными правами указать необходимые права в инструкции. Пустой массив отправлять исключительно при подтверждённо пустом справочнике: сервер помечает все отсутствующие организации исчезнувшими.

HTTP 200 требует разбора `support.level`. При `supported` продолжить, при `warning` продолжить с видимым предупреждением, при `unsupported` показать сообщение и остановить выгрузку. Первый валидный handshake закрепляет базу за подключением, в том числе при `unsupported`. Признак `mapped` означает наличие привязки. Действующий ответ не сообщает флаг «загружать», поэтому обработка не может выводить из `mapped=true` разрешение на запись счетов.

## 4. Как читать счета

До реализации отправки изучить метаданные тестовой базы. Подготовить короткую таблицу «вид счёта → объект метаданных → реквизиты → источник статуса и суммы оплаты», указать проверенный релиз. Для каждого вида сверить несколько документов с формой счёта в БП. Имена регистров и наличие реквизитов нельзя считать одинаковыми для всех релизов без проверки.

Основная выборка — все счета выбранных организаций и видов, дата которых попадает в календарное окно базы. Для поля с временем использовать интервал от начала первого дня до начала дня после последнего. В выборку входят оплаченные, частично оплаченные, непроведённые и помеченные на удаление документы. Дополнительные открытые счета вне периода передаются только при включённой опции и согласованном правиле определения открытого счёта; каждый GUID попадает в снимок один раз.

| Поля документа | Требование к значению |
|---|---|
| `guid`, `type`, `number`, `date`, `organization_guid` | UUID ссылки, `customer_invoice` или `supplier_invoice`, исходный номер строкой с ведущими нулями, дата документа, GUID организации |
| `counterparty`, `contract`, `bank_account_guid` | Контрагент — `{guid,name,inn,kpp}`; договор — `{guid,name}` либо null; банковский счёт — только GUID либо null. ИНН/КПП передавать строками; ИНН физлица исключать и здесь |
| `amount`, `vat_amount`, `currency`, `due_date` | Сумма документа в его валюте, НДС и срок оплаты при наличии. Сохранять исходную точность; ноль отличать от отсутствующего значения. Не подставлять RUB по умолчанию |
| `status_raw`, `status`, `paid_amount` | Передать исходное значение статуса и сумму оплаты, если она достоверно относится к данному счёту. Согласованный код — `not_paid`, `partially_paid`, `paid`, `cancelled` либо null. При неизвестном статусе сохранить исходное значение, передать null и предупреждение. Если оплату нельзя установить, передать неизвестное значение по контракту, не записывать ноль |
| `posted`, `deletion_mark`, `comment` | Передавать фактические булевы признаки проведения и удаления. Комментарий — исходное значение при наличии; в фикстурах обезличивать |

Минимум для осмысленного документа — `guid`, `type`, `date`, `organization_guid`, `amount`. При недоступном необязательном реквизите продолжить чтение остальных полей и выдать диагностическое предупреждение. Если документ пропущен из-за ошибки, пометить затронутую область неполной. Отсутствие реквизита «оплачено» само по себе не означает отсутствия платежей. Распределение банковской оплаты между счетами, расчёт по сальдо договора и догадки по тексту платежа в задачу не входят.

## 5. Пакет счетов — проект для согласования с серверной командой

Маршрут — `POST /api/onec/v1/packages`, формат и коды ответа — в [контракте v1](api-contract.md#приём-части-пакета), он источник истины.

1. Сформировать снимок по выбранному периоду и зафиксировать его состав перед первой отправкой. `package_id` — один UUID на выгрузку. Во всех частях одинаковы `base_id`, `kind=invoices`, `processor_version`, `period_from`, `period_to`, `include_open_outside_period`, `parts_total`. Часть содержит `part`, `warnings[]`, `documents[]`. Предложение для mock — нумерация с 1, максимум 500 документов и 10 МиБ сериализованного UTF-8 JSON на часть.
2. Для каждой пары **организация + вид счёта** явно описать полноту выборки внутри периода. Состояния, которые сервер обязан различать: полностью прочитано (включая ноль документов), прочитано частично, область не выбрана. Потеря прав, ошибка запроса, пропущенный документ или прерванное чтение исключают отметку полноты затронутой области. Если корректный снимок при параллельном изменении документов подтвердить невозможно, область остаётся неполной.
3. Пример: счета покупателям прочитаны полностью, найдено 0; запрос счетов от поставщиков завершился ошибкой. Первый результат можно передать как подтверждённый пустой снимок, второй — как неполную выборку с предупреждением. Получение всех частей подтверждает доставку. Основание для серверной сверки отсутствующих счетов даёт только подтверждённая полнота внутри окна. Счета вне окна обновляются по явно переданным документам.
4. Между попытками сохранять неизменные байты неподтверждённых частей и состояние отправки в защищённом хранилище. После тайм-аута или потери ответа повторить тот же `package_id + part` с тем же содержимым. Правки в 1С после подготовки снимка относятся к новой выгрузке. Параллельные нажатия «Отправить» не должны запускать конкурирующие отправки одного подключения.
5. Сейчас ответ — `accepted`, `package_id`, `part`, `status`, `duplicate`; `created`, `updated`, `cancelled`, `errors[]` с GUID и сообщением добавятся с этапом разбора. При принятой части показать ошибки документов, продолжить другие части. Счётчики повторного ответа учитывать в итоге один раз. Завершить пакет после подтверждения всех частей; ошибочные документы показать оператору для разбора.
6. При 401/403 показать причину и остановить отправку. При 409 сверить идентичность базы/пакета. При 413 или 422 сохранить диагностику, исключить автоматический повтор неизменённой ошибки. Исправленная выгрузка получает новый идентификатор; не изменять уже отправленную часть под прежним ключом. При 429 учитывать `Retry-After`; при сетевых сбоях и 5xx использовать ограниченные повторы с возрастающей паузой и ручное продолжение. При отсутствии маршрута на стенде показать, что приём счетов ещё недоступен.

Пример одного документа для mock. Цифры и наименования синтетические. Десятичные строки и даты `YYYY-MM-DD` показаны как предлагаемое представление; значение `status_raw` в реальной выгрузке берётся из проверенного источника БП.

```json
{
  "guid": "29b49210-1111-4000-8000-000000000001",
  "type": "customer_invoice",
  "number": "ТЕСТ-00017",
  "date": "2026-10-12",
  "organization_guid": "23c15967-e31e-49bb-afa7-8441c7784b63",
  "counterparty": {
    "guid": "29b49210-1111-4000-8000-000000000002",
    "name": "Тестовый покупатель",
    "inn": null,
    "kpp": null
  },
  "contract": null,
  "bank_account_guid": null,
  "amount": "1000.00",
  "vat_amount": null,
  "currency": "RUB",
  "due_date": "2026-10-26",
  "status": "partially_paid",
  "status_raw": "Частично оплачен",
  "paid_amount": "400.00",
```

**Решения перед подключением реального приёмника.** Команды 1С и сервера фиксируют в `api-contract.md` представление сумм, валюты, дат и неизвестных значений; правила открытия счёта вне окна; формат полноты и предупреждений; семантику пустого снимка; порядок пересекающихся снимков. Предложение для порядка — сохраняемый в базе монотонный номер выгрузки с правилами восстановления после копирования или отката. UUID пакета и часы рабочей станции для определения старшинства недостаточны. Согласовать также, как обработка узнаёт разрешение организации на загрузку, и подтвердить предельный размер и нумерацию частей.

## 6. Приёмка и комплект поставки

Начать с обезличенных примеров и ожидаемых результатов. Проверки приёмки:

| Сценарий | Наблюдаемый результат |
|---|---|
| Установка и обновление EPF, повтор с другого рабочего места | Одна база сохраняет UUID; токен закрыт от просмотра. Неверный токен даёт понятное сообщение. Другая база с тем же токеном получает 409 |
| В базе две организации, в форме выбрана одна | В handshake обе организации. В выборке счетов только выбранная. При неполных правах handshake с урезанным справочником не отправляется |
| Ответы supported, warning и unsupported, в том числе HTTP 200 с unsupported | Оператор видит причину; при unsupported отправка счетов заблокирована |
| Счёт покупателю на 1 000, оплачено 400; счёт поставщика с иным статусом | Типы и GUID различимы. Суммы и статус сверены с БП. Отдельно проверены неизвестный статус и отсутствие надёжных данных об оплате |
| Распроведение, пометка удаления, оплата после первой выгрузки | В следующем снимке сохраняется GUID и меняются соответствующие поля. Оба флага передаются явно |
| Пустая область, частичная выборка, документ за пределами окна | Из пакета однозначно видно, для какой организации, вида и периода допустима сверка отсутствующих. Документ вне окна не расширяет эту область |
| Выгрузка более 500 документов, потерян ответ на часть, обработка перезапущена | На mock получены все части. Повтор имеет тот же идентификатор, номер и байты. Итоги и документы учтены по одному разу |
| Ошибка отдельного документа, 429, 422 и временный сетевой сбой | Оператор видит проблемный документ и причину, остальные подтверждённые результаты сохраняются. Для 429 выдерживается пауза |
| Обезличивание | В исходящих данных нет ИНН физлиц. В журнале и примерах нет секретов, реальных персональных данных и тел производственных запросов |

Исполнитель передаёт версионированный EPF и редактируемые исходники, инструкцию установки и обновления, порядок настройки прав и восстановления/создания копии базы, таблицу источников полей по проверенным релизам, обезличенные реальные JSON-снимки с эталонами и протокол прогона. Обязательные примеры — покупатель с частичной оплатой, поставщик, распроведение или удаление, пустая и неполная область. В протоколе указать точные версии БП, платформы и обработки, а для каждого сценария — реальный сервер или mock. Итоговое испытание на целевом релизе БП проводит исполнитель с владельцем тестовой базы.
