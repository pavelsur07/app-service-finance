# Интеграция с МойСклад — архитектура

> Проектный набросок. Код не написан, реализация не начата.

## 1. Сначала границы, потом код

Двунаправленность — это не «всё синхронизируется в обе стороны». Это **матрица владения**: у каждой сущности (в идеале — у каждого поля) ровно одна система-владелец. Иначе получаются гонка записи и вечный конфликт-резолвер, который никто не сможет отладить.

| Сущность | Владелец | Направление | Комментарий |
|---|---|---|---|
| Контрагенты | МойСклад | МС → мы | справочник ведут в МС |
| Товары/номенклатура | МойСклад | МС → мы | |
| Заказы покупателя | мы | мы → МС | создаём заказы/отгрузки |
| Платежи (paymentin/out) | МойСклад | МС → мы | ложатся в ДДС |
| Статус заказа | МойСклад | МС → мы | обратно не пишем |

Реально двунаправленная сущность — редкость. Обычно это набор односторонних потоков в разные стороны, и это **сильно** проще. Начинать с 1–2 сущностей, а не со всего справочника.

Отдельно зафиксировать: что делать с сущностью, которой нет на той стороне (создавать / игнорировать / ставить в очередь ручного разбора). Ответ «создавать автоматически в обе стороны» на старте — почти всегда ошибка.

## 2. Куда положить

Один модуль, конкретный, без прослойки «универсальный коннектор». Второй ERP появится — тогда и вынесете общее.

```
src/MoySklad/
  Entity/
    MoyskladConnection.php          companyId, accountId, token(encrypted), enabled
    MoyskladEntityLink.php          мэппинг: companyId, entityType, localId, msId, msUpdatedAt, syncHash, lastSyncedAt
    MoyskladSyncCursor.php          companyId, entityType, direction, lastUpdatedAt
  Enum/
    MoyskladEntityType.php          counterparty, product, customerorder, paymentin...
    SyncDirection.php               inbound|outbound
  Repository/
  Facade/MoyskladFacade.php         единственная точка входа для чужих модулей
  Application/
    Sync/InboundSyncAction.php      тянуть изменения по курсору
    Sync/OutboundSyncAction.php     толкать изменения по курсору
    DTO/                            нормализованные DTO, не сырой JSON МС
  Infrastructure/
    Api/MoyskladClient.php          обёртка над Symfony HttpClient (scoped client)
    Api/Exception/                  MoyskladRateLimitException, MoyskladAuthException
    Normalizer/                     МС JSON ↔ наши DTO — вся грязь живёт тут
    Console/MoyskladSyncCommand.php
  Message/ + MessageHandler/        MoyskladSyncMessage → async_sync
  Controller/                       экран настроек подключения
```

Направление зависимостей — **строго одностороннее**: `MoySklad` знает Facade модулей Counterparty / Cash / Document; они о МоёмСкладе не знают ничего. Никаких `if ($moyskladEnabled)` в доменных Action.

Конфиг: `messenger.yaml` → `App\MoySklad\Message\*: async_sync` (внешние HTTP). `doctrine.yaml`, `routes.yaml` — по шаблону нового модуля.

## 3. Ключевые механики

**Транспорт.** Symfony HttpClient как scoped client (`base_uri`, таймауты, дефолтные заголовки) через `framework.yaml`. Свой HTTP-слой не писать.

**Авторизация.** Не хранить логин/пароль. `POST /api/remap/1.2/security/token` один раз → Bearer-токен в БД зашифрованным. Отдельный служебный пользователь МС — он же потом даёт бесплатный anti-echo (см. ниже).

**Курсоры вместо вебхуков — на старте.** Одна scheduled-команда, обе стороны:

- inbound: `filter=updated>=<cursor>&order=updated,asc&limit=100`, идём страницами, курсор двигаем по последней обработанной записи;
- outbound: наши сущности с `updatedAt > cursor`.

Вебхуки МС не отдают данных — только `meta`-ссылку, всё равно нужен GET. То есть вебхук ≠ источник данных, вебхук = триггер «дёрни синк раньше». Добавлять, когда пятиминутная задержка кого-то реально начнёт раздражать, не раньше.

**Идемпотентность.** У сущностей МС есть поле `externalCode` — писать туда наш UUID. Это даёт поиск `filter=externalCode=<uuid>` и защиту от дублей при ретрае без дополнительной логики. `MoyskladEntityLink` — локальный индекс поверх этого, а не единственный источник правды.

**Защита от петли.** Наша запись → МС меняет `updated` → следующий inbound тянет её обратно → мы пишем снова → бесконечный цикл. Лечится одним полем: `syncHash` — хэш нормализованного payload последней успешной синхронизации. Пришло то же самое — пропускаем. Работает в обе стороны, не требует разбора `auditContext`.

**Лимиты.** ~45 запросов / 3 сек на аккаунт, не более 5 параллельных. При 429 МС отдаёт заголовок с интервалом — уважать его, а не свой backoff. Массовые операции: `POST` массивом (до ~100 объектов за раз) вместо цикла по одному — это разница между «укладываемся» и «постоянный 429».

**Ошибки и уровни логов** (важно, чтобы не засорять GlitchTip): 429 / 5xx / таймаут → `warning` + `RecoverableMessageHandlingException`, ретраим. 401 / 403 / невалидный маппинг → `error` + `Unrecoverable`, нужен человек. Один агрегированный `error` со счётчиком на пачку, не по записи.

**Грабли МоегоСклада, на которые стоит заложиться заранее:**

- даты в API — в таймзоне аккаунта (Москва), не UTC; формат `Y-m-d H:i:s.v`. Курсор хранить в UTC, конвертировать на границе;
- суммы — целые в копейках (×100). Ни одного `float` в нормализаторе;
- `limit` по умолчанию 25, максимум 1000. Забыли `limit` — синхронизировали 25 записей и решили, что всё;
- удаления через `filter=updated` **не приходят**. Ловятся вебхуком DELETE или эндпоинтом аудита. В первой итерации — не удалять у себя, а помечать и показывать списком на разбор;
- `meta.href` — единственный надёжный идентификатор связи между объектами; парсить id из URL, а не изобретать свою схему.

## 4. Что осознанно не делать в первой версии

- **Вебхуки** — курсорный поллинг покрывает. Добавить, когда нужна задержка < 1 мин.
- **Автоматический conflict resolution** — при владельце-на-сущность конфликтов нет. Появятся спорные поля — очередь ручного разбора, не автомерж.
- **Универсальный слой «любая ERP»** — интерфейс с одной реализацией. Выносить при появлении второй.
- **Своя таблица outbox** — Messenger уже outbox с ретраями и failed-очередью.
- **Полный ресинк по кнопке** — только курсор. Кнопку «переcинхронизировать с даты X» добавить, когда впервые поедут данные (а они поедут).
- **Синхронизация остатков в реальном времени** — самая дорогая по лимитам часть. Отдельной задачей, если вообще нужна.

## 5. Порядок работ

1. Подключение + токен + экран настроек + проверка связи (`GET /context/employee`).
2. Inbound одной сущности (контрагенты) с курсором и линками — весь каркас обкатывается на самом безопасном потоке.
3. Inbound второй сущности — проверка, что каркас переиспользуется, а не копипастится.
4. Outbound одной сущности — здесь появляются `externalCode`, `syncHash`, дедуп.
5. Наблюдаемость: последний успешный синк, счётчик ошибок, очередь ручного разбора на экране настроек.

Пункт 5 не откладывать в конец списка «на потом»: интеграция без видимого статуса отлаживается по логам в три часа ночи.
