# Этапы и чек-лист приёмки внешнего MCP для ДДС

Каждый этап принимается по наблюдаемому результату на стенде. Для проверки нужны две компании с разными счетами, сотрудник с правом записи ДДС, подключение только для чтения и подключение с разрешением создавать черновики. Форматы запросов, ответов и ошибок заданы в [контракте v1](contract-v1.md). Общая цель и границы описаны в [ТЗ](TASK.md).

## Этап 1. Доступ к своей компании

**Результат.** Согласованный внешний клиент подключается к компании сотрудника. Каждое действие ограничено разрешениями подключения и текущими правами сотрудника.

**Чек-лист приёмки**

- [ ] Действующее подключение получает каталог разрешённых инструментов. Просроченное или отозванное подключение получает отказ.
- [ ] Подключение только для чтения получает отказ при прямом вызове создания черновика. Дополнительное разрешение на черновики выдаётся с отдельного согласия.
- [ ] Подстановка компании или пользователя в запросе отклоняется. После отзыва у сотрудника прав на ДДС прежнее подключение теряет соответствующий доступ.
- [ ] Административный токен и ключ другого API отклоняются пользовательским MCP.

**Вне этапа.** Административный доступ, выдача новых ролей, изменение тарифов и правил подписки.

## Этап 2. Чтение справочников

**Результат.** Внешняя система может найти свой счёт по названию, узнать его валюту и выбрать статью ДДС по её месту в справочнике.

**Чек-лист приёмки**

- [ ] Для активного рублёвого счёта возвращаются его ID, название и RUB. Активный BTC-счёт также виден со своей валютой. Закрытый для использования счёт отсутствует в выдаче активных счетов.
- [ ] У дочерней статьи указан ID её родителя, у корневой — пустое значение. Поиск по части названия даёт одинаковый результат при смене регистра.
- [ ] На фиксированном наборе все страницы вместе содержат каждую подходящую запись один раз. Поиск без совпадений возвращает пустой список.
- [ ] Разрешение только на счета не открывает статьи. Чужой курсор отклоняется. Счета и статьи второй компании отсутствуют в выдаче.

**Вне этапа.** Создание и изменение счетов и статей, выдача банковских реквизитов, остатков и других справочников.

## Этап 3. Чтение фактических операций

**Результат.** Клиент получает операции за период и может сверить их с реестром ДДС компании по счёту, направлению и статье.

**Чек-лист приёмки**

- [ ] Обе границы периода включены. Период длиннее 366 дней отклоняется. Операции одного дня сохраняют порядок при переходе по страницам. Черновики и удалённые операции в списке отсутствуют.
- [ ] Фильтры по счёту и направлению возвращают только подходящие операции. Каждая сторона перевода показана по своему счёту с признаком перевода. Чужой счёт и отсутствующий счёт дают одинаковую ошибку.
- [ ] При платеже 1 000,00 ₽ с разбивкой 700,00 ₽ и 300,00 ₽ фильтр по первой статье возвращает один платёж на 1 000,00 ₽ с обеими строками. По первой статье с реестром сверяется 700,00 ₽.
- [ ] Если у исторической операции статья только в заголовке, клиент получает одну строку распределения на всю сумму. Если статьи нет, список распределения пуст. Валюта, знак и нулевые исторические суммы передаются как в реестре.

**Вне этапа.** Пересчёт показателей, исправление исторических записей, новые отчёты и изменение существующих фильтров в интерфейсе ДДС.

## Этап 4. Создание черновика и фиксация источника

**Результат.** Один внешний платёж создаёт один черновик со статусом `awaiting_confirmation`. Можно определить компанию, сотрудника, подключение, внешний ID, время получения и источник `mcp`.

**Чек-лист приёмки**

- [ ] Платёж с допустимой датой, активным счётом, направлением и положительной суммой принят. При пропуске валюты берётся валюта счёта. Платёж без статьи принимается. Если статья указана, она подходит для данного направления. Остатки, обороты и число фактических операций совпадают со значениями до отправки.
- [ ] Некорректная дата, закрытый период, нулевая сумма, лишний знак после запятой, JSON-число вместо строки или несовместимая валюта дают отказ. Создание по BTC-счёту отклоняется и при пропущенной валюте. Чужая статья и попытка задать источник вручную также отклоняются. При каждом таком отказе число черновиков остаётся прежним.
- [ ] Два одновременных одинаковых запроса и повтор после потери ответа возвращают один ID. Порядок полей и явная передача валюты счёта вместо значения по умолчанию результат не меняют.
- [ ] Изменение суммы при том же внешнем ID в том же подключении возвращает конфликт и сохраняет исходный платёж. В другом подключении такой внешний ID допустим для отдельного черновика.

**Вне этапа.** Подтверждение оплаты внешней системой, автоматическое проведение, создание перевода между счетами и импорт пачки платежей.

## Этап 5. Подтверждение сотрудником и сквозная приёмка

**Результат.** Владелец черновика может подтвердить оплату или отменить черновик в разделе ДДС. После подтверждения внешний клиент с правом чтения видит одну фактическую операцию с источником `mcp`.

**Чек-лист приёмки**

- [ ] В карточке видны счёт, дата, сумма, валюта, направление, статья (если указана), источник и внешний ID. Подтверждение требует явной отметки сотрудника о факте оплаты. Другой сотрудник с правом записи в этой же компании получает отказ при подтверждении и при отмене чужого черновика.
- [ ] Если период закрыт или право записи отозвано после создания черновика, проведение отклоняется. Устаревшая версия карточки не позволяет провести изменившийся платёж.
- [ ] На стенде передать расход 1 250,00 ₽, повторить запрос и подтвердить платёж в VashFinDir. Клиент находит одну расходную операцию на 1 250,00 ₽. Остаток счёта уменьшается ровно на 1 250,00 ₽. Сохраняются связь с черновиком, исходный внешний ID, автор и время подтверждения. Проверить и два одновременных подтверждения одной версии из двух сеансов владельца, и повтор после ответа. В каждом сценарии создаётся ровно одна операция и происходит одно списание.
- [ ] Второй черновик отменить. Фактическая операция отсутствует, остаток прежний. Повтор исходного запроса после отмены или подтверждения возвращает прежний ID с соответствующим конечным статусом.
- [ ] Ввод через Telegram и действующие черновики сохраняют прежние результаты и источник. Обычный пользователь второй компании не видит ни черновик, ни факт первой компании.

**Вне этапа.** Изменение финансовых формул и других каналов ввода, проведение или отмена фактической операции через MCP.

**Общая приёмка.** Все пункты пяти этапов пройдены на тестовых данных. Запросы и успешные ответы трёх инструментов проверены по схемам v1, ошибки — по контракту. К результату приложены фактические статусы и ID одного подтверждённого и одного отменённого черновика, сумма и остаток до и после, а также результаты проверок повторного запроса и доступа второй компании. В журнале вызова доступны ID вызова и подключения, результат и длительность. Токены и содержимое платежей исключены из журналов. В отчёте о приёмке используются только тестовые данные.
