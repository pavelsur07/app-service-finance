# План подключения внешних MCP-клиентов к ДДС

**Цель** — выпустить три инструмента из [контракта v1](TASK.md) и дать сотруднику завершить обработку черновика в VashFinDir. Symfony обслуживает MCP, Cash отвечает за проверки и проведение. Реализация относится к классу Large. План и схемы поставляются отдельно от реализации.

**Исходная база** — `origin/master` на `d4cefc951`. Изучены `site/src/Cash/Facade/CashFacade.php` (счета, дерево статей), `site/src/Cash/Entity/Transaction/CashTransaction.php` (сумма, разбивки, уникальность импорта) и `site/src/Cash/Application/PaymentIntake/PaymentIntakeAction.php` (владелец, подтверждение, блокировки, источник `payment_intake`). Удаление прежней stdio-заглушки описано в `ARCHITECTURE.md`, версия 2.92. Для новых публичных методов использовать узкие DTO и границы Facade.

**Перед разработкой.** Сверить текущий master и состав модулей. Сверить готовность пользовательского транспорта, OAuth и consent по [плану внешнего доступа](../mcp-access/plan.md). Если они ещё проектируются, согласовать порядок поставки общей части. Решения D1–D3 базового проекта (выдача доступа, поддерживаемые клиенты, подписка) применяются и здесь. Проверить совместимость согласованных клиентов с выбранной версией протокола. На локальном окружении использовать тестового issuer. Зафиксировать baseline действующих тестов `PaymentIntakeTest`, `PaymentIntakeConcurrencyTest`, `TelegramPaymentIntakeTest` и их результат в checkpoint. В каждом этапе записать базовый коммит, сначала выполнить новые тесты на старой реализации, затем реализовать сценарий и повторить проверку.

## Stage 1. Удалённый MCP и чтение (HIGH-LOCAL)

- [ ] 1.1. Контрактный тест Symfony HTTP-клиентом для согласования версии, получения каталога `tools/list` и вызова `tools/call`. Валидировать опубликованные схемы и фактические ответы по файлам v1. Подключить инструменты к общему пользовательскому endpoint в Symfony. Один транспорт и issuer обслуживают весь пользовательский каталог. Сначала публиковать только реализованные инструменты.
- [ ] 1.2. Проверить OAuth discovery, issuer, подпись или introspection, audience, срок токена, отзыв подключения, разрешённый Origin и ограничения частоты. Связать доверенную регистрацию подключения с компанией и пользователем. Проверить отдельный consent на создание черновика, отказ для административного токена, доступ только к разрешённому типу справочника. Тестировать прямой вызов инструмента при отсутствии scope, прав Cash или активного членства.
- [ ] 1.3. Реализовать чтение через CashFacade. В Cash переиспользовать выборки счетов, статей и фильтры реестра. Для операций выбирать страницу уникальных ID, затем загрузить разбивки пакетом. Проверить пустой результат, последнюю страницу, поиск, фильтры, границы периода, две операции с одинаковой датой, перевод, разбивку и исторические строки.
- **Приёмка и проверка.** Функциональные тесты MCP проверяют изоляцию двух компаний, включая чужой курсор и чужие ID. Повтор на фиксированном наборе возвращает стабильные страницы. Без фильтра по статье сверить операции и суммы с реестром. При фильтре сверить сумму совпавших строк разбивки с суммой по статье в UI, отдельно проверить полный платёж в ответе MCP и историческую запись со статьёй только в заголовке. Проверить чтение BTC-счёта и его фактов.

## Stage 2. Черновик и подтверждение в Cash (HIGH-LOCAL)

- [ ] 2.1. Интеграционные тесты для структурированного черновика и миграции. Затем расширить `PaymentIntakeDraft` типизированным путём создания одной строки из входных данных. Задать исходные флаги строки согласно Cash: факт оплаты ещё не подтверждён. Обеспечить непересекающиеся ключи источника и выборки открытых черновиков Telegram и MCP, включая доступ по известному ID. Для этого пути отключить очередь разбора текста и redispatch. Миграцией добавить данные происхождения и уникальность ключа MCP. Старым черновикам сохранить текущий жизненный цикл. До миграции проверить существующие уникальные ограничения и план совместимого развёртывания.
- [ ] 2.2. Добавить в CashFacade создание черновика по доверенному контексту, в MCP опубликовать `create_cash_draft`. Тесты на PostgreSQL с двумя соединениями покрывают одновременный дубль, конфликт содержимого, одинаковый внешний ID разных подключений, потерю ответа, повтор после подтверждения и отмены. После отката частичной записи повтор создаёт один целый черновик.
- [ ] 2.3. Расширить подтверждение в `PaymentIntakeAction`. Использовать существующее создание операции в текущей транзакции, проверку периода и блокировку черновика. Для канала MCP сохранять происхождение до и после проведения. Проверить отмену, гонку двух подтверждений, отзыв прав и закрытие периода между вводом и подтверждением. Регрессия Telegram и текстового ввода покрывает действующий источник `payment_intake`.
- **Приёмка и проверка.** До подтверждения реестр, остатки и обороты совпадают с исходными. После подтверждения существует одна операция со ссылкой на исходную запись и однократным финансовым эффектом. В логах присутствуют ID вызова и подключения, результат и длительность. Токены и содержимое платежа исключены из логов.

## Stage 3. Проверка сотрудником и сквозная приёмка (MEDIUM)

- [ ] 3.1. Через обычный интерфейс ДДС показать владельцу очередь его MCP-черновиков, счёт, дату, сумму, направление, статью, источник и внешний ID. Предусмотреть пустой список, конфликт версии и недоступное подтверждение. Дать сотруднику явно подтвердить факт оплаты. Передать версию при подтверждении и отмене. Использовать серверные правила Stage 2.
- [ ] 3.2. Пройти сценарий реальным MCP-клиентом на стенде с тестовыми данными: прочитать справочник, создать черновик, повторить запрос, открыть в VashFinDir, подтвердить и найти факт через MCP. Повторить для пользователя с правом только на чтение и для второй компании.
- **Приёмка и проверка.** Сотрудник видит происхождение платежа и результат подтверждения. Scope создания даёт право только на черновик. Инструментов проведения, удаления, изменения справочников в публичном каталоге нет.

## Чек-лист сдачи реализации

- [ ] Каждый инструмент принимает и возвращает данные по опубликованным схемам. Обязательные поля, неизвестные аргументы, некорректные даты, нулевая сумма, лишняя точность, JSON-число вместо строки и несовпадение валюты покрыты негативными тестами.
- [ ] Тесты двух компаний, подмены источника, идемпотентности, закрытого периода, истории старых данных и финансового эффекта прошли. Добавлены контрактные проверки повторов с разным порядком полей и эквивалентной валютой.
- [ ] Фасады и контракты отражены в `ARCHITECTURE.md`. Выполнены модульные проверки этапов и итоговые `make site-stan`, `make site-cs-check`, `make site-cs-strict-types`, `make site-test-unit`, `make site-test` и проверки затронутого интерфейса.
- [ ] Выполнены внутреннее и внешнее ревью по AGENTS.md. Для поставки с миграцией подготовлен запрос по `docs/workflow/release.md`. Для промышленного OAuth и изменений инфраструктуры действуют отдельные согласования проекта.
