# Технический план реализации MCP для ДДС

Требования и границы определены в [ТЗ](TASK.md), наблюдаемая приёмка — в [пяти этапах](plan.md), внешний интерфейс — в [контракте v1](contract-v1.md). База ветки — `56252d618`.

## Stage 1. Общий пользовательский доступ (HIGH-LOCAL)

Результат — пользовательский OAuth и MCP-каталог принимают только действующие подключения и применяют актуальные права компании. Зависимость — [проект общего доступа](../mcp-access/TASK.md), решения D1–D3 и выбор authorization server. Общая часть обслуживает инструменты Cash. До её готовности выполняются этапы Cash, которые проверяются независимо в Symfony.

## Stage 2. Справочники (MEDIUM)

- 2.1. Интеграционный тест с двумя компаниями, активным BTC-счётом, архивным счётом, родительской статьёй и поиском.
- 2.2. Company-scoped запросы Cash для страницы счетов и страницы статей. Граница страницы — UUID последней строки, лимит на число записей. CashFacade возвращает скалярные данные.
- Готовность — стабильно возвращаются только записи компании, включая совпадения без учёта регистра и поиск по буквальным wildcard-символам. При подключении общей части проверить отдельные права и защищённый курсор на MCP.

## Stage 3. Фактические операции (HIGH-LOCAL)

- 3.1. Интеграционный тест с разбивкой, исторической статьёй из заголовка, мягким удалением, двумя компаниями и курсором по дате и ID.
- 3.2. Cash выбирает страницу фактов с company scope. Фильтр по статье учитывает строки разбивки и исторический заголовок только при отсутствии разбивки. Разбивки выбираются для ограниченной страницы в том же снимке PostgreSQL.
- Готовность — факты совпадают с контрактом на обоих концах периода, связи проверяются внутри компании, суммы остаются строками. Текущий реестр и отчётные запросы проверяются отдельно как регрессия.

## Stage 4. Черновик и подтверждение в Cash (HIGH-LOCAL)

- 4.1. Интеграционные тесты создания, повторов, конфликта, закрытого периода и двух компаний. Проектирование и тест миграции происхождения и уникальности.
- 4.2. Структурированный ввод в Cash без очереди разбора. Хранение исходных параметров, ключа повтора и происхождения. Подтверждение использует текущие правила Cash в транзакции, отмена оставляет баланс прежним.
- Готовность — черновик сохраняется один раз и не меняет фактические операции. Только подтверждение владельца создаёт одну связанную операцию. Действующий ввод Telegram проходит регрессионные тесты.

## Stage 5. Карточка и сквозная приёмка (HIGH-LOCAL)

- 5.1. Функциональные тесты карточки сотрудника, CSRF, чужих черновиков, устаревшей версии и оплаты. Интерфейс просматривает, подтверждает и отменяет черновики через правила Cash.
- 5.2. Связать JSON-схемы, scopes и инструменты с общим пользовательским MCP. Сквозная проверка по пяти этапам [плана приёмки](plan.md).
- Готовность — согласованный клиент проходит сценарий на стенде. При handoff выполнить гейты AGENTS.md, ревью, зафиксировать результаты и условия выкладки миграции.

Для каждого этапа перед кодом запускаются тесты на прежнем поведении, после изменения — целевые тесты и проверка диффа. `checkpoint.md` фиксирует исходные прогоны, точки остановки и следующий шаг.
