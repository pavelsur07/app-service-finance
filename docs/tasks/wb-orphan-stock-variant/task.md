# Остаток WB без карточки в каталоге

## Симптом

В `inventory_stock_snapshots` есть строки Wildberries с `listing_id IS NULL` и
`mapping_status = 'unmapped'`. Это один вариант одной компании:

| Поле | Значение |
|---|---|
| Компания | `19621cff-b028-45d9-9193-11f47ad9a8b2` |
| `chrtId` (WB size id) | `461725762` |
| `nmId` (WB card id) | `303930179` |
| Период | с 2026-07-13 по сегодня, 38 дней |
| Строк | 114 — по три на день (три статуса остатка) |

## Что говорят данные

Сырой ответ WB по этой позиции (актуальный, из `inventory_raw_snapshots`):

```json
{
  "nmId": 303930179,
  "chrtId": 461725762,
  "quantity": 0,
  "regionName": "Склад WB",
  "warehouseId": -999999,
  "inWayToClient": 1,
  "inWayFromClient": 0,
  "warehouseName": "Склад WB"
}
```

Единственная единица — «в пути к клиенту», и висит она так **56 дней**.

## Почему листинг не находится

Маппинг WB идёт по `chrtId` → `marketplace_listings.marketplace_variant_id`
(`NormalizeInventorySnapshotAction`, ветка Wildberries). Такой записи нет.

Существенно: `RefreshWbListingCatalogAction` тянет **и активные карточки, и корзину**
(`WbProductCardsClient::fetchAll()` + `fetchAllTrash()`), а `normalizeVariants()`
ничего не отфильтровывает — только валидирует форму. То есть карточки нет **ни в
активных, ни в удалённых** на стороне WB.

Хронология подтверждает, что карточка не «выпала» из нашего каталога, а никогда в
него не попадала:

| Событие | Дата |
|---|---|
| Каталог WB компании создан | 2026-03-27 |
| Последняя запись в каталог | 2026-07-13 19:07:32 |
| Первый день загрузки остатков WB | **2026-07-13** |
| Первый день появления сироты | **2026-07-13** |

Каталог обновлялся в тот же день, за шесть минут до первой сессии остатков — и
среди его 200 вариантов этого `chrtId` не было.

## Влияние на отчётность — нулевое

Это главное, что определяет приоритет.

- `available = 0` — количественный остаток по позиции нулевой.
- Единственная единица в статусе `in_transit_to_customer`, а `ARCHITECTURE.md:2935`
  прямо фиксирует: «Товары в пути в количественный остаток `InventoryFacade` не
  входят». `StockQtyByListingOnDateQuery` фильтрует `status = 'available'`.

Даже если привязать листинг, в отчёт попадёт ноль. **Юнит-экономика от этой карточки
не страдает ни на копейку.**

## В чём тогда проблема

Проблема не в цифрах, а в том, что расхождение между двумя источниками WB —
остатками и каталогом — деградирует в `NULL` и **никак не видно**. Узнать о нём
можно только руками сходив в базу, что и было сделано.

Это ровно тот антипаттерн, который запрещает `CLAUDE.md` в разделе о health-гейтах:

> Неизвестное значение из внешней системы деградирует в видимую очередь на ручной
> разбор (синтетическая «неизвестная» сущность), а не в `NULL`: `NULL` одновременно
> ломает данные и прячет факт поломки.

Сейчас это буквально `NULL`.

Второе: механизм повторится. Сегодня это одна карточка с нулём, завтра — карточка с
реальным остатком, и заметить это будет так же нечем.

# Предложение: шаги на существующих паттернах

Порядок выбран так, чтобы каждый шаг имел ценность сам по себе и ни один не был
предусловием следующего.

## Шаг 1. Сделать расхождение видимым — гейт по свежести

**Откуда паттерн:** `app:inventory:stock-freshness-check` (`src/Inventory/Command/`)
и правила health-гейтов из `CLAUDE.md`.

Read-only команда `app:inventory:unmapped-stock-check`: сколько строк остатка
появилось **непривязанными за окно свежести**. Ненулевой exit code — только на
новые случаи, а не на накопленную историю: «сколько плохих строк появилось в окне
обработки», а не «сколько их всего». Иначе гейт станет вечно красным из-за 445
исторических позиций Ozon, которых нет в каталоге, и обесценится.

Охват равен охвату починки — только компании с активным подключением, как в гейте
свежести. Один агрегированный `error` со счётчиком при провале, не запись на строку.

Переиспользовать существующий предикат: определение «строка не смаплена» уже живёт
в `SessionsToRenormalizeQuery` (`mapping_status IS DISTINCT FROM 'mapped'`). Держать
его в одном месте — прямое требование `CLAUDE.md`, три копии в трёх запросах
разойдутся.

**Ценность сама по себе:** сегодня о таких случаях не узнаёт никто.

## Шаг 2. Дать очереди лицо

**Откуда паттерн:** страница `/marketplace/unmapped` + `UnmappedListingsQuery`
(`src/Marketplace/`), плюс правила пагинации из `CLAUDE.md`.

Отдельная страница «остатки без листинга»: `chrtId`, `nmId`, первый и последний день,
количества по статусам. Query отдаёт `QueryBuilder` для Pagerfanta, `limit` ≤ 200,
обязательный `companyId` в каждом методе репозитория.

**Существующую страницу переиспользовать нельзя** — `UnmappedListingsQuery` фильтрует
`l.product_id IS NULL`, то есть показывает *листинги без товара*. Здесь другая
сущность: *остаток без листинга*. Это разные очереди, и путать их не стоит.

## Шаг 3. Дать явное решение по каждой позиции

Два законных исхода, оба поддержаны архитектурой.

**а) Создать листинг** — через `MarketplaceFacade` → `WbListingResolverService::resolve()`.
Это единственная точка создания WB-листингов, и она уже умеет то, что здесь нужно:
каскад ключей (натуральный `nmId+size` → `chrtId` → баркод) и привязку идентичности
по `chrtId`. Если WB когда-нибудь вернёт карточку, синхронизация каталога найдёт
листинг по `chrtId` и свяжется с ним, а не создаст дубль.

Из выгрузки остатков доступны только `nmId` и `chrtId`; размер неизвестен → `UNKNOWN`,
что и есть собственная конвенция резолвера. Ни названия, ни артикула, ни цены не будет.

**б) Пометить как разобранное** — терминальное состояние, чтобы очередь не росла
известными мёртвыми карточками.

Для (б) есть развилка проектирования: добавлять четвёртое значение в
`StockSnapshotMappingStatus` (сейчас `Mapped`/`Unmapped`/`Ambiguous`) — это изменение
контракта, затрагивающее уникальный ключ и upsert. Либо завести отдельную сущность
`IgnoredStockVariant` в `Inventory` с ключом «компания + источник + sourceSku».
Второе дешевле и не трогает горячий путь нормализации.

## Шаг 4. Починить историю после решения

**Откуда паттерн:** `app:inventory:renormalize-snapshots` — команда уже написана,
проверена и отработала на проде 2026-09-06.

Маппинг замерзает в момент нормализации: ключ upsert включает `snapshot_date`,
поэтому созданный сегодня листинг вчерашние строки не чинит. После создания листинга
достаточно прогнать:

```
app:inventory:renormalize-snapshots --from=2026-07-13 --to=<вчера> --source=wildberries
```

Инструмент есть, отдельной работы шаг не требует.

## Шаг 5. Убрать молчаливый `NULL` в принципе — но осознанно

`NormalizeInventorySnapshotAction` уже создаёт недостающую сущность на лету:
`findOrCreateWbLocation()` заводит склад, если его нет. Листинг — не создаёт.
Асимметрия ничем не обоснована технически.

Сделать её симметричной — значит убрать `NULL` совсем. Но у этого есть цена, и она
продуктовая, а не техническая: авто-созданный листинг не имеет ни названия, ни
артикула, ни цены, а после Stage 2 задачи `inventory-stock-analytics-visibility`
листинги с остатком становятся источником строк отчёта. То есть молчаливый `NULL`
меняется на **видимую строку-призрак в юнит-экономике**.

**Рекомендация: авто-создание по умолчанию не включать.** При нулевом влиянии на
отчёт отслеживаемое исключение лучше, чем безымянная строка в отчёте. Создание
листинга остаётся явным действием человека из очереди шага 3.

# Приоритет

**Низкий, но не нулевой.** Сама карточка не стоит ничего: ноль в остатке, ноль в
отчёте. Стоит внимания механизм — сейчас расхождение между двумя источниками WB
не видно никому.

Если делать, то ради шагов 1 и 2: они закрывают класс проблем, а не эту карточку.
Шаги 3–5 без них бессмысленны, потому что решать будет нечего — очереди не существует.

Наименьший осмысленный объём — **только шаг 1**: одна команда по образцу уже
работающего гейта, без UI и без изменения контрактов.

# Открытый вопрос к Владельцу

Единица «в пути к клиенту» висит 56 дней. Для WB это ненормально: либо доставка
зависла, либо WB не присылает финальное событие. Стоит проверить в кабинете WB, что
с заказом по `nmId 303930179` — возможно, настоящая проблема там, а расхождение в
каталоге лишь её тень.
