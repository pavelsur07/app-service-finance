# pl-category-subtree-levels: уровень потомков статьи ОПиУ при переносе ветки

Источник: Владелец, чат 2026-10-09. На проде у ИП Лазарева в отчёте ОПиУ
«Налоги на ФОТ» показывается группой внутри «Общепроизводственных», хотя
дочерних статей у неё нет. Поручение: «делай оба одним PR» — исправить код и
данные.

Класс: **Large** (миграция с данными). Ветка `fix/pl-category-subtree-levels`
от `master` @ `7c2b8278`. Один Draft PR.

## Причина (подтверждена на данных прода, 2026-10-09)

- Отчёт ОПиУ (`templates/finance/report/preview.html.twig:483`, Excel —
  `PlReportXlsxExporter.php:53`) считает строку группой, если следующая строка
  стоит глубже по `level`. Связь «родитель — потомок» при этом не смотрится.
- `PLCategory::setParent()` пересчитывает `level` только у самой статьи.
  Потомки сохраняют старый уровень. Так происходит на обоих путях смены
  родителя: форма `PLCategoryController::edit` и `ImportPLCategoryTreeAction`.
- У ИП Лазарева группу «Общепроизводственные» перенесли в корень (уровень 1),
  а 8 её дочерних статей остались на уровне 3. «Налоги на ФОТ» создали позже,
  у неё правильный уровень 2. Она стоит по `sort_order` перед статьёй с
  уровнем 3, поэтому отчёт выделяет её как группу.

## Замеры «до» (прод, read-only, 2026-10-09)

- `pl_categories`: 325 строк, все достижимы от корней (циклов нет), максимальная
  фактическая глубина 3, межкомпанийных ссылок на родителя 0.
- `level <> фактическая глубина`: **11 строк**, 2 компании:
  - ИП Лазарева (`3f4d87cc-…`): 8 детей «Общепроизводственные» (OVERHEAD_PROD_*),
    `level` 3, должно быть 2.
  - Ваш ФинДир (`1bc282b2-…`): 3 ребёнка «Прямые затраты услуг CFO»,
    `level` 2, должно быть 3.

## Stage 1 — код (HIGH-LOCAL: инвариант дерева, финансовый отчёт)

DoD: после смены родителя у всех потомков `level = level родителя + 1`;
ветка, которая уйдёт глубже 5 уровней, не принимается; экран редактирования
не предлагает родителя, при котором ветка выходит за предел.

- 1.1 Регрессионные тесты: unit на сущность (перенос в корень, перенос глубже,
  выход потомка за предел), functional на `edit` (сценарий прода, фильтр
  родителей). Доказать красными на старом коде.
- 1.2 `PLCategory::setParent()` каскадно пересчитывает уровень потомков,
  `getSubtreeHeight()`; `edit` фильтрует родителей по высоте ветки.

## Stage 2 — данные (HIGH-LOCAL: миграция)

DoD: миграция пересчитывает `level` по фактической глубине для всех строк, где
он расходится. `down()` возвращает 11 снятых значений.

- 2.1 Миграция и интеграционный тест на её SQL.
- 2.2 Прогон на локальной БД, сверка.

## Границы

- Отчёт по-прежнему определяет группу по `level` соседней строки: после
  исправления данных и кода этого достаточно. Перевод отчёта на связь
  «родитель — потомок» — FOLLOW-UP, не здесь.
- Промежуточное состояние импорта: импорт проверяет глубину итогового дерева,
  а каскад срабатывает на каждом `setParent()`. Если узел переносится глубже,
  а его глубокий потомок будет вынесен из него позже в том же импорте,
  возможен ложный отказ. На проде максимальная глубина 3, лимит 5. Это
  FOLLOW-UP.
