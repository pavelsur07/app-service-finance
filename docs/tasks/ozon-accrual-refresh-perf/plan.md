# ozon-accrual-refresh-perf — ускорение обновления метаданных статей Ozon by-day

> Статус: план, к работе не принят. Модуль — Ingestion
> (`RefreshOzonAccrualCategoryMetadataAction`, `OzonAccrualByDayMapper`,
> `FinancialTransactionRepository`). ОПиУ, Marketplace и Cash не затрагиваются.

## 1. Проблема

### Симптом

18.10.2026 ремонт истории после #2717 (`app:ingestion:ozon-accrual:daily-maintenance
--from=2026-05-17 --to=2026-10-17 --execute`) шёл по одной компании больше часа:

| Компания | Транзакций by-day | Затронуто правкой | Время `--execute` |
|---|---|---|---|
| 3f4d87cc | 17 928 | 2 526 | ~2 мин |
| 19621cff | 70 279 | 16 222 | ~7 мин |
| 78f0cc9f | 159 164 | 18 632 | ~20 мин |
| b57d7682 | 915 357 | 124 800 (обновлено 134 338) | ~90 мин |

Изменилось ~125 тыс. строк, но просмотрено ~2,5 млн: около 2 мс на одну проверку.
Команда ничего не печатает до конца, поэтому терминал выглядит зависшим.

### Причины (по коду и замерам прода)

1. **Обновление не учитывает `selected_dates`.** `OzonAccrualRawCoverageSelector::selectLatest()`
   выбирает для каждого дня самую свежую выгрузку и кладёт эти дни в
   `selected_dates`. `RefreshOzonAccrualCategoryMetadataAction::refresh()`
   (`site/src/Ingestion/Application/Action/RefreshOzonAccrualCategoryMetadataAction.php:125`)
   читает и разбирает выгрузку **целиком**, по всем её дням. Окна выгрузок
   перекрываются, поэтому каждая транзакция проверяется в среднем 2,7–2,9 раза
   (dry-run: 3f4d87cc — 50 894 совпадения на 17 928 строк; 19621cff — 190 058 на 70 279).
   Другие команды фильтр соблюдают: `OzonAccrualNormalizeStoredCommand.php:132`,
   `OzonAccrualVerifyRollingRefreshCommand.php:343`, `OzonAccrualCompareCommand.php:389`.
   Побочный эффект: один запуск может записать одной строке метаданные из более
   старой выгрузки, если описание операции в ней отличалось (`description` берётся
   из строки выгрузки). Это надо проверить отдельно.
2. **На каждую строку отдельный запрос (N+1).** `findByNaturalKey()` делает один
   `SELECT` через ORM на каждую `MappedTransaction` (`:139`), затем гидрирует
   сущность и декодирует `source_data` (~880 байт jsonb). Индекс
   `uniq_ftx_natural_key` используется, кэш индексов 99,55%, сам запрос дешёвый.
   Время уходит на ~2,5 млн обращений к БД и гидрацию.
3. **Нет отбора по тому, что могло измениться.** Чтобы поправить статьи шести
   типов Ozon, команда сверяет все типы. Отфильтровать заранее нельзя:
   метаданные вычисляются из сырой строки текущим каталогом.
4. **Разбор выгрузки собирается в массив.** `OzonAccrualByDayMapper::mapRows()`
   возвращает `list<MappedTransaction>`, а не генератор. Комментарий в Action
   говорит об обратном. По памяти это укладывается в лимит (OOM-задача
   `ozon-accrual-refresh-oom`), но держит в памяти всю выгрузку сразу.
5. **Дорогая запись.** Обновлений без HOT-оптимизации почти нет:
   4,8 тыс. HOT на 14,25 млн обновлений за жизнь таблицы. `fillfactor` по
   умолчанию (100), поэтому каждое обновление пишет новую версию строки и
   вставку во все 8 индексов. Таблица 2,4 ГБ (heap 1,9 ГБ) при
   `shared_buffers = 1GB`, кэш heap 76%. После ремонта ~173 тыс. мёртвых строк.
6. **Нет прогресса в выводе.** Итог печатается только в конце, по ходу
   работы ничего не видно.

### Чем это мешает

- Ремонт после правки каталога (повторяется при каждом расширении словаря
  Ozon) занимает часы на крупной компании и держит транзакцию на выгрузку.
- Ночной `daily-maintenance --days-back=45` (cron 05:15) делает ту же работу
  с тем же перекрытием. Его длительность сейчас не замерена (Stage 0).
- Нагрузка на БД (запись во все индексы, мёртвые строки) пропорциональна
  числу просмотров, а не числу реальных изменений.

## 2. Цель и метрики

| Метрика | Сейчас | Цель |
|---|---|---|
| Просмотров на одну транзакцию | 2,7–2,9 | 1,0 |
| Запросов к БД на 1000 просмотров | ~1000 | ≤ 2 |
| Ремонт b57d7682 за 5 месяцев | ~90 мин | ≤ 10 мин |
| Ночной `daily-maintenance` по всем компаниям | не замерен | замерен, −70% |
| Записи при отсутствии изменений | 0 | 0 (сохранить) |
| Результат (какие строки и как обновлены) | — | идентичен текущему |

## 3. Решение — бэст практики

1. **Обрабатывать только выбранные дни.** Передать `selected_dates` из строки
   покрытия в `refresh()` и отбрасывать строки выгрузки вне этих дней до
   маппинга. Тот же контракт уже есть у `normalize-stored`, включая отказ
   работать с выгрузкой без `selected_dates` (`LogicException`). Это убирает
   перекрытие ×2,8 и неоднозначность «какая выгрузка победила».
2. **Пакетный поиск вместо N+1.** Разбирать выгрузку потоком и группировать
   `MappedTransaction` в порции по 1000–5000. На порцию — один запрос по
   естественному ключу: `company_id = :c AND source = :s AND (external_id, type)
   IN (...)` или `external_id IN (...)` с фильтром типа в PHP. Индекс
   `uniq_ftx_natural_key` покрывает оба варианта. Образец порционного `IN` по 5000 —
   фикс OOM сверки (`OzonAccrualListingRelinker`, память `ozon-reconcile-oom`).
3. **Сравнивать без гидрации.** Для проверки отличий тянуть только `id`,
   `external_id`, `type`, `description` и нужные ключи `source_data`
   (`source_data->'_ozon_category_code'` и т. д.) через DBAL-Query. Сущность
   загружать только для строк, которые действительно меняются (~5% просмотров).
   Ещё дешевле — точечный `UPDATE ... SET source_data = source_data || :patch`
   пачкой через DBAL, если Владелец согласует обход ORM. Иначе
   оставить `replaceSourceDataFields()` на сущности, загруженной `findByCompanyAndIds()`.
4. **Генератор в маппере.** `mapForCategoryMetadataRefresh()` отдаёт
   `iterable<MappedTransaction>`: память — одна порция, а не вся выгрузка.
   Комментарий в Action станет правдой.
5. **Прогресс и наблюдаемость.** Строка INFO на каждую выгрузку (компания,
   выгрузка, дни, просмотрено/обновлено, мс), итог по компании с длительностью.
   В `--execute` без `--quiet` — прогресс-бар Symfony Console. Для ночного cron —
   длительность в итоговом логе, чтобы сравнить «до/после».
6. **Опционально: ускорить запись в БД** (отдельная миграция, HIGH-LOCAL):
   `ALTER TABLE ingest_financial_transactions SET (fillfactor = 90)`. Действует
   на новые страницы сразу, на старые — после `VACUUM FULL`/`pg_repack`, который
   отдельно не делаем. Рассмотреть только по замеру Stage 3: после пп. 1–3 записей
   станет в разы меньше, и выигрыш может не окупить рост таблицы на ~10%.
7. **Не делать:** параллельный запуск по компаниям в одном процессе, отключение
   индексов, `SET synchronous_commit = off` — выигрыш не стоит риска, причина
   медленности в объёме лишней работы, а не в БД.

## 4. Этапы

### Stage 0 — замеры «до»

- **Задача:** зафиксировать базу для сравнения.
- **Результат:** `measurements/before.md` — длительность ночного
  `daily-maintenance` за 3 дня (лог cron или итог команды), dry-run по
  b57d7682 за 45 дней с `time`, число просмотров/совпадений/обновлений.
- **Выполнено, когда:** цифры сняты на проде read-only (dry-run).
- **Чек-лист:** [ ] длительность ночного прогона; [ ] dry-run 45 дней по
  крупной компании с временем; [ ] коэффициент перекрытия по всем компаниям.

### Stage 1 — только выбранные дни

- **Задача:** `refresh()` обрабатывает строки выгрузки только за её
  `selected_dates`.
- **Результат:** просмотров на транзакцию 1,0; выгрузка без `selected_dates`
  отвергается, как в `normalize-stored`.
- **Выполнено, когда:** регрессионный интеграционный тест (две перекрывающиеся
  выгрузки → каждая транзакция просмотрена один раз, метаданные из победившей
  выгрузки) красный на старом коде и зелёный на новом.
- **Чек-лист:** [ ] тест перекрытия; [ ] тест отказа без `selected_dates`;
  [ ] dry-run на проде: `scanned ≈ число транзакций`, `updated` = числу реально
  отличающихся строк; [ ] проверено, что описание не «скачет» между выгрузками.

### Stage 2 — пакетный поиск и сравнение без гидрации

- **Задача:** убрать N+1 и лишнюю гидрацию.
- **Результат:** новый метод репозитория (или Query) с `string $companyId`,
  порции 1000–5000; генератор в маппере; сущности грузятся только для изменений.
- **Выполнено, когда:** тест на порцию (число запросов к БД на 5000 строк — константа,
  через DBAL-логгер или счётчик), результат идентичен Stage 1 на одном наборе данных.
- **Чек-лист:** [ ] IDOR: метод принимает `companyId`, `RepositoryCompanyScopeRule`
  зелёный; [ ] `flush()`/`clear()` только в Action каждые N; [ ] пик памяти не вырос
  (замер на крупной выгрузке); [ ] `ARCHITECTURE.md` — Changelog.

### Stage 3 — наблюдаемость и замеры «после»

- **Задача:** прогресс в выводе и логах, сравнение с Stage 0.
- **Результат:** INFO по выгрузке и компании с длительностью; `measurements/after.md`.
- **Выполнено, когда:** dry-run b57d7682 за 5 месяцев ≤ 10 мин, ночной прогон
  укоротился, выводы по `fillfactor` записаны (делать / не делать).
- **Чек-лист:** [ ] метрики раздела 2 сняты; [ ] `verify-rolling-refresh` не
  изменил статус; [ ] решение по п. 6 записано в handoff.

## 5. Риски

- **Изменится состав обновлений.** После Stage 1 метаданные строки берутся
  только из победившей выгрузки дня. Сейчас победителем фактически становится
  последняя по порядку обработки. Проверить на проде dry-run'ом, что набор
  отличающихся строк совпадает или расхождение объяснимо.
- **Длинная транзакция на выгрузку.** Сейчас транзакция на выгрузку целиком.
  Вариант — коммит на порцию; тогда повторный запуск обязан быть идемпотентным
  (уже так: неизменные строки пропускаются).
- **Обход ORM при пакетном `UPDATE`.** Повышает скорость, но требует явного
  согласования и теста, что `updated_at`/`version` пишутся так же, как через сущность.

## 6. Вне задачи

- Строки `type = 'other'` у типов 46/76/77/84 (остаток #2440).
- Перенос `description` словаря Ozon в справочник (следующая задача по статьям).
- Настройка `shared_buffers`/памяти БД — решение по инфраструктуре, не по коду.
