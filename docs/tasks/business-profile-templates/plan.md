# Профиль бизнеса и шаблоны онбординга — план

Статус: в работе Stage 1–2, ветка `feat/business-profile`. Дата: 2026-10-20. Ход — `checkpoint.md`.
Класс: Large (миграция, новое поле Company, шаблоны в Finance и Balance, формы).
Основа — онбординг новой компании (PR #2746, `docs/tasks/company-onboarding/`).

## 1. Задача

Сейчас любая новая компания получает один набор стартовых справочников, и он целиком
сделан под продавцов на маркетплейсах: дерево ОПиУ `config/finance/default_pl_tree.json`
(СПП, комиссия МП, ФФ, CM1–CM4, ДРР) и структура Баланса
`config/balance/default_structure.yaml` («Маркетплейсы, к выплате», товар на складах МП).
Для бизнеса без маркетплейсов этот набор лишний.

Нужно:

1. Ввести у компании **профиль бизнеса** `businessProfile` с двумя значениями:

   | Значение | Название в интерфейсе | Кому |
   |---|---|---|
   | `MARKETPLACE` | Маркетплейсы и e-com | продавцы на маркетплейсах и в интернет-магазине |
   | `UNIVERSAL` | Базовый | любой другой бизнес |

2. Спрашивать профиль **при регистрации** («Как вы продаёте?»); значение по умолчанию —
   `MARKETPLACE`.
3. Выбирать стартовые шаблоны ОПиУ и Баланса по профилю.

## 2. Результат

- Поле `Company::$businessProfile` (enum `BusinessProfile`), у всех существующих компаний —
  `MARKETPLACE` (они получили или получат маркетплейсный шаблон).
- Вопрос в форме регистрации; то же поле в `/company/new` и в создании аккаунта через
  админку; смена профиля в настройках компании.
- `CompanyCreatedEvent` несёт профиль; подписчики Finance и Balance берут шаблон по профилю.
- Шаблоны по профилям: `config/finance/pl_templates/{marketplace,universal}.json`,
  `config/balance/templates/{marketplace,universal}.yaml`; единый словарь кодов, тест его
  согласованности.
- Ручное применение шаблона с выбором профиля («Применить шаблон…», режим «добавить
  недостающее»).
- В аудите записано, какой шаблон какой версии получила компания.

## 3. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Наложение «база + расширение» или полные шаблоны | Полные шаблоны на профиль | У профилей разные итоги и формулы (CM1–CM4/ДРР против валовой прибыли); слияние формул при наложении хрупкое |
| Как держать шаблоны согласованными | Единый словарь кодов: одинаковый смысл — один код с теми же типом и направлением потока; тест | Дашборды и KPI читают коды; маппинги маркетплейсов ищут статьи по коду; переход Базовый → Маркетплейсы — импорт «добавить недостающее» по коду |
| Где хранится профиль | Company (`businessProfile`), передаётся в `CompanyCreatedEvent` | Подписчики не обращаются к Company за профилем; Company не знает о шаблонах |
| Смена профиля | Разрешена, шаблоны заново не применяются | Дерево пользователя уже настроено; дополнить — явное действие «Применить шаблон…» |
| Приглашённый пользователь | Вопроса нет | Регистрация по приглашению не создаёт компанию |
| Значение по умолчанию | `MARKETPLACE` | Основная аудитория продукта; лишнего шага для неё нет |
| ДДС | Без профиля | Системные статьи ДДС одинаковы для всех |
| Денежные счета, проект, ЦФО | Без профиля | Нужны любому бизнесу |

**Решает Владелец до Stage 3** (финансовая семантика, агент её не придумывает):
содержание универсального дерева ОПиУ и структуры Баланса — набросок в §5.

## 4. Этапы

Каждый этап начинается с `stages/stage-N.md` (задача, результат, что считаем выполненным,
чек-лист приёмки). Этапы — локальные коммиты, push и PR — одним шагом на handoff.

### Stage 1. Профиль бизнеса в Company

Риск: HIGH-LOCAL (миграция, формы регистрации и создания компании).

1. Enum `App\Company\Enum\BusinessProfile`: `MARKETPLACE`, `UNIVERSAL`, метод `label()`.
2. Миграция: `companies.business_profile VARCHAR(32) NOT NULL DEFAULT 'MARKETPLACE'`.
   Существующие строки получают `MARKETPLACE` — это совпадает с тем, что они получили.
   Обратимая (down — drop column). Замер «до»: число компаний.
3. Entity `Company`: поле с значением по умолчанию `MARKETPLACE`, `getBusinessProfile()`,
   `changeBusinessProfile()`.
4. `CompanyCreatedEvent(companyId, businessProfile)`; оба места диспатча передают профиль.
5. Пути создания:
   - `RegistrationFormType`: поле `businessProfile` (`EnumType`, `expanded: true`, две
     карточки с описанием, по умолчанию `MARKETPLACE`), только без `is_invite`;
     `RegistrationController` передаёт значение в `CreateCompanyOwnerAccountAction`;
   - `CompanyType` (`/company/new` и редактирование): то же поле;
   - `CompanyFacade::createOwnerAccount()` и `Admin\CreateAccountAction`: параметр профиля
     с умолчанием `MARKETPLACE`, поле в форме админки.
6. Шаблоны: `templates/security/register.html.twig` — блок выбора в стиле DS «Ваш Финдир»
   (`CLAUDE.frontend.md`), подписи и подсказки; `company/new`, форма админки.
7. Тесты: регистрация с каждым профилем сохраняет его; без выбора — `MARKETPLACE`;
   приглашение — без поля; событие несёт профиль; миграция на пустой БД (`migrations-empty-db`).
8. `ARCHITECTURE.md`: Company — поле и событие; `Changelog`.

### Stage 2. Реестр шаблонов по профилю

Риск: MEDIUM. Поведение не меняется: маркетплейсный профиль получает те же шаблоны.

1. Файлы переезжают: `config/finance/pl_templates/marketplace.json`,
   `config/balance/templates/marketplace.yaml`; в шаблоне — `profile` и `version`.
2. Finance: `DefaultPLCategoryTreeProvider::nodes(BusinessProfile)`; `EnsureDefaultPLTreeAction`
   принимает профиль; подписчик берёт его из события.
3. Balance: `BalanceStructureTemplateReader::read(BusinessProfile)`; сид, счета и ленивый сид —
   по профилю компании (ленивый путь читает профиль через `CompanyFacade`).
4. Дозаполнение `app:company:onboarding-backfill`: `CompanyOnboardingBackfillEvent` несёт
   профиль компании.
5. Тест словаря кодов (`tests/Unit/Onboarding/TemplateCodeDictionaryTest` или в Finance):
   код, встречающийся в нескольких шаблонах, везде имеет тот же `type`, `flow`, `format` и тот
   же код родителя; коды маппингов маркетплейсов (`config/marketplace/*.yaml`) есть в
   маркетплейсном шаблоне (сейчас — `DefaultPLCategoryTreeProviderTest`).
6. Аудит применения: Finance и Balance пишут, какой шаблон и версию получила компания
   (Balance — в `balance_audit_events.changes`; Finance — INFO-лог с `companyId`, профилем,
   версией; отдельная таблица — только если понадобится выборка).
7. Тесты: маркетплейсный профиль получает ровно прежний набор (70 статей, 33 статьи и 2 счёта
   Баланса) — регрессия на перенос файлов.
8. `ARCHITECTURE.md`: Finance и Balance — шаблоны по профилю, словарь кодов; `Changelog`.

### Stage 3. Универсальные шаблоны

Риск: HIGH-LOCAL (финансовая семантика). Начинается только с содержанием, утверждённым
Владельцем.

1. Перед копированием — проверить маркетплейсный шаблон: у `PRODUCT_INFRA_TOTAL`,
   `BELOW_EBITDA_INCOME_TOTAL`, `PROFIT_DISTR_TOTAL` и `BELOW_EBITDA_OTHER_INCOME`
   направление потока `NONE`; выяснить, влияет ли это на знак в CM4 и «Чистой прибыли»,
   при необходимости исправить отдельным пунктом с тестом расчёта.
2. `config/finance/pl_templates/universal.json` по утверждённому содержанию; коды — из словаря.
3. `config/balance/templates/universal.yaml`: деньги, дебиторская задолженность, запасы,
   основные средства, капитал, обязательства — без статей маркетплейсов; счета банка и кассы
   на `CASH_BANK`/`CASH_REGISTER` (те же коды).
4. Тесты: шаблоны валидны; словарь кодов согласован; расчёт отчёта ОПиУ по универсальному
   дереву на фикстуре даёт ожидаемые итоги (валовая прибыль, EBITDA, чистая прибыль).
5. Регистрация с `UNIVERSAL` → универсальные дерево и Баланс (сквозной тест).

### Stage 4. «Применить шаблон…» и смена профиля

Риск: MEDIUM.

1. Экран импорта ОПиУ: кнопка «Базовый шаблон ОПиУ» → «Применить шаблон…» с выбором профиля;
   режим `onlyCreate` (существующие статьи не меняются, недостающие добавляются по коду).
2. Настройки компании: смена профиля с предупреждением «Справочники не изменятся;
   дополнить их можно кнопкой „Применить шаблон…“».
3. Подсказка при подключении первого маркетплейса у компании с профилем `UNIVERSAL`:
   предложить дополнить дерево статьями маркетплейса.
4. Тесты: применение маркетплейсного шаблона к универсальному дереву добавляет только
   недостающие статьи; смена профиля не трогает справочники.
5. `ARCHITECTURE.md`, handoff.

## 5. Набросок универсального дерева ОПиУ (утверждает Владелец)

Коды из маркетплейсного шаблона там, где смысл совпадает; новые помечены *.

- **Выручка** `REV_TOTAL`
  - Выручка от продаж `REV_SALES`*
  - Возвраты (−) `REV_RETURNS_TOTAL`*
- **Себестоимость** `COGS_TOTAL`
  - Себестоимость товаров/услуг `COGS_PRODUCT`
  - Доставка до клиента `COGS_DELIVERY`
  - Эквайринг `COGS_ACQUIRING`
- **Валовая прибыль** `GROSS_PROFIT`* = REV_TOTAL + COGS_TOTAL; **Валовая маржа, %** `GROSS_MARGIN`*
- **Коммерческие расходы** `OVERHEAD_SALES_TOTAL`: реклама `PROMO_TOTAL`, ФОТ продаж,
  контент, сервисы
- **Управленческие расходы** `OVERHEAD_ADMIN_TOTAL`: ФОТ, налоги на ФОТ, аренда, связь,
  подрядчики, сервисы, банк, прочие
- **EBITDA** `EBITDA`; **Рентабельность EBITDA, %** `EBITDAK`
- **Расходы ниже EBITDA** `BELOW_EBITDA_TOTAL`: НДС, УСН/АУСН, проценты по кредитам
- **Доходы ниже EBITDA** `BELOW_EBITDA_INCOME_TOTAL`
- **Чистая прибыль** `NET_PROFIT`
- **Распределение прибыли** `PROFIT_DISTR_TOTAL`: дивиденды

Вопросы к Владельцу по содержанию: нужна ли разбивка выручки по направлениям; держать ли
себестоимость одной статьёй; отдельный ли блок «Производственные расходы» (как в
маркетплейсном) или он входит в себестоимость.

## 6. Вне scope

- Профили кроме двух («Услуги», «Розница», «Производство») — после проверки спроса.
- Разные шаблоны ДДС по профилю.
- Автоматическая перестройка справочников при смене профиля.
- Дозаполнение существующих компаний универсальным шаблоном (все они — `MARKETPLACE`).

## 7. Риски

| Риск | Мера |
|---|---|
| Лишний шаг в регистрации снизит конверсию | Один вопрос, значение выбрано по умолчанию, две карточки без текста мелким шрифтом |
| Коды разойдутся между шаблонами | Тест словаря кодов в CI |
| Перенос файлов шаблонов сломает онбординг маркетплейсов | Stage 2 — регрессионный тест «прежний набор» |
| Миграция на большой таблице | `ADD COLUMN … DEFAULT` в PostgreSQL 15 — без перезаписи таблицы; отдельный ручной dispatch миграции (AGENTS §3.2) |
| Ошибка знака в итогах шаблона тиражируется | Stage 3 п. 1 — проверка направлений потока до копирования |
