# Категория листинга — уровень аналитики для Ozon и WB

Заменяет черновик PR #3059 (там категория назначалась товару в `Catalog`).
Здесь категорию получает **листинг**. Причины ниже, в разделе «Решения».

## Задача

Продавец группирует свои листинги Ozon и WB в собственные категории («Платья»,
«Аксессуары») и видит экономику по категориям: сумма по категориям равна
итогу отчёта.

## Результат

- Справочник категорий компании. У каждого листинга не больше одной категории.
- В реестре листингов: колонка, фильтр и массовое назначение категории.
- В «Экономике SKU» (`/marketplace/economics`): фильтр и группировка
  «Категория → листинг», XLSX с той же группировкой.
- Подсказки по категории площадки (Ozon `description_category_id` + `type_id`,
  WB `subjectID`) и по связанному товару.

## Что уже есть (master 0ee70c971)

| Факт | Где |
|---|---|
| Теги листингов: многие-ко-многим, фильтр, «выбрать все N по фильтру» (лимит 5000) | `Marketplace/Facade/ListingTagFacade`, ARCHITECTURE «Marketplace: теги листингов» |
| Отчёт строится из витрины `me_day_line` с ключом `listing_id`. Фильтр по тегам — в построителе через фасад | `MarketplaceEconomics/Application/Service/SkuEconomicsReportBuilder` |
| Показатели строк складываются через `SkuMetrics::merge()`, проценты считаются из сумм | `MarketplaceEconomics/Domain/SkuMetrics` |
| Ozon: в метаданных листинга хранится `description_category_id`, без названия и без `type_id` | `OzonProductCatalogNormalizer.php:185` |
| WB: хранится `subjectName`, без `subjectID` | `RefreshWbListingCatalogAction.php:182` |

## Решения (рекомендация; ждут подтверждения Владельца)

| # | Вопрос | Рекомендация | Почему |
|---|---|---|---|
| D1 | Кому назначается категория | **Листингу** (модуль `Marketplace`, рядом с тегами) | Работает без привязки к товару. Листинги без товара не теряются в «Без категории». Межмодульной записи нет |
| D2 | Ozon и WB одного товара | Назначаются отдельно; кнопка «как у связанного товара» | Связь с товаром остаётся подсказкой, а не условием |
| D3 | История смены категории | **Нет.** Текущая категория применяется ко всему периоду | Так работают теги и большинство BI-систем. Пересчёт и даты не нужны. История по датам — отдельная задача, если понадобится |
| D4 | Иерархия | **Плоский** справочник | Второй уровень добавить позже: колонка `parent_id` без переделки отчёта |
| D5 | Почему не теги | Категория — отдельная сущность, ровно одна на листинг | Тег кладёт сумму листинга в каждый свой тег, поэтому колонки тегов не складываются в итог. Категории складываются |

## Лучшие практики, на которые опирается план

1. **Ровно одна категория держится на уровне БД:** колонка `category_id` у листинга, а не таблица связей. Тогда сумма по категориям = итог по построению.
2. **Категория — измерение, а не факт.** Группировка выполняется при чтении, витрину `me_day_line` не трогаем. Переназначение видно сразу, без пересчёта и «грязных» окон.
3. **Итог всегда сходится:** явные строки «Без категории» (листинг без назначения) и «Не распределено по листингам» (`listing_id IS NULL`).
4. **Ручное назначение сильнее правила.** У листинга хранится `category_source` (`manual` | `rule`). Синхронизация меняет только `rule` и пустые.
5. **Ключ площадки — по ID, не по названию:** у Ozon `(description_category_id, type_id)`, у WB `subjectID`. Названия меняются и дублируются.
6. **Массовые операции — по фильтру реестра**, с лимитом и идемпотентно (повтор даёт то же состояние). Механика тегов переиспользуется.
7. **Изоляция компании:** все методы фасада принимают `companyId`. Категорию из чужой компании назначить нельзя (проверка в Action и тест).
8. **Используемую категорию удалить нельзя:** отказ в диалоге со ссылкой на листинги (паттерн удаления статьи ОПиУ).
9. **Покрытие видно:** в отчёте показывается «Доля выручки с категорией, %», чтобы было видно, насколько можно доверять разрезу.
10. **Легаси не трогаем:** `unit-extended` и `pl-preview` в объём не входят.

## Этапы

Каждый этап начинается с `stages/stage-N.md` из 4 частей и тестов на приёмку.

### Этап 0. Замер (read-only, прод)

- Листинги по компаниям: всего, с товаром, с `description_category_id`, с `subject_name`.
- Доля выручки `me_day_line` за 90 дней по листингам без товара.

Приёмка: цифры записаны в `measurements/stage-0.md`. По ним подтверждено или пересмотрено D1.

### Этап 1. Справочник и назначение (`Marketplace`, HIGH-LOCAL — миграция)

- Entity `MarketplaceListingCategory` (`marketplace_listing_categories`: `id` UUIDv7, `company_id`, `name`, `slug`, `created_at`, unique `(company_id, slug)`).
- `marketplace_listings.category_id` (nullable, FK `ON DELETE RESTRICT`) и `category_source`.
- `ListingCategoryFacadeInterface` + `ListingCategoryFacade`: `list()`, `categoriesForListings(companyId, listingIds)` (порциями по 5000), `listingIdsByCategories(companyId, ids|none)`.
- Actions: создать, переименовать, удалить (отказ, если категория используется), назначить или снять (по id или по фильтру, лимит 5000).
- ARCHITECTURE: раздел «Marketplace: категории листингов». Миграция выходит отдельным релизом.

Приёмка:
- [ ] Повторное массовое назначение даёт то же состояние и то же число строк.
- [ ] Чужую категорию или чужой листинг назначить нельзя: тест IDOR.
- [ ] Удаление используемой категории — отказ, данные не меняются.
- [ ] Гейты: stan по каталогу модуля, cs, strict-types, `SchemaInSyncWithMigrationsTest`.

### Этап 2. Реестр листингов (UI, MEDIUM)

- Справочник категорий (создать, переименовать, удалить).
- Колонка «Категория», фильтр `?category=<uuid>|none`, массовое назначение по выбранным и «все N по фильтру».

Приёмка:
- [ ] Сценарий в браузере: создать категорию → назначить 3 листингам Ozon и 2 WB → отфильтровать → снять.
- [ ] Ошибки назначения видны на экране, а не в тултипе.

### Этап 3. «Экономика SKU» по категориям (`MarketplaceEconomics`, HIGH-LOCAL — деньги)

- Фильтр по категориям (как `tagIds`) и переключатель «По листингам / По категориям» с раскрытием до листинга.
- Группировка в построителе: `SkuEconomicsRow` → категория через фасад → `SkuMetrics::merge()`. Запрос к витрине не меняется.
- XLSX с выбранной группировкой; показатель покрытия.

Приёмка:
- [ ] При тех же фильтрах сумма по категориям + «Без категории» + «Не распределено» = итог «По листингам», до копейки (выручка, СМ1–СМ3, реклама).
- [ ] Проценты и ДРР группы считаются из сумм, а не средним по строкам.
- [ ] XLSX совпадает с экраном.
- [ ] Ozon и WB в одной категории, площадка видна в детализации.

### Этап 4. Подсказки по площадке (`Marketplace`, HIGH-LOCAL — правила)

- Сохранять Ozon `type_id` и названия категории и типа (`/v1/description-category/tree`), WB `subjectID`.
- Правила `(company_id, marketplace, source_key) → category_id`, unique. Применяются при обновлении каталога к листингам с `category_source` ≠ `manual`.
- Экран «Неразмеченные ключи площадок»: ключ, число листингов, выручка → «назначить правило». Подсказка «как у связанного товара».

Приёмка:
- [ ] Одно правило размечает все листинги с этим ключом.
- [ ] Повторная синхронизация не меняет ручные назначения и не дублирует правила.
- [ ] Правила другой компании не применяются.

### Вне объёма (отдельные задачи по запросу)

История категорий по датам, иерархия, колонки категорий в «Предпросмотре ОПиУ», импорт и экспорт XLSX «артикул → категория», категории в воронке и оборачиваемости.
