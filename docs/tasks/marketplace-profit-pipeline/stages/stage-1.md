# Этап 1. Эталон с прода

План от 13.11.2026. Кода приложения этап не меняет.

## 1. Какую задачу решаем

Новый контур будет приниматься сверкой с тем, что сегодня считает легаси. Данные легаси
изменяемы (сырьё перезаписывается, хвост перегружается, реклама доразносится), поэтому цифры
нужно снять сейчас и зафиксировать, а запрос сделать повторяемым.

## 2. Что будет результатом

1. **Запросы эталона** `stages/stage-1-baseline.sql` — только `SELECT`, повторяют источники
   «Unit — Экономика» (`ListingSalesAggregateQuery`, `ListingReturnAggregateQuery`,
   `ListingCostAggregateQuery`, статистика рекламы `MarketplaceAds`), но с разрезом по дням:

   | Набор | Разрез | Поля |
   |---|---|---|
   | A. Продажи | день × листинг | выручка (`total_revenue`), шт., себестоимость ₽, шт. с себестоимостью |
   | B. Возвраты | день × листинг | сумма возврата, шт. |
   | C. Затраты | день × листинг (или пусто) × код категории | сумма со знаком сторно, число строк; **все** категории, рекламные под статистикой (`AdStatisticsCostCategories`) — с признаком, а не исключением |
   | D. Реклама | день × листинг × вид (`AdSpendKind`) | разнесённый расход из статистики |
   | E. Контроль | день | итоги A–D одной строкой на день |
   | F. Справочник | код категории | название, число строк, сумма за период |

2. **Снимок** по кабинету Ozon компании 3f4d87cc за 08.09 – 12.11.2026: CSV наборов A–F
   **вне git** (`~/vf-measurements/marketplace-profit-pipeline/2026-11-13/`), в `stage-1.md` — время
   снятия (МСК), число строк и sha256 каждого файла. Клиентские суммы в репозиторий не попадают.
3. **Таблица уровней** `stages/stage-1-category-levels.md`: каждый код категории легаси из набора F →
   уровень каскада (выручка / прямые МД1 / реклама МД2 / общие / справочно) и вид операции будущего
   канона. Это заготовка справочника этапов 3–4.
4. **Правило сравнения** для этапов 4–6: что сверяем (уровень каскада × день × кабинет), допуск 1 ₽,
   два окна — «устойчивое» 08.09 – 31.10 (сверка со снимком) и «подвижное» с 01.11 (сверка со
   свежим прогоном того же запроса).

- Каждый код из набора F имеет уровень каскада; таблица уровней утверждена Владельцем.

## 4. Чек-лист приёмки

- [ ] В `stage-1-baseline.sql` только `SELECT`, везде фильтр `company_id` и `marketplace`, явные колонки.
- [ ] Наборы A–F сняты одним заходом (время начала и конца — в пределах 10 минут, вне окна ночных

- [ ] Σ A по дням = «Выручка» экрана; Σ B = «Возвраты»; Σ C (листинг есть, без рекламных кодов) =

- [ ] Число листингов в A ∪ C ∪ D = число строк экрана (+ строка нераспределённого).

- [ ] В git нет CSV и сумм кабинета; есть запросы, счётчики строк, sha256.

## Особенности легаси, которые новый контур не повторяет

1. **Два источника рекламы.** Учётные строки (`ozon_cpc`, `ozon_marketing_action`, предоплата
   `ozon_marketing_services`) и статистика `MarketplaceAds` живут параллельно; отчёты берут
   статистику и вычитают учёт. У кабинета за период учёт кликов и статистика кликов расходятся
   на сотни рублей (лаг D+2). В каноне реклама — один вид операции с одним источником суммы
   (учёт) и разнесением по SKU из статистики; расхождение учёт ↔ статистика — отдельная сверка.
2. **Оплата за заказ почти вся не разнесена.** Статистика `pay_per_order` есть только за отдельные
   дни ноября; основная сумма учёта «Маркетинговых акций» за период остаётся в «Не распределено».
   Этап 6 должен разнести её за всю историю с 08.09, а не с даты запуска.
3. **Знак сторно через `ABS` и `operation_type`.** Суммы затрат хранятся с разным знаком, итог
   получается только через `CASE operation_type`. В каноне сумма хранится со знаком, сторно —
   отрицательная операция того же вида.
4. **Затраты у листингов без продаж** (209 листингов с затратами против 184 с продажами): строки
   есть только из-за затрат. В R1 такие SKU показываются, а не отбрасываются.
5. **Один новый тип Ozon дошёл до учёта как `ozon_unknown_119`.** В новом контуре неизвестный
   тип останавливается в карантине переводчика и поднимает гейт.
