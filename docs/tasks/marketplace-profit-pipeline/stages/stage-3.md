# Этап 3. `MarketplaceOperations` — канон

План от 13.11.2026 (Владелец: «Делай» — план и выполнение без промежуточных согласований).
Основа — решения `DATA.md` §5, §9.

## 1. Какую задачу решаем

Переводчики каналов (Ozon — этап 4, WB — этап 8) должны писать результат разбора в одно место
одного формата, а экономика SKU (этап 5) — читать его, не зная каналов. Этап создаёт это место:
модуль канонических операций, который проверяет вход и не даёт записать операцию мимо правил.

## 2. Что будет результатом

**Модуль `site/src/MarketplaceOperations`**, таблицы `mo_*`:

| Таблица | Строка | Ключ |
|---|---|---|
| `mo_operation` | одна операция: `company_id`, `channel`, `connection_ref`, `operation_date`, `listing_id` (пусто — без SKU), `source_type`, `kind`, `amount_minor` + `currency`, `quantity`, `source_refs` (jsonb, ссылки на факты), `rules_version`, `allocation_key` | `id` UUID v7; индекс `(company_id, channel, connection_ref, operation_date)` |
| `mo_dirty_window` | день кабинета изменился, витрина должна пересчитать | `(company_id, channel, connection_ref, operation_date)` |

**Справочник видов — enum `OperationKind`** с уровнем каскада (`CascadeLevel`: выручка / МД1 /
МД2 / общие / справочно): 25 видов из `stage-1-category-levels.md` + `sale`, `return`, `spp`,
`coinvestment`. Уровень — свойство вида; правило «прямой вид без листинга → общие» применяет
витрина (этап 5).

**Фасад `MarketplaceOperationsFacadeInterface::replaceDay(DayOperations): int`** — единственная запись:
- замена дня кабинета целиком: удалить операции `(компания, канал, кабинет, день)` → вставить новые →
  отметить окно грязным; под `pg_advisory_xact_lock` дня;
- транзакцией владеет вызывающий (Action/Handler переводчика); без активной транзакции — исключение;
- проверки входа: вид из enum, `source_type` и хотя бы одна ссылка на факт обязательны, `channel` —
  `[a-z_]+`, деньги — `Money` (копейки + валюта); день задаёт вызов, у операции своей даты нет.

**Границы и документы:** PHPat — `MarketplaceOperations` не зависит от модулей каналов, легаси
маркетплейсов, `SourceFacts` и учёта; модуль — в списке модулей с закрытыми слоями (запись только
через фасад). Устав модуля, кто коммитит и порядок блокировок — `ARCHITECTURE.md`; Changelog.

### Отклонения от `TASK.md` / `DATA.md` (решение этапа)

- **Справочник видов — enum, не таблица.** Новый вид редок (новый код маркетплейса почти всегда
  ложится в существующий вид); enum не требует seed-миграции и восстановления в тестах. Когда на
  этапе 4 появится экран подтверждения нового кода администратором (`DATA.md` §9.4) и новый вид
  понадобится без деплоя — перевести в таблицу тем же PR.
- **`sku` не хранится отдельно** — это атрибут листинга (`listing_id`), дублировать его в каждой
  операции незачем.
- **Фасад чтения не делается** — потребитель (витрина) появится на этапе 5 вместе с ним.
