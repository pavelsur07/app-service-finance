# Этап 4. `MarketplaceOzon` — переводчик by-day

План от 14.11.2026 (Владелец: «Делай этап 4, начинай с технического плана и чек-листа приёмки»).
Основа — `TASK.md` этап 4, `DATA.md` §5, §9, таблица уровней `stage-1-category-levels.md`.

## 1. Какую задачу решаем

Начисления Ozon по дням уже приходят в приложение (`sf_fact`, этап 2), канон операций создан и
пуст (`mo_operation`, этап 3). Не хватает звена между ними: разобрать каждое начисление на
компоненты, дать каждому код Ozon (`source_type`) и наш вид (`kind`), найти листинг и записать день
в канон. Неизвестный код не должен молча уходить в «Прочее»: он ждёт решения администратора, а
ИИ готовит черновик решения.

## 2. Что будет результатом

### 2.1. Модуль `site/src/MarketplaceOzon`, таблицы `moz_*`

| Таблица | Строка | Ключ |
|---|---|---|
| `moz_source_type` | справочник кодов Ozon: `source_type`, название как в кабинете, `kind` (пусто — не решено), статус `confirmed` / `pending`, черновик ИИ (jsonb), кто и когда подтвердил, где и когда код встретился впервые | `source_type` |
| `moz_day` | день кабинета, переведённый в канон: ревизия фактов, версия правил, число фактов, Σ `total_amount`, Σ компонентов, Σ записанного в канон, Σ в карантине, число компонентов без листинга, время перевода | `(company_id, connection_ref, operation_date)` |
| `moz_quarantine` | компонент с кодом без решения: день, `source_type`, сумма, число строк, ссылки на факты | `(company_id, connection_ref, operation_date, source_type)` |

Справочник общий для всех компаний: это коды Ozon, а не данные клиентов.

### 2.2. Коды `source_type`

| Компонент by-day | `source_type` | `kind` |
|---|---|---|
| `posting.products[].commission.sale_amount` | `ozon:field:sale_amount` | `sale`, при отрицательной сумме — `return` |
| `…commission.bonus` | `ozon:field:bonus` | `spp` |
| `…commission.coinvestment` | `ozon:field:coinvestment` | `coinvestment` |
| `…commission.sale_commission` | `ozon:field:sale_commission` | `commission` |
| `…delivery.services[]`, `item_fees.fees[].fees[]`, `non_item_fee`, `container_fees` (рекурсивно) | `ozon:service:{type_id}` | из справочника |

- `type_id` — номер из справочника Ozon (`ingest_ozon_accrual_types`, 137 типов), один на всех.
- Суммы — как отдаёт Ozon, со знаком, `Money` в рублях. Сторно приходит той же услугой с обратным
  знаком, ничего не переворачиваем.
- Выручка с СПП = `sale` − `spp` − `coinvestment` (см. исправление `DATA.md` §9.2 в этом PR).
- Компонент с нулевой суммой не пишется — так же делает легаси.
- Проверено на проде 14.11 (все факты Вумджой): `total_amount` начисления = `sale_amount` + `sale_commission` +
  Σ услуг у всех 2293 отправлений; `sale_amount` = `sale_price` + `bonus` + `coinvestment` у всех 872 продаж.
  `seller_price` — цена за штуку (расходится при количестве > 1), в канон не идёт. Контроль дня:
  Σ компонентов = Σ `total_amount` начислений.

### 2.3. Начальное наполнение справочника

- Разовый скрипт `stages/stage-4-seed.sql` читает прод только на `SELECT`: справочник типов Ozon,
  базовый маппинг легаси «тип → категория» (`external_category_mappings` без компании) и названия.
- Категория легаси переводится в `kind` по таблице уровней этапа 1, расширенной на все коды
  `OzonCostCategory`.
- Результат — данные в миграции модуля: в коде нет зависимости от `Ingestion` и `Marketplace\Ozon`.
- Тип, который однозначно не ложится в вид (категория без строки в таблице или спорная), получает
  статус `pending`. Решать по нему будет администратор через экран (2.6), а не этот план.

### 2.4. Перевод дня

`app:marketplace-ozon:translate` — cron каждые 15 минут, через 5 минут после `app:source-facts:pull`,
с `LockableTrait`.
1. Список периодов `ozon.finance.accrual-by-day` с текущей ревизией — через новый фасад чтения
   `SourceFactsFacadeInterface` (2.5). Сравнивается с `moz_day`. Переводятся дни, где ревизия
   выросла, сменилась версия правил или подтверждён код из карантина этого дня.
2. По каждому дню — одна транзакция:
   - факты дня → компоненты (чистый класс `AccrualByDayTranslator`, без БД);
   - SKU → листинг одним запросом за день через `MarketplaceFacade::findListingsByMarketplaceSkus`;
   - коды с решением → `MarketplaceOperationsFacade::replaceDay`;
   - коды без решения → `moz_quarantine`;
   - итоги → `moz_day`.

   Сбой одного дня не останавливает остальные; в конце один агрегированный `error`.
3. Новый `source_type` при первой встрече записывается строкой `pending`, после commit ставится
   задача ИИ (2.6).
4. SKU без листинга: операция пишется с `listing_id = null`, SKU лежит в `source_refs`, счётчик —
   в `moz_day`. Когда каталог подтянет листинг, день переводится заново: `app:marketplace-ozon:translate
   --relink` раз в сутки берёт дни со счётчиком > 0.

Порядок блокировок: блокировка дня канона берётся внутри `replaceDay`, у переводчика своих
блокировок нет. Транзакцией владеет команда.

### 2.5. Фасад чтения `SourceFacts`

`SourceFactsFacadeInterface`:
- `periods(string $resourceType): list<SourcePeriod>` — компания, кабинет, период, текущая ревизия;
- `activeFacts(string $companyId, string $connectionRef, string $resourceType, string $periodKey): iterable<SourceFactRecord>` —
  действующие записи текущей ревизии: `source_key`, `payload`.

Потребитель — только переводчики. PHPat: `MarketplaceOzon` знает `SourceFacts`, `MarketplaceOperations` и
листинги `Marketplace` только через фасады; `MarketplaceOperations` и `SourceFacts` не знают `MarketplaceOzon`.

### 2.6. Новый код: черновик ИИ и подтверждение администратором

- Задача ИИ `marketplace_source_type_draft`:
  - контракт — в `services/_contracts/ai-task`;
  - промпт и evals — в `ai-service`;
  - вход: код, название Ozon, место в начислении (posting / item / non_item), есть ли SKU, знак,
    список видов с уровнями, три похожих подтверждённых кода, без сумм;
  - выход: название, `kind`, уверенность и пояснение.

  Задача ставится от компании, у которой код встретился впервые: её бюджет и учёт. ИИ выключен
  для компании — черновика нет, экран работает без него.
- Экран `/admin/marketplace/ozon-source-types` (Twig, роль администратора платформы):
  - список `pending` с черновиком ИИ, суммой и числом дней в карантине по всем компаниям;
  - форма «название, вид» — вид выбирается из справочника видов;
  - подтверждение → `confirmed`; дни карантина с этим кодом переводятся следующим прогоном (2.4, п. 1).
- Гейт: код в `pending` дольше 24 часов — красный.

### 2.7. Отклонения от `TASK.md` / `DATA.md` (решение этапа)

- **Вид остаётся enum.** Почти любой новый код Ozon ложится в существующий вид, поэтому администратор
  выбирает из списка. Если ИИ предлагает новый вид, на экране видна пометка «нужен новый вид» —
  это правка кода и деплой. Таблицу видов делаем, когда такой случай случится не раз.
- **Месячная сверка с отчётом о реализации** в этом этапе — разовая проверка октября запросом на
  чтение. Автоматическая сверка — в `MarketplaceReconciliation`: отчёт о реализации ещё не идёт
  каналом фактов.
- **Статья шаблона ОПиУ** в подтверждении нового кода не выбирается: маппинга нет до
  `MarketplacePlProjection`.
- **Флаг включения не нужен:** переводчик берёт то, что есть в `sf_fact`. Факты есть только у
  кабинетов из `SOURCE_FACTS_COMPANIES`, а канон пока никто не читает.

## Риски

- **Названия и места `type_id`.** Один `type_id` может встречаться в разных блоках (delivery /
  item / non_item) с разным смыслом. Перед кодом проверить по `sf_fact` прода: если смысл
  расходится, `source_type` получает блок (`ozon:service:{scope}:{type_id}`).
- **Объём перевода истории.** Первый прогон переводит ~75 дней на кабинет. Если прогон не
  укладывается в 15 минут, ограничить число дней за прогон (`--limit`).
- **Расхождения с легаси ожидаемы:** у легаси сторно уходит в расход, реклама приходит на D+2,
  а сами начисления менялись после его последней синхронизации (этап 2, +2 записи). Это
  объясняется, а не подгоняется.
- **ИИ-сервис** включён не у всех компаний — черновика может не быть. Экран от черновика не зависит.
