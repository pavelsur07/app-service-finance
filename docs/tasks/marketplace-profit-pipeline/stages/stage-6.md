# Этап 6. Реклама по SKU из нового контура, отчёты R2 и R3 (Ozon)

Задача `marketplace-profit-pipeline`, этап 6 из `TASK.md`. План — 14.11.2026.

## 1. Задача

1. Витрина `MarketplaceEconomics` раскладывает рекламу Ozon по SKU по долям легаси
   `MarketplaceAds` (этап 5, временно). Нужен свой источник: статистика Performance из
   ozon-fetcher → факты → канон. После этого витрина не зависит от легаси рекламы.
2. Отчёт R2 «Динамика» — показатели кабинета и SKU по дням / неделям / месяцам.
3. Отчёт R3 «Неделя» — в понедельник утром файл и короткая сводка получателям компании.

Условие Владельца (14.11) действует: легаси (`MarketplaceAds`, «Unit — Экономика», реклама в
ОПиУ) не меняется ни в одной строке; новые экраны — отдельные.

## 2. Результат

### 6.1. ozon-fetcher публикует рекламу фактами

- `ozon.ads.statistics` (день `period_key`) уже грузится. Публикуется фактами: запись — строка
  отчёта «кампания × SKU» как в CSV, ключ `ozon:ads-statistics:{campaign}:{sku}`.
  Хвост `ozon.ads.statistics.tail` (14 дней) не публикуется — см. «Что выполнено».
- Оплата за заказ (CPO) и «Продвижение в поиске» (ALL_SKU_PROMO) — новые ресурсы
  `ozon.ads.orders` (`statistic/orders/generate`) и `ozon.ads.search-promo`
  (`search_promo/v2/products`) по образцу Ingestion. Квота Performance — общая с легаси.
- Контракт `source-fact-envelope` v1 CHANGELOG — новые `resource_type`;
  `SourceFactsGatewayFacade::RESOURCES` — белый список.

### 6.2. Канон: реклама дня по SKU

Переводчик `MarketplaceOzon` при переводе дня раскладывает рекламные операции без SKU
(`ads_cpc` — тип 41, `ads_pay_per_order` — тип 54, ALL_SKU_PROMO) на операции с `listing_id`
по фактам статистики того же дня; ключ распределения — в `allocation_key`, остаток округления —
методом наибольшего остатка, Σ дня не меняется. Нет статистики — операция остаётся без SKU.
Приход фактов рекламы за день отмечает день «грязным» — день переводится заново.

Сначала проверить на данных Вумджой: дата статистики = дата начисления by-day или сдвиг (D+2
для type 41 — память `ozon-ppc-posting-lag`). Решение по сопоставлению — по результату.

### 6.3. Витрина без легаси рекламы

`DayEconomicsCalculator` берёт рекламу SKU из канона; вызов `MarketplaceAdsFacade` удаляется,
PHPat снова запрещает `App\MarketplaceAds` в модуле. `RULES_VERSION` → `economics-3`.

### 6.4. R2 «Динамика» — `/marketplace/economics/dynamics`

Server Twig на новом слое, как R1. Шаг день/неделя/месяц, кабинет, SKU (поиск), теги.
Ряды: выручка, продажи шт., МД1, реклама, ДРР, МД2, маржа МД2 %. Таблица + график (один
график, существующая библиотека слоя). xlsx — тот же отчёт. Данные — `me_day_line`.

### 6.5. R3 «Неделя»

- `app:marketplace-economics:weekly-report` — cron `0 9 * * 1` МСК, прошлая неделя пн–вс.
- Содержание: итоги против прошлой недели и среднего за 4 недели; топ-10 роста и падения МД2;
  SKU с отрицательной МД2; ДРР выше 20 %; строка «поправки за прошлые недели» (D7);
  реклама последних 2 дней — «предварительно».
- Доставка: xlsx на e-mail владельцу компании (`NotificationRouter` + `EmailSender`) и в
  Telegram привязанным пользователям (новый `sendDocument` у бота).
- Журнал `me_weekly_report` с unique `(company_id, week_start, channel)` — захват до отправки,
  повтор не шлёт дважды (образец — `billing_expiry_reminders`). Миграция — отдельный релиз.

## 3. Что выполнено

### 6.1–6.2 (14.11, ветка `feat/marketplace-ads-canon`)

- Сверка до кода (прод, Вумджой, read-only): дата статистики легаси = дата CPC в by-day по
  каждому дню 01.09–10.11, расхождения — копейки; сдвига нет, сопоставление по той же дате.
  By-day CPC приходит на D+2 — последние 2 дня без CPC в каноне, это лаг источника.
- ozon-fetcher публикует `ozon.ads.statistics` (дневной отчёт; CSV/ZIP → строки «кампания × SKU»),
  миграция `00009` ставит в очередь уже загруженные дни. Хвост (`.tail`) не публикуется:
  `ponytail:` нужен, если дневная статистика окажется неокончательной — сверка 6.1 покажет.
- Переводчик разносит CPC по долям расхода SKU; `moz_day.ads_revision` — день переводится заново при
  новой статистике. Миграция — отдельный релиз.
- На проде с 14.11 (#2994, миграция). Сверка ИП Лазарева (Вумджой, `3f4d87cc`) 21.10–10.11: 100 % CPC
  на SKU, Σ дня = by-day. Статистика в ozon-fetcher — с 21.10, раньше витрина делит по долям легаси.
- Витрина без изменений: CPC с листингом из канона идёт прямо в SKU, доли легаси применяются
  только к остатку без SKU.

### 6.4 R2 «Динамика» (14.11, #2995)

`/marketplace/economics/dynamics`, вкладка рядом с R1. Запрос за 366 дней по дням — 38 мс. Владелец
проверил R1 и R2 на ИП Лазарева 14.11: работают; правки UI — отдельной задачей. Подписи уровней —
СМ1 / СМ2 / СМ3 по шаблону ОПиУ (#2997). Состав уровней не меняем (решение Владельца 14.11:
хранение остаётся в СМ1, как утверждено 13.11).

### Прочее 14.11

- Вид `compensation` (#2996): коды Ozon 10 и 25, уровень «общие» (+); код 25 подтверждён администратором.
- Новый контур включён для всех компаний (`SOURCE_FACTS_COMPANIES=*`, решение Владельца 14.11).

### 6.1b, упрощённо (14.11)

Оплата за заказ (тип 54) у ИП Лазарева — почти вся ALL_SKU_PROMO: с 01.10 в каноне 60 318 ₽, легаси
раскладывало только SEARCH_PROMO (2 088 ₽), остальное было «нераспределено». Переводчик делит тип 54 дня
по проданным штукам SKU за день (`sales_qty_share`); нет продаж — без SKU. `RULES_VERSION` →
`ozon-by-day-2`, история переводится заново сама.
`ponytail:` ALL_SKU_PROMO делится по продажам всех SKU, а не только товаров кампании; SEARCH_PROMO — не
на заказанный SKU. Точно — отчёт заказов (`statistic/orders/generate`) и товары кампании
(`search_promo/v2/products`) из ozon-fetcher; делать, если сверка с легаси покажет заметную разницу.
