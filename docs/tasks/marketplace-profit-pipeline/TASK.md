# Новый контур данных маркетплейсов: экономика SKU и отчёты

Поручено Владельцем 13.11.2026. Цель — точная экономика каждого SKU (с разнесёнными
общими затратами и без них), динамика за любой период и еженедельный аналитический отчёт
на новом контуре вместо легаси `Marketplace` / `Ingestion` / `MarketplaceAds`.

## Документы задачи

| Файл | Что |
|---|---|
| `AUDIT.md` | аудит легаси 13.11 и решения Владельца |
| `REPORTS.md` | утверждённые отчёты, показатели, приоритеты, определения D1–D7 |
| `DATA.md` | нужные факты, пробелы источников, модули, канон, границы, новый канал |
| `stages/stage-N.md` | план этапа (задача, результат, что выполнено, чек-лист приёмки) и итог — пишется в начале этапа |

## Как сейчас

- `Marketplace` (кроме листингов и себестоимости по датам), `Ingestion`, `MarketplaceAds` — легаси
  с 13.11.2026 (ADR в `ARCHITECTURE.md`): только исправления, без которых ломается прод, и удаление.
- Экономика SKU — `/marketplace-analytics/unit-extended` (≈ МД2 по строкам, общие затраты — строка
  «Не распределено»), дневной динамики и еженедельного отчёта нет.
- ozon-fetcher и wb-fetcher пишут сырьё в S3; Symfony факты из них не забирает
  (`source-fact-envelope` v1 — проект).

## Правила задачи

- Только новые модули по `DATA.md` §4; в легаси ничего не добавляется.
- Каждый этап — свой PR (или пара «миграция + код» по `migration-pr-release-flow`), система после
  этапа рабочая; легаси продолжает считать ОПиУ и текущие экраны.
- Границы — PHPat с первого модульного PR (`DATA.md` §6), устав модуля — в `ARCHITECTURE.md` в том же PR.
- Приёмка расчётов — сверка с эталоном (этап 1): суммы по уровню каскада × день × кабинет, допуск
  1 ₽ на день и уровень; каждое расхождение объяснено (ошибка легаси, ошибка нового, разное
  определение) до перехода к следующему этапу.
- Деньги — `string` / `bcmath`, без float; сравнение по копейкам.
- Ozon by-day доступен с 08.09.2026 (`EARLIEST_SAFE_DAY`) — эталон и сверки начиная с сентября.

### 1. Эталон с прода

- **Результат:** `measurements/baseline-ozon.csv` (и позже WB): кабинет 3f4d87cc, 08.09 – 12.11.2026,

- **Приёмка:** Σ эталона по дням = итог «Unit — Экономика» за тот же период (± 1 ₽); каждая
  категория легаси имеет уровень каскада; клиентские данные — не в PR (только агрегаты кабинета
  в `measurements/`, вне git при необходимости).

### 2. Канал фактов и `SourceFacts`

- **Задача:** Symfony забирает факты из ozon-fetcher.
- **Результат:** `source-fact-envelope` v1 из «проекта» в «опубликован» для
  `ozon.finance.accrual-by-day`; в ozon-fetcher — outbox, `GET /internal/source-facts`, `POST …/ack`;
  модуль `SourceFacts`: pull по cron, приём идемпотентно по `(source_key, source_revision)`,
  карантин формата, ack; устав модуля и первые правила PHPat (`SourceFacts` не знает каналов).
- **Выполнено:** на проде факты Ozon by-day приходят по всем кабинетам ежедневно.
- **Приёмка:** повторный pull → то же число строк; неизвестная `schema_version` → карантин;
  число фактов за день = число компонентов сырья за день (сверка с S3); ack только после commit;
  гейт свежести.
- **Ход (13.11.2026):** #2983, #2984 на проде, миграция применена; включён кабинет 3f4d87cc
  (`SOURCE_FACTS_COMPANIES`). Первый pull 19:00 МСК: 73 дня 01.09 – 12.11, 4858 фактов, карантин 0,
  повтор — те же счётчики. Сверка с легаси-сырьём: 08.09 – 12.11 все начисления легаси есть, +2
  начисления без отправления (30.09, 31.10 — Ozon добавил после последней загрузки легаси).
  Осталось: гейт 3 дня, ночная ревизия хвоста, остальные кабинеты.

### 3. `MarketplaceOperations` — канон

- **Задача:** единое хранилище канонических операций, одинаковое для всех каналов.
- **Результат:** модуль с сущностью операции (`DATA.md` §5, §9: `channel`, `connection_ref`, `listing`,
  `date`, `source_type`, `kind`, `amount` — `Money`, `quantity`, ссылки на факты, версия правил, ключ
  распределения; без проекта); справочник видов с уровнем каскада, включая `sale`, `spp`,
  `coinvestment`; новый вид — только подтверждённый (§9.4); фасад записи «замена окна» под advisory
  lock; отметка «окно грязное»; правила PHPat для канона (ниже канона — только `channel`), префикс таблиц.
- **Выполнено:** модуль на проде, пустой; запись возможна только через фасад.
- **Приёмка:** тест замены окна (повтор → то же число строк, конкурентный вызов); вид без уровня
  каскада и операция без `source_type` не принимаются; сторно — тот же вид с обратным знаком;
  PHPat ловит запись мимо фасада и имена каналов ниже канона.

### 4. `MarketplaceOzon` — переводчик by-day

- **Задача:** перевести факты Ozon by-day в канон.
- **Результат:** справочник типов начислений (из `ozon.finance.accrual-types`, данные переносятся
  из легаси `OzonAccrualType` / `OzonCostCategory`) — `source_type` → название как в кабинете, `kind`,
  статус; компоненты → операции без свёртки (`DATA.md` §9.1); две выручки из by-day: `seller_price` →
  `sale`, `bonus` → `spp`, `coinvestment` (§9.2); отправление → листинг через фасад листингов;
  карантин неизвестных типов с гейтом; черновик ИИ для нового типа и экран подтверждения в админке
  (§9.4); контрольные итоги дня; месячная сверка с отчётом о реализации.
- **Выполнено:** канон Ozon наполняется ежедневно по всем кабинетам, история с 08.09.
- **Приёмка:** сверка с эталоном по уровням МД1 / общие × день — в допуске или объяснена;
  Σ канона по `source_type` = Σ компонентов фактов за день до копейки; `sale` + `spp` +
  `coinvestment` = цена покупателя по каждой продаже; Σ месяца ↔ реализация — в допуске или
  объяснено; новый тип → карантин, черновик ИИ и гейт, не «Прочее»; после подтверждения карантин
  разбирается сам; пересчёт окна при смене справочника.

### 5. `MarketplaceEconomics` — витрина и R1 (Ozon)

- **Задача:** экономика SKU за любой период по уровням каскада.
- **Результат:** витрина SKU × день из канона + себестоимость на дату (`MarketplaceInventoryCostPrice`,
  D5) + налог по профилю (D4); разнесение общих затрат по ключу D3 с сохранением ключа и строкой
  «нераспределено»; отчёт R1 (уровни валовая / МД1 / МД2 / полная, сравнение с прошлым периодом,
  фильтры, xlsx) — новая страница, легаси-экран не трогаем.
- **Выполнено:** R1 по Ozon на проде (реклама в МД2 пока из легаси-разнесения через фасад
  `MarketplaceAds` — временно, до этапа 6).
- **Приёмка:** Σ SKU (полная) + нераспределённое = итог кабинета; МД2 сходится с «Прибылью» легаси
  или расхождение объяснено; период до 366 дней — время ответа замерено; тест каждого уровня.

### 6. Реклама Ozon в переводчике, R2 и R3

- **Задача:** МД2 без легаси, динамика и еженедельный отчёт.
- **Результат:** в ozon-fetcher — оплата за заказ и ALL_SKU_PROMO (сейчас через `Ingestion`);
  разнесение CPC / оплаты за заказ / ALL_SKU_PROMO в `MarketplaceOzon` с ключом; R2 (динамика
  показателя по дням / неделям / месяцам); R3 (пн 09:00 МСК, xlsx + Telegram/e-mail, журнал
  отправок, строка корректировок прошлых периодов — D6, D7).
- **Выполнено:** реклама Ozon в каноне сходится с легаси `MarketplaceAds`; R3 пришёл Владельцу
  два понедельника подряд.
- **Приёмка:** Σ рекламы по SKU = расход кабинета за день; повторная отправка R3 не дублирует;
  отчёт с пометкой «предварительно» для рекламы D+2.

### 7. R10 и ежедневные сверки нового контура

- **Задача:** видеть качество данных без ручных запросов.
- **Результат:** сверки факты = канон = витрина по дням, свежесть по кабинетам, карантин,
  доля нераспределённого; экран R10; недельная и месячная сверки — отдельной задачей
  `MarketplaceReconciliation` после этапа 8.
- **Выполнено:** гейты в cron на проде, первые 7 дней чистые или расхождения разобраны.
- **Приёмка:** каждое сравнение — красный гейт с суммой расхождения; описание в
  `docs/workflow/health-gates.md`.

### 8. WB

- **Задача:** WB в новом контуре.
- **Результат:** в wb-fetcher — реклама (`upd`, `fullstats`) и публикация фактов
  `sales-report.daily`; модуль `MarketplaceWb` (калькуляторы «поле / операция строки → `source_type`,
  `kind`» с тем же карантином и черновиком ИИ, что у Ozon; `deduction`, СПП из строки → `spp`; разнесение
  рекламы, итоги недельного отчёта); эталон WB (как этап 1); R1–R3 по обоим каналам. Заказы и
  остатки WB — «нет данных» (Q2), следующей задачей.
- **Выполнено:** R1–R3 по WB на проде, сверка с эталоном WB.
- **Приёмка:** как этапы 4–6 для WB; PHPat — `MarketplaceWb` не знает `MarketplaceOzon`.

## Дальше (отдельные задачи)

- `MarketplaceReconciliation`: недельные (отчёт WB, выплаты) и месячные (реализация Ozon, M-1,
  закрытые месяцы) сверки, отчёт МП ↔ выплаты в ДДС.
- `MarketplacePlProjection`: ОПиУ по дням из канона, затем отключение легаси-закрытия месяца.
  По `DATA.md` §9.3–9.4: проект — от кабинета; маппинг «`kind` [× канал | `source_type`] → статья»;
  шаблон и маппинг компании с версиями; признак `preset` / `custom`; перенос правил легаси со списком
  конфликтов; для `custom`-компаний — предложение ИИ из их дерева статей и экран у клиента, до решения
  строка «не сопоставлено».
- P2/P3 из `REPORTS.md`: каскад затрат, реклама, OOS, ABC, цены, воронка, внешние затраты.
