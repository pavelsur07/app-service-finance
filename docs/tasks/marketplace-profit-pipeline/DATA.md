## 2. Пробелы источников для P1

1. **WB реклама** в wb-fetcher (`/adv/v1/upd`, `fullstats`) — без неё нет МД2 по WB.
2. **Ozon оплата за заказ / ALL_SKU_PROMO** в ozon-fetcher — без неё МД2 Ozon занижает рекламу.
3. **WB заказы и остатки** в wb-fetcher — для % выкупа и OOS в R3; можно P1-минимум без них
   (% выкупа и OOS по WB — «нет данных» в первой версии).
4. **WB каталог** — связка nmId ↔ листинг уже есть в живой зоне листингов; ресурс нужен только
   для объёма (ключ хранения).
5. **Канал фактов** `source-fact-envelope` v1 — статус «проект»: Symfony пока не забирает
   факты ни из одного fetcher. Для снимков есть `service-snapshot` (pull без ack).

## 4. Модули

```
ozon-fetcher ─┐                     ┌─ MarketplaceOzon ─┐
              ├─ SourceFacts ───────┤                   ├─ MarketplaceOperations ─┬─ MarketplaceEconomics (R1–R3)
wb-fetcher  ──┘   (без знания МП)   └─ MarketplaceWb  ──┘   (канон, общий)        ├─ MarketplaceReconciliation (позже)
                                                                                  └─ MarketplacePlProjection (позже)
Листинги (живая зона Marketplace) ← переводчики, Economics
```

| Модуль | Причина изменений | Делает | Не делает |
|---|---|---|---|
| `SourceFacts` | контракт и транспорт | приём фактов (pull + ack), ревизии, карантин формата | не знает каналов; тип факта — непрозрачная строка |
| `MarketplaceOzon` | изменения Ozon | справочник типов начислений, компоненты → виды операций, отправление → SKU, разнесение рекламы Ozon (CPC, оплата за заказ, ALL_SKU_PROMO), контрольные итоги реализации, свой карантин | не пишет мимо фасада канона, не знает WB |
| `MarketplaceWb` | изменения WB | калькуляторы строки отчёта (комиссия, логистика, удержания), разбор `deduction`, СПП, разнесение рекламы WB, итоги недельного отчёта, свой карантин | не пишет мимо фасада канона, не знает Ozon |
| `MarketplaceOperations` | общая модель | канонические операции; запись только через фасад с проверкой | никаких правил каналов |
| `MarketplaceEconomics` | показатели и отчёты | витрина SKU × день, разнесение общих затрат с ключом, МД1 / МД2 / полная, R1–R3, журнал отправок R3 | не пишет в ОПиУ, не ходит к провайдерам |
| `MarketplaceReconciliation` | правила сверок (позже) | день / неделя / месяц по слоям и с ДДС | данные не чинит |
| `MarketplacePlProjection` | правила учёта (позже) | маппинг вид → статья с версиями, документы ОПиУ по дням | экономику не считает |

## 5. Каноническая операция

Поля: `company`, `channel`, `connection_ref` (кабинет), `listing` (пусто — затрата без SKU), `date`,
`source_type`, `kind`, `amount`, `quantity`, ссылки на исходные факты, версия правил переводчика,
ключ распределения (если сумма разнесена). Решения по полям — §9.

- `source_type` — код маркетплейса как есть (тип начисления / услуга Ozon, поле или операция WB);
  `kind` — наш вид. Оба обязательны: сверка с кабинетом идёт по `source_type`, экономика — по `kind`.
- Канон не сворачивает: одна услуга / один компонент источника — одна операция.
- Каждый `kind` привязан к уровню каскада: выручка / прямые (МД1) / реклама SKU (МД2) / общие
  (полная) / справочно. Виды могут быть специфичны каналу (магистраль Ozon, `deduction` WB).
- `amount` — `Money` (копейки + валюта, тип `money_amount_minor`), со знаком; сторно — тот же `kind` и
  `source_type` с обратным знаком и ссылкой на исходное начисление.
- Проекта ОПиУ в каноне нет — его даёт кабинет в проекции ОПиУ.
- Пересчёт — замена окна по (компания, канал, исходный документ или день) под advisory lock.
- Неизвестный тип или строка без калькулятора — карантин переводчика, в канон не попадает.
- Цепочка факты → переводчик → витрина — через отметку «окно грязное» в той же транзакции,
  не через `dispatch()` после commit.
- SKU в каноне — листинг канала, связанный с товаром каталога: один товар собирается по каналам.

## 9. Решения 13.11.2026 (вечер, Владелец): виды, выручка, ОПиУ, новые коды

### 9.1. Два кода у каждой операции

Свести все виды логистики в `logistics_to` нельзя — без исходного кода не сверить с кабинетом Ozon / WB.

| Поле | Чьё | Зачем | Пример |
|---|---|---|---|
| `source_type` | код маркетплейса как есть | сверка с кабинетом, детализация, аудит | `ozon:service:32`, `wb:delivery_rub` |
| `kind` | наш вид канона | экономика SKU, уровни, сравнение каналов | `logistics_to` |

- Справочник кодов маркетплейса (`source_type` → название как в кабинете, `kind`, статус) — в переводчике
  канала (`MarketplaceOzon`, `MarketplaceWb`); в каноне только `kind` → уровень.
- Два разреза одних строк: сверка с кабинетом — Σ по `source_type`; отчёты — по `kind` и уровню.
  Итог кабинета в обоих разрезах один.

### 9.2. Две выручки: без СПП и с СПП

Проверено на данных кабинета 3f4d87cc за октябрь 2026 (`SourceFacts`, 1014 строк продаж): в каждой продаже
by-day `commission.seller_price` = `sale_price` + `bonus` + `coinvestment` до копейки, без исключений.
Значит обе выручки Ozon есть **по дням** в начислениях by-day, ждать отчёт о реализации (2–8 число
следующего месяца) не нужно.

| kind | Источник Ozon (by-day) | Источник WB | Уровень |
|---|---|---|---|
| `sale` | `seller_price` (цена продавца) | строка отчёта | выручка (D2) |
| `spp` | `bonus` (скидка за счёт Ozon) | СПП строки | справочно |
| `coinvestment` | `coinvestment` (банк, ПВЗ) | — | справочно |

Выручка с СПП (цена покупателя, `sale_price`) = `sale` − `spp` − `coinvestment`: `bonus` и `coinvestment`
Ozon отдаёт положительными у продажи и отрицательными у возврата (пример: 2999 − 1818,74 − 11,69 = 1168,57),
канон хранит их как есть. Исправлено 14.11.2026 (было «`sale` + `spp` + `coinvestment`» — неверный знак).
Отчёт о реализации Ozon (помесячно по SKU, без дат) — **месячная сверка** Σ by-day за месяц, а не
источник СПП (октябрь: доли совпадают, разница ~3 % — база дат: доставки месяца против даты начисления,
разобрать на этапе 4).

### 9.3. Маппинг на ОПиУ и проекты «Озон» / «ВБ»

- Канон хранит кабинет (`connection_ref`), не проект. Проект — из настройки подключения
  (как сейчас `settings.project_direction_id`); переназначение проекта не пересчитывает канон.
- Ключ маппинга — `kind` (одна статья для Ozon и WB, разделение даёт проект); исключения — правило по
  `kind` × канал или по конкретному `source_type`, оно приоритетнее.
- Шаблон маппинга (преднастройка для всех компаний) и маппинг компании — с версиями и датой действия;
  смена маппинга пересчитывает проекцию ОПиУ окна.
- Правило компании помечено происхождением: `preset` (из шаблона, клиент не трогал — обновления
  шаблона приходят сами) / `custom` (клиент менял — шаблон его не перезаписывает).
- Перенос правил легаси «категория → статья» в «вид → статья» — по таблице уровней этапа 1;
  конфликты (категории с разными статьями слились в один вид) — списком клиенту.
- Всё это — модуль `MarketplacePlProjection`; канон и экономика маппинга не знают.

### 9.4. Новый код маркетплейса — через ИИ и подтверждение

```
новый код → карантин переводчика (в канон не идёт) → черновик ИИ → администратор платформы
  → справочник канала (+ новый kind с уровнем) + шаблон маппинга → повторный разбор карантина
  → компании с preset — статья из шаблона сразу;
    компании с custom — отдельное предложение ИИ из их дерева статей, решает пользователь компании
```

| | Платформа | Компания |
|---|---|---|
| Решает | название, `kind` (или новый вид), уровень, листинг, знак, статья шаблона | статья своего ОПиУ |
| Подтверждает | администратор платформы (админка) | пользователь компании |
| Контекст ИИ | словарь маркетплейса, существующие виды, похожие коды, примеры строк без сумм | дерево статей компании, её прошлые решения |
| Влияет на | экономику SKU всех компаний | только ОПиУ компании |

- ИИ только предлагает (через существующий ИИ-сервис и шлюз: учёт, лимиты, evals); применяет человек.
- Экономика SKU считается после решения администратора и не ждёт клиентов; до решения компании
  в её ОПиУ видна строка «не сопоставлено», а не потеря суммы.
- «Клиент менял сам» по умолчанию = компания меняла дерево статей ОПиУ или правило маппинга
  (тогда новые виды ей — на подтверждение). Пересмотреть, если Владелец решит иначе.
- Гейты: код в карантине без решения администратора дольше N часов — красный; предложение компании
  без ответа дольше N дней — предупреждение.
