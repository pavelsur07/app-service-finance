Черновик 13.11.2026. Исходник — утверждённый `REPORTS.md` (P1: R1, R2, R3, R10 и каскад
МД1 / МД2 / полная). Только планирование.

исходные факты; классификация, разнесение, экономика — в Symfony.

## 1. Какие факты нужны

| Факт | Нужен для | Ozon: ресурс fetcher | WB: ресурс fetcher |
|---|---|---|---|
| Продажа / возврат по SKU и дню (сумма, шт.) | выручка, шт., % выкупа | `ozon.finance.accrual-by-day` ✅ | `wb.finance.sales-report.daily` ✅ |
| Удержания МП по SKU (комиссия, логистика туда/обратно, эквайринг, приёмка) | МД1 | `accrual-by-day` ✅ | `sales-report.daily` ✅ |
| Удержания без SKU (хранение, подписки, штрафы кабинета, финпродукты) | полная прибыль | `accrual-by-day` ✅ | `sales-report.daily` ✅ (хранение / удержания — проверить разрез по nmId) |
| Справочник типов начислений | классификация, карантин | `ozon.finance.accrual-types` ✅ | — (названия операций в отчёте) |
| Реализация за месяц | сверка месяца | `ozon.finance.realization` ✅ | `sales-report.weekly` ✅ |
| Реклама CPC по кампании × SKU × день | МД2 | `ozon.ads.statistics` / `.daily` ✅ | **нет** — сейчас Symfony ходит в WB API сам (`LoadWbAdSpendDayAction`) |
| Оплата за заказ, ALL_SKU_PROMO | МД2 | **нет** — сейчас через `Ingestion` (statistic/orders) | — |
| Заказы по SKU и дню | шт. заказов, % выкупа | `ozon.orders.fbo` / `.fbs` ✅ | **нет** |
| Остатки по SKU на день | дней запаса, OOS в R3, ключ хранения (D3) | `ozon.stocks` ✅ | **нет** — сейчас `Inventory` сам |
| Каталог SKU (артикул, nmId/sku, баркоды, объём) | связка с листингом, ключ хранения | `ozon.products.*` ✅ | **нет** |

Свои данные Symfony (не из fetcher): листинги и связка с товаром, себестоимость на дату
(`MarketplaceInventoryCostPrice`, живая зона), налоговый профиль компании, теги/проекты.

## 2. Пробелы источников для P1

1. **WB реклама** в wb-fetcher (`/adv/v1/upd`, `fullstats`) — без неё нет МД2 по WB.
2. **Ozon оплата за заказ / ALL_SKU_PROMO** в ozon-fetcher — без неё МД2 Ozon занижает рекламу.
3. **WB заказы и остатки** в wb-fetcher — для % выкупа и OOS в R3; можно P1-минимум без них
   (% выкупа и OOS по WB — «нет данных» в первой версии).
4. **WB каталог** — связка nmId ↔ листинг уже есть в живой зоне листингов; ресурс нужен только
   для объёма (ключ хранения).
5. **Канал фактов** `source-fact-envelope` v1 — статус «проект»: Symfony пока не забирает
   факты ни из одного fetcher. Для снимков есть `service-snapshot` (pull без ack).

## 3. Решения (13.11.2026, Владелец)

- Q1: сначала Ozon целиком, WB — вторым этапом (после рекламы в wb-fetcher).
- Q2: P1 по WB допустим без заказов и остатков — % выкупа и OOS по WB «нет данных».
- Q3: модули — по причине изменений; на каждый канал свой переводчик, ниже канона каналы неразличимы.
- Каноническое поле — `channel` (тип: маркетплейс / свой магазин, подключение), не `marketplace`.

## 4. Модули

```
ozon-fetcher ─┐                     ┌─ MarketplaceOzon ─┐
              ├─ SourceFacts ───────┤                   ├─ MarketplaceOperations ─┬─ MarketplaceEconomics (R1–R3)
wb-fetcher  ──┘   (без знания МП)   └─ MarketplaceWb  ──┘   (канон, общий)        ├─ MarketplaceReconciliation (позже)
                                                                                  └─ MarketplacePlProjection (позже)
Листинги (живая зона Marketplace) ← переводчики, Economics
```

| Модуль | Причина изменений | Делает | Не делает |
|---|---|---|---|
| `SourceFacts` | контракт и транспорт | приём фактов (pull + ack), ревизии, карантин формата | не знает каналов; тип факта — непрозрачная строка |
| `MarketplaceOzon` | изменения Ozon | справочник типов начислений, компоненты → виды операций, отправление → SKU, разнесение рекламы Ozon (CPC, оплата за заказ, ALL_SKU_PROMO), контрольные итоги реализации, свой карантин | не пишет мимо фасада канона, не знает WB |
| `MarketplaceWb` | изменения WB | калькуляторы строки отчёта (комиссия, логистика, удержания), разбор `deduction`, СПП, разнесение рекламы WB, итоги недельного отчёта, свой карантин | не пишет мимо фасада канона, не знает Ozon |
| `MarketplaceOperations` | общая модель | канонические операции; запись только через фасад с проверкой | никаких правил каналов |
| `MarketplaceEconomics` | показатели и отчёты | витрина SKU × день, разнесение общих затрат с ключом, МД1 / МД2 / полная, R1–R3, журнал отправок R3 | не пишет в ОПиУ, не ходит к провайдерам |
| `MarketplaceReconciliation` | правила сверок (позже) | день / неделя / месяц по слоям и с ДДС | данные не чинит |
| `MarketplacePlProjection` | правила учёта (позже) | маппинг вид → статья с версиями, документы ОПиУ по дням | экономику не считает |

## 5. Каноническая операция

Поля: `company`, `channel`, `listing`, `sku`, `date`, `kind`, `amount`, `quantity`, ссылки на исходные
факты, версия правил переводчика, ключ распределения (если сумма разнесена).

- Каждый `kind` привязан к уровню каскада: выручка / прямые (МД1) / реклама SKU (МД2) / общие
  (полная) / справочно. Виды могут быть специфичны каналу (магистраль Ozon, СПП WB).
- Пересчёт — замена окна по (компания, канал, исходный документ или день) под advisory lock.
- Неизвестный тип или строка без калькулятора — карантин переводчика, в канон не попадает.
- Цепочка факты → переводчик → витрина — через отметку «окно грязное» в той же транзакции,
  не через `dispatch()` после commit.
- SKU в каноне — листинг канала, связанный с товаром каталога: один товар собирается по каналам.

## 6. Границы (PHPat с первого PR, устав каждого модуля в `ARCHITECTURE.md`)

- Зависимости только по схеме §4, вызовы через фасады; чужие таблицы не читаются и не пишутся.
- Классы с Ozon / WB — только в своём переводчике; переводчики не знают друг о друге.
- Ниже канона от канала остаётся только `channel`.

- Задача, не подходящая ни одному уставу, — обсуждение нового модуля, а не «немного» в ближайший.

## 7. Новый канал

| Шаг | Маркетплейс (Яндекс Маркет, Мегамаркет) | Интернет-магазин |
|---|---|---|
| 1. Загрузка | Go-сервис или провайдер в общем; ключи строк — в контракте | по сервису на источник: CMS / 1С (заказы), платёжный провайдер, служба доставки, рекламный кабинет |
| 2. Переводчик | `Marketplace{Name}`: справочники, калькуляторы, виды → уровни, карантин, контрольные итоги | `Store{Name}`: связывает источники по номеру заказа; выручка — по оплате или доставке |
| 3. Листинги | идентификация SKU канала в живой зоне листингов | артикул магазина ↔ товар каталога |
| 4. Регистрация | значение канала + строка в уставе | то же |

Экономика, отчёты, сверки и ОПиУ подхватывают канал без изменений.
