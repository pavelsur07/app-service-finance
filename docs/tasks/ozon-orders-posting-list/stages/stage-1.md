# Этап 1. Загрузка заказов Ozon в `ozon-fetcher` (raw)

Риск: MEDIUM (новые ресурсы сервиса; БД Symfony, ОПиУ и загрузка заказов в Ingestion не затрагиваются).
`stage_base_commit`: `4b1262a2a`. Ветка — своя на каждый шаг. Решения Владельца — `problem.md` §5, §7.

**Только загрузка**: ответы Ozon — в S3, журнал — в БД сервиса. Выдача фактов в Symfony, запись
`ingest_orders`, выключение старых `posting/*/list` и `posting/*/get` — не в этом плане: Symfony не
отключается (решение 21.10), импорт и выключение — отдельным решением (`problem.md` §7). Общий план
загрузки Ozon — `docs/tasks/marketplace-data-ingestion/plan-ozon.md` (этот файл — его этапы 1–2).
До этапа 2 Symfony по-прежнему получает 400 на `list` (#439/#442) и обновляет статусы через `get`.

## Решения для всех шагов

| Вопрос | Решение |
|---|---|
| Ресурсы | `ozon.orders.fbo`, `ozon.orders.fbs` — по дате создания (`filter.since/to`); `ozon.orders.fbo-status-changes`, `ozon.orders.fbs-status-changes` — по `filter.last_changed_status_date` |
| Методы | `POST /v3/posting/fbo/list`, `POST /v4/posting/fbs/list`; `limit=100`; `cursor` из ответа; `offset` и `dir` не шлются (Ozon молча их игнорирует и отдаёт первые 100) |
| Период | день МСК `YYYY-MM-DD`, окно `[00:00; 00:00 следующего дня)` МСК — тот же `period_key`, что у начислений, без миграции |
| Свежесть | сегодня — каждый проход планировщика (`PLAN_EVERY` = 1 ч); вчера и позавчера — раз в сутки |
| Догон | с `ORDERS_FROM` = `2026-10-18` (день перекрытия с последним успехом Symfony), низкий приоритет |
| Без тихой обрезки | признак продолжения без нового курсора, повтор курсора, больше 100 страниц за день — ошибка `invalid_response`, не «последняя страница» |
| Отказ метода | `obsolete_endpoint` → `resource_stop` + ERROR в GlitchTip с телом ответа (без ключей); остальные ресурсы работают |
| Очередь | одна `running`-задача на кабинет — как сейчас; заказы за сегодня — высокий приоритет, догон — низкий |
| Персональные данные | `with.analytics_data`, `with.financial_data` — да; `addressee`, `customer`, `legal_info` — не запрашиваются |

## Шаги

| Шаг | Что | Где | Прод меняется? |
|---|---|---|---|
| 1.1 | Клиент Ozon для списков отправлений | `ozon-fetcher`: `internal/ozon` | нет — код никто не вызывает |
| 1.2 | Ресурсы заказов в исполнителе | `ozon-fetcher`: `internal/executor`, `internal/ratelimit` | нет — задач на них никто не ставит |
| 1.3 | Окна заказов в планировщике | `ozon-fetcher`: `internal/planner`, `internal/config` | нет — ни один кабинет не объявляет ресурс |

### Шаг 1.1. Клиент Ozon для списков отправлений

**Результат.** В `internal/ozon` метод `FetchPostingList(ctx, creds, ref, scheme, filter, fromCursor,
firstPageNo, onPage)`: FBO → `/v3/posting/fbo/list`, FBS → `/v4/posting/fbs/list`; фильтр — по дате
создания или по дате смены статуса; страницы по 100 до `has_next=false`, каждая страница сразу
отдаётся в `onPage` с курсором следующей. Разбор терпимый: `postings`/`has_next`/`cursor` на верхнем
уровне или внутри `result`. Тело ответа при 4xx/5xx — в `APIError` (без заголовков).

**Чек-лист**
- [ ] Тест на моке: 3 страницы → 3 вызова `onPage`, курсоры по порядку, конец на `has_next=false`.
- [ ] Тело запроса: `limit=100`, `cursor`, `filter.since/to` (или `last_changed_status_date`); **нет**
      `offset` и `dir`.
- [ ] «Первая страница и тишина»: `has_next=true` без курсора → ошибка, не успех.
- [ ] Повтор курсора → ошибка; 101-я страница → ошибка.
- [ ] Продолжение с переданного курсора и номера страницы.
- [ ] 400 `{"code":9,...}` → класс `obsolete_endpoint`, тело ответа есть в ошибке; 400 другой → `invalid_request`; 429 → `rate_limit`.
- [ ] Ответ FBS с `postings` на верхнем уровне и с `result.postings` — оба читаются.
- [ ] `make ozon-fetcher-test` (пакет `ozon`, `-race`), `-vet`, `-lint` — зелёные.

### Шаг 1.2. Ресурсы заказов в исполнителе

**Результат.** `internal/executor` выполняет задачи `ozon.orders.fbo` и `ozon.orders.fbs`: день из
`period_key` → окно МСК → клиент из 1.1; каждая страница — в S3 и журнал до запроса следующей;
курсор задачи сохраняется. Лимитер знает дефолтный RPS для двух `list`-эндпоинтов. Задержка
`not_ready` для ресурсов задана.

**Чек-лист**
- [ ] Тест: задача дня → окно `2026-10-19T00:00+03:00 … 2026-10-20T00:00+03:00` в запросе.
- [ ] Тест: падение на 2-й странице → повтор продолжает со 2-й страницы, первая не перезапрашивается.
- [ ] Тест: тот же день повторно с тем же содержимым → `unchanged`; с другим → ревизия +1.
- [ ] Тест: `obsolete_endpoint` → `StopResource(ozon.orders.fbo, …)`, финансовые ресурсы не останавливаются.
- [ ] Ключ S3 — `ozon/{ref}/ozon.orders.fbo/{день}/…`.
- [ ] Дефолт RPS для `/v3/posting/fbo/list` и `/v4/posting/fbs/list` — в `ratelimit`, с тестом.
- [ ] Гейты Go зелёные.

### Шаг 1.3. Окна заказов в планировщике

**Результат.** `internal/planner` ставит задачи заказов кабинетам, которые объявляют ресурс:

позавчера — перезагрузка раз в сутки. `internal/config`: `ORDERS_FROM` (по умолчанию `2026-10-18`),
`ORDERS_TAIL_DAYS` (по умолчанию 2), проверка значений.

**Чек-лист**
- [ ] Тест: кабинет без ресурса в `resource_types` → задач заказов нет.
- [ ] Тест: кабинет с ресурсом, `now` = 21.10 12:00 МСК → ensure 18.10…21.10; refresh сегодня — в каждом проходе; хвост 19–20.10 — один раз за дату.
- [ ] Приоритеты: сегодня — высокий, догон — низкий; начисления за вчера не ниже, чем до изменения (тест на порядок захвата).
- [ ] Неверный `ORDERS_FROM` (не дата, в будущем) — ошибка конфигурации при старте.
- [ ] README: переменные `ORDERS_FROM`, `ORDERS_TAIL_DAYS`.
- [ ] Гейты Go зелёные.

### Шаг 1.4. Включение на одном кабинете

**Результат.** Ресурсы `ozon.orders.fbo` и `ozon.orders.fbs` объявлены в снимке кабинетов только
для одного кабинета — `3f4d87cc` (16 отправлений в неделю: малый риск лимитов). Механизм — список
компаний для ресурсов заказов в Symfony (параметр, пусто — никому). Карта покрытия подписывает новые
ресурсы. Контракт `marketplace-connections` v1 — новые `resource_type` в описании и `CHANGELOG.md`.
По живым ответам подтверждается форма FBO v3 и FBS v4.

**Чек-лист**

- [ ] Тест карты покрытия: подписи «Заказы FBO», «Заказы FBS».
- [ ] PHPStan, CS, strict_types, phpunit по изменённым тестам — зелёные.
- [ ] Прод (read-only): у `3f4d87cc` задачи `ozon.orders.*` за 18.10…сегодня — `done`; в `fetch_attempt` нет 400 по `posting/*/list`.
- [ ] Прод: отправлений в raw за 18.10…сегодня — порядка 2–3 в день (в `ingest_orders` за 12–18.10 — 16); форма ответа (`postings`, `has_next`, `cursor`) записана в `docs/ozon-api.md`.

### Шаг 1.6. Смены статусов

**Результат.** Ресурсы `ozon.orders.fbo-status-changes` и `ozon.orders.fbs-status-changes`: тот же
клиент с фильтром `last_changed_status_date`, те же окна и хвост; объявлены сначала для одного
кабинета, после проверки — для всех. Если Ozon не принимает фильтр (400 `invalid_request`), ресурс —
`failed_permanent` с ERROR, и смены статусов грузятся через актуальные версии `posting/*/get` в
`ozon-fetcher` по номерам заказов шага 1.5 (Symfony продолжает обновлять статусы сам).

**Чек-лист**
- [ ] Тесты Go: запрос с `last_changed_status_date` вместо `since/to`; 400 на фильтре → `failed_permanent`, `resource_stop` не вызывается (метод не снят), заказы по созданию продолжают грузиться.
- [ ] Прод (один кабинет): фильтр принят — задачи `done`; или отказ записан в `problem.md` с телом ответа.
- [ ] Прод (все кабинеты, если принят): задачи за 18.10…сегодня `done`; в окне есть отправления, созданные раньше окна (подтверждение, что фильтр работает по смене статуса).
- [ ] Итог этапа 1 и вопросы этапа 2 — в `problem.md`; README и `docs/ozon-api.md` обновлены.
