# Stage 1. Заказы и смены статусов Ozon — raw в `ozon-fetcher`

Риск: MEDIUM (новые ресурсы сервиса; БД Symfony и ОПиУ не затрагиваются). `stage_base_commit`:
`4b1262a2a`. Ветка `feat/ozon-fetcher-orders`. Поручение Владельца 21.10.2026 — решения §5.1–3
`problem.md`. Миграций БД сервиса не ожидается (`period_key` — день, как у by-day).

## 1. Какую задачу решаем

С 19.10 отправления Ozon не загружаются: Symfony ходит в отключённые `/v2/posting/fbo/list` и
`/v3/posting/fbs/list`. Решено переносить загрузку в `ozon-fetcher`, Symfony не править. Этап 1
возвращает поток данных: сервис грузит отправления и смены статусов новыми методами в raw S3, догоняет
разрыв с 18.10 и сам сообщает об отключении метода. Выдача фактов и импорт в `ingest_orders` — этап 2.

## 2. Решения этапа (технические, в рамках §5)

| Вопрос | Решение | Почему |
|---|---|---|
| Ресурсы | `ozon.orders.fbo`, `ozon.orders.fbs` — по дате создания (`filter.since/to`); `ozon.orders.fbo-status-changes`, `ozon.orders.fbs-status-changes` — по `filter.last_changed_status_date` | статус меняется неделями после создания; окно по созданию его не видит |
| Период | день МСК `YYYY-MM-DD`, окно `[день 00:00; следующий 00:00)` МСК; границу «включительно/исключительно» у Ozon проверить, перекрытие — на стороне импорта (ключ `posting_number`) | тот же `period_key`, что у by-day: без миграции, работает покрытие и перезагрузка с ревизией |
| Свежесть | сегодня — перезагрузка каждый проход планировщика (`PLAN_EVERY`, 1 ч); вчера + 2 дня — перезагрузка раз в сутки | как часовое обновление в Symfony; поздние отправления подхватываются хвостом |
| Догон | `ORDERS_FROM` (по умолчанию `2026-10-18`, день перекрытия с последним успехом) — задачи ensure, приоритет `Backfill` | разрыв с 19.10; более ранняя история уже в `ingest_orders` |
| Пагинация | `limit=100`, `cursor` из ответа, `has_next`; `offset`/`dir` не шлются; `has_next=true` без нового курсора, повтор курсора или > 100 страниц за день — `invalid_response`, не обрезка | защита от «тихих первых 100» (§4) |
| Лимит | свой дефолт RPS для `posting/*/list` в лимитере (консервативный, адаптация по 429 уже есть) | фаза 429 19.10 — лимит метода жёсткий |
| Группы | инвариант «одна `running`-задача на кабинет» сохраняется; финансы и заказы делят слот по приоритету: сегодня заказов — `CurrentMonth`, догон — `Backfill` | инвариант защищает лимит кабинета; отдельные слоты на группу — только если замер покажет вытеснение |
| Отказ метода | `obsolete_endpoint` → `resource_stop` + ERROR в GlitchTip с телом ответа (без ключей), остальные ресурсы работают | следующее отключение видно сразу |
| Фильтр статусов не поддерживается | 400 `invalid_request` на ресурсе status-changes → `failed_permanent`, ERROR; статусы остаются за Symfony `get` (работает) до решения этапа 2 | пробы до кода нет: ключи живут только в Symfony и памяти сервиса |
| Включение | ресурсы добавляются в `SELLER_RESOURCE_TYPES` снимка кабинетов (Symfony, контракт `marketplace-connections` v1 — аддитивно) и в подписи карты покрытия | сервис грузит только объявленные ресурсы; старый путь Symfony не трогаем |

## 3. Что будет результатом

- `internal/ozon`: `FetchPostingList(ctx, creds, ref, scheme, filter, fromCursor, firstPageNo, onPage)` —
  FBO v3 и FBS v4, терпимый разбор ответа (`postings`/`has_next`/`cursor` на верхнем уровне или в
  `result`); тело 4xx/5xx — в `APIError` для журнала (без заголовков и ключей).
- `internal/executor`: четыре ресурса, продолжение с курсора задачи, `NotReadyDelay` для них.
- `internal/planner`: окна заказов (ensure с `ORDERS_FROM`, сегодня — каждый проход, хвост — раз в
  сутки); `internal/config`: `ORDERS_FROM`, `ORDERS_TAIL_DAYS` (2).
- `internal/ratelimit`: дефолты RPS для двух `list`-эндпоинтов.
- Symfony: `MarketplaceConnectionsSnapshotBuilder::SELLER_RESOURCE_TYPES` + 4 типа, подписи в
  `CoverageHeatmapBuilder`; тесты снимка и карты.
- Документы: `services/ozon-fetcher/docs/ozon-api.md` (тела запросов, пагинация, лимит),
  README (ресурсы), контракт `marketplace-connections` v1 (список ресурсов), `ARCHITECTURE.md`
  (ServiceGateway/Marketplace — ресурсы снимка), `problem.md` — итог этапа.
- Тесты Go: мок Ozon — пагинация по курсору до `has_next=false`; тело запроса без `offset`/`dir`,
  `limit=100`; «первые 100 и тишина» (`has_next=true` без курсора) → ошибка; повтор курсора; предел
  страниц; продолжение после рестарта с курсора; 400 `code 9` → `resource_stop` и тело в журнале;
  400 фильтра статусов → `failed_permanent` без остановки остальных ресурсов; планировщик — окна,
  приоритеты, хвост раз в сутки, сегодня каждый проход.

## 4. Что считаем выполненной работой

На проде сервис по всем кабинетам грузит отправления FBO/FBS и смены статусов новыми методами в raw
S3, разрыв с 18.10 догружен, свежесть — до часа; ни один запрос не идёт в отключённые методы и не
содержит `offset`/`dir`; отключение метода останавливает ресурс и видно в GlitchTip с телом ответа;
финансовые ресурсы не замедлились; Symfony изменён только списком ресурсов снимка и подписями;
гейты зелёные, ревью без BLOCKER/IMPORTANT.
