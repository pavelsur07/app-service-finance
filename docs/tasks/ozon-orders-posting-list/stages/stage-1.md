# Этап 1. Загрузка заказов Ozon в `ozon-fetcher` (raw)

Риск: MEDIUM (новые ресурсы сервиса; БД Symfony, ОПиУ и загрузка заказов в Ingestion не затрагиваются).
`stage_base_commit`: `4b1262a2a`. Ветка `feat/ozon-fetcher-orders` — шаги 1.1–1.4 одним PR (код без
включения не меняет прод, включение — один кабинет). Решения Владельца — `problem.md` §5, §7.

**Только загрузка**: ответы Ozon — в S3, журнал — в БД сервиса. Выдача фактов в Symfony, запись
`ingest_orders`, выключение старых `posting/*/list` и `posting/*/get` — не в этом плане: Symfony не
отключается (решение 21.10), импорт и выключение — отдельным решением (`problem.md` §7). Общий план
загрузки Ozon — `docs/tasks/marketplace-data-ingestion/plan-ozon.md` (этот файл — его этапы 1–2).
Symfony по-прежнему получает 400 на `list` (#439/#442) и обновляет статусы через `get`.

## Живая проверка методов (21.10.2026, тестовый ключ Владельца только для чтения)

- FBO v3: `postings`/`has_next`/`cursor` — на верхнем уровне, курсор 40 символов, у последней
  страницы `has_next: false`, `cursor: ""`. FBS v4 — та же форма (у кабинета FBS нет).
- `limit: 101` — 400 на обоих методах.
- **Фильтр `last_changed_status_date` не работает**: без `since/to` — 400, вместе с ними FBO
  молча его игнорирует (2 348 = 2 348 отправлений за 30 дней). Отдельные ресурсы смен статусов
  сняты; статус приходит в каждом отправлении — смены видны перечитыванием дней по дате создания:
  сегодня — каждый час, 30 предыдущих дней — раз в сутки (`ORDERS_TAIL_DAYS`). Это дешевле обхода
  `posting/*/get` по номерам: у крупного кабинета ≈ 430 запросов в сутки.

Подробно — `services/ozon-fetcher/docs/ozon-api.md`.

## Решения для всех шагов

| Вопрос | Решение |
|---|---|
| Ресурсы | `ozon.orders.fbo`, `ozon.orders.fbs` — по дате создания (`filter.since/to`); смены статусов — перечитыванием тех же дней (фильтр по смене статуса Ozon игнорирует) |
| Методы | `POST /v3/posting/fbo/list`, `POST /v4/posting/fbs/list`; `limit=100`; `cursor` из ответа; `offset` и `dir` не шлются (Ozon молча их игнорирует и отдаёт первые 100) |
| Период | день МСК `YYYY-MM-DD`, окно `[00:00; 00:00 следующего дня)` МСК — тот же `period_key`, что у начислений, без миграции |
| Свежесть | сегодня — каждый проход планировщика (`PLAN_EVERY` = 1 ч); 30 предыдущих дней — раз в сутки (смены статусов), изменение дня — новая ревизия |
| Догон | с `ORDERS_FROM` = `2026-10-18` (день перекрытия с последним успехом Symfony), низкий приоритет |
| Без тихой обрезки | признак продолжения без нового курсора, повтор курсора, больше 1 000 страниц за день (по номеру страницы окна) — ошибка `invalid_response`, не «последняя страница»; 400 на продолжении сохранённого курсора — повтор окна с первой страницы |
| Отказ метода | `obsolete_endpoint` → `resource_stop` + ERROR в GlitchTip с телом ответа (без ключей); остальные ресурсы работают |
| Очередь | одна `running`-задача на кабинет — как сейчас; заказы за сегодня и хвост — обычный приоритет (не опережают финансовые отчёты), догон — низкий; снятый с кабинета ресурс не грузится и по уже поставленным задачам |
| Персональные данные | `with.analytics_data`, `with.financial_data` — да; `addressee`, `customer`, `legal_info` — не запрашиваются |

### Шаг 1.1. Клиент Ozon для списков отправлений — готово

**Результат.** `internal/ozon/postings.go`: `FetchPostingList(ctx, creds, ref, scheme, window,
fromCursor, firstPageNo, onPage)`; FBO → `/v3/posting/fbo/list`, FBS → `/v4/posting/fbs/list`; окно по
дате создания; страницы по 100 до `has_next: false`, каждая страница — в `onPage` с курсором следующей
до запроса следующей. Разбор — форма живого ответа (верхний уровень) и запасной `result`. Текст ошибки
Ozon (`message`) — в `APIError.Error()`, причина `invalid_response` — тоже (раньше терялась).

**Чек-лист**
- [x] Тест на моке: 3 страницы → 3 вызова `onPage`, курсоры по порядку, конец на `has_next: false`.
- [x] Тело запроса: `limit: 100`, `cursor`, `filter.since/to`, `sort_dir: ASC`, `with` без персональных данных; **нет** `offset` и `dir`.
- [x] «Первая страница и тишина»: `has_next: true` без курсора, полная страница без `has_next` и `cursor`, не-массив `postings` → `invalid_response`, страница не сохраняется.
- [x] Повтор курсора → ошибка; 1 001-я страница окна → ошибка, в том числе при продолжении после рестарта (ревью Codex).
- [x] Продолжение с переданного курсора и номера страницы; ошибка сохранения останавливает обход до следующего запроса.
- [x] 400 `code 9` → `obsolete_endpoint`; 400 `code 3` (как живой `limit: 101`) → `invalid_request`; 429 → `rate_limit`; текст Ozon — в ошибке, ключа нет.
- [x] Ответ с `postings` на верхнем уровне и в `result`; без `has_next` — продолжение по курсору, пустая страница — конец.
- [x] Живая проверка формы ответа (21.10, раздел выше).
- [x] `go test -race`, `go vet`, `golangci-lint` — зелёные.

### Шаг 1.2. Ресурсы заказов в исполнителе — готово

**Результат.** `internal/executor` выполняет `ozon.orders.fbo` и `ozon.orders.fbs`: день из
`period_key` → окно МСК (`Config.Location`, приложение передаёт Europe/Moscow) → клиент 1.1; каждая
страница — в S3 и журнал до запроса следующей; курсор задачи сохраняется. Лимитер: старт 0,2
запроса/с для обоих `list`. ERROR об отключённом методе несёт текст Ozon (`message`).

**Чек-лист**
- [x] Тест: задача дня `2026-10-19` → окно `2026-10-18T21:00Z … 2026-10-19T21:00Z`.
- [x] Тест: падение S3 на 2-й странице → повтор продолжает со 2-й, первая не перезапрашивается, хеш как у загрузки целиком.
- [x] Тест: все страницы уже сохранены прежней попыткой → Ozon не вызывается.
- [x] Тест: то же содержимое → `unchanged`; другое → ревизия +1.
- [x] Тест: `obsolete_endpoint` → `StopResource(ozon.orders.fbo)`, текст Ozon в логе; `invalid_request` → `failed_permanent` без остановки ресурса; на продолжении сохранённого курсора — повтор окна с первой страницы (ревью).
- [x] Тест: ресурс снят с кабинета в снимке → Ozon не вызывается, задача ждёт с курсором (ревью Codex).
- [x] Store (на Postgres): плановая перезагрузка задачи с незавершённой загрузкой откладывается до её итога (`refresh_pending`) — часовые проходы «сегодня» не сбрасывают прогресс между паузами 429, а проход хвоста не поглощается продолжением прежней попытки; касается и финансовых ресурсов (ревью Codex, 3 прохода).
- [x] Ключ S3 — `ozon/{ref}/ozon.orders.fbs/{день}/…`; кривой `period_key` → `invalid_task` без запроса.
- [x] Дефолт RPS для `/v3/posting/fbo/list` и `/v4/posting/fbs/list` — в `ratelimit`, с тестом.
- [x] Гейты Go зелёные.

### Шаг 1.6. Смены статусов — снят

Живая проверка 21.10: `filter.last_changed_status_date` FBO v3 игнорирует. Смены статусов
загружаются перечитыванием дней (шаг 1.3, `ORDERS_TAIL_DAYS` = 30). Проверка — в чек-листе 1.5:
у дней прошлой недели после ежедневного перечитывания растёт ревизия, когда отправления меняют
статус.
