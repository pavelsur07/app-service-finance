# Рефакторинг Cash по контекстам без изменения импорта 1С

## Статус и назначение

Техническое задание на будущую реализацию. Текущая поставка содержит только
документацию; рефакторинг и удаление кода ещё не выполнены. Поручение владельца:
подготовить ТЗ, технический план и чек-лист приёмки; **импорт 1С не трогать**.

Исходный аудит: `1d62bba73`; база документов: `44d2b1090` (`master`). Перед
реализацией повторить проверку достижимости кода и границ на актуальном master.
Классификация реализации — Large, четыре Stage; подготовка документов — Fast Path.

Документы:

- [Технический план](plan.md).
- [Чек-лист и доказательства приёмки](acceptance.md).
- [Защищённые пути импорта 1С](protected-paths.txt).

## Цель

Убрать подтверждённый неиспользуемый код, сгруппировать Action и вспомогательные
сервисы по контекстам, разделить файловый импорт и автоправила по обязанностям.
Результаты операций, финансовые правила, публичные контракты и обработка повторов
должны остаться прежними. Сокращение строк само по себе не является результатом.

## FR-1. Граница импорта 1С

Запрещены изменение, перенос, переименование и удаление:

- `ClientBank1CImportService`, `ImportBank1CStatementAction`, контроллеров
  `Bank1C*`, `Bank1CImportPage`, шаблонов, тестов и fixtures импорта 1С;
- общих зависимостей из `protected-paths.txt`, включая `AccountBalanceService`,
  `ImportLogger`, `CashImportAccountLock`, `CashImportLogLease`,
  `CashTransactionResponsibilityCenterResolver`, `CashSettlementSourceLifecycle`,
  `AccountMasker`, `CashFileImportPage`, `CashFileMappingValidator`, общую import
  session, сущности и репозитории Cash;
- DI-привязок, route names, ключей сессии и форматов, используемых путём 1С.

Нельзя извлекать общий dedupe/normalizer из 1С, подключать к 1С новые компоненты,
обновлять его импорты ради красивой структуры папок или маскировать перенос alias.
Исправление старого дефекта в 1С также вне этой задачи. При необходимости изменить
защищённый путь соответствующий рефакторинг оставляется FOLLOW-UP.

Список путей — минимальный предохранитель, а не разрешение менять любую другую
транзитивную зависимость. В Phase 0 проверить фактический граф вызовов 1С; найденные
дополнительные зависимости с риском изменения поведения включить в защиту. Новые
файлы, wiring или listeners не должны обходить запрет через изменение поведения
неизменённого кода. Регрессионные тесты 1С выполняются без изменения ожиданий.
Manifest разрешено расширять; удалять или сужать его существующие записи ради
прохождения проверки запрещено.

Особая общая зависимость: `Bank1CImportCommitController` получает `CashFileImportPage`
для `actorId()`, а Page получает `CashFileMappingValidator`. Поэтому даже файловый
валидатор с названием CashFile остаётся в прежнем namespace и не переносится.

## FR-2. Порядок удаления

1. Удалить целиком `Service/Import/Identity/CashTransactionExternalIdGenerator.php`
   после повторного поиска точного имени в tracked source/config/tests/templates/scripts,
   проверки атрибутов, интерфейсов и динамической регистрации.
2. Удалить только `CashTransactionToDocumentService::createOperationFromTransaction()`.
   `createDocument()` и используемые им helpers остаются; создание документов ОПиУ
   должно проходить существующие integration-тесты.
3. Перенести две проверки `findMatchingRule()` на `match()->rule`, затем удалить
   обёртку `CashTransactionAutoRuleService::findMatchingRule()`. Проверяемые случаи
   сохраняются, удаление тестов ради зелёного результата запрещено.
4. `AccountBalanceService::getBalanceOnDate()` и `getBalancesForPeriod()` **не удалять**:
   весь сервис защищён FR-1. Зафиксировать как отдельный FOLLOW-UP вне реализации.

Отсутствие прямого вызова не доказывает неиспользуемость tagged service. В частности,
`CashCategorizationResultConsumer` остаётся: он вызывается через consumer interface
и tagged iterator. Ветка обновления внешней операции в `AddCashTransactionAction`
также остаётся: возможен конкурентный вызов.

## FR-3. Размещение по контекстам

Сохранить слои модуля. Action размещать в `Application/<Context>/`, сервисы —
`Application/Service/<Context>/`, техническое чтение файлов — `Infrastructure/Import/File/`.
Контексты: `Transaction`, `Transfer`, `Accounts`, `Funds`, `Category`, `AutoRule`,
`AiCategorization`, `PaymentPlan`, `Document`, `Import/File`, `Import/BankStatement`,
`Import/Recovery`. Классы по конкретным назначениям перечислены в плане.

Правила переноса:

- имена классов и сигнатуры сохраняются, меняется namespace и ссылки на него;
- не создавать пустые каталоги, generic manager, интерфейс с одной реализацией
  или совместимые обёртки без действующего потребителя;
- Action 1С и защищённые общие сервисы остаются на текущих местах; неполная
  раскладка является намеренным результатом, а не недоделкой;
- DTO, Facade, Entity, Repository, Enum, Exception, Message и MessageHandler
  не переносить; FQCN сериализованных сообщений и payload неизменны;
- публичные методы `CashFacade` и типы `Application/DTO` не менять;
- у потребителей разрешено обновить import/type ссылки на перенесённые классы,
  если файл не защищён FR-1. Финансовую логику потребителей не менять;
- структуру и намеренные исключения описать в `site/src/Cash/README.md` и разделе
  «Cash: размещение классов» в `ARCHITECTURE.md`.

## FR-4. Файловый импорт

Разделить `CashFileImportService` на доступ к сохранённому файлу, потоковое чтение
строк, построение квот совпадений и существующую оркестрацию записи пачек. Использовать
`FileTabularReader`, `CashFileRowNormalizer`, `CashFileDescriptionPlan` и
`CashFileDescriptionMatcher`; не писать второй механизм нормализации или matching.

Сохранить:

- текущие storage keys и чтение legacy key без расширения, временные файлы и cleanup;
- текущую поддержку форматов и конвертацию XLS, без добавления новых форматов;
- первый лист, номера строк, пустые заголовки, обработку дат/чисел и mapping;
- текущие отдельные алгоритмы CSV для header/sample и для import rows. Их сведение
  к одному алгоритму является изменением поведения и выносится в FOLLOW-UP;
- `normalizedRows()` и `planInput()` как единую нормализацию для плана и применения;
- исходные dedupe hash, квоты по количеству и документам, две законные одинаковые
  операции, независимость от порядка строк и границ пачки;
- размеры пачек, callbacks коммита, границы транзакций, locks, журнал и пересчёт остатков;
- immutable description plan и его версию/формат, выбор пользователя, проверку
  snapshot, защиту ручного описания, атомарность description + audit + progress;
- обработку старых jobs без плана и новых jobs с планом, повторную доставку и resume;
- очистку состояния между заданиями одного worker, сохранность чужого UnitOfWork.

Записи, созданные 1С, могут участвовать в прежнем сценарии файлового сопоставления.
Менять правила этого взаимодействия, алгоритмы 1С или его зависимости запрещено.

## FR-5. Автоправила

Разделить `CashTransactionAutoRuleService` на сопоставление условий/победителей,
построение плана применения и предпросмотр со статистикой. Небольшая точка входа
сохраняет публичные методы, кроме удаляемой FR-2 обёртки. План применения остаётся
общим для preview и записи; preview не мутирует сущности и не делает flush.

Сохранить company isolation, порядок приоритетов и specificity, конфликты по полям,
пропуск непригодных операций, пары проект/ЦФО, режимы SAFE/REPLACE_AUTO_ASSIGNED,
provenance, ручные назначения, результаты и группировки preview. Не добавлять
запросов к БД/Company Facade на каждую строку вместо существующего batch snapshot.
Не менять async routing, debounce, payload, handlers и точки commit.

## NFR. Ограничения и критерий качества

- Нет schema/data migrations, изменения БД, UI/маршрутов, публичного API, денежных
  формул, статусов и бизнес-правил; нет новых зависимостей, CI/CD и production-действий.
- Новые сервисы не вызывают flush/commit, не скрывают транзакции и не используют HTTP/session.
- Переносы и выделение обязанностей — отдельные коммиты. Characterization-тесты
  сначала проходят на старом коде, затем на новом; red/green нужен для отдельно
  разрешённого bugfix, которого это ТЗ не содержит.
- Размеры классов — индикатор: ориентир для оркестратора до 250–300 строк, для
  компонента до 200–250. Превышение требует объяснения связности, не искусственного дробления.
- Full gates выполняются один раз на handoff; этапы используют профильные проверки.
