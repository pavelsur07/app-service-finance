# Онбординг новой компании — план

Статус: в работе, ветка `feat/company-onboarding`. Дата: 2026-10-20.
Класс: Large (несколько модулей, онбординг финансовых справочников). Ход работ — `checkpoint.md`,
планы и итоги этапов — `stages/stage-N.md`.

## 1. Задача

При создании компании автоматически заводить базовую настройку, чтобы пользователь
сразу мог вести учёт:

1. Денежный счёт «Основной счет» (BANK, RUB) и касса «Основная» (CASH, RUB).
2. Проект «Общий» (общий проект компании по умолчанию).
3. ЦФО «Общий».
4. Статьи ДДС — 4 основные категории.
5. Статьи ОПиУ — дерево по умолчанию.
6. Баланс — книга, структура статей и базовые учётные счета.

Компанию создают три пути, онбординг должен одинаково срабатывать во всех:

| Путь | Вход | Код |
|---|---|---|
| Регистрация | `/register` | `RegistrationController` → `CreateCompanyOwnerAccountAction` |
| Админка | создание аккаунта | `Admin\CreateAccountAction` → `CompanyFacade::createOwnerAccount` → `CreateCompanyOwnerAccountAction` |
| Ещё одна компания | `/company/new` | `CompanyController::new` |

## 2. Результат

- После любого из трёх путей у компании есть полный набор из п. 1, создан в одной
  транзакции с компанией: сбой любого шага откатывает создание целиком.
- Каждый шаг идемпотентен: повторный запуск ничего не дублирует и не трогает
  переименованное пользователем.
- Существующие компании дозаполняются командой с dry-run.
- Есть проверка целостности: какие компании без базовой настройки.
- `ARCHITECTURE.md` описывает онбординг как текущий контракт.

## 4. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Центральный оркестратор или события | События: каждый модуль сам заводит свои данные | Оркестратор знал бы все модули — циклы зависимостей, нарушение `ModuleBoundaryRules` |
| Синхронно или async | Синхронно, в транзакции создания | Данных мало; компания без статей хуже, чем ошибка создания. Async — только письмо |
| Ключ идемпотентности | Системный код или тип/код записи, не имя | Пользователь переименует «Основной счет» — поиск по имени создаст второй. Денежные счета — по типу (нет счёта типа → создать), статьи ОПиУ и Баланса — по коду |
| Шаблоны | Конфиг/провайдер с версией | Смена шаблона касается только новых компаний |
| Инициализация книги Баланса (дата начала, остатки) | Не автоматизировать | Это решение пользователя; нулевые остатки по умолчанию — ложные данные |
| Существующие компании | Дозаполнять командой, dry-run по умолчанию, `--execute` — через Владельца | Прод-данные |

Проект «Общий» оставлен как есть: «(Shared)» в постановке — пояснение, не новое имя.
Отдельного этапа по проекту и ЦФО нет; сквозной тест (Stage 4) проверяет, что они создаются.

**Принятые по умолчанию — подтвердить до начала Stage 1:**

- «4 основные категории ДДС» — текущие операционная / финансовая / инвестиционная /
  технические. Stage по ДДС не меняет набор.
- Учётные счета Баланса — минимум: «Расчётный счёт (основной)» на статье
  `CASH_BANK`, «Касса (основная)» на `CASH_REGISTER`.
- Дозаполнение существующих компаний — касса, ОПиУ, счета Баланса; только где
  данных этого вида у компании нет совсем.

## 5. Этапы и шаги

Каждый Stage — отдельный PR, локальные коммиты, push и PR одним шагом на handoff.

### Stage 1. Cash: счёт и касса переезжают в Cash

Без миграции и системного кода (решение Phase 0, см. `stages/stage-1.md`): счёт по
умолчанию создаётся, только если у компании нет ни одного активного или архивного
счёта этого типа. Это и есть подтверждённое правило «только где данных этого вида нет
совсем»; переименованный счёт не дублируется, потому что тип у него тот же.

1. `MoneyAccountRepository::existsByCompanyIdAndType()` / `existsByCompanyIdAndName()`.
2. `EnsureDefaultMoneyAccountsAction(string $companyId)`: «Основной счет» BANK RUB и
   «Основная» CASH RUB, UUID v7, `flush()` в Action.
3. Подписчик `EnsureDefaultMoneyAccountsOnCompanyCreated`.
4. Company перестаёт создавать `MoneyAccount`; ID в `CompanyOwnerMembershipCreator` —
   UUID v7.
5. Тесты и `ARCHITECTURE.md`.

### Stage 2. Finance: дерево ОПиУ при создании компании

1. `ApplyDefaultPLTreeAction(string $companyId)` в `src/Finance/Application/Action/`:
   вызывает `ImportPLCategoryTreeAction` с `DefaultPLCategoryTreeProvider::nodes()`,
   режим «сохранить существующее». Логика общая с `pl-tree:apply-default` — команду
   перевести на этот Action.
2. Проверить вложенность транзакции: `ImportPLCategoryTreeAction` вызывает
   `wrapInTransaction` внутри внешней транзакции создания — на DBAL 4 это savepoint;
   ошибка должна откатывать создание компании целиком (тест).
3. Подписчик `ApplyDefaultPLTreeOnCompanyCreated` (`src/Finance/EventListener/`).
4. `DomainException` из импорта не глотать: создание компании падает, это баг шаблона.
5. Тесты: новая компания получает дерево; повторный вызов — `created = 0`;
   формулы без статей (`unresolvedFormulaCodes`) — пусто для шаблона по умолчанию.
6. `ARCHITECTURE.md`: раздел Finance; `Changelog`.

### Stage 3. Balance: базовые учётные счета

1. Шаблон `config/balance/default_structure.yaml` → версия 3: у конечных статей
   необязательный список `accounts: [{code, name, allow_negative}]`;
   `CASH_BANK` → `ACC_MAIN_BANK` «Расчётный счёт (основной)»,
   `CASH_REGISTER` → `ACC_MAIN_REGISTER` «Касса (основная)».
2. `BalanceStructureTemplateReader` + DTO: читать и валидировать `accounts`
   (только у `kind: article`, коды уникальны в файле).
3. `EnsureBalanceAccountsAction(string $companyId)`: по коду статьи находит
   `article_id`, создаёт отсутствующие по коду счета записи `balance_accounts` +
   `balance_account_states` (balance 0) + аудит `system_seed`. Отдельно от
   `SeedBalanceStructureAction`, потому что тот выходит при наличии статей, а
   существующим компаниям нужны только счета.
4. Вызывать после seed структуры в том же подписчике
   `SeedBalanceStructureOnCompanyCreated`.
5. Книгу не инициализировать: `initialized = false`, экран настройки Баланса
   остаётся первым шагом пользователя.
6. Тесты: seed → 2 счёта на нужных статьях; повтор → без дублей; статья
   архивирована или удалена пользователем → счёт не создаётся, без исключения,
   warning в лог.
7. `ARCHITECTURE.md`: раздел Balance; `Changelog`.

### Stage 4. Сквозная проверка, дозаполнение, мониторинг

1. Функциональный тест `CompanyOnboardingFlowTest` по всем трём путям: проверяет
   2 денежных счёта, проект, ЦФО, статьи ДДС, дерево ОПиУ, структуру и счета
   Баланса. Второй тест — повторный dispatch `CompanyCreatedEvent` ничего не
   дублирует. Третий — сбой подписчика откатывает компанию.
2. Команда `app:company:onboard {companyId|--all} [--execute]`: вызывает те же
   Ensure-Action'ы по очереди; dry-run печатает, что будет создано; `flush()` и
   `clear()` порциями по компаниям; лог старт/финиш с `companyId` и счётчиками.
3. Query `CompaniesWithIncompleteOnboardingQuery` → `list<DTO>`
   (`companyId`, недостающие пункты); вывод в команде `--report`.
4. Прод: замер «до» (сколько компаний без кассы / ОПиУ / счетов Баланса),
   dry-run, `--execute` — через Владельца, замер «после», сверка.
5. Wrapper `codex-console` для команды — по образцу `pl-tree:apply-default`,
   только через Владельца.
6. `ARCHITECTURE.md`: общий раздел «Онбординг компании» — список подписчиков
   `CompanyCreatedEvent` и что каждый создаёт.
7. Исправить `src/Billing/README.md` §4.1: пробная подписка при создании компании
   не реализована — пометить как план, не как факт.

## 7. Риски

| Риск | Мера |
|---|---|
| Ошибка в шаблоне ОПиУ/Баланса ломает регистрацию | Шаблон валидируется до транзакции; тест на шаблон по умолчанию в CI |
| Создание компании замедлится (дерево ОПиУ) | Замер времени `/company/new` до и после; N+1 в импорте проверить |
| Дубли счетов у существующих компаний при дозаполнении | Счёт создаётся только при отсутствии счёта этого типа; уникальное имя `(company_id, name)` — пропуск с warning; dry-run |
