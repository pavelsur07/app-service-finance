# Оплата за заказ Ozon — этап 3 (исследование): второе списание типа 54

## Задача

У части кабинетов в начислении Ozon тип 54 («Promotion», категория `ozon_marketing_action`) за день две
операции, а отчёт по заказам продвижения в поиске (этап 1) сходится только с одной. Вторая остаётся без
товара: b57d7682 с 07.11.2026, 3f4d87cc с июня (большая часть типа 54). Нужно понять, что это за расход
и можно ли его разнести по SKU.

## Что уже установлено (11.11.2026, данные прода)

- `unit_number` начисления by-day — id рекламной кампании: у кликов (тип 41) он совпадает с id CPC-кампаний
  в `marketplace_ad_documents`. У типа 54 — id кампании «за заказ».
- Тип 54 по кампаниям (с 01.06.2026):

  | Кабинет | Кампания | Период | Сумма, ₽ | В отчёте по заказам |
  |---|---|---|---|---|
  | b57d7682 | 11383505 | 18.08–09.11 | 156 424 | да (SEARCH_PROMO, сходится до копейки) |
  | b57d7682 | 49903075 | 07.11–09.11 | 8 545 | нет |
  | 3f4d87cc | 13846607 | 12.08–01.11 | 12 294 | да (01.11 1 044 ₽) |
  | 3f4d87cc | 23660699 | 03.06–09.11 | 205 156 | нет |
  | 78f0cc9f | 13075769 | 20.06–31.10 | 426 650 | — (с ноября предоплата) |

- Ingestion запрашивает список кампаний только типов `SKU` и `SEARCH_PROMO`, MarketplaceAds — только `SKU`.
  Кампаний 49903075 и 23660699 нет ни в одном загруженном объекте. Отчёт расходов
  `/api/client/statistics/expense/json` грузится без фильтра — по всем кампаниям организации.

## Гипотеза

Вторая кампания — другого типа (не `SKU` и не `SEARCH_PROMO`) с оплатой за заказ, её заказы в
организационный отчёт `SEARCH_PROMO_ORGANISATION_ORDERS` не входят.

## Результат этапа

1. Read-only команда `app:ingestion:ozon-performance:campaigns-probe --company-id= [--from= --to=]`:
   - все кампании кабинета живым запросом `GET /api/client/campaign` без фильтра — id, тип, состояние и
     прочие скалярные поля, без названий; отметка «грузится ли Ingestion»;
   - расход по кампаниям за период из загруженного отчёта `expense` (последняя версия окна).
2. Владелец ставит команду в `codex-console`, прогон по b57d7682 и 3f4d87cc.
3. Вывод в этот файл: тип кампании, совпадение расхода `expense` с типом 54 по дням, есть ли у типа
   отчёт с SKU (заказы / объекты кампании). Решение — новый этап разнесения или отдельная категория.

## Предложение этапа 4

1. Живая read-only проба (тот же `campaigns-probe`, новый флаг) для `ALL_SKU_PROMO`: отчёт
   `statistic/orders/generate` с фильтром кампании, список товаров кампании, `statistics/daily`.
   Цель — найти разрез по SKU.
2. Есть SKU → разнесение тем же путём, что этап 2 (служебная кампания `all-sku-promo`).

   товары)» из `expense` вместо «расхождения»; в юнит-экономике — пропорционально выручке либо
   в «Прочих» (как сейчас) — решение Владельца.
