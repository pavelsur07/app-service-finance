# connection-auth-status — handoff

**Branch:** `feat/connection-auth-status` · **PR:** #2447 · **База:** `master`

## Зачем задача существовала

9 сентября разбор failed-очереди прода показал: 51 сообщение за сутки от одного
подключения Ozon, чей ключ маркетплейс перестал принимать 8 сентября в 09:35.
Обработчик помечал падающее задание причиной `auth` и уходил, а подключение
оставалось внешне здоровым — `is_active` истинно, `last_sync_error` пуст.
Крон продолжал ставить два задания в час по заведомо мёртвому ключу, каждое
падало в failed, а в кабинете не показывалось ничего: страница подключений
выводит ошибку только при `is_active = false`.

Три дыры сразу: состояние негде хранить, планировщик его не учитывает,
пользователь ничего не видит. Три Stage закрывают их по одной.

## Итог по Stage

**Stage 1 — состояние.** Enum `MarketplaceConnectionAuthStatus`, поля
`authStatus`, `authFailedAt`, `authFailureCount`, обратимая миграция, методы
фасада как точка входа для Ingestion. Три отказа подряд ломают подключение,
успех обрывает серию. Переход — один атомарный оператор на направление.

**Stage 2 — автостоп.** Обработчик пишет исход через фасад; сломанное
подключение выпадает из выборки крона через `executeSyncable()`, на который
переключён только `RunIncrementalCommand`; обновление ключа снимает состояние
одной транзакцией с самим ключом.

**Stage 3 — видимость.** Бейдж, строка с датой и кнопка «Обновить ключ» на
странице подключений; блок на дашборде; серверный запрет ручной синхронизации
по отвергнутому ключу.

## Ревью

Внутреннее: 6 итераций суммарно. Существенные собственные находки — частичный
индекс, невыразимый в маппинге Doctrine; отсутствие покрытия DQL; ложный алерт
в GlitchTip на каждой удачной синхронизации.

Внешнее (Codex, high): 4 раунда, 10 находок. Восемь подтверждены и исправлены,
включая две серьёзные: закрытый EntityManager после неудачного flush и
обходимый клиентский запрет ручной синхронизации. Одна отклонена с записанной
причиной (модульные права — предсуществующее свойство страниц, не дефект
задачи). Одна вынесена в FOLLOW-UP.

## Известные ограничения

- **FOLLOW-UP из Stage 1: исправление гонки не покрыто регрессионным тестом.**
  Тест, отличающий атомарный инкремент от чтения-правки-записи, обязан
  прочитать значение до чужого коммита и записать после — это требует форка
  процесса, оснастки для которого в репозитории нет. Записано честно, а не
  выдано за покрытие.
- Тексты и вёрстка проверены автотестами; вживую страницы не открывались.
- Порог 3 привязан к часовой каденции крона.
- Отсутствие модульных ограничений на странице подключений и дашборде —
  предсуществующее свойство, кандидат в отдельную задачу.

## Что произойдёт на проде после деплоя

Подключение `148a5bb6` компании `b57d7682` получит статус `failed` на третьей
неудаче, то есть в пределах трёх часов. С этого момента:

- крон перестанет ставить по нему задания, и failed-очередь перестанет расти;
- в кабинете появятся бейдж, строка с датой и кнопка «Обновить ключ»;
- на дашборде появится блок «Загрузка данных остановлена»;
- ручная синхронизация по этому подключению будет отклоняться с внятным
  сообщением.

Накопленные 52 сообщения в failed-очереди остаются: их перезапуск или удаление
— отдельное решение, к этой задаче не относится и требует отдельного одобрения.
Синхронизация кабинета возобновится только после замены ключа через форму.
