# Этап 5 — онлайн-оплата через ЮKassa

## Задача

Клиент сам оплачивает тариф картой (или другим способом ЮKassa) со страницы
«Тариф и оплата»; после оплаты период продлевается автоматически, без ручной
отметки администратора. Оплата по счёту из админки остаётся.

Решение №6 — ЮKassa (Владелец, 02.11.2026). Ключей магазина пока нет
(Владелец регистрируется): код готовится без них, онлайн-оплата скрыта, пока
`YOOKASSA_SHOP_ID` / `YOOKASSA_SECRET_KEY` пусты. Обмен с ЮKassa проверяется
заранее на мок-ответах в формате API v3.

## Результат

Ветка `feat/billing-yookassa`, один PR.

1. **Модель.** `BillingCheckout` (`billing_checkouts`): попытка онлайн-оплаты —
   `id` (UUIDv7 из скрытого поля формы: ключ повтора, `Idempotence-Key` ЮKassa
   и ID будущей `BillingPayment`), компания, тариф, срок, сумма из справочника,
   статус (`pending` / `succeeded` / `canceled` / `failed_to_apply`),
   `provider_payment_id` (unique), ссылка на оплату. `PaymentSource::YOOKASSA`.
   Миграция — новая таблица.
2. **Клиент ЮKassa** `Infrastructure/YooKassa/YooKassaClient`: `POST
   /v3/payments` (Basic `shopId:secretKey`, `Idempotence-Key`, `capture: true`,
   `confirmation.redirect`, `metadata`), `GET /v3/payments/{id}`. Чек 54-ФЗ —
   если задан `YOOKASSA_RECEIPT_VAT_CODE` (иначе не передаётся). Лог — метод,
   адрес, статус, время; без тела и ключей.
3. **`StartCheckoutAction`**: проверки до денег — онлайн-оплата включена,
   публичный тариф с ценой за срок, правила продления (с «Друга» онлайн не
   переводим; другой тариф при действующем платном периоде — нельзя);
   запись checkout (commit) → HTTP вне транзакции → ссылка на оплату (commit).
   Повтор той же формы — та же ссылка, второго платежа нет.
4. **`ApplyYooKassaPaymentAction`**: истина — `GET` платежа из ЮKassa, тело
   уведомления не доверяется. `succeeded` и сумма совпадает →
   `RegisterPaymentAction` (`source = yookassa`, `externalId` = ID платежа,
   `paymentId` = ID checkout) → checkout `succeeded`; `canceled` → `canceled`;
   доменный отказ при зачислении (деньги списаны, применить нельзя) →
   `failed_to_apply` + `error` (разбирает администратор). Повтор безопасен.
5. **Входы**: уведомление `POST /billing/yookassa/webhook` (публичный, только
   ставит `ApplyYooKassaPaymentMessage` → `async_sync`, отвечает 200); возврат
   с ЮKassa на «Тариф и оплата» — синхронная проверка статуса; cron
   `app:billing:yookassa-sync` каждые 10 мин — недождавшиеся `pending` за сутки.
6. **UI**: на «Тариф и оплата» владельцу — выбор тарифа и срока, «Оплатить
   онлайн» (только при заданных ключах и если продление допустимо); статус
   после возврата; в истории оплат и в админке — источник («Счёт» /
   «ЮKassa»); в админке — checkout'ы `failed_to_apply`.
7. **Тесты на мок-данных** (`MockHttpClient` с ответами в формате ЮKassa v3):
   создание платежа и ссылка, повтор формы, успешная оплата по уведомлению и по
   возврату, повтор уведомления, отмена, расхождение суммы, ЮKassa недоступна
   (429/5xx), отказ в зачислении → `failed_to_apply`, поддельное уведомление
   (`GET` говорит «pending») ничего не зачисляет.
8. `ARCHITECTURE.md`, `TASK.md`; инструкция включения для Владельца
   (`docs/tasks/billing/yookassa-setup.md`): ключи в GitHub variables/secrets (деплой прокидывает их в контейнеры), адрес
   уведомлений в кабинете ЮKassa, чеки, тестовый магазин.

## Что считаем выполненным

- Без ключей ничего не меняется для клиентов; с ключами тестового магазина
  оплата проходит целиком: форма → ЮKassa → возврат → период продлён.
- Деньги не теряются: каждый успешный платёж ЮKassa либо зачислен, либо виден
  администратору как `failed_to_apply`.
- Повтор формы, уведомления и cron не создают дублей.
- Тесты по таблице CLAUDE.md, гейты, внутреннее и внешнее ревью, CI зелёный.
