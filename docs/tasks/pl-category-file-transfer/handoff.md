# Handoff — перенос категорий ОПиУ файлом между компаниями и аккаунтами

Ветка: `task/pl-category-file-transfer`
Base commit: `7992b6e354c181ce7b086e098b20898bf1608007`
Draft PR: https://github.com/pavelsur07/app-service-finance/pull/2298

## Что умеет система после задачи

1. На экране категорий ОПиУ кнопка «Выгрузить в файл» скачивает дерево активной
   компании в JSON.
2. На экране импорта этот файл загружается в другую компанию — в том числе в
   другом аккаунте, где у пользователя нет никакого доступа к компании-источнику.
   Показывается предпросмотр «создать / обновить / без изменений», применение —
   отдельным подтверждением.
3. Прежний перенос «из другой компании этого же аккаунта» остался и работает
   через тот же движок.

## Stage 1 — развязка движка и выгрузка файлом

`ImportPLCategoryTreeAction` принимает источник как `list<PLCategoryTreeNode>` в
DFS pre-order вместо `sourceCompanyId` и больше не ходит в БД за деревом
источника. Это и было единственным препятствием переносу между аккаунтами.
Матчинг, диффы, освобождение кодов, порядок мутаций и транзакция не менялись.

`PLCategoryTreeExporter` — сущности → узлы → payload файла. `GET
/pl-categories/export/json` отдаёт скачиваемый файл. Из шаблона удалены ~50 строк
JS, выводивших JSON в `<pre>` для копипаста.

Проверка «источник ≠ цель» переехала в контроллер — туда, где вообще существует
понятие компании-источника.

Отчёт: `stages/stage-1.md`.

## Stage 2 — загрузка из файла

`PLCategoryTreeFileReader` — разбор и валидация файла, единственная граница
доверия задачи. `POST /pl-categories/import/upload` (предпросмотр) и
двухрежимный `POST /pl-categories/import/apply`. Предупреждение о формулах,
ссылающихся на коды, которых не будет в целевой компании.

Отчёт: `stages/stage-2.md`.

## Миграции

Нет. Схема БД не менялась ни на одном Stage.

## Изменённые публичные контракты

- `GET /pl-categories/export/json` — вместо голого массива категорий отдаёт
  конверт `{version, exportedAt, company, categories[]}` и заголовок
  `Content-Disposition: attachment`. Из элементов убраны `id` и `level`.
  Единственный известный потребитель — JS на экране категорий — удалён в этой же
  задаче. Обратной совместимости для внешних потребителей нет; читатель импорта
  голый массив по-прежнему принимает.
- `ImportPLCategoryTreeCommand` — `list<PLCategoryTreeNode> $sourceNodes` вместо
  `string $sourceCompanyId`.
- `ImportPLCategoryTreeResult` — добавлено поле `$unresolvedFormulaCodes`
  (со значением по умолчанию, аддитивно).
- `PLCategoryController` получил конструктор с DI; методы `index`, `new`, `edit`
  больше не принимают `PLCategoryRepository` аргументом.
- Новый маршрут `pl_category_import_upload` (`POST /pl-categories/import/upload`).

## Формат файла v1

```json
{ "version": 1, "exportedAt": "...", "company": "...",
  "categories": [ { "name": "...", "code": "...", "type": "...", "format": "...",
                    "flow": "...", "expenseType": "...", "weightInParent": "1.0000",
                    "isVisible": true, "formula": null, "calcOrder": null,
                    "sortOrder": 10, "children": [] } ] }
```

Категория обязана нести весь набор полей (`children` необязателен). Ограничения
читателя: 1 МБ, 1000 узлов, 5 уровней, уникальность `code` внутри файла,
однозначность одноимённых соседей, конечность и границы `decimal(10,4)`, границы
PostgreSQL `integer` для `calcOrder`/`sortOrder`, запрет нулевого байта. Отсутствующие поля берут дефолты сущности; неизвестные
ключи игнорируются; голый массив без конверта принимается как прежний формат.

Контракт зафиксирован в `ARCHITECTURE.md`, раздел «Finance: перенос дерева
категорий ОПиУ между компаниями».

## Риски

- Содержимое файла (до 1 МБ) возвращается в браузер в hidden-поле формы
  предпросмотра и приходит обратно в POST применения. Осознанный размен:
  состояние живёт на странице, показавшей предпросмотр, поэтому две вкладки не
  подменяют друг другу файл. Серверный слот на сессию этим свойством не обладал
  — на нём вкладка A импортировала файл, загруженный в вкладке B (подтверждено
  красным тестом). Поле не подписано: подделать его может только сам
  аутентифицированный пользователь (CSRF закрывает третью сторону), для своей
  же активной компании и с полной повторной валидацией — то есть ровно то, что
  он и так может сделать, загрузив другой файл.
- Предупреждение о формулах — эвристика на токенах, парсера формул в проекте
  нет. Возможны ложные срабатывания на именах функций; в тексте предупреждения
  это сказано. Импорт не блокируется (решение Владельца).
- Экспорт и импорт обходят дерево через ленивые `getChildren()`, то есть N+1 по
  числу узлов. Поведение существовало до задачи; при потолке в 5 уровней и
  сотнях узлов некритично.
- Экраны остались на существующей Tabler-разметке файлов, которые правились.

## Follow-ups, сознательно вынесенные за scope

- ДДС (`CashflowCategory`) и `BalanceCategory` — переноса файлом нет; у них нет
  и движка импорта. Формат v1 специфичен для ОПиУ и заранее не обобщался.
- Схема по-прежнему разрешает создать в компании две одноимённые категории у
  одного родителя. Импорт больше не выбирает из них произвольную (бросает
  понятную ошибку), но сам запрет на создание такой пары в формах не появился —
  это отдельная задача.
- Настоящий парсер формул вместо токенизации регуляркой (помечено
  `ponytail:`-комментарием в `ImportPLCategoryTreeAction`).
- Перевод экранов категорий ОПиУ на UI Kit.
- CLI-режим экспорта/импорта — Владелец решил не делать.

## Ручная приёмка (не выполнялась, требует браузера)

1. В компании A нажать «Выгрузить в файл» — скачивается `pl-categories-*.json`.
2. Переключиться в компанию B (можно в другом аккаунте), `/pl-categories/import`
   → загрузить файл → предпросмотр показывает счётчики и, при наличии формул,
   предупреждение.
3. Применить → дерево B совпадает с A; категории B, которых не было в файле, на
   месте.
4. Загрузить тот же файл повторно → «создать 0, обновить 0».
5. Загрузить битый файл → осмысленная ошибка, БД не изменилась.

Шаги 1–5 покрыты функциональными тестами через полный HTTP-цикл; визуальная
проверка вёрстки в браузере остаётся за Владельцем.
