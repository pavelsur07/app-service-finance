# ИИ: качество категоризации и статьи ОПиУ для затрат маркетплейсов

Поручение Владельца 06.11.2026: пункты 1 и 2 списка «что ещё поручить ИИ».

- **Часть A (пункт 2) — довести категоризацию ДДС.** Первый живой прогон COMPSHOP 06.11:
  из 200 операций статья предложена у 109, у 91 — `no_answer`. Из 91: 68 — переводы между своими
  счетами и в «налоговую копилку» («Перевод собственных средств…»), 5 — пустое назначение,
  остальное — кассовые расходы с коротким описанием («обед», «Стас оплатил ВПН…»).
  Переводы не должны получать статью ДДС вообще — их зря отправили и оплатили. Во входе модели
  нет ни одного примера того, как сама компания разносила похожие операции.
- **Часть B (пункт 1) — статья ОПиУ для категории затрат маркетплейса.** Сейчас ночной
  `cost-pl-mapping:sync-default` берёт статью из шаблона или единогласных образцов компании
  (#2605, #2608, #2609). Что не угадано — гейт `unmapped-check` 06:50 и ручное решение
  Владельца. ИИ предлагает статью из дерева ОПиУ компании, человек подтверждает.

Порядок: часть A раньше — она дешевле, тратит деньги уже сейчас и даёт замер качества, на
который опирается часть B.

## Решения по умолчанию (меняются ответом Владельца)

- Переводы распознаются до LLM, по признакам (этап 2); превращать их в настоящий перевод
  (парная операция, `is_transfer`) — вне задачи: это правка денежных данных, отдельная задача.
- Повтор `no_answer` — один раз на новую версию промпта, не чаще.
- Подсказку статьи ОПиУ подтверждает админ на существующем экране правил затрат; автоприменения
  нет. Клиентский интерфейс — после замера качества.
- Новый *сырой* тип WB/Ozon (нужен калькулятор или правка словаря) остаётся в коде: ИИ здесь не
  пишет код. Подсказка к такому типу в сообщении гейта — вне задачи, кандидат на следующий шаг.
- Все вызовы — через тот же учёт `ai_usage`, лимиты и журнал `ai_run`.

Автоприменение статей ОПиУ; разбор документов; комментарии к отчётам; пункты 3–6 разбора
лучших практик.
