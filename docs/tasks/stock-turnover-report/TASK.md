# stock-turnover-report: отчёт «Оборачиваемость» — где заморожены деньги

Дата: 2026-11-06. Владелец: задача поставлена в чате, цель уточнена там же —
«где заморожены деньги», не «что дозаказать». Классификация — Large
(кросс-модульная: Inventory + Marketplace + MarketplaceAnalytics; схемы и
миграций нет).

## Зачем

У селлера деньги лежат в товаре на складах маркетплейсов и на своём складе.
Сегодня система знает остатки по дням (Inventory), продажи по дням и
себестоимость (Marketplace/Catalog), но нигде не сводит их в ответ на вопрос
«сколько денег в товаре и какая часть из них мёртвая». Отчёт отвечает на него
и сразу показывает, что распродавать: первые строки списка.

## Результат

Страница `/inventory/stock-turnover`, вкладка «Оборачиваемость» в
разделе «Unit-экономика» (аналитика маркетплейсов), доступ `ROLE_COMPANY_USER`.

**Фильтры (GET):** `period` — окно продаж 30 | 60 | 90 дней (по умолчанию 30);
`source` — все | ozon | wildberries; `scheme` — все | fbo | fbs (по умолчанию
все: деньги заморожены на любом складе); `date` — дата остатков (по умолчанию
сегодня, будущая дата → сегодня); `bucket` — фильтр по корзине; `tags[]` —
теги листингов (любой из). Неверное значение любого параметра → значение по
умолчанию, как в остальных отчётах.

**Строка = листинг с ненулевым остатком** на дату. Колонки: товар (название,
SKU, артикул продавца), источник, остаток (шт, целое), продано за период (шт),
продаж в день, дней запаса, себестоимость за единицу, в деньгах (остаток ×
себестоимость), корзина. Сортировка — по сумме «в деньгах» по убыванию,
листинги без себестоимости — в конце списка.

**Корзины по дням запаса** (остаток ÷ средние продажи в день за период):

| Корзина | Условие |
|---|---|
| до 30 дней | дней < 30 |
| 30–60 | 30 ≤ дней < 60 |
| 60–90 | 60 ≤ дней ≤ 90 |
| свыше 90 | дней > 90 |
| нет продаж | продаж за период 0 при остатке > 0 |

«Заморожено» = корзины «свыше 90» + «нет продаж».

**Сводка над таблицей:** всего в товаре ₽; заморожено ₽ и доля в процентах;
деньги по каждой корзине; отдельно «без себестоимости: N листингов, M шт» —
эти остатки в суммы не входят и прячутся не должны, иначе итог занижен.
Сводка считается по всем строкам фильтра (источник, схема, теги, дата), фильтр
по корзине её не меняет — он только сужает таблицу.

**Происхождение остатков:** под сводкой строка «остатки Ozon на 05.11, WB на
05.11»; источник со снимком старше порога свежести (`StockSnapshotFreshnessPolicy`,
2 дня) в отчёт не входит, и об этом написано явно («остатки WB устарели,
последний снимок 01.11»). Без остатков вовсе — пустое состояние с подсказкой.

**Экспорт в Excel** — те же фильтры, все строки без пагинации, колонки как на
экране плюс listingId; корзина словами.

## Данные и правила расчёта

- Остатки: `InventoryFacade::getStockQtyByListingOnReportDate()` — остатки
  статуса «на складе» из последней сессии каждого источника на дату, уже
  включает FBS (Ozon fbs/rfbs, WB склад продавца). Получает новый необязательный
  параметр схемы (`FulfillmentScheme`), чтобы отчёт мог показать только FBO
  или только FBS. Товар в пути к клиенту/от клиента в «деньги в товаре» не
  входит (он уже продан или возвращается).
- Продажи: `MarketplaceFacade::getSalesAggregatesByListing()` за окно
  `[date − (period − 1), date]`; `quantity` — продано штук. Возвраты не
  вычитаются (решение по умолчанию: оборачиваемость меряет отгрузки; возвраты
  вернутся в остаток следующим снимком).
- Себестоимость: `MarketplaceFacade::getCostPricesForListingsOnDate()` —
  себестоимость листинга на дату отчёта (`marketplace_inventory_cost_prices`,
  та же, что в юнит-экономике; закупочная цена каталога не используется);
  нулевая цена = «без себестоимости».
- Арифметика: продаж/день = продано ÷ period (2 знака); дней запаса =
  floor(остаток ÷ продаж/день), null при нуле продаж; в деньгах = остаток ×
  себестоимость, `bcmul` scale 2. Остатки целые (`(int) round`).

## Подходы

1. **Сводный запрос «на лету» из трёх Facade** (остатки, продажи, себестоимость),
   строки собираются в PHP, пагинация в памяти. Без новых таблиц, cron и
   бэкфилла; объём — сотни-тысячи листингов на компанию. **Выбран.**
2. Ежедневный регистр «листинг × день × остаток × себестоимость» с cron и
   историей. Даёт тренды «заморозка по неделям», но это новая таблица,
   миграция, воркер и бэкфилл по снимкам с мая. Отложено до запроса на тренды;
   DTO отчёта из подхода 1 переиспользуется.
3. Колонки «дней запаса / в деньгах» внутри «Unit — Экономика». Дёшево, но
   смешивает два вопроса и не даёт сводки по корзинам. Отклонено.

Страница — Twig в легаси-слое по дизайн-системе (как `/inventory/stocks`),
не React: отчёт табличный, без интерактива; слой данных (Query + DTO) от UI
не зависит, React-страница возможна позже без переделки расчёта.

## Не в объёме

- Тренды и история заморозки по периодам (подход 2).
- Рекомендации по закупке, точка заказа, страховой запас.
- Учёт возвратов и товара в пути; стоимость хранения маркетплейса.
- Сохранение фильтров в сессии, уведомления.

## Приёмка

- Unit: все ветки `StockTurnoverPolicy` (границы 30/60/90, нет продаж, нулевой
  остаток), подписи `TurnoverBucket`.
- Integration: фильтр схемы в `StockQtyByListingOnDateQuery`; `StockTurnoverQuery`
  — строки, корзины, сводка, «без себестоимости», листинг с продажами без
  остатка не попадает, фильтр по тегам, устаревший источник.
- Functional: страница 200, значения по умолчанию при мусорных параметрах,
  фильтр корзины не меняет сводку, пагинация, экспорт xlsx (заголовок и строка).
- Гейты `site-stan`, `site-cs-check`, `site-cs-strict-types`, `site-test-unit`,
  functional/integration по затронутым модулям; скриншоты страницы на стенде.
- ARCHITECTURE.md: новые Query/DTO/Enum, параметр Facade, маршруты, Changelog.
