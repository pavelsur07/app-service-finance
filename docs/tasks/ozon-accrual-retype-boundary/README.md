# Ozon accrual: граница расхождения после перетипизации (GlitchTip #274)

## Симптом

Ночной гейт `app:ingestion:ozon-accrual:verify-rolling-refresh --days-back=45`
(06:45 MSK) падает с 08.09.2026 по всем четырём активным магазинам Ozon:
`amountMismatches` и `countMismatches` больше нуля одновременно. Он же даёт
30 из последних 100 событий supercronic (GlitchTip issue #2).

## Причина

Коммит `534b1fe2` «feat: normalize new marketplace cost types» (merge `101f38d4`,
PR #2440, в master **2026-09-07 16:46 MSK**) научил
`OzonAccrualByDayPreviewMapper::collectTypedFee()` брать тип из распознанной
категории Ozon вместо fallback-а `OTHER`.

`type` входит одновременно в:

- ключ группировки сверки — `GROUP BY DATE(occurred_at), type, direction`;
- естественный ключ upsert — `findByNaturalKey(companyId, source, externalId, type)`.

Превью считается живым кодом и даёт новый тип; канон, записанный до деплоя,
остался с `type = 'other'`. Группа `other` даёт «канон есть, превью нет», группа
`fee` — обратное. Отсюда расхождение сразу по обоим счётчикам и одинаково на всех
магазинах: маппер общий.

**Потери данных нет.** Суммы в канонe верные, неверно их разнесение по типам.

## Граница — 2026-08-28

```sql
SELECT shop_ref, max(d) FROM (
  SELECT shop_ref, DATE(occurred_at) d, count(*) FILTER (WHERE type='other') o
  FROM ingest_financial_transactions
  WHERE source='ozon' AND occurred_at >= '2026-07-01' GROUP BY 1,2
) t WHERE o > 0 GROUP BY 1;
```

| магазин | последний день с `type='other'` | строк `other` |
|---|---|---|
| `90b72323` | 2026-08-28 | 513 |
| `f01dd285` | 2026-08-28 | 295 |
| `148a5bb6` | 2026-08-28 | 5540 |
| `e6457d19` | 2026-08-30 | 965 |

### Почему именно этот день

Ночной `rolling-refresh --days-back=45` берёт **все 45 дней** и завершается —
глубина у него та же, что у сверки (проверено по `ingest_sync_jobs`: окна
`31.07…13.09` на 14.09, `02.08…15.09` на 16.09, все `completed`).

Но перевыборка не означает перенормализацию. Дедуп сравнивает `external_id`
**и хеш содержимого** (`StoreRawBatchAction`), поэтому:

- Ozon правит начисления задним числом → хеш чанка меняется → появляется новая
  запись сырья → она нормализуется текущим маппером → дни чанка перетипируются
  сами, без обнулённых строк (прунер сносит строки перекрытого снапшота целиком);
- содержимое совпало → `markSeen()`, и прежняя типизация остаётся.

Прямая улика: снапшот `accrual-by-day:2026-08-04:2026-08-10` у магазина
`90b72323` лежит в таблице **дважды** — выбран 14.08 и заново 18.09. Тот же
`external_id`, другой хеш.

Отсюда остаток после правки маппера — это дни, вышедшие из 45-дневного окна
раньше, чем Ozon успел их поправить. Он не обязан быть непрерывным до даты
деплоя, и считать его надо запросом, а не арифметикой от релиза:

| дата замера | грязный остаток | живых `other` |
|---|---|---|
| 16.09 | 01.07 … 28.08 (30.08 у `e6457d19`) | 295 / 513 / 965 / 5540 |
| 18.09 | **01.07 … 03.08** | 7 / 307 / 551 / 3338 |

За два дня дни 04.08–28.08 починились сами: ночная цепочка 18.09 в 02:35–02:38
перенормализовала чанки, по которым Ozon прислал правки. Дни до 03.08 в окно уже
не попадают и сами не починятся никогда.

Расхождение в самой сверке убывает на дневную порцию групп в сутки, потому что
старые дни выходят из её 45-дневного окна: 627 групп на 08.09 → 483 на 16.09.
К середине октября гейт позеленеет **сам, не починив данные**.

## Проверено и отвергнуто

- **Stale projection (runbook §10).** `count(DISTINCT raw_record_id)` по дню равен
  1 для всех дней — остатков от перекрытых снапшотов нет ни одного.
- **Retention выел сырьё.** Cron гоняет `raw:prune --dry-run`, окно 365 дней.
- **Методика сверки поехала.** `canonicalGroups`, `parityRows`, `includeSaleRefund`,
  `window()` не менялись с 30.06.
- **Загрузчик by-day в Marketplace.** Другой модуль и другие таблицы, в
  `ingest_financial_transactions` не пишет.
- **Миграции.** Ни одна в период не трогает `ingest_financial_transactions`.

Строки `other` несут реальные деньги (у `e6457d19` — 4,87 млн ₽). После починки

## Что сделано в этой задаче

1. **`--from` / `--to` у `rolling-refresh`.** Скользящее окно всегда упирается в
   сегодня, а чинить нужно участок, который из него вышел. Пара сделана по образцу
   `prune-stale-projection` / `normalize-stored`.
2. **Сверка перестала считать обнулённые строки.** Ремонт перетипизации гасит
   прежнюю строку через `voidForReplay()`: `amount_minor = 0` плюс отметка
   `_ingestion_voided`. `SUM` её не замечает, а `COUNT(*)` замечал — и один ремонт
   покрасил бы гейт по `countMismatches` навсегда. Регрессионный тест воспроизводит
   ровно это: на старом коде `countMismatches 1` при `amountMismatches 0`.

## Что осталось — отдельными задачами

### Починка данных (требует одобрения Владельца)

```bash
app:ingestion:ozon-accrual:normalize-stored \
  --company-id=<uuid> --shop-ref=<ref> \
  --from=2026-07-01 --to=2026-07-31 --include-done --dry-run   # затем --execute-inline
```

Объём считать запросом про живые строки старого типа перед каждым заходом: часть
дней чинится сама, и список сокращается. На 18.09 остаток — 01.07 … 03.08.

Между окнами сверять инварианты из замеров выше. Риск: Ozon правит начисления
задним числом, поэтому расхождение сумм с замерами нужно объяснить, а не просто
зафиксировать.

**Результат первого окна** (`f01dd285`, июль, 16.09) — метод подтверждён:

| | замер «до» | после |
|---|---|---|
| живых строк | 4771 | 4771 |
| сумма, коп. | 495 807 362 | 495 807 362 |
| живых `other` | 148 | **0** |
| дней с несколькими raw | 0 | 0 |

Перетипировано 148 компонентов: прежние строки погашены, новые вставлены с верным
типом, сумма и число живых строк не изменились. Общее число строк в таблице
выросло на 148 обнулённых — их и перестали считать в PR #2480.

#### Дубли на краях окна — дефект найден и закрыт

Ремонт второго магазина (`90b72323`, июль, 18.09) удвоил **8 строк на 6 310,05 ₽
за 25.06** — день вне окна ремонта. Причина: снапшот покрывает семь дней, но
авторитетом является лишь для части, а реплей писал строки за всё окно. На чужом
дне рядом с актуальной строкой появлялась вторая с другим типом: естественный ключ
содержит `type`, поэтому upsert не нашёл прежнюю и создал новую, а prune такую
пару не разбирает — он сносит перекрытых, а не перекрывающих.

Устранено на месте перенормализацией авторитета за 25.06: дублей ноль, суммы
совпали с замерами. Сама причина закрыта в коде — реплей ограничен
`selected_dates`, то есть днями, которыми снапшот владеет.

Сопутствующее: тот же прогон завёл 738 открытых `sum_mismatch`, из которых
настоящей была одна группа. Остальные — промежуточные состояния при
последовательной обработке 17 снапшотов; они закрываются при следующей
перенормализации своих записей.

#### Почему не повторная выборка — проверено на проде 16.09.2026

Первая попытка ремонта шла через `rolling-refresh --from/--to` и **не сработала**.
Дедуп сырья идёт по `external_id` **и хешу содержимого**
(`StoreRawBatchAction::findOneByCompanySourceExternalIdAndHash`). Ozon на
исторические окна вернул те же данные, поэтому записи были переиспользованы:
`last_seen_at` обновился на сегодня, `fetched_at` остался июльским,
перенормализации не произошло.

Из девяти чанков новую запись дал ровно один — `accrual-by-day:2026-08-26:2026-08-28`,
частичный хвостовой, чьего `external_id` раньше не существовало. Именно эти три
дня и починились: у магазина `f01dd285` строки `other` 295 → 275, расхождения
сверки 103 → 91. Инварианты при этом сохранились: 7532 строки и 847 226 465 коп.
без изменений, 0 обнулённых, 0 дней с несколькими raw.

Сдвиг границ окна не помогает: ночное скольжение создало семидневное окно с
началом на каждую дату, новыми могут быть только частичные хвосты.

Ошибка рассуждения, которую стоит не повторять: дни ≥29.08 вылечились не потому,
что повторная выборка что-то чинит, а потому, что по ним Ozon прислал правки —
изменился хеш, появилось новое сырьё, и нормализация прошла текущим маппером.

`--include-done` требует `--execute-inline`. Побочный эффект — обнулённые строки
(`voidForReplay()`); с PR #2480 их не считают ни гейт сверки, ни
`FinancialSummaryQuery` / `CoverageQuery` / `ReconciliationQuery`.

### Про «разрыв глубин» — версия снята

В первой редакции этого документа было записано, что сверка проверяет 45 дней, а
обновление достаёт около 10, и что это структурный дефект. **Это неверно.**
Обновление берёт все 45 дней и завершается; вывод был сделан по числу новых
записей сырья, без учёта того, что дедуп по хешу скрывает перевыборку с
совпавшим содержимым.

Настоящее ограничение другое и дефектом не является: день, вышедший из
45-дневного окна, не перевыбирается больше никогда. Поэтому любая правка маппера
оставляет хвост из дней, которые вышли из окна раньше, чем Ozon успел их
поправить, и этот хвост добирается вручную через `normalize-stored`.
