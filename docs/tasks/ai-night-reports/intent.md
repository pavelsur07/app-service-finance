# Intent: ночные ИИ-отчёты

Зачем это делается и по каким правилам принимать решения. Как именно — в
`TASK.md`. Если `TASK.md` расходится с этим файлом, верен этот файл, а
`TASK.md` правится.

Статус: план, к разработке не приступаем (2026-10-12). Решения интервью — в конце.

## Зачем

Пользователь хочет получить разбор своих финансов, на который у него нет
времени или навыков: что происходит с деньгами, где отклонения, что требует
внимания. Готовые отчёты VashFinDir показывают цифры, но не объясняют их.

Нужен **аналитик, который работает ночью**: вечером пользователь ставит
задание, утром получает файл с выводами, в которых каждая цифра настоящая.

## Каким должен быть результат

1. **Утром — готовый файл**, который можно переслать собственнику или
   бухгалтеру без правок.
2. **Каждой цифре можно доверять.** У каждого числа есть источник в данных
   компании, и оно перепроверено. Лучше честный отказ («не удалось проверить»),
   чем отчёт с одной неверной суммой. Это главный критерий качества,
   важнее полноты и красоты.
3. **Ответ на вопросы шаблона** (на старте — обзор ДДС за период), а не
   общий обзор «обо всём». Свободного текста на старте нет: так проще
   проверять и меньше поверхность для недоверенного ввода.
4. **Видно, что произошло**: статус задания и понятная причина, если отчёт
   не получился.

## Границы: как поступать и почему

Каждое правило — что делать, и почему это важно. Защита строится на
ограничении возможностей (что агенту технически доступно), а не на тексте
промпта: данные компании (названия, комментарии) недоверенные и могут
содержать инструкции.

| Как поступать | Почему |
|---|---|
| ИИ только читает данные компании. Не хватает данных — пишет в отчёте «не удалось проверить», а не дополняет и не исправляет | данные — бухгалтерия клиента; одна ошибочная запись дороже любого отчёта |
| Доступ к данным — только к компании задания, на время задания | утечка между компаниями — инцидент с клиентом, а не баг |
| Ночная работа укладывается в окно и лимиты ресурсов; не уложилась — задание ждёт следующей ночи | прод и разработка важнее скорости отчёта |
| Агент работает в отдельной учётной записи, видит только свой каталог и API прода | на машине лежат прод-ключи, `.env` с боевым DSN и репозиторий |
| Воркер работает на подписке Владельца и укладывается в ночное окно; упёрся в лимит подписки — задание ждёт следующей ночи, а не падает | лимиты подписки общие с дневной разработкой, и днём они нужнее |
| В логи пишутся события, длительности и счётчики; содержимое (промпты, данные, ответы) — никогда | логи и GlitchTip читают люди и внешние сервисы; это данные клиента |

## Вне рамок

- Онлайн-режим «отчёт за минуту» — только ночная очередь.
- Любая запись в данные компании, включая «подсказки» и автоисправления.
- Изменения модулей `Ai` и `Api` (ключи компаний).
- Отдельная машина для воркера — заложена в архитектуру, но не делается сейчас.

## Самостоятельность при разработке

До handoff — всё по `AGENTS.md` §3.1, без промежуточных вопросов. Любые
действия на проде (создание токена воркера, включение функции) и установка
воркера на машину через sudo — только после «merge and deploy» и явного
поручения Владельца.

## Почему на этой машине и почему многошагово

- Задача — не «один вызов LLM», а работа аналитика: спланировать, собрать
  данные, посчитать, **перепроверить себя**. Для этого нужен агент с
  инструментами (Claude Code), а не вызов API из PHP.
- Эта машина уже есть и ночью простаивает. Отдельная машина сейчас — лишняя
  инфраструктура до того, как ценность подтверждена.
- **Позже воркер переедет** на отдельную машину. Поэтому с первого дня он не
  зависит от этой машины: ни от репозитория, ни от dev-стека, ни от её доступа
  к проду. Переезд не должен требовать изменений на проде.

## Как решать спорные вопросы

| Конфликт | Приоритет |
|---|---|
| Точность ↔ полнота отчёта | точность: убрать непроверенное, а не показать |
| Безопасность ↔ удобство агента | безопасность: ограничивать возможности, а не надеяться на промпт |
| Дневная работа ↔ успеть всё за ночь | дневная работа: не успели — значит следующей ночью |
| Простота ↔ гибкость | простота: один шаблон, свободный текст — отдельным решением после пилота |
| Скорость ↔ точность модели | Sonnet на всех шагах; если пилот покажет ошибки точности — менять модель, а не ослаблять проверку |

## Когда разработка готова

Агент проверяет сам, без Владельца: автоматические тесты из `TASK.md` §10
(изоляция компаний, недоступность записи, lease и идемпотентность, окно и
лимиты воркера) зелёные, плюс сквозной прогон на локальном стеке с
фикстурной компанией: задание → ночной прогон → xlsx, где каждая цифра
совпадает с данными фикстуры. Финальную сверку диффа с `TASK.md` и этим
файлом делает рецензент в чистом контексте. Тесты и критерии не удаляются и
не ослабляются ради «готово».

## Как поймём, что сработало (пилот, 2 компании, 7 ночей)

- Отчёты готовы к утру в ≥ 80 % ночей, когда были задания.
- **Ноль** неверных цифр в выданных отчётах (выборочная ручная сверка
  Владельцем).
- Сверка: в каждом отчёте 10 случайных чисел с источниками.
- Владелец сам переслал бы отчёт собственнику без правок хотя бы в половине
  случаев.
- Нет инцидентов на проде и жалоб на работу dev-машины; ночная работа не
  мешает дневной разработке по лимитам подписки.

Если пилот провален по точности, функцию не расширяем, пока причина не устранена.

## Решения

Принято (2026-10-12):
- Агент работает на этой машине, многошаговый анализ с проверкой.
- Перенос на отдельную машину заложен в архитектуру, но не делается сейчас.
- План зафиксирован, к разработке не приступаем.

Интервью Владельца (2026-10-12):
- Подписка Владельца, без дополнительного лимита расходов.
- Sonnet 5.5 на всех шагах по умолчанию; провайдер выбирается: Anthropic
  (Claude Code), OpenAI (Codex CLI) или Kimi (Kimi CLI). Компании разрешаются только провайдеры, на которых есть
  согласие клиента; новая модель допускается только после eval.
- Только шаблон «обзор ДДС», без текста пользователя.
- Согласие на передачу данных провайдеру Владелец получает у пилотных
  клиентов сам; в продукте текста нет.
- ИИ-обработку для компании включает администратор в admin-разделе;
  пилот — 2 компании, 7 ночей.
- ОПиУ и юнит-экономика: MCP читает сразу, шаблоны — после пилота.
- Ставит, видит и удаляет отчёты только владелец компании.
- Без уведомлений: только статус в UI. Только xlsx.
- Период — месяц или квартал за последние 12 месяцев; запуск только по
  заданию; хранение в S3 бессрочно, скачивание только через приложение.
- «Обзор ДДС»: приток/отток по статьям, динамика к прошлому периоду,
  остатки и кассовые разрывы, аномалии и проблемы учёта.
- Читатель: простой язык, больше деталей; главные выводы на первом листе,
  детали в таблицах.
- Один отчёт на период: новый заменяет предыдущий.
- ИИ-обработку включает только `ROLE_SUPER_ADMIN`.
- Критерии пилота подтверждены.

Интервью Владельца (2026-10-13):
- Платные API-ключи не используются: работаем на CLI, подключённых по подписке.
- Проверяющий шаг по умолчанию на том же провайдере.
- Eval-набор собирает агент, эталонные ответы утверждает Владелец до пилота.
- Ручная сверка в пилоте — 10 случайных чисел из каждого отчёта.
- Stage 1 — по отдельному поручению; пилотные компании — к Stage 6.
- Выдержку из условий подписки готовит агент, решение — за Владельцем.

Принимаемый риск: подписка делит лимиты с разработкой, а её условия для
автоматизации её ограничивают (`subscription-terms.md`); запасной путь —
CLI другого провайдера без релиза кода.
