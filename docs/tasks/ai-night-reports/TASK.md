# TASK: ИИ-отчёты по заданию с прода — ночной воркер на dev-машине

Статус: **план зафиксирован, к разработке не приступаем** (решение Владельца 2026-10-12).
Решения §9 приняты (интервью 2026-10-12). Stage 1 — только по отдельному поручению.

Источник: бриф Владельца в чате 2026-10-12. Класс **Large**: новый модуль, схема,
публичный (машинный) API, cron/воркер, инфраструктура вне прода.

## Контекст

Пользователь VashFinDir на проде ставит задание: отчёт по шаблону за период
(на старте один шаблон, без свободного текста). Ночью задание обрабатывает ИИ-агент на dev-машине
(`ams-1-vm-2a0q`, Claude Code 2.1.x): несколько шагов анализа по данным компании,
затем независимая проверка результата. Готовый файл возвращается на прод, и
владелец компании видит его в списке заданий.

Решение Владельца: агент работает **на этой машине**, потому что нужны
многошаговый анализ и проверка, а не один вызов LLM. Позже воркер **может уехать
на отдельную машину**, поэтому он не должен зависеть ни от репозитория, ни от
dev-окружения, ни от прод-доступа этой машины.

Что уже есть и переиспользуется:
- `src/Mcp`: `McpToolInterface`, `ToolRegistry`, инструменты ДДС (`Cash*Tool`),
  `isWriting()`. `companyId` в них берётся из контекста процесса, а не из
  аргументов. Транспорт сейчас только stdio (`app:mcp:serve`).
- `src/Api`: stateless firewall `/api/external/v1/`, Bearer-ключи с SHA-256 и
  constant-time сравнением, rate limiter, Problem Details. Это образец
  аутентификации, но **не** сами ключи компаний (см. §4.3).
- `App\Shared\Service\Storage\ObjectStorageInterface` + `FlysystemS3ObjectStorage` —
  файл результата хранится в S3 (§2.6).
- `phpoffice/phpspreadsheet` — рендер xlsx на проде.
- `ApiOwnerGuard` (`src/Api`) — образец проверки «фактический владелец компании».

## Цель

1. Владелец компании ставит задание на отчёт и видит его статус.
2. Ночью воркер выполняет задания по одному: план → сбор данных → анализ →
   проверка → структурированный результат.
3. Прод принимает результат, рендерит xlsx и сохраняет его; статус и файл
   видны в списке заданий. Уведомлений нет (§9).
4. Ничто из этого не мешает ни проду, ни работе на dev-машине.

## Не цели

- ИИ ничего не пишет в данные компании: ни операций, ни правил, ни справочников.
  Write-инструменты MCP воркеру недоступны совсем.
- Нет онлайн-режима «отчёт за минуту»: только ночная очередь.
- Не меняем существующие модули `Ai` (`AiAgentRunner`, `AiSuggestion`) и `Api`
  (ключи компаний).
- Нет прод-доступа воркера через SSH, `codex-*` wrapper'ы, `codex-psql-ro` или
  прямого подключения к БД. Только HTTPS API, описанный ниже.

## 1. Общая схема — pull

```
ПРОД                                           ВОРКЕР (dev-машина, позже — отдельная)
────                                           ──────────────────────────────────────
UI: задание → AiReportJob(queued)
                                     ◄──  00:30 МСК timer: POST /claim  (worker token)
выдаёт ≤1 задание + job token,       ──►
lease 60 мин
                                          claude -p  (план → сбор → анализ)
MCP over HTTP, read-only,            ◄──    инструменты только этой компании
company из job token                        (job token)
                                          claude -p  (проверка: verifier)
POST /heartbeat (продлить lease)     ◄──
POST /result  (JSON по схеме)        ◄──
валидирует → рендер xlsx →
S3 → status=done (видно в UI)
```

Прод **не подключается** к воркеру. У воркера только исходящий HTTPS к одному
хосту. Поэтому перенос на другую машину — это скопировать каталог воркера и
токен; на проде ничего не меняется.

### 2.2 Состояния

```
queued ──claim──► claimed ──result ok──► rendering ──► done
  ▲                  │  └──result fail/verify fail──► failed
  └──lease истёк, attempts<3──┘
                     └──lease истёк, attempts=3──► failed (lease_exhausted)
queued ──пользователь отменил──► cancelled
queued ──старше 7 суток──► expired
done ──владелец удалил отчёт──► deleted (объект удалён из S3)
done ──новый отчёт за тот же период done──► superseded (объект удалён из S3)
```

- Переходы — только в Domain/Action, с инвариантами. Недопустимый переход →
  `AiReportInvalidTransitionException` (409).
- Возврат по lease делает cron-команда `app:ai-report:reclaim-expired`
  (каждые 10 мин, lock), а не воркер.
- Результат с job token, который уже не текущий (lease переназначен),
  отклоняется 409 `job_token_superseded`.

### 2.3 UI

- «Отчёты → ИИ-отчёты»: форма (шаблон; период — месяц или квартал из списка
  за последние 12 месяцев), список заданий компании с
  Pagerfanta, статусами, ошибкой (видимо, а не в тултипе) и ссылкой на файл.
- Раздел виден только компаниям, которым администратор включил ИИ-обработку
  (§2.4).
- Квоты (§9): **один отчёт на пару «шаблон + период»**. Повторный заказ
  того же периода ставит новое задание; когда оно `done`, предыдущий отчёт
  за этот период переходит в `superseded` и его файл удаляется из S3. Пока по
  периоду есть задание в `queued`/`claimed`, новый заказ — 422
  `ai_report_already_in_progress`. Не больше 3 заданий в очереди на компанию →
  422 `ai_report_quota_exceeded`.
- Ставить задания, видеть список, скачивать и удалять отчёты может **только
  фактический владелец компании** (проверка внутри Actions по образцу
  `ApiOwnerGuard`, плюс IDOR по `activeCompany`); участник — 403.
- Запуск только по заданию владельца, без автоматического расписания (§9).
- Отчёты хранятся бессрочно; владелец может удалить отчёт вручную (файл
  удаляется из S3, задание остаётся со статусом `deleted`).
- Текст в UI: «Отчёт будет готов к утру».

### 2.4 Включение ИИ-обработки — admin

Признак «ИИ-обработка» ставит **администратор платформы** в admin-разделе
(`/admin/ai-reports`, только `ROLE_SUPER_ADMIN`: включение означает
передачу данных клиента в Anthropic — это решение платформы); ни агент, ни владелец компании его не
включают.

- Entity `AiReportCompanySetting` (`ai_report_company_settings`) в модуле
  `AiReport`, а не поле в legacy `Company`: `companyId` (unique), `enabled`,
  `allowedProviders` (`anthropic` / `openai` / `kimi`, §3.5), `changedAt`,
  `changedByUserId`. Нет записи — выключено; включение без провайдеров
  запрещено (422).
- Страница: список компаний с включённой обработкой; поиск компании по
  публичному ID через `CompanyFacade::findByPublicId()`; кнопки «Включить» /
  «Выключить» и выбор разрешённых провайдеров (POST, CSRF). Контроллер живёт в модуле `AiReport` под маршрутом
  `/admin/…` — так модуль `Admin` не импортирует чужие классы.
- Каждое изменение — запись в `Shared\Entity\AuditLog` (кто, когда, компания,
  было/стало) в одной транзакции с изменением.
- Выключение: новые задания не принимаются (422 `ai_reports_disabled`),
  задания в `queued` переходят в `cancelled`, уже готовые отчёты остаются
  доступны владельцу компании. `claim` проверяет признак повторно и не выдаёт
  задание выключенной компании.

### 2.5 Шаблон `cashflow_review` — «Обзор ДДС»

Решение Владельца 2026-10-12. Период — месяц или квартал (§2.1), сравнение — с
предыдущим периодом той же длины.

| Раздел | На какой вопрос отвечает | Данные (MCP, §4.2) |
|---|---|---|
| Приток и отток | сколько пришло и ушло, чистый денежный поток; крупнейшие статьи прихода и расхода | обороты по статьям ДДС за период |
| Динамика | что выросло и упало к прошлому периоду и насколько | обороты по статьям за текущий и прошлый период |
| Остатки и разрывы | остатки по счетам на начало и конец; дни с минимальным остатком; были ли кассовые разрывы | остатки по счетам на даты, помесячная/подневная динамика |
| Аномалии и учёт | необычно крупные платежи; операции без статьи; новые контрагенты с крупными суммами | операции ДДС за период (read), справочник статей |

**Читатель и стиль.** Простой язык, без бухгалтерских терминов без
расшифровки, но с деталями. Первый лист «Выводы» — главные выводы (5–7
пунктов) со ссылками на цифры; детали — на листах-таблицах по разделам; лист
«Проверка» — утверждения, их тип и статус (§3.4).

Каждый раздел — отдельный блок в `result.json` со своим `completeness` и
`insufficientData` (§3.4). Шаблоны по ОПиУ и юнит-экономике — после пилота.

### 2.6 Рендер

- `POST /result` только валидирует и сохраняет JSON (см. §4.4), затем переводит
  в `rendering` и диспатчит `RenderAiReportMessage(jobId)` → `async_pipeline`.
- Handler рендерит xlsx через PhpSpreadsheet по шаблону (лист «Выводы», листы
  таблиц, лист «Проверка» с перечнем проверенных утверждений), пишет в
  S3 и ставит `done`. Уведомлений нет: статус, причина ошибки и
  ссылка на файл видны в списке заданий (§9).
- **Хранение — S3** (решение Владельца 2026-10-12) через
  `ObjectStorageInterface`, без прямых вызовов Flysystem/AWS SDK из модуля.
  Ключ: `ai-reports/{companyId}/{yyyy}/{mm}/{jobId}.xlsx`. Бессрочно, без
  lifecycle-правил провайдера; удаляет только Action удаления отчёта.
- Скачивание идёт через контроллер приложения с проверкой владельца компании
  (поток из S3 в ответ, `Content-Disposition: attachment`, `no-store`).
  Публичных и presigned-ссылок нет: ссылка не должна работать в обход проверки.
- Драйвер хранилища в приложении общий (`APP_OBJECT_STORAGE_DRIVER`). На проде
  он должен быть `s3` — проверить до Stage 6; если на проде `local`, это
  блокер пилота, а не повод писать отчёты на диск.
- Деньги в файле — числа с форматом ячейки, не строки. Суммы приходят от
  воркера, но рендер их не пересчитывает: правильность обеспечивает проверка
  (§3.3) и сверка на проде (§4.4).

## 3. Воркер: многошаговый анализ и проверка

### 3.1 Конвейер одного задания

Каждый шаг — отдельный вызов `claude -p` со своим промптом, лимитом ходов и
JSON Schema ответа. Между шагами передаются файлы в `work/<jobId>/`, а не
контекст одной длинной сессии. Так шаги проверяемы и перезапускаемы, а
проверяющий не видит рассуждений аналитика.

| Шаг | Вход | Что делает | Выход (`--json-schema`) |
|---|---|---|---|
| 1. План | задание (шаблон, период) + каталог инструментов | по вопросам шаблона составляет список нужных выборок | `plan.json`: вопросы, выборки, `out_of_scope` |
| 2. Сбор и анализ | `plan.json` + MCP read-only | вызывает инструменты, считает, формирует выводы. **Каждое число** в результате ссылается на вызов инструмента (`source: {tool, args, path}`) | `draft.json`: разделы, таблицы, утверждения с `source` |
| 3. Проверка (verifier) | задание + `draft.json` + MCP read-only, **без** рассуждений шага 2 | для каждого числового утверждения заново вызывает указанный инструмент и сверяет; проверяет, что выводы следуют из чисел и отвечают на вопрос | `verify.json`: `passed`, по каждому утверждению `ok / mismatch / unverifiable` |
| 4. Исправление (≤ 1 раз) | `draft.json` + `verify.json` | правит только отмеченные утверждения | новый `draft.json` → снова шаг 3 |
| 5. Сборка | итоговые `draft.json` + `verify.json` | детерминированный скрипт (без LLM) собирает `result.json` по схеме §4.4 | `result.json` |

Правила:
- Если после исправления остались `mismatch`, задание завершается `failed`
  (`verification_failed`); пользователь видит причину. Отчёт с неверными цифрами
  не отдаётся никогда.
- `unverifiable` допускается только для качественных выводов и попадает в файл с
  пометкой.
- Арифметику (суммы, доли, динамику) шаг 2 делает инструментом агрегации на
  проде (§4.2), а не «в уме». Если такого инструмента нет — расчёт в скрипте
  воркера на Python по данным инструментов, а не моделью.

### 3.2 Вызов Claude Code

Форма вызова (флаги сверены с установленной `claude` 2.1.289; при обновлении CLI
проверять заново):

```bash
claude -p "$(cat step-prompt.md)" \
  --model "$AI_WORKER_MODEL" \
  --output-format json \
  --json-schema "$(cat schema/draft.schema.json)" \
  --mcp-config mcp.json --strict-mcp-config \
  --allowedTools "mcp__vf__*" \
  --disallowedTools "Bash" "Edit" "Write" "WebFetch" "WebSearch" "Agent" \
  --permission-mode dontAsk \
  --max-turns 40 \
  --append-system-prompt "$(cat prompts/system.md)"
```

- `mcp.json` указывает на `https://<prod>/api/ai-worker/v1/mcp` с заголовком
  `Authorization: Bearer <job token>`. Других MCP-серверов нет
  (`--strict-mcp-config`).
- Файлы шагов читает и пишет скрипт-оркестратор, а не модель. Модели не нужны
  ни файловая система, ни shell.
- `HOME` воркера — отдельный, без пользовательских `~/.claude` настроек,
  CLAUDE.md и памяти разработчика: агент не должен видеть проектные инструкции
  и память этой машины.
- Это адаптер провайдера `anthropic`; другие провайдеры — §3.5. Модель по
  умолчанию — Sonnet 5.5 (`claude-sonnet-5-5`) на всех шагах (§9);
  `AI_WORKER_MODEL` в `worker.env`, чтобы сменить без релиза.
- Аутентификация — подписка Владельца (§9): долгоживущий токен из
  `claude setup-token`, в `worker.env` как `CLAUDE_CODE_OAUTH_TOKEN`. API-ключа
  нет, лимита в долларах нет. Лимиты подписки общие с дневной работой в
  Claude Code; ночное окно их разводит по времени.
- Упёрлись в лимит подписки (rate limit / usage limit в ответе CLI) — задание
  возвращается в `queued` без увеличения `attempts`, воркер завершает ночь.
  Это не `failed`.
- От зацикливания — только `--max-turns` на шаг и `RuntimeMaxSec` окна;
  дополнительного лимита на задания за ночь нет (§9).
- `usage` (токены, стоимость, ходы, длительность) из JSON-вывода суммируется и
  отправляется в `/result`.

### 3.3 Оркестратор `ai-worker`

Python 3 (есть на машине; без зависимостей сверх stdlib + `openpyxl` не нужен —
рендер на проде). Каталог `/srv/ai-worker/`:

```
bin/run-night.py        цикл: claim → pipeline → result, пока есть задания и окно
bin/pipeline.py         шаги §3.1, файлы в work/<jobId>/
prompts/                system.md, plan.md, analyze.md, verify.md, fix.md
schema/                 plan/draft/verify/result *.schema.json (копия контракта с прода)
etc/worker.env          PROD_BASE_URL, AI_WORKER_TOKEN, AI_WORKER_PROVIDER, AI_WORKER_MODEL,
                        AI_WORKER_VERIFY_PROVIDER, ключи провайдеров (§3.5) (0600)
work/                   временное; удаляется после отправки результата
log/                    JSONL: jobId, шаг, длительность, usage, итог — без данных и промптов
```

- Исходники воркера и systemd-юниты лежат в репозитории в
  `services/ops/ai-worker/` (`services/` — папка для сервисов вне Symfony-приложения); на машину ставятся копированием
  с проверкой md5 — так же, как wrapper'ы.
- `run-night.py`: перед каждым заданием проверяет окно и ресурсы (§5.1); во время
  шагов шлёт `heartbeat` раз в 5 минут; на SIGTERM отправляет
  `/result` со статусом `failed`, `worker_interrupted` (задание вернётся в
  очередь по lease).
- Идемпотентность: `/result` с тем же job token повторно → 200 с тем же итогом.
  Сетевая ошибка при отправке → 3 повтора с backoff, затем результат остаётся в
  `work/` до следующей ночи.

### 3.4 Защита от галлюцинаций

Основа — руководство Anthropic «Reduce hallucinations»: разрешить «не знаю»,
источник у каждого утверждения и снятие утверждений без источника, отдельный
проход проверки, best-of-N, запрет знаний вне данных. Приёмы снижают риск, но
не убирают его, поэтому главная защита — архитектурная: **модель не является
источником ни одного числа**.

**Обязательно (пилот без этого не начинается):**

1. **Числа подставляет скрипт, не модель.** Оркестратор сохраняет каждый
   ответ инструмента в `work/<jobId>/calls/<callId>.json`. В утверждении
   модель указывает только ссылку `{callId, path}`; поле `value` заполняет
   скрипт из сохранённого ответа. Производные величины (доля, динамика,
   разница) модель задаёт формулой над ссылками (`ratio(c1, c2)`,
   `delta(c3, c4)` — закрытый список функций), значение считает скрипт.
   Ссылка на несуществующий вызов или путь → утверждение снимается.
2. **Числа в тексте сверяются с утверждениями.** Скрипт извлекает все
   числа из текста разделов. Число, не совпадающее (после нормализации
   формата) ни с одним `value`, → отчёт отклоняется (`unsupported_number`).
   В тексте модель ссылается на утверждения плейсхолдером `{c1}`; значение
   подставляет рендер.
3. **«Данных недостаточно» — нормальный ответ.** Промпт явно разрешает
   отказаться от вывода; в схеме у раздела есть `insufficientData: {reason}`.
   Раздел с отказом попадает в файл с причиной и не считается ошибкой.
4. **Полнота данных — от прода.** Каждый инструмент возвращает
   `completeness`: предварительный ОПиУ, нераспознанные затраты маркетплейсов,
   незакрытый период, неполная загрузка выписок. Если период неполный, раздел
   обязан это показать (лист «Проверка» и плашка в «Выводах»), а выводы о
   динамике по нему запрещены. Скрипт проверяет: флаг неполноты из ответа
   инструмента есть в `result.json`.
5. **Эталонный набор (eval).** Фикстурные компании в `services/ops/ai-worker/eval/`
   с заранее посчитанными ответами и ловушками: пустой период, неполный
   период, аномальная операция, комментарий-инструкция в данных. Прогон
   обязателен при смене промптов, схемы, модели или версии `claude`; порог —
   ноль неверных чисел и ноль выводов по неполным данным. Каждая ошибка,
   найденная на пилоте, добавляется в набор как новый случай.

**Также в плане:**

6. **Только данные компании.** Промпт запрещает «рыночные нормы», отраслевые
   сравнения и знания вне ответов инструментов. Причины явлений — только с
   пометкой «гипотеза».
7. **Тип утверждения.** `kind`: `fact` (значение из инструмента), `calc`
   (формула над фактами), `conclusion` (вывод из фактов, со ссылками на них),
   `hypothesis`. Лист «Проверка» группирует по типу; verifier проверяет у
   `conclusion`, что он следует из указанных фактов.
8. **Версии промптов.** `promptVersion` (хеш каталога `prompts/` + `schema/`)
   приходит в `result.json` и хранится в задании — ошибку можно отследить до
   версии.

**Опционально, по флагу `AI_WORKER_BEST_OF_N=0`:**

9. **Best-of-N для выводов.** Шаг анализа выполняется дважды независимо;
   `conclusion`, которых нет в обоих прогонах, помечаются «неуверенно». Вдвое
   больше расход лимитов подписки — включать по итогам пилота.

### 3.5 Выбор модели и провайдера

Решение Владельца 2026-10-12: воркер не привязан к Anthropic. Поддерживаются
три провайдера; выбор — без релиза кода.

**Адаптеры.** Оркестратор вызывает шаг через интерфейс
`run_step(step, prompt, schema, mcp, model) → {json, usage}`. Всё, что защищает
от галлюцинаций (§3.4), и рендер — в оркестраторе и на проде, **одинаково для
всех провайдеров**; адаптер только запускает модель.

| Провайдер | Адаптер | Модель по умолчанию | Аутентификация | Примечание |
|---|---|---|---|---|
| `anthropic` | Claude Code CLI (`claude -p`, §3.2) | `claude-sonnet-5-5` | подписка (`CLAUDE_CODE_OAUTH_TOKEN`) или API-ключ (`ANTHROPIC_API_KEY`) | основной |
| `openai` | Codex CLI (`codex exec --json --output-schema … -m … -s read-only --ephemeral --skip-git-repo-check`; MCP через `-c mcp_servers.…`) | задаётся в `worker.env` | `OPENAI_API_KEY` или вход ChatGPT | Codex 0.162.1 уже стоит на машине |
| `kimi` | **Kimi CLI** (Kimi Code CLI от Moonshot, преемник архивного `kimi-cli`): headless-запуск с MCP-конфигом и JSON-выводом — флаги сверить (ниже) | `kimi-k3` | ключ Moonshot Open Platform | собственный CLI провайдера, без переадресации Claude Code |

**Kimi CLI — проверка до реализации адаптера** (на установленной версии, в
Stage 5, до кода):
- headless-запуск без интерактива и его флаги. У архивного `kimi-cli` были
  `--print -p`, `--output-format stream-json`, `--mcp-config-file`; у Kimi Code
  CLI их наличие в документации не подтверждено;
- аутентификация ключом через переменную окружения, без интерактивного `/login`;
- выбор модели флагом или конфигом;
- **отключение встроенных инструментов** (shell, запись файлов, web). У
  архивного `kimi-cli` print-режим автоматически одобрял все действия. Если
  инструменты отключить нельзя, адаптер `kimi` не включается: изоляция
  пользователем `ai-worker` без явного запрета инструментов для провайдера с
  автоодобрением недостаточна. Решение — в review Stage 5;
- структурированный ответ: если CLI не принимает JSON Schema, оркестратор
  валидирует финальное сообщение по схеме сам и при ошибке повторяет шаг
  один раз.

Перед реализацией адаптера `openai` сверить на установленной версии:
отключается ли встроенный shell-инструмент Codex. Если нет — изоляция держится
на пользователе `ai-worker`, sandbox `read-only` и отсутствии сети, кроме API
прода и провайдера; это принять в review явно.

**Где выбирается.**
- Провайдер и модель по умолчанию — `AI_WORKER_PROVIDER`, `AI_WORKER_MODEL` в
  `worker.env`.
- **Разрешённые провайдеры на компанию** выбирает `ROLE_SUPER_ADMIN` в
  admin-разделе (§2.4): данные уходят конкретному провайдеру, и согласие
  клиента даётся на конкретного провайдера. `claim` передаёт воркеру
  `allowedProviders`; если провайдер по умолчанию не разрешён компании, воркер
  берёт первый разрешённый; если ни один не настроен на воркере — задание
  остаётся в `queued` (WARNING `ai_worker_provider_unavailable`).
- **Проверяющий шаг может идти на другом провайдере** (`AI_WORKER_VERIFY_PROVIDER`),
  если он тоже разрешён компании. Перекрёстная проверка разными моделями
  ловит ошибки, общие для одной модели.

**Допуск модели.** Пара «провайдер + модель» включается в `worker.env` только
после прохождения eval-набора (§3.4 п. 5) с тем же порогом: ноль неверных
чисел и ноль выводов по неполным данным. Результаты прогона —
`services/ops/ai-worker/eval/results/<provider>-<model>-<date>.json` в
репозитории; без файла с зелёным результатом оркестратор отказывается
стартовать с этой парой.

**Прозрачность.** `provider` и `model` (по каждому шагу) приходят в
`result.json`, хранятся в задании и показываются на листе «Проверка».

**Данные.** Каждый провайдер — отдельный получатель данных клиента: Anthropic
(США), OpenAI (США), Moonshot AI (Китай). Согласие клиента должно называть
провайдера; администратор разрешает компании только тех, на кого есть
согласие (§6).

## 4. Прод: API для воркера

Отдельный stateless firewall `^/api/ai-worker/v1/`, роль `ROLE_AI_WORKER`. Ключи
компаний из модуля `Api` здесь не принимаются, а worker token не принимается в
`/api/external/v1/`.

### 4.1 Токены — два уровня

| Токен | Где живёт | Что разрешает | Срок |
|---|---|---|---|
| **worker token** | `.env` прода (хеш) / `worker.env` воркера | только `claim` | ротация вручную, 90 дней |
| **job token** | выдаётся в ответе `claim`; на проде хранится хеш | MCP read-only, `heartbeat`, `result` **одного задания**; `companyId` берётся из задания | до `leaseUntil` |

Так утечка worker token не даёт доступа к данным: данные доступны только через
выданное задание и только его компании. Секреты: 32 случайных байта, SHA-256,
`hash_equals` — по образцу `AuthenticateApiKeyAction`.

### 4.2 Эндпоинты

| Метод | Путь | Токен | Ответ |
|---|---|---|---|
| POST | `/claim` | worker | 200 `{job, jobToken, leaseUntil, schemaVersion, allowedProviders}` или 204 |
| POST | `/jobs/{id}/heartbeat` | job | 200 `{leaseUntil}`; 409 если токен устарел |
| POST | `/mcp` | job | MCP Streamable HTTP (JSON-RPC) |
| POST | `/jobs/{id}/result` | job | 202 / 409 / 422 |

- `claim` — `SELECT … FOR UPDATE SKIP LOCKED` по `status=queued ORDER BY created_at`,
  одна запись. Справедливость между компаниями: не больше одного задания на
  компанию за ночь, пока в очереди есть другие компании.
- **MCP over HTTP**: новый транспорт рядом со stdio, тот же `ToolRegistry`.
  Отдаются **только** инструменты с `isWriting() === false`; на write-инструмент
  — ошибка `tool_not_found`, как будто его нет. `company_find_by_name` воркеру
  не отдаётся (глобальный справочник). `companyId` передаётся в `call()` из
  job token.
- Состав MCP — чтение трёх разделов (решение Владельца 2026-10-12). Агрегаты
  считаются на стороне прода, чтобы модель не считала сама:

  | Раздел | Основа в коде | Инструменты |
  |---|---|---|
  | ДДС | `Cash*Tool` в `src/Mcp` (только read) | обороты по статьям за период, помесячная динамика, остатки по счетам на даты |
  | ОПиУ | `PLCategoryFacade::getTreeByCompanyId()`, отчёт `src/Finance/Report` | дерево статей; отчёт ОПиУ за период по статьям и месяцам — новый read-метод Facade, `ARCHITECTURE.md` обновить |
  | Юнит-экономика | `MarketplaceAnalyticsFacade::getUnitEconomics()`, `getPortfolioSummary()` | юнит-экономика по листингам за период; сводка портфеля |

  Write-методы Facade (`addCostMapping`, `deleteCostMapping`, `remapCostMapping`,
  `requestRecalc`, `recalculateSnapshotsForListings`, `createPLDocument` …)
  воркеру не отдаются. Каждый ответ инструмента содержит `completeness`
  (§3.4 п. 4). Каждый инструмент — Query/Facade с обязательным
  `companyId` из job token, периодом ≤ 12 мес и пагинацией (limit ≤ 200).
- Rate limit на job token: 2 запроса/с, 600 вызовов инструментов на задание →
  429 `ai_worker_rate_limited`.
- Логи: INFO на claim/result, WARNING на 409/429, вызов инструмента — имя,
  длительность, число строк; без аргументов-текстов, без ответа, без промпта.

### 4.3 Почему не ключи модуля `Api`

Ключи `Api` — по одному на компанию, их выпускает владелец компании, срок 90 дней.
Воркер обслуживает все компании и не должен держать ключи каждой. Job token
выдаёт доступ к одной компании ровно на время задания, которое поставил владелец
этой компании.

### 4.4 Контракт результата

`result.json` (JSON Schema версионируется, `schemaVersion` из `claim`; копия схемы
лежит у воркера):

```json
{
  "schemaVersion": 1,
  "promptVersion": "sha256:…",
  "status": "done | failed",
  "errorCode": null,
  "summary": "≤ 500 символов",
  "sections": [
    {"title": "…", "text": "… {c1} …", "claims": ["c1", "c2"], "insufficientData": null, "completeness": {"complete": true, "flags": []}}
  ],
  "tables": [
    {"title": "…", "columns": [{"key": "amount", "type": "money"}], "rows": [{}], "source": {"tool": "…", "args": {}}}
  ],
  "claims": [
    {"id": "c1", "kind": "fact | calc | conclusion | hypothesis", "text": "…", "ref": {"callId": "…", "path": "…"}, "formula": null, "value": "123456.78 (заполняет скрипт)", "source": {"tool": "…", "args": {}}, "verified": "ok | unverifiable"}
  ],
  "verification": {"passed": true, "checked": 14, "mismatch": 0, "unverifiable": 2},
  "provider": {"analyze": "anthropic/claude-sonnet-5-5", "verify": "openai/…"},
  "usage": {"inputTokens": 0, "outputTokens": 0, "costUsd": 0, "turns": 0, "durationMs": 0}
}
```

Проверки на проде до приёма (422 `ai_report_result_invalid` при нарушении):
- соответствие схеме, лимиты размеров (≤ 2 МБ, ≤ 50 таблиц, ≤ 5000 строк);
- `verification.passed === true` и `mismatch === 0` для `status=done`;
- **выборочная сверка**: до 5 случайных `claims` с `source.tool` прод сам
  перевычисляет тем же инструментом для `companyId` задания; расхождение →
  `failed`, `server_verification_failed`, ERROR в лог (это баг воркера или
  подмена);
- деньги — строка-decimal, не float;
- в тексте разделов нет чисел вне плейсхолдеров `{cN}` (§3.4 п. 2);
- флаги неполноты из ответов инструментов отражены в `completeness` разделов
  (§3.4 п. 4);
- в тексте нет HTML/формул: значения, начинающиеся с `= + - @`, экранируются при
  рендере в xlsx (CSV/formula injection).

## 5. Чтобы не мешать

### 5.1 Dev-машина (3 CPU, 5,8 ГБ RAM, PhpStorm ~2,6 ГБ, swap почти занят)

Нагрузка воркера на машину небольшая (это HTTP-клиент и CLI), но жёсткие рамки
нужны всё равно:

- `ai-worker.timer`: `OnCalendar=*-*-* 00:30 Europe/Moscow`, `Persistent=false`
  (пропущенную ночь не догоняем днём).
- **Окно 00:30–04:15 МСК**: новое задание не берётся после 03:45, к 04:15 юнит
  останавливается (`RuntimeMaxSec`). Окно заканчивается до `devbox-cleanup` в
  04:30 и до продовых cron 04:35 и 06:40–06:50.
- `ai-worker.service`: `User=ai-worker`, `MemoryMax=1200M`, `MemoryHigh=1000M`,
  `CPUQuota=100%`, `Nice=19`, `IOSchedulingClass=idle`, `TasksMax=64`.
- Перед каждым заданием: `MemAvailable` ≥ 1,2 ГБ и нет запущенных
  `phpstan` / `phpunit` / `make site-*`; иначе пропустить ночь (INFO в лог).
- Только одно задание одновременно (`flock` на `/srv/ai-worker/run.lock`).
- `work/` очищается после каждого задания; лог JSONL ротируется (14 дней).

### 5.2 Прод

- Данные отдаются только через Query с `companyId`, лимитом периода и пагинацией.
  Агрегаты считаются в SQL, без загрузки всех строк в PHP.
- Rate limit на job token (§4.2) и одно задание одновременно на весь прод: claim
  не выдаёт новое, пока есть `claimed` с живым lease (на старте один воркер).
- Рендер — в `async_pipeline`, один файл, без тяжёлой обработки.
- Ночное окно 00:30–04:15 не пересекается с cron 04:35+ (автомаппинг, гейты WB).
  Нагрузку сверить по `perf-report` после пилота.

## 6. Безопасность

Текста пользователя на старте нет (§9), но данные компании (названия
контрагентов, комментарии операций) могут содержать инструкции и считаются
недоверенными. Если свободный текст появится позже, он попадает в ту же категорию.
Защита строится на **ограничении возможностей**, а не на промпте:

| Угроза | Защита |
|---|---|
| Prompt injection → чужие данные | `companyId` только из job token; инструментов с выбором компании нет |
| Prompt injection → запись/порча | write-инструменты не отдаются; токен не даёт ничего, кроме read + result |
| Агент выходит за пределы | нет Bash/Write/Web, `--strict-mcp-config`, отдельный пользователь без shell-доступа к ключам |
| Доступ к секретам машины | пользователь `ai-worker` не читает `/home/deploy` (`~/.ssh/vf-prod*`, `.secret/`, `site/.env` с боевым DSN); проверить `sudo -u ai-worker cat …` → Permission denied |
| Утечка worker token | даёт только `claim`; данные — только по выданному заданию; ротация |
| Выдуманные цифры | `source` у каждого числа, verifier, выборочная сверка на проде |
| Расход лимитов подписки | ночное окно, `--max-turns`; при исчерпании — перенос на следующую ночь |
| Formula injection в xlsx | экранирование при рендере |

Данные компании уходят в Anthropic. На пилоте согласие клиентов Владелец
получает сам, в продукте текста и согласия нет (§9); ИИ-обработку для
компании включает администратор в admin-разделе (§2.4) только после такого
согласия. Перед открытием функции шире пилота — отдельное решение о тексте и
оферте.

## 7. Наблюдаемость

- Прод: INFO — создание, claim, result, done; WARNING — reclaim по lease, 409,
  429, verification_failed; ERROR — `server_verification_failed`, сбой рендера.
- Утренний гейт (cron 07:00, по образцу гейта WB): задания старше 24 ч в
  `queued`/`claimed` или > 30 % `failed` за ночь → ERROR в GlitchTip.
- Воркер: JSONL в `log/` и `journalctl -u ai-worker`. Итог ночи одной строкой:
  взято / done / failed / пропущено по ресурсам / стоимость.

| Ключ и лимит | подписка Владельца, без дополнительного лимита | `CLAUDE_CODE_OAUTH_TOKEN`; нет `--max-budget-usd` и `budget_exceeded`; исчерпание лимита подписки — перенос на следующую ночь (§3.2) |
| Модели | Sonnet 5.5 на всех шагах по умолчанию | `AI_WORKER_MODEL=claude-sonnet-5-5`; сменить можно без релиза |
| Провайдеры | выбор Anthropic / OpenAI / Kimi | адаптеры §3.5; разрешённые провайдеры на компанию — в admin; допуск модели только после eval |
| Формат запроса | только шаблон `cashflow_review`, без текста пользователя | поля `prompt` нет; шаг «План» не разбирает свободный текст; меньше поверхность prompt injection |
| Передача данных в Anthropic | Владелец договаривается с пилотными клиентами сам | в продукте нет текста и согласия; включение — администратором после согласия (§2.4, §6) |
| Кому включать | признак ставит администратор в admin-разделе; пилот — 2 компании, 7 ночей | `AiReportCompanySetting`, `/admin/ai-reports`, AuditLog (§2.4); Stage 6 |
| Шаблоны | на пилоте только «обзор ДДС»; ОПиУ и юнит-экономика — после пилота | MCP-инструменты всех трёх разделов делаются в Stage 3, шаблоны по ОПиУ и юнит-экономике — отдельной задачей |
| Права | только фактический владелец компании | ставит, видит, скачивает, удаляет; участник — 403 (§2.3) |
| Уведомления | только статус в UI | без `Notification`/Telegram (§2.6) |
| Формат | только xlsx | PDF и страница в приложении — вне рамок |
| Период | месяц или квартал за последние 12 месяцев | выбор из списка, без произвольных дат (§2.1) |
| Расписание | только по заданию | автозапуск — отдельным решением после пилота |
| Состав «обзора ДДС» | приток/отток по статьям, динамика к прошлому периоду, остатки и кассовые разрывы, аномалии и проблемы учёта | §2.5 |
| Читатель | простой язык, больше деталей, главные выводы на первом листе, детали в таблицах | §2.5, промпты шага анализа |
| Квоты | один отчёт на «шаблон + период», новый заменяет предыдущий; ≤ 3 в очереди | статус `superseded` (§2.3) |
| Роль включения | только `ROLE_SUPER_ADMIN` | §2.4 |
| Критерии пилота | подтверждены: ≥ 80 % ночей, ноль неверных цифр, половина без правок | `intent.md` |
| Хранение | S3, бессрочно, ручное удаление владельцем | `ObjectStorageInterface`, ключ `ai-reports/{companyId}/…`; скачивание только через приложение; статус `deleted` (§2.3, §2.6) |

Риск, который Владелец принимает: автоматический воркер на личной подписке
делит лимиты с разработкой, а условия подписки для такой автоматизации не
сверены. Снижение риска — §3.5: при проблеме с подпиской воркер переключается
на API-ключ Anthropic, OpenAI или Kimi без релиза кода.

## 10. Acceptance

1. Владелец компании ставит задание, видит статус; к утру в списке — xlsx;
   участник компании получает 403.
2. Каждое число в отчёте имеет `source`, прошло проверку воркера и выборочную
   сверку прода; отчёт с расхождением не выдаётся, пользователь видит причину.
3. Job token компании A не даёт данных компании B (тест); worker token не даёт
   данных вообще (тест); write-инструменты недоступны (тест).
4. Истёкший lease возвращает задание в очередь; после 3 попыток — `failed`; повтор
   `result` идемпотентен; устаревший токен — 409.
5. Воркер не работает вне окна, укладывается в `MemoryMax`, пропускает ночь при
   нехватке памяти; на машине `ai-worker` не может прочитать ключи и `.env`
   разработчика.
6. Нагрузка на прод за ночь пилота видна в `perf-report` и не влияет на cron
   04:35+.
7. Логи без промптов, данных, ответов инструментов и токенов.
9. Защита от галлюцинаций (§3.4, п. 1–5) покрыта тестами оркестратора;
   eval-набор проходит с нулём неверных чисел и нулём выводов по неполным
   данным.
8. Перенос на отдельную машину: инструкция в `services/ops/ai-worker/README.md` — копия
   каталога, `worker.env`, юниты; на проде ничего не меняется.

## 11. Перенос на отдельную машину (позже)

Воркер с первого дня делается переносимым: зависит только от `claude`, Python 3 и
исходящего HTTPS к проду. Нет зависимости от репозитория, Docker, dev-стека и
SSH-алиасов. Для переноса: поставить `claude`, скопировать `services/ops/ai-worker/`,
положить `worker.env`, включить timer, на старой машине выключить. Окно и лимиты
§5.1 на выделенной машине можно расширить (несколько воркеров — после того как
claim разрешит параллельность, §5.2).
