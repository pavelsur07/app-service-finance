# TASK: схлопнуть дубли WB-листингов «без размера» (`size='0'` vs `size='UNKNOWN'`)

## Проблема

Один и тот же физический товар Wildberries заводится в `marketplace_listings` дважды, потому что WB отдаёт «безразмерный» товар по-разному в разных отчётах:

| Источник | `ts_name` | Что записывается | Что приносит |
|---|---|---|---|
| Отчёты продаж / затрат | `"0"` | `size='0'` | продажи, затраты, баркоды |
| Каталог карточек (`RefreshWbListingCatalogAction`) | `""` | `size='UNKNOWN'` | chrtId (`marketplace_variant_id`) |

`WbListingResolverService::normalizeWbSize()` (`site/src/Marketplace/Application/Service/WbListingResolverService.php:207`) приводит к `UNKNOWN` только пустую строку, `'0'` остаётся как есть. Натуральный ключ листинга — `(company_id, marketplace, marketplace_sku, size)`, поэтому получается два листинга на один nm_id.

Дедуп-миграция `Version20260331120000` эту пару не схлопывает: она партиционирует по `size`, для неё `'0'` и `'UNKNOWN'` — разные группы.

## Факты с прода (read-only, 28.07.2026)

- Пар-двойников: **140** (280 листингов). ИП Лазарева — 135 nm_id из 317, ИП Сухоносов — 5.
- Асимметрия внутри пары: у `size='0'` есть продажи и нет chrtId; у `size='UNKNOWN'` есть chrtId и нет продаж.
- Данные, висящие на двойниках: продажи 3925, затраты 27240, строки рекламных документов 220, баркоды 168, возвраты 7, себестоимость 10.
- Конфликтов при слиянии: `marketplace_inventory_cost_prices` по `(listing_id, effective_from)` — **0**; `marketplace_ad_document_lines` по `(ad_document_id, listing_id)` — **212** (обе половины пары присутствуют в одном рекламном документе); пар с двумя разными chrtId или разными `product_id` — **0**.
- Вумджой ООО не затронут: там 194 листинга с настоящими размерами (XS/S/M/L) и ни одного `size='0'`.

## Последствия

- Себестоимость нужно заводить на обоих двойников, иначе часть продаж считается с нулевой себестоимостью. У ИП Сухоносова так и вышло: nm_id 994977888 — 129 ₽ на одном двойнике и 154 ₽ на другом, продажи разбиты 61/52.
- Остатки, юнит-экономика и P&L по такому товару собираются из двух половин; реклама размазана по двум строкам одного документа.
- В списке «Себестоимость» строки визуально дублируются.

## Scope

1. Убрать источник задвоения: `normalizeWbSize()` приводит `'0'` к `'UNKNOWN'`.
2. Сохранить запись баркодов для безразмерных листингов (см. «Побочное изменение»).
3. Разовая миграция: слить существующие пары и нормализовать `size='0'` → `'UNKNOWN'` для WB.

### Побочное изменение (обязательное)

В `createListing()` баркод записывается только при `size !== 'UNKNOWN'`. После нормализации это правило перестало бы записывать баркоды для безразмерных товаров, и покрытие баркодами WB (сейчас 317 из 452 листингов у Лазаревой) перестало бы расти — а это единственный способ массовой загрузки себестоимости WB. Условие снимается: до `createListing()` вызов уже проверил, что баркод не принадлежит другому листингу WB этой компании (`resolve()`, ветка при `size==='UNKNOWN'`), а `WbBarcodeUpsertQuery::upsertIfNotExists()` идемпотентен и защищён уникальным индексом `(company_id, marketplace, barcode)`. Побочно это усиливает дедуп: следующие безразмерные строки найдут листинг по баркоду вместо создания нового.

## Вне scope

- Пересчёт себестоимости продаж после слияния (`RecalculateSalesDocumentsCostPriceAction`) — отдельным решением Владельца, после проверки результата слияния.
- Массовая загрузка себестоимости WB по nm_id (пункт 3 разбора) — отдельная задача.
- Проверка неоднозначности в barcode-режиме импорта (пункт 1 разбора) — отдельная задача.

## Definition of Done

- `normalizeWbSize('0') === 'UNKNOWN'`, есть регрессионный unit-тест (красный на старом коде).
- Баркод записывается при создании безразмерного листинга, есть unit-тест.
- Миграция:
  - переносит на канонический листинг все 14 таблиц с `listing_id`;
  - разрешает конфликты уникальных ключей: себестоимость `(listing_id, effective_from)`, теги `(listing_id, tag_id)`, дневные срезы `(company_id, listing_id, snapshot_date)`, рекламные затраты `(company_id, listing_id, date, advertising_type, external_campaign_id)`;
  - **суммирует** строки рекламных документов `(ad_document_id, listing_id)`, а не удаляет — иначе теряется рекламный расход;
  - переносит на выжившего chrtId / product_id / supplier_sku / name, если у него их нет;
  - удаляет дубли и приводит `size='0'` → `'UNKNOWN'` для WB;
  - не трогает листинги с настоящими размерами и другие маркетплейсы.
- `make site-test-unit` и `make site-cs-check` зелёные.
- Миграция проверена на локальной тестовой БД на сценарии-двойнике.

## Риски

- Миграция необратима (`down()` бросает `IrreversibleMigrationException`): удалённые дубли не восстановить.
- Затрагивает денежные данные (продажи, затраты, реклама, себестоимость) — прогон на проде только в отдельном Production Gate по явному разрешению Владельца, с бэкапом.
- Выбор канонической строки — самая старая по `created_at`; идентичность (chrtId, product_id) переносится на неё, поэтому выбор не влияет на результат.
