# МойСклад: контракт чтения товаров и модификаций

Проверено 2026-09-20 по официальной документации JSON API 1.2,
ревизия [`74f6a4fa`](https://github.com/moysklad/api-remap-1.2-doc/tree/74f6a4fa1c0021dba2df927bdd688900e97cb736).
Это входные данные для проектирования следующего потока после контрагентов,
а не решение о составе таблиц, ценах, остатках или финансовом учёте.

## Ресурсы и форма ответа

| Ресурс | Назначение | Связь |
| --- | --- | --- |
| `GET /entity/product` | Список товаров. | У товара есть обязательное `variantsCount`; это число модификаций, а не их содержимое. |
| `GET /entity/variant` | Список модификаций. | Обязательное `product.meta.href` ссылается на товар; UUID родителя извлекается только после проверки URL и типа `product`. |

Оба списка возвращают объект с `context`, `meta`, `rows`. `rows` — массив
объектов; `meta` содержит `size`, `limit`, `offset` и может содержать
`nextHref`/`previousHref`. По документации `limit` от 1 до 1000 (по умолчанию
1000), `offset` по умолчанию 0. Для первого прохода нужны явные
`filter=archived=false` и `filter=archived=true`: нельзя считать выдачу без
фильтра полным набором архивных записей. Отсутствие строки в странице не
означает удаление или архивирование.

Идентификатор записи — `id` UUID. `externalCode` — отдельный строковый код,
не ключ импорта. `accountId` UUID должен совпадать с проверенным аккаунтом
подключения; `companyId` приходит из нашего подключения, в API его нет.
Общие для двух типов обязательные поля ответа: `accountId`, `archived`,
`discountProhibited`, `externalCode`, `id`, `meta`, `name`, `updated`.
`updated` — `DateTime` источника; при проектировании хранения применить тот
же явный разбор часового пояса и миллисекунд, что у контрагентов.
API требует `Accept-Encoding: gzip`: без поддерживаемого сжатия возможен
HTTP 415. При HTTP 429 заголовок `X-Lognex-Retry-After` задаёт задержку в
миллисекундах; частоту запросов нельзя выводить из старого лимита аккаунта.
По опубликованным ограничениям на 2026-09-20 пользовательский токен имеет
лимит 15 запросов за 3 секунды, зависящий от веса запроса.

Дополнительно у **товара** обязательны `group` (`Meta`), `pathName`
(строка), `shared` (boolean), `useParentVat` (boolean) и `variantsCount`
(integer). `images`, `productFolder`, `uom`, `article`, `code`, `barcodes`,
`weight`, `volume`, `salePrices`, `buyPrice`, `vat` и другие свойства могут
отсутствовать в ответе. У **модификации** обязательны `characteristics`
(массив, в том числе пустой), `images` (`MetaArray`) и `product` (`Meta`).
`article`, `code`, `barcodes`, `salePrices`, `buyPrice` и другие свойства
необязательны. Характеристики в образце документации имеют `id`, `name`,
`value` и `meta`; конкретное хранение характеристик определять вместе с
потребностями следующего потока.

## Фильтрация, сортировка и проход страниц

- Для обоих ресурсов задокументированы `filter=archived=true|false` и
  сравнение `updated` (`=`, `!=`, `<`, `>`, `<=`, `>=`). Это само по себе не
  гарантирует корректный инкрементальный обход при изменениях между
  страницами. Без доказательства такой гарантии первый загрузчик должен
  делать полный постраничный проход обеих архивных выборок и повторять его
  после сбоя; локальные строки обновляются по `(connectionId, externalId)`.
- Для `variant` документирован фильтр `productid=<UUID>` (также `!=`).
  Это средство чтения модификаций одного товара, но не замена полного
  списка модификаций аккаунта без дополнительного доказательства.
- Общая документация разрешает `order`. Для `product` приведён пример
  `order=code,desc`. Для `variant` список сортируемых полей ограничен
  `code`, `externalCode`, `archived`, `article`; `id` в нём **не указан**.
  Уникальность этих строковых полей и стабильность границ страниц не
  подтверждены. Нельзя переносить `order=id,asc` из загрузчика
  контрагентов без живой проверки.
- Сначала загружать товары, затем модификации; запись модификации с
  неразрешённой ссылкой на товар требует отдельного решения в модели.
  Архивирование определяется только явным `archived` каждой записи.

## Живая проверка до реализации

Тестовый токен не хранится в репозитории или фикстурах. Проверка через
тестовый аккаунт ещё нужна для следующего минимального набора read-only
запросов (с `Accept: application/json;charset=utf-8` и сжатием ответа):

1. `product` и `variant` с `limit=2`, `offset=0`, отдельно для
   `archived=false` и `archived=true`; затем вторая и пустая страницы.
   Проверить `meta`, обязательные поля и наличие ссылок родителя.
2. Проверить `order=id,asc` на обоих ресурсах и сохранить только код HTTP
   и допустимость сортировки. Если для `variant` это не работает, проверить
   документированный порядок и поведение при одинаковом значении поля;
   до этого алгоритм обхода страниц не считать окончательно согласованным.
3. При наличии хотя бы одной модификации проверить `filter=productid=<UUID>`
   и соответствие `product.meta.href`. Если модификаций в аккаунте нет,
   зафиксировать отсутствие покрытия, не создавать записи в живом API.
4. Сохранить обезличенные реальные JSON-ответы в
   `site/tests/Fixtures/MoySklad/Product/` и
   `site/tests/Fixtures/MoySklad/Variant/`. Сохранить форму, типы,
   `meta.size`, `limit`, `offset` и различие отсутствующего поля от `null`;
   заменить имена, идентификаторы, ссылки и коммерческие значения
   синтетическими. Сырые ответы после проверки удалить. Нельзя выдавать
   пример документации за ответ тестового аккаунта.
