# МойСклад: Stage 0 — модель данных и контракт загрузки

Статус: проектное решение для следующего этапа. Первый поток — контрагенты,
только МойСклад → `MoySklad`. Этот документ не вводит миграции, импорт,
фоновые задачи или запись в API МойСклад.

Ранее выполненное подключение описано в
[`ARCHITECTURE.md`](../../../ARCHITECTURE.md#moysklad-подключение-и-проверка-доступа).
Для модели данных и направления обмена этот документ заменяет решения
старого проектного наброска `docs/integrations/moysklad.md` о прямой записи
в `Cash`, `Catalog` и другие модули. Набросок остаётся без изменений.

## 1. Граница данных

`MoySkladConnection` остаётся границей аккаунта МойСклад и нашей компании:
у него неизменяемый `companyId`, после проверки — `accountId`, а токены
остаются только в подключении. Несколько подключений одной компании могут
иметь отдельные наборы импортированных записей. Импорт никогда не копирует
токен в сущности, курсор или журнал запуска.

Все полученные данные хранятся внутри `MoySklad`. Другие модули смогут
получать их только через будущий `MoySkladFacade` с нормализованными DTO и
обязательным `companyId`. Автоматического создания или сопоставления
локального контрагента по имени, ИНН либо другим реквизитам нет. Связи между
импортированными объектами, когда они появятся, остаются внутри `MoySklad`.
Правила использования данных в финансах проектируются отдельно.

## 2. Схема первого потока

Имена колонок ниже приведены в `snake_case`. Идентификаторы наших записей —
UUID v7; время в БД — UTC. Для каждой таблицы `company_id` обязателен,
неизменяем и равен `company_id` подключения. Каждый запрос репозитория,
включая поиск по внутреннему или внешнему ID, принимает `string $companyId`
и ограничивает им выборку. Поиск по одному `external_id` или `connection_id`
без проверки компании запрещён. При доступе из контроллера сначала
определяется активная компания.

| Сущность / таблица | Поля и ограничения |
| --- | --- |
| `MoySkladCounterparty` / `moysklad_counterparties` | `id` PK, `company_id`, `connection_id`, `external_id`, `name`, `company_type`, nullable `legal_title`, `inn`, `kpp`, `ogrn`, `ogrnip`, `legal_address`, `archived`, `source_updated_at`, `loaded_at`. Уникальный ключ `(connection_id, external_id)`; индекс `(company_id, connection_id)` для выборок компании. |
| `MoySkladSyncCursor` / `moysklad_sync_cursors` | `id` PK, `company_id`, `connection_id`, `entity_type`, nullable `last_completed_at` (UTC). Уникальный ключ `(connection_id, entity_type)`; индекс `(company_id, connection_id)`. Для первого потока `entity_type = counterparty`. `last_completed_at` — отметка успешного **полного** прохода, не номер страницы и не значение фильтра API. |
| `MoySkladSyncRun` / `moysklad_sync_runs` | `id` PK, `company_id`, `connection_id`, `entity_type`, `status` (`running`, `succeeded`, `failed`), `started_at`, nullable `finished_at`, целочисленные счётчики `processed`, `created`, `updated`, `unchanged` с нулевыми значениями по умолчанию, nullable `error_category`. Индекс `(company_id, connection_id, entity_type, started_at)` для истории запусков. |

Все поля, не помеченные `nullable`, имеют `NOT NULL`. UUID хранятся в типе
`uuid`; `name` и реквизиты — `varchar` с длинами из словаря ниже;
`company_type` и `entity_type` — `varchar(64)`, `status` — `varchar(16)`,
`error_category` — `varchar(32)`, счётчики — `integer` с ограничением
`>= 0`. Все моменты времени имеют точность до миллисекунд. Для запуска
`processed = created + updated + unchanged`; `unchanged` сравнивает поля
снимка без служебного `loaded_at`. У `running` и `succeeded` категория ошибки
пуста; у `failed` она обязательна.

`connection_id` во всех трёх таблицах ссылается на существующий
`MoySkladConnection`; удаление подключения с данными синхронизации
ограничивается внешним ключом. Следующий этап должен согласовать это с
существующим действием удаления: отключение сохраняет данные и останавливает
новые запуски, а удаление с данными требует отдельного решения об их судьбе.
Автоматически удалять данные по каскаду нельзя. Данные разных подключений не
сливаются, даже если их внешние ID или реквизиты совпадают.

Существующий `MoySkladConnection.lastSyncAt` не используется как курсор:
он один на подключение и не различает типы сущностей. При добавлении новых
потоков каждый получает отдельную строку курсора и историю запусков.

### Словарь полей `MoySkladCounterparty`

Источник — `GET /entity/counterparty` JSON API 1.2. «Обязательно» ниже
означает обязательность **в ответе API**, если не сказано «наше поле».
Отсутствующее необязательное поле очищает прежнее значение при обновлении;
пустая строка после `trim` хранится как `NULL`. ИНН и прочие номера хранятся
строками без числового преобразования, форматирования или проверки по
российским длинам: набор реквизитов зависит от региона и типа контрагента.

| Наше поле | Поле API; обязательность | Тип и нормализация |
| --- | --- | --- |
| `id` | Наше поле | UUID v7, создаётся один раз и не меняется при повторной загрузке. |
| `company_id`, `connection_id` | Наши поля | UUID из проверенного подключения; перед записью проверяется соответствие компании. |
| `external_id` | `id`; обязательно | UUID; проверить и хранить в нижнем регистре. Это ID записи МойСклад, а не `externalCode` или `syncId`. |
| `name` | `name`; обязательно | Строка до 255 символов; `trim`, пустое значение — ошибка данных страницы. |
| `company_type` | `companyType`; обязательно | Строковый код типа МойСклад до 64 символов без перевода в закрытый enum; так сохраняются региональные варианты. |
| `legal_title` | `legalTitle`; необязательно | Nullable строка до 4096 символов; применимость зависит от `companyType`. |
| `inn`, `kpp`, `ogrn`, `ogrnip` | Одноимённые поля; необязательны | Nullable строки до 255 символов; региональные реквизиты сохраняются только при наличии в ответе. |
| `legal_address` | `legalAddress`; необязательно | Nullable строка до 255 символов. Детализированный `legalAddressFull` пока не сохраняется. |
| `archived` | `archived`; обязательно | Boolean без значения по умолчанию при разборе ответа; `true` сохраняется, запись не удаляется. |
| `source_updated_at` | `updated`; обязательно | DateTime МойСклад в MSK, с миллисекундами или без них; разобрать как `Europe/Moscow`, сохранить UTC с точностью до миллисекунд. Неверный формат — ошибка страницы. |
| `loaded_at` | Наше поле | UTC-время последней успешной записи этой строки при загрузке; обновляется и для неизменившегося содержимого. |

Данные `contactpersons`, `email`, `phone`, `fax`, `attributes`,
`actualAddress`/`actualAddressFull`, `legalAddressFull`, банковские счета,
файлы, скидки, теги, комментарии, ФИО, региональные вложенные реквизиты,
`externalCode`, `syncId` и `meta.href` в первом потоке сознательно не
сохраняются. Для связей будущих потоков используется внешний UUID, а не
сопоставление по имени. Состав реквизитов первого потока не обещает полный
юридический профиль для всех регионов.

## 3. Контракт загрузки

1. Запуск допускается для активного, проверенного подключения; до HTTP
   проверяются `companyId` и принадлежность подключения. На пару
   `(connectionId, entityType)` одновременно работает только один запуск:
   использовать PostgreSQL advisory lock на время прохода с освобождением
   при завершении или разрыве соединения. Конкурирующий запуск не начинает
   загрузку. Нельзя держать транзакцию БД открытой во время HTTP-запросов.
2. И первичная, и последующая загрузка выполняют **два полных** постраничных
   прохода `GET /entity/counterparty`: сначала с `filter=archived=false`,
   затем с `filter=archived=true`. Проверка на тестовом аккаунте показала,
   что запрос без фильтра не возвращает архивных контрагентов. В каждом
   проходе задаются `limit=100`, `offset=0,100,…`, `order=id,asc`;
   страницы читаются последовательно, без `expand`, до пустой страницы
   или страницы короче `limit`. `offset` растёт на фактическое число строк
   в текущем проходе и сбрасывается перед вторым. `meta` и `rows`
   проверяются как ожидаемые типы; неполный или неверный ответ завершает
   запуск ошибкой, а не считается пустой страницей.
3. Каждая страница целиком нормализуется и записывается в одной короткой
   транзакции. Для каждой строки проверяются обязательные поля, включая
   `accountId`, и сверяется с `accountId` подключения. Upsert использует
   `(connection_id, external_id)`, поэтому
   повторный запуск не создаёт дублей; при обновлении заменяются все поля
   снимка, включая ставшие пустыми nullable реквизиты и `archived`.
   Счётчики запуска отражают только зафиксированные страницы.
4. Только после последней страницы **обоих** проходов запуск получает
   `succeeded` и `finished_at`,
   а `last_completed_at` курсора меняется на время окончания прохода в той
   же транзакции. При сбое страницы её транзакция откатывается; ранее
   зафиксированные страницы остаются, запуск получает `failed`, а курсор
   сохраняет предыдущую успешную отметку. Следующий запуск снова идёт с
   `offset=0` и безопасно обновляет уже сохранённые записи.

Документация API подтверждает фильтр `updated`, сортировку и `offset`, но не
гарантирует снимок неизменной коллекции между страницами. Поэтому
инкрементальный проход с `filter=updated>=…` здесь не утверждается:
изменения во время прохода и сдвиги страниц догоняются следующими полными
запусками. Исчезновение записи из частичного ответа или из завершённого
прохода не означает удаление: локальную строку не удалять и не архивировать
только из-за отсутствия. Архив определяется исключительно явным полем
`archived` в полученной записи. Настоящее удаление в источнике требует
отдельного механизма и решения по жизненному циклу данных.

## 4. Ошибки и наблюдаемость

| Событие | Поведение запуска |
| --- | --- |
| HTTP 401 | `failed`, категория `auth`; остановить проход, показать администратору необходимость проверить подключение/токен. Автоматического повтора до исправления доступа нет. |
| HTTP 403 | `failed`, категория `forbidden`; остановить проход, показать проблему прав доступа. Не смешивать с 401. |
| HTTP 429 | `failed`, категория `rate_limited`; повторять позже с учётом `X-Lognex-Retry-After` (миллисекунды) и ограниченным backoff, без плотного цикла. Следующий запуск начинает полный проход. |
| HTTP 5xx, таймаут, сбой сети | `failed`, категория `temporary`; ограниченный повтор с backoff, затем новый полный запуск. |
| Прочий HTTP 4xx или неожиданный redirect | `failed`, категория `invalid_request`; остановить проход без автоматического повтора, проверить контракт и настройки. Redirect автоматически не выполнять. |
| Неверный JSON, отсутствующее обязательное поле, несовпадение `accountId` | `failed`, категория `invalid_response`; не продвигать курсор, дать администратору диагностируемый статус без содержимого записи. |
| Локальная ошибка хранения | `failed`, категория `internal`; откатить текущую страницу, сохранить предыдущий курсор. |

История запусков доступна администратору только в контексте активной
компании: состояние, время начала и окончания, последний успешный полный
проход, обработано/создано/обновлено/без изменений, безопасная категория
ошибки. За этим же экраном остаётся различие «подключение выключено» и
«последний запуск завершился ошибкой». В логах допустимы ID компании,
подключения и запуска, тип сущности, код HTTP и агрегированные счётчики;
токены, заголовок Authorization, тело ответа, ФИО и реквизиты не пишутся
даже на DEBUG. Для HTTP-запроса — только метод, безопасный URL без query с
данными, статус и время. 429 и ожидаемые повторы — warning; окончательный
сбой — агрегированный error, успешное завершение — info.

## 5. Следующие потоки и проверки

Порядок и границы будущих потоков:

| Очередь | Будущие сущности | Назначение и связь |
| --- | --- | --- |
| 1. Номенклатура | `MoySkladProduct`, `MoySkladVariant` | Товары и модификации; модификация связана с товаром внутри `MoySklad`. |
| 2. Склады и остатки | `MoySkladStore`, `MoySkladStockSnapshot`, `MoySkladStockSnapshotRow` | Склад, снимок остатков и его строки; строка относится к снимку, складу и объекту номенклатуры внутри модуля. |
| 3. Документы | `MoySkladCustomerOrder`, `MoySkladPurchaseOrder`, `MoySkladDemand`, `MoySkladSupply`, `MoySkladSalesReturn`, `MoySkladPurchaseReturn` | Отдельные типы для заказов, отгрузок, приёмок и возвратов. |
| 4. Платежи | `MoySkladPaymentIn`, `MoySkladPaymentOut` | Отдельные типы платежей; сверка с нашими финансовыми данными проектируется отдельно. |

Поля, ключи снимков, интерпретация документов и правила финансового учёта
определяются перед соответствующим потоком. Универсальная таблица
документов с произвольным JSON не вводится. До отдельного решения никакой
поток не записывает данные в `Cash` или другой модуль.

Следующий этап создаёт схему, загрузчик и тесты на первичные проходы по
активным и архивным записям,
обновление реквизитов и архива, повторный запуск без дублей, сбой на средней
странице с повтором от начала, 429 с отложенным повтором, 401/403,
неверный ответ и доступ только к своей компании/подключению. Отдельно
проверяются параллельный запуск, отсутствие удаления по пропуску записи и
сохранение курсора при сбое.
