# Задача: Symfony-виджет выбора контрагента для legacy-страниц

Источник: решение Владельца от 30.07.2026 — Stage 4 задачи
`counterparty-name-normalization` (UI-автокомплит) вынесен сюда отдельной
задачей; подход — **Symfony form widget для legacy-страниц**, не React-остров.

Зависимость: требует `GET /api/counterparties/search` из Stage 3 задачи
`counterparty-name-normalization`. До её мержа задача не стартует.

---

## 1. Зачем

Сейчас выбор контрагента — плоский `ChoiceType` со всем справочником компании
(`src/Cash/Form/Transaction/CashTransactionType.php:89`,
`CashTransactionController.php:63`,
`CashTransactionAutoRuleController.php:145,209`). На PROD это максимум 128
вариантов на компанию (замер 30.07.2026), поэтому задача не про
производительность, а про две вещи:

- найти контрагента по ИНН и по любому порядку ОПФ (`ООО "Ромашка"` /
  `"Ромашка" ООО`) — работает нормализация из основной задачи;
- один переиспользуемый виджет вместо четырёх мест, где справочник грузится
  списком, каждое со своими правилами (в `CashTransactionType.php:89` в список
  попадают ещё и архивные — этот баг закрывается в основной задаче, work
  item 3.4).

## 2. Почему Symfony-виджет, а не React-остров

- Экраны выбора контрагента — legacy Tabler-страницы (`base.html.twig` →
  `_layout/legacy.html.twig`, Tabler JS с CDN). На новом UI-Kit-лэйауте в
  проекте **1** шаблон из 113.
- React-острова в проекте есть, но все — виджеты **целой страницы**
  (`<div id="…-root">`). Поля внутри Symfony-формы островом не делает ни один
  экран: остров пришлось бы связывать со скрытым полем, сохранением значения при
  ошибке валидации и CSRF, а при переезде экрана на UI Kit — переписывать.
- Symfony FormType + form theme переиспользуется во всех четырёх местах и
  умирает вместе с legacy-страницами, ничего за собой не оставляя.

Отступление от `CLAUDE.frontend.md:19` («логика с запросами к API — React-остров»)
согласовано Владельцем для этой задачи: ~60 строк Stimulus на автокомплит внутри
Symfony-формы на Tabler-странице. Виджет для UI-Kit-экранов, когда они появятся,
делается отдельно на `entity-picker` + React-обёртке.

## 3. Что делаем

**Stage 1 — виджет.** Risk: MEDIUM · owner_gate: no

- `src/Company/Form/CounterpartyPickerType.php` — `final class`,
  `getParent(): HiddenType` (значение поля = UUID контрагента). Опции:
  `company_id` (required), `allow_create` (bool, default `false`),
  `placeholder`.
- `templates/form/counterparty_picker.html.twig` — блок темы формы:
  видимый `input.form-control` (Tabler-классы, как на остальных полях),
  скрытый input с id, `<ul>` под подсказки, `data-controller` +
  `data-*-value` для URL поиска и текущего значения. Регистрация в
  `config/packages/twig.yaml` → `form_themes`.
- `assets/controllers/counterparty_picker_controller.js` — debounce 250 мс,
  `AbortController` на предыдущий запрос, `q` короче 2 символов не отправляется,
  навигация ↑/↓/Enter/Esc, в строке результата **название + ИНН**, при
  `allow_create` — пункт «Создать контрагента» со ссылкой на
  `counterparty_new`.
- Без JS виджет не работает и fallback не делаем: приложение и так требует JS
  (Tabler JS, React-острова). Фиксируем это решение явно, чтобы не искали потом.

**Stage 2 — подключение и защита.** Risk: MEDIUM · owner_gate: yes

- `CashTransactionType`: `ChoiceType` со всем справочником → `CounterpartyPickerType`.
- Серверная проверка выбранного id **обязательна** — скрытому полю не доверяем:
  разрешение через существующий `CompanyFacade::findCounterpartyByIdAndCompany()`,
  `null` → ошибка формы (не 500, не молчаливый `null`).
- Тесты: functional на форму транзакции (валидный id сохраняется, чужой id
  отклоняется, пустое значение допустимо), functional на рендер виджета
  (в HTML нет всего справочника).

**Stage 3 — остальные экраны.** Risk: LOW · owner_gate: yes

`CashTransactionController.php:63`, `CashTransactionAutoRuleController.php:145,209`
— по мере совпадения паттерна. Где список заведомо короткий и фильтр не нужен,
оставляем `<select>` и пишем это в Stage Report, а не переводим «для
единообразия».

## 4. Не входит

- UI-Kit/React-вариант пикера и `entity-picker`-разметка — вместе с переездом
  экранов на UI Kit.
- Секция «Недавние» в подсказках (нужен запрос из `Cash` по
  `cash_transaction.counterparty_id` через фасад) — отдельная задача.
- Создание контрагента inline, без перехода на форму.
- Замена `<select>` на экранах вне списка из §1.

## 5. Критерии приёмки

- [ ] В HTML формы транзакции нет полного справочника; поиск идёт запросом с `q`.
- [ ] Поиск находит контрагента по ИНН, по названию и при обоих порядках ОПФ.
- [ ] Архивные не предлагаются.
- [ ] Контрагент другой компании не выбирается: подстановка чужого UUID в
      скрытое поле даёт ошибку формы (тест обязателен).
- [ ] Значение сохраняется при повторном рендере формы после ошибки валидации.
- [ ] `q` короче 2 символов не порождает запрос; предыдущий запрос отменяется.
- [ ] Виджет переиспользован без копипасты разметки в каждый шаблон.
- [ ] `make site-test`, `make site-cs-check`, `npm run lint`, `npm run build` — зелёные.
- [ ] Новых npm-зависимостей нет.
