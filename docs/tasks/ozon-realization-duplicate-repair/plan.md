# Реализация Ozon: план исправления двойной выручки

> Исполнение после отдельного поручения Владельца: `executing-plans` либо
> `subagent-driven-development`, с workflow AGENTS.md. Чекбоксы отражают
> будущую реализацию, а не выполненную работу.

**Цель:** одна обработанная копия сохранённой реализации при любом способе
запуска; восстановленный октябрьский ОПиУ компании `b57d7682…`.
**Архитектура:** переиспользовать `MonthCloseAdvisoryLockQuery` внутри общей
транзакции `ProcessOzonRealizationAction`, до определения режима обработки.
Ремонт строит строки заново из raw и пересоздаёт документ через существующие
Action переоткрытия/закрытия в одной транзакции.
**Стек:** Symfony, Doctrine ORM/DBAL, PostgreSQL, PHPUnit; без новых зависимостей.
**Основание и замеры:** [TASK.md](TASK.md).
**Класс будущей реализации:** Large, HIGH-LOCAL; две Stage и отдельный
production-шаг HIGH-EXTERNAL. Сейчас выполняется только подготовка плана.

## Границы и выбор подхода

- Рекомендуется PostgreSQL transaction advisory lock: уже используется
  закрытием и держится до commit/rollback без TTL. Закрытие и обработка
  одной компании/маркетплейса/месяца должны использовать один ключ.
- Перенос одной Redis-блокировки в Action сериализует обработчики, но
  не связывает их с закрытием месяца и зависит от TTL — не выбирать.
- Unique по SKU/цене или удаление `DISTINCT` недопустимы: исходный отчёт
  содержит законные одинаковые строки. Идентификатор исходной строки
  Ozon не вводить без отдельного подтверждённого контракта.
- Маппинги, финансовые формулы, WB, начисления Ozon by-day и расписания
  не менять. Миграция схемы для выбранного решения не требуется.
- Production-ремонт только для указанной компании, raw-документа и октября;
  не выполнять массовое исправление и не загружать новый отчёт из API.
- Обычная обработка не должна переписывать финально закрытый или
  заблокированный период; ремонт финального месяца требует явного
  переоткрытия, без обхода `financeLockBefore`.

- обновить ARCHITECTURE.md: граница транзакции и порядок блокировок.

**Контракт:** сохранить `ProcessOzonRealizationAction::__invoke(string $companyId,
string $rawDocId): array{created:int,updated:int,skipped:int}`. Все текущие
точки входа продолжают вызывать Action; общей защитой владеет Action,
а не контроллер, CLI или Handler.

Work items:
- [ ] **1.1 — красные регрессии.** Два независимых процесса на одном документе:
  первичная обработка + первичная; переобработка + переобработка;
  ручной прямой вызов + путь Handler. Барьер гарантирует перекрытие,
  ожидание ограничено таймаутом. Итог обязан равняться одному raw-набору
  по кратности и денежным суммам. Проверить, что тест падает на старом коде.
- [ ] **1.2 — общая транзакция.** Порядок: начать транзакцию → lock периода
  → перечитать raw и состояние месяца → определить первичную/повторную
  обработку → заменить/записать все строки → сверить результат → commit.
  Не использовать загруженное до ожидания lock состояние EntityManager.
  Сверить период raw/header; не направлять неполный header в текущий месяц
  через fallback даты. Зафиксировать версию raw на время обработки через
  блокировку строки документа после lock периода и повторное чтение.
  Батчевые `flush/clear` оставить, промежуточных commit быть не должно.
- [ ] **1.3 — границы.** Проверять компанию, `financeLockBefore` и финальное
  закрытие под тем же lock; преждевременный отказ не меняет строки/связи.
  Обычное предварительное закрытие не превращать в финальное.
  Переоткрытие должно использовать тот же порядок блокировок; после `clear()`
  и после ожидания перечитывать сущности по scalar ID.
- [ ] **1.4 — зелёные регрессии.** Повторный последовательный запуск оставляет
  N строк; одинаковые законные raw-строки сохраняются с исходной кратностью;
  ошибка после первого батча первичной обработки оставляет 0 новых строк;
  ошибка переобработки сохраняет прежние строки, суммы и ссылки.
  Обработку и закрытие/переоткрытие одного периода проверить в обоих порядках.
  Другая компания/месяц не должны ждать занятого ключа этого периода.

Definition of Done: все точки входа сериализованы, первичная и повторная
обработка атомарны, реальная гонка воспроизведена на старом коде и устранена.

Stage checks: тесты `tests/Integration/Marketplace/Ozon`, новые сценарии
закрытия/переоткрытия; focused PHPStan/CS изменённых PHP-файлов;
`git diff --check`. Полные gates только на handoff.
Reviewer focus: lock взят до чтения состояния, общая транзакция, rollback
после `clear()`, порядок блокировок, сохранение финансовых ограничений.

## Stage 2: контролируемое восстановление и его проверка

Risk: HIGH-LOCAL. `stage_base_commit`: записать перед Work item 2.1.

**Файлы:**
- добавить `site/src/Marketplace/Ozon/Command/RepairOzonRealizationOctoberB57d7682Command.php`;
- добавить `site/tests/Integration/Marketplace/Ozon/Command/RepairOzonRealizationOctoberB57d7682CommandTest.php`;
- сохранить обезличенные SQL-замеры и порядок запуска в этой директории задачи.
  Референсный production-wrapper менять только по отдельному named approval.

**Интерфейс:** одноразовая команда
`app:marketplace:ozon-realization:repair-october-b57d7682 [--execute]`.
Цель жёстко ограничена raw UUID из TASK.md, его полной компанией-владельцем
и периодом октября 2026. Без флага — только SELECT, без переоткрытия,
записи снимков, блокирующей транзакции или внешнего API.

Work items:
- [ ] **2.1 — dry-run и контроль исходного состояния.** Показать raw/normalized
  counts, кратности и суммы; действующий документ ОПиУ и его суммы; статус
  периода и finance lock. Перед execute под lock заново прочитать все условия,
  подтвердить точное удвоение и неизменившуюся версию raw. Полное совпадение
  source/normalized/ОПиУ означает «уже исправлено», 0 записей; любое другое
  расхождение — отказ с причиной без изменений.
- [ ] **2.2 — атомарный ремонт.** В одной внешней транзакции и под lock периода:
  переоткрыть только `sales_returns` через `ReopenMonthStageAction`, применить
  raw через исправленный `ProcessOzonRealizationAction`, затем закрыть этот
  этап финально через `CloseMonthStageAction(preliminary:false)` с существующим
  actor ID. Не вызывать предварительную пересборку: этап уже финальный.
  Старый документ обработать штатным Finance-сценарием; не править напрямую
  `document_operations` или `pl_daily_totals`. После батчевых `clear()` перечитать
  месяц перед закрытием. Проверить, что вложенные Action/Facade не делают
  отдельного верхнего commit. После успешного внешнего commit вызвать
  `FinanceFacade::invalidatePLRegisterCache(string $companyId): void`.
  Раннюю инвалидацию существующего `DeletePLDocumentAction` внутри внешней
  транзакции не считать финальной: читатель мог снова закэшировать старые суммы.
- [ ] **2.3 — приёмка до commit.** Мультимножество реализации совпадает с raw,
  продажи/возвраты/нетто совпадают с raw до копейки, документ и регистр совпадают
  с источниками. Только один актуальный документ этапа; нет потерянных ссылок.
  Денежные поля/кратность продаж и возвратов Ozon by-day, этап затрат, WB и
  остальные периоды/компании неизменны. Привязки `document_id` источников
  `sales_returns` закономерно переводятся со старого документа на новый.
  Любое нарушение откатывает весь ремонт, включая статус месяца и регистр.
- [ ] **2.4 — тесты ремонта.** Синтетические raw с законными одинаковыми строками
  и return-only, точная двойная копия в normalized и ошибочный финальный ОПиУ.
  Проверить dry-run без записей, полное исправление, повторный no-op,
  блокировку периода, изменение raw после dry-run, чужую компанию,
  неравномерные/частичные дубли, исключение между переоткрытием и закрытием,
  параллельный обычный запуск, повторное заполнение кэша до внешнего commit
  с обязательной инвалидацией после него. Для каждого отказа состояние остаётся прежним.

Definition of Done: dry-run объясняет изменения; execute на локальных данных
восстанавливает полный цикл атомарно; повтор безопасен; production не изменён.

Stage checks: тесты команды, тесты Stage 1, набор Marketplace/Finance,
focused lint/static analysis. Stage Report, commit/push одного task Draft PR.

## Review focus на весь task

1. Законные одинаковые строки не удаляются — тесты 1.4 и 2.4.
2. После batch `clear()` ссылки/статус перечитаны — тесты rollback 1.4/2.4.
3. Raw изменился или удалён во время ожидания — тесты 1.2/2.4, отказ без записей.
4. Закрытие конкурирует с ручной обработкой — два порядка в 1.4/2.4.
5. Финальный/заблокированный месяц не меняется обычной обработкой — 1.3/2.4.
