## Одобрения и подготовка

После локальных тестов, внутреннего и внешнего review подготовить один
запрос с каждым действием, названным отдельно:

1. Merge + автоматический deploy PR #2913. Миграции схемы нет.
2. Резервная копия перечисленных ниже target rows на production.
3. Установка узкого временного разрешения для команды ремонта владельцем/DevOps;
   после применения — удаление именно этого временного разрешения.
4. Единственный execute ремонта с приведённым хешем raw.

Агент не использует root-алиас, unrestricted Docker, write-capable psql или
обход существующих wrappers. Если узкого разрешения/бэкапа нет — execute не идёт.

Владелец/DevOps сохраняет бэкап на production в
`/var/backups/app-service-finance/` с доступом только администратора; файлы и
данные в git/локальный workspace не переносить. Нужны:

- целевой `marketplace_raw_documents` и все его `marketplace_ozon_realizations`;
- запись `marketplace_month_closes` компании/Ozon/октября;
- документы из `stage_sales_returns_pl_document_ids` и все их `document_operations`;
- `marketplace_sales` и `marketplace_returns`, связанные с этими документами:
  ремонт меняет их ссылки `document_id`, денежные поля сохраняются;
- `pl_daily_totals` компании за 31.10.2026 по всем статьям/проектам/ЦФО.

Перед копированием проверить реальные FK и дополнительные ссылки документов
через `pg_constraint` / `information_schema`: нестандартные связи не терять.
Проверить читаемость копии и записать IDs, counts, суммы и контрольные хеши.
Если есть нестандартная связь/ручная операция, которую штатное удаление не
допускает, выполнение откатится; не обходить отказ прямым SQL.

## Узкое временное разрешение

Это **предложение для отдельного одобрения**, не установленная настройка.
Владелец/DevOps добавляет в актуальный `codex-console` только точную команду
и две допустимые формы аргументов: пусто (dry-run), либо ровно:

```text
--execute --expected-raw-hash=304dd45f03283e2973b9b78e50b40635
```

Никаких `--all`, произвольной компании/месяца, другого хеша, SQL, shell или
расширения sudoers. Встроенные аргументы команды проверяют исходный UUID и месяц.
После установки — `bash -n` и безопасный dry-run от restricted user.
Если меняется постоянная референсная копия wrapper, синхронизировать её отдельно
по правилам `docs/maintenance/prod-access.md`, не устанавливать вслепую старую копию.

## Последовательность после approvals

Проверить завершённый deploy и новый image tag через разрешённые wrappers.
До любых production-проверок стандартная проверка доступа:

```bash
timeout 20 ssh -o BatchMode=yes vf-prod-codex "sudo -n /usr/local/bin/codex-docker-ps" < /dev/null
```

Read-only предпросмотр:

```bash
timeout 60 ssh -o BatchMode=yes vf-prod-codex "sudo /usr/local/bin/codex-console app:marketplace:ozon-realization:repair-october-b57d7682" < /dev/null
```

Сверить хеш/суммы/counts с этим runbook и бэкапом. `doubled` — ожидаемое
исходное состояние; `already repaired` — не повторять мутацию, сверить acceptance.
Exit 1 — причина для диагностики, не для обхода preflight.

После одобренного бэкапа, установленного разрешения и точного совпадения:

```bash
timeout 180 ssh -o BatchMode=yes vf-prod-codex "sudo /usr/local/bin/codex-console app:marketplace:ozon-realization:repair-october-b57d7682 --execute --expected-raw-hash=304dd45f03283e2973b9b78e50b40635" < /dev/null
```

Команда держит общий lock до commit: переоткрывает только `sales_returns`,
восстанавливает строки из raw, закрывает этот этап финально. Проверяет исходную
кратность, неизменность остальных сумм/аналитик, новый документ, полный ключ
регистра и привязки. Исключение до commit откатывает весь сценарий.
После commit обновляет cache namespace; ошибка этого шага отдельно сообщает,
что данные уже зафиксированы, и не должна трактоваться как откат данных.

После execute повторить только read-only dry-run: ожидается `already repaired`.
Дополнительно сверить SQL-агрегаты/counts/ссылки, финальный статус месяца,
«Выручку с СПП» на экране (включая проекты/ЦФО), сохранность Ozon by-day,
этапа затрат, WB и контрольных периодов/компаний. Не печатать raw или PII.
Зафиксировать acceptance и удалить временное разрешение через владельца/DevOps.

## Сбой и восстановление

- До commit — полный rollback; проверить прежние document IDs и контрольные суммы.
- Если соединение оборвалось/timeout и исход неизвестен — сначала read-only dry-run
  и SQL acceptance; не запускать повторный execute вслепую.
- После commit при неожиданном расхождении прекратить мутации и сохранить замеры.
  Восстановление из бэкапа — только отдельным одобрением, узкой операцией,
  согласованной с новыми ссылками и регистром. Не восстанавливать весь production.
