# pnl-document-company-refs: справочники документа ОПиУ — только своей компании

Поручение: вопрос №8 отчёта `docs/plan/ds-pnl-documents.md` («show/edit показывают справочник по FK без проверки
компании»); запуск — Владелец 16.10.2026 «Делай задачу №8».

## Аудит (до правок)

- **Данные прода (16.10.2026, `codex-psql-ro`, 756 документов):** 0 ссылок на справочники чужой компании по всем
  связям — у документа (контрагент, проект, основание ДДС, ЦФО), у операции (статья, контрагент, проект, ЦФО),
  в регистре `pl_daily_totals` (статья). Дефект в данных не подтверждён; задача — предотвращение.
- **Форма** (`DocumentType`, `DocumentOperationType`): все поля справочников ограничены компанией — статьи и проекты
  передаются списками компании, контрагент — `CounterpartyPickerType` (choices из `CounterpartyFacade::getSelectable`),
  ЦФО — активные ЦФО компании плюс текущий через `findByIdAndCompany`. Из интерфейса чужую ссылку не создать.
- **Чтение без проверки:** `show`, `edit` (подписи), `copy` (переносит ссылки в новый документ), `document_export_json`,
  «Удалённые» (fetch-join без условия компании), регистр ОПиУ (`PLRegisterUpdater` берёт статью и проект операции).
  Списки «Документы» и «Операции» защищены с #2697 (join справочника своей компании).

## Решение

Не латать каждую страницу чтения, а закрыть запись в одном месте — инвариант сущности (CLAUDE.md: «Entity защищает
свои инварианты»): `Document` и `DocumentOperation` не принимают контрагента, проект, основание ДДС и статью другой
компании. Тогда испорченная ссылка не появится ни из формы, ни из импорта, ни из Action, и все страницы чтения
корректны без своих проверок. Защита списков из #2697 остаётся вторым рубежом.

ЦФО — строковый id без связи: сущность компанию не проверит; путь записи — форма (ограничена) и
`FinanceDocumentResponsibilityCenterNormalizer` (проверяет пару проект × ЦФО компании). Не меняется.

## Stage 1: инвариант компании
Risk: HIGH-LOCAL (инвариант сущности на всех путях записи документов ОПиУ: форма, Cash, маркетплейсы, импорт)
Definition of Done:
- `App\Finance\Exception\DocumentForeignReferenceException` (final, `\RuntimeException`): какая связь, id справочника.
- `Document`: `setCounterparty`, `setProjectDirection`, `setCashTransaction`, `setCompany` (перепроверяет все связи
  и операции), `addOperation` (проверяет связи операции) — отказ при чужой компании; `null` разрешён.
- `DocumentOperation`: `setCategory`, `setCounterparty`, `setProjectDirection`, `setDocument` — отказ, если документ
  задан и компания справочника другая; операция без документа проверяется при `addOperation`.
- Сравнение — по id компании (не по объекту: прокси и разные экземпляры одной компании).
- Unit-тесты на каждую связь (своя — ок, чужая — отказ, null — ок, порядок «операция заполнена до addOperation»).
- Тесты, которые сами собирают испорченную строку сеттерами (`PlOperationJsonExportControllerTest`,
  `DocumentOperationIndexViewTest`), — строка портится SQL-ом в обход сущности: проверяют защиту чтения.
- Полный набор тестов зелёный: ни один путь записи не создаёт чужих ссылок (иначе — разобрать, это и есть дефект).
Stage checks: unit Finance, Functional/Integration Finance, затем полный `phpunit`; PHPStan, cs.
Reviewer focus: все пути записи (Cash → документ, marketplace_pl, импорт, копирование), прокси Doctrine при
сравнении компании, гидрация из БД не вызывает сеттеры (Doctrine пишет в свойства напрямую).
