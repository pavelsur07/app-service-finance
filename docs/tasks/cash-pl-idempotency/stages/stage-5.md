# Этап 5 — повтор формы создания и ночная проверка целостности ДДС/ОПиУ

Дата: 2026-10-23. Решение Владельца — «Делай этап 5, делай формы только из
модуля ДДС или ОПиУ, другие модули не трогай, блок Б делай».

## 1. Какую задачу решаем

**А. Двойная отправка формы создания.** Ручная транзакция ДДС и перевод уже
несут ключ повтора (этап 2). Три формы ДДС/ОПиУ — нет:

- документ ОПиУ: создание и копия (`DocumentController::new/copy` →
  `CreateManualDocumentAction`);
- плановый платёж (`PaymentCalendarController::new` → `CreatePaymentPlanAction`);
- движение по фонду (`FundController::addMovement` →
  `CreateMoneyFundMovementAction`).

Двойной клик, повтор браузера или прокси создаёт две записи. Документ ОПиУ —
дважды в регистре и отчёте.

Замер «до» (прод, эвристика: одинаковые компания, дата, тип, описание,
контрагент, операции):

- ручных документов 204, групп-кандидатов 1 — два документа по 1 199,00 ₽ от
  10.09.2025 компании 19621cff с **разными номерами** (1153770/1262 и
  1153776/1262): разные операции, не повтор формы;
- плановых платежей 5, дублей 0; движений по фонду 4, дублей 0.

Повреждений нет — профилактика, ремонта данных нет.

**Б. Тихие поломки.** Этап 4 нашёл 15 потерянных заданий импорта и 2
устаревших `allocated_amount`, которые жили с февраля незамеченными. Ночной
проверки этих состояний нет; сверка регистра ОПиУ (`app:finance:verify-pl-register`,
этап 1) по расписанию не запускается и в GlitchTip не пишет.

## 2. Что будет результатом

1. Ключ повтора в трёх формах — образец `AddCashTransactionAction`:
   - скрытое поле с UUIDv7, ключ — ID создаваемой записи;
   - повтор с ключом существующей записи своей компании возвращает её, вторая не
     создаётся;
   - гонка двух отправок упирается в PK: проигравший после rollback находит
     запись своей компании и возвращает её; ключ чужой компании — исключение;
   - тест на каждую форму: повторный вызов → та же запись, то же число строк;
     гонка через PK.
2. Ночной гейт `app:cash:integrity-check` (read-only):
   - потерянные задания импорта — предикат `CloseLostCashFileImportJobsAction`
     (dry-run по всем компаниям с `queued` старше 24 ч);
   - `allocated_amount` ≠ сумма живых документов — предикат
     `RecalculateAllocatedAmountsAction`;
   - находки — один агрегированный `error` со стабильным текстом + exit 1;
     очередь Redis недоступна — отдельный `error`, а не «чисто».
   Починка каждого состояния есть: команды ремонта этапа 4.
3. `app:finance:verify-pl-register` при расхождении пишет агрегированный
   `error` (GlitchTip); починка — `app:finance:recalc-pl-register`.
4. Расписание в `docker/cron/app.cron`: 07:43 и 07:44, после остальных утренних
   гейтов. Замер: сверка регистра на проде — 3 с, 988/988.

## 3. Что считаем выполненной работой

- Повтор любой из трёх форм не создаёт второй записи ни последовательно, ни
  параллельно; формы правки не меняются.
- Гейты на проде зелёные (после ремонта этапа 4 — 0/0/0), красные на
  подставленных данных в тестах.
- Тесты красные на старом коде, гейты, CI, ревью Codex `REVIEW_GREEN`;
  смержено и задеплоено; `ARCHITECTURE.md` обновлён.
