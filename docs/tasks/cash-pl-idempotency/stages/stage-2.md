# Этап 2 — файловый импорт ДДС и ручная транзакция

Дата: 2026-10-22. Решение Владельца — «Делай этап 2» (повторный импорт всегда
отсекает строки, уже лежащие в БД).

## 1. Какую задачу решаем

- `CashFileImportService` ищет дубль `existsByCompanyAndDedupe()` в БД, а
  строки пачки пишутся только на `flushBatch()` (200 строк). Одинаковые строки
  внутри пачки импортируются все, на границе пачек — вторая отсекается:
  результат повторного импорта зависит от нарезки, законные одинаковые
  операции (этап 0: 30 групп) то импортируются, то теряются.
- Ключ — только `dedupe_hash` (дата, сумма, назначение): реальная операция из
  второго файла с тем же хешем, но другим номером документа, отсекается.
- Два задания одного счёта не сериализованы (этап 0: 11 файлов импортированы
  больше одного раза) — check-then-insert без unique их не разводит.
- Задание, чей воркер умер в `processing`, при повторной доставке сообщения
  пропускается навсегда; 15 jobs `queued` с 07–08.02.2026.
- Ручная транзакция ДДС (`AddCashTransactionAction` из формы) без ключа
  повтора: двойная отправка формы — две операции (этап 0: слабый сигнал).

Вне этапа: `ClientBank1CImportService` (синхронный HTTP-импорт 1С, уже считает
вхождения через external_id с суффиксом), платёжные планы, PHPStan-гейт.

## 2. Что будет результатом

1. **Дедуп по количеству.** Ключ строки — `dedupe_hash` + номер документа
   (пустой — `''`). Для ключа при первой встрече в файле запоминается M —
   сколько неудалённых транзакций компании с ним уже есть; k-я строка файла с
   этим ключом создаётся, только если k > M. Повтор файла даёт 0 новых строк
   при любой нарезке на пачки; законные одинаковые операции не теряются;
   возобновление прерванного импорта дописывает только недостающее.
2. **Сериализация по счёту.** Session-level `pg_try_advisory_lock(компания, счёт)`
   в `CashFileImportHandler` до захвата задания. Занято — задание не
   трогается, `RecoverableMessageHandlingException` с повтором через 60 с.
   Сессионная блокировка — она же lease: умер воркер — закрылось соединение —
   блокировка снята.
3. **Возобновление брошенного задания.** Повторная доставка задания в
   `processing` при свободной блокировке счёта = прежний воркер мёртв →
   импорт продолжается (п. 1 делает это безопасным), `warning` в лог.
4. **Ключ формы ручной транзакции.** Скрытый UUIDv7 в форме = ID транзакции.
   Повторная отправка находит транзакцию компании с этим ID и возвращает её,
   второй операции нет; гонка двух одновременных отправок упирается в PK.
5. **Отчёт по данным** (read-only, в этом файле): 15 старых `queued`,
   кандидаты в дубли этапа 0 — решение о ремонте за Владельцем.

## 3. Что считаем выполненной работой

- Повторный, возобновлённый и «нарезанный» импорт дают тот же набор строк,
  что один импорт; два задания одного счёта не идут параллельно.
- Двойная отправка формы — одна транзакция.
- Тесты красные на старом коде; гейты, CI, ревью Codex `REVIEW_GREEN`;
  смержено и задеплоено; `ARCHITECTURE.md` обновлён.
