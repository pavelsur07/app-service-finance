# Этап 4 — плановые платежи, граница транзакции импортов, ремонт данных

Дата: 2026-10-23. Решение Владельца — «Делай этап 4, по вопросам — твои предложения»:

- плановый платёж правила повтора — это правило и исходная дата; правка суммы
  правит тот же платёж;
- один план закрывается одной транзакцией;
- ужесточение PHPStan-гейта для `flush()` — отдельной задачей: правило
  проектное, 96 из 100 записей baseline вне ДДС и ОПиУ.

## 1. Какую задачу решаем

**А. Плановые платежи.**

- `PaymentPlanMatcher` берёт план без сопоставления запросом без блокировки.
  Две транзакции, создаваемые параллельно, выбирают один план. В БД уникален
  только `transaction_id`, поэтому план получает два сопоставления, а
  `PAID` выставляется дважды.
- `MaterializeRecurringPaymentPlansAction` проверяет дубль, потом вставляет, без
  unique. Ключ — сумма и статья: план с изменённой суммой при следующем
  открытии календаря получил бы двойника.

**Б. Граница транзакции импортов ДДС.** `flush()` в сервисах:

- `ClientBank1CImportService` — построчно;
- `CashFileImportService` — пачкой;
- `BankImportService` — по дню;
- `ImportLogger::finish()` — журнал. `flush()` журнала сохраняет весь
  UnitOfWork: на этапе 3 это обходили отсоединением строк.

Транзакцией не владеет точка входа (Handler, Action). В baseline PHPStan
4 записи `vashfindir.flushOutsideBoundary` в Cash.

**В. Данные прода (этап 0).**

- 15 заданий файлового импорта компании 5d26f9aa в `queued` с 07–08.02.2026:
  сообщения Messenger потеряны, сами задания не поднимутся.
- 2 транзакции ДДС с `allocated_amount` 69 859,00 ₽ без живых документов —
  след удалений до этапа 1.

## 2. Что будет результатом

1. Сопоставление с планом:
   - уникальный индекс `payment_plan_match (plan_id)`; миграция проверяет
     отсутствие дублей до создания (прод: 1 сопоставление);
   - `PaymentPlanMatcher` перебирает кандидатов по рангу и берёт план под
     `FOR UPDATE`, проверяя статус и отсутствие сопоставления. Занятый план —
     следующий кандидат, конфликта unique нет.
2. Правила повтора: путь создания `PaymentRecurrenceRule` в коде отсутствует
   (ни формы, ни API, ни миграций; на проде 0 правил).
   - Материализация недостижима, поэтому новую схему (столбец исходной даты,
     unique) под неё не строим.
   - Решение Владельца о ключе записано в `ARCHITECTURE.md` для того, кто будет
     делать UI правил.
3. Импорты:
   - сервисы получают от точки входа callback коммита порции (`CLAUDE.md`,
     «Транзакции», пакеты);
   - `ImportLogger::finish()` только меняет журнал;
   - `flush()` — в `CashFileImportHandler`, `BankImportHandler` и новом
     `ImportBank1CStatementAction` (контроллер 1С больше не трогает журнал сам);
   - baseline −4.
4. Ремонт:
   - команды `app:cash:close-lost-import-jobs` (задания `queued` без
     сообщения в очередях старше порога → `failed`) и
     `app:cash:recalculate-allocated-amounts`;
   - обе по умолчанию dry-run, `--execute` с `--expected-count`, по компании;
   - блоки `codex-console` — запуск Владельцем.

## 3. Что считаем выполненной работой

- Один план не получает двух сопоставлений ни последовательно, ни параллельно.
- В Cash нет `flush()` вне Action/Handler/Command; поведение импортов
  (дедуп, блокировка счёта, журнал, остатки) прежнее.
- Команды ремонта на проде в dry-run показывают 15 и 2. После `--execute`,
  который запускает Владелец, повторный dry-run показывает 0.
- Тесты красные на старом коде, гейты, CI, ревью Codex `REVIEW_GREEN`;
  смержено и задеплоено; `ARCHITECTURE.md` обновлён.
