# Этап 1 — документ ОПиУ из ДДС и регистр ОПиУ

Дата: 2026-10-22. Правила — `CLAUDE.md` «Транзакции», «Идемпотентность».
Итог этапа 0 — `stage-0.md`.

## 1. Какую задачу решаем

- Суммы `pl_daily_totals` внутри дня не сверены с документами (этап 0, R2).
- `PLRegisterUpdater` удаляет строки окна и пишет новые сразу, без транзакции
  и без блокировки: сбой посередине оставляет день пустым или частичным, два
  параллельных пересчёта перемешивают DELETE и upsert. Собственный `flush()`
  сервиса сохраняет чужой UnitOfWork.
- Оба пути «документ ОПиУ из транзакции ДДС»
  (`CreateDocumentFromTransactionAction`, `CreatePnlDocumentFromTransactionAction`)
  проверяют остаток без блокировки транзакции ДДС и по коллекции документов,
  загруженной до проверки: параллельный или «устаревший» запрос создаёт второй
  документ на тот же остаток. Первый путь коммитит документ и регистр раздельно.
- Удаление и восстановление документа (`SoftDeleteDocumentAction`,
  `RestoreDocumentAction`, `DeletePLDocumentAction`) коммитят документ, потом
  отдельно пересчитывают регистр; повтор после сбоя выходит раньше пересчёта.

Вне этапа: `DocumentController` (легаси, flush в контроллере — перенос в Action
отдельно), `CreatePLDocumentAction` (вызывается из закрытия месяца Marketplace
внутри его транзакции), ключ повтора из формы (см. решение ниже), ручные
транзакции ДДС, файловый импорт, платёжные планы, PHPStan-гейт.

**Решение по ключу повтора.** Оба пути создают документ на весь остаток.
Под блокировкой второй запрос видит остаток 0 и получает понятный отказ —
второго документа не будет. Колонка ключа и миграция не нужны; данные этапа 0
двойных отправок не показали.

## 2. Что будет результатом

**PR A (read-only, без изменения поведения):**
- `app:finance:verify-pl-register [--company=UUID] [--from=Y-m-d] [--to=Y-m-d]`:
  пересчитывает регистр в памяти тем же кодом агрегации и сравнивает с
  `pl_daily_totals` по ключу (компания, статья, день, проект, ЦФО). Ничего не
  пишет; ненулевой exit code при расхождении.
- Блок команды в `docs/maintenance/codex-console.sh` и команда установки для
  Владельца.

**PR B (поведение):**
- `PLRegisterUpdater`: пересчёт окна в DBAL-транзакции (во внешней — точкой
  сохранения) под `pg_advisory_xact_lock` регистра компании; без `flush()`.
- Оба Cash-пути: `wrapInTransaction()` → `SELECT … FOR UPDATE` транзакции ДДС и
  `refresh` → проверка остатка → документ → `flush` → пересчёт дня, один commit.
- Удаление/восстановление/физическое удаление документа — документ и регистр
  одной транзакцией.
- Порядок блокировок: транзакция ДДС (источник) → регистр ОПиУ компании
  (производное). Обратного порядка в коде нет.
- `ARCHITECTURE.md` — контракты; baseline `flushOutsideBoundary` по
  `PLRegisterUpdater` сокращён.

## 3. Что считаем выполненной работой

- PR A и PR B смержены и задеплоены, гейты зелёные, baseline не вырос.
- Тесты: сверка находит расхождение и молчит на верном регистре; «устаревшая»
  коллекция документов не даёт второй документ (красный на старом коде);
  пересчёт не сохраняет чужой UnitOfWork (красный на старом коде);
  удаление/восстановление пересчитывают регистр в той же транзакции.
- Сверка на проде снята до PR B и после его деплоя, цифры — в этом файле.
