# inventory-stocks-fbs: переключатель FBO / FBS в отчёте «Остатки»

Дата: 2026-11-06. Владелец: описал задачу в чате, подход выбран там же.

## Зачем

Отчёт `/inventory/stocks` сегодня суммирует в один «Остаток» всё, что отдал
маркетплейс: склады маркетплейса и склад продавца. Владельцу нужно смотреть эти
две величины раздельно, одним переключателем с одинаковым смыслом для любого
источника: **FBO — товар на складе маркетплейса, FBS — товар на складе продавца**.

«Одинаково для всех маркетплейсов» — про интерфейс и смысл, а не про цифры:
один переключатель, не «FBS Ozon» / «FBS WB» / «rFBS» по отдельности. Фильтр
«Источник» остаётся; Ozon и WB по одному товару могут показывать разные числа,
потому что каждый показывает то, что продавец выгрузил именно ему. Сводить их в
одно число не нужно.

## Результат

- В форме фильтров появляется сегментированный переключатель «Схема: FBO | FBS»,
  параметр URL `scheme=fbo|fbs`, по умолчанию `fbo`. Неверное значение → `fbo`,
  как у остальных фильтров отчёта.
- FBO: Ozon — строки `fulfillment_type = fbo` (и строки без типа); WB — склады WB
  (`fbw`) с разбивкой по статусам «на складе / в пути к клиенту / от клиента».
- FBS: Ozon — `fbs` и `rfbs` вместе (разбивка по колонкам FBS / RFBS); WB —
  остатки по складам продавца из marketplace-api.
- Эффективная дата («снимка нет — показан ближайший») считается внутри схемы:
  если ночью FBS-часть WB не загрузилась, отчёт покажет последний день, где
  FBS-строки есть, а не пустой день.
- Колонки разбивки показываются только когда внутри схемы больше одного типа;
  одна колонка, дублирующая «Доступно расчётно», не выводится.

## Данные

- Ozon: `fbs`/`rfbs` уже лежат в `inventory_stock_snapshots` — нужен только фильтр.
- WB: остатков склада продавца нет. Ночной синк `app:inventory:wb-daily-sync`
  дополняется фазой FBS в том же обработчике и той же сессии:
  `GET /api/v3/warehouses` (склады продавца) → `POST /api/v3/stocks/{warehouseId}`
  с баркодами листингов компании порциями по 1000 → raw-страницы в
  `inventory_raw_snapshots` → нормализация в строки `fulfillment_type = fbs`,
  `status = available`, `source_sku = баркод`, `source_offer_id = nmId`, локация
  типа «склад продавца» (`LocationType::SellerWarehouse`), `external_id = seller:<id>`.
- `source_sku` для FBS WB — баркод, а не `chrtId`: у одного размера может быть
  несколько баркодов, и `chrtId` в уникальном ключе снимка схлопнул бы их в одну
  строку с потерей количества. Маппинг на листинг идёт по баркоду, строки всегда
  `mapped`.

## Подходы к загрузке WB FBS

1. **Внутрь текущего синка WB (выбран).** Та же сессия, то же сообщение, тот же
   cron. Сбой FBS-фазы (нет доступа у токена к «Маркетплейсу», 429, 5xx) пишется
   `warning`, сессия завершается `completed` с данными FBW. Меньше кода и сущностей.
2. Отдельный синк со своей сессией, сообщением и cron. Чище изоляция, но ещё
   одна цепочка ради тех же данных. Отклонён.
3. Через `wb-fetcher` (Go). Он про финансы, Inventory читает из Symfony. Отклонён.

## Решения по умолчанию (мои, можно поправить)

- `StockQtyByListingOnDateQuery` (остатки для юнит-экономики) суммирует все
  `available`-строки источника, значит после задачи в остаток WB войдёт и склад
  продавца — так же, как у Ozon уже входит `fbs`. Поведение становится
  единообразным; отдельно не фильтруем.
- Сбой FBS-фазы не повторяется внутри сессии; следующая ночь — новая попытка.
- Контракт WB (`/api/v3/warehouses`, `/api/v3/stocks/{warehouseId}`, тело
  `{"skus":[...]}` ≤ 1000, ответ `{"stocks":[{"sku","amount"}]}`, лимит
  300 запросов/мин, категория токена «Маркетплейс») зафиксирован по OpenAPI WB;
  официальная страница за антибот-стеной, поэтому первая боевая ночь — проверка.

## Не входит

- Остатки по конкретным складам Ozon (FBS Ozon остаётся суммарной «локацией»).
- Свой складской учёт компании и сведение Ozon и WB в одну цифру.
- Переделка дизайна отчёта, миграции схемы (новое значение enum без CHECK в БД).

## Приёмка

- На проде `?source=wildberries&scheme=fbs` после первой ночи показывает строки
  со складами продавца; `scheme=fbo` — те же цифры, что до задачи минус FBS.
- У Ozon сумма «Доступно расчётно» FBO + FBS равна прежнему общему значению.
- В логах ночного прогона нет `error` от FBS-фазы; `warning` допустим только при
  отсутствии доступа у токена, и тогда в задаче фиксируется, какой кабинет.
