# Замер памяти на конвертации .xls → .xlsx

Число `LegacyXlsConverter::BYTES_PER_CELL` получено замером, а не оценкой.
Здесь — как его перемерить, если обновится PhpSpreadsheet.

## Результат

| Лист (плотный, числа) | memory_limit | Размер .xls | Пик памяти | Байт на ячейку |
|---|---|---|---|---|
| 2000 × 20 = 40 000 ячеек | 1G | 0,70 МБ | 55,0 МБ | 747 |
| 4369 × 20 = 87 380 ячеек | 256M | 1,52 МБ | 83,5 МБ | 414 |

PhpSpreadsheet 5.2.0, PHP 8.3.

Вторая строка — проверка самого предела, а не только константы: при `memory_limit=256M`
конвертер разрешает 87 381 ячейку, и лист впритык под этим потолком отработал с пиком
83,5 МБ, то есть внутри отведённого бюджета в 128 МБ и вдвое ниже самого лимита.
Байт на ячейку там ниже, потому что постоянные накладные расходы размазываются по
большему листу; константа считается по худшей из строк.

В константу заложено 1536 байт — вдвое больше замеренного. Запас нужен потому,
что замер сделан на числах: строковые ячейки и стили тяжелее, а ошибка в меньшую
сторону оплачивается убитым воркером.

Обратите внимание на первую строку таблицы: файл в 0,7 МБ разворачивается в 55 МБ
объектов. Поэтому предел по размеру файла (`DEFAULT_MAX_SOURCE_BYTES`) сам по себе
от OOM не защищает — он отсекает только совсем аномальные загрузки, а настоящая
защита идёт по числу ячеек.

## Как перемерить

```bash
docker compose run --rm -v "$PWD/docs/tasks/fix-xls-import/measure.php:/app/measure.php" \
    site-php-cli php -d memory_limit=1G /app/measure.php 2000 20
```

Скрипт — `measure.php` рядом с этим файлом. Он пишет плотный .xls, затем гоняет
ровно тот путь, который выполняет конвертер (`listWorksheetInfo` → `setLoadSheetsOnly`
→ `load` → `XlsxWriter::save`), и печатает пик.

Если байт на ячейку вырастет, обновите `BYTES_PER_CELL`: предел числа ячеек
считается из него и из `memory_limit` процесса, поэтому воркеры с разной
конфигурацией получают разный потолок автоматически.

## Почему одного предела оказалось мало

Предел по ячейкам защищает от честного большого файла. От повреждённого он не
защищает вовсе, и это выяснилось тестом, а не рассуждением.

Обрезанный `.xls` с целой сигнатурой — обычный результат прерванной загрузки —
заставляет PhpSpreadsheet запросить сотни мегабайт прямо в разборе OLE-заголовка:

```
PHP Fatal error: Allowed memory size of 1073741824 bytes exhausted
(tried to allocate 803209248 bytes) in .../Shared/OLERead.php on line 143
```

Файл при этом занимает килобайты, до подсчёта ячеек дело не доходит, а фатальную
ошибку PHP нельзя перехватить — `try/catch` бессилен. То есть любой предел внутри
того же процесса здесь фикция: воркер умирал бы молча ровно так же, как до всей
этой правки.

Поэтому конвертация вынесена в дочерний процесс (`app:xls:convert`) с собственным
`memory_limit` и таймаутом. Умирает только он; родитель читает код возврата и
превращает его во внятный отказ. Предел по ячейкам остался — он даёт пользователю
точную причину («слишком много ячеек») вместо общего «файл не читается».

Регрессия закреплена тестом `testTruncatedFileDoesNotKillTheProcess`. До выноса
в отдельный процесс он ронял весь прогон PHPUnit.
