# Stage 7 — проверка в песочнице Альфы

> План этапа: задача, результат, что считаем выполненным, чек-лист приёмки.
> Общий план — `../plan.md`, раздел «Stage 7». Runbook канала и входа — `../alfa-demo.md`.

## 1. Какую задачу решаем

Код Альфы (Stage 4–6) проверен только против заглушек. Три вещи документация банка
не гарантирует, и до прода их нужно увидеть на живом API:

- **ключ операции.** В одном разделе документации уникальным назван `uuid`, в другом —
  `transactionId`. Сейчас ключ дедупликации — `uuid`. Если он меняется между двумя
  чтениями одного дня, повторная загрузка задвоит ДДС. Переключить ключ можно только
  пока данных Альфы на проде нет;
- **список счетов.** Работает ли v3.0 `aisp-le/accounts` со scope `obru_accounts_le`,
  и не бывает ли больше одной страницы;
- **обороты (`summary`).** Сходятся ли остатки и число операций с выпиской за день.
  На этом держится сверка Stage 9.

Есть и условие банка. Прод-интеграцию с каким-либо scope нельзя создать без
успешного (2xx) запроса с этим scope в песочнице. Тестовая интеграция
деактивируется после 3 месяцев простоя (п. 4.1.9 договора).

Где проводить проверку. Банк возвращает пользователя после входа только на
`redirect_uri`, зарегистрированный на портале. Онлайн-демонстрацию банку тоже
показывают на работающем приложении. Поэтому **песочница настраивается на проде**:
- подключается в отдельной тестовой компании;
- кнопка «Войти в Альфа-Банк (песочница)» видна только администратору (`ROLE_ADMIN`);
- клиенты её не видят и войти в песочницу не могут.

Тогда отдельный стенд с публичным адресом не нужен. Ночная сверка согласий на проде
сама каждый день делает успешный запрос в песочницу, так что интеграция не
деактивируется.

## 2. Что будет результатом

Код (можно выложить до получения доступа: на проде без настройки ничего не меняется):

```
site/src/BankSync/
  Infrastructure/OAuth/…               среда песочницы — только для ROLE_ADMIN (кнопка и старт входа)
  Infrastructure/Bank/Alfa/AlfaApiClient   + обороты: GET {base}/api/jp/v1/statement/summary
  Infrastructure/Bank/Alfa/AlfaStatementMapper  + mapSummary → AlfaStatementSummary
  Command/AlfaSandboxCheckCommand.php  bank-sync:alfa:sandbox-check — только чтение
  Infrastructure/Bank/Alfa/AlfaFixtureAnonymizer  обезличивание ответов для фикстур
.github/workflows/deploy.yml + docker-compose.prod.yml
                                       переменные ALFA_* из секретов и каталог сертификатов
                                       (только чтение) в php-fpm, воркер sync, scheduler
```

`bank-sync:alfa:sandbox-check --connection=<id> [--date=Y-m-d] [--save-fixtures=<dir>]`
работает только для подключения к песочнице и только читает. Что делает:
- запрашивает счета, выписку выбранного дня дважды с паузой и обороты дня;
- печатает отчёт:
  - сколько счетов и сколько страниц;
  - по каждому привязанному счёту — число операций в обоих чтениях;
  - совпадают ли множества `uuid` и `transactionId` в двух чтениях;
  - сходится ли «входящий + приход − расход = исходящий» по оборотам и по выписке;
  - список `X-TraceId`;
- номера счетов в отчёте — только последние 4 цифры;
- с `--save-fixtures` пишет обезличенные ответы: номера, ИНН, наименования, назначения
  платежа и ФИО заменены, суммы, даты и структура сохранены.

Результаты (после доступа):
- полный цикл тестовым пользователем банка;
- решения по ключу, методу счетов и оборотам — в §4 `plan.md`;
- фикстуры песочницы — в тестах маппера;
- сценарий демонстрации, исходящий IP, примеры `X-TraceId` — в `alfa-demo.md`.

### Решения, уточнённые при детализации

- **Песочница на проде, только для администратора.** Альтернатива — локальный стенд с
  туннелем: нужен публичный адрес, стабильный для `redirect_uri`, и машина, которая
  раз в 3 месяца делает запрос в банк. Прод даёт и то, и другое. Тестовые данные
  песочницы остаются только в тестовой компании.
- **Метод списка счетов — v3.0 `aisp-le/accounts`**, `jp/v2/customer-info` не
  добавляется. v3.0 уже реализован (Stage 6), а для `customer-info` нужен лишний
  scope. Если в песочнице v3.0 не ответит 2xx — пересмотр в этом этапе.
- **Обороты — только клиент и маппер**, без записи в БД. Хранение остатков и сверка —
  Stage 9. Здесь обороты нужны, чтобы проверить формат и сходимость.
- **Ключ операции переключается, только если `uuid` нестабилен**, а `transactionId`
  стабилен. Если нестабильны оба — STOP и вопрос банку (`alfa-letter.md`, п. 5).
- **Тестовый TLS-сертификат песочницы и прод-сертификат — разные файлы.** Сейчас
  канал берёт один сертификат на развёртывание (`ALFA_TLS_*`). Пока прод-интеграции
  нет, на проде лежит тестовый. Раздельные сертификаты по среде — Stage 11.
- **Команда проверки на проде запускается через wrapper `codex-console`.** Его
  allowlist меняет Владелец (как `perf-report`, `pl-tree:apply-default`). До этого
  команду запускает Владелец.

## 3. Что считаем выполненной работой

- Без доступа к банку:
  - в песочницу может войти только администратор;
  - обороты разбираются по фикстуре из спецификации;
  - команда проверки работает против заглушки банка и не пишет в БД;
  - обезличивание проверено тестом;
  - на прод доставляются переменные и каталог сертификатов;
  - без них поведение прода не меняется.
- С доступом:
  - полный цикл в песочнице: вход → согласие → счета → привязка → выписка → обороты;
  - есть 2xx по `openid`, `transactions`, `obru_accounts_le`;
  - ключ, метод счетов и обороты решены и записаны;
  - фикстуры песочницы подключены к тестам;
  - сценарий демонстрации записан.
- `ARCHITECTURE.md`, `alfa-demo.md`, «История плана».
- Гейты зелёные, ревью внутреннее и внешнее, handoff.

Поставка в две части:
- **7A** — код и доставка секретов, деплоится сразу;
- **7B** — живая проверка и фикстуры, после доступа от Владельца.

7B не блокирует Stage 8: загрузка по расписанию не зависит от результатов песочницы,
кроме ключа операции. Если ключ переключится, это случится до появления данных
Альфы на проде.
