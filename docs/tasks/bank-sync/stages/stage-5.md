Risk: HIGH-LOCAL (вход во внешний банк, секреты приложения, подпись токенов, миграция,
новый cron-гейт).
stage_base_commit: `9debf04e3` (ветка `feat/bank-sync-stage5` от `master`, после merge #2802).
Поставка: B (Stage 4–10, Альфа на проде скрыта, `plan.md` §5).

## 1. Какую задачу решаем

Клиент должен подключить Альфу сам: нажать кнопку, войти через Alfa ID, подписать
согласие и вернуться в приложение, после чего загрузка выписок работает без
поддержки. В Stage 3 сделана общая часть входа по OAuth (state, PKCE, callback,
обновление токенов под блокировкой, статусы), но провайдера Альфы нет — в тестах её
заменяет заглушка. Сейчас нажать «Подключить через Альфа-Банк» нельзя: кнопки нет.

Что нужно Альфе сверх общей части (документация банка, `docs/plan/alfa/`, разбор —
`plan.md` §3a):

- **Адреса и пара приложения.** authorize — `id-sandbox.alfabank.ru` /
  `id.alfabank.ru` `/oidc/authorize`; token, revoke, client-consents —
  `sandbox.alfabank.ru` / `baas.alfabank.ru` `/oidc/...`, по mTLS (Stage 4: хост
  требует клиентский сертификат на всех путях). `client_id`/`client_secret` — у
  песочницы и прода свои.
- **`id_token` подписан банком** (JWS RS256, заголовок `kid`), ключ — файл
  сертификата `cer.crt` («certificate-prod»), **JWKS нет**. В примерах банка
  `kid = alfa-test-jwt`, `iss` встречается в двух видах — `https://id.alfabank.ru` и
  `https://id.alfabank.ru/oidc`; `aud` — строка или массив; `nonce` возвращается,
  только если мы его передали.
- **`sub`** из `id_token` — идентификатор пользователя Alfa ID (UUID, без ФИО). Только
  по нему подключение находится в ответе «Данные по согласиям пользователей».
- **Согласие живёт 365 дней**, отзывается и по событиям банка (смена пароля,
  блокировка, смена уполномоченного лица). Дату окончания отдаёт
  `GET /oidc/client-consents` (`sub`, `clientId`, `isActive`, `expireDate`,
  `organizationIdHash`, пагинация `limit`/`offset`, до 1000 на страницу) по токену
  **Client Credentials** уровня приложения.
- **Отзыв:** `POST /oidc/revoke` (`client_id`, `client_secret`, `token`,
  `token_type_hint=refresh_token`) — отзыв refresh гасит и access.
- **403** от API данных — запрошенный сервис не входит в scope токена: повтор не
  поможет, нужен новый вход с правами. Сейчас 403 даёт `error` и падение сообщения.
- **Режим «токен клиента» для Альфы не годится** (это Alfa API Direct, только для
  своей организации, `plan.md` §4), а форма «Добавить» сейчас предлагает Альфу со
  статическим токеном.

Проверено на проде 27.10 (read-only): `bank_sync_connection` — 0 строк.

Устройство:

- **Провайдер Альфы и «скрыта на проде».** Провайдер зарегистрирован всегда, но среда
  доступна, только если для неё заданы `client_id`, `client_secret` и файл ключа
  подписи (`environments()`). Кнопка «Подключить через Альфа-Банк» — по одной на
  настроенную среду (песочница подписана). На проде переменных нет → кнопки нет,
  старт входа отвечает «вход пока не подключён». Отдельного флажка не нужно.
- **Вход.** URL authorize: `response_type=code`, `client_id`, `redirect_uri`,
  `scope=openid transactions <scope счетов>`, `state`, `nonce`, `code_challenge`,
  `code_challenge_method=S256`. `nonce` — новый случайный, хранится в
  `PendingAuthorization` рядом с verifier. `userinfo` и scope с ПДн не запрашиваются.
  Scope счетов — константа провайдера (`obru_accounts_le`, окончательный выбор в
  Stage 7).
- **Обмен кода** — `OAuthTokenEndpointClient` на `bank_sync.alfa.http_client` (mTLS);
  `client_secret` в теле формы. Ответ без `id_token` или с неверным `id_token` —
  токены не сохраняются, вход отклонён.
- **Проверка `id_token`** — свой `IdTokenVerifier` на `openssl_verify` (библиотеки JWT
  в проекте нет, для одного алгоритма она не нужна):
  - только `alg = RS256`; `none`, `HS*` и прочие — отказ до проверки подписи;
  - подпись проверяется сертификатами из файла среды (PEM, один или несколько:
    при смене ключа банком на время перехода лежат оба), истёкший сертификат не
    используется;
  - перебираются все действующие сертификаты файла: JWKS у банка нет, имя ключа
    (`kid`) в сертификате не записано;
  - `iss` — из списка допустимых среды (оба вида из документации; точный — Stage 7);
    `aud` содержит наш `client_id`; `azp`, если есть, равен `client_id`; `exp` в
    будущем, `iat` не в будущем (допуск 60 с); `nonce` совпадает (`hash_equals`);
    `sub` — непустая строка до 255 символов;
  - причина отказа — машинная (`signature`, `issuer`, `audience`, `expired`,
    `nonce`…), токен и claims в лог не пишутся.
- **Что храним.** `external_subject` = `sub` (открытой колонкой: псевдоним без ФИО,
  нужен ночной сверке без расшифровки), `consent_expires_at` — колонка (сверка и
  список подключений). Токены — как в Stage 3, только шифротекст.
- **Повторный вход** обновляет `sub` и сбрасывает срок согласия до следующей сверки
  (новое согласие — новый срок). Вход **другим пользователем** Alfa ID в то же
  подключение разрешён: подключение принадлежит компании, а не человеку.
- **Отключение (удаление).** Под блокировкой токенов подключения: расшифровать →
  `POST /oidc/revoke` refresh-токеном (HTTP вне транзакции) → удалить. Ошибка отзыва
  (сеть, 4xx/5xx, нечитаемые учётные данные) — один `warning`, удаление всё равно
  проходит: клиент хочет отключиться, а токен банк погасит сам по сроку. Блокировку
  держит другой процесс дольше 10 с — «подключение обновляется, повторите», ничего не
  удалено. Статический токен — отзывать нечего.
- **Сверка согласий** `bank-sync:alfa:consents-sync` (cron 07:52, раз в сутки):
  - по каждой настроенной среде, где есть подключения Альфы с `sub`: токен Client
    Credentials → все страницы `client-consents?clientId=…` (HTTP до записи в БД);
  - по `sub`: дата окончания — самая ранняя `expireDate` среди активных согласий
    (у одного пользователя может быть несколько организаций; ранняя дата —
    осторожная);
  - есть только неактивные или все истекли → подключение `revoked`
    (`consent_expired`) — по смыслу статуса из Stage 3 «согласие отозвано или
    истекло», выход — новый вход клиента;
  - `sub` в ответе банка нет — срок не трогаем, считаем «не найдено» (один
    агрегированный `warning`): пустой или урезанный ответ банка не должен разом
    погасить все подключения;
  - смена статуса — под блокировкой токенов подключения на перечитанной строке
    (правило Stage 3), даты — порциями с `flush()` в команде;
  - осталось 30 дней и меньше — один агрегированный `warning` со счётчиком;
    отказ в токене Client Credentials (наша настройка) — `error`, exit 1; банк
    недоступен — `warning`, exit 1, данные не тронуты;
  - в лог и вывод — только счётчики и ID подключений, без `sub`,
    `organizationIdHash`, ФИО; на проде без настройки — «не настроено», exit 0.
- **403 API данных** → `needs_reauth` с причиной `insufficient_scope`, один `warning`,
  без ретраев и без `error` (повторится — уже `needs_reauth`, загрузка не ставится).
  401 — как в Stage 3 (обновление и один повтор).
- **Нет статического токена у Альфы.** `BankCode::supportsStaticToken()` (Альфа —
  нет); форма «Добавить» предлагает только такие банки, у Альфы её нет; кнопка
  «Добавить» скрыта, пока таких банков нет; правка OAuth-подключения не показывает
  поле токена (сейчас ввод токена молча заменил бы OAuth-учётные данные статическими).
- **Срок согласия в списке подключений:** «согласие до ДД.ММ.ГГГГ», за 30 дней и
  меньше — предупреждение «войдите заново». Полноценный интерфейс — Stage 10.
- **Гейт сроков сертификатов** (Stage 4) проверяет и файлы ключа подписи Alfa ID:
  истечение `cer.crt` остановит все новые входы.

### Решения, уточнённые при детализации

- **Свой проверщик JWS вместо библиотеки:** один алгоритм (RS256), ключ из файла, без
  JWKS — это ~100 строк на `openssl_verify` с жёстким allowlist алгоритма; библиотека
  тянет зависимости ради неиспользуемого.
- **Ключ подписи и `client_id` — по среде** (`ALFA_SANDBOX_*`, `ALFA_PROD_*`): в
  примерах песочницы `kid = alfa-test-jwt`, а `cer.crt` назван «certificate-prod»;
  Stage 3 уже решил «пара на банк и среду». Клиентский TLS-сертификат (Stage 4) пока
  один на развёртывание; раздельные сертификаты по среде — вопрос Stage 11.
- **`kid` не обязателен для выбора ключа:** JWKS нет, в `cer.crt` имени ключа нет.
  План Stage 5 требовал «неизвестный `kid` → отказ»; эквивалент — «ни один
  сертификат среды не подтверждает подпись → отказ», тест есть.
- **Истёкшее согласие → `revoked`, а не `needs_reauth`:** так определены статусы в
  Stage 3; кнопка «войти заново» у обоих одна.
- **`sub` не найден → без смены статуса:** защита от массового отключения при
  неполном ответе банка (урок `replay-restriction`: сужение данных не должно доходить
  до гашения без явного признака).
- **Scope токена Client Credentials для client-consents** в документации не назван —
  константа провайдера, проверяется в песочнице (Stage 7); до проверки — `openid`.

## 3. Что считаем выполненной работой

- Против заглушки банка (MockHttpClient) проходит весь путь: кнопка → URL входа с
  nonce и PKCE → callback → обмен кода → `id_token` проверен → токены зашифрованы,
  `sub` сохранён → загрузка работает. Неверный `id_token` — ничего не сохранено.
- Удаление подключения отзывает refresh в банке до удаления; сбой отзыва не мешает
  удалению.
- Ночная сверка согласий обновляет сроки, гасит истёкшие, предупреждает за 30 дней,
  не пишет ПДн; на проде без настройки — «не настроено», exit 0.
- 403 → `needs_reauth` без ретраев и `error`.
- На проде кнопки входа через Альфу нет; формы статического токена для Альфы нет.
- **В песочнице тестовым пользователем банка: вход → согласие → токены сохранены,
  отключение отзывает токен, сверка согласий находит подключение.** Зависит от
  договора, `client_id`/`client_secret` песочницы, `test_cert.zip` с паролем и
  `cer.crt` от Владельца — до их получения пункт открыт (как 4.9), остальной этап
  деплоится: на проде провайдер не настроен.
- Миграция, `ARCHITECTURE.md`, runbook, `health-gates.md`, «История плана».
- Гейты зелёные, ревью внутреннее и внешнее, handoff.
