# bank-sync: автоматическая загрузка выписок и остатков из банков

Статус: план, ветка `feat/bank-sync`. Дата: 2026-10-25.
Класс: Large (новый модуль, схема, Messenger и cron, внешняя интеграция, изменение
границы между модулями). Ход работ — `checkpoint.md`, планы и итоги этапов —
`stages/stage-N.md`.

## 1. Задача

Компания подключает свой банк, после чего приложение само:

1. Получает доступ к банку способом, который этот банк поддерживает (OAuth 2.0
   партнёрского API, токен клиента, при необходимости mTLS).
2. Регулярно загружает выписки по привязанным счетам в ДДС без дублей, в том числе
   операции, проведённые банком задним числом.
3. Ежедневно сверяет остаток банка на конец дня с остатком учёта и показывает
   расхождения.

Банков будет несколько. Первый — Альфа-Банк.

## 2. Результат

- Новый модуль `src/BankSync`: подключения, учётные данные, адаптеры банков,
  расписание загрузки, остатки банка и сверка.
- `Cash` остаётся владельцем ДДС: создание транзакций, дедупликация, блокировка
  счёта, пересчёт остатков. Код банков `Cash` не знает.
- Зависимость в одну сторону: `BankSync → CashFacade`. PHP-импорта из `Cash` в
  `BankSync` нет.
- Второй банк добавляется новой папкой `Infrastructure/Bank/<Code>/` с адаптером и
  маппером, без правок в `Cash` и в общем коде загрузки.

## 4. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где код | Новый модуль `BankSync` | Обсуждено с Владельцем 25.10, вариант B. Интеграции меняются по своим причинам; на проде нет данных, перенос дешёвый |
| Граница с `Cash` | `BankSync` вызывает `CashFacade`; `Cash` про `BankSync` не знает | Без циклов; правила ДДС в одном месте |
| Кто коммитит | `BankSync`-handler. Методы `CashFacade` только `persist()`; в `ARCHITECTURE.md` — «коммитит вызывающий» | CLAUDE.md, «Транзакции» |
| Формат данных адаптера | Нормализованные DTO (`BankAccountDTO`, `BankStatementLineDTO`, `BankDailyBalanceDTO`), сырой `array` за пределы адаптера не выходит | Иначе второй банк не встанет |
| День выписки | Все страницы дня собираются в память, потом один вызов `CashFacade` и коммит | HTTP-сбой случается до первого `persist()`, отсоединять недописанные строки больше не нужно |
| Вебхук или опрос | Опрос — источник правды; вебхук только ставит задание на загрузку | Вебхуки теряются и есть не у всех банков |
| Окно перечитывания | Последние 3 дня от курсора (настраивается на банк) | Задним числом и корректировки |
| Учётные данные | Общий `Shared\Security` (`FieldEncryptionServiceInterface`, sodium `secretbox`, ключи `APP_ENCRYPTION_*`, `key_version`); кодек по образцу `MoySklad\Infrastructure\Security\ConnectionTokenCodec` | Механизм есть, ключи на прод доставляет `deploy.yml`; своего ключа не заводим |
| Когда шифровать | С Stage 1: новая таблица `bank_sync_connection` создаётся без колонки с открытым токеном | Шифрование уже готово; иначе пришлось бы делать expand/contract, как у маркетплейсов, на ровном месте |
| Ротация ключа | Общая команда `app:security:rotate-keys`: каждый модуль регистрирует свой ротатор (тег), команда обходит все — `Marketplace`, `MoySklad`, `BankSync`; dry-run по умолчанию; инструкция `docs/maintenance/encryption-key-rotation.md` переписывается на общую команду | Сейчас ротация есть только у маркетплейсов: смена ключа по инструкции сделает нечитаемыми токены MoySklad, а потом и банков |
| Старые таблицы | Новые таблицы `bank_sync_*` со `string $companyId`, старые удаляются, если на проде пусты | Не тащить `ManyToOne Company` в новый модуль |
| Сверка | Две проверки на день: полнота данных банка (входящий + приход − расход = исходящий) и совпадение остатка с учётом, допуск 0 | Первая ловит недогрузку, вторая — расхождение учёта |
| Предупреждение о ручном импорте | У `MoneyAccount` признак источника выписки; `BankSync` ставит его через `CashFacade` при привязке, `Cash` сам показывает предупреждение | `Cash` не должен знать про `BankSync` |
| Исправление расхождений | Автоматически не исправляем; показываем и поднимаем гейт | Прод-деньги |

**Нужно от Владельца (не блокирует Stage 1):**
- Партнёрский доступ к API Альфа-Бизнес: договор, тестовая среда, документация,
  сертификат mTLS, если нужен. Без этого Stage 2 закрывает только общую часть, а
  OAuth Альфы ждёт документации.

**Принятые по умолчанию — поправить, если не так:**
- Ручной импорт (1С, файл) в счёт, привязанный к банку по API, не запрещается, а
  предупреждает о риске дублей (Stage 3).
- Сверка по рублёвым и валютным счетам одинаково, в валюте счёта.
- Общая ротация ключей (включая MoySklad) делается в этой задаче, в Stage 2, а не
  отдельной задачей: банковским подключениям она нужна в любом случае.

## 5. Этапы

Каждый этап начинается с `stages/stage-N.md` из четырёх частей (задача, результат,
что считаем выполненным, чек-лист приёмки), итог дописывается туда же. Локальные
коммиты, push и Draft PR — одним шагом на handoff. Backend и frontend — разными
этапами.

| Stage | Что | Risk |
|---|---|---|
| 1 | Модуль `BankSync`, перенос кода из `Cash`, граница через `CashFacade`, DTO и реестр адаптеров, учётные данные сразу зашифрованы, пересчёт остатков после импорта | HIGH-LOCAL (миграция, Messenger routing, граница модулей, секреты) |
| 2 | Авторизация и ключи: статус подключения, OAuth 2.0 с обновлением токена, mTLS, привязка счетов банка к `MoneyAccount`, общая ротация ключей шифрования | HIGH-LOCAL (секреты, auth, миграция, затрагивает `Marketplace` и `MoySklad`) |
| 3 | Регулярная загрузка: cron (днём и утром), окно перечитывания, сырые ответы в хранилище, отменённые банком операции, предупреждение о ручном импорте в счёт с API | HIGH-LOCAL (cron, Messenger) |
| 4 | Остатки банка и сверка: `BankBalanceSnapshot`, проверки дня, ночной гейт, начальный остаток при первом подключении | HIGH-LOCAL (финансовая логика) |
| 5 | UI: подключения, привязка счетов, статус сверки на странице счетов (DS «Ваш Финдир») | MEDIUM |
| 6 (после документации банка) | Вебхуки Альфы, второй банк для проверки абстракции | HIGH-LOCAL |

Ниже по каждому этапу: цель, состав, что считаем выполненной работой и обязательные
тесты. Это рамка; в начале этапа она детализируется в `stages/stage-N.md` (шаги,
команды, файлы) и не может быть уже рамки без записи причины в «Историю плана».

Общее для каждого этапа (в чек-листы ниже не повторяется):
- [ ] план этапа в `stages/stage-N.md` до начала работ, итог — туда же, сверен с
      чек-листом;
- [ ] `stage_base_commit` записан, `checkpoint.md` обновлён;
- [ ] модульные тесты зелёные, PHPStan и CS по изменённым файлам без новых ошибок,
      baseline не вырос;
- [ ] `ARCHITECTURE.md` — текущее состояние новых сущностей, Facade-методов, Enum,
      routing и cron, строка в `Changelog`;
- [ ] внутреннее ревью полного diff этапа; для HIGH-LOCAL — внешнее ревью;
- [ ] в логах, исключениях и GlitchTip нет токенов, номеров счетов в `error`,
      назначений платежей и тел ответов банка.

### Stage 1 — модуль BankSync и граница с Cash

**Цель.** Отделить интеграцию с банками от учёта ДДС так, чтобы второй банк
добавлялся новой папкой адаптера, а `Cash` не знал о банках. Заодно учётные данные
хранятся зашифрованными и импорт пересчитывает остатки счёта. Поведение для
пользователя не меняется.

Состав и шаги — `stages/stage-1.md`.

**Что считаем выполненной работой:**
- [ ] модуль `src/BankSync` подключён в `routes.yaml`, `doctrine.yaml`, `twig.yaml`,
      `messenger.yaml`;
- [ ] в `Cash` не осталось банковского кода; `BankSync` импортирует из `Cash`
      только `Facade` и `Application\DTO`, `ModuleBoundaryRules` зелёный;
- [ ] адаптер отдаёт DTO; разбор формата Альфы — только в `AlfaStatementMapper`;
      банк выбирается реестром, `match ('alfa')` удалён;
- [ ] новые методы `CashFacade` (счёт по номеру, блокировка счёта, журнал импорта,
      импорт дня) описаны в `ARCHITECTURE.md` с «коммитит вызывающий»;
- [ ] день счёта — один `wrapInTransaction()`: строки, пересчёт
      `money_account_daily_balance`, курсор; HTTP до транзакции;
- [ ] таблицы `bank_sync_connection`, `bank_sync_import_cursor` со `string
      $companyId`; старые удалены (0 строк на проде подтверждено п. 1.1) либо
      перенесены;
- [ ] токен хранится только в шифротексте (`Shared\Security`), колонки с открытым
      токеном нет;
- [ ] страница подключений и `bank-sync:enqueue --bank=alfa` работают как раньше
      (smoke на стенде против заглушки HTTP).

**Тесты:**
- [ ] `AlfaStatementMapper` — unit: счета, строки, пагинация, приход/расход,
      пропуск строки без `uuid`/даты/суммы/с неизвестным направлением;
- [ ] `BankProviderRegistry` — unit: известный код, неизвестный код;
- [ ] `CashFacade::importBankStatementDay` — functional: happy path; повтор того же
      дня → те же строки и то же число строк; дубль `uuid` внутри дня → одна
      строка; чужая валюта → строка не создана; счёт чужой компании → исключение;
- [ ] **регрессия** — functional: после импорта дня остатки счёта пересчитаны
      (красный на `a9eb74206`);
- [ ] handler — unit: временный сбой → исключение для retry, курсор не сдвинут;
      отказ банка → `Unrecoverable…`; нет подключения → `Unrecoverable…`; занятый
      счёт → пропуск с `warning`;
- [ ] сбой на втором дне — functional: первый день и курсор сохранены, второго нет;
- [ ] `BankCredentialsCodec` — unit + functional: шифрование и расшифровка
      сходятся, в строке БД нет токена, неизвестная версия ключа → исключение без
      токена;
- [ ] изоляция — functional: подключение другой компании → 404 на
      `edit`/`delete`/`sync`;
- [ ] `MessengerRoutingTest` — новое сообщение в `async_sync`;
- [ ] миграция `up` → `down` → `up` на локальной БД.

### Stage 2 — авторизация, привязка счетов, ротация ключей

**Цель.** Клиент подключает банк сам, без передачи нам паролей и долгоживущих
токенов: через OAuth 2.0 с автоматическим обновлением токена. Приложение явно
знает, к какому денежному счёту относится каждый счёт банка. Ключ шифрования можно
сменить, не потеряв ни одного секрета ни в одном модуле.

**Состав.**

Авторизация:
- статус подключения: `active` / `needs_reauth` / `revoked` / `disabled`; 401 после
  обновления токена → `needs_reauth` без ретраев;
- тип учётных данных `oauth2` (access, refresh, `expires_at`) в том же
  зашифрованном JSON; обновление токена заранее, под advisory-блокировкой
  подключения; OAuth callback с `state` против CSRF;
- mTLS: сертификат приложения как партнёра банка — путь к файлу и пароль из
  `.env`, не в git; нужен ли он Альфе — по документации;
- специфика OAuth Альфы — после получения документации (см. «Нужно от Владельца»);
  без неё этап закрывается общей частью и заглушкой провайдера.

Привязка счетов:
- `bank_sync_account_link`: счёт банка (номер, БИК, валюта) → `money_account_id`,
  unique (компания, подключение, номер счёта) и (компания, `money_account_id`);
- счёт банка без пары не пропускается молча: попадает в список «не привязан»;
- при привязке `BankSync` через `CashFacade` отмечает у `MoneyAccount` источник
  выписки «банк по API» (нужно для предупреждения в Stage 3 без зависимости
  `Cash → BankSync`).

Ротация ключей шифрования (общая):
- read-only проверка на проде до начала: распределение записей по версиям ключа у
  маркетплейсов (`app:marketplace:rotate-connection-keys` без `--execute`) и у
  MoySklad (число строк с `*_encrypted` и без);
- `Shared\Security`: интерфейс ротатора модуля (подсчёт по версиям, перешифровка
  порции) и команда `app:security:rotate-keys` (dry-run по умолчанию,
  `--execute`, порции по 100, `flush`/`clear` в команде, вывод — только версии и
  счётчики);
- ротаторы: `Marketplace` (логика из `RotateConnectionKeysCommand`), `MoySklad`
  (access и refresh), `BankSync`;
- `app:marketplace:rotate-connection-keys` — тонкая обёртка над общей командой до
  обновления инструкции, затем удаляется;
- `docs/maintenance/encryption-key-rotation.md` — на общую команду и все модули;
  старый ключ удаляется, только когда ни один модуль не держит записей на нём.

**Что считаем выполненной работой:**
- [ ] подключение проходит полный цикл OAuth против заглушки авторизационного
      сервера: редирект → callback → токены зашифрованы → загрузка работает;
- [ ] истёкший access-токен обновляется до запроса к банку; два воркера не
      обновляют один refresh-токен одновременно;
- [ ] отозванный или невалидный refresh → `needs_reauth`, загрузка этого
      подключения не ставится в очередь, одно `warning`, без `error` на каждый
      прогон;
- [ ] привязка счетов сохраняется; один денежный счёт нельзя привязать к двум
      счетам банка; непривязанный счёт банка не загружается и виден в списке;
- [ ] `app:security:rotate-keys` в dry-run показывает распределение по версиям по
      всем трём модулям; `--execute` переводит всё на активную версию;
- [ ] инструкция по смене ключа обновлена; старая команда маркетплейсов —
      обёртка;
- [ ] mTLS включается конфигурацией и не мешает банкам без него.

**Тесты:**
- [ ] OAuth callback — functional: верный `state` → токены сохранены зашифрованными;
      неверный или просроченный `state` → отказ, ничего не сохранено; callback
      чужой компании → отказ;
- [ ] обновление токена — unit: за N минут до истечения обновляет, раньше — нет;
      ответ 400/401 на refresh → `needs_reauth`;
- [ ] конкурентное обновление — functional: два процесса, один refresh-запрос
      (advisory-блокировка);
- [ ] статусы — unit на матрицу переходов (`revoked` не возвращается в `active`
      без нового согласия);
- [ ] привязка — functional: уникальность обоих ключей, IDOR (чужой
      `money_account_id` → отказ);
- [ ] каждый ротатор — functional: запись на старой версии перешифрована и
      читается, на активной не тронута, повторный запуск ничего не меняет;
- [ ] `app:security:rotate-keys` — functional: dry-run ничего не пишет, вывод без
      ключей и секретов, отсутствующая версия ключа → ненулевой код без
      частичной записи порции;
- [ ] старая команда маркетплейсов — тот же результат, что раньше (существующие
      тесты зелёные).

### Stage 3 — загрузка по расписанию

**Цель.** Выписка приходит в ДДС сама: операции дня видны в течение часа,
финальная выписка за вчера — к утру, операции задним числом и отмены банка не
теряются, а дубли с ручным импортом не возникают незаметно.

**Состав.**
- cron: днём раз в час (08:00–20:00 МСК) — сегодняшний день; утром (06:30) —
  вчера и окно перечитывания; одно задание на подключение за раз;
- окно перечитывания — 3 дня от курсора, настраивается на банк;
- сырые ответы банка — в `ObjectStorageInterface`
  (`bank/{company}/{bank}/{account}/{date}/{fetchedAt}.json.gz`), хранение год,
  очистка командой с dry-run;
- отмена банком: строка с нашим `external_id`, которой нет в перечитанном окне,
  не удаляется, а помечается «нет в выписке банка» через `CashFacade`;
- предупреждение на страницах импорта 1С и файла, если у счёта источник «банк по
  API»; импорт не блокируется;
- наблюдаемость: старт и финиш задания с `companyId`, один агрегированный `error`
  на сбой прогона; подключение, не загружавшееся больше 26 часов, попадает в
  ночной гейт.

**Что считаем выполненной работой:**
- [ ] строки cron в `docker/cron/app.cron` с комментарием, команда не ставит второе
      задание на подключение, у которого задание уже в работе;
- [ ] операция, проведённая банком задним числом в пределах окна, появляется в
      ДДС следующим прогоном;
- [ ] отменённая банком операция помечена, сумма и остатки не меняются молча,
      пометка видна в списке операций;
- [ ] сырой ответ каждого запроса сохранён и читается для повторного разбора без
      обращения к банку;
- [ ] предупреждение о риске дублей на страницах ручного импорта для счетов с API;
- [ ] гейт «подключение не загружалось > 26 ч» — read-only, exit 1 и один `error`;
- [ ] `needs_reauth` и `disabled` подключения в расписание не попадают.

**Тесты:**
- [ ] планировщик — unit: какие дни берутся днём и утром, окно от курсора,
      подключения в `needs_reauth`/`disabled` пропускаются;
- [ ] повтор прогона — functional: тот же день дважды → то же число строк
      (идемпотентность);
- [ ] задним числом — functional: строка появилась в уже загруженном дне внутри
      окна → создана; вне окна → не тронута;
- [ ] отмена — functional: строки нет в перечитанном дне → помечена, не удалена;
      появилась снова → пометка снята;
- [ ] сырые ответы — unit: путь, gzip, очистка в dry-run ничего не удаляет;
- [ ] предупреждение — functional: страница импорта 1С для счёта с API показывает
      предупреждение, для обычного — нет;
- [ ] гейт — functional: свежее подключение → 0, просроченное → exit 1;
- [ ] `MessengerRoutingTest` и проверка cron-строк (команда существует,
      аргументы валидны).

### Stage 4 — остатки банка и ежедневная сверка

**Цель.** Каждый день видно, совпадает ли остаток учёта с остатком банка по
каждому привязанному счёту, а при расхождении — с какого дня и на сколько.
Данные не исправляются автоматически.

**Состав.**
- `bank_sync_balance_snapshot`: компания, `money_account_id`, дата, входящий и
  исходящий остаток банка, обороты, валюта, `is_final`, `fetched_at`; unique
  (компания, счёт, дата); адаптер отдаёт `BankDailyBalanceDTO` (из итогов выписки
  или метода остатков банка);
- `CashFacade::getDailyClosingBalances(companyId, moneyAccountId, from, to)` →
  DTO с остатками учёта;
- две проверки на день: полнота данных банка (входящий + приход − расход =
  исходящий; входящий(D) = исходящий(D−1)) и совпадение исходящего остатка банка
  с остатком учёта, допуск 0 копеек;
- статус дня в `bank_sync_reconciliation_day`: `matched` / `mismatch` /
  `incomplete` (данные банка не сходятся сами с собой) / `pending` (день в банке не
  закрыт); разница и первая дата расхождения по счёту;
- пересчёт сверки — замена окна под `pg_advisory_xact_lock` счёта, не дельта;
  запускается после загрузки дня и командой `bank-sync:reconcile`;
- ночной гейт `bank-sync:reconcile-check` (cron после утренней загрузки,
  read-only): расхождения и `incomplete` → exit 1 и один агрегированный `error`;
- начальный остаток при первой привязке: Action предлагает входящий остаток банка
  на дату старта как начальный остаток счёта; применяется только явным
  подтверждением (UI — Stage 5).

**Что считаем выполненной работой:**
- [ ] остатки банка загружаются вместе с выпиской, предварительные (`is_final =
      false`) заменяются финальными;
- [ ] по каждому привязанному счёту есть статус каждого дня с даты подключения;
- [ ] после исправления учёта (ручная правка, догрузка) пересчёт сверки переводит
      день в `matched`;
- [ ] гейт в cron, его срабатывание и действия описаны в `ARCHITECTURE.md` и
      `docs/workflow/health-gates.md`;
- [ ] начальный остаток не применяется без подтверждения;
- [ ] валютные счета сверяются в валюте счёта.

**Тесты:**
- [ ] проверки дня — unit на все ветки: совпало; расхождение учёта; данные банка не
      сходятся сами с собой; разрыв цепочки входящий/исходящий; день не закрыт;
      день без операций (остаток переносится); допуск 0 (расхождение в 1 копейку —
      `mismatch`);
- [ ] суммы — unit: строки и `bcmath`, без `float`;
- [ ] пересчёт — functional: повторный запуск → то же число строк сверки;
      исправление учёта → `mismatch` становится `matched`;
- [ ] конкурентный пересчёт одного счёта — functional: результат как у
      последовательного;
- [ ] `CashFacade::getDailyClosingBalances` — functional: остатки, чужой счёт →
      исключение;
- [ ] гейт — functional: всё сошлось → 0; расхождение → exit 1, один `error`;
- [ ] начальный остаток — functional: без подтверждения ничего не меняется, с
      подтверждением — остаток счёта на дату старта равен банковскому.

### Stage 5 — интерфейс

**Цель.** Пользователь без поддержки подключает банк, привязывает счета, видит,
когда была последняя загрузка, и понимает, сходится ли учёт с банком и что
делать при расхождении или потере доступа.

**Состав.**
- страница «Банки»: подключения, статус, последняя успешная загрузка, кнопки
  «Подключить» (OAuth), «Переподключить» при `needs_reauth`, «Загрузить сейчас»;
- привязка счетов: счета банка, выбор денежного счёта или создание нового,
  подтверждение начального остатка;
- сверка: по счёту — список дней со статусом и разницей, первая дата
  расхождения; на странице счетов `Cash` — индикатор, встроенный шаблоном из
  `BankSync` (`render(controller(...))`), без PHP-зависимости `Cash → BankSync`;
- баннер `needs_reauth` в рабочей области компании;
- визуал — DS «Ваш Финдир», суммы через `vf_money`, ошибки и расхождения видны
  на странице, а не только в тултипе.

**Что считаем выполненной работой:**
- [ ] весь путь «подключить → привязать → загрузить → увидеть сверку» проходится
      в UI на стенде;
- [ ] права: просмотр — `FINANCE_READ`, изменения — `FINANCE_WRITE`;
- [ ] страницы и индикатор в светлой и тёмной теме и на ширине телефона;
- [ ] пустые состояния (нет подключений, нет привязанных счетов, нет данных
      сверки) и состояния ошибок оформлены;
- [ ] скриншоты ключевых экранов в отчёте этапа.

**Тесты:**
- [ ] контроллеры — functional: каждая страница рендерится; изменения без
      `FINANCE_WRITE` → 403; чужое подключение или счёт → 404;
- [ ] «Загрузить сейчас» — functional: ставит одно сообщение, повторное нажатие
      при задании в работе — не ставит второе;
- [ ] индикатор на странице счетов — functional: статусы `matched` /
      `mismatch` / нет данных;
- [ ] подтверждение начального остатка — functional: CSRF, повторная отправка не
      применяет дважды;
- [ ] ручной smoke по чек-листу экранов (автотестов фронта в проекте нет —
      записать, что проверено).

### Stage 6 — вебхуки и второй банк (после документации банка)

**Цель.** Ускорить появление операций до минут там, где банк присылает

общего кода.

**Состав.**

  операции из тела вебхука не создаются;

  банка.

**Что считаем выполненной работой:**

**Тесты:**

- [ ] контрактные тесты провайдера — для Альфы и второго банка: счета, строки,
