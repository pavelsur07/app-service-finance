# bank-sync: автоматическая загрузка выписок и остатков из банков

Статус: план, ветка `feat/bank-sync`. Дата: 2026-10-25, этапы пересобраны 2026-10-26.
Класс: Large (новый модуль, схема, Messenger и cron, внешняя интеграция, изменение
границы между модулями). Ход работ — `checkpoint.md`, планы и итоги этапов —
`stages/stage-N.md`.

## 1. Задача

Компания подключает свой банк, после чего приложение само:

1. Получает доступ к банку способом, который этот банк поддерживает (OAuth 2.0
   партнёрского API, токен клиента, при необходимости mTLS).
2. Регулярно загружает выписки по привязанным счетам в ДДС без дублей, в том числе
   операции, проведённые банком задним числом.
3. Ежедневно сверяет остаток банка на конец дня с остатком учёта и показывает
   расхождения.

Банков будет несколько. Первый — Альфа-Банк.

## 2. Результат

- Новый модуль `src/BankSync`: подключения, учётные данные, адаптеры банков,
  расписание загрузки, остатки банка и сверка.
- `Cash` остаётся владельцем ДДС: создание транзакций, дедупликация, блокировка
  счёта, пересчёт остатков. Код банков `Cash` не знает.
- Зависимость в одну сторону: `BankSync → CashFacade`. PHP-импорта из `Cash` в
  `BankSync` нет.
- Второй банк добавляется новой папкой `Infrastructure/Bank/<Code>/` с адаптером и
  маппером, без правок в `Cash` и в общем коде загрузки.

## 3a. Альфа-Банк: что известно из документации (на 2026-10-25)

Прочитаны: договор Alfa API (редакция 14.03.2025, 19 стр.) и «Правила взаимодействия
участников системы „Альфа-Бизнес Онлайн“» (редакция 18.04.2026, 124 стр.), оба с
CDN банка. Техническая «Спецификация Alfa API» (запросы, OAuth, эндпоинты) лежит на
developers.alfabank.ru, который отвечает автоматическим клиентам блокировкой WAF и
сертификатом Минцифры. Её Владелец выгрузил 25–26.10 в `docs/plan/alfa/` — разбор
ниже, в подразделе «Спецификация Alfa API по загруженным файлам» и четырёх
дополнениях. Этот блок — выводы из договора и правил.

**Три услуги Alfa API — для нас подходит только одна:**

| Услуга | Что даёт | Подходит ли |
|---|---|---|
| **Alfa ID / B2B SaaS** | Партнёр получает данные клиента банка после входа клиента через Alfa ID и подписанного им «Согласия Alfa ID» | **Да — основной путь для SaaS** |
| Alfa API Direct | Данные **о собственной организации** партнёра (договор 1.27, правила) | Нет: каждый клиент сам должен стать «Партнёром API» и заключить договор с банком |
| Alfa Pay | Платежи клиента партнёру | Не наша задача |

Вывод: нынешний режим кода — токен, выпущенный клиентом, `Bearer` из
`BankConnection` — по смыслу соответствует Alfa API Direct и для клиентов SaaS не
годится. Для Альфы подключение — только через Alfa ID и B2B SaaS.

**Кто может быть партнёром (договор 2.3):** юрлицо или ИП, налоговый резидент РФ, с
расчётным счётом в Альфе и подключённым «Альфа-Бизнес Онлайн». Присоединение — в
интерфейсе «Альфа-Бизнес Онлайн» («Подтверждение о присоединении к Договору ИТВ»);
настройка интеграции — «Личный кабинет разработчика» на developers.alfabank.ru под
логином «Альфа-Бизнес Онлайн» уполномоченного лица.

**Порядок подключения (договор, Приложение 1, раздел 3; Приложение 2, п. 2.2):**
1. Присоединиться к договору ИТВ; запросить услугу Alfa ID/B2B SaaS письмом с
   адреса из подтверждения о присоединении (`Alfa_API@alfabank.ru`).
2. Получить `Client_ID`, `Client_Secret` и тестовый сертификат TLS (запросы — только
   с адреса из подтверждения, п. 3.7).
3. Доработать сервис по Спецификации и пройти тестирование на тестовом сервере.
   Банк вправе потребовать **онлайн-демонстрацию** без макетов (п. 3.3).
4. Промышленный доступ — только после успешных запросов в тестовой среде (п. 3.4);
   банк может потребовать демонстрацию и в промышленной среде (п. 3.5).
5. Кнопку входа через Alfa ID оформить по указаниям банка и обновлять при их
   изменении (Приложение 2, п. 3.2.3, 3.4.4).

**Технические условия, которые влияют на код:**
- Аутентификация партнёра — `Client_ID` + `Client_Secret` и **сертификат TLS
  (mTLS)**; ключ шифрования TLS и сертификат партнёр меняет сам (п. 4.3.4), банк
  вправе потребовать замену за **10 рабочих дней** (п. 4.1.7) и приостановить
  обмен при истечении ключа (п. 4.1.5).
- `access_token` банк **подписывает своей ЭП** и может обновлять ключ подписи
  (п. 4.1.8) — если проверяем подпись токена, ключ банка должен обновляться без
  релиза.
- Запросы версионируются; ранние версии банк выводит из эксплуатации со сроком
  перехода в Спецификации (п. 4.1.1–4.1.4) — версия запроса фиксируется в
  адаптере, переход на новую — отдельной задачей.
- Тестовые и промышленные данные **деактивируются после 3 месяцев без успешных
  запросов** (п. 4.1.9) — ежедневная загрузка это закрывает, но тестовый контур
  нужно «будить».
- Банк вправе приостановить обмен при «запросах с ненормальной частотой» (п.
  4.1.5) — нужен лимитер запросов на банк.
- **Тариф — за каждый успешный запрос** B2B SaaS (Приложение 2, п. 2.3, 4.1);
  служебные запросы и ошибки не тарифицируются (п. 2.4). Частота опроса напрямую
  влияет на расходы. Портал при этом пишет «комиссия не взимается» — вопрос 5
  банку.

**Согласие клиента (правила, «Согласие Alfa ID»):**
- подписывает уполномоченное лицо клиента с правом подписи в «Альфа-Бизнес Онлайн»;
- действует до истечения указанного в нём срока, отзыва, прекращения доступа
  уполномоченного лица или отключения от системы — то есть доступ пропадает и по
  событиям на стороне банка, без нашего участия;
- цели: аутентификация, доступ к сервису, создание кабинета, заключение договора и
  «иные цели, предусмотренные Согласием». Договор (Приложение 2, п. 3.4.1, 3.4.3)
  запрещает использовать данные вне целей Согласия, для аналитических исследований
  и передавать неуполномоченным лицам.

### Спецификация Alfa API по загруженным файлам (`docs/plan/alfa/`, 2026-10-25)

Файлы: `statement1c.yaml` (OpenAPI «Получение выписки в формате 1С»),
`transactions_postman.json` (коллекция Postman раздела «Выписки по счетам ЮЛ»; копия
`transactions_postman (1).json` идентична), PDF страниц «Получение выписки» и
«Получение выписки в формате 1C» (обрезаны: видны меню и заголовок, без схем).

**Среды:** песочница `https://sandbox.alfabank.ru/api/`, прод
`https://baas.alfabank.ru/api/`.

**Авторизация (securitySchemes `bearerAuth`):** два варианта —
`Bearer {access_token}`, полученный по Authorization Code Flow или Authorization
Code Flow H2H (Alfa ID), либо `ApiKey {API Key}` из портала разработчика. Токен —
JWT, издатель `https://id.alfabank.ru/oidc` (OIDC), доступ ограничен
`scope_services` (для выписки — `transactions`; встречаются также `statement`,
`customer_info`, `webhooks`, `payment`). У токенов-образцов песочницы
`exp − iat = 3600` — access-токен живёт час, значит нужен refresh. 403 — сервис не
входит в scope токена.

**Запросы раздела «Выписки по счетам ЮЛ» (из Postman):**

| Запрос | Метод и путь (от `/api`) | Параметры |
|---|---|---|
| Получение выписки (JSON) | `GET jp/v1/statement/transactions` | `accountNumber`, `statementDate`, `page`, `curFormat`; `limit` нет, страница до 1000 операций |
| Выписка в формате 1С (XML) | `GET jp/v2/accounts/{accountNumber}/transactions/1C` | `executeDate`, `offset`, `limit` |
| Выписка MT940 | `GET jp/v1/accounts/{accountNumber}/transactions/MT940` | `executeDate`, `limit` |
| Информация об оборотах | `GET jp/v1/statement/summary` | `accountNumber`, `statementDate` |
| Выписка по корсчетам | `GET jp/v1/correspondent-accounts/{n}/transactions` | не для нас |
| Файл выписки (асинхронно) | `POST jp/v1/accounts/{n}/transactions/files/requests` → `GET jp/v1/accounts/transactions/files/requests/{id}` | заявка и опрос статуса |
| Список счетов (стандарт Банка России, «АФТ») | `GET jp/open-banking/v1.3/accounts/` (Postman); на сайте последняя версия — `GET jp/open-banking/v3.0/aisp-le/accounts` | заголовок `x-fapi-interaction-id`; scope `obru_accounts_le` |
| Выписка по стандарту Банка России | `GET jp/open-banking/v1.3/accounts/{accountId}/statements` (Postman); на сайте — `GET jp/open-banking/v3.0/aisp-le/accounts/{accountId}/statements`, один календарный день | `fromBookingDateTime`, `toBookingDateTime`; есть и асинхронный вариант |

**Что даёт выписка 1С (по `statement1c.yaml`, формат 1C:DirectBank 2.3.2):**
- на день — `OpeningBalance`, `ClosingBalance`, `TotalDebits`, `TotalCredits`
  одним запросом вместе с операциями: этого достаточно для сверки Stage 9 без
  отдельного запроса остатков;
- `StatementType`: `0` — окончательная, `1` — промежуточная, `2` — текущий
  остаток → признак `is_final` для остатков и для перечитывания дня;
- операция: `DC` (`1` списание, `2` поступление), дата проводки, `PayDoc@id`
  (идентификатор документа в банке), `docKind`, номер и дата документа,
  плательщик и получатель (счёт, БИК, ИНН, КПП, наименование), назначение, статус
  исполнения (`02` — исполнен), бюджетные реквизиты;
- пагинация `limit`/`offset` и `TotalCount` в ответе; глубина — не раньше 5 лет от
  1 января текущего года;
- ошибки: 400 (`1010`), 401 `invalid_token` (истёк — обновить через
  `refresh_token`; отозван — пройти авторизацию заново), 403 (scope), 404, 429, 500,
  503. **`ErrorDescription` содержит номер счёта** — в логи не писать.

**Расхождения с текущим кодом `AlfaApiClient`:**
- путь выписки `/jp/v1/statement/transactions` без префикса `/api`, а базовый URL
  в форме — `https://baas.alfabank.ru`: получается
  `https://baas.alfabank.ru/jp/v1/...` вместо `.../api/jp/v1/...` — запрос не
  дойдёт. Путь списка счетов (`/api/jp/open-banking/v1.3/accounts`) верный;
- у JSON-выписки параметра `limit` нет (схема 26.10): страница — до 1000 операций,
  дальше `page` и `_links` с `rel=next`; текущий код пагинирует по `_links` — верно.
  `limit` (по умолчанию 10) есть у выписки 1С и MT940 — при переходе на 1С передавать
  максимальный;
- разбор JSON-ответа (`transactions`, `uuid`, `amount.amount`, `direction`,
  `_links.next`) совпадает со схемой; не разбираются `transactionId`, `revaln`
  (переоценка валютного счёта), `curFormat`.

**Решение по формату** — заменено 26.10 после схемы JSON-выписки: см. «Решение по
формату (обновлено)» во втором пакете ниже.

**Дополнение по спецификациям 26.10, второй пакет** (`statement (1).yaml`,
`turnover.yaml`, `accounts-ob.yaml`, `statement-ob.yaml`; HTML «Как использовать
ACF», «Получение кода авторизации», «Получение токена доступа», «Обновление токена
доступа», «Получение профиля представителя пользователя», «Тестовые интеграции»):

*Alfa ID (Authorization Code Flow):*
- authorize: песочница `https://id-sandbox.alfabank.ru/oidc/authorize`, прод
  `https://id.alfabank.ru/oidc/authorize`; параметры `response_type=code`,
  `client_id`, `redirect_uri`, `scope` (минимум `openid`, через пробел), `state`
  (UUID 36 символов, привязан к сессии), необязательные `nonce`, PKCE
  `code_challenge` + `code_challenge_method=S256`, `prompt`
  (`consent` — при смене набора scope, `select_org` — выбор организации);
- код авторизации живёт **2 минуты, одноразовый**; ошибки возврата —
  `access_denied`, `consent_required`, `login_expired` (15 минут) и др.;
- token: песочница `https://sandbox.alfabank.ru/oidc/token`, прод
  `https://baas.alfabank.ru/oidc/token`; form-urlencoded, `client_secret` в теле
  (mTLS на token endpoint в документации не упомянут); ответ — `access_token`
  (1 час), `refresh_token`, `id_token`;
- **refresh-токен живёт 180 дней и годится не больше чем на 2 обновления**; ответ
  на обновление несёт новый `refresh_token` — сохранять его в той же транзакции,
  обновление строго под блокировкой подключения: параллельное обновление сожжёт
  токен;
- **согласие клиента живёт 365 дней**, потом — новая авторизация; дату окончания
  отдаёт метод «Данные по согласиям пользователей» (не загружен);
- токены отзываются: смена пароля, блокировка, истечение согласия, смена
  уполномоченного лица организации, **повторная авторизация того же пользователя с
  того же устройства** (прежняя пара отзывается — переподключение заменяет
  учётные данные, а не добавляет второе подключение);
- `userinfo` (`/oidc/userinfo`, ответ — подписанный JWT) отдаёт ФИО, паспорт, ИНН
  физлица, роль. Нам не нужно: запрашивать минимальные scope, не хранить; связь
  подключения с организацией — через список счетов;
- для данных юрлиц и физлиц — разные `client_id`; в интеграции до 20
  `redirect_uri`; тестовая партнёрская интеграция появляется на портале после
  договора, авторизация в ней — только Alfa ID.

*Выписки:*
- **JSON-выписка** (`jp/v1/statement/transactions`): `uuid` — «уникальный
  идентификатор операции», плюс `transactionId`; страница до 1000, `limit` нет;
  остатков нет. Глубина — 5 лет от 1 января текущего года.
- **Обороты** (`jp/v1/statement/summary`): на день — `openingBalance`,
  `closingBalance`, обороты по дебету и кредиту, **число дебетовых и кредитовых
  операций**, `composedDateTime`, `lastMovementDate`. Признака окончательности
  нет.
- **Стандарт Банка России v3** (`aisp-le`): список счетов — `accountId`, статус,
  валюта, номер в `AccountDetails.identification`; выписка — один календарный
  день, `page` до 5000, остатки `OpeningBooked` и `ClosingAvailable` (доступный,
  не учётный — для сверки хуже), операции с `transactionIdentification`.

*Решение по формату (обновлено):* два кандидата, выбор в песочнице (Stage 7) по
одному критерию — устойчив ли идентификатор операции при повторном чтении дня:
- **A. JSON-выписка + обороты** — 2 платных запроса на счёт в день при ≤1000
  операций; `uuid` банк называет уникальным (на нём уже держится дедупликация);
  обороты дают остатки и число операций — Stage 9 проверяет и суммы, и количество;
- **B. Выписка 1С** — 1 запрос; остатки и признак окончательности, но
  уникальность `PayDoc@id` не обещана.
По умолчанию — **A**: дубли или потери в учёте дороже одного запроса в день.

**Дополнение 26.10, третий пакет** (защита канала, сертификаты, подключение и
запуск в проме, тестирование, согласия, отзыв токена, вебхуки, подпись JSON):

*Канал и сертификаты:*
- **Прод-интеграция создаётся «Заблокированной» и разблокируется только после
  выпуска и установки TLS-сертификата** — mTLS обязателен; по странице
  «TLS-сертификат» (четвёртый пакет) он нужен **и в песочнице** (тестовый
  сертификат банка).
- **Сервера банка — на сертификатах Минцифры** (Russian Trusted Root CA / Sub CA):
  HTTP-клиенту Альфы нужен этот CA (`cafile` scoped-клиента, не в системное
  хранилище всего контейнера). Отсюда и ошибка самоподписанного сертификата при
  попытке открыть developers.alfabank.ru.
- **Метод шифрования канала зависит от персональных данных:** без ПДн — TLS RSA;
  **если передаются ПДн — обязателен ГОСТ** (TLS ГОСТ или ФПСУ ГОСТ). В выписке —
  наименования плательщиков и получателей, у ИП и физлиц это ФИО. Если банк
  сочтёт выписку ПДн, нужен ГОСТ-TLS: PHP/curl с OpenSSL его не умеет, понадобится
  отдельный шлюз (`stunnel`/`nginx` с ГОСТ-движком или ФПСУ) — это инфраструктура
  вне кода. **Главный вопрос к банку** (вопрос 7 ниже).
- Транспортная подпись и шифрование JSON (RSA/ГОСТ, сертификат УЦ Альфа-Банка,
  методы `gd/v1/crypto-service/certificates`) включаются настройками интеграции —
  это для платёжных сценариев; для чтения выписки не ожидается, подтвердить у
  банка.

*Подключение и прод:*
- договор ИТВ подписывается в «Альфа-Бизнес» (Все сервисы → Alfa API), OTP или
  УКЭП; **«комиссия за подключение и использование API не взимается»** — расходится
  с тарифом за запрос из договора 2025 года (§3a выше), уточнить у банка;
- тестовые интеграции (партнёрская B2B и H2H) появляются на портале сами;
  **прод-интеграцию со scope можно создать только после хотя бы одного успешного
  (2xx) запроса с этим scope в песочнице**; не больше 5 прод-интеграций;
- одна интеграция — один сценарий (своя компания / чужие компании / физлица):
  BankSync — отдельная партнёрская интеграция;
- тестовые логин, пароль и OTP песочницы для ЮЛ — на странице «Как это
  тестировать» (`docs/plan/alfa/kak-eto-testirovat.html`), годятся для
  автоматического e2e-прогона в песочнице.

*Согласия и отзыв:*
- `GET /oidc/client-consents` (пром `https://baas.alfabank.ru/oidc/`): токен
  **Client Credentials Flow** (уровня партнёра) или ACF; фильтры `clientId`, `sub`,
  `organizationIdHash`, `isActive`, `limit` (по умолчанию 1000), `offset`; в ответе
  дата окончания согласия → ночная сверка сроков согласий всех подключений одним
  запросом;
- `POST /oidc/revoke` (`client_id`, `client_secret`, `token`, `token_type_hint`);
  отзыв refresh отзывает и access → отключение в UI сначала отзывает токен в банке,
  потом удаляет учётные данные.

*Вебхуки (Stage 12):* есть событие «Выписки по счетам ЮЛ» (scope `transactions`);
подключение — письмо в поддержку с `callbackUri`, затем создание вебхука методом
API; домен `callbackUri` (второго уровня) должен совпадать с доменом
`redirect_uri`; нужен наш открытый «Партнёрский метод для получения вебхуков»
(страница не загружена). Права пользователя — те же, что для выписки.

**Дополнение 26.10, четвёртый пакет** (TLS-сертификат, Client Credentials Flow,
проверка подписи, права доступа, scopes, пагинация, версионирование, вебхуки
полностью, сертификаты Минцифры файлами):

*mTLS (страницы «TLS-сертификат», «TLS-сертификаты на портале»):*
- двусторонний TLS **1.2** на всех запросах к API, в песочнице тоже;
- песочница: общий тестовый сертификат банка `test_cert.zip` (сертификат, ключ,
  цепочка УЦ банка `alfa-bank_st_ca_root` + `alfa-bank_st_ca_sub2`, контейнер

- пром: ключ RSA 2048 и CSR генерируем сами (`openssl_INNLE.cnf` банка; в subject —

  ключом;

  интеграций; компрометация ключа — письмо в поддержку и перевыпуск;

  Файлы Минцифры загружены (`Russian_Trusted_Root_CA.cer` до 2032-02-27,
  `Russian_Trusted_Sub_CA.cer` до **2027-03-06**, `Russian_Trusted_Sub_CA_2024.cer`

`client_id`, `client_secret`, `scope`; access на час, без refresh. Методы с
банковской тайной по CCF недоступны — выписка только по токену клиента (ACF);
CCF нужен для `client-consents`.

открытый ключ — файл сертификата `https://developers.alfabank.ru/files/cer.crt`
(«certificate-prod»), **JWKS нет**. Проверяем `id_token` при входе (подпись, `iss`,
`aud` = наш `client_id`, `exp`, `nonce`); сертификат — в конфигурации, смена без
релиза.

*Scopes:* `transactions` покрывает JSON-выписку, 1С, MT940, обороты и файл выписки;
список счетов — `obru_accounts_le` (стандарт Банка России) или `customer`
(`GET /jp/v2/customer-info`, профиль организации) — выбор в песочнице. Набор для
авторизации: `openid transactions` + scope списка счетов; лишнего (ПДн
представителя, `payment`) не запрашиваем.

*Пагинация (общая):* `limit` до 1000, `offset`, ответ `pagination.totalCount`;
сортировка — новые сверху.

*Вебхуки полностью (Stage 12):*

## 4. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где код | Новый модуль `BankSync` | Обсуждено с Владельцем 25.10, вариант B. Интеграции меняются по своим причинам; на проде нет данных, перенос дешёвый |
| Граница с `Cash` | `BankSync` вызывает `CashFacade`; `Cash` про `BankSync` не знает | Без циклов; правила ДДС в одном месте |
| Кто коммитит | `BankSync`-handler. Методы `CashFacade` только `persist()`; в `ARCHITECTURE.md` — «коммитит вызывающий» | CLAUDE.md, «Транзакции» |
| Формат данных адаптера | Нормализованные DTO (`BankAccountDTO`, `BankStatementLineDTO`, `BankDailyBalanceDTO`), сырой `array` за пределы адаптера не выходит | Иначе второй банк не встанет |
| День выписки | Все страницы дня собираются в память, потом один вызов `CashFacade` и коммит | HTTP-сбой случается до первого `persist()`, отсоединять недописанные строки больше не нужно |
| Вебхук или опрос | Опрос — источник правды; вебхук только ставит задание на загрузку | Вебхуки теряются и есть не у всех банков |
| Окно перечитывания | Последние 3 дня от курсора (настраивается на банк) | Задним числом и корректировки |
| Учётные данные | Общий `Shared\Security` (`FieldEncryptionServiceInterface`, sodium `secretbox`, ключи `APP_ENCRYPTION_*`, `key_version`); кодек по образцу `MoySklad\Infrastructure\Security\ConnectionTokenCodec` | Механизм есть, ключи на прод доставляет `deploy.yml`; своего ключа не заводим |
| Когда шифровать | С Stage 1: новая таблица `bank_sync_connection` создаётся без колонки с открытым токеном | Шифрование уже готово; иначе пришлось бы делать expand/contract, как у маркетплейсов, на ровном месте |
| Ротация ключа | Общая команда `app:security:rotate-keys`: каждый модуль регистрирует свой ротатор (тег), команда обходит все — `Marketplace`, `MoySklad`, `BankSync`; dry-run по умолчанию; инструкция `docs/maintenance/encryption-key-rotation.md` переписывается на общую команду | Сейчас ротация есть только у маркетплейсов: смена ключа по инструкции сделает нечитаемыми токены MoySklad, а потом и банков |
| Старые таблицы | Новые таблицы `bank_sync_*` со `string $companyId`, старые удаляются, если на проде пусты | Не тащить `ManyToOne Company` в новый модуль |
| Сверка | Две проверки на день: полнота данных банка (входящий + приход − расход = исходящий) и совпадение остатка с учётом, допуск 0 | Первая ловит недогрузку, вторая — расхождение учёта |
| Предупреждение о ручном импорте | У `MoneyAccount` признак источника выписки; `BankSync` ставит его через `CashFacade` при привязке, `Cash` сам показывает предупреждение | `Cash` не должен знать про `BankSync` |
| Исправление расхождений | Автоматически не исправляем; показываем и поднимаем гейт | Прод-деньги |
| Подключение Альфы | Только Alfa ID + B2B SaaS (OAuth, согласие клиента). Тип учётных данных `static_token` остаётся в общем коде для банков, которые выдают токен клиенту, но для Альфы в UI не предлагается | Токен клиента у Альфы — Alfa API Direct, только для собственной организации партнёра (§3a) |
| Учётные данные партнёра | `Client_ID`, `Client_Secret`, сертификат и ключ TLS — одни на приложение, в `.env`/файлах прода (не в БД, не в git); у компании в БД — только её токены | Это идентификация нашего приложения перед банком, не клиента |
| Частота опроса | Настраивается на банк; для Альфы дневной опрос по умолчанию выключен до ответа о тарифе, утренняя загрузка — включена | По договору каждый успешный запрос B2B SaaS платный, портал пишет обратное (§3a, вопрос 5) |
| Формат выписки Альфы | JSON-выписка (`jp/v1/statement/transactions`) + обороты (`jp/v1/statement/summary`) | У JSON `uuid` назван уникальным; обороты дают остатки и число операций для сверки (§3a) |
| Ключ дедупликации Альфы | `external_id` = `uuid`; `transactionId` есть в DTO и в сырых ответах; стабильность проверяется в Stage 7, переключение ключа — до Stage 11, пока данных Альфы на проде нет | Банк в разных разделах называет уникальным то один, то другой (§3a, вопрос 3) |

Локальные коммиты, push и Draft PR — одним шагом на handoff. Backend и frontend —

### Stage 2 — общая ротация ключей шифрования

**Цель.** Ключ шифрования можно сменить, не потеряв ни одного секрета ни в одном
модуле. Сейчас ротация есть только у маркетплейсов: смена ключа по инструкции

**Состав.**
- read-only проверка на проде до начала: распределение записей по версиям ключа у

- ротаторы: `Marketplace` (логика из `RotateConnectionKeysCommand`), `MoySklad`

- `app:marketplace:rotate-connection-keys` — тонкая обёртка над общей командой до

- `docs/maintenance/encryption-key-rotation.md` — на общую команду и все модули;

**Что считаем выполненной работой:**
- [ ] `app:security:rotate-keys` в dry-run показывает распределение по версиям по

**Тесты:**

### Stage 3 — OAuth-подключение, общая часть

**Цель.** Подключение банка живёт на токенах OAuth 2.0, которые обновляются сами,
а потеря доступа видна и не засоряет логи. Банк-специфики нет — проверяется на
заглушке авторизационного сервера.

**Состав.**
- статус подключения: `active` / `needs_reauth` / `revoked` / `disabled`; 401
  после обновления токена → `needs_reauth` без ретраев;
- тип учётных данных `oauth2` (access, refresh, `expires_at`, срок согласия) в том
  же зашифрованном JSON;
- обновление токена заранее, под advisory-блокировкой подключения; **новый
  `refresh_token` из ответа сохраняется в той же транзакции** — у Альфы refresh
  годится не больше чем на 2 обновления, параллельное обновление сожжёт его;
- вход: `state` (UUID в сессии) и PKCE S256; callback обменивает код сразу (у
  Альфы код живёт 2 минуты); повторная авторизация заменяет учётные данные того же
  подключения, а не создаёт второе;
- интерфейс провайдера авторизации (адреса, scope, разбор ответа) — реализация
  для Альфы в Stage 5;
- `Client_ID`/`Client_Secret` приложения — из `.env`, по одной паре на банк и
  среду (песочница/прод).

**Что считаем выполненной работой:**
- [ ] подключение проходит полный цикл против заглушки: редирект → callback →
      токены зашифрованы → загрузка работает;
- [ ] истёкший access-токен обновляется до запроса к банку; два воркера не
      обновляют один refresh-токен одновременно;
- [ ] отозванный или невалидный refresh → `needs_reauth`, загрузка этого
      подключения не ставится в очередь, одно `warning`, без `error` на каждый
      прогон.

**Тесты:**
- [ ] callback — functional: верный `state` → токены сохранены зашифрованными;
      неверный или просроченный `state` → отказ, ничего не сохранено; callback
      чужой компании → отказ; неверный `code_verifier` → отказ;
- [ ] обновление токена — unit: за N минут до истечения обновляет, раньше — нет;
      ответ 400/401 на refresh → `needs_reauth`; новый refresh сохранён;
- [ ] конкурентное обновление — functional: два процесса, один refresh-запрос;
- [ ] статусы — unit на матрицу переходов (`revoked` не возвращается в `active`
      без нового согласия);
- [ ] повторная авторизация — functional: то же подключение, учётные данные
      заменены, второго подключения нет.

### Stage 4 — канал Альфы: mTLS и сертификаты

**Цель.** HTTP-клиент Альфы ходит в песочницу и на прод по mTLS (TLS 1.2), доверяет
только нужным CA, а истечение любого сертификата видно заранее.

**Состав.**
- клиентский сертификат и ключ — путь к `.p12` (или паре `.cer`/`.key`) и пароль
  из `.env`, файлы вне git; песочница — общий тестовый сертификат банка, прод —
  свой (Stage 11);
- доверенные CA сервера банка — файлом в репозитории (публичные сертификаты):
  Минцифры (Root, Sub, Sub 2024 — сейчас в `docs/plan/alfa/`) + цепочка УЦ банка
  `alfa-bank_st_ca_root`/`sub2`; `cafile` только у scoped-клиента Альфы, другие
  клиенты не меняются;
- ночной гейт сроков: клиентский сертификат и CA — предупреждение за 30 дней,
  ошибка за 10 (банк требует замену за 10 рабочих дней; Sub CA Минцифры истекает
  2027-03-06); прод-сертификат живёт 365 дней;
- runbook замены сертификата без простоя (у интеграции до 2 активных): выпустить
  новый → выкатить → отозвать старый — в `alfa-demo.md`;
- если банк потребует ГОСТ-канал (§3a, вопрос 7) — этот этап не меняется, ГОСТ-шлюз
  встаёт отдельной задачей перед Stage 11.

**Что считаем выполненной работой:**
- [ ] запрос в песочницу Альфы с тестовым сертификатом проходит TLS (ответ банка,
      а не ошибка рукопожатия);
- [ ] без сертификата клиент Альфы не стартует с понятной ошибкой конфигурации,
      остальные HTTP-клиенты работают;
- [ ] гейт сроков в cron, действия при срабатывании — в
      `docs/workflow/health-gates.md`.

**Тесты:**
- [ ] конфигурация клиента — unit: Альфа получает `local_cert`/`cafile`, другой
      scoped-клиент — нет;
- [ ] гейт — unit: больше 30 дней → 0; меньше 30 → `warning`; меньше 10 или
      истёк → exit 1 и `error`; проверяются и клиентский сертификат, и CA;
- [ ] пароль и путь к ключу не попадают в логи и исключения.

### Stage 5 — Alfa ID

**Цель.** Клиент подключает Альфу сам: входит через Alfa ID, подписывает согласие,
и приложение получает токены его организации. Отзыв доступа и истечение согласия
обрабатываются без участия поддержки.

**Состав.**
- провайдер авторизации Альфы для Stage 3: authorize
  (`id-sandbox.alfabank.ru` / `id.alfabank.ru`), token/refresh
  (`sandbox.alfabank.ru` / `baas.alfabank.ru` `/oidc/token`); scope минимальный —
  `openid transactions` + scope списка счетов (выбор в Stage 7); `userinfo` и ПДн
  представителя не запрашиваем и не храним;
- проверка `id_token` при входе: RS256 по `kid`, `iss`, `aud` = наш `client_id`,
  `exp`, `nonce`; сертификат проверки `cer.crt` банка — путь из `.env`, смена без
  релиза (JWKS у банка нет);
- отключение: `POST /oidc/revoke` refresh-токеном до удаления учётных данных;
  ошибка отзыва не мешает отключению (`warning`);
- сроки согласий: токен Client Credentials (только для этого метода) и ночная
  команда `GET /oidc/client-consents` — дата окончания согласия у подключений,
  предупреждение клиенту за 30 дней, истёкшее → `needs_reauth`;
- ошибки банка: 401 `invalid_token` → обновить токен или `needs_reauth`; 403
  `insufficient_scope` → `needs_reauth` с подсказкой о правах (список прав
  пользователя клиента — §3a);
- в UI нет режима «токен клиента» для Альфы, только Alfa ID (кнопка — по
  указаниям банка, Stage 10).

**Что считаем выполненной работой:**
- [ ] в песочнице тестовым пользователем банка («Как это тестировать»): вход →
      согласие → токены сохранены зашифрованными;
- [ ] отключение отзывает токен в банке;
- [ ] ночная команда согласий обновляет даты и не пишет ПДн в лог.

**Тесты:**
- [ ] `id_token` — unit: верная подпись → принят; чужой `aud`, просроченный `exp`,
      неверный `nonce`, неизвестный `kid` → отказ;
- [ ] провайдер — unit: authorize-URL (параметры, PKCE, `state`), разбор ответа
      token/refresh, ошибки `invalid_grant`/`invalid_client`;
- [ ] отзыв — unit: вызывается до удаления; ошибка банка → подключение всё равно
      отключено;
- [ ] согласия — functional: дата обновлена; осталось меньше 30 дней →
      предупреждение; истекло → `needs_reauth`;
- [ ] 403 `insufficient_scope` → `needs_reauth` без ретраев.

### Stage 6 — счета банка и привязка

**Цель.** Приложение явно знает, к какому денежному счёту относится каждый счёт
банка; непривязанный счёт не загружается и не теряется молча.

**Состав.**
- список счетов клиента — через адаптер (`BankAccountDTO`); для Альфы
  `jp/open-banking/v3.0/aisp-le/accounts` или `jp/v2/customer-info` (выбор в
  Stage 7, до него — v3.0; путь v1.3 из старого кода не используется);
- `bank_sync_account_link`: счёт банка (номер, БИК, валюта) → `money_account_id`,

- счёт банка без пары попадает в список «не привязан»;
- при привязке `BankSync` через `CashFacade` отмечает у `MoneyAccount` источник

**Что считаем выполненной работой:**
- [ ] привязка сохраняется; один денежный счёт нельзя привязать к двум счетам
      банка; непривязанный счёт банка не загружается и виден в списке;

**Тесты:**

- [ ] загрузка — functional: непривязанный счёт пропущен с `info`, без `error`.

### Stage 7 — проверка в песочнице Альфы

**Цель.** До прода подтвердить на живом API банка то, что документация не
гарантирует, и выполнить условие банка: прод-интеграцию со scope можно создать

**Состав.**

- дважды прочитать один день: какой идентификатор стабилен — `uuid` или
  `transactionId` (сейчас `external_id` = `uuid`, `transactionId` — в DTO и сырых
  ответах); если стабилен только `transactionId` — переключить ключ в маппере, пока
  данных Альфы на проде нет;
- выбрать метод списка счетов (`obru_accounts_le` или `customer`);
- проверить, что обороты (`summary`) сходятся с операциями выписки за день;
- записать в `alfa-demo.md`: сценарий онлайн-демонстрации банку, результаты,
  исходящий IP, примеры `X-TraceId`;
- регулярный проверочный запрос в песочнице, чтобы тестовая интеграция не
  деактивировалась через 3 месяца простоя (п. 4.1.9 договора).

**Что считаем выполненной работой:**
- [ ] все пункты выше проверены, решения записаны в §4 и «Историю плана»;
- [ ] обезличенные ответы песочницы сохранены фикстурами для тестов.

**Тесты:** фикстуры из песочницы подключены к тестам маппера (Stage 1, 6).

### Stage 8 — загрузка по расписанию

**Цель.** Выписка приходит в ДДС сама: финальная выписка за вчера — к утру,
операции задним числом и отмены банка не теряются, а дубли с ручным импортом не
возникают незаметно.

**Состав.**
- cron: утром (06:30) — вчера и окно перечитывания 3 дня от курсора; дневной опрос
  (раз в час 08:00–20:00) — настройкой банка, для Альфы выключен до ответа о
  тарифе (§3a, вопрос 5); одно задание на подключение за раз;
- лимитер запросов на банк (образец — `SharedQuota` Ozon); счётчик запросов на банк
  и компанию в логе прогона; `X-TraceId` ответа банка в логе запроса;
- страница JSON-выписки Альфы — до 1000 операций, дальше по `_links` `next`;
  каждая страница — отдельный запрос;
- сырые ответы банка — в `ObjectStorageInterface`
  (`bank/{company}/{bank}/{account}/{date}/{fetchedAt}.json.gz`); срок хранения —
  по ответу банка (§3a, вопрос 6), по умолчанию год; очистка командой с dry-run;
  доступ только из `BankSync`;
- отмена банком: строка с нашим `external_id`, которой нет в перечитанном окне,
  не удаляется, а помечается «нет в выписке банка» через `CashFacade`; появилась
  снова — пометка снимается;
- предупреждение на страницах импорта 1С и файла, если у счёта источник «банк по
  API»; импорт не блокируется;
- старт и финиш задания с `companyId`, один агрегированный `error` на сбой
  прогона; ночной гейт «подключение не загружалось > 26 часов».

**Что считаем выполненной работой:**
- [ ] строки cron в `docker/cron/app.cron` с комментарием; второе задание на
      подключение, у которого задание в работе, не ставится;
- [ ] операция задним числом в пределах окна появляется в ДДС следующим прогоном;
- [ ] отменённая банком операция помечена, сумма и остатки не меняются молча;
- [ ] сырой ответ каждого запроса сохранён и читается без обращения к банку;
- [ ] `needs_reauth` и `disabled` подключения в расписание не попадают.

**Тесты:**
- [ ] планировщик — unit: какие дни берутся утром и днём, окно от курсора,
      `needs_reauth`/`disabled` пропускаются, дневной опрос выключен настройкой;
- [ ] повтор прогона — functional: тот же день дважды → то же число строк;
- [ ] задним числом — functional: строка в окне → создана; вне окна → не тронута;
- [ ] отмена — functional: строки нет → помечена, не удалена; появилась → снята;
- [ ] лимитер — unit: сверх квоты запрос ждёт, а не уходит;
- [ ] сырые ответы — unit: путь, gzip, очистка в dry-run ничего не удаляет;
- [ ] предупреждение — functional: страница импорта 1С для счёта с API
      показывает предупреждение, для обычного — нет;
- [ ] гейт — functional: свежее подключение → 0, просроченное → exit 1;
- [ ] `MessengerRoutingTest` и проверка cron-строк.

### Stage 9 — остатки банка и ежедневная сверка

**Цель.** Каждый день видно, совпадает ли остаток учёта с остатком банка по
каждому привязанному счёту, а при расхождении — с какого дня и на сколько.
Данные не исправляются автоматически.

**Состав.**
- `bank_sync_balance_snapshot`: компания, `money_account_id`, дата, входящий и
  исходящий остаток банка, обороты, число операций, валюта, `is_final`,
  `fetched_at`; unique (компания, счёт, дата); адаптер отдаёт
  `BankDailyBalanceDTO`; у Альфы — из оборотов `jp/v1/statement/summary`;
  `is_final` = день раньше текущего по времени банка, окно перечитывания обновляет
  снимок;
- `CashFacade::getDailyClosingBalances(companyId, moneyAccountId, from, to)` →
  DTO с остатками учёта;
- три проверки на день: полнота данных банка (входящий + приход − расход =
  исходящий; входящий(D) = исходящий(D−1)); число операций банка = числу
  загруженных строк; исходящий остаток банка = остатку учёта, допуск 0 копеек;
- статус дня в `bank_sync_reconciliation_day`: `matched` / `mismatch` /
  `incomplete` / `pending`; разница и первая дата расхождения по счёту;
- пересчёт сверки — замена окна под `pg_advisory_xact_lock` счёта, не дельта;
  после загрузки дня и командой `bank-sync:reconcile`;
- ночной гейт `bank-sync:reconcile-check` (после утренней загрузки, read-only):
  расхождения и `incomplete` → exit 1 и один агрегированный `error`;
- начальный остаток при первой привязке: входящий остаток банка на дату старта
  предлагается начальным остатком счёта, применяется только подтверждением
  (UI — Stage 10).

**Что считаем выполненной работой:**
- [ ] остатки банка загружаются вместе с выпиской, предварительные заменяются
      финальными;
- [ ] по каждому привязанному счёту есть статус каждого дня с даты подключения;
- [ ] после исправления учёта пересчёт переводит день в `matched`;
- [ ] гейт в cron, действия при срабатывании — в `ARCHITECTURE.md` и
      `docs/workflow/health-gates.md`;
- [ ] начальный остаток не применяется без подтверждения;
- [ ] валютные счета сверяются в валюте счёта.

**Тесты:**
- [ ] проверки дня — unit на все ветки: совпало; расхождение учёта; данные банка не
      сходятся сами с собой; разрыв цепочки; число операций не совпало; день не
      закрыт; день без операций; расхождение в 1 копейку → `mismatch`;
- [ ] суммы — unit: строки и `bcmath`, без `float`;
- [ ] пересчёт — functional: повтор → то же число строк сверки; исправление
      учёта → `matched`;
- [ ] конкурентный пересчёт одного счёта — functional: результат как у
      последовательного;
- [ ] `CashFacade::getDailyClosingBalances` — functional: остатки, чужой счёт →
      исключение;
- [ ] гейт — functional: всё сошлось → 0; расхождение → exit 1, один `error`;
- [ ] начальный остаток — functional: без подтверждения ничего не меняется.

### Stage 10 — интерфейс

**Цель.** Пользователь без поддержки подключает банк, привязывает счета, видит
последнюю загрузку и понимает, сходится ли учёт с банком и что делать при

**Состав.**

  «Подключить» (Alfa ID, кнопка по указаниям банка), «Переподключить» при
  `needs_reauth`, «Загрузить сейчас», «Отключить»;
- подсказка перед подключением: какие права нужны пользователю в «Альфа-Бизнес»

- привязка счетов: выбор денежного счёта или создание нового, подтверждение
  начального остатка;
- сверка: по счёту — дни со статусом и разницей, первая дата расхождения; на
  странице счетов `Cash` — индикатор, встроенный шаблоном из `BankSync`
  (`render(controller(...))`);
- банк виден в списке для подключения, только если для него настроены учётные
  данные интеграции в `.env` (до Stage 11 Альфы на проде в списке нет);
- баннер `needs_reauth` и «согласие скоро истекает»;
- визуал — DS «Ваш Финдир», суммы через `vf_money`, ошибки видны на странице, а
  не только в тултипе.

**Что считаем выполненной работой:**
- [ ] путь «подключить → привязать → загрузить → увидеть сверку» проходится в UI
      на стенде;
- [ ] права: просмотр — `FINANCE_READ`, изменения — `FINANCE_WRITE`;
- [ ] светлая и тёмная тема, ширина телефона; пустые состояния и ошибки
      оформлены;
- [ ] скриншоты ключевых экранов в отчёте этапа.

**Тесты:**
- [ ] контроллеры — functional: каждая страница рендерится; изменения без
      `FINANCE_WRITE` → 403; чужое подключение или счёт → 404;
- [ ] «Загрузить сейчас» — functional: одно сообщение, повторное нажатие при
      задании в работе — не ставит второе;
- [ ] индикатор на странице счетов — functional: `matched` / `mismatch` / нет
      данных;
- [ ] подтверждение начального остатка — functional: CSRF, повторная отправка не
      применяет дважды;
- [ ] ручной smoke по чек-листу экранов.
