**Тема:** Партнёрская интеграция (B2B, Alfa ID) для загрузки выписок клиентов в
сервис управленческого учёта — вопросы перед подключением

Здравствуйте!

Мы — [наименование юрлица], ИНН [ИНН], клиент Альфа-Банка. Разрабатываем
сервис управленческого учёта «Ваш Финдир» (SaaS для малого бизнеса) и планируем
подключиться к Alfa API как партнёр: клиенты сервиса через Alfa ID (Authorization
Code Flow) дают согласие, а сервис раз в сутки загружает выписку и остатки по их
расчётным счетам в рублях.

Планируемые методы (scope `transactions`, `openid`, scope списка счетов):
- `GET /jp/v1/statement/transactions` — выписка за день;
- `GET /jp/v1/statement/summary` — обороты и остатки за день;
- `GET /jp/open-banking/v3.0/aisp-le/accounts` или `GET /jp/v2/customer-info` —
  список счетов клиента;
- позже — вебхук `ul_transaction_default`.

Объём: одна загрузка в сутки на счёт с перечитыванием трёх последних дней, то
есть около 6–8 запросов на счёт в сутки.

Перед подписанием договора и разработкой просим ответить на вопросы.

**1. Допустимость сценария (вопрос 1).** Допускает ли партнёрская B2B-интеграция
постоянную (ежедневную) загрузку выписки и остатков клиента в сторонний сервис
управленческого учёта на основании «Согласия Alfa ID»? Есть ли ограничения по
целям использования данных?

**2. Защита канала (вопрос 7).** В выписке есть реквизиты контрагентов, в том
числе ФИО индивидуальных предпринимателей и физических лиц. Считается ли это
передачей персональных данных, при которой, согласно разделу «Защита канала»,
обязателен ГОСТ (TLS ГОСТ или ФПСУ ГОСТ)? Или для нашего сценария достаточно
mTLS с RSA-сертификатом?

**3. Стоимость (вопрос 5).** На портале указано: «комиссия за подключение и
использование API не взимается». Договор об ИТВ от 14.03.2025 предусматривает
плату за успешный запрос. Что действует для партнёрской интеграции? Если
использование платное:
- сколько стоит запрос;
- считается ли каждая страница выписки отдельным запросом;
- оплачиваются ли ответы 401, 404 и 429.

**4. Лимиты (вопрос 3).**
- Какие ограничения частоты запросов действуют: на `client_id`, на организацию,
  на метод?
- Передаётся ли при ответе 429 заголовок `Retry-After`?
- Какая частота считается «ненормальной» по п. 4.1.5 договора?

**5. Идентификатор операции (вопрос 3).** В схеме «Получение выписки»
уникальным идентификатором операции назван `uuid`. В разделе «Партнёрский метод
для получения вебхуков» дубли предлагается отбрасывать по `transactionId`.
- Какой из них остаётся неизменным при повторном запросе выписки за тот же день
  и после изменения операции (`actionType=update`)?
- Может ли один идентификатор встретиться дважды в выписке за день?

**6. Изменение прошлых дней (вопрос 3).**
- Могут ли в выписке за уже прошедший день появиться, измениться или исчезнуть
  операции (`actionType=update`/`delete` в вебхуках)? Если да, на какую глубину
  назад?
- Когда выписка и обороты за день становятся окончательными? В оборотах
  (`statement/summary`) нет признака окончательности, как в выписке 1С
  (`StatementType`).

**7. Подпись и шифрование JSON (вопрос 8).** Включены ли для партнёрской
интеграции транспортная подпись или шифрование сообщений при чтении выписки
(GET-запросы)? Или они нужны только для платёжных методов?

**8. Хранение данных (вопрос 6).** Есть ли требования банка к хранению
полученных данных, например запрет или обязательный срок хранения исходных
ответов API?

**9. Деактивация (п. 4.1.9 договора).** Применяется ли деактивация через три
месяца без успешных запросов к промышленной партнёрской интеграции, пока к ней
ещё не подключён ни один клиент?

**10. Тестовый доступ.**
- Просим пароль к архиву тестового TLS-сертификата `test_cert.zip`.
- Актуален ли сертификат проверки подписи токенов `/files/cer.crt`
  («certificate-prod»)?
- Как банк уведомляет о его замене?
