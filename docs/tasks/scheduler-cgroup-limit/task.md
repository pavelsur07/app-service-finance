# Задача: у контейнера `scheduler` нет cgroup-лимита памяти

## Источник

Пункт 4 из `docs/tasks/scheduler-memory-limit/task.md`, не закрытый той задачей.
Та задача починила путь `codex-console` (перевела ad-hoc команды в одноразовый
`site-php-cli` с лимитом 1536M, PR #2421/#2422). Ночной cron идёт **другим путём** и
остался как был.

Заведено по прямому запросу Владельца 2026-09-06.

## Подтверждено в коде и конфигурации

- **Секции `deploy:` у `scheduler` нет вовсе.** Блок в `docker-compose.prod.yml`
  заканчивается на `restart: unless-stopped`, дальше идёт top-level `volumes:`.
  Проверено построчно. Это единственный PHP-сервис в файле без лимита: у
  `site-php-fpm` — 800M, `site-php-cli` — 1536M, `-worker-sync` — 256M,
  `-pipeline` — 768M, `-wb-finance` — 256M, `-ads` — 256M.
- Контейнер поднимается из того же образа `ghcr.io/pavelsur07/site-php-cli`, но с
  `user: root` и `entrypoint: ["/usr/local/bin/supercronic"]` — штатный
  `entrypoint-cli.sh` (который переключает на пользователя `app`) обойдён,
  cron-команды выполняются от root.
- **34 активные строки** в `docker/cron/app.cron`, из них **4** с явным
  `-d memory_limit=1G`.

### Профиль одновременности

| Периодичность | Задачи |
|---|---|
| каждую минуту | `marketplace-ads:scheduler`, `marketplace-ads:poller`, второй `poller` со сдвигом `sleep 30`, `marketplace-ads:finalizer` — **4 процесса** |
| каждые 2 мин | `marketplace-ads:ozon-poll-reports` |
| каждые 5 мин | `app:storage:healthcheck` |
| каждые 10 мин | `app:ingestion:normalize-pending --limit=50` |
| каждые 30 мин | heartbeat `wget` |

На минуте `:00` каждого получаса совпадают все пять групп — до **8 процессов PHP
одновременно**, и это штатный фон, а не пик.

Ночное окно тяжёлых батчей (MSK): 02:30 `rolling-refresh --execute`, 03:00
`run-incremental`, 03:10/03:20 WB-отчёты, 04:00–04:45 четыре daily-sync и
`month-preliminary-rebuild`, **05:15 `daily-maintenance` (1G)**, 05:45
`reconcile-financial-projection` (1G), 06:30 `reconcile-financial-projection` (1G),
06:45 `verify-rolling-refresh` (1G), 07:25 `ozon-performance:daily-load --execute`.
Фон из 4–8 частых задач продолжает идти всё это время.

### Множитель, который легко упустить

`app:ingestion:ozon-accrual:daily-maintenance` — не один процесс.
`OzonAccrualCategoryMetadataBulkRunner::refreshRawRecordInSubprocess()` порождает
**подпроцессы**, и `-d memory_limit=1G` родителя на них не распространяется: подпроцесс
стартует как новый `php` и читает `php.ini` (1024M из
`docker/common/php/conf.d/memory-limit.ini`). То есть одна эта cron-строка может
занимать до ~2G: родитель плюс подпроцесс.

### Прочее из данных

- Хост — **2 CPU** (`runtime.NumCPU: 2`, `GOMAXPROCS: 2` в контексте события supercronic
  в GlitchTip). 8 одновременных PHP-процессов на 2 ядрах — отдельный источник
  растягивания задач по времени, а значит и наложения окон.
- Есть **месячная** задача: `0 6 5 * *` `ozon-realization-sync`. Полная картина пиков
  требует наблюдения не меньше месяца, а не одних суток.

## Чего в данных НЕТ — и это важно

**Вина `scheduler` в OOM не доказана.** GlitchTip issue 262
(`ProcessSignaledException: signal "9"`) — 11 событий, `firstSeen` 2026-07-03,
`lastSeen` 2026-09-05T11:17. Попытка атрибутировать их конкретному контейнеру
не удалась:

- Флаг `--quiet` **не различает пути**: cron-строка и ручной вызов через
  `codex-console` имели дословно одинаковые аргументы
  (`--days-back=45 --execute --no-interaction --quiet`). Изначально я счёл `--quiet`
  признаком cron — это неверно, проверено по транскрипту ручных запусков.
- `server_name` в событии — короткий id контейнера (`47be2f9d4bb1`), эфемерный; с тех
  пор было три деплоя, сопоставить не с чем.

Событий июля ручные прогоны объяснить не могут (тогда команду так не запускали), но это
рассуждение, а не доказательство.

**Полезное следствие уже сделанного изменения.** С 2026-09-06 `codex-console` выполняет
команды в отдельном контейнере с лимитом 1536M, то есть второй кандидат на источник
signal-9 из уравнения убран. Любое **новое** событие issue 262 после этой даты
однозначно принадлежит cron-пути. Это даёт чистую атрибуцию без дополнительных
инструментов — достаточно подождать и посмотреть.

## Ловушка мониторинга

supercronic схлопывает **все** отказы cron в один issue GlitchTip: issue 2
`error running command: exit status 1`, **553 события**. Различить задачи можно только
по `context.job.command` / `job.schedule` внутри события. Практическое следствие:
OOM-килл отдельной cron-команды не заводит отдельный issue и в списке не виден —
он растворяется в общем счётчике. Планировать проверку эффекта нужно с учётом этого.

Отдельно: `daily-maintenance` ловит падение подпроцесса и логирует `error` сам
(issue 262 и 252), поэтому именно её сбои видны отдельно. У остальных 33 строк такого
перехвата нет.

## Как получить недостающее число

Гадать не нужно — ядро хранит точную величину. Хост на cgroup v2 (`stat -fc %T
/sys/fs/cgroup` → `cgroup2fs`), и контейнер видит свой cgroup изнутри:

```bash
docker exec scheduler cat /sys/fs/cgroup/memory.peak     # high-water mark с момента старта, байт
docker exec scheduler cat /sys/fs/cgroup/memory.current  # текущее потребление
docker exec scheduler cat /sys/fs/cgroup/memory.max      # сейчас вернёт "max" = лимита нет
docker exec scheduler cat /sys/fs/cgroup/memory.events   # счётчики low/high/max/oom/oom_kill
```

`memory.peak` отвечает на вопрос размера одним чтением, без сэмплирования `docker stats`
— именно поэтому раньше сказать было нечего: я искал не тот инструмент.

**Условия замера:**

1. Считать **не раньше**, чем через сутки после деплоя: счётчик сбрасывается при
   пересоздании контейнера, а деплой его пересоздаёт. Последний деплой — 2026-09-06,
   `6826fdf6`.
2. Для полной картины — после 5-го числа, иначе месячный `ozon-realization-sync` в
   пик не попадёт.
3. Записать значение до любых изменений: после установки лимита восстановить его будет
   нечем (см. «Замеры "до" снимать до изменения» в `CLAUDE.md`).

**Ограничение доступа (снято 2026-09-06).** Существующие wrapper-ы (`codex-console`,
`codex-psql-ro`, `codex-docker-ps`) команды `docker exec ... cat` не дают, а
`codex-console` принимает только Symfony-команды из allowlist. Поэтому заведён
четвёртый read-only wrapper — `codex-cgroup`, референсная копия в
`docs/maintenance/codex-cgroup.sh`. Он читает cgroup **с хоста**, без `docker exec`,
и отдаёт `memory.max` / `memory.current` / `memory.peak` / `memory.events`.

После его установки Владельцем замер шага A выполняется так:

```bash
ssh -o BatchMode=yes vf-prod-codex "sudo /usr/local/bin/codex-cgroup scheduler" < /dev/null
```

До установки — Владельцем вручную через `docker exec`. Агент себе прав не расширяет:
и файл, и строку sudoers ставит Владелец.

## Варианты решения

**A. Сначала замерить `memory.peak`, потом ставить лимит от факта.** Чтение
безрисковое, ничего не меняет. Рекомендую как первый шаг — без него любое число
будет гаданием.

**B. Поставить заведомо щедрый лимит сразу (например 3G), не дожидаясь замера.**
Смысл не в экономии памяти, а в том, чтобы перевести отказ из host-wide OOM
(ядро выбирает жертву по своим правилам и может убить постороннний сервис) в
container-scoped: убит будет процесс внутри `scheduler`, остальные контейнеры целы.
Щедрый лимит почти не рискует убить легитимную задачу, а `memory.events` начнёт
считать `max`/`oom_kill` — появится сигнал, которого сейчас нет вовсе.

**C. Разделить `scheduler` на два контейнера** — частые лёгкие задачи и ночные тяжёлые
батчи, с разными лимитами. Устраняет корень: сейчас профиль одного контейнера обязан
одновременно вмещать 4-8 фоновых процессов и батч на 2G, из-за чего любой единый лимит
— компромисс. Но это структурное изменение: два crontab, два сервиса, изменение деплоя.

**D. Не делать ничего.** Допустимо, если после 2026-09-06 новых signal-9 не появится:
тогда единственный наблюдавшийся симптом принадлежал уже исправленному пути.

Рекомендация: **B+A** — щедрый лимит закрывает худший сценарий (посторонний сервис
убит из-за cron) немедленно и дёшево, замер уточняет число позже. **C** — кандидат в
follow-up, если замер покажет, что фон и батчи действительно не помещаются в один
разумный потолок. **D** рассматривать всерьёз только с наблюдением в пару недель.

## Риск

`docker-compose.prod.yml` — HIGH-LOCAL. Специфика именно этой правки:

- **Слишком тесный лимит опаснее отсутствующего.** Сейчас тяжёлая задача может
  доработать, заняв память хоста; с тесным лимитом она будет убиваться каждую ночь
  детерминированно, и — из-за схлопывания supercronic в issue 2 — тихо.
- Проверить лимит функциональными тестами нельзя: эффект виден только на проде под
  реальной ночной нагрузкой. Это Production Gate, а не Release Gate.
- Перезапуск `scheduler` обнуляет `memory.peak`. Если ставить лимит и замерять в один
  заход, замер «до» теряется — порядок шагов имеет значение.

## Что решить Владельцу

1. Вариант — A, B+A, C или D?
2. Если B: какое стартовое число? Из профиля выше нижняя граница правдоподобного пика —
   фон из 4–8 процессов плюс до ~2G от `daily-maintenance` с подпроцессом; 3G выглядит
   щедрым, но это оценка сверху по составу, а не замер.
3. Кто снимает `memory.peak` — Владелец вручную или заводим read-only wrapper?

## Решение (2026-09-06) — вариант B+A, лимит 3G

Владелец выбрал B+A и назначил стартовое число **3G**.

`docker-compose.prod.yml`, сервис `scheduler`:

```yaml
deploy:
    resources:
        limits:
            memory: 3G          # → 3221225472 байт, проверено `docker compose config`
        reservations:
            memory: 256M
```

Резервация добавлена для единообразия с остальными шестью PHP-сервисами (у всех она
есть) — это soft-limit, влияющий только на поведение под давлением памяти хоста.

Лимит применится при ближайшем деплое: шаг «[4/5] Обновляем воркеры и CLI» в
`.github/workflows/deploy.yml` перечисляет `scheduler` явно, поэтому контейнер
пересоздаётся.

### Шаг A — что и когда мерить

Замер «до» не снят и снять его было нечем: чтения `/sys/fs/cgroup/memory.peak`
существующие wrapper-ы не дают (проверено `sudo -n -l`: у `codex-prod` ровно три
wrapper-а, ни один не читает cgroup). Потеря невелика — контейнер пересоздавался
деплоем 2026-09-06 утром, то есть накопленный им пик не содержал ни одного ночного
цикла и как база сравнения был бесполезен.

**Лимит подтверждён на проде Владельцем 2026-09-06 после деплоя `805e9946`:**

```
docker exec scheduler cat /sys/fs/cgroup/memory.max     → 3221225472
docker exec scheduler cat /sys/fs/cgroup/memory.events  → low 0 / high 0 / max 0
                                                           oom 0 / oom_kill 0
```

Это и есть база для шага A: счётчики ведут отсчёт от пересоздания контейнера деплоем
`805e9946` (2026-09-06, около 13:00 MSK). Все нули означают, что за первые минуты
потолок не задевался — иного и не ожидалось, ценность появляется после ночного цикла.

После деплоя счётчики становятся осмысленными:

```bash
docker exec scheduler cat /sys/fs/cgroup/memory.peak    # пик с момента старта
docker exec scheduler cat /sys/fs/cgroup/memory.max     # должно стать 3221225472
docker exec scheduler cat /sys/fs/cgroup/memory.events  # max / oom / oom_kill
```

Читать:

1. **Через сутки** — попадёт полный ночной цикл 02:30–07:25.
2. **После 5-го числа** — попадёт месячный `ozon-realization-sync` (`0 6 5 * *`).
3. Не после деплоя: любой деплой пересоздаёт контейнер и обнуляет `memory.peak`.

### Как читать результат

| `memory.events` | Смысл |
|---|---|
| `max 0`, `oom_kill 0` | лимит ни разу не достигнут — можно тянуть вниз к `memory.peak` с запасом |
| `max > 0`, `oom_kill 0` | контейнер упирался в потолок, но выжил за счёт reclaim — 3G впритык, снижать нельзя |
| `oom_kill > 0` | процесс убит внутри контейнера. Хост при этом цел — ради этого лимит и ставился. Смотреть `context.job.command` в issue 2 GlitchTip, чтобы понять чей |

Переход к варианту C (разделение `scheduler` на контейнер частых задач и контейнер
ночных батчей) остаётся кандидатом на follow-up, если замер покажет, что фон и батчи не
помещаются под один разумный потолок.

## Коррекция плана шага A (2026-09-06): `memory.peak` на проде недоступен

Первый же запуск `codex-cgroup` на проде показал, что `memory.peak` пуст — и не только
у `scheduler`, а **у всех одиннадцати** контейнеров. Значит дело не в конфигурации, а в
ядре: `memory.peak` добавлен в cgroup v2 только в Linux 5.19.

Косвенное подтверждение из того же вывода: на проде `memory.events` содержит 5 полей
(`low/high/max/oom/oom_kill`), тогда как на машине агента — 7 (добавлены
`oom_group_kill`, появившийся в 5.17, и `sock_throttled`). То есть прод-ядро старше 5.17. **Подтверждено точно после переустановки wrapper'а:
`5.15.0-141-generic`** — вывод по числу полей оказался верным, но теперь это факт.

**Весь план шага A, построенный на «одном чтении `memory.peak` без сэмплирования»,
на этом ядре неисполним.** Формулировка «величина читается одним `cat`» была верна для
ядра машины агента и неверна для прода — проверять надо было там, а не экстраполировать.

### Что работает вместо этого

`memory.events` накапливается ядром сам, сэмплирования не требует и есть на любом
cgroup v2:

| Счётчик | Что означает |
|---|---|
| `max` | сколько раз cgroup упирался в `memory.max` |
| `oom` / `oom_kill` | сколько раз сработал OOM и сколько процессов убито |

Для вопроса «достаточно ли 3G» этого хватает: `max 0` после ночного цикла означает, что
потолок не задевался ни разу.

### Как теперь тянуть лимит вниз

High-water mark из ядра недоступен, поэтому вместо «замерить пик и поставить пик плюс
запас» — храповик:

1. Прожить ночной цикл, снять `memory.events`.
2. `max 0` → снизить лимит шагом (3G → 2G → 1.5G), каждый раз проживая полный цикл.
3. Первое появление `max > 0` означает, что предыдущий шаг был минимально достаточным;
   вернуться на него.
4. `oom_kill > 0` на любом шаге — откат немедленно, шаг был слишком мал.

Каждый шаг — деплой, а деплой пересоздаёт контейнер и обнуляет счётчики; это не помеха,
наоборот: каждый шаг измеряется с чистого листа.

Медленнее, чем один замер пика, но не требует того, чего на этом ядре нет.

### Точная версия ядра

`5.15.0-141-generic` — обновлённый `codex-cgroup` печатает `uname -r` в шапке.

### Как убедиться, что замер вообще годен

Счётчики `memory.events` обнуляются при пересоздании контейнера, то есть при каждом
деплое. Поэтому перед тем как трактовать `max 0` как «потолок не задет», надо
убедиться, что контейнер прожил всё окно 02:30–07:25 непрерывно:

```bash
ssh -o BatchMode=yes vf-prod-codex "sudo /usr/local/bin/codex-docker-ps" < /dev/null
```

Смотреть колонку `STATUS` у `scheduler`: аптайм обязан покрывать ночное окно целиком.
Если контейнер моложе — был деплой, счётчики обнулены, и `max 0` не значит ничего,
кроме «с момента рестарта не задевали». Замер переносится на следующие сутки.

Без этой проверки забытый ночной деплой даёт ложный зелёный: показания выглядят
благополучно именно потому, что мерить было нечего.

### База отсчёта: снимок после деплоя `805e9946` (2026-09-06)

Счётчики обнулены пересозданием контейнеров, `oom_kill` везде 0. **Снимок сделан
днём 2026-09-06; в тот же день ожидались деплои до 18:00–19:00 MSK, поэтому он
устарел как точка сравнения** — актуальной базой становится состояние после
последнего деплоя дня. Ценность снимка в другом: он фиксирует, какие лимиты
сконфигурированы и что до ночного цикла `oom_kill` был нулевым везде.

```
CONTAINER                         LIMIT  CURRENT  OOM_KILL
land-nginx                        —      3M       0
scheduler                         3072M  12M      0
site-messenger-worker-ads         256M   19M      0
site-messenger-worker-pipeline    768M   19M      0
site-messenger-worker-sync        256M   19M      0
site-messenger-worker-wb-finance  256M   19M      0
site-nginx                        —      3M       0
site-php-fpm                      800M   15M      0
site-redis                        —      7M       0
symfony-postgres                  —      2084M    0
traefik                           —      65M      0
```

`CURRENT` воркеров сравнивать между замерами бессмысленно: они перезапускаются
ежечасно по `--time-limit=3600`, и значение зависит от момента снятия.

Побочное наблюдение, не входящее в эту задачу: `symfony-postgres` работает без
cgroup-лимита и держит 2084M (аптайм 4 месяца). Для СУБД отсутствие лимита часто
осознанный выбор — ограничивать её так же, как приложение, нельзя, — но зафиксировать
стоит: это второй контейнер, чей OOM ударил бы по хосту целиком.

## Шаг A выполнен (2026-09-07): 3G не задет ни разу

### Годность замера проверена до трактовки

`codex-docker-ps`: `scheduler` — `Up 13 hours` при деплое `7b4328cc` около 19:00
2026-09-06. Ночное окно 02:30–07:25 целиком внутри непрерывного аптайма, счётчики
за него не обнулялись. Замер годен.

### Решение: 3G оставить, храповик не запускать

Формально `max 0` разрешает снижать. Делать этого не нужно, и вот почему.

3G выбирались не как «пик плюс запас», а как оценка сверху по составу: до ~2G способна
занять одна `daily-maintenance` (родитель с `-d memory_limit=1G` плюс порождённый ею
подпроцесс, читающий `php.ini` — те же 1024M), плюс фон. Следующий шаг храповика — 2G —
поставил бы лимит **ровно на известный легитимный worst case**, то есть туда, где он
начнёт убивать не аварию, а штатную работу.

Смысл лимита здесь — ограничить радиус поражения, а не экономить память. 3G ≈ 1.5× от
worst case: авария будет поймана, штатная работа — нет. Минимизировать это число ценности
не имеет: незанятая память не расходуется, а `memory.current` в 43M показывает, что
контейнер и близко не подходит к потолку в обычном режиме.

Храповик остаётся описанным выше на случай, если появятся основания — например если
состав расписания изменится или `max` станет ненулевым.

**Задача закрыта.** Остаётся вариант C (разделение `scheduler` на контейнер частых задач
и контейнер ночных батчей) — но он про изоляцию, а не про память, и оснований для него
замер не дал.
