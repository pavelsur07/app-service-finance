# Поставки Ozon в пути в отчёте остатков

Статус: **закрыта** 13.11.2026 (PR #2976, #2979), итог — раздел 7. План — 12.11.2026. Повод — пункт 4 аналитика (DIHOOKL1, Сухоносов): остаток FBO 1–3 шт с
08.11, а есть ли поставка в пути, по данным сервиса не ответить.

## 1. Какую задачу решаем

Отчёт «Остатки» (`/inventory/stocks`) по Ozon показывает одну цифру на товар — «доступно на FBO» из
`/v4/product/info/stocks`. Товара, который едет на склады Ozon по заявке на поставку, в нём нет.
Поэтому «остаток 1 шт» нельзя отличить от «остаток 1 шт, но завтра приедет 500».

Данные уже есть: `ozon-fetcher` каждый день в 05:00 снимает `ozon.supplies` — активные заявки на
поставку FBO с составом по SKU (`/v3/supply-order/list|get`, `/v1/supply-order/bundle`), у всех 4
кабинетов `done` (витрина покрытия, 12.11). Но приложение сырьё сервиса не читает: канала «сервис →
Symfony» для данных ещё нет (есть только `/internal/coverage`), а содержимое бакета
`vashfindir-services-raw` Symfony не видит.

## 2. Что будет результатом

1. **`ozon-fetcher` отдаёт последний снимок ресурса**: `GET /internal/snapshots/latest?connection_ref=…&resource_type=ozon.supplies`
   — страницы последней `done`-ревизии задачи (тела JSON по порядку, `period_key`, `revision`,
   время загрузки). Авторизация — тот же `SERVICE_API_TOKEN`, что у `/internal/coverage`.
   Разрешённые ресурсы — белый список (сейчас только `ozon.supplies`). Контракт —
   `services/_contracts/service-snapshot/v1` (pull, без ack: снимок «на сейчас», повторное чтение безопасно).
2. **Symfony забирает снимок** командой `app:inventory:ozon-supplies-sync` (cron 05:40, после снимка
   05:00; `OZON_FETCHER_BASE_URL/_API_TOKEN` уже есть в scheduler) по каждому активному кабинету Ozon
   с ключом seller. Сохраняет через существующий конвейер Inventory: сессия → `InventoryRawSnapshot`
   (страницы как есть) → нормализация. Новый нормализатор `OzonSupplyOrdersRawNormalizer`:
   строка остатков на (SKU, заявка) со статусом `in_supply` (новый `StockStatus::InSupply`, «В поставке»),
   `fulfillment_type = fbo`, локация — склад хранения заявки (`inventory_locations`,
   тип `mp_acceptance`, `external_id` = id склада Ozon). Миграции нет: `status` — строка.
3. **Отчёт «Остатки» по Ozon** получает колонку «В поставке» рядом с FBO/FBS. Сейчас разбивка Ozon в
   `InventoryStockReportQuery` — по `fulfillment_type` без фильтра статуса, поэтому `in_supply`
   выводится отдельной колонкой и исключается из колонок FBO/FBS и из «доступно»; иначе поставка
   сложилась бы с остатком FBO. Оборачиваемость и юнит-экономика читают остаток через
   `InventoryFacade` → `StockQtyByListingOnDateQuery` с `status = available` и не меняются.

## Решение Владельца 12.11.2026 — канал «последний снимок»

Владелец согласился с предложением. Как понято и как исполняется:

1. **Направление.** Приложение (Symfony) само запрашивает у сервиса данные, сервис ничего в
   приложение не шлёт. Это продолжение pull-модели (решение 13.10).
2. **Что отдаётся.** Последний полностью загруженный снимок ресурса кабинета — страницы ответа Ozon
   как есть. Сервис ничего не разбирает и не пересчитывает; разбор — в приложении.
3. **Для каких данных.** Только снимки «на сейчас» (поставки, позже остатки по складам, акции,
   кластеры): их можно перечитывать сколько угодно, поэтому подтверждения получения нет.
   Финансовые данные и заказы этим каналом **не** идут — для них остаётся `source-fact-envelope`
   с подтверждением, отдельной задачей.
4. **Доступ.** Тот же внутренний адрес и токен `SERVICE_API_TOKEN`, что у карты покрытия; только
   внутри серверной сети. Отдаются только ресурсы из белого списка сервиса — сейчас `ozon.supplies`.
   Новый ресурс — правкой списка и версии контракта.
5. **Не делаем.** Приложение не читает хранилище сервиса (S3) напрямую и не обращается к Ozon
   Seller API само — весь Seller API остаётся в `ozon-fetcher` (решение 21.10).
6. **Отказ канала** (сервис недоступен, снимка нет) — предупреждение в логе и пропуск дня, не ошибка
   и не подмена данными; отчёт показывает прошлый снимок с его датой.

## 3. Решения по умолчанию (меняются ответом Владельца)

| Вопрос | Решение | Почему |
|---|---|---|
| Какие статусы заявки считать «в поставке» | все активные, кроме `DATA_FILLING` (черновик) | черновик — не отгружено и может не поехать |
| Канал данных | выдача последнего снимка сервисом, а не чтение S3 из Symfony и не прямой вызов Ozon из Symfony | весь Seller API — в `ozon-fetcher` (решение 21.10); раскладка ключей S3 — внутреннее дело сервиса; pull-модель (решение 13.10) |
| Нормализация | в Symfony, сервис отдаёт сырые страницы | сервис — «только загрузка» (решение 17.10), как у остальных ресурсов |
| Остатки по складам/кластерам (`ozon.stocks.warehouses`) | **не в этой задаче** | на вопрос «есть ли товар» отвечают поставки; разбивка по складам — когда понадобится, тем же каналом |
| Снимок устарел (нет `done` за сегодня) | берётся последний `done`, дата снимка — его `period_key`; старше 2 дней — WARNING и пропуск | без тихой подмены вчерашним «сегодняшнего» |
