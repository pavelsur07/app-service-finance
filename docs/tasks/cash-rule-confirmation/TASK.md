# Автоправила ДДС для всех компаний

**Запуск сразу для всех компаний. Финансист один раз подтверждает правило после предпросмотра.** Затем оно автоматически обрабатывает подходящие операции. Для изменения действующего правила подтверждается новая версия. Уже активные правила продолжают работать. Поиск закономерностей по истории доступен всем компаниям, а поиск фраз через ИИ учитывает действующий доступ и бюджет компании.

## Этапы реализации

| Этап | Что делаем | Что принимает пользователь |
|---|---|---|
| **1. Предпросмотр и подтверждение** | Расширяем существующий механизм проверки. На одних и тех же операциях сравниваем два результата: с текущими правилами и с предложенным изменением. При редактировании подставляем новую версию вместо старой. Используем тот же алгоритм выбора правил, что и фоновый обработчик. | В форме видны операции, которые впервые получат статью, смена победившего правила по каждому полю, появившиеся и устранённые конфликты. У каждого счётчика есть примеры. «Проверить» только показывает результат. «Подтвердить и включить» активирует именно проверенную версию. |
| **2. Исключения в назначении платежа** | К условию «содержит» добавляем «не содержит» и «точно равно». Для новых операторов используем действующую обработку регистра и букв «е/ё». Пустое назначение не удовлетворяет текстовому условию. | Можно задать «списание этому контрагенту, назначение содержит “по договору аренды” и не содержит “обеспечительный платеж”» и увидеть примеры обоих случаев до включения. |
| **3. Предложения правил по истории** | В существующем разделе «Кандидаты» добавляем переход от найденной закономерности к предзаполненному черновику с точными условиями. Для компаний с доступом к ИИ добавляем поиск устойчивых фраз в назначениях одного контрагента. Модель предлагает фразу, Symfony проверяет её на истории компании и показывает совпадения, включая случаи, где человек выбрал другую статью. | Финансист видит, на каких платежах основано предложение, может уточнить условие и пройти общий предпросмотр. Например, для одного поставщика можно разделить платежи за лицензии и за внедрение. При выключенном ИИ или исчерпанном бюджете обычные кандидаты остаются доступны. |
| **4. Статистика качества** | В списке правил показываем за выбранный период, скольким операциям правило назначило статью, в скольких из них человек затем изменил её и по скольким возник конфликт по статье. Назначения и исправления связываем с версией правила по аудиту. Для конфликтов сохраняем факт срабатывания с момента выпуска. | По каждому числу можно открыть операции для разбора. Повторная обработка одной операции не увеличивает счётчик той же версии. Для периода до начала учёта конфликтов интерфейс показывает дату начала наблюдения. |

## Как работает подтверждение

- Черновик — содержимое формы. Пока финансист проверяет новую редакцию, фоновый обработчик использует последнюю утверждённую версию. Изменение условий, приоритета или назначаемых полей требует нового предпросмотра.
- Сервер связывает подтверждение с компанией, пользователем, содержимым формы и версиями участвующих правил. Если другой сотрудник успел изменить правило или набор активных правил, форма предлагает пересчитать результат. Повторный клик не создаёт второе правило.
- Предпросмотр моделирует действующий безопасный режим. Отдельно показывает **какое правило победило** и **какое значение действительно изменится**. При уже заполненной вручную статье эти ответы могут различаться. Закрытые периоды и операции с ручной разбивкой видны среди пропущенных с указанием причины.
- Включение правила само по себе не запускает обработку истории. Для пересчёта за прошлый период остаётся существующее отдельное действие с подтверждением. Просмотр и подтверждение ограничены правами сотрудника в активной компании.

## Технические границы

Используем существующие формы Symfony/Twig, механизм выбора правил и журнал аудита. Для предпросмотра добавляем внутреннее действие формы без записи финансовых данных. Для ИИ вводим одну версионированную задачу через `ServiceGateway`: на входе обезличенные примеры компании, на выходе предложенные текстовые условия либо ответ «недостаточно данных». Запрос запускается из экрана кандидатов. Финансовые данные изменяет только существующий механизм применения утверждённых правил.

## Проверка и выпуск

- **Начинаем с тестов.** Фиксируем текущее поведение адресными тестами Cash. Первый новый тест воспроизводит ключевой случай: выключенное правило в предпросмотре должно показать собственный вклад, а данные операции и состояние правила должны остаться прежними.
- **Проверяем путь целиком.** Создание, изменение и повторное включение правила, два сотрудника одновременно, повторное подтверждение, конфликт только по одному полю, исключение в тексте, закрытый период, ручная разбивка и попытка открыть данные другой компании. На одинаковых исходных данных результат предпросмотра должен совпасть с результатом рабочего обработчика.
- **Проверяем ИИ и статистику.** Для фраз — минимум 20 обезличенных тестовых случаев, включая переменные номера счетов, схожие назначения с разными статьями и недостаточную историю. Для статистики — ручное исправление, повтор фоновой задачи и смена версии правила.
- **Выпускаем одним PR после проектных проверок и ревью.** При выпуске учитываем миграцию для истории конфликтов. Базовые функции становятся доступны всем компаниям одновременно. После деплоя проверяем доступность форм, работу существующих правил и отсутствие массового пересчёта. Эффект оцениваем по двум показателям вместе: доле разнесённых правилами операций и доле назначений, которые финансист впоследствии исправил.
