# ozon-fetcher-ingestion: загрузка raw финансовых данных Ozon по всем активным кабинетам

План по этапам для `services/ozon-fetcher`. Правила: `services/AGENTS.md`,
`services/go.md`, `services/ozon-fetcher/AGENTS.md`, workflow — корневой
`AGENTS.md` (§5 этапы, §7 ревью).

## Цель программы

Сервис сам, по расписанию:

1. получает активные Ozon-кабинеты и ключи из Symfony;
2. выгружает финансовые отчёты Ozon по нескольким кабинетам **параллельно**,
   с **собственными лимитами каждого кабинета**;
3. кладёт ответы API как есть в S3 (immutable);
4. ведёт в своей БД журнал загрузок: что, за какой период, когда, хеши,
   размеры, статус, класс ошибки, попытки;
5. сам дозагружает пропуски и поздние правки Ozon.

## Как читать этапы

- **Цель** — зачем этап. **Результат** — что появится. **Выполнено, когда** —
  проверяемый критерий приёмки. **Чек-лист** — отмечается по ходу.
- **Внешнее ревью** (Codex, `site/bin/external-review.sh`, `AGENTS.md` §7.2):
  **да** — на этапах с авторизацией, конкурентностью, миграцией, целостностью
  данных; **нет** — остальное, их diff смотрит внешнее ревью на handoff PR.
  Внутреннее ревью полного diff — на каждом этапе.
- Каждый этап — отдельный локальный коммит; push и PR — по группам (таблица в
  конце). Прод — только этап 14, после отдельного одобрения.

## Справка: архитектура

```
Symfony GET /internal/marketplace-connections
        │  poll 5m, кэш в памяти, при недоступности — последний кэш
        ▼
Планировщики (первичная / хвост / дозагрузка / справочники) ──upsert──► fetch_task
                                                                         │ захват с lease
                                                                         ▼
                        Диспетчер: ≤ MAX_PARALLEL_CONNECTIONS кабинетов, честная очередь
                      ┌───────────────┬───────────────┐
                      ▼               ▼               ▼
                  кабинет A        кабинет B       кабинет C      ← задачи кабинета по очереди
                  лимитер(A,ep)    лимитер(B,ep)   лимитер(C,ep)  ← свой лимит + адаптация на 429
                      └───────────────┴───────────────┘
                                      ▼
                    Ozon API → S3 PUT (страница) → commit журнала и курсора в БД
```

**Таблицы БД сервиса** (без сумм, ПДн, ключей):

| Таблица | Что хранит | Ключ |
|---|---|---|
| `fetch_task` | что должно быть загружено: статус, попытки, `next_retry_at`, `priority`, lease, курсор, `content_hash`, `revision` | `(connection_ref, resource_type, period_key)` |
| `fetch_attempt` | журнал попыток: время, страницы, байты, HTTP-коды, `error_class` | `attempt_id` |
| `raw_object` | объект S3 на страницу: `storage_uri`, sha256, размер | `(attempt_id, page_no)` |
| `connection_limit` | лимит кабинета по endpoint'у: ручной, текущий адаптированный, пауза | `(connection_ref, endpoint)` |

`period_key`: `YYYY-MM-DD` (дневные), `YYYY-MM` (месячные), `ref` (справочники).

**Ресурсы первой волны:**

| `resource_type` | Endpoint | Период |
|---|---|---|
| `ozon.finance.accrual-by-day` | `POST /v1/finance/accrual/by-day` | день, пагинация `last_id` |
| `ozon.finance.accrual-types` | `POST /v1/finance/accrual/types` | справочник, раз в сутки |
| `ozon.finance.realization` | `POST /v2/finance/realization` | месяц, после закрытия |
| `ozon.finance.mutual-settlement` | `POST /v1/finance/mutual-settlement` → `/v1/report/info` → файл | месяц, асинхронный отчёт (XLSX); форма не подтверждена на проде |

Детали запросов, классы ответов и дефолтные лимиты — `services/ozon-fetcher/docs/ozon-api.md`.

**Окна загрузки** (Europe/Moscow):

| Период | Что делаем | Частота | Приоритет |
|---|---|---|---|
| Первичная (новый кабинет) | текущий месяц с 1-го числа по вчера; затем сама подтягивается дозагрузка M-1, M-2 (итого ≈90 дней, `services/AGENTS.md` §3) | один раз | высокий для M, низкий для M-1/M-2 |
| Текущий месяц | вчера + 3 предыдущих дня (конфиг) | ежедневно | средний |
| Пропуски в M, M-1, M-2 | день без успешной загрузки или с ошибкой | проверка ежедневно | низкий |
| M-1 целиком | полная перезагрузка, смена хеша = новая ревизия | раз в неделю | низкий |
| M-2 целиком | финальная перезагрузка, после неё период для автоматики «заморожен» | раз в месяц, 10-го числа | низкий |
| Старше M-2 | автоматически не трогаем; только ручной запрос (позже — UI) | — | — |
| Месячные отчёты | с 1-го числа ежедневно до первого успешного ответа; «отчёт не готов» — исход `not_ready`, не ошибка | ежедневно | средний |
| Справочник типов начислений | полная загрузка | раз в сутки | средний |

Смена хеша — ревизия + INFO-событие с числом изменённых дней (сигнал для
будущей сверки, не ошибка). Дозагрузка не вытесняет хвост и первичную
загрузку; лимит кабинета общий для всех режимов.

**Классы ошибок:**

| Класс | Пример | Действие | Затрагивает |
|---|---|---|---|
| `rate_limit` | 429 | снизить скорость кабинета, пауза | кабинет + endpoint |
| `transient` | 5xx, таймаут | повтор с backoff, затем отложить | задачу |
| `auth` | 401/403 | обновить ключ, 1 повтор, затем пауза кабинета | кабинет |
| `invalid_response` | битый ответ, повтор курсора | ошибка задачи + error-лог | задачу |
| `invalid_request` | прочий 4xx | ошибка задачи + error-лог | задачу |
| `not_ready` | отчёт ещё не сформирован | повтор по расписанию, не ошибка | задачу |
| `obsolete_endpoint` | 400 `code 9` | стоп ресурса у всех кабинетов + error-лог | ресурс |

**Границы:** сервис не пишет в БД Symfony и не нормализует; ключи — только в
памяти; raw в S3 не перезаписывается; `EARLIEST_SAFE_DAY` — ограничение
импорта в Symfony, не загрузки.

### Этап 5. Лимитер кабинета

- **Цель:** каждый кабинет работает в своём лимите и не мешает остальным.
- **Результат:** реестр лимитеров по `(connection_ref, endpoint)`; скорость =
  `min(ручная ?? дефолт, адаптированная)`; на 429 — снижение вдвое и пауза,
  после серии успехов — плавный рост до потолка.
- **Выполнено, когда:** тесты доказывают, что 429 у кабинета A не меняет
  скорость B; снижение и рост упираются в пол и потолок; ожидание прерывается
  отменой контекста; `-race` чистый.
- **Чек-лист:**
  - [ ] дефолты по endpoint'ам из конфига (значения из этапа 0)
  - [ ] ручное значение по кабинету (интерфейс; хранение — этап 7)
  - [ ] адаптация на 429 с учётом `Retry-After`
  - [ ] интерфейс сохранения адаптированной скорости (реализация — этап 7)
  - [ ] тесты изоляции кабинетов, пол/потолок, отмена, `-race`
- **Внешнее ревью:** **да** — конкурентность.

### Этап 8. Запись raw в S3

- **Чек-лист:**
  - [ ] MinIO в dev-compose
  - [ ] запрет перезаписи (`If-None-Match: *` или проверка существования — что поддерживает Timeweb, сверить)
  - [ ] env `S3_*`, README
  - [ ] тесты, гейты сервиса
- **Внешнее ревью:** нет.

### Этап 9. Выполнение одной задачи

- **Цель:** одна задача (кабинет + ресурс + период) выполняется до конца без потерь и дублей при любом сбое.
- **Результат:** исполнитель: страница → S3 → commit; продолжение с курсора;
  итоговый хеш и ревизия; ошибки по классам → статусы, пауза кабинета, стоп ресурса.
- **Выполнено, когда:** тесты: сбой посреди пагинации → продолжение без
  дублей; 401 → пауза только этого кабинета; `obsolete_endpoint` → стоп
  ресурса; повтор без изменений → нет новой ревизии и объектов.
- **Чек-лист:**
  - [ ] порядок «S3 → БД» соблюдён
  - [ ] курсор сохраняется после каждой страницы
  - [ ] `content_hash` и `revision`
  - [ ] переходы статусов по всем 7 классам
  - [ ] graceful shutdown: страница дописывается, lease снимается
  - [ ] тесты сценариев сбоя
- **Внешнее ревью:** **да** — целостность данных.

### Этап 10. Параллельная обработка кабинетов

- **Цель:** несколько кабинетов грузятся одновременно, честно и в пределах ресурсов сервиса.
- **Результат:** диспетчер: до `MAX_PARALLEL_CONNECTIONS` кабинетов, очередь
  `priority DESC` → дольше всех не обслуживавшийся кабинет, задача
  отпускается после каждого периода, lease продлевается.
- **Выполнено, когда:** тест: 3 кабинета параллельно, у одного 429 и 401 —
  остальные завершаются; длинная первичная загрузка не блокирует хвост
  других; два экземпляра сервиса на одной БД не берут один кабинет; `-race` чистый.
- **Чек-лист:**
  - [ ] `MAX_PARALLEL_CONNECTIONS` в конфиге
  - [ ] пул БД под N, соединение не держится во время HTTP
  - [ ] честная очередь

### Этап 14. Секреты и вывод на прод — отдельная ветка

Решение Владельца 2026-10-17: секреты и деплой не решены и делаются
**отдельной веткой** `infra/ozon-fetcher-deploy`, своим PR, после приёмки на
стенде. Изменения прода, CI/CD и секреты — HIGH-EXTERNAL (§3.3 корневого
`AGENTS.md`): только после именованного одобрения.

- **Цель:** сервис работает на проде, сначала на одном кабинете, затем на всех.
- **Результат:** секреты заведены, сервис в `docker-compose.prod.yml` во
  внутренней сети, образ и гейты в CI, миграции — явный шаг деплоя.

**Секреты** (по образцу существующих: GitHub secrets → `export` в SSH-шаге
`deploy.yml` → подстановка в `docker-compose.prod.yml`; в репозитории — только имена):

| Секрет | Кто создаёт | Где используется |
|---|---|---|
| `INTERNAL_AUTH_TOKEN` (≥ 32 символов, случайный) | агент генерирует, Владелец кладёт в GitHub secrets | Symfony (`x-php-env`) и ozon-fetcher — одно значение |
| `INTERNAL_ALLOWED_IPS` (CIDR docker-сети прода) | агент определяет по `docker network inspect`, read-only | Symfony |
| `OZON_FETCHER_DB_PASSWORD` | агент генерирует; роль создаёт Владелец/root | DSN роли `svc_ozon_fetcher` |
| `OZON_FETCHER_S3_ACCESS_KEY_ID`, `OZON_FETCHER_S3_SECRET_ACCESS_KEY` | Владелец: доп. пользователь Timeweb только на бакет `vashfindir-services-raw` | ozon-fetcher |

Ротация `INTERNAL_AUTH_TOKEN` — обе стороны одним деплоем; утечка — смена
секрета и деплой. Ключи кабинетов в секреты не попадают: их отдаёт Symfony.

**Деплой:**
- CI: job гейтов сервиса (vet, lint, `-race`), сборка образа
  `ghcr.io/pavelsur07/ozon-fetcher:<sha>` (`services/ozon-fetcher/docker/Dockerfile`).
- `docker-compose.prod.yml`: сервис `ozon-fetcher` только в сети `default`
  (без traefik-лейблов), `restart: always`, лимит памяти, healthcheck `/health`;
  `SYMFONY_INTERNAL_BASE_URL=http://site-nginx`.
- Миграции — явный шаг деплоя `ozon-fetcher -migrate` до `up`.
- Разовая подготовка (Владелец/root, скрипт в `docs/maintenance/`): БД
  `ozon_fetcher` и роль `svc_ozon_fetcher` на общем инстансе PostgreSQL.
- **Поэтапное включение:** env `CONNECTION_ALLOWLIST` (новое, в этой ветке) —
  сначала только кабинет «Вумджой», затем все; лимит by-day для первого
  кабинета снижен вручную (`connection_limit`), чтобы не мешать прод-синку
  Symfony с теми же ключами.
- Откат: остановить сервис; путь загрузки Symfony не меняется.

- **Выполнено, когда:** после одобрения Владельца сервис на проде загрузил
  первичное окно «Вумджой», ошибки — 0 или объяснены, прод-синк Symfony без
  новых 429; затем — все кабинеты.
- **Чек-лист:**
  - [ ] одобрение Владельца на секреты, CI и прод получено
  - [ ] секреты заведены (таблица выше), в репозитории — только имена
  - [ ] Timeweb S3: пользователь только на бакет; `If-None-Match` проверен
  - [ ] БД и роль созданы, `sslmode=require`, миграции явным шагом
  - [ ] сервис без ingress; `/internal/*` Symfony открыт только для docker-сети
  - [ ] `CONNECTION_ALLOWLIST`: «Вумджой» → все кабинеты
  - [ ] приёмка: статус по кабинетам, GlitchTip без новых ошибок, 429 у прод-синка не выросли
- **Внешнее ревью:** да — на PR ветки.
