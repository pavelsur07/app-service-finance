#### Цель
Несколько кабинетов загружаются одновременно, честно и в пределах ресурсов
сервиса; остановка сервиса не оставляет задач в `running`.

#### Результат
Пакет `internal/dispatcher`, `Dispatcher.Run(ctx)`:
- до `MAX_PARALLEL_CONNECTIONS` одновременных задач (по одной на кабинет —
  гарантия БД из этапа 7); слот освобождается после каждой задачи
- захват — `ClaimNext` по `connection_ref` активного снимка; пока снимка нет
  (`Ready() = false`) — ожидание, не ошибка
- нет готовых задач — пауза `IdlePoll` или до освобождения слота
- фоновый `ReleaseExpired` раз в `ReleaseEvery`
- `attempt_id` — UUID v4 из `crypto/rand`; `lease_owner` — `hostname:pid`;
  `trace_id` на задачу
- graceful shutdown: новые задачи не берутся, текущие доводятся исполнителем
  до `released`, `Run` возвращается после всех воркеров
- пул БД — `max(5, N + 3)` соединений (`store.Open` получает размер)

#### Решения
- Честность и «один кабинет — один воркер» обеспечивает SQL `ClaimNext`
  (этап 7); диспетчер только ограничивает число одновременных задач.
- Ошибка БД при захвате — warning и пауза, не остановка сервиса.
- Кабинет исчез из снимка между захватом и запуском — исполнитель получает
  пустой кабинет и откладывает задачу (`no_credentials`).
