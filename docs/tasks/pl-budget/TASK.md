# Модуль планирования ОПиУ (бюджет)

Обсуждение с Владельцем 04.11.2026. Правила планирования —
`docs/plan/planning-rules-pnl-cashflow.md`. Цель MVP — не усложнять.

## Как сейчас

- Дерево статей ОПиУ — `Finance\Entity\PLCategory`: типы `LEAF_INPUT` /
  `SUBTOTAL` / `KPI`, признак расхода `VARIABLE` / `OPEX` / `OTHER`,
  `weightInParent`.
- Проекты — дерево `Company\Entity\ProjectDirection`; ЦФО —
  `FinancialResponsibilityCenter`; допустимые пары «проект × ЦФО»,
  по умолчанию `PROJECT_GENERAL × CFO_GENERAL`.
- Факт ОПиУ — `pl_daily_totals`: статья × день × проект × ЦФО
  (`NULL` ЦФО — легаси «Не задано»).
- Плана ОПиУ нет. Модуля плана продаж нет.

## Принципы

1. **План в том же разрезе, что и факт, только по месяцам:**
   вариант × статья × месяц × проект × ЦФО → сумма. План–факт почти даром.
2. **Планируются только листовые статьи** (`LEAF_INPUT`). Итоги и KPI
   считаются по дереву тем же кодом, что и для факта.
3. **Варианты плана.** Несколько вариантов на год (Базовый, Оптимистичный…),
   статусы черновик / утверждён / архив. Утверждённый на год — ровно один
   (частичный unique в БД). Новый вариант — копией или пустой.
4. **Проекты и ЦФО** — только допустимые пары. Компания без разрезов
   работает в паре по умолчанию и разрезов не видит. Родительский проект
   в отчёте суммирует поддерево. Ввод — по одной выбранной паре; режим
   «все проекты» только показывает сумму.
5. **Расшифровки статьи («из чего состоит») в MVP нет.** Ячейка — одна сумма
   и необязательный комментарий («2 менеджера × 80 + РОП 120»). Строки
   расшифровки — после MVP; если они есть, сумма статьи считается из них.
6. **Источник строки плана:** `manual` | `sales_plan`. В MVP только `manual`;
   поле закладывается сразу. Загрузка из плана продаж — **снимком**, не живой
   ссылкой: утверждённый бюджет сам не меняется, при обновлении плана продаж —
   подсказка «загрузить заново»; перезагрузка трогает только строки
   `sales_plan`. Контракт: Facade модуля продаж отдаёт суммы «месяц × статья
   ОПиУ × проект × ЦФО» (выручка и, если умеет, себестоимость, комиссии,
   логистика); бюджет ничего не знает про товары.
7. **Помощники заполнения пишут только суммы:** из факта прошлого года / из
   среднего за N месяцев, распределить годовую сумму поровну, копировать
   месяц вправо, разово «X% от выручки». Живое правило «% от выручки» — после
   MVP.

## Модель (черновик, уточняется в этапе 0)

Новый модуль `Budget` (`docs/workflow/new-module.md`); ссылки на статью,
проект и ЦФО — строковыми ID без внешних ключей (удаление статьи в Finance не
должно падать на плане; строки удалённой статьи в отчёт не попадают),
справочники и факт — через Facade `Finance` и `Company`. Собственный Facade
модуля появится, когда план понадобится другому модулю (связка с ДДС).

| Entity | Таблица | Поля |
|---|---|---|
| `BudgetVersion` | `budget_versions` | `id` (UUIDv7), `companyId`, `year`, `name`, `status` (`draft` / `approved` / `archived`), `copiedFromId`, `createdAt`; частичный unique `(company_id, year) WHERE status = 'approved'` |
| `BudgetLine` | `budget_lines` | `id`, `companyId`, `versionId`, `plCategoryId`, `month` (дата 1-го числа), `projectDirectionId`, `responsibilityCenterId`, `amount` (`NUMERIC(18,2)`, строка, как `pl_daily_totals`), `source` (`manual` / `sales_plan`), `comment`, `updatedAt`; unique `(version_id, pl_category_id, month, project_direction_id, responsibility_center_id)` |

Сумма хранится в знаке значения отчёта ОПиУ (доход − расход: расходная
статья — отрицательная), как `PLDailyTotalFactsProvider`. Нулевая ячейка без
комментария — строки нет.

## Этапы MVP

Каждый этап начинается с файла `stages/stage-N.md` (задача, результат, что
считаем выполненным, чек-лист приёмки); итог дописывается туда же.

### Этап 0. Модель и операции без UI

- **Задача:** хранить варианты и строки плана, держать инварианты в БД.
- **Результат:** модуль `Budget`, 2 Entity + Builders, миграция, Actions:
  создать вариант (пустой / копией), утвердить, вернуть в черновик,
  архивировать, сохранить пачку ячеек (upsert, идемпотентно); в
  `PLCategoryDTO` — тип статьи; раздел в `ARCHITECTURE.md`.
- **Выполнено, когда:** гейты зелёные, миграция в синхроне со схемой, тесты
  на все Actions.
- **Чек-лист приёмки:**
  - [ ] второй утверждённый вариант на тот же год отклоняется БД и Action;
  - [ ] копия переносит все строки, исходник не меняется;
  - [ ] сохранение не-листовой статьи, чужой статьи, недопустимой пары
        «проект × ЦФО» — отказ;
  - [ ] повторное сохранение той же пачки → то же число строк;
  - [ ] все запросы с `companyId` (IDOR), тест на чужую компанию.

### Этап 1. Варианты и ввод плана

- **Задача:** пользователь создаёт вариант и заполняет его.
- **Результат:** страница списка вариантов (создать, копировать, утвердить,
  архив); экран ввода: дерево статей × 12 месяцев + «Итого», фильтр «проект /
  ЦФО», редактируются только листовые статьи, итоги и KPI пересчитываются,
  комментарий к ячейке; пункт меню. Вёрстка по DS «Ваш Финдир».
- **Выполнено, когда:** сценарий «создал → заполнил → утвердил» проходит
  руками на стенде, functional-тесты контроллеров.
- **Чек-лист приёмки:**
  - [ ] компания без проектов/ЦФО видит таблицу без фильтров разреза;
  - [ ] итог родительской статьи = сумма детей с учётом `weightInParent`;
  - [ ] утверждённый вариант помечен и редактируется по правилам этапа 0;
  - [ ] двойной клик «Сохранить» не плодит строк;
  - [ ] скриншоты до/после.

### Этап 2. План–факт

- **Задача:** сравнить утверждённый план с фактом.
- **Результат:** отчёт статьи × месяцы: План / Факт / Отклонение / %;
  фильтры вариант, проект (с поддеревом), ЦФО; факт из `pl_daily_totals`
  через Facade `Finance`, суммы по месяцам.
- **Выполнено, когда:** цифры факта совпадают с действующим отчётом ОПиУ за
  тот же период и фильтр.
- **Чек-лист приёмки:**
  - [ ] сверка факта с предпросмотром ОПиУ на реальной компании, расхождение 0;
  - [ ] «Не задано» ЦФО попадает в итог без фильтра и выпадает при выборе ЦФО;
  - [ ] нет N+1, отчёт за год одной выборкой факта.

### Этап 3. Помощники заполнения

- **Задача:** заполнить бюджет за минуты, а не за час.
- **Результат:** «Из факта прошлого года», «Среднее за N месяцев»,
  «Распределить годовую сумму», «Копировать месяц вправо», разово «X% от
  выручки» для переменных статей. Пишут суммы в выбранную пару через Action
  сохранения пачки.
- **Выполнено, когда:** каждый помощник покрыт тестом и не трогает строки
  вне выбранного диапазона.
- **Чек-лист приёмки:**
  - [ ] «Из факта» даёт те же суммы, что отчёт ОПиУ прошлого года;
  - [ ] помощник перезаписывает только выбранные статьи/месяцы, с
        подтверждением при наличии сумм;
  - [ ] строки `sales_plan` помощники не трогают.

## После MVP (не планируем сейчас)

- Строки расшифровки статьи (название + суммы / количество × цена).
- Живое правило «% от выручки» для переменных статей.
- Загрузка выручки из модуля плана продаж (источник `sales_plan`, снимок).
- Сравнение двух вариантов, импорт/экспорт Excel.
- Связка с планом ДДС (сдвиг строк на задержку денег).
- История изменений и согласование.

## Решения Владельца (04.11.2026)

1. Год — календарный.
2. Утверждает вариант только владелец компании; он же возвращает
   утверждённый вариант в черновик.
3. Утверждённый вариант не редактируется — только через «вернуть в
   черновик» (принято предложение).
4. «Без проекта» в бюджете не планируется — всегда есть пара «проект × ЦФО»,
   хотя бы по умолчанию.
