# Удаление шести флагов завершённого поэтапного включения

Дата: 15 ноября 2026. Статус: планирование; реализация и production-изменения
не запрошены. Основание — аудит GitHub Actions и запрос Владельца подготовить
план удаления шести переменных. Проверенная база:
`a2032eb82cd6e47aaad67199954bbace48afdb86` (`master`).

## Цель и границы

Убрать зависимость работающих функций от шести GitHub Actions Variables:

```text
AI_SERVICE_ENABLED
OZON_FETCHER_ENABLED
WB_FETCHER_ENABLED
SOURCE_FACTS_COMPANIES
TELEGRAM_PAYMENT_INTAKE_ENABLED
TELEGRAM_PAYMENT_INTAKE_COMPANIES
```

В GitHub первые три флага включены, `SOURCE_FACTS_COMPANIES=*`, Telegram-флаг
включён, его список содержит один кабинет. Значения и идентификаторы кабинетов
в документы не копируются.

Целевое поведение:

- Ozon/WB/ИИ и business/payment-intake workers постоянно входят в production
  deployment; запуск, миграции сервисов и проверки обязательных секретов
  больше не зависят от трёх `*_ENABLED` и Telegram pilot scope.
- SourceFacts принимает факты всех действительных подключений — как сейчас
  при `*`. Проверки принадлежности подключения, контракта, карантин,
  идемпотентность, commit-before-ack и health-check сохраняются.
- Новые ИИ-разборы Telegram доступны кабинетам, подключённым администратором
  через существующий `ai_company_access`. Выдача доступа в админке сама по себе
  открывает новый разбор; повторный deploy для нового кабинета не нужен.
- Отсутствие URL или токена ИИ оставляет `isServiceEnabled()` ложным. Наличие
  настройки подключения не заменяет доступность сервиса: сетевые сбои по-прежнему
  обрабатываются существующим клиентом и health-check.
- Платформенный кабинет сохраняет существующее исключение из выдачи ИИ-доступа
  администратором. Новых записей доступа и автоматического подключения всех
  кабинетов к платному ИИ нет.
- Без ИИ-доступа новое сообщение для ранее не выбранного PaymentIntake binding
  сохраняет существующий legacy-маршрут. У уже выбранного binding или известного
  source не происходит возврата в legacy и повторного создания платежа.
- Старый черновик можно вручную уточнить и подтвердить после отзыва ИИ-доступа,
  если сохранены actor/binding/financial write права. Это уже закреплено тестом
  `testManualFieldReplyWorksWithoutAiGrantAndDoesNotRequestNewParse`.
  Новый разбор, retry и изменение исходного текста с повторным разбором после
  отзыва доступа не запускают модель. Платёж создаётся только явным Confirm.
- Автовосстановление охватывает подключённые к ИИ кабинеты и незавершённую
  доставку уже существующих Telegram-черновиков; не теряет уведомления при
  отзыве ИИ-доступа, не создаёт платежей и не обходит финансовые права.

## Подход

Выбран для плана: удалить ветвления и зависимости целиком; сохранить существующие
проверки админского доступа и стандартный deployment pipeline. Нового реестра
флагов, таблицы настроек или отдельного переключателя Telegram не добавлять.

Рассмотренные альтернативы: оставить шесть констант `true`/`*` — сохраняет мёртвую
конфигурацию; перенести шесть флагов в админку — добавляет второй источник доступа
и ненужный UI. Ни одна не решает задачу удаления зависимостей.

## Исключено

`AI_SERVICE_EVAL_ENABLED`, бюджет 30 ₽/ночь и 900 ₽/месяц, модели/промпты/эталоны,
`ECONOMICS_WEEKLY_REPORT_COMPANIES`, остальные Variables и все Secrets остаются.
Dev-профиль `services` сохраняется. Публичные HTTP-контракты, финансовые формулы,
данные, записи доступа и маршрутизация Messenger не меняются. Миграций БД и новых
зависимостей не ожидается. Архивные отчёты задач не переписываются.

## Выпуск и разрешения

Сам этот документ разрешает только подготовку плана. Реализация затрагивает
CI/CD, production Compose/профили и scheduler: перед соответствующими изменениями
нужно проверить именованное разрешение на этот scope по `AGENTS.md` §3.3.
Обычное разрешение на merge/deploy само по себе не разрешает удаление Variables.

На implementation handoff представить единый запрос с отдельно перечисленными
действиями: merge/deploy, предусмотренные изменения запуска/cron и удаление
ровно шести GitHub Variables **после** успешного deploy и приёмки. До этого
Variables сохраняются для старого кода и отката. Ни один ручной backfill,
production recovery, consume или live-запрос не входит в этот план выпуска.

## Критерий готовности

Без всех шести переменных работа и deployment проходят тесты; новый кабинет
подключается к ИИ через админку; старые черновики и права сохранены; SourceFacts
не ограничен списком; nightly по-прежнему управляется своим флагом. После
согласованного выпуска GitHub содержит две оставшиеся из исходных восьми
Variables; остальные настройки, включая добавленные параллельно, не удалены.
