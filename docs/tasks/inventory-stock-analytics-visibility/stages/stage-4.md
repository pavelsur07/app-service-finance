# Stage 4 — Разовая пере-нормализация исторических снапшотов

`owner_gate: yes` · `release_candidate: no` · `independently_deployable: no`
Риск: 🟠 HIGH-LOCAL — команда меняет исторические данные остатков на проде.

- `stage_base_commit`: `a1a46e57`
- Ветка: `feat/inventory-stock-freshness`

## Зачем

Маппинг «строка остатка → листинг» замораживается в момент нормализации: ключ upsert
включает `snapshot_date`, но не сессию. Листинг, появившийся в каталоге позже,
вчерашние строки уже не чинит — они остаются `unmapped` навсегда. Аналитика
Маркетплейса строится именно на `listing_id`, поэтому такие строки для неё не существуют.

## Дефект подтверждён в данных до написания кода

| Факт | Значение (PROD, 2026-09-06) |
|---|---|
| Непривязанных строк Ozon | **6687** за 114 дней, с 2026-05-11 по 2026-09-01 |
| Непривязанных строк WB | 111 за 37 дней |
| Диапазон 25.08–01.09 (запрошенный «конец августа») | **40 сессий, 701 строка из 7461** |
| Из непривязанных Ozon-SKU конца августа листинг существует сейчас | **76 из 76 — 100%** |
| Raw-снимки за 25.08–02.09 | все на месте, 4 Ozon + 3 WB в день |

Последняя строка решающая: пере-нормализация починит **каждую** непривязанную строку,
а не часть. Если бы листингов не появилось, чинить было бы нечего.

## Что сделано

| Файл | Роль |
|---|---|
| `Infrastructure/Query/SessionsToRenormalizeQuery.php` | Находит сессии, у которых остались непривязанные строки |
| `Command/RenormalizeInventorySnapshotsCommand.php` | `app:inventory:renormalize-snapshots` |

Команда не загружает данные заново: она переиспользует уже сохранённый
`InventoryRawSnapshot` и прогоняет по нему тот же нормализатор. Внешние API не
вызываются, количества берутся из того же ответа маркетплейса — меняются только поля
маппинга.

```
app:inventory:renormalize-snapshots --from=YYYY-MM-DD --to=YYYY-MM-DD
                                    [--source=ozon|wildberries] [--company=UUID] [--execute]
```

Без `--execute` — только подсчёт, ничего не меняется.

## Две защиты от порчи данных

**Только последняя сессия дня.** На проде есть два дня, где у пары «компания +
источник» две сессии: `2026-05-11` (ozon) и `2026-07-13` (wildberries). Ключ upsert
сессию не содержит, поэтому пере-нормализация старой сессии затёрла бы строки,
записанные новой. Запрос берёт последнюю тем же правилом, что и отчётный запрос
остатков: `snapshot_at DESC, snapshot_session_id DESC`.

**Диапазон строго в прошлом.** `--to` обязан быть раньше сегодняшнего дня. Новая
сессия всегда пишется текущей датой, поэтому для прошедших дней набор сессий
зафиксирован и после выборки не меняется.

## Внешнее ревью

Codex, два круга.

**Круг 1 — IMPORTANT, принята.** Гонка между выборкой и асинхронной обработкой:
правило «только последняя сессия дня» проверялось в момент `SELECT`, а применялось в
момент upsert, и между ними ничего его не держало. Пока сообщение ждёт в очереди,
более новая сессия того же дня могла бы быть нормализована раньше, и отложенная
обработка старой затёрла бы её данные.

Закрыто **без правки горячего upsert**, который лежит на ежедневном пути:
нормализация выполняется синхронно в самой команде (окна между выборкой и upsert
больше нет), а диапазон ограничен прошедшими днями (новых сессий для них не появится).

**Круг 1 — три MINOR, все приняты.** `IS DISTINCT FROM 'mapped'` вместо `<>` (страховка
на случай `NULL`); тест tie-break по `snapshot_session_id` при равном `snapshot_at`;
поведение повторного запуска задокументировано.

**Круг 2 — `REVIEW_GREEN`**, одна MINOR: тесты не доказывали отсутствие мутации в
dry-run. Добавлен `testDryRunLeavesRowsUntouched` — состояние строк сверяется до и
после запуска. Доказательство фактической нормализации оставлено там, где оно уже
есть: `NormalizeInventorySnapshotActionTest` проверяет сам нормализатор, а тесты
команды — выбор целей и режимы запуска.

Первая попытка ревью прошла впустую: новые файлы не отслеживались Git, и в промпт
попал пустой дифф. Ревьюер это заметил и отказался давать вердикт; вызов повторён с
`git add -N`. Пустой дифф зелёным ревью не считается.

## Доказательность тестов

`testEqualSnapshotAtIsResolvedByGreaterSessionId` прогнан красным: при развороте
направления сортировки на `ASC` команда выбирает другую сессию и тест падает.

## Не сделано намеренно

Команда **не ставится в cron** — она разовая. Запуск на проде требует отдельного
одобрения Владельца и добавления в allowlist wrapper'а `codex-console`, что делает
только Владелец.
