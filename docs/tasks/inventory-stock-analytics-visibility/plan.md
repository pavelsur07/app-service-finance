# Остатки в аналитике Маркетплейса: видимость, свежесть, отсутствие данных

## Context

Загрузка остатков с маркетплейсов работает исправно: за 31.08–06.09.2026 все 49 сессий
`completed`, все raw обработаны, 0 ошибок API, обрезки пагинации нет, нормализация сходится
построчно. Связь `stock → listing` тоже здорова — 99.7% строк смаплены, не смаплены 3.

Проблема не в загрузке и не в маппинге, а в том, **как аналитика Маркетплейса потребляет
остатки**. Три независимых дефекта на стороне потребления:

1. **Остатки не создают строк отчёта.** `UnitExtendedQuery` склеивает `$allListingIds` из
   продаж, возвратов и расходов. Остатки не источник — их только подмешивают в готовые строки.
   Листинг с товаром на складе, но без движения за период, в юнит-экономику не попадает вовсе.
   Это ровно тот залежавшийся товар, ради которого остатки и грузят.
2. **Отсутствие данных неотличимо от нуля.** `UnitExtendedQuery:118` —
   `$stockQty = (float) ($stockQtyByListing[$listingId] ?? 0.0)`, далее
   `stockCapitalRub = stockQty * costPriceUnit`. Не загрузилось, не смаппилось, позиция пришла
   с пустым `stocks` — везде выходит уверенный «остаток 0» и «капитал 0».
3. **У запроса остатков нет нижней границы свежести.** `StockQtyByListingOnDateQuery` берёт
   последнюю сессию с `snapshot_date <= :reportDate` без ограничения снизу.

### Замеры на PROD (2026-09-06, read-only)

> **Поправка по итогам Stage 2:** цифра 246 завышена — в измерявшем её запросе в
> `DISTINCT` попала колонка `quantity`, из-за чего листинг считался повторно на
> каждое различное значение остатка. Корректный пересчёт с границей свежести из
> Stage 1 даёт **177** новых строк; разбивка — в `stages/stage-2.md`.

Дефект 3 уже стреляет, а не гипотетичен. Компания `5d26f9aa`: последний снапшот
**2026-05-23, 106 дней назад**, активного подключения нет — запрос по сей день отдаёт её
34 листинга как остаток на дату отчёта. Мёртвый пайплайн выглядит как здоровые данные.

## Решения, принятые до начала

| Вопрос | Решение | Обоснование |
|---|---|---|
| Порог свежести | **2 суток** | Загрузка ежедневная (04:05 Ozon, 04:15 WB). Двое суток переживают один пропущенный прогон без ложной тревоги |
| Какие листинги мёржить как источник строк | Только с **`quantity > 0`** в выбранной сессии | Строка «остаток 0, продаж нет» — чистый шум. Позиция, ушедшая в ноль и продававшаяся в периоде, уже попадёт в отчёт через продажи |
| Как показывать неизвестное | `null` в контракте и API, «—» в таблице, пустая ячейка в XLSX, **в суммы не входит** | Ноль в денежной колонке — утверждение о факте. Прочерк — отсутствие утверждения |
| Порядок этапов | Свежесть → видимость → «нет данных» | Мёржить как источник строк можно только уже отфильтрованные по свежести данные, иначе Stage 2 затащит в отчёт 106-дневные остатки |
| Охват гейта свежести | Только компании с **активным** подключением нужного маркетплейса | Правило `CLAUDE.md` «охват проверки = охват починки»: у `5d26f9aa` подключения нет, чинить нечем, и вечно красный гейт обесценит канал |

### Требуют подтверждения Владельца до старта Stage 3

Stage 3 меняет видимый отчёт и контракт API. Позиции для подтверждения — порог свежести
(2 суток), поведение сумм в `TagSummaryTable` при неизвестных значениях, и допустимость
`null` в поле `stockQty` для внешних потребителей API, если они есть за пределами репозитория.

## Stage 1 — Свежесть остатков

`owner_gate: no` · `release_candidate: no` · `independently_deployable: yes`
Риск: 🟠 HIGH-LOCAL — меняет денежную величину, показанную в отчёте.

### Цель

`StockQtyByListingOnDateQuery` перестаёт отдавать протухший снапшот как остаток на дату отчёта.

### Work items

**1.1. Ограничение свежести в запросе.**
Добавить в `StockQtyByListingOnDateQuery::execute()` параметр максимального возраста снапшота
и нижнюю границу в CTE `latest_sessions`. Сессия старше порога не выбирается вовсе — компания
получает пустой набор, а не устаревшие числа. Параметр — константа класса со значением из
решения выше, не «магическое число» внутри SQL.

**1.2. Контракт фасада.**
`InventoryFacade::getStockQtyByListingOnReportDate()` возвращает не голую карту, а
`final readonly class` DTO в `Inventory/Application/DTO/` — карта `listingId => qty` плюс
`snapshotDateBySource` и признак, что данных нет по причине устаревания. `Application/DTO`
публичен как часть контракта Facade (`CLAUDE.md`, раздел Facade), новых нарушений границ
не вносит. Обновить докблок фасада: правило выбора снапшота теперь включает верхнюю границу
возраста.

**1.3. Адаптация потребителя без смены видимого поведения.**
`UnitExtendedQuery` читает новый DTO, но продолжает подставлять `0.0` при отсутствии значения.
Визуально отчёт после Stage 1 меняется ровно в одном месте: у компании с протухшим снапшотом
остаток становится `0` вместо 106-дневного числа. Замена нуля на прочерк — это Stage 3.

**1.4. Гейт свежести остатков.**
Read-only консольная команда: для каждой компании с **активным** подключением маркетплейса
проверить наличие сессии `completed` за окно порога. Ненулевой exit code — только по свежести,
не по накопленному счётчику исторических дыр. Уровень лога — `error` лишь на недостижимое
состояние, иначе `warning` (`CLAUDE.md`, «Health-гейты» и «error vs warning»). Предикат
«снапшот протух» определить **в одном месте** и переиспользовать в запросе и в гейте.
В cron на этом Stage не ставить — сначала прогон вручную и подтверждение, что гейт достижимо
зелёный.

### Definition of Done

- **Наблюдаемое поведение:** снапшот старше порога не участвует в расчёте; `5d26f9aa` перестаёт
  отдавать остатки от 2026-05-23; свежие компании не затронуты.
- **Тесты:** регрессионный тест на устаревший снапшот, **прогнанный на старом коде и красный**
  (`CLAUDE.md`: «регрессионный тест доказывается красным»); unit-тест границы порога — ровно
  на пороге и на секунду за ним; тест, что компания со свежими данными не изменилась.
- **Проверки:** `make site-cs-check --using-cache=no`, `site-cs-strict-types`, `site-stan`,
  все пять перечисленных в baseline тестовых файлов зелёные.
- **Документация:** `ARCHITECTURE.md` — новый DTO и изменённая сигнатура метода Facade.
- **Наблюдаемость:** гейт прогнан вручную, зафиксировано, что он зелёный на текущих данных.
- **Совместимость:** сигнатура `InventoryFacade` меняется; единственный внешний потребитель —
  `MarketplaceAnalytics`, обновляется в этом же Stage.
- **Вне Stage:** прочерки вместо нулей, мёрж остатков в источники строк, постановка гейта в cron.

## Stage 2 — Остатки как источник строк отчёта

`owner_gate: yes` · `release_candidate: yes` · `independently_deployable: no` (зависит от Stage 1)
Риск: 🟠 HIGH-LOCAL — меняет состав строк и знаменатели агрегатов.

### Цель

Листинг с ненулевым остатком попадает в юнит-экономику, даже если за период не было ни продаж,
ни возвратов, ни расходов.

### Work items

**2.1. Остатки — четвёртый источник `allListingIds`.**
В `UnitExtendedQuery` добавить в merge идентификаторы листингов с `quantity > 0`. Рядом лежит
осознанное решение **не** мёржить листинги из рекламы — «the row would be empty otherwise».
Оставить его нетронутым и дописать комментарий, почему для остатков вывод обратный: строка не
пустая, в ней остаток и капитал в остатках. Порядок операций сохранить: мёрж до фильтра по
тегам, чтобы `totals` считались по уже отфильтрованному набору, как сейчас.

**2.2. Метаданные для новых строк.**
Листинги из остатков не имеют продаж, поэтому попадают в `$nonSalesIds` и метаданные тянутся
через `getListingsMetaByIds`. Проверить, что batch не растёт до N+1 и что листинг без метаданных
не роняет цикл.

**2.3. Проверка агрегатов.**
Убедиться, что 246 новых строк с нулевой выручкой не сдвигают `revenue`, `quantity`, `profit`,
и явно проверить величины, где новые строки попадают в знаменатель.

### Definition of Done

- **Наблюдаемое поведение:** листинг с остатком и без движения даёт строку с заполненными
  «Ост. шт.» и «Остаток на МП» и нулями в денежных колонках движения; на PROD-профиле это
  порядка 246 новых строк.
- **Тесты:** unit-тест — листинг только с остатком даёт строку; unit-тест — листинг с нулевым
  остатком и без движения строки **не** даёт; тест на неизменность `totals` по выручке и
  количеству при добавлении stock-only листингов; тест совместимости с фильтром по тегам.
- **Проверки:** полный набор из baseline + три интеграционных теста `UnitExtended*`.
- **Документация:** комментарий в коде о причине асимметрии с рекламой; запись в Stage Report
  о фактическом приросте строк.
- **Совместимость:** форма ответа API не меняется, меняется только число элементов.
- **Вне Stage:** прочерки вместо нулей, изменения фронтенда.
- **Owner gate:** отчёт видимо меняется — на границе Stage запросить решение Владельца до
  перевода PR в Ready.

## Stage 3 — Явное «нет данных» вместо нуля

`owner_gate: yes` · `release_candidate: yes` · `independently_deployable: no` (зависит от Stage 1–2)
Риск: 🟠 HIGH-LOCAL — сквозное изменение контракта: PHP → JSON API → XLSX → React.
Фронтенд-часть выполняется по `CLAUDE.frontend.md`.

### Цель

Неизвестный остаток отображается как неизвестный, а не как ноль.

### Work items

**3.1. Бэкенд-контракт.**
Убрать `?? 0.0` в `UnitExtendedQuery:118`. `stockQty` и `stockCapitalRub` становятся nullable;
`stockCapitalRub` не вычисляется, когда `stockQty` неизвестен. Прокинуть в ответ дату снапшота
из DTO Stage 1, чтобы отчёт мог подписать, на какой момент показаны остатки.

**3.2. XLSX-экспорт.**
`UnitExtendedXlsxExporter` — колонка `stockQty` объявлена как `'type' => 'number'`. Обработать
`null`: пустая ячейка, не `0`. Проверить, что тип колонки не ломает формат листа.

**3.3. React.**
`unitExtended.types.ts` — `stockQty: number | null`, `stockCapitalRub: number | null`.
`UnitExtendedTable.tsx:493` вызывает `row.stockQty.toLocaleString(...)` — **на `null` это падение
в рантайме**, обязателен рендер «—». То же для `formatMoney(row.stockCapitalRub)` в
`UnitExtendedTable.tsx:494` и `TagSummaryTable.tsx:77`.

**3.4. Суммы при неизвестных значениях.**
`TagSummaryTable` агрегирует `stockCapitalRub`. Неизвестные в сумму не включать и пометить
сумму как частичную — иначе частичный результат читается как полный
(`CLAUDE.md`, «инструмент, который сэмплирует, обязан печатать своё покрытие»).

### Definition of Done

- **Наблюдаемое поведение:** там, где остаток неизвестен, в таблице «—», в XLSX пустая ячейка,
  в JSON `null`; в шапке отчёта видна дата снапшота; известный ноль по-прежнему показывается нулём.
- **Тесты:** unit-тест «неизвестно ≠ 0» на уровне запроса; тест экспортера на `null`;
  фронтенд-тест рендера `null` в обеих таблицах; тест частичной суммы в `TagSummaryTable`.
- **Проверки:** полный backend-набор + сборка и линт фронтенда по `CLAUDE.frontend.md`.
- **Документация:** `ARCHITECTURE.md`, докблок Facade, описание поля в типах фронтенда.
- **Совместимость:** ломающее изменение поля `stockQty` для потребителей API — подтвердить
  с Владельцем, что внешних потребителей за пределами репозитория нет.
- **Вне Stage:** авто-создание листингов из остатков, backfill исторического `listing_id`.

## Вне scope всей задачи

- **Связь `listing → product`.** Владелец зафиксировал: отчётность на ней не строится.
  Каталог на PROD пуст (2 товара, 0 баркодов, 0 импортов) — отдельное решение, не эта задача.
- **Авто-создание листинга из остатков** и **backfill исторического `listing_id`**. Маппинг
  замерзает в момент нормализации: ключ upsert включает `snapshot_date`, поэтому появившийся
  позже листинг вчерашние строки не чинит. Подтверждено данными: Ozon 30.08–01.09 остался
  unmapped после того, как листинги подтянулись 02.09. Требует отдельного плана из четырёх
  шагов, а не работы внутри этого.
- **Три строки WB `unmapped`** (`chrtId 461725762`, карточка ушла из каталога, товар в пути).
- **Позиции Ozon с пустым `stocks`** (232 из 372 у `78f0cc9f`) — они не дают строк вовсе.
  После Stage 3 они станут неотличимы от «нет данных», что честнее нынешнего нуля, но
  собственного решения «показывать как 0» эта задача не принимает.
- **Постановка гейта свежести в cron** — после подтверждения, что он достижимо зелёный.
