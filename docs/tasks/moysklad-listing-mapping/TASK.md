# Маппинг листингов маркетплейсов на номенклатуру МойСклад

## Основание и результат

План и ревью подготовлены и приняты в PR #3015. После его слияния владелец
поручил автономно выполнить все четыре Stage. Текущая задача — реализация
утверждённого маппинга с тестами, миграцией и двумя легаси-вкладками.
Merge, production-миграция и deploy запрашиваются отдельно на handoff.

Будущая функция: пользователь выбирает подключение МойСклад и связывает
существующий листинг маркетплейса с импортированным товаром либо конкретной
модификацией этого подключения. Связь подтверждается вручную, её изменения
сохраняются в истории. Пользователь видит неразрешённые и недоступные связи.

Уточнение владельца: две отдельные вкладки «Маппинг Ozon» и «Маппинг
Wildberries» в легаси-части модуля МойСклад, с существующими легаси-стилями.
Реализация UI — Twig/Tabler в site/templates/moy_sklad, без SPA/React.

## Границы

- Marketplace владеет листингами и их идентификаторами.
- MoySklad владеет импортированной номенклатурой, связями и историей связей.
- Межмодульное чтение — только через существующий MarketplaceFacade и DTO.
- Существующий MarketplaceListing.product относится к внутреннему Catalog;
  его не переиспользовать, не изменять и не использовать как признак маппинга МС.
- Отчёт комиссионера, продажи/возвраты, FIFO, ОПиУ, Inventory, остатки,
  автосоздание товаров, комплекты, коэффициенты упаковок и HTTP-запись в МС
  в эту реализацию не входят.

## Предлагаемые правила первой версии

Это проектные решения для реализации, а не утверждение о текущем поведении:

1. Ключ связи — companyId + moySkladConnectionId + marketplaceListingId.
   В Marketplace у листинга сейчас нет seller connectionId: не выдумывать его.
2. Один листинг имеет одну текущую цель на подключение; несколько листингов
   могут указывать на одну цель. Разные подключения имеют независимый маппинг.
3. Цель — внешний UUID и тип product/variant. Нельзя выбирать родительский
   товар с модификациями вместо конкретной модификации.
4. Артикул — подсказка, а не идентификатор. Автоматического сохранения нет;
   даже единственный кандидат требует подтверждения. Размеры и характеристики
   показываются рядом, но не интерпретируются автоматически.
5. Архивная номенклатура и архивный родитель варианта не выбираются заново;
   существующая связь сохраняется и помечается недоступной.
6. Неактивный листинг можно сопоставлять вручную для исторических операций.
   Его состояние видно пользователю; автоматическое включение запрещено.
7. Новое назначение и замена разрешены у активного подключения с привязанным
   accountId после хотя бы одного успешного полного прохода product и variant.
   Последняя транспортная ошибка не отменяет ранее загруженный каталог.
   Снятие связи разрешено и у выключенного подключения; история доступна на чтение.
8. История фиксирует время изменения в системе, не дату продажи. Задним
   числом связи не назначаются. Будущий отчёт должен сохранять ID ревизии
   и снимок цели; разрешение маппинга для старых операций проектируется отдельно.

## Приёмка будущей функции

- [x] Связь создаётся, заменяется и снимается; история не теряется.
- [x] WB с одним nm_id и двумя размерами сопоставляется двумя listingId.
- [x] Два листинга могут указывать на одну цель; разные подключения независимы.
- [x] Чужая компания/подключение/номенклатура недоступны на чтение и запись.
- [x] Нет побочных изменений Catalog, финансовых данных, остатков или листинга.
- [x] Архивирование не удаляет связь и не подменяет внешний UUID.
- [x] Две открытые формы не перезаписывают друг друга молча.
- [x] Повтор принятого запроса не создаёт повторную ревизию.
- [x] Каталог и листинги читаются страницами, без N+1 и загрузки всех ID.
- [x] Права чтения/записи, CSRF, ошибочные UUID и состояния UI покрыты.
- [x] Две легаси-вкладки показывают только свой маркетплейс; подмена UUID
  листинга другого маркетплейса не позволяет выполнить назначение/снятие.
