# Единый план статей ДДС группы — основа консолидированной отчётности

Поручено Владельцем 17.11.2026: у всех компаний должна быть одинаковая
структура ДДС для MVP «Консолидированная отчётность». Решение того же дня:
эталон — дерево статей ДДС ООО «Максимедиа» + ядро `core.yaml`. Все 9 статей
Максимедиа покрыты ядром, и её дерево заменяется ядром (этап 0a), поэтому
эталон — `core.yaml`.

## Как сейчас

- `CashflowCategory` (`cashflow_categories`) принадлежит одной компании.
  Стабильный код есть только у 7 системных групп (`system_code`: `CF_OP`,
  `CF_FIN`, `CF_INV`, `CF_TECH*`, `CF_UNALLOC`), unique
  `(company_id, system_code)`.
- Ядро `site/config/cash/cashflow_templates/core.yaml` (v1: 7 групп и 30 статей)
  ставит `ApplyCashflowCoreTemplateAction`, но только новой компании без
  несистемных статей. Кодов у статей нет.
- На проде 21 компания, 378 обычных статей, у каждой компании своё дерево.
  Ссылаются на статью: `CashTransaction`, `CashTransactionSplit`, `PaymentPlan`,
  `CashTransactionAutoRule`, ИИ-категоризация.
- Понятия «группа компаний» нет. У `Company` есть `inn`, у `Counterparty` тоже есть `inn`.

Сводить по названиям нельзя: после переименования консолидация молча
разъедется.

## Решение — план статей группы и привязка к нему

Так делают в МСФО-консолидации: group chart of accounts плюс привязка
local → group.

1. **Эталон** — `core.yaml` v2: каждый узел получает `code` (стабильный, латиница,
   например `OP_IN_CUSTOMERS`). Содержание — объединение дерева Максимедиа и
   ядра (этап 0), его утверждает Владелец. Один файл служит и онбордингу, и группе:
   новая компания сразу получает статьи с кодами.
2. **`cashflow_categories.group_code`** — `varchar(64) NULL`, unique
   `(company_id, group_code)` (NULL не уникален — статьи без кода
   допустимы). Код ставит только шаблон или привязка, руками в форме не
   редактируется.
3. **Своя детализация разрешена.** Под статьёй с кодом компания заводит свои
   подстатьи. В консолидации они сворачиваются к ближайшему предку с кодом.
4. **Защита.** Статью с кодом нельзя удалить и нельзя перенести под предка с
   другим кодом. Переименовывать можно: в консолидации название берётся из эталона.
5. **Синхронизация «эталон → компания»** — одна Action для команды и экрана.
   План: привязать по коду → привязать по похожему названию в той же ветке →
   создать недостающую → конфликт (показать, не трогать). Ничего не удаляет и
   не переименовывает. Сначала dry-run. Повтор под `pg_advisory_xact_lock`
   компании, журнал применений. Образец — `ApplyDefaultPLTemplateAction`,
   `PLCategoryNameSimilarity`, `pl_template_applications`.
6. **Консолидированный ДДС** — `SUM … GROUP BY group_code` по выбранным
   компаниям, в которых пользователь участник. Компании проверяются по членству
   (IDOR), а не по id из запроса. Операции на статьях без кода попадают в строку
   «Не сопоставлено» и не теряются.
7. **Внутригрупповые обороты.** Операция, у которой ИНН контрагента совпадает с
   ИНН другой выбранной компании, считается внутригрупповой: показываем её
   отдельной колонкой и исключаем из итога.

Связь ДДС → ОПиУ (`plCategory`) не синхронизируется: у каждой компании своя,
решение #2934.

## Не делаем в MVP

- Сущность «Группа/холдинг» и права на группу: группа = выбранные компании, в
  которых пользователь участник. Вводим, когда понадобятся права или хранимый состав группы.
- Синхронизацию удалений и переименований эталона в компании.
- Консолидацию ОПиУ и Баланса — отдельная задача на том же принципе.
- Пересчёт валют: в MVP только RUB, остальные валюты — отдельной строкой.

## Этапы

| # | Этап | Результат | Миграция |
|---|---|---|---|
| 0a | Ядро для существующей компании | `app:cash:cashflow-core:apply`, первой — Максимедиа (`stages/stage-0a-core-for-existing.md`) | — |
| 0 | Эталон | `chart.md`: дерево с кодами (Максимедиа + `core.yaml`), таблица «откуда узел»; утверждает Владелец | — |
| 1 | Коды в модели | `core.yaml` v2 с `code`, `group_code` + unique, онбординг ставит коды, защита удаления и переноса | да |
| 2 | Синхронизация | `SyncCashflowGroupChartAction`, команда `app:cash:group-chart:sync <companyId> [--execute]`, журнал `cashflow_group_chart_applications`, проверка в `app:directories:integrity-check` | да |
| 3 | Экран сопоставления | `/cashflow-categories/group-chart`: дифф dry-run, «применить», ручная привязка и отвязка, список «Не сопоставлено» | — |
| 4 | Консолидированный ДДС | Отчёт: выбор компаний, строки по эталону, «Не сопоставлено», внутригрупповые; Excel | — |
| 5 | Выкат | sync на всех компаниях прода (запускает Владелец через wrapper), замеры покрытия до и после | — |

План каждого этапа — `stages/stage-N.md` (задача, результат, что считаем
выполненным, чек-лист приёмки); итог этапа пишется в тот же файл.

## Приёмка задачи

- [ ] Эталон утверждён Владельцем, `core.yaml` v2 на проде.
- [ ] Новая компания получает все статьи эталона с `group_code`.
- [ ] У каждой компании прода есть все статьи эталона; число операций на статьях без кода
      замерено до и после выката.
- [ ] Повторная синхронизация ничего не меняет (тест и прод: план пуст).
- [ ] Статью с кодом нельзя удалить или перенести в чужую ветку (тест).
- [ ] Консолидация: сумма по компаниям = сумма их отдельных отчётов ДДС за период
      минус внутригрупповые; строка «Не сопоставлено» видна.
- [ ] Компанию, в которой пользователь не участник, нельзя выбрать в консолидации
      (функциональный тест).
- [ ] `ARCHITECTURE.md`: контракт `group_code`, синхронизация, кто коммитит,
      Facade-метод консолидации.

## Риски

- **Дерево Максимедиа читается только с прода.** SQL через `codex-psql-ro`
  требует явного разрешения Владельца (auto mode режет чтения прода).
  Альтернатива — Владелец выгружает дерево сам через `!`.
- **Похожие названия в разных ветках** («Прочие поступления» в операционной и
  финансовой деятельности): похожесть сравниваем только внутри секции
  деятельности (`flowKind`) и направления.
- **Конфликт кода:** у компании две статьи, похожие на одну статью эталона. Код не
  ставим, оставляем конфликт для ручной привязки на экране.
- **Перенос существующей статьи под другого предка** при привязке меняет вид
  отчёта ДДС компании. Поэтому в MVP привязка только ставит код, дерево компании
  не перестраивает. Если статья компании лежит в другой секции деятельности, это конфликт.
