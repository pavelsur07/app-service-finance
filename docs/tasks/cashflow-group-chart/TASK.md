# Единый план статей ДДС группы — основа консолидированной отчётности

Поручено Владельцем 17.11.2026: у всех компаний должна быть одинаковая
структура ДДС для MVP «Консолидированная отчётность». Решение того же дня:
эталон — дерево статей ДДС ООО «Максимедиа» + ядро `core.yaml`. Все 9 статей
Максимедиа покрыты ядром, и её дерево заменяется ядром (этап 0a).

Уточнение Владельца 17.11.2026: у разных групп компаний может быть своё ядро
статей ДДС, и живёт оно в другом кабинете. Поэтому эталон не глобальный: у каждой
группы — головная компания, по умолчанию (компания вне группы, новая компания) — `core.yaml`.

## Как сейчас

- `CashflowCategory` (`cashflow_categories`) принадлежит одной компании.
  Стабильный код есть только у 7 системных групп (`system_code`: `CF_OP`,
  `CF_FIN`, `CF_INV`, `CF_TECH*`, `CF_UNALLOC`), unique
  `(company_id, system_code)`.
- Ядро `site/config/cash/cashflow_templates/core.yaml` (v1: 7 групп и 30 статей)
  ставит `ApplyCashflowCoreTemplateAction`, но только новой компании без
  несистемных статей. Кодов у статей нет.
- На проде 21 компания, 378 обычных статей, у каждой компании своё дерево.
  Ссылаются на статью: `CashTransaction`, `CashTransactionSplit`, `PaymentPlan`,
  `CashTransactionAutoRule`, ИИ-категоризация.
- Понятия «группа компаний» нет. У `Company` есть `inn`, у `Counterparty` тоже есть `inn`.

Сводить по названиям нельзя: после переименования консолидация молча
разъедется.

## Решение — эталон группы и привязка к нему

Так делают в МСФО-консолидации: план статей группы (group chart of accounts) и
привязка статей компаний к нему (local → group). Эталон у каждой группы свой.

1. **Группа консолидации задаётся в настройках головной компании** (решение Владельца
   17.11.2026). В настройках компании включается «Головная компания группы», и там же
   отмечаются компании кабинета, которые входят в группу. Кабинет — компании, где пользователь
   владелец. Дерево ДДС головной компании и есть эталон группы: все участники от него зависят.
   Структура группы своя, но строится на основе базовой: головная компания начинает с ядра
   (`core.yaml`, этап 0a) и дополняет его своими статьями.
   Модель в модуле Company (группа понадобится и для консолидации ОПиУ и Баланса): одна
   таблица `company_consolidation_member` (`company_id` PK, `head_company_id`). У головной
   компании своя строка, где `head_company_id = company_id`. Инварианты держит PK: компания
   входит не больше чем в одну группу, головная не может быть участником другой группы,
   участник не может быть головной (этап 1b).
   Контракт — `ConsolidationGroupFacadeInterface` (`headOf(companyId)`, `members(headCompanyId)`).
2. **Эталон по умолчанию — `core.yaml`** v2 с `code` у каждого узла: для компаний вне
   группы и для онбординга. Группа может взять его за основу: головная компания
   получает ядро командой этапа 0a.
3. **`cashflow_categories.group_code`** — `varchar(64) NULL`, unique
   `(company_id, group_code)`. Ключ консолидации одинаков для обоих видов эталона:
   - у статьи из `core.yaml` — код из файла (`OP_IN_CUSTOMERS`);
   - у статьи головной компании — код, который она получает при включении группы или
     при создании, если кода ещё нет (id статьи эталона: стабилен и уникален);
   - у статьи компании-участника — код статьи эталона, к которой она привязана.
   Руками в форме код не редактируется.
4. **Своя детализация разрешена.** Под статьёй с кодом участник заводит свои
   подстатьи. В консолидации они сворачиваются к ближайшему предку с кодом.
5. **Защита.** Статью с кодом нельзя удалить и нельзя перенести под предка с другим
   кодом. В головной компании статью с кодом нельзя удалить, пока к ней привязан
   кто-то из участников. Переименовывать можно: в консолидации название берётся из эталона.
6. **Синхронизация «эталон группы → участник»** — одна Action для команды и экрана.
   Источник — дерево головной компании или `core.yaml`. План: привязать по коду →
   привязать по похожему названию в той же секции и направлении → создать
   недостающую → конфликт (показать, не трогать). Ничего не удаляет и не
   переименовывает. Сначала dry-run. Повтор под `pg_advisory_xact_lock` компании,
   журнал применений. Образец — `ApplyDefaultPLTemplateAction`,
   `PLCategoryNameSimilarity`, `pl_template_applications`. Новая статья в эталоне
   доходит до участников при следующей синхронизации (кнопка и ночной cron с dry-run и
   отчётом о расхождениях).
7. **Доступ (IDOR).** Включить головную компанию и менять состав может только владелец
   головной компании, а добавлять в группу — только компании, где он тоже владелец
   (`CompanyFacade::ownedCompanyIds()`). Чтение дерева головной компании при синхронизации
   идёт через состав группы, а не по id из запроса.
8. **Консолидированный ДДС** — по группе: `SUM … GROUP BY group_code` по всем её
   компаниям. Отчёт открывается пользователю с доступом на чтение ко всем компаниям
   группы, иначе 403. Названия строк — из эталона. Операции на статьях без кода
   попадают в строку «Не сопоставлено» и не теряются.
9. **Внутригрупповые обороты.** Операция, у которой ИНН контрагента совпадает с ИНН
   другой компании группы, считается внутригрупповой: показываем её отдельной
   колонкой и исключаем из итога.

Связь ДДС → ОПиУ (`plCategory`) не синхронизируется: у каждой компании своя,
решение #2934.

## Не делаем в MVP

- Вложенные группы (холдинг из холдингов) и компанию сразу в нескольких группах.
- Отдельные роли и права на группу: доступ выводится из членства в компаниях.
- Синхронизацию удалений и переименований эталона в участников.
- Консолидацию ОПиУ и Баланса — отдельная задача на том же принципе.
- Пересчёт валют: в MVP только RUB, остальные валюты — отдельной строкой.

## Риски

- **Головная компания правят как обычную компанию.** Удаление статьи с кодом
  закрыто защитой (п. 5), но перенос между секциями деятельности ломает
  сопоставление участников. Перенос статьи с кодом в другую секцию запрещён.
- **Компания уже в группе с другим эталоном.** Переход в другую группу — отвязка кодов
  и повторная синхронизация; в MVP только командой, по решению Владельца.
- **Похожие названия в разных ветках** («Прочие поступления» в операционной и
  финансовой деятельности): похожесть сравниваем только внутри секции
  деятельности (`flowKind`) и направления.
- **Конфликт кода:** у компании две статьи, похожие на одну статью эталона. Код не
  ставим, оставляем конфликт для ручной привязки на экране.
- **Перенос существующей статьи под другого предка** при привязке меняет вид
  отчёта ДДС компании. Поэтому в MVP привязка только ставит код, дерево компании
  не перестраивает. Если статья компании лежит в другой секции деятельности, это конфликт.
