# Этап 2 — синхронизация «эталон группы → компания»

## Какую задачу решаем

После этапа 1b известно, кто в группе. Но деревья ДДС участников не связаны с эталоном: у
статей участника нет кода, и консолидировать нечего. Нужна одна операция, которая
выравнивает дерево компании по эталону и ничего не ломает.

## Что будет результатом

1. **Эталон компании** (`CashflowGroupChartSource`):
   - участник группы (`headOf ≠ сама`) — дерево головной компании, все несистемные статьи.
     Статьи головной без кода получают код, равный своему id: эталон готовится в той же
     транзакции, головная блокируется первой;
   - головная компания и компания вне группы — `core.yaml`.
   Узел эталона: `code`, название, секция (`CF_OP`/`CF_FIN`/`CF_INV`), код родителя (или
   секция), направление, описание.
2. **`SyncCashflowGroupChartAction`** — план (dry-run) и применение одной функцией. Узлы идут от
   родителя к детям. Для каждого:
   - у компании есть статья с этим кодом → уже привязана, ничего не меняем (не переименовываем
     и не переносим);
   - иначе ищем статью без кода внутри ветки привязанного родителя с тем же названием после
     нормализации (регистр, «ё», знаки). Ровно одна — привязать (проставить код);
   - две и больше — конфликт: показать и не трогать. Дети узла с конфликтом пропускаются,
     с причиной;
   - нет ни одной — создать под привязанным родителем с кодом, названием, направлением и
     описанием эталона.
   Ничего не удаляет и не переименовывает. Под `pg_advisory_xact_lock(hashtext(companyId))`:
   сначала головная, потом компания (источник раньше производных). Повтор — пустой план.
3. **Журнал `cashflow_group_chart_applications`**: компания, источник (`core`/`head`), головная
   компания, сколько привязано, создано и конфликтов, время. Пишется только при изменениях.
4. **Команда `app:cash:group-chart:sync <companyId> [--execute]`**: без `--execute` печатает план.
   Блок для wrapper `codex-console`.
5. **`ARCHITECTURE.md`:** эталон, синхронизация, кто коммитит, журнал, порядок блокировок.

Вне этапа: экран сопоставления и ручная привязка (этап 3), ночная проверка расхождений и
`integrity-check` (этап 3 или 5 — Company не может вызывать Cash без цикла модулей). Сравнение
названий — точное после нормализации, без совпадения «до разделителя» из ОПиУ: если на проде
окажется мало привязок, расширим на этапе 3.

## Что считаем выполненной работой

PR влит, миграция применена, код выкачен, wrapper пропускает команду. Синхронизация
участников на проде — этап 5, после того как Владелец задаст группы.

## Чек-лист приёмки

- [ ] Тест: участник с пустым деревом получает все статьи головной с кодами головной; статьи
      головной без кода получают код = id.
- [ ] Тест: статья участника с тем же названием в той же ветке привязывается, не создаётся
      вторая; операции на ней остаются.
- [ ] Тест: две статьи с одним названием в ветке — конфликт, ни одна не привязана, дети узла
      пропущены.
- [ ] Тест: повторная синхронизация — пустой план, журнал не растёт.
- [ ] Тест: две группы с разными головными — участник каждой получает свой эталон.
- [ ] Тест: компания вне группы и головная синхронизируются с `core.yaml`.
- [ ] Тест: dry-run ничего не пишет.
- [ ] Тест команды: план и `--execute`.
- [ ] `SchemaInSync`, PHPStan по каталогам модулей, CS, Architecture; внешнее ревью (миграция).
