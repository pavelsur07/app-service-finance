# G2 — ai-service через шлюз (доработка PR #2834)

Общий план — `plan.md`, шлюз — `g1.md`, выкат сервиса — `../stages/prod-rollout.md`.

## Задача

ai-service ходит к OpenAI, DeepSeek и Kimi только через `ai.vashfindir.ru`,
предъявляя `AI_GATEWAY_TOKEN`; на app-сервере и в контейнерах сервиса нет ключей
провайдеров. Выкат сервиса (#2834) по-прежнему за флагом `AI_SERVICE_ENABLED`
(выключен).

## Исходное состояние (31.10.2026)

- G1 на проде: шлюз отвечает, проверка 1 — OpenAI и DeepSeek 200, Kimi без ключа (#2837).
- `AI_GATEWAY_TOKEN` — в GitHub Secrets (им же пользуется деплой шлюза).
- #2834 (не смёржен): маршрут `deepseek → yandex → anthropic` напрямую к
  провайдерам, в прод-compose и деплое — `AI_OPENAI/DEEPSEEK/ANTHROPIC/YANDEX_*`.
  Ветка перебазирована на master, запись ARCHITECTURE — 2.100.

## Результат

```
ai-service (app) ── base_url https://ai.vashfindir.ru/{openai|deepseek|kimi}/v1
                    api_key_env AI_GATEWAY_TOKEN ──▶ шлюз ──▶ провайдер
```

- `config/routes.yaml` — провайдеры `stub`, `openai`, `deepseek`, `kimi`, все
  три через шлюз с `AI_GATEWAY_TOKEN`; `local`, `anthropic`, `yandex` из прод-маршрутов
  убраны. `categorize_transactions`: `fallback` `deepseek/deepseek-chat` →
  `openai/gpt-4.1-mini`. Kimi объявлен, в маршрут — после ключа (#2837): иначе
  каждая задача тратила бы повторы на 503 шлюза. Модели — кандидаты, порядок
  утверждается по `evals-compare` в G3.
- **Сторож шлюза.** `AI_SERVICE_LLM_GATEWAY_URL` задан → у каждого провайдера,
  кроме `stub`, `base_url` начинается с `<gateway>/`; иначе `api`, `worker`,
  `llm-ping`, `gateway-check`, `evals-compare` не стартуют (выход 2). Провайдер
  без `base_url` (адаптер ходит на свой адрес по умолчанию) — тоже отказ.
- `python -m ai_service gateway-check` — проверки 2 и 4 (бесплатно): у каждого
  провайдера маршрутов `GET <base_url>/models` с токеном → 200 и без токена →
  401. Выход 0 только при всех ожиданиях.
- `python -m ai_service llm-ping` — проверка 3: у каждого провайдера маршрутов
  чат «Ответь одним словом: ok», `max_tokens` 5, первая модель провайдера из
  маршрутов. Строка `<провайдер>: ok <модель> <мс>` или `<провайдер>: fail <код>`;
  ответ модели и токен не печатаются. Выход 0 только если ответили все.
- Обе команды — без БД и токена API, трассы не пишут, в pipeline не участвуют.
- `prices.yaml` — модели маршрута и Kimi (цены — в G3 вместе с `evals-compare`).
- Образ сервиса несёт наборы evals (`/app/evals`, `AI_SERVICE_EVALS_DIR`), а
  команды берут маршруты из `AI_SERVICE_ROUTES_FILE`: в образе пакет лежит в
  site-packages, пути рядом с ним нет (находки ревью).
- Прод-compose: `AI_GATEWAY_TOKEN`, `AI_SERVICE_LLM_GATEWAY_URL:
  https://ai.vashfindir.ru` (литерал — сторож не выключить пустой переменной);
  ключей провайдеров нет. Деплой: вместо ключей — `AI_GATEWAY_TOKEN` (алфавит,
  ≥ 32 при включённом сервисе); при включённом сервисе после миграций —
  `gateway-check` (провал → деплой красный до запуска воркера).
- Runbook `docs/maintenance/ai-service-prod.md`, `plan.md`, `keys.md`, README
  сервиса, ARCHITECTURE 2.100.

## Решения

- **Сторож по префиксу `<gateway>/`, а не по хосту:** закрывает и чужой хост с
  тем же началом (`ai.vashfindir.ru.evil`), и `http://`.
- **Сторож на всех объявленных провайдерах, не только в маршрутах:**
  `llm-ping` и `evals-compare --models` могут вызвать любой объявленный.
- **`evals-compare` — тоже через шлюз:** значит, только с app-сервера (в
  контейнере сервиса, G3); с dev-машины шлюз ответит 403 — так задумано.
- **Kimi вне маршрута до #2837:** у всех провайдеров один токен, «провайдер без
  ключа выключен» больше не работает — шлюз отвечал бы 503 и задача тратила бы
  повторы.
- **`gateway-check` в деплое только при включённом сервисе:** образ сервиса
  тянется только тогда; пока флаг выключен, токен на app не материализуется.
  Поэтому проверки 2 и 4 выполняются при первом включении (G3) автоматически.
  Проверка 5 (чужой IP → 403) сделана в G1 снаружи.
