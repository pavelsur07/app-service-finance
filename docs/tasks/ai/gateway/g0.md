# G0 — tg-gateway → `gateway/` без изменения поведения

Общий план — `plan.md`. G0 — чистый перенос: после деплоя шлюз Telegram
отвечает так же, как до него; меняется только устройство репозитория, деплоя
и формат access log.

## Задача

Превратить `tg-gateway/` в единый проект `gateway/`, куда в G1 добавится домен
`ai.vashfindir.ru`: общие сниппеты, один workflow с атомарной установкой всех
файлов шлюза и проверкой конфига в CI до мержа.

## Состояние хоста (read-only, 31.10.2026)

- 109.73.204.179, nginx 1.28.3 (Ubuntu); `sites-enabled`: `default` (Ubuntu,
  `listen 80 default_server`), `mybots` (443 без `default_server` — по порядку
  загрузки отвечает на неизвестные Host на 443), `tg-gateway`.
- `/etc/nginx/sites-available/tg-gateway` совпадает с
  `tg-gateway/nginx/tg.vashfindir.ru.conf` (md5 `a9e1d5c7…`).
- `conf.d` пуст; `snippets` — только стандартные; logrotate уже ротирует
  `/var/log/nginx/*.log` (daily, 14); ufw выключен.

## Результат

```
gateway/
  nginx/
    conf.d/gateway-log-format.conf    log_format gateway_json (http-контекст, один раз на хост)
    snippets/app-only.conf            allow 217.198.13.171; deny all — IP app в одном месте
    snippets/upstream-tls.conf        proxy_ssl_verify on, CA, verify_depth 3, server_name on
    sites/tg.vashfindir.ru.conf       текущий конфиг через сниппеты
  scripts/install.sh                  установка набора на хосте с откатом
  scripts/nginx-test.sh               nginx -t в контейнере (CI и локально)
  README.md                           схема, файлы на хосте, деплой, откат
.github/workflows/deploy-gateway.yml  validate (PR) + deploy (master / dispatch)
```

Файлы на хосте (управляет только workflow):

| Репозиторий | Хост |
|---|---|
| `nginx/conf.d/gateway-log-format.conf` | `/etc/nginx/conf.d/gateway-log-format.conf` |
| `nginx/snippets/*.conf` | `/etc/nginx/snippets/gateway/*.conf` |
| `nginx/sites/tg.vashfindir.ru.conf` | `/etc/nginx/sites-available/tg-gateway` + symlink в `sites-enabled` (имя прежнее) |

Решения:

- `log_format` — в `conf.d`: формат объявляется в `http` один раз, а сайты
  грузятся по алфавиту (`ai-…` раньше `tg-…`) — объявление в файле сайта
  ломало бы порядок.
- Имя сайта на хосте прежнее (`tg-gateway`) — без дубля server_name.
- Секреты деплоя прежние (`TG_SSH_PRIVATE_KEY`, `TG_SERVER_HOST`,
  `TG_SERVER_USER`) — это доступ к хосту шлюза, заводить новые не нужно.
- Заглушка неизвестных Host (`00-default`, `ssl_reject_handshake`) в G0 **не
  входит**: она меняет ответ для чужого `mybots` и Ubuntu `default` — отдельный
  пункт G1 с явным решением.

## Детальный план

1. **Сниппеты** — вынести из конфига Telegram:
   - `app-only.conf`: `allow 217.198.13.171; deny all;`
   - `upstream-tls.conf`: `proxy_ssl_server_name on; proxy_ssl_verify on;
     proxy_ssl_trusted_certificate /etc/ssl/certs/ca-certificates.crt;
     proxy_ssl_verify_depth 3;`
2. **Конфиг Telegram** через сниппеты; директивы по смыслу те же.
   `/bot-api/` сейчас без `proxy_ssl_verify` — включение проверки TLS
   `api.telegram.org` — единственное изменение поведения прокси, безопасное
   (сертификат Telegram публичный); проверка — шаг 7.
3. **JSON-лог** `gateway_json`: время, метод, путь без query, статус,
   upstream_status, request_time, upstream_response_time, байты. Без
   `Authorization`, query (в нём бывают токены) и тел. `/bot-api/` остаётся с
   `access_log off` (токен бота в пути).
4. **Workflow `deploy-gateway.yml`**:
   - `validate` (PR, push, dispatch): `nginx -t` в `nginx:1.28` с самоподписанными
     сертификатами-заглушками и файлами certbot — ловит синтаксис и битые
     include до мержа;
   - `deploy` (push в master по `gateway/**`, dispatch): бэкап всех управляемых
     файлов → установка → `nginx -t` → при ошибке откат **всех** файлов и
     повторный `nginx -t` → `reload`;
   - проверки после reload: `/health` по 443 локально; с хоста шлюза
     `/bot-api/` → 403 (хост не в allowlist — значит allowlist работает);
     доступность `app.vashfindir.ru` и `api.telegram.org`.
5. **Удалить** `tg-gateway/` и `deploy-tg-gateway.yml`; обновить ссылки
   (`ARCHITECTURE.md`, комментарий в `docker-compose.prod.yml`, `plan.md`).
6. **Сверка эквивалентности локально**: раскрыть include нового конфига и
   сравнить директивы со старым — разница только в `proxy_ssl_*` для
   `/bot-api/` и `access_log`.
7. **Живая проверка** после деплоя (по «merge and deploy»):
   - лог workflow: все проверки зелёные;
   - `nginx -T` на хосте — сайты `default`, `mybots` не изменились (md5 до/после);
   - Владелец пишет боту — операция создаётся (вход через вебхук) и бот отвечает
     (выход через `/bot-api/`).

## Откат

Workflow откатывает сам при провале `nginx -t`. После успешного деплоя —
`git revert` PR и деплой (вернёт прежний файл сайта; сниппеты и формат лога
без ссылок на них безвредны), либо вручную: прежний файл из коммита
`tg-gateway/nginx/tg.vashfindir.ru.conf` в `/etc/nginx/sites-available/tg-gateway`,
`nginx -t && systemctl reload nginx`.
