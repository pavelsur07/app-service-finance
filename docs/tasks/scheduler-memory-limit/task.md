# Задача: `codex-console` выполняет тяжёлые ad-hoc команды в контейнере с лимитом 256M

## Источник

Продолжение `docs/tasks/ozon-accrual-refresh-oom/`. В той задаче лимит памяти
(`deploy.resources.limits.memory: 1536M`) был добавлен сервису `site-php-cli` в
`docker-compose.prod.yml`. Проверка показала: это не тот сервис.

## Подтверждено — прочитан сам wrapper (без sudo, `/usr/local/bin/codex-console` читаем всем)

```bash
exec docker exec -u app -i site-messenger-worker-sync php \
  -d memory_limit=512M bin/console "$cmd" "$@"
```

**Первая гипотеза (exec в `scheduler`) была неверной** — исправлено после прямого чтения
файла по просьбе Владельца, а не оставлено как непроверенное предположение.

`codex-console` выполняет ЛЮБУЮ команду, включая
`app:ingestion:ozon-accrual:daily-maintenance --execute`, через `docker exec` внутрь
контейнера **`site-messenger-worker-sync`** — постоянно работающего consumer'а очереди
`async_sync`, а не через `site-php-cli` и не через `scheduler`.

## Обнаруженная реальная причина у ЭТОГО пути

`site-messenger-worker-sync` уже имеет `deploy.resources.limits.memory: 256M`
(строки 235-238/266-269 `docker-compose.prod.yml`) — рассчитан на его штатную нагрузку:
`messenger:consume async_sync -vv --time-limit=3600 --memory-limit=160M` (Symfony Messenger
`--memory-limit` — это порог перезапуска воркера, отдельное от PHP `memory_limit` понятие,
и он сам укладывается в 256M с запасом).

`codex-console` подсаживает поверх этого **второй** PHP-процесс с `-d memory_limit=512M` —
собственный soft-cap PHP БОЛЬШЕ, чем cgroup-лимит контейнера (256M). Это значит, что PHP
никогда не успевает дойти до своего внутреннего fatal error — kernel OOM-killer убивает
процесс по превышению 256M раньше. Вдобавок это происходит НЕ в пустом контейнере: consumer
`async_sync` уже работает и занимает часть тех же 256M, пока ad-hoc команда пытается
распаковать/замапить raw-запись в 5-8 тыс. строк.

## Это отдельный путь от ночного cron — они используют разные контейнеры

Ночной `app:ingestion:ozon-accrual:daily-maintenance --execute` (`docker/cron/app.cron`,
`15 5 * * *`) выполняется НЕ через `codex-console`, а через supercronic внутри **`scheduler`**
с явным `-d memory_limit=1G`. У `scheduler` нет `deploy:` секции вовсе (проверено построчно
до конца блока в `docker-compose.prod.yml`) — там OOM ограничен только физической памятью
хоста, это отдельный, более широкий бюджет.

Итого — **два независимых пути выполнения одной и той же команды с разными профилями риска**:

| Путь | Контейнер | cgroup-лимит | PHP memory_limit | Разделяет ресурсы с |
|---|---|---|---|---|
| Ночной cron | `scheduler` | нет | 1G (явно в cron-строке) | другими cron-задачами (см. ниже) |
| `codex-console --execute` | `site-messenger-worker-sync` | **256M** | 512M (задан wrapper'ом, больше cgroup) | активным `messenger:consume async_sync` |

Issues 252/262 (`firstSeen` июль) почти наверняка родом из ночного cron-пути — там нет
cgroup-потолка, значит потребовался настоящий host-wide OOM. Оба РУЧНЫХ прогона этой сессии
шли через `codex-console`, то есть через гораздо более тесный 256M-путь.

## Контрольные прогоны после фикса двойной материализации

- Первый ручной прогон (до фикса `RefreshOzonAccrualCategoryMetadataAction`) упал с тем же
  SIGKILL на нескольких raw-записях одного шопа — ожидаемо для 256M cgroup на raw-записи из
  5-8 тыс. строк.
- Второй ручной прогон (после фикса, `--days-back=45 --execute`, без `--company-id`, по
  всем компаниям) прошёл **без единого сбоя** за тот же путь через тот же 256M-контейнер.
  Это более сильное свидетельство, чем казалось изначально: устранение двойной
  материализации (Work Item 2 предыдущей задачи) не просто немного снизило пик на
  синтетическом тесте — оно позволило пройти через контейнер с ЖЁСТКИМ 256M потолком,
  которого раньше не хватало. Одного успешного прогона недостаточно для гарантии на все
  возможные объёмы данных, но это не «повезло с состоянием хоста» — это конкретный,
  измеримый cgroup-потолок, и он был пройден.

## Что нужно решить

1. **`site-messenger-worker-sync` (256M) — тесен для ad-hoc backfill-класса команд.**
   Поднимать сам сервис нельзя бездумно: 256M выбран под ЕГО штатную нагрузку
   (`messenger:consume async_sync`), и увеличение лимита меняет профиль контейнера, который
   работает 24/7 и обрабатывает реальные сообщения — рост лимита посреди инцидента с этой
   очередью может замаскировать будущую проблему с ней самой.
2. **Смешивать ad-hoc диагностические/бэкфильные команды с постоянным consumer'ом одной и
   той же очереди — сама по себе спорная конструкция**, независимо от лимита памяти: пока
   `daily-maintenance --execute` час занимает `docker exec`-слот и долю cgroup у
   `site-messenger-worker-sync`, реальные сообщения `async_sync` (внешние HTTP-интеграции —
   маркетплейсы, банк, email, см. `CLAUDE.md`) обрабатываются медленнее или простаивают.
   Это не гипотеза — количественно не измерено, но логически следует из общего cgroup и
   общего PID-неймспейса контейнера.
3. **Варианты, не взаимоисключающие:**
   - **A.** Завести отдельный wrapper-путь для `codex-console` — не `docker exec` в
     `site-messenger-worker-sync`, а `docker compose run --rm site-php-cli ...` (сервис,
     который я уже снабдил лимитом 1536M в прошлой задаче — тогда он наконец пригодится).
     Устраняет и тесноту лимита, и конкуренцию с живым consumer'ом одним изменением.
   - **B.** Поднять лимит `site-messenger-worker-sync` до значения, покрывающего и его
     штатную нагрузку, и разовые ad-hoc команды — компромисс, не убирающий конкуренцию за
     CPU/PID-неймспейс с живым consumer'ом.
   - **C.** Отдельно исправить `scheduler` (см. ниже) — не отменяет A/B, это другой путь.
   Рекомендация: **A** — она чинит сразу оба риска (лимит и конкуренцию с очередью) и
   использует уже сделанную в прошлой задаче работу, а не выбрасывает её.
4. **`scheduler` (ночной cron) по-прежнему без cgroup-лимита вообще.** Это отдельный,
   более сложный случай — общий контейнер для 33 активных cron-строк, часть из которых
   пересекается по времени каждую минуту (`marketplace-ads:scheduler/poller×2/finalizer`,
   `ozon-poll-reports`), плюс шесть ночных тяжёлых батчей (каждый уже с `-d memory_limit=1G`
   в самой cron-строке). Взять то же число, что и для `site-messenger-worker-sync` или
   `site-php-cli`, было бы гаданием — нужна отдельная оценка пикового одновременного
   потребления, для которой у агента нет доступа к `docker stats`/`free` через существующие
   read-only wrappers.
5. **Пересмотреть исходный лимит 1536M на `site-php-cli`.** Если пойдём по варианту A —
   он наконец начнёт использоваться по назначению, менять не нужно. Если нет — он остаётся
   безвредным, но неиспользуемым.

## Риск

`docker-compose.prod.yml` — HIGH-LOCAL. Вариант A меняет то, как `codex-console` вызывает
команды (сам wrapper `/usr/local/bin/codex-console` — это production access control,
изменение требует отдельного явного разрешения Владельца по разделу «Добавление
PROD-разрешений» в `AGENTS.md`/`docs/maintenance/prod-access.md`, не только правки compose).
Вариант B меняет ресурсный профиль постоянно работающего consumer'а очереди — риск скрыть
будущую деградацию самой очереди `async_sync`. `scheduler` — риск OOM-килла здоровых частых
задач при слишком тесном лимите; менять только после отдельной оценки пикового потребления.

---

## Решение (2026-09-06) — выбран вариант A

Владелец выбрал вариант A: `codex-console` выполняет команду в одноразовом контейнере
`docker compose run --rm --no-deps -T site-php-cli`, а не через `docker exec` в живой
`site-messenger-worker-sync`.

Отдельно рассматривался и **отвергнут** промежуточный вариант — сделать `site-php-cli`
постоянно живущим (`command: ["sleep", "infinity"]`), чтобы в него можно было
`docker exec`. Возражение Владельца: смысл CLI-образа в том, что он «запустился,
отработал и вырубился». Возражение принято — одноразовый `run --rm` и есть уже
действующий паттерн этого репозитория: `deploy.yml` тем же способом выполняет
`doctrine:migrations:up-to-date`.

### Что проверено экспериментально, а не предположено

Проверялось локально на макете, повторяющем структуру `docker-compose.prod.yml`
(якорь `x-php-env`, `container_name`, `deploy.resources.limits`), Docker Compose v5.5.0:

| Вопрос | Результат |
|---|---|
| Применяет ли `docker compose run` лимит из `deploy.resources.limits.memory`? | **Да.** `HostConfig.Memory` совпадает с `up`: 536870912 при `512M` |
| Есть ли у `run` флаг `--memory`, если бы не применял? | Нет — compose-файл единственный источник лимита |
| Мешает ли заданный `container_name` вызову `run`? | Нет — `container_name` игнорируется, генерируется `<project>-<service>-run-<hash>`, одновременные вызовы не конфликтуют |
| Восстанавливается ли окружение из работающих контейнеров при пустом host-env? | Да, побайтно — включая пароль со спецсимволами `@ : / #`, `APP_SECRET` с несколькими `=` и JSON ключей шифрования |
| Подхватывается ли `IMAGE_TAG`? | Да, compose сам читает `.env` из каталога проекта (его пишет `deploy.yml`) |
| Появляются ли файлы с секретами на диске? | Нет — значения живут только в памяти процесса wrapper'а |

### Почему секреты берутся именно так

`deploy.yml` кладёт в `.env` на проде **только** `IMAGE_TAG` (строка 688); остальные 13
переменных лишь `export`-ятся внутри эфемерного SSH-heredoc и через час после деплоя их
в окружении хоста нет. При этом compose-файлу для подстановки нужны пять переменных без
дефолта: `APP_SECRET`, `HEALTH_CHECK_TOKEN`, `POSTGRES_PASSWORD`, `SENTRY_DSN`,
`SITE_MAILER_DSN`.

Wrapper восстанавливает их из окружения уже работающих контейнеров через
`docker inspect`. Две неочевидные детали, из-за которых наивная реализация тихо
сломалась бы:

- **`POSTGRES_PASSWORD` в php-контейнерах отсутствует.** Он подставляется внутрь
  `DATABASE_URL` ещё при разборе compose, отдельной переменной не остаётся. Единственный
  контейнер, несущий его как есть, — `symfony-postgres`. Без этого `${POSTGRES_PASSWORD}`
  подставился бы пустым и дал `pgsql://app:@site-postgres:5432/app`: команда упала бы на
  аутентификации, а не на понятной ошибке.
- **Имя переменной меняется на границе.** В compose — `SITE_MAILER_DSN`, внутри
  контейнера — `MAILER_DSN`.

Постоянный env-файл на диске (обсуждался как альтернатива) не понадобился вовсе.

### Что осталось открытым

Пункт 4 выше — `scheduler` без cgroup-лимита — этим решением **не закрыт**. Ночной cron
идёт другим путём и по-прежнему ограничен только физической памятью хоста. Для оценки
нужен доступ к `docker stats`/`free`, которого у существующих read-only wrappers нет.

Пункт 5 закрыт: лимит 1536M на `site-php-cli` начинает работать по назначению.
