# MCP: внешний доступ к данным и административное управление

Дата: 2026-11-15. Статус: расширенное предложение; разрешена подготовка плана,
реализация приложения и production-действия не выполняются.
Основание: запрос владельца в чате и независимое ревью Claude CLI.
Проверенная база: `5aff7dbfd0f11f4c0d2181e04eda7743920018f9` (`origin/master`).

## 1. Зафиксированные требования владельца

- Внешние пользователи подключают AI-клиенты к ВашФинДир через MCP.
- Пилота на отдельных компаниях и allowlist компаний **нет**.
- Нужен отдельный административный MCP: диагностика сервиса, статусы задач,
  прикладные команды и повтор обработки.
- Деплой, инфраструктура и изменение финансовых данных не входят в этот
  административный контур. Добавление таких функций требует нового scope.
- Разработка начинается с тестов; исполнение — по AGENTS.md, без owner gate
  между Stage. Этот документ сам по себе не запускает разработку.

## 2. Архитектурное решение — рекомендация

Два MCP resource server внутри одного Symfony-приложения. Общие SDK,
OAuth-интеграция и технические компоненты; разные audience, principal,
OAuth grants, consent, firewall и каталоги tools. Отдельный микросервис сейчас
не оправдан: он дублирует авторизацию и требует дополнительного развёртывания.
Один смешанный каталог с `admin=true` не использовать.

```text
AI-клиент клиента  -> account-host /mcp
                     -> user grant -> company + live financial rights
                     -> read-only tools -> Report/Finance/Cash Facade

AI-клиент оператора -> admin-host /mcp/admin
                      -> admin grant -> live platform roles + ops scopes
                      -> diagnostics -> ServiceGateway Facade -> read models
                      -> prepare operation -> подтверждение человеком в админке
                      -> durable job -> worker -> разрешённый Action
```

Администратор платформы (`ROLE_ADMIN`) и владелец компании — разные субъекты.
Ни владение компанией, ни пользовательский OAuth-токен не дают ops-доступ.
Административный токен не принимается пользовательским MCP и наоборот.
Для одного человека, работающего в двух контурах, создаются два подключения.

## 4. Внешние tools первой версии

| Tool | Scope | Ответ |
|---|---|---|
| `get_connection_info` | authenticated connection | Название клиента, текущая компания, разрешённые scopes, expiry; без токенов |
| `list_accounts` | `accounts.read` | Пагинированные ID, названия, типы, валюты; без банковских реквизитов и остатков |
| `get_cashflow_report` | `cashflow_reports.read` | ДДС по периоду и валютам |
| `get_profit_loss_report` | `pl_reports.read` | ОПиУ по периоду, группировке и разрешённым разрезам |

Имена scopes переиспользуются из ApiScopeCatalog. Доступность MCP задаётся
отдельно; его выпуск **не** переключает `connected` для Bearer API-ключей
и не наделяет старые ключи новыми правами. Общая политика — пересечение
согласованных scopes, инструментов канала и текущего `financialAccess.read`.
Отсутствие tool policy означает отказ, включая прямой `tools/call`.

Компания берётся только из подключения, выбранного и проверенного сервером
при согласии. Аргумента смены компании у tools нет. Проекты/ЦФО дополнительно
проверяются в этой компании; чужой ID не превращается в отчёт без фильтра.
Отчёты используют тот же расчёт, что UI. Старые report endpoint'ы не служат
OAuth-адаптером и в этой задаче не удаляются.

Семантика project/ЦФО фильтров: отсутствующее поле — все, включая
нераспределённые факты; пустой список — ошибка; частичный список — выбранный
разрез. Полный набор доступных UI choices нормализуется в отсутствие фильтра,
как в интерфейсе. Чужой/недопустимый ID — ошибка до нормализации, не skip.
Группировка — строгий enum; неизвестное значение не заменяется на month.
Паритет сверяется с JSON-экспортами UI, включая нормализацию фильтров.

Деньги в MCP — decimal string + ISO currency. Текущее использование float
в CashflowReportBuilder не «исправляется» форматированием: сначала фиксируется
текущая семантика и округление тестами. Если паритет с UI обеспечить нельзя,
нужно отдельное согласованное решение о расчёте, а не молчаливая замена формул.
Разные валюты не складываются. `generated_at` — время расчёта; свежесть исходных
данных указывается отдельно, с `unknown`, если достоверного watermark нет.
ОПиУ сейчас не имеет currency breakdown в builder: его строкам передаются
форматы MONEY/PERCENT/RATIO/QTY и warnings, а не выдуманная валюта для всех
значений. Валюта денежных строк требует решения D6; до этого не подставлять
RUB и не обещать мультивалютный ОПиУ. Для ДДС сохраняется реальное разделение
по валютам, для процентных/количественных строк валюта неприменима.

## 5. Отдельный административный доступ

| Tool | Роль и scope | Граница |
|---|---|---|
| `get_service_status` | ROLE_ADMIN + `ops.services.read` | Последнее состояние витрины и stale, без секретов/внутренних URL |
| `get_service_coverage` | ROLE_ADMIN + `ops.coverage.read` | Сводка выбранного зарегистрированного сервиса за один допустимый месяц |
| `list_tasks`, `get_task` | ROLE_ADMIN + `ops.tasks.read` | Только задачи, созданные через MCP; без payload, сумм и ПДн |
| `prepare_coverage_refresh` | ROLE_SUPER_ADMIN + `ops.coverage.refresh` | Создать предварительную заявку на обновление витрины одного сервиса |
| `prepare_task_retry` | ROLE_SUPER_ADMIN + `ops.tasks.retry` | Предварительная заявка на повтор одной завершившейся ошибкой задачи |

Рекомендуемые role/scopes — ограничения будущей функции, не предоставление
пользователям новых ролей. Старые admin-токены и сессии не становятся MCP grants.
Для admin OAuth используется предварительная регистрация конкретных
доверенных клиентов; внешний self-registration туда не переносится.

Начальный конкретный тип задач — `service_coverage_refresh`: уже существующий
GET внутреннего покрытия + замена Symfony-витрины. Начальный список сервисов
берётся из CoverageServices (ozon-fetcher, wb-fetcher), не из URL, присланного LLM.
Повтор — повтор этого типа задачи после `failed_retryable`; running, succeeded,
failed_permanent и неизвестные типы отклоняются. Это первый реализуемый срез
управления, а не обещание общего retry любых задач.

Запрос на дальнейшие типы (ingestion, AI, Messenger failed messages) требует
разбора владельца данных, исходного idempotency key, стоимости и побочных
эффектов. Пока адаптера и контракта нет, возвращать `unsupported_task_type`,
не пытаться вызывать консоль, общий retry очереди или внутренний URL.
Состояние витрины не выдаётся за liveness процесса; AI-запуски и ai-service
задачи не объявляются одной сущностью.
Сбои регулярного cron refresh пока видны через stale витрины и существующий
мониторинг; они не появляются в list_tasks задним числом. Расширение общего
журнала cron-задач — отдельный последующий срез.

### 5.1. Подтверждение и исполнение

1. Tool создаёт `prepared`-заявку с неизменяемыми параметрами: вид операции,
   сервис, исходная задача/версия, причина, actor, connection, срок, idempotency key.
2. Возвращает ID и ссылку на страницу админки. Ссылка — идентификатор заявки,
   без bearer/approval secret. GET ничего не выполняет и не подтверждает.
3. Человек входит в admin realm. При рекомендации D4 это тот же пользователь,
   который создал заявку; её связь с исходным активным connection проверяется
   сервером. Сервер показывает нормализованные параметры
   и эффект; POST с CSRF и недавней повторной аутентификацией подтверждает
   именно эту версию. `confirmed=true` и текст согласия от модели не принимаются.
4. Подтверждение атомарно создаёт durable job и аудит. Выполнение начинается
   после подтверждения; отдельного tool, способного одобрить заявку, нет.
5. Worker перечитывает статус подключения, роль, scopes, expiry заявки и
   исходное состояние. Потеря полномочий до выполнения отменяет ещё не начатую
   операцию; уже выполненный эффект отзыв токена не откатывает.
6. Повтор запроса с тем же ключом и параметрами возвращает прежний operation ID;
   с другими параметрами — conflict. Параллельные исполнения исключаются БД и
   общей с cron блокировкой. Retry не очищает историю исходной попытки.

Одна подтверждённая заявка — одна попытка, без фонового автоматического
retry. Все исходы succeeded/failed_retryable/failed_permanent терминальные;
новая попытка после временного сбоя требует новой заявки и подтверждения.
Только queued/running занимают активный слот сервиса; prepared его не блокирует.

Первую очередь брать из БД операций, используя claim/lease и периодический
подхват существующим scheduler через обычный релиз. Не вводить новый сервис,
новый Redis transport или ненадёжный dispatch-after-commit.
Если вместо этого используется Messenger, долговечная постановка должна быть
доказана outbox/транзакционным транспортом, а не только вызовом `dispatch()`.
Изменение production scheduler/worker config требует отдельного named approval
по AGENTS.md §3.3; этот план такого одобрения не даёт.

### 5.2. Что не является административным MCP

Нет tools для shell/SSH/SQL, произвольного HTTP, secrets/env, изменения ролей,
Docker, деплоя, рестарта воркеров, миграций, backfill/recalc/prune,
массового retry и редактирования финансовых операций. Доступ к диагностике
не включает выдачу сырого журнала или AI traces. Компания-владелец не
подменяет оператора платформы. Строки из логов и документов — недоверенные данные.

Подтверждение в приложении — контроль будущего продукта. Оно не отменяет
сессионные ограничения AGENTS.md на ручные production-команды агента.

## 6. Вопросы, которые нужно решить до реализации

План и ревью можно завершить до ответов; реализацию зависимой бизнес-логики
начинать нельзя. Рекомендации не записывать как уже одобренные требования.

| ID | Вопрос | Рекомендация |
|---|---|---|
| D1 | Кто выдаёт внешнему AI доступ к компании? | В первой версии только фактический владелец, как у существующих API-ключей; делегирование сотрудникам отдельно |
| D2 | Какие внешние клиенты гарантированно поддерживаем? | Минимум два названных клиентом продукта с зафиксированными версиями; не обещать «любой MCP» |
| D3 | Доступ при отсутствии подписки (`NONE`)? | Явное решение владельца; ACTIVE/GRACE/READ_ONLY читают по действующим правам, для NONE не придумывать новую тарифную политику |
| D4 | Кто подтверждает admin-команду? | Инициатор ROLE_SUPER_ADMIN через собственную admin-сессию с повторной аутентификацией; второй оператор только если нужен бизнесу |
| D5 | Какие task types после coverage нужны первыми? | Точный перечень; до появления адаптера другие типы доступны только в согласованной диагностике |
| D6 | Какая отчётная валюта денежных строк ОПиУ? | Зафиксировать существующую бизнес-семантику до реализации tool; не выводить валюту из формата и не добавлять конвертацию |

Ответ на admin scope уже получен: диагностика и прикладные команды, без инфраструктуры.
Подключение внешних компаний не выборочное; D1/D2 и consent — правила доступа,
а не скрытый пилот. Решения D1–D6 фиксируются в Phase 0 перед зависимым кодом.

## 7. Источники best practices

- [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization): OAuth discovery и разделение authorization/resource server.
- [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html): один authorization server может обслуживать разные целевые resources; выдача и приём токенов ограничены целевым ресурсом.
- [MCP authorization security](https://modelcontextprotocol.io/specification/latest/basic/authorization/security-considerations): PKCE, redirect validation, целевая аудитория токенов.
- [MCP Streamable HTTP](https://modelcontextprotocol.io/specification/latest/basic/transports/streamable-http): транспорт и требования проверки Origin.
- [Symfony MCP Bundle](https://symfony.com/doc/current/ai/bundles/mcp-bundle.html): интеграция официального PHP SDK, не готовый OAuth authorization server.
- [OWASP MCP Security](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html): минимальные полномочия, разделение контуров и недоверенные результаты tools.
- [OWASP Transaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html): подтверждение конкретных параметров и серверная проверка исполнения.

Локальная интеграция, начальные лимиты, набор tools и этапы ниже — проектные
рекомендации. Источники не объявляют их обязательными значениями стандарта.
