#### Почему правило уже буквы CLAUDE.md
`CLAUDE.md` требует `companyId` от каждого метода Repository. Буквально это
покрыло бы и `save()` (29 штук), и `remove()`, которым компания не нужна:
сущность её уже несёт. Правило ограничено методами-запросами — теми, которые
физически могут вернуть чужие данные.

Второе сужение важнее и появилось по находке внешнего ревью: правило применяется
только к репозиториям, чья сущность **принадлежит компании**. Проверка сделана
по модели — у сущности либо есть поле `company`/`companyId`, либо нет, — а не
списком исключений, который пришлось бы вести руками. Сущность определяется
двумя способами, потому что в проекте сосуществуют два стиля: docblock
`@extends ServiceEntityRepository<Entity>` (41 репозиторий) и только
`parent::__construct($registry, Entity::class)` (59). Если сущность определить
не удалось, принадлежность считается подтверждённой: цена ложноположительного
срабатывания — строка в baseline, цена ложноотрицательного — инцидент.

Третьим сужением был параметр-носитель: `DocumentRepository::findByCompany(DocumentListDTO $dto)`
фильтрует по `$dto->company`. Оно **отменено** — см. «Упрощение правила» ниже.

Для метода, который обязан ходить по всем компаниям (агрегат по платформе,
backfill из CLI), есть явный отказ: тег `@companyScopeExempt <причина>` в
docblock. Причина обязательна, отказ виден в диффе рядом с кодом, а не спрятан
в конфиге.

**Утверждение «у всех нарушений один путь починки» снято как неверное.**
Оставшиеся 51 требуют поштучной классификации: часть — добавить параметр и
фильтр, часть — оформить `@companyScopeExempt` с причиной. Это записано в
FOLLOW-UP, а не выдано за однородный долг.

#### Упрощение правила — вывод из четырёх итераций ревью
Итерации 2, 3 и 4 внешнего ревью нашли по новой дыре, и все они были одного
рода: я добавлял очередной способ *принять* метод как ограниченный (носитель
типа, затем ненулевой носитель, тег отказа), а проверял каждый только на
счастливом пути. Дыры находились в этих же послаблениях — nullable-поле
носителя, ветвь union без гарантии, intersection, голый тег отказа, тег,
закрытый `*/` на своей строке, nullable и нетипизированный `$companyId`.

Корневая причина — не отдельные ошибки, а конструкция: правило пыталось
угадать семантику. Подход изменён на противоположный. Предикат сведён к тому,
что нельзя обыграть:

- ограничением считается **только** явный параметр `string $companyId` либо
  объектный `$company`, и тип обязан быть ненулевым;
- инференс параметра-носителя удалён целиком вместе с разбором union и
  intersection;
- всё остальное — включая компанию внутри DTO и намеренно глобальные
  запросы — объявляется явно: `@companyScopeExempt <причина>`.

Правило стало короче и строже, число находок выросло с 25 до 39, а после
транзитивного владения и префикса `stream*` — до **51**. Это честнее: методы,
скрывающие компанию в DTO, и репозитории сущностей с косвенным владением
(`LoanPaymentSchedule` → `Loan`, `ReconciliationLog` → `ProcessingBatch`)
теперь видны, и у каждого есть выбор — сделать параметр явным или написать
причину рядом с кодом.

Отдельно: на каждое послабление и на каждый способ обхода теперь есть
негативная фикстура. В тесте правила 7 методов и 10 негативных сценариев,
в тесте guard'а — 11.

#### Что правило не доказывает — сказано прямо
После пятой итерации ревью стало очевидно: сигнатурная эвристика в принципе не
может доказать, что выборка ограничена. Каждая итерация находила новый класс
неполноты — транзитивное владение, префикс вне списка, параметр без
использования. Часть из них закрыта (владение на один уровень, `stream*`,
`iterate*`), часть закрыть в этой конструкции нельзя.

Поэтому ограничения перечислены в докблоке правила и в `CLAUDE.md`:
1. проверяется сигнатура, а не использование параметра;
2. владение прослеживается на один уровень;
3. читающий метод определяется по префиксу имени;
4. унаследованные finder'ы Doctrine в местах вызова не проверяются вовсе.

Формулировка «зелёный гейт не означает отсутствия IDOR» внесена в `CLAUDE.md`
намеренно: правило сокращает ручную проверку, но не отменяет её. Полноту дало бы
только fail-closed правило с явным исключением на каждый метод — это отдельное
решение о цене, и оно за Владельцем.

#### Инцидент в ходе работы — удаление рабочего файла
При проверке правила `companyId` проба создавалась командой
`mkdir -p site/src/Shared/Repository` с последующим `rm -rf` этого каталога.
Каталог существовал: в нём лежал `AuditLogRepository.php`. Удаление снесло его
вместе с пробой, что немедленно проявилось десятью падениями `composer test:unit`
(«Class or interface "App\Shared\Repository\AuditLogRepository" does not exist»).

Файл восстановлен из `HEAD` и байт-в-байт совпадает с оригиналом:
`git status` по этому пути пуст, `composer test:unit` вернулся к 1928 OK.

Причина — не опечатка, а порядок действий: путь пробы не был проверен на
существование, а уборка удаляла каталог, а не созданный файл. Практика на
будущее: проба создаётся только по пути, чьё отсутствие проверено, и уборка
удаляет ровно созданные файлы. Инцидент записан здесь, а не умолчан: он был
пойман собственными проверками Stage, и это единственная причина, по которой
он остался локальным.
