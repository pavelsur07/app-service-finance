# Как добавлять примеры в проверку PaymentIntake

Первый интерфейс — версионируемые JSONL-файлы и проверка через PR. Код ядра
не зависит от канала: в metadata указывается Telegram, web, email или другой
источник. Самой модели передаются только платёжный текст и рабочий контекст.

## Откуда брать новые случаи

Кандидаты: пользователь исправил черновик; бот потерял/добавил платёж;
перепутал статью/проект/ЦФО; не задал нужный вопрос; выбран новый источник или
встречено сокращение. Нужны также обычные успешные случаи — один набор ошибок
не показывает качество на типичных сообщениях.

Правка пользователя не означает ошибку модели автоматически: могли измениться
сумма или назначение самого платежа. Человек проверяет исходный смысл и отдельно
утверждает ожидаемый ответ. Нельзя автоматически записывать ответ модели в gold.

## Подготовка и разметка

1. Обезличить текст и справочники согласованно: убрать имена, телефоны, карты,
   токены и названия реальных клиентов. Не копировать credentials или raw
   production выгрузки в Git. Даты/время и денежные фрагменты преобразовывать
   последовательно, сохраняя проверяемый смысл и связь с expected output.
2. Заполнить полный PaymentInput: text, reference_at с timezone, валюту,
   допустимые категории/проекты/ЦФО и allowed_pairs. Источник и review metadata
   находятся вне payload и не становятся инструкциями модели.
3. Разметить все ожидаемые кандидаты и поля: amount/currency/direction/
   execution_status/date/category_id/project_id/cfo_id, literal monetary anchor
   и требование вопросов. `null` означает «правильный ответ — неизвестно»,
   а не отсутствие разметки. Неполный gold нельзя выдавать за полный.
4. Для нескольких допустимых решений перечислить варианты, например безопасные
   project/CFO tuples. Не выбирать скрытый приоритет при запрещённой паре.
5. Другой проверяющий подтверждает смысл; записать reviewer_ref и reviewed_at.
   Использовать идентификатор review/псевдоним (напримерreview-123), не URL,
   персональные данные или токен.

Для reviewed-наборов v1 нужны однозначно проверяемые monetary anchors.
Неизвестный масштаб, например короткое число без единицы, может иметь
`amount: null` с обязательным вопросом; anchor при этом остаётся буквальным
денежным фрагментом источника. Повторяющиеся нормализованные суммы и
неоднозначные anchors в этой версии не поддержаны. Если
валидатор отвергает неоднозначный или повторяющийся anchor, пример остаётся
кандидатом: требуется отдельный тест/доработка разметки occurrence. Не менять
исходный смысл ради успешной валидации и не выдавать такой случай за проверенный.

## Формат и команды

Шаблон: `services/ai-service/evals/parse_payment_message/reviewed-template.jsonl`.
Его статус pending; автоматическое включение запрещено. Непроверенные рабочие
копии хранить вне репозитория и evals directory: Docker COPY копирует все eval
файлы, даже не перечисленные в индексе. В репозиторий переносится только
обезличенный файл, полностью прошедший human review. Один JSON-объект на строку:

```json
{
  "format_version": 1,
  "source": {"channel": "web", "provenance": "anonymized", "annotation_origin": "human"},
  "review": {"status": "pending", "reviewer_ref": null, "reviewed_at": null},
  "case": {"id": "web-example-001", "family": "multiple_payments", "payload": {}, "expected_items": [], "questions_required": true}
}
```

Это схема заготовки, не готовый валидный gold. После human review явно
установить `status: human_reviewed`, заполнить `reviewer_ref` и `reviewed_at`
в формате YYYY-MM-DD. Ни одной строки pending в проверяемом файле не оставлять.
Заполненный файл, например
`reviewed-regression-2026-11-15.jsonl`, проверить без сети:

```bash
docker compose --profile services run --rm services-ai-service-dev \
  python -m ai_service.evals.payment_intake_assets \
  --validate-dataset evals/parse_payment_message/reviewed-regression-2026-11-15.jsonl
```

Добавить новую версию/path/SHA256 в
`evals/parse_payment_message/reviewed-index.json`. В индекс попадают только
утверждённые файлы; произвольный локальный файл не становится nightly dataset.
Затем собрать и проверить runtime snapshot:

```bash
docker compose --profile services run --rm services-ai-service-dev \
  python -m ai_service.evals.payment_intake_assets

docker compose --profile services run --rm services-ai-service-dev \
  python -m ai_service.evals.payment_intake_assets --check
```

Новая версия, её review metadata и snapshot проходят PR. После штатного deploy
ночная проверка использует новый packaged manifest. Старые версии и отчёты
сохраняются. Если размер набора превышает объявленный call/time/budget cap,
полный PASS не допускается; объём и политику покрытия меняют явно.

## Regression и независимая проверка

Известные случаи, на которых исправляли код/prompt, входят в regression.
Отдельные новые примеры откладываются для независимой проверки; не читать их
ответы при настройке. После использования для исправлений они становятся
regression, а независимую часть пополняют другими примерами. Название версии
и review фиксируют назначение; публичные development cases не переименовываются
в holdout для улучшения отчёта. Автоматического обучения на этих файлах нет.

Ошибочный эталон исправляется отдельной ревизией с причиной и review. Ночной
job не меняет gold, baseline или prompt самостоятельно. При разборе важны
case ID и несовпавшее поле, а не копирование raw клиентского сообщения в алерт.
