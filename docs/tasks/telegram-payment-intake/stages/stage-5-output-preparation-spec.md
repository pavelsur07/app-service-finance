# Stage 5 — подготовка проверяемого черновика после ответа модели

## Причина изменения

Promptv4+totalguard прошёл318локальных тестов, но полный41case-run дал
38needs_review/3rejected:tg006/tg011paid_unanchored, tg008context_total_amount.
Суммы44/47,кандидаты46/49,направления6/7. Это ухудшение относительноv3 не скрываем.
Кампания163/163вызова исчерпана; оценка токенов11.92739911RUB. Дополнительных
платных запросов в этой локальной работе не выполнять. Операционный postcheck
v4PASS:точное freshbefore/aftermatch,evalcontainers0.

Повторное уточнение промпта не гарантирует дисциплину каждого поля. Текущий
pipeline отвергает всё сообщение из-за неподтверждённого paid или строкиитога,
теряя остальные проверяемые кандидаты. Меняем границу обработки: модель даёт
предложение, код готовит безопасный черновик и затем повторно проверяет его.
Это не автоматическое подтверждение финансового факта.

## Конкретное решение

TaskSpec получает необязательныйprepare_output(input,output,CheckContext).
По умолчаниюNone: остальные задачи проходят прежний путь без преобразования.
Pipeline вызывает callback после успешного schema parse, до всех checks;
повторно валидирует подготовленный результат по той же outputschema. Невалидный
результат callback отклоняется без нового LLMretry; сообщения ошибок содержат
только число ошибок. В private trace допустимы только boolean-признаки подготовки,
без дополнительных rawзначений/логов. Ядро не знает финансовых правил.

ФункцияPaymentIntake использует существующий verifier как источник правил:

- Начальный полныйverify. При privacy/ID/денежных/currency/occurrence/контрактных
 проблемах, которые не входят в ограниченный список ниже, исходный ответ не
 преобразуется и остаётся отклонённым. Не скрывать чужие ID, duplicate refs,
 неверное monetary evidence, нормализацию/масштаб/валюту или forbiddenpair.
- Для неподтверждённого paid устанавливатьunknown и явный вопрос в этой строке.
 Неподтверждённая/неоднозначная дата становитсяnull+вопрос; неподтверждённое или
 противоречивое направление становитсяnull+вопрос. Ни одной новой даты/суммы/
 валюты/paid/направления не вычислять и не подставлять.
- Если направление и разрешённая статья несовместимы, статья становитсяnull+
 вопрос. Неизвестный/чужой ID статьи по-прежнему критическая ошибка.
- Использовать только существующие machinecodes:paid_unanchored,date_unanchored,
 date_ambiguous,date_question,direction_contradiction,direction_ambiguous,
 direction_question,category_direction,execution_question,grouping_question,
 context_total_amount и вспомогательныйambiguous_occurrence. Остальные коды
 не переводить в успешный черновик.
- После понижения unsupportedполей повторно проверить строку; удалять её как
 справочный итог только если она остаётсяcontext_total_amount во всех привязках
 без других ошибок, кроме вспомогательногоambiguous_occurrence. Такой код
 допустим только при доказанном отсутствии чистой привязки у этой строки;
 независимая коллизия строк остаётся ошибкой итогового полногоverify. При совпадении того же числа с настоящим платежом чистая
 привязка сохраняется. Удаление предложенной строки отражается общим вопросом;
 это не удаление финансовой операции, денег в ai-serviceнет.
- При нескольких оставшихся кандидатах добавить явный вопрос о группировке,
 если преобразование затронуло набор/поля или исходно отсутствовал вопрос.
- После преобразования полныйverify остаётся обязательным. Коллизия денежных
 occurrence, чужие ID и другие оставшиеся ошибки всё равно отклоняют результат.
- Не мутировать исходныйoutput. Вопросы не обрезать и не заменять: если явный
 новый вопрос не помещается в лимит50, вернуть исходный результат для отказа.
 Correction/no_payment/невалидныйtarget не ремонтировать. HIGH/manual Confirm
 остаётся неизменным. В Telegram уже есть прямой ответ «оплачено» с actualactor,
 который меняет paid_confirmedвCashбез LLM — подготовка не блокирует этот путь.

Promptv4/schema/coregateway/PHPконтракт неизменны; новые runtime source/hash и
ADR фиксируют изменение алгоритма. Старые live-результаты не пересчитываются:
rawответы не сохранялись. Новый live-run потребует отдельного оставшегося
согласования лимита/подготовленного объёма после завершения локальной работы.
