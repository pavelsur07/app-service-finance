# Telegram Payment Intake — план реализации

Статус: **план для согласования; реализация не начата**.
Дата: 13 ноября 2026. Класс будущей реализации: **Large**.

**Цель:** из свободного текста с сокращениями получать проверяемый черновик
одного или нескольких платежей, предлагать статью ДДС, проект и ЦФО и
сохранять операции только после подтверждения пользователя.

**Архитектура:** новая задача `parse_payment_message` внутри существующего
Python `ai-service`; субмодуль PaymentIntake внутри Symfony Cash; Telegram
как адаптер. Symfony владеет контекстом, правами, черновиками и записью ДДС.
Python возвращает предложения по контракту через существующий ServiceGateway.

**Стек:** Python 3.12, Pydantic v2, Decimal, pytest, существующий LLM gateway;
PHP/Symfony, Doctrine/PostgreSQL, Messenger, существующие Telegram и Cash.

**Основание:** [описание сценария](README.md),
[41 исходный пример после обезличивания](examples/messages.jsonl),
переписка с владельцем, `AGENTS.md`, `services/ai-service/AGENTS.md`,
`docs/architecture/service-gateway.md`.

**Исполнение:** после отдельного поручения на реализацию — навык
`executing-plans` для последовательного исполнения либо
`subagent-driven-development` при выбранной работе с агентами. Репозиторный
workflow имеет приоритет: Work item не является отдельным Stage или review gate.

## 1. Границы первой версии и решения

Текущая приёмка реализации ведётся в спецификациях и отчётах этапов:
[Stage 1](stages/stage-1.md), [Stage 2](stages/stage-2.md),
[Stage 3](stages/stage-3.md), [Stage 4](stages/stage-4.md),
[Stage 5](stages/stage-5.md). Исходные чек-листы ниже сохраняют требования;
отметки и доказательства фактической приёмки находятся в соответствующем
`stage-N-spec.md` и отчёте. Live-модель и включение пилота не приняты по stub.

Включены: только текст, сокращения, несколько денежных упоминаний, общие
указания для нескольких строк, предложение аналитики из справочников,
редактирование черновика, уточнение и подтверждение.

Фото, OCR, обучение собственной модели и новый отдельный Python-сервис
в эту итерацию не входят. Исправление проведённой операции через свободный
текст предлагается отложить: бот узнаёт намерение, предлагает открыть
существующую операцию, но не выбирает и не меняет её молча.

Решения, требующие согласования бизнес-смысла в Stage 1:

| Вопрос | Предложение для v1 | Что зависит от решения |
|---|---|---|
| Факт или будущая оплата | Сохранять только подтверждённый факт; будущую оплату распознавать и объяснять ограничение | Допуск к записи и сценарии календаря |
| «120», «-10» без масштаба | Уточнять рубли/тысячи, не обучаться на старой сумме в БД | Нормализация и готовность черновика |
| Несколько сумм одной услуги | Уточнять отдельные платежи или части одного; не суммировать автоматически | Группировка строк и распределения |
| Один платёж с несколькими статьями | В v1 запросить явное распределение через существующий механизм Cash либо оставить черновик незавершённым; выбрать один вариант до Stage 3 | Объём сохранения и тесты разбивок |
| Неизвестны проект/ЦФО/статья | Следовать обязательности текущей модели Cash; согласовать, какие поля обязательны именно для бота | Проверка ready |
| Отсутствуют дата/валюта/счёт | Разрешённые значения из выбранной кассы и даты сообщения показывать как подставленные; неоднозначность уточнять | Контекст и предпросмотр |
| «Оплатила сотрудница», личная карта | Уточнять источник денег и факт компенсации, не создавать компенсацию автоматически | Денежный счёт и учёт задолженности |

Эти вопросы не мешают подготовке контракта и тестов с результатом
`needs_clarification`. Зависимую финансовую логику до ответа не реализовывать.

## 2. Инварианты и границы ответственности

- `companyId` определяется Symfony из авторизованной привязки, никогда из
  текста/ответа модели. Все чтения и записи ограничены компанией.
- Только Symfony сохраняет ДДС. Python не имеет доступа к БД Symfony,
  самостоятельно не получает справочники и не отправляет сообщения Telegram.
- Пользовательский текст — данные. Инструкции внутри него не могут расширить
  справочник, поменять компанию или инициировать запись.
- Модель извлекает смысл; код проверяет денежные выражения. Деньги — строки
  десятичного формата/Decimal; точность валют берётся из действующего Cash.
- Каждое извлечённое значение имеет источник: фрагмент текста, контекст,
  правило или ручное решение. Процент модели не является вероятностью ошибки
  и не открывает автосохранение.
- Время для «вчера» фиксировано исходным сообщением и часовым поясом.
  Повтор задачи через сутки не меняет дату.
- Одно входное сообщение не равно одной операции. Число денежных упоминаний
  также не равно числу платежей. Неоднозначное распределение уточняется.
- Ручной выбор не перезаписывается поздним ответом модели или автоправилом.
- Ответ модели со старой версией черновика не применяется к новой версии.
- Успешное подтверждение атомарно: все выбранные валидные строки и отметка
  подтверждения сохраняются вместе. Частичный успех не маскируется общим «готово».
- Идемпотентность удерживается уникальными ограничениями БД, не проверкой
  «есть ли запись» перед INSERT. Повтор подтверждения возвращает прежние ID.
- Первое принятие `(bot, chat, message)` закрепляет маршрут company/draft
  независимо от последующего переключения компании. Повтор и edited-message
  используют этот маршрут с повторной проверкой прав; не раскрывают чужой draft.
- Исходные тексты и реквизиты не попадают в обычные логи; маскирование и TTL
  ai-service сохраняются. Срок хранения черновиков согласовать в Stage 1.

Это будущие пути/имена, а не уже существующие классы.

| Область | Файлы / назначение |
|---|---|
| Контракт | `services/_contracts/ai-parse-payment-message/v1/schema.json`, `README.md`, `examples/`, `CHANGELOG.md` |
| Python | `services/ai-service/src/ai_service/tasks/parse_payment_message/{schemas.py,task.py,checks.py,prompts/v1.md}` |
| Регистрация | Существующие `tasks/registry.py`, `config/routes.yaml`, API/parser конверта задачи — только необходимые изменения |
| Eval | `services/ai-service/evals/parse_payment_message/`; `tests/unit/test_parse_payment_message.py`, `tests/evals/test_parse_payment_message_evals.py` |
| Черновики | `site/src/Cash/Entity/PaymentIntake/`, `Repository/PaymentIntake/`, `Enum/PaymentIntake/`; миграция с новым номером |
| Сценарии | `site/src/Cash/Application/PaymentIntake/`: Request, Amend, Confirm, Cancel Actions; сервисы проверки и подготовки контекста рядом с существующими Cash-сервисами |
| DTO | `site/src/Cash/Application/DTO/PaymentIntake/` — доступные через границу модуля типы |
| Cash API | Расширить `site/src/Cash/Facade/CashFacade.php`; обновить `ARCHITECTURE.md` |
| Результат ИИ | `PaymentIntakeResultConsumer` в Cash реализует существующий `AiTaskResultConsumerInterface` |
| Telegram | Обработчики текста/callback, адаптер запросов и представление черновика в `site/src/Telegram/` |
| Тесты PHP | `site/tests/Unit/Cash/PaymentIntake/`, `Integration/Cash/PaymentIntake/`, `Functional/Telegram/` |

Предлагаемый контракт Facade:

```text
requestPaymentIntake(RequestPaymentIntakeCommand): PaymentIntakeDraftView
getPaymentIntakeDraft(companyId, actorId, draftId): PaymentIntakeDraftView
amendPaymentIntakeDraft(AmendPaymentIntakeCommand): PaymentIntakeDraftView
confirmPaymentIntakeDraft(ConfirmPaymentIntakeCommand): PaymentIntakeConfirmation
cancelPaymentIntakeDraft(companyId, actorId, draftId, expectedRevision): void
```

Команды обязательно несут `companyId`, авторизованного `actorId` и ключ повтора;
изменяющие существующий черновик — `draftId` и `expectedRevision`.
`Request` также содержит источник `(bot, chat, message)`, исходный текст,
время, timezone, выбранный счёт. `Amend` ссылается на стабильные ID строк и
поля; номера строк из текста переводятся в ID на текущей ревизии.
`Confirm` содержит выбранные ID строк; остальные строки явно исключены
пользователем, а не теряются при валидации. Повторное сохранение исключённых
строк из уже подтверждённого черновика не допускается.

Вход Python: текст, reference time/timezone, ограниченный контекст черновика,
справочники и разрешённые связи, релевантные примеры компании.
Выход: `intent`, кандидаты, предложения изменений, вопросы и доказательные
фрагменты. У кандидата — локальный ref модели, денежное выражение,
направление, дата, назначение, аналитика и статус исполнения
`paid|planned|unknown`. Стабильные ID назначает Symfony. Неизвестные поля
представляются `null`; отсутствие платежей — валидный пустой результат.

## 5. Stage 1 — согласованный контракт и проверяемые примеры

**Risk:** MEDIUM. **Зависимости:** Phase 0.
**stage_base_commit:** записать перед первым Work item.
**Результат:** PHP и Python могут независимо реализовать один сценарий;
известно, когда нужно уточнение, а когда разрешён черновик с готовыми полями.

### Work items

- [ ] **1.1. Разметить корпус.** Проверить все 41 текста и partial annotations.
  Для каждого задать извлечённые факты, неоднозначности и запрещённые догадки.
  Не переносить старую сохранённую сумму/аналитику как правильный ответ.
- [ ] **1.2. Согласовать решения §1.** Записать ответы и примеры применения;
  нерешённое оставить явно открытым, без скрытых умолчаний.
- [ ] **1.3. Описать и проверить JSON Schema.** Определить intent, кандидатов,
  правки, вопросы, nullable-поля, источники значений и ошибки. Пределы входа
  предложены: 16 000 Unicode-символов и 50 кандидатов; превышение возвращает
  понятную ошибку, текст/платежи не обрезаются. Уточнить лимиты справочников
  на основе действующих методов без потери доступных вариантов.
- [ ] **1.4. Проверить совместимость конверта `ai-task`.** Изучить schema/API/
  PHP parser: можно ли зарегистрировать новый тип без изменения опубликованной
  версии. Если нет — новая версия конверта с поддержкой старой; существующий
  v1 не переписывать. Решение и затронутые файлы закрепить до Stage 2.
- [ ] **1.5. Подготовить synthetic directories и отдельные диалоги.** Компании
  A/B, одинаковые названия с разными ID, запрещённая пара проект–ЦФО,
  архивная статья, отсутствующий счёт. Реальные строки корпуса не считать
  одной перепиской. Примеры для промпта и holdout разделить по семействам,
  чтобы похожие аренда/комиссия не утекали между выборками.

### Приёмка Stage 1

- [ ] Все 41 записи валидны, ID уникальны, все размеченные фрагменты есть в тексте.
- [ ] Есть отдельные случаи: номера списка, количество людей, несколько сумм,
  «плюс», тысячи словами, справочный итог, исправление, личная карта, будущая оплата.
- [ ] Для «120», «-10», группировки 600/1700 записаны вопросы, а не выдуманные ответы.
- [ ] Решение по факту/плану и обязательным полям явно зафиксировано или отмечено
  как зависимость, блокирующая только соответствующую реализацию.
- [ ] Примеры контракта принимаются schema; неверные типы, лишние поля,
  превышение лимитов и невалидные десятичные строки отвергаются тестами.
- [ ] Определены формат fragment references и проверка Unicode: цитата и
  указатель однозначно относятся к оригинальному тексту, а не к нормализованной копии.
- [ ] Новая версия не ломает `echo` и `categorize_transactions`.

**Checks:** JSON/schema validation, контрактные тесты Python/PHP без LLM.
**Reviewer focus:** скрытые финансовые предположения, неполная разметка,
совместимость конверта, утечка данных и тестовых ответов в промпт.

## 6. Stage 2 — распознавание внутри Python ai-service

**Risk:** HIGH-LOCAL — контракт и извлечение финансовых значений.
**Зависимости:** контракт Stage 1; нерешённое возвращает needs_clarification.
**stage_base_commit:** записать перед первым Work item.
**Результат:** входной текст превращается в проверенный структурированный
результат; интеграция не пишет ДДС.

### Work items

- [ ] **2.1. Схемы и регистрация.** Сначала тесты нового task_type и версий,
  затем `schemas.py`, `task.py`, registry и маршрут существующего gateway.
  Пользоваться TaskSpec, существующими очередью, бюджетом и retry.
- [ ] **2.2. Извлечение смысла.** `prompts/v1.md`: полный текст, роли чисел,
  общие указания, intent correction, неизвестные значения и инструкция
  игнорировать команды внутри пользовательских данных. Один вызов модели
  на разбор в нормальном случае; дополнительные вызовы только по измерениям.
- [ ] **2.3. Детерминированная проверка.** Проверить цитаты, нормализацию денег,
  валюту, относительные даты, refs кандидатов, ID справочников и допустимые
  связи. Маскирование ПДн не должно менять денежные выражения или разрушать
  сопоставление фрагментов; проверить отображение маскированного текста на оригинал.
- [ ] **2.4. Неуспешные ответы.** Структурная ошибка, обрыв, отказ провайдера,
  timeout, исчерпанный бюджет и unsupported task имеют явный результат.
  Неполный ответ не становится успешным черновиком; retry ограничен существующей
  политикой, нет бесконечных попыток «добиться JSON».
- [ ] **2.5. Eval.** Подключить размеченный корпус и synthetic cases.
  Отдельно оценивать границы, суммы, направления, даты, аналитику и уточнения;
  отчёт содержит N, numerator/denominator, ошибки, модель и версию промпта.

### Приёмка Stage 2

- [ ] `1. Аренда ... 25 200` не отдаёт 1 как сумму; `10 человек ... 10 000`
  не отдаёт 10 как сумму. «Итого 11» не становится новой выплатой.
- [ ] `20 тысяч`, `6 тыс`, `1700р`, `1 018` нормализуются кодом без float.
- [ ] Две денежные суммы не теряются; неизвестная группировка остаётся вопросом.
- [ ] «Плюс 79000» распознаётся как inflow; неизвестное направление не становится
  расходом только потому, что старая реализация так делала.
- [ ] «Вчера» одинаково разрешается при retry на следующий день.
- [ ] Исправление не выдаётся как новый платёж; инструкция «игнорируй правила»
  не открывает произвольные ID, компании или инструменты.
- [ ] Невалидный ID, отсутствующее доказательство суммы и невозможная пара
  проект–ЦФО не проходят проверки как готовые значения.
- [ ] Unit/contract тесты работают без сети; отдельно видно, какие проверки
  используют stub и какие подтверждены живой моделью.
- [ ] Предлагаемый порог пилота: критические сценарии проходят без опасных
  догадок; на holdout не менее 95% точных сумм/направлений однозначных кандидатов.
  Показывать также долю корректно найденных кандидатов и долю уточнений, чтобы
  ответ «всегда уточняй» не считался успехом. Порог согласовать в Stage 1.
- [ ] Live eval проводится только при разрешённом внешнем вызове; без него
  честно отмечено, что реальная точность модели и задержка не проверены.

**Checks:** targeted pytest нового модуля, затем `make ai-service-lint`,
`make ai-service-test`, `make ai-service-evals` для закрытия Python Stage.
**Reviewer focus:** происхождение сумм, false confidence, маскирование,
сокрытие пропущенных платежей, деградация других задач.

## 7. Stage 3 — черновики и сохранение в Cash

**Risk:** HIGH-LOCAL — миграция, транзакции, финансовая запись.
**Зависимости:** Stage 1; consumer проверяется результатами Stage 2/stub.
**stage_base_commit:** записать перед первым Work item.
**Результат:** сценарий работает через Cash Facade независимо от Telegram.

### Work items

- [ ] **3.1. Хранение.** Draft, Item и долговечный запрос разбора: companyId,
  source key, author, selected account, reference time, revision, status,
  source/evidence, ручные значения, taskId и сохранённые transaction IDs.
  Unique источника в компании, unique строки подтверждения, индексы
  `(company_id, status)` и всех добавленных FK. Сроки хранения и удаления
  совместить с существующим удалением компании.
  Для Telegram дополнительно долговечно закрепить первоначальный маршрут
  источника с уникальностью `(bot, chat, message)` независимо от выбранной
  компании. Получение содержимого всегда проверяет actor и company;
  уникальный конфликт не должен раскрывать данные недоступной компании.
- [ ] **3.2. Постановка и восстановление.** В одной DB-транзакции сохранить
  черновик и pending request с заранее рассчитанным taskId через `taskIdFor`.
  После commit — существующий `requestTask`. Recovery повторяет pending request
  с тем же неизменным payload/key. Нужен проверяемый recovery-вход и план его
  расписания; изменение production scheduler требует отдельного разрешения.
  Ключ нового разбора: `(draftId, revision, parseAttempt)`. Повтор доставки
  сохраняет key/taskId/payload; явный повтор после terminal failure создаёт
  следующую попытку, edited-message — новую revision. Consumer принимает
  только текущую попытку текущей ревизии.
- [ ] **3.3. Consumer и состояния.** Применять результат только к совпавшим
  company/task/revision. Consumer только persist, коммитом и ack управляет
  `ImportAiResultsAction`. Поздний/повторный ответ — безопасный no-op с причиной.
  received → parsing → needs_clarification|ready; подтверждение только из ready;
  failed допускает явный повтор, cancelled/confirmed не открываются поздним ответом.
- [ ] **3.4. Аналитика и правки.** Переиспользовать действующий matcher/planner
  Cash и проверки project–ЦФО, не создавать второй набор правил. Явный ручной
  выбор важнее модели; конфликт с правилом показывается. Amend проверяет revision,
  меняет только указанные поля и повторно валидирует зависимые поля.
- [ ] **3.5. Confirm.** Заблокировать черновик, проверить права, company,
  revision, статус исполнения, валюту, период и актуальность справочников.
  Установить idempotency на стабильные строки. Проверить существующий путь
  `CashFacade::createTransaction` на внутренние commit/flush и события:
  пакет должен иметь одного владельца транзакции и долговечные side effects.
  Если текущий путь не позволяет это, минимально выделить общую операцию
  сохранения внутри Cash с регрессионными тестами старого пути.

### Приёмка Stage 3

- [ ] Миграция проходит на local/test; schema sync и индексы проверены;
  существующие операции и их суммы миграция не меняет.
- [ ] Другой пользователь/компания не может прочитать, изменить или подтвердить
  черновик, в том числе через угаданный ID строки.
- [ ] Падение между commit и requestTask восстанавливается без нового черновика.
- [ ] Повтор результата и сбой ack не удваивают строки и учёт расхода ИИ.
- [ ] Ответ на старую revision не стирает исправление пользователя.
- [ ] Failed → явный retry создаёт новую попытку; повтор доставки этой попытки
  не создаёт третью. Ответ предыдущей попытки не применяется.
- [ ] Два одновременных Confirm создают один набор операций с теми же ID.
- [ ] Гонка Amend/Confirm не сохраняет незаметно устаревший вариант.
- [ ] Ошибка на второй строке откатывает весь выбранный пакет и подтверждение;
  повтор после устранения причины безопасен.
- [ ] Архивация статьи, закрытие периода, отзыв прав или отключение компании
  после preview проверяются повторно и дают понятный отказ.
- [ ] Ручная аналитика сохраняет provenance и не перезаписывается автоправилами.
- [ ] Cancel не создаёт операции; source key не совпадает с legacy externalId.
  Семантически похожие платежи отмечаются как возможный дубль, но не удаляются.
- [ ] Публичные Facade/DTO, владение транзакцией и состояния описаны в ARCHITECTURE.

**Checks:** unit/integration Cash PaymentIntake, concurrency на настоящем test
PostgreSQL, тесты старого createTransaction, focused PHPStan/CS, schema sync.
**Reviewer focus:** company isolation, потеря задачи, stale result, вложенные
commit, события после commit, ledger duplicates, миграция и удаление компании.

## 8. Stage 4 — Telegram-диалог и получение результата

**Risk:** HIGH-LOCAL — webhook, права и Messenger.
**Зависимости:** Stage 2 и Stage 3.
**stage_base_commit:** записать перед первым Work item.
**Результат:** пользователь проходит полный сценарий в Telegram.
Новый веб-интерфейс в этом Stage не создаётся.

### Work items

- [ ] **4.1. Адаптер.** Сохранить /start, /set_cash и отчёты; новые тексты для
  включённого сценария отправлять через CashFacade. Не запускать одновременно
  legacy создание операции и новый разбор. При отключённом ИИ явно сообщать
  о недоступности, не переходить молча к опасному парсеру первой цифры.
- [ ] **4.2. Быстрый pull.** Переиспользовать gateway client/parser/consumer/ack.
  Для интерактивных запросов добавить получение результата по taskId в рамках
  версии контракта Stage 1, если текущий API этого не умеет. Ожидание — через
  отложенные короткие Messenger-задания на существующем transport, без sleep
  в webhook/worker. Ограничить время ожидания и HTTP timeout; общий импорт
  остаётся fallback. Исключить лишние опросы разных пользователей одной задачи.
- [ ] **4.3. Представление.** Карточка каждой строки: сумма, направление, дата,
  касса, назначение, статья, проект, ЦФО, вопросы и подставленные значения.
  Кнопки исправления, исключения строки, подтверждения выбранного и отмены.
  Длинный список выводить частями с сохранением stable ID, не обрезать хвост.
- [ ] **4.4. Диалог.** Ответ на вопрос связывать с draft/item/revision.
  Несколько открытых черновиков — явный выбор, не «последний в компании».
  Edited-message до подтверждения — новая ревизия; после подтверждения —
  уведомление и переход к отдельному сценарию, без тихого изменения ДДС.
- [ ] **4.5. Доставка уведомлений.** Фиксировать необходимость ответа долговечно;
  повтор отправки не повторяет Confirm. Различать сохранение платежей и
  успешную отправку ответа Telegram: timeout Telegram не откатывает уже
  подтверждённые деньги и не предлагает создать их заново.

### Приёмка Stage 4

- [ ] Поддельный webhook, чужой callback и отозванная привязка не запускают разбор/запись.
- [ ] При нескольких компаниях выбранная company/cash сохраняется однозначно;
  существующий отказ при нескольких привязках не переносится в новый сценарий.
- [ ] Обычное сообщение → статус обработки → черновик → подтверждение работает.
- [ ] Нумерованный список из корпуса показывает все кандидаты и вопросы;
  нет операции на номер пункта или количество участников.
- [ ] «Измени на 20000» и «у второго проект…» изменяют только явно выбранный
  черновик; без цели задаётся уточнение.
- [ ] Сбой модели, бюджет, timeout и недоступность сервиса имеют различимые
  сообщения и безопасный retry. Получение результата не зависит исключительно
  от периодического cron через несколько минут.
- [ ] Повтор webhook/callback, поздний callback и повтор доставки не создают дубли.
- [ ] Сообщение принято в A → пользователь выбрал B → повтор/редактирование
  исходного сообщения не создаёт draft в B. Обращение к A снова проверяет
  права и не раскрывает её данные при отзыве доступа.
- [ ] Edited-message создаёт новую revision и новый запрос разбора; повтор
  того же edit не создаёт ещё одну revision/попытку.
- [ ] Бот корректно экранирует текст/названия, не выполняет пользовательскую разметку.
- [ ] Длинный текст/список не теряет строки; превышение лимита даёт объяснение.
- [ ] Отправка ответа не удваивает операции при timeout Telegram.
- [ ] /start, /set_cash, отчёты и прежние разрешённые сценарии проходят регрессию.

**Checks:** Functional Telegram с mock HTTP/LLM, integration Cash + gateway,
Messenger routing/retry, ручной полный диалог на разрешённой тестовой среде.
**Reviewer focus:** выбор компании, callback tampering, потеря контекста,
конкуренция импорта/быстрого pull, доставка ответа и двойной legacy-путь.

## 9. Stage 5 — общая приёмка и подготовка выпуска

**Risk:** HIGH-LOCAL. **Зависимости:** Stage 1–4.
**stage_base_commit:** записать перед первым Work item.
**Результат:** отдельно доказанная готовность интеграции и качество живой
модели, затем конкретный запрос на выпуск. Без разрешённого live eval
интеграцию можно принять по stub, но качество распознавания и готовность
включить пилот остаются неподтверждёнными; Stage 5 полностью не закрывается.

### Work items

- [ ] **5.1. Сквозной прогон.** Зафиксировать версии кода, схемы, промпта,
  модели, набора. Пройти матрицу ниже и собрать результаты без ПДн.
- [ ] **5.2. Отказы и нагрузка.** Воспроизвести падение после commit, потерю ack,

## 11. Как закрываем этапы и выпускаем

После Work item — targeted checks, focused review и checkpoint. После Stage —
module checks, полный diff от stage_base_commit, Stage Report, commit/push и
обновление одной Draft PR; между этапами ручных approval gate нет.
HIGH-LOCAL Stage с diff >500 строк требует external review; общий handoff —
обязательно. На этапе только планирования эти действия не запускаются.

Выпуск после реализации: Ready PR и единый запрос merge + deploy. Поскольку
ожидается миграция, перед запросом прочитать `docs/workflow/release.md` и
запросить также отдельный migration dispatch. Изменения production scheduler,
workers, инфраструктуры/доступов и любые ручные processing-команды перечислить
по имени и согласовать отдельно. Ни один из этих шагов не разрешён одним
фактом согласования плана.

После разрешённого выпуска — дождаться CI/deploy, выполнить read-only
post-deploy checks через разрешённые wrappers. Живые тестовые сообщения
и создание операций на production требуют явного согласования соответствующего
сценария; миграционный smoke в тестовой среде этого не заменяет.
