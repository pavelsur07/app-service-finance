# Ночной контроль качества PaymentIntake — ТЗ и план

Статус: владелец согласовал реализацию 14 ноября 2026, ночной лимит30рублей
и месячный900рублей. Реализация начата; runtime-код и production scheduler
ещё не включены. Автоотключение отдельно не согласовано и в v1 не реализуется.
Это дополнение к плану качества, а не продление четырёх разовых проходов.

## Задача и ограничения

Ночной прогон обнаруживает регрессию на эталонах. Проверка каждого входящего
ответа и ручной Confirm защищают обработку новых сообщений в течение суток.
Нельзя выдавать успешный nightly run за гарантию правильности любого ответа.

Сейчас есть 41 development message с partial annotations, 12 synthetic cases
с 13 явно ожидаемыми строками, общий pipeline, strict verifier и два scorer.
После исправлений три последовательных прохода одной версии прошли все
измеряемые метрики. Это baseline регрессий, не независимый holdout.
Источник результатов: [четыре прохода](live-eval-four-passes-2026-11-14.md).

Регулярные проверки и human feedback соответствуют рекомендациям
[OpenAI по evaluation](https://developers.openai.com/api/docs/guides/evaluation-best-practices).
Зависимость от алиаса существенна: DeepSeek описывает обновление модели при
сохранении имени `deepseek-flash` в [официальном changelog](https://api-docs.deepseek.com/updates/).
Не обещать доступность фиксированного provider snapshot без проверки поддержки.

## Выбранный подход

Рассмотрены только offline tests, только ночной живой canary и их сочетание.
Offline не замечает изменения внешней модели; ночной canary без runtime checks
не защищает новые сообщения между запусками. Выбрано сочетание трёх уровней:

1. **Каждый ответ:** существующие schema, money/source evidence, ID/company,
   пары проект–ЦФО, privacy, date/paid и idempotent Confirm. Неизвестные поля
   остаются вопросами. Ни nocturnal score, ни самооценка модели в процентах
   не разрешают автоматическую запись денег.
2. **На изменении кода и ночью:** deterministic tests и живой canary через
   фактическую рабочую конфигурацию ai-service/gateway. Ночной запуск проверяет
   deployed image/prompt/schema/verifier/preparer, а не свежую неподнятую ветку.
3. **Независимое качество:** отдельно размеченные новые реальные обезличенные
   примеры с подтверждёнными справочниками. Не использовать их для prompt tuning;
   после использования при настройке переносить в regression и заменять holdout.
   Новые случаи ошибок добавлять после проверки человеком; не переписывать gold
   по новому ответу модели. Синтетические мутации и новые real cases различать.

## Ночной сценарий

Предлагаемое время — 03:00 Europe/Moscow; точное время выбирается с учётом
существующих заданий scheduler. Один запуск в сутки, последовательные запросы,
lock/lease и дедупликация по дате, задаче, deployed version и manifest.

- Preflight проверяет конфигурацию маршрута/модели, доступность fixtures,
  hashes, свободный бюджет, отсутствие предыдущего active run и разрешение
  технического eval. Второй ключ не требуется, но бюджет eval учитывается
  отдельно от бизнес-запросов компаний.
- Сначала deterministic tests инвариантов и scorer. Затем полный source41 +
  synthetic12. Повторы наиболее нестабильных critical cases допускаются только
  в выделенном call/token/time/budget cap. Повтор не стирает исходный FAIL.
- Сравнение семантическое: деньги до копейки, currency/direction/date/status,
  ID и допустимые пары, missing/extra candidates, expected-null/уточнения.
  Полный текст JSON и формулировка вопроса не обязаны совпадать побайтово.
- Раздельно сохраняются dataset/family/field fractions с denominator, число
  проверенных/ожидаемых cases, rejections, unsafe passes, вопросы/abstention,
  preparation rate, provider failures, tokens/cost estimate и p95.
  `needs_review=100%` нормально для HIGH risk, это не ошибка.
- Отчёт содержит run ID, deployed image, commit, prompt/schema/scorer/dataset/
  verifier/preparer hashes, выбранный model alias и доступную идентичность ответа
  провайдера. Совпадение alias не доказывает неизменность весов модели.
- Сохраняется immutable metadata-only report и last-success/last-run статус.
  Успех означает полный прогон нужной версии/набора, не просто exit0 или наличие
  файла. Исчерпанный бюджет, N=0, missing fixtures, timeout и пропуск запуска
  не считаются PASS. Падение мониторинга не должно блокировать ручные операции.

## Метрики и реакция

Финансовые и контрактные ограничения проверяет код. LLM-as-judge допустим
впоследствии только как вспомогательная оценка понятности вопросов, сверенная
с оценками человека; он не устанавливает правильную сумму или компанию.

| Сигнал | Смысл | Предлагаемая реакция |
|---|---|---|
| Unsafe accepted output: чужой ID/company, неверная сумма пропущена проверкой, privacy leak, duplicate write | Критическая ошибка защиты | Один ERROR; блокировать новые AI-предложения этой задачи/маршрута по заранее утверждённой политике, оставить ручной ввод и существующие черновики |
| Точный gold не совпал, либо валидный пример rejected | Качество ухудшилось, финансовая защита могла сработать правильно | Отчёт FAIL с case IDs/полями; уведомление, ограниченный диагностический повтор в бюджете; исправление и новый immutable report |
| Provider timeout/429/5xx, неверный ключ | Проверка недоступна, качество не измерено | Отдельный UNAVAILABLE, bounded retry/backoff; не смешивать с точностью распознавания |
| Нет полного свежего run | Мониторинг не отработал | Отдельный freshness alert после согласованного срока, например 36 часов |
| Бюджет закончился | Штатный запрет новых запросов | SKIPPED_BUDGET и предупреждение; не «качество хорошее» |

Порог unsafe accepted output — 0 допустимых нарушений. Для существующей небольшой
fixed regression suite предлагается exact agreement100% по её размеченным
ожиданиям; доля и знаменатель видны отдельно, недостаточную выборку не скрывать
за общим95%. Пороги больших real datasets и частоту алертов утвердить отдельно.
Наличие вопроса не оценивает его качество; unknown вместо ожидаемого значения
считается промахом соответствующего gold, а не автоматически успехом.

Один агрегированный алерт на task/model/version/failure signature в существующий
GlitchTip; повторы дедуплицируются, восстановление отмечается отдельно. Проверять
текущий прогон/свежесть, не краснить бессрочно из-за суммы исторических ошибок.
Реакция исправима конкретным действием: поправить код/prompt, восстановить
provider/scheduler, подтвердить новую разметку или согласовать лимит.
Согласуется с [health-gates](../../workflow/health-gates.md).

Автоматически не менять prompt, gold, маршрут, модель или финансовые правила,
не перепроводить операции. Политика блокировки только данной задачи/маршрута
ещё не реализована и требует отдельного согласования; не выключать все AI задачи
из-за одного некритического несовпадения canary.

## Размещение в существующей архитектуре

Вычисление остаётся Python-субмодулем внутри ai-service. Переиспользуются
`ai_service.evals.payment_intake`, semantic scorer, Pipeline и gateway.
Нового отдельного сервиса и внешней платформы eval для v1 не требуется.

Плановый запуск — через существующий Symfony scheduler/supercronic:
короткая команда ServiceGateway инициирует техническое async задание;
Python выполняет, Symfony забирает статус/метрики по pull. Аутентификация,
timeouts, job states и read model — по
[service-gateway](../../architecture/service-gateway.md).
Длинные модельные запросы не выполнять внутри короткой cron-команды.

Повторное использование бизнес-очереди ai_task с фиктивной компанией без
отдельного технического контракта не допускается. Не передавать eval output
в Cash consumer/Telegram и не создавать drafts/transactions от nightly run.
Конкретное хранение technical job/дедупликации выбирается по существующим
контрактам до реализации; не добавлять новый framework или зависимость.

**Выявленный prerequisite:** текущий payment eval ориентирован на checkout и
читает source corpus из docs, а schema/source hashes — из файлов репозитория.
Runtime Docker image копирует `/app/evals`; source docs/schema пути checkout
не гарантированы. До scheduler нужно упаковать immutable runtime fixtures и
manifest с проверяемым происхождением, использовать `AI_SERVICE_EVALS_DIR` и
протестировать установленный wheel/runtime image без checkout mounts. Один
canonical dataset + проверенная сборка snapshot, без ручных расходящихся копий.
Ночной job использует обычный установленный код deployed image; одноразовый
root-SSH механизм прошлых eval не является постоянным решением.

## Бюджет и данные

Согласованы 30 рублей в сутки и 900 рублей в календарный месяц Europe/Moscow.
Технический call cap — до82вызовов на ночной job; неизвестный расход остаётся
зарезервированным. Ручные дополнительные платные прогоны без отдельного объёма
не запускаются. Прежнее root-SSH исключение четырёх eval закончено.
Ориентир только по измерению 14 ноября: 53 запроса одной версии стоили примерно
5.3 рубля по token estimate; это не обещание будущего счёта или фиксированная цена.
Учитываются schema retries, повторы critical cases и аварийный резерв.

Текущий BoundedAdapter накапливает максимальные резервы всех calls. Нельзя
выбрать маленький nightly budget исходя только из фактических5.3 рубля: при
текущих65536 input/16000 output верхний резерв одного запроса3.1929024 рубля.
До включения выбирается и тестируется политика: подходящий суммарный резерв
либо reserve→settle известной usage с fail-closed для неизвестного расхода.
Бюджет глобальный для всех частей одного job, дневной и месячный ledger атомарны;
части набора не получают каждая новый полный лимит. При неучтённой попытке
повтор запрещён до сверки; 429 не запускает бесконечные ретесты.

Fixtures — обезличенные/синтетические, не случайные вчерашние сообщения клиентов
без проверенной разметки. Raw payload/output, ПДн, токены и финансовые значения
не попадают в операционные логи. Пользовательские правки могут давать сигнал
для отдельной проверки, но не автоматически становиться истиной/новым gold.

## Этапы и чек-листы приёмки

### 1. Runtime-ready regression и правила оценки

- [ ] ТЗ фиксирует dataset/version/provenance, критические случаи и пороги.
- [ ] Тесты до кода: missing assets/schema/hash, wrong-intent, extra/missing rows,
  ambiguous/null, source occurrence, fake green при N=0/partial run.
- [ ] Installed wheel/runtime image без checkout проходит offline preflight.
- [ ] Источник данных и scorer единые; модель не получает expected values.
- [ ] Базовый nightly manifest повторяет существующие source41/semantic12 метрики.

### 2. Ограниченный технический live job и статус

- [ ] До кода RED-тесты на lock/concurrent runs, budget reserve/settle, unknown
  usage, retries, lease/timeout/restart и честные PASS/FAIL/UNAVAILABLE/SKIPPED.
- [ ] Job вызывает ту же deployed задачу/route и пишет immutable safe report.
- [ ] Нет доступа к бизнес-данным компаний и вызовов Cash/Telegram consumer.
- [ ] Короткая gateway-команда + async/pull контракт, права и read model проверены.
- [ ] Дневной/месячный общий бюджет и coverage/freshness видны; не скрыт skipped run.
- [ ] Локальные gates и независимый review без открытых BLOCKER/IMPORTANT.

### 3. Расписание, наблюдаемость и выпуск

- [ ] Именованно согласованы постоянный scheduler, суточный/месячный/call лимиты,
  окно запуска, alert policy и реакция на critical regression.
- [ ] Изменения scheduler/CI/production config предъявлены как конкретный diff;
  AGENTS.md §3.3 соблюдён. Разрешение четырёх проходов не переиспользуется.
- [ ] Monitor-of-monitor: пропуск запуска и missing complete report дают сигнал.
- [ ] Один агрегированный алерт, дедупликация и восстановление проверены тестами;
  контрольная ошибка показывает alert, исправление возвращает достижимый GREEN.
- [ ] Ночной job не создаёт платежи; budget exhaustion/provider outage не мешают
  ручному вводу и не включают автоматическую замену модели.
- [ ] Документированы включение/откат, владельцы сигналов, TTL артефактов,
  baseline promotion и включение новых проверенных примеров в regression.

Бюджет и реализация согласованы. Production включение следует стандартному
выпуску с отдельным migration dispatch; merge/deploy пока не разрешены.


## Добавление новых данных

Новый пример проходит цикл: кандидат → обезличивание → проверка специалистом →
утверждённый expected output → validator → версионируемый dataset через PR.
Нужны исходный текст, контекст даты/валюты, синтетические или обезличенные
справочники, expected candidates/fields и поля, которые должны быть unknown/
вопросом. Отдельно указываются источник сообщения и происхождение разметки;
проверка ядра не зависит от Telegram. Положительные финансовые ответы не
генерируются автоматически из предположений модели.

Исправление пользователя — сигнал для кандидата на разметку, не автоматический
эталон: пользователь мог менять сам платёж. Полные ответы разных людей могут
иметь несколько допустимых вариантов; перечисляем допустимые tuples и unknown,
не вводим скрытый приоритет проекта/ЦФО. Поиск похожих/дублирующихся примеров
и разбиение по семействам предотвращают утечку между regression и holdout.

V1 без новой админки: JSONL + template + offline validator с санитизированными
ошибками, semantic scorer и packaging check. Новый набор получает version/hash
и review metadata; старые отчёты и gold не переписываются. Ошибочный gold
исправляется отдельной ревизией с причиной, baseline продвигается явно.

## Расширение имени и границ

Ядро — PaymentIntake («Разбор платёжных сообщений»), модельная задача уже
`parse_payment_message`. Telegram — адаптер. Убираем bot/chat/message IDs из
общего RequestPaymentIntakeCommand в opaque sourceKey; Telegram-адаптер сохраняет
старый алгоритм source identity byte-for-byte. Entity уже хранит sourceKey;
исторические task docs/path не переименовываем, чтобы сохранить manifests/links.
Новые источники позднее получают отдельные адаптеры, а не фиктивный Telegram bot.
