# Telegram Payment Intake: первая итерация

Статус: предложение реализации и стартовый корпус примеров. Обработчик,
API, модель хранения и работающий eval этой задачей не добавлены.

Подробный [план по этапам с чек-листами приёмки](plan.md).
Текущее состояние подготовки — [checkpoint.md](checkpoint.md).

## Основание и границы

Владелец просит разбирать свободный текст с сокращениями, выделять несколько
платежей и предлагать статьи ДДС, проекты и ЦФО. Первая итерация — без фото.
Для начала взяты 41 сообщение, сохранённое в операциях ДДС при чтении прода.
Это сохранённые входные тексты, а не полный архив переписки.

Пачка относится к 12 ноября 2026, 22:30–22:46 UTC, то есть к 13 ноября,
01:30–01:46 по Москве. В корпусе нет production ID, привязок к компаниям,
чатам и пользователям, состояния записей или назначенной им аналитики.
Имена, username, названия проекта и мест заменены условными обозначениями;
денежные суммы, сокращения, опечатки и числовые ловушки сохранены.
Это производный набор примеров, а не побайтовая копия сообщений.

## Где живёт логика

Предлагаемая структура использует существующие модули и шлюз:

```text
site/src/Telegram/
  Controller/                    приём webhook и callback, ответы пользователю
  Application/                   адаптация сообщения к сценарию Cash

site/src/Cash/
  Application/PaymentIntake/      запрос разбора, уточнение, подтверждение
    DTO/                         команды и представление черновика
  Entity/PaymentIntake/           черновик и его строки
  Repository/PaymentIntake/       загрузка только в области companyId
  Application/Service/PaymentIntake/
                                 проверки, подготовка контекста и результата
  Facade/CashFacade.php           вход для Telegram и будущих каналов

site/src/ServiceGateway/          существующий обмен задачами с ai-service

services/ai-service/src/ai_service/tasks/parse_payment_message/
  schemas.py                     типизированный вход и результат
  task.py                        подключение к существующему pipeline
  checks.py                      проверка результата и исходных фрагментов
  prompts/v1.md                  версия инструкции распознавания

services/_contracts/ai-parse-payment-message/v1/
                                 будущий контракт payload/output
```

Названия и пути выше — предложение, не текущие контракты. Новые методы
Facade и контракт задачи оформляются при реализации по правилам проекта.
Отдельный микросервис, новый бот и второй механизм вызова LLM не нужны.
Telegram вызывает Cash через Facade; Python получает только переданный ему
контекст и справочники, не читает БД Symfony и не сохраняет платежи.

## Как обрабатываем сообщение

1. **Принимаем и надёжно регистрируем.** Telegram проверяет подлинность
   webhook. Symfony разрешает пользователя, компанию, права и выбранную
   кассу. В области компании регистрирует источник с ключом повтора и
   запрос разбора. Повтор webhook не создаёт новый черновик. Подтверждение
   приёма не зависит от ожидания ответа модели; постановка задачи должна
   переживать сбой после commit. Исходный текст не идёт в обычные логи.
2. **Подготавливаем контекст.** Передаём текст целиком, фиксированное время
   сообщения и часовой пояс компании, выбранную кассу, допустимые статьи,
   проекты, ЦФО и их связи. Только ограниченный относящийся к задаче контекст
   переписки; история другой компании не используется. Отсутствие выбора
   компании или кассы не подменяется догадкой модели.
3. **Распознаём.** Python отличает платёж, список, уточнение, исправление и
   недостаточный контекст. Для чисел выделяет роль: денежная сумма, номер
   пункта, количество, период, справочный итог. Возвращает кандидатов и
   исходные фрагменты для полей, а также предложения по аналитике. Сначала
   это одна ИИ-задача; разделение на дополнительные вызовы определяется
   измерениями качества, задержки и стоимости.
4. **Проверяем кодом.** Нормализация денежных выражений проверяема по
   исходным фрагментам; деньги — десятичные строки, не float. Symfony
   проверяет компанию, активность справочников и допустимые пары проект–ЦФО.
   Учитываются существующие правила и ручной выбор пользователя. Время для
   «вчера» фиксировано исходным сообщением, а не временем повторной обработки.
   Оценка уверенности модели не заменяет эти проверки.
5. **Сохраняем черновик.** Каждая строка имеет стабильный ID, назначенный
   Symfony. Показываем суммы, даты, направления, счёт и аналитику; явно
   отмечаем значения, взятые из контекста. Нужные уточнения привязываем к
   строке и полю. Поддерживаем состояния received, parsing,
   needs_clarification, ready, confirmed, cancelled, failed.
6. **Уточняем.** «У второго платежа проект Юг» меняет конкретную строку
   текущей версии черновика. Если у «измени на 20000» нет однозначной цели,
   спрашиваем её. Исправление не создаёт новый платёж. Изменение уже
   сохранённой операции — отдельный сценарий выбора, проверки прав и
   подтверждения, а не неявная правка последней записи.
7. **Подтверждаем и сохраняем.** Проверяем версию черновика, актуальные права,
   справочники, валюту и закрытый период. Подтверждение сериализовано с
   правками черновика. Сохраняем выбранные строки одной транзакцией через
   существующий механизм Cash; ключи повтора привязаны к источнику и
   стабильным ID строк. Повтор подтверждения возвращает прежний результат.

Результат модели Symfony забирает по существующей pull-модели. Для диалога
нужен ограниченный по времени путь получения результата; ожидание только
периодического импорта с минутным интервалом не подходит. Конкретная механика
выбирается при реализации без неутверждённых изменений production scheduler.

## Что нельзя выводить из этих примеров автоматически

- «120» и «-10» могут подразумевать тысячи, но это нельзя утверждать по
  текущему значению суммы в БД. Требуется уточнение или заранее согласованное
  правило пользователя. Контекстные масштабы «итого 11» также неоднозначны.
- Список расходов и две суммы в одной строке не доказывают число банковских
  платежей. Необходимо различать платежи и распределение одного платежа.
- «Оплачивал сотрудник» не определяет счёт компании и не доказывает, что
  компенсация сотруднику уже выплачена.
- Число участников не является правилом расчёта комиссии. Периоды зарплаты
  не превращаются автоматически в отдельные выплаты.
- Прошлые ручные правки сумм, удаления и назначенная аналитика не являются
  эталонными ответами распознавания.
- Фактический платёж и будущая оплата должны различаться. Политика записи
  будущих оплат пока не согласована; неопределённый статус исполнения
  уточняется до записи факта ДДС.

## Стартовый корпус

[examples/messages.jsonl](examples/messages.jsonl) содержит 41 независимый
пример с частичной ручной разметкой. Каждый пример — одна строка JSON.
Это материал для проектирования и будущих eval, а не подключённый тестовый
набор или публичный контракт.

Поля:

- `id` — локальный ID примера, не ID исходного сообщения.
- `text` — текст после замены имён и названий.
- `context` — синтетический контекст: фиксированное время, часовой пояс,
  отсутствие выбранной валюты, справочников и истории.
- `annotations.kind`, `tags` — тип и особенности примера.
- `money_mentions` — денежные упоминания: исходный фрагмент, буквальная
  нормализация и роль. `literal_amount` не означает утверждённую сумму
  платежа; это особенно важно для сокращённых сумм и справочных итогов.
- `non_money_spans` — фрагменты с числами, которые не должны стать суммами.
- `explicit_direction`, `relative_date` — только явно выраженные признаки,
  когда они размечены; отсутствие поля не задаёт значение по умолчанию.
- `clarification_topics`, `notes` — известные неоднозначности; списки
  частичные и не запрещают другие необходимые уточнения.

Порядок строк не означает общую переписку: примеры нельзя автоматически
связывать как последовательность исправлений. Значение `reference_at`
синтетическое и одинаково для всех примеров; production-время не перенесено.
`currency: null` не запрещает распознать явно написанное «руб.» в тексте.
Для проверки аналитики потребуются отдельные синтетические справочники и
согласованная разметка. Если часть корпуса используется в промпте, близкие
и повторяющиеся случаи нельзя выдавать за независимую проверочную выборку.

## Порядок реализации

1. Утвердить контракт результата и ожидаемое поведение на этом корпусе;
   неоднозначности сохранить как уточнения, а не заполнить предположениями.
2. Реализовать Python-задачу и проверки на корпусе без записи в ДДС.
   Дополнить кейсами общих указаний, опечаток и сообщениями без платежей.
3. Реализовать черновики и подтверждение в Cash, затем адаптер Telegram.
   Проверить компанию и права, повторы, конкурентную правку и подтверждение.
4. Проверить сценарий целиком в тестовой среде. Живые вызовы провайдера,
   production-изменения и rollout — по правилам одобрений проекта.

Качество измерять отдельно: границы кандидатов, суммы, направление, даты,
аналитика и правильность уточнений. Полнота JSON не является доказательством
финансовой корректности. В первой итерации запись — только после подтверждения.
