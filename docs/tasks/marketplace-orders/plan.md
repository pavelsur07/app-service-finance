# Задача: загрузка заказов Ozon и Wildberries с историей статусов

## Контекст

Заказов в системе нет. Сущность `MarketplaceOrder`, таблица `marketplace_orders`
и репозиторий существуют, но **не пишутся никем**: объект создаётся только в
тестовом билдере `tests/Builders/Marketplace/MarketplaceOrderBuilder.php`.
Клиентов к заказным API ни у Ozon, ни у WB нет.

`Marketplace\Enum\OrderStatus` содержит четыре значения
(`ordered / delivered / returned / cancelled`) — для отслеживания реальных
статусов двух маркетплейсов этого мало, а таблицы истории статусов нет вовсе.

Модуль `Ingestion` уже несёт всё, что нужно для инкрементальной почасовой
загрузки, и это работает в проде:

| Механизм | Что даёт |
|---|---|
| `IngestCursor`, уникальный по `(company, connection, resource_type, shop_ref)` | позиция инкремента на ресурс |
| `SyncJobKind::INCREMENTAL` | режим прогона |
| `SourceConnectorInterface` + `ConnectorRegistry` | реестр коннекторов; `OzonSellerReportConnector` — первый боевой |
| `RunSyncChunkHandler` (`ingest_fetch`) → `RawStorageFacade` → `NormalizeRawRecordMessage` (`ingest_normalize`) | pull → raw на S3 → нормализация |
| Дедуп raw по sha256 | при часовом опросе неизменившаяся страница не создаёт новый объект |
| `ListingResolverRegistry` + `ListingResolverInterface` | связь строк с листингами; так уже связан `FinancialTransaction` |

**Препятствие, которое надо закрыть в рамках задачи.**
`SourceMapperInterface::map()` возвращает `list<MappedTransaction>`, а
`NormalizeRawRecordAction` пишет исключительно `FinancialTransaction`. Заказы —
не финансовые транзакции, поэтому нормализация заказов требует второго пути
внутри Ingestion, а не переиспользования существующего маппера.

## Решения Владельца

| Вопрос | Решение |
|---|---|
| Схемы | **FBS и FBO обе** |
| Где живут заказы | **новые сущности в `Ingestion`**; `MarketplaceOrder` не трогаем |
| История статусов | **append-only** журнал переходов |
| Словарь статусов | **сырая строка маркетплейса + нормализованный enum** |
| Retention raw на S3 | **год горячего хранения, затем удаление** |
| Зачем связь с листингами | расчёт выкупа и прочих показателей |

## Модель данных

Три сущности в `App\Ingestion\Entity`, все tenant-owned
(`string $companyId` + marker `TenantOwnedInterface`, как требует
`ARCHITECTURE.md`):

```
IngestOrder
    companyId, connectionRef, shopRef, source, scheme (FBO|FBS)
    externalId            posting_number (Ozon) | id заказа (WB)
    orderedAt
    rawStatus             сырая строка маркетплейса
    status                нормализованный enum
    statusObservedAt
    UNIQUE (companyId, source, externalId)
    INDEX  (companyId, status), (companyId, orderedAt)

IngestOrderItem
    orderId, companyId
    externalSku, offerId, name, quantity, price
    listingId             ?string UUID — связь с листингом
    listingSku            ?string — сырой ключ, по которому резолвили
    INDEX  (companyId, listingId)

IngestOrderStatusEvent    append-only
    orderId, companyId
    rawStatus, status, previousStatus
    observedAt
    INDEX  (orderId, observedAt)
```

`scheme` хранится отдельно от `source`: наборы статусов у FBO и FBS разные, и
без явного различения нормализация станет угадыванием.

## Словарь статусов

Сырая строка сохраняется всегда и без изменений — это то, что действительно
прислал маркетплейс, и единственное доказательство при разборе.

Нормализованный enum `IngestOrderStatus`:
`ORDERED / SHIPPED / DELIVERED / CANCELLED / RETURNED / UNKNOWN`.

Правила:

- маппинг сырых строк в enum задаётся **в одном месте** на пару
  `(source, scheme)` — три копии предиката в трёх запросах рано или поздно
  разойдутся (`CLAUDE.md`, «Health-гейты»);
- неизвестная строка даёт `UNKNOWN` и попадает в **видимую очередь на разбор**,
  а не в `NULL`: `NULL` одновременно ломает данные и прячет факт поломки;
- терминальные статусы: `DELIVERED`, `CANCELLED`, `RETURNED`. Именно они
  останавливают опрос и ограничивают объём работы цикла статусов.

## Связь заказов с листингами

**Связь на уровне позиции, а не заказа.** Отправление Ozon содержит `products[]`
с несколькими SKU, а выкуп считается по листингу; связь на заказе не дала бы
посчитать показатель в многострочном заказе.

**Механизм — существующий `ListingResolverRegistry`**, новый не заводим.
Но состояние резолверов разное, и это проверено в коде:

- `OzonListingResolver` **рабочий**: читает `offer_id`, `item_code`, `sku`,
  `name`, `items` — те самые поля, что лежат в `products[]` отправления.
- `WbListingResolver` — **заглушка**: логирует «not implemented yet» и
  возвращает `null`. Без его реализации у каждой WB-позиции будет
  `listingId = null`, и **выкуп по WB не посчитается вообще**. Это отдельный
  work item со своим ревью, а не деталь стадии.

Лестница резолва WB (первое попадание выигрывает): штрихкод (`skus[0]` из
marketplace, `barcode` из statistics) → `chrtId` → `nmId` + `techSize` →
артикул. **`nmId` сам по себе не различает размеры**, поэтому первым ключом
быть не может.

**Побочный эффект, который надо замерить.** `ListingResolverRegistry` выбирает
резолвер только по `IngestSource`, без `resourceType`. Замена заглушки
немедленно начнёт заполнять `FinancialTransaction.listingId` для WB-финансов —
поведение вне scope задачи. Вероятно улучшение, но в Stage Report нужны цифры
«до/после».

Хранение — **скаляры** `listingId` + `listingSku`, без `#[ManyToOne]` на
сущность чужого модуля: так требует граница модулей и так уже сделано в
`FinancialTransaction` (индекс `idx_ftx_company_listing`).

**Нерезолвленное не теряется молча:** `listingId = null`, но `listingSku`
сохраняется — это очередь на разбор. Для дозаполнения нужен релинкер;
прецедент — `OzonAccrualListingRelinker`.

Синергия с уже выпущенной каталожной загрузкой Ozon: она заполнила
`supplier_sku` и наименования листингов, поэтому резолв по `offer_id` будет
попадать чаще, чем до неё.

**Выкуп** (потребитель, вне этого scope): доля позиций листинга, чей заказ
достиг `DELIVERED`, к общему числу заказанных за период. Требует обеих
половин — `item → listingId` и историю статусов. Считать будет
`MarketplaceAnalytics`, читая через `IngestionFacade` DTO: сущности Ingestion
наружу не выходят (`EntityBoundaryTest`).

## Часовой цикл

Два **разных** цикла, а не один. Это принципиально.

### Цикл обнаружения — курсорный

Новые заказы с момента курсора; курсор двигается только вперёд.

| resourceType | Эндпоинт |
|---|---|
| `ozon_orders_fbs` | `POST /v3/posting/fbs/list` |
| `ozon_orders_fbo` | `POST /v2/posting/fbo/list` |
| `wb_orders_marketplace` | `GET marketplace-api /api/v3/orders` |
| `wb_orders_statistics` | `GET statistics-api /api/v1/supplier/orders` |

### Цикл обновления статусов — НЕ курсорный

Идёт от собственной БД: «заказы в нетерминальном статусе, созданные за
последние 30 дней» (значение по умолчанию, параметризуемо). Курсором это не
выражается: попытка дала бы либо вечный перечит всего каталога заказов, либо
потерю зависших. У Ozon статусы приезжают
внутри тех же списков при перезапросе окна, у WB — отдельным
`POST /api/v3/orders/status` пачками по id.

### Правила журнала

- Событие пишется, **только если статус отличается** от текущего у заказа.
  Иначе часовой опрос дал бы 24 одинаковые строки в сутки на заказ.
  `IngestOrder.status` — единственный источник «что сейчас»,
  `IngestOrderStatusEvent` — только переходы.
- **Статус не едет назад.** Маркетплейсы отдают устаревшее состояние; событие
  записываем всегда (это факт наблюдения), но `status`/`statusObservedAt`
  двигаем только вперёд по `observedAt`. Тот же урок, что с `last_seen_at`
  в каталоге листингов.
- Заказ, застрявший в нетерминальном статусе дольше N дней, уходит в видимую
  очередь на разбор, а не опрашивается вечно.

### Чем запускается

Отдельный cron для обнаружения **не нужен**: механизм уже есть.
`app:ingestion:run-incremental` обходит активные подключения × стратегии
`IncrementalResourceStrategyInterface`, а каденция каждого ресурса выражается
его методом `cursorIsDue()`. Для суточных ресурсов это делает
`AbstractDailyCursorIncrementalStrategy`.

Заказам нужен часовой аналог базового класса, а cron-строку
`0 3 * * * app:ingestion:run-incremental` придётся перевести на почасовую.

**Это меняет поведение существующей финансовой загрузки** — её стратегии станут
опрашиваться каждый час вместо раза в сутки. Само по себе это дёшево (проверка
курсора без обращения к API) и безопасно, потому что суточные стратегии вернут
`false` до смены дня, но изменение общего расписания обязано быть отдельным
пунктом ревью, а не побочным эффектом.

Цикл обновления статусов курсором не выражается, поэтому получает собственную
команду и собственный часовой слот. Занятые минуты проверить перед выбором:
`20 * * * *` (WB financial orchestrate), `*/2`, `*/5`, `*/10`, `*/30`.

## Хранение raw на S3

Действующая раскладка (`RawStoragePathBuilder`) переиспользуется без изменений:

```
{company}/{source}/{shop}/{resource}/{yyyy}/{mm}/{dd}/{syncJobId}/{externalId}/{hash}.ndjson.gz
```

Правила, которые задача обязана соблюдать:

1. **Партиционирование: арендатор → источник → дата.** Позволяет удалить данные
   одной компании при офбординге и применять retention к одному источнику.
2. **Дата в пути — дата загрузки, а не бизнес-события.** Иначе retention
   ломается: объект, скачанный сегодня за прошлый месяц, попал бы в старый
   префикс и был бы удалён раньше срока.
3. **Объекты неизменяемы и адресуются содержимым** (sha256 в имени). Перезапись
   по существующему ключу запрещена: иначе нельзя доказать, что прислал
   маркетплейс.
4. **В пути нет секретов и персональных данных.** Путь виден в листингах, логах
   и метриках.
5. **Источник истины о существовании объекта — БД**, S3 — только байты. Листинг
   бакета не является частью бизнес-логики.
6. **Гранула — страница ответа, не запись.** NDJSON + gzip.
7. **`externalId` — стабильный ключ дедупликации.** Для заказов это окно, а не
   порядковый номер: `window-2026-09-01T14-page-3`. Неизменившаяся страница часа
   не плодит объект, страницы разных часов не конфликтуют.

### Retention: год, затем удаление

Провайдер — timeweb (`s3.twcstorage.ru`), настраивается только через `.env`;
конфигурации бакета в репозитории нет.

**Удаление делаем командой приложения, а не lifecycle-правилом провайдера.**
Причина: правило на стороне провайдера снесёт объекты, но оставит строки
`ingest_raw_records`, указывающие в пустоту, — а `ReadRawRecordAction` на них
будет падать. Команда удаляет объект и строку одной операцией и потому
проверяема тестом.

  `listingSku`.
- Курсор двигается только вперёд; повторный прогон идемпотентен.
- Ответ с нарушенной структурой поднимает доменное исключение, а не
  завершается «успехом» с нулём заказов.
- Фикстуры реальных ответов обеих схем, обезличенные.

## Stage 3: загрузка заказов Wildberries

Risk: 🟠 HIGH-LOCAL · зависит от Stage 1

Три ресурса, и каждый обязателен — проверено на выгрузке:

| Ресурс | Что видит только он |
|---|---|
| `wb_orders_marketplace` (`/api/v3/orders` + `/orders/status`) | обнаружение FBS и **две оси статуса**. В выгрузке 18 из 18 — `deliveryType: fbs` |
| `wb_orders_statistics` (`/api/v1/supplier/orders?flag=0`) | **единственный канал, видящий FBO**: «Склад WB» 43 против «Склад продавца» 25. Даёт `scheme` прямо из `warehouseType`, плюс `orderedAt`, цены, `isCancel` |
| `wb_orders_sales` (`/api/v1/supplier/sales`) | **факт выкупа.** Признака доставки нет ни в одном захваченном эндпоинте: `wbStatus` доходит до `sorted`, у statistics только `isCancel`. Без него статус WB упирается в `ORDERED`/`CANCELLED`, и цель задачи на половине объёма не достигается |

Выкинуть statistics — потерять все FBO-заказы WB: все 16 пересекающихся
`rid = srid` относятся к «Склад продавца», то есть к FBS.

Definition of Done:
- `WbOrdersConnector` для трёх ресурсов выше.
- Реализован `WbListingResolver` (см. «Связь заказов с листингами»).
- Курсор statistics двигается по `max(lastChangeDate)` **вернувшихся строк**,
  а не по `now`: иначе изменения, легшие между запросом и ответом, теряются.
- Строки вне запрошенного окна **не отбрасываются**: `flag=0` отдаёт по
  `lastChangeDate`, и в выгрузке окно вернулось шире запрошенного.
- Заказ из двух потоков даёт одну строку: `externalId` = `rid`/`srid`, числовой
  `id` живёт в отдельной колонке `externalOrderId` для `/orders/status`.
- 429 обрабатывается ретраем транспорта, а не падением прогона.

## Stage 4: цикл обновления статусов и журнал

Risk: 🟠 HIGH-LOCAL · зависит от Stage 2 и Stage 3

Definition of Done:
- Выборка «нетерминальные заказы за N дней» — одно определение, переиспользуемое
  и опросом, и монитором.
- **Порядок очереди — по отметке ПОПЫТКИ** (`statusRefreshAttemptedAt`):
  сначала ни разу не спрошенные, затем по возрастанию, затем по `id`.
  Изначально в спеке стояла сортировка по `statusObservedAt`; она оказалась
  дефектной и заменена в ходе реализации. Попытка бывает без наблюдения — 404,
  ответ без поля статуса, отсутствие заказа в успешном ответе WB, — такие
  заказы отметку наблюдения не двигают, а сортировка устойчива: они вечно
  занимали бы начало лимита, и остальные заказы кабинета не опрашивались бы
  никогда, попадая сразу в STUCK_ORDER.
- Событие пишется только при смене статуса; повторный опрос без изменений не
  создаёт строк.
- `status`/`statusObservedAt` не двигаются назад; событие фиксируется всегда,
  но устаревшее наблюдение переходом не считается: у него `applied = false` и
  пустой `previousStatus`.
- **Ключ наблюдения — порядковый номер (`occurrence`) внутри пары
  (сырьё, заказ), а не содержание.** Изначально в спеке стояла дедупликация по
  `(companyId, rawRecordId, orderId, rawStatus)`; она заменена в ходе Stage 5.
  Содержательный ключ подавляет законный повтор перехода — одно сырьё может
  нести A → B → A → B, и второе «A → B» совпадает с первым: заказ переход
  применяет, а журнал теряет. От повторной записи защищает не ключ, а
  транзакция разбора (всё сырьё пишется одним коммитом) и отдельный путь
  повтора `OrderStatusJournal::reapply()`, который событий не создаёт.
- Заказы, застрявшие в нетерминальном статусе дольше **30 дней** (значение по
  умолчанию, вынесено в параметр команды), попадают в видимую очередь и
  перестают опрашиваться.
- Cron-строка на час, слот выбран без конфликта с занятыми.
- Регрессионный тест: два опроса подряд с одинаковым статусом дают одну строку
  журнала; смена статуса даёт вторую.

## Stage 5: retention raw

Risk: 🟡 MEDIUM · независим от Stage 2–4

Definition of Done:
- Команда удаляет объекты старше года **вместе** со строками
  `ingest_raw_records`; висячих указателей не остаётся.

- Cron-строка; `ARCHITECTURE.md` описывает политику.

## Открытые вопросы и FOLLOW-UP

1. **Окно опроса статусов — 30 дней по умолчанию**, параметром команды.
   Значение выбрано без данных: зависит от того, за сколько реально закрывается
   доставка у конкретного продавца. Уточнить по данным первой недели, а не
   считать обоснованным сейчас.
2. **Расчёт выкупа** — отдельная задача в `MarketplaceAnalytics`, здесь только
   готовятся данные и контракт `IngestionFacade`.
3. **`MarketplaceOrder` остаётся мёртвым** по решению Владельца. Со временем
   стоит решить его судьбу: удалить или наполнить — сейчас это таблица без
   писателя.
4. **Словари статусов неполны, и это установлено выгрузкой.** Ozon FBS вернул
   ноль отправлений — словарь неизвестен; засеваем из документации, помечая
   непроверенным: пустой словарь устроил бы шторм issue на первой же реальной
   FBS-загрузке. У WB наблюдались три пары из десятка. Расширение словаря не
   требует перекачки S3 — `rawStatus` хранится на самих событиях, поэтому
   `status` пересчитывается по истории.
5. **`substatus` Ozon в нормализованный enum не пускаем.**
   `posting_on_way_to_city` (68) и `posting_in_pickup_point` (19) оба лежат под
   `delivering` — это уточнение, а не статус. Хранить в `rawSubstatus`.
6. **Ключ идемпотентности позиций** — `UNIQUE (company_id, order_id, line_no)`,
   где `line_no` — индекс в `products[]`. По `external_sku` нельзя: один sku
   может повториться на двух строках.
7. **Многострочных отправлений в выгрузке нет** — все 100 однопозиционные.
   Фикстура многострочного заказа синтетическая и помечена как таковая.
