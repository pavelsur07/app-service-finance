# Новый бэкэнд account/admin: план параллельного перехода

**Дата:** 2026-11-11.
**Статус:** планирование; реализация не начата.
**Основание:** требования владельца в чате: новый бэкэнд по аналогии с
`app-service-analytics`, контуры account и admin, те же базы и клиенты,
старый Symfony продолжает работать параллельно. Этап 0 — основа,
зависимости, тесты, папки и заглушки.

> Для исполнителя: выполнять утверждённый объём по этапам с навыком
> `executing-plans`; правила и полномочия — корневой `AGENTS.md`.
> Сохранение этого плана не означает начало реализации.

**Цель:** подготовить отдельный API для клиентского кабинета account и
административного контура admin, затем постепенно переносить сценарии
без остановки существующего приложения и без копирования клиентских данных.

**Архитектура:** действующее приложение остаётся в `site/`, новый API
предлагается разместить в `api/`. Оба приложения работают с существующими
пользователями, компаниями и общей схемой finance; ответственность за
изменение данных, фоновые задания и миграции определяется явно.
Один новый API обслуживает account и admin с разделением доступа.

**Стек:** PHP 8.4, Symfony 7.4, PostgreSQL 15, Doctrine, Redis,
Composer, PHPUnit, PHPStan, PHP CS Fixer, Docker Compose.
Точные совместимые версии зависимостей фиксируются при реализации;
структура analytics служит образцом, его lock-файл не копируется.

## 1. Как понята задача

Нужна постепенная смена бэкэнда при сохранении действующего продукта.
Новые клиенты и повторная регистрация существующих пользователей не нужны.
Существующие идентификаторы, компании, права и данные сохраняются.
Account означает клиентский кабинет, а не банковский счёт.

На Этапе 0 создаётся технический фундамент. Результат — запускаемый,
проверяемый каркас, а не перенос финансовых возможностей или готовые UI.
Сейчас изменяется только этот Markdown-документ.

## 2. Подтверждённые требования и предлагаемые решения

### Подтверждено владельцем

- Старый Symfony продолжает работать параллельно с новым бэкэндом.
- Новый бэкэнд использует те же базы, пользователей и компании.
- Нужны контуры account и admin по аналогии с analytics.
- Сейчас только планирование и сохранение плана.
- Этап 0 охватывает основу, зависимости, тесты, папки и заглушки.

### Предлагается этим планом

- Один новый Symfony API в `api/` с двумя контурами доступа.
- На первом этапе миграциями общей схемы управляет существующее приложение.
- Действующие воркеры, cron, вебхуки и интеграции сохраняют своих владельцев.
- Сессии нового приложения изолированы от старого; единый вход — отдельное
  решение до реализации авторизации.
- Для будущих интерфейсов резервируются `apps/account/` и `apps/admin/`
  документацией. React-приложения создаются только в отдельном этапе UI.
- Включение нового контура по компаниям и сценариям, с возвратом на старый.

### Решить до соответствующего этапа

- До Этапа 1: домены и адреса нового account/admin, повторный или единый вход,
  поведение выхода, смены пароля и отзыва доступа в двух приложениях.
- До Этапа 2: первый раздел для чтения и способ повторного использования
  существующих правил доступа и бизнес-логики.
- До Этапа 3: первый сценарий записи, его владелец, транзакция,
  идемпотентность, события, очередь и правила конкурентного редактирования.
- До Этапа 4: пилотные компании, объём интерфейсов, условия включения и отката.
- Production Docker, маршрутизация, CI/CD и выкладка требуют отдельного
  именованного разрешения по `AGENTS.md` §3.3; план их не разрешает.

## 3. Что уже существует и влияет на переход

| Область | Факты из репозитория | Следствие для нового API |
|---|---|---|
| Приложение | Основной Symfony находится в `site/` | Новый API запускается отдельно, старые маршруты сохраняются |
| Пользователи | `site/src/Company/Entity/User.php`, отдельные firewall main/admin | Существующая модель учётных записей сохраняется; модель Administrator из analytics автоматически не переносится |
| Права | CompanyMember, CompanyRole, ModuleAccessResolver, ActiveCompanyService | ROLE_USER недостаточно: нужны компания, активное членство и права на модуль |
| Биллинг | ReadOnlyModeSubscriber проверяет firewall `main` | Ограничение записи по тарифу нужно явно обеспечить в новом API |
| Создание компании | CompanyCreatedEvent запускает настройку баланса, ДДС, ОПиУ и trial | Вставка строки в таблицу не заменяет существующий сценарий |
| База | В Doctrine finance зарегистрированы собственные типы денег, дат и encrypted_json | Маппинг analytics нельзя считать совместимым с общей БД |
| Очереди | Messenger имеет несколько транспортов и существующих обработчиков | Новый процесс не должен случайно забирать чужие сообщения или дублировать задания |
| Сессии и блокировки | Redis, префикс сессий `sess_`, Redis locks и PostgreSQL advisory locks | Сессии/кеш разделяем; координацию общих операций сохраняем общей |
| Аналог | Analytics: `api/`, `apps/seller/`, `apps/admin/`, `packages/api-schema/` | Используем организацию API и контрактов, адаптируя к finance |

Перед реализацией перечитать эти места: код мог измениться после планирования.

## 4. Общие ограничения

- Никаких копий production-базы или production-учётных данных для локальных тестов.
- Dev: существующая локальная база finance. Test: отдельная тестовая база;
  она не является заменой общей клиентской базы в целевой архитектуре.
- На Этапе 0 нет миграций, schema update, фикстур пользователей и записи
  клиентских данных. Не переносить миграции analytics в finance.
- Перед реализацией снять baseline старого приложения узкой проверкой.
  Полные старые гейты — на handoff реализации по `AGENTS.md`, не после каждого шага.
- Финансовые суммы, знаки, периоды, валюты и даты не менять при переносе API.
- Каждый сценарий записи должен сохранять существующие инварианты,
  побочные действия и защиту от повторов; независимое дублирование формул запрещено.
- Глобальная изоляция компаний не предполагается автоматически:
  права и companyId проверяются для каждого сценария.
- Изменение общей схемы сначала совместимо с обеими версиями кода;
  удаление старых колонок и контрактов — после прекращения использования.
- Ни один новый cron, consumer, webhook или внешний вызов не включается
  автоматически вследствие создания каркаса.
- В API не публикуются токены, адреса внутренних сервисов, версии окружения
  и диагностические сведения, не нужные клиенту.

- [ ] Новый nginx привязать локально к `127.0.0.1:8088`; при занятом порте

- [ ] Dev-соединение направить в существующий локальный PostgreSQL finance,

- [ ] Для доступных в каркасе ORM-операций запретить изменение схемы:

- [ ] Определить отдельные cookie name, Redis session prefix и cache namespace

- [ ] Добавить защиту тестового bootstrap от запуска DB-тестов с dev/prod

- [ ] Зафиксировать будущие команды `make api-console`, `api-test-unit`,

**Результат:** два приложения могут быть запущены одновременно локально;
проверка соединения нового API не изменяет общую схему или данные.

#### 0.3 — Технические маршруты и заглушки

- [ ] Сначала написать HTTP-тесты наблюдаемого поведения, получить ожидаемый
  FAIL из-за отсутствующего маршрута/контракта, затем реализовать минимум.
- [ ] `GET /health` → 200, `{"status":"ok"}`. Liveness не обращается к БД.
- [ ] `GET /ready` → 200, `{"status":"ready"}` при доступной БД;
  при недоступной БД → 503, `{"status":"not_ready"}` без деталей соединения.
  Проверка — только чтение (`SELECT 1`); на этом этапе маршрут только локальный.
- [ ] Только в dev/test: `GET /api/account/ping` → 200,
  `{"status":"stub","scope":"account"}`.
- [ ] Только в dev/test: `GET /api/admin/ping` → 200,
  `{"status":"stub","scope":"admin"}`.
- [ ] В prod-конфигурации ping-маршруты не импортируются: оба дают 404.
  Заглушки не означают, что авторизация или доступ к клиентским данным готовы.
- [ ] Неизвестный `/api/...` → 404 и JSON
  `{"error":{"code":"not_found","message":"Ресурс не найден"}}`.
- [ ] Неподдерживаемый метод технического API → 405 с JSON-ошибкой
  `method_not_allowed` и корректным Allow; без HTML и stack trace.
- [ ] Не создавать `/me`, списки клиентов, операции, тестовые логины
  или ответы с выдуманными компаниями под видом готовых бизнес-endpoint.

**Результат:** есть проверяемые точки запуска и два явно обозначенных контура,
но ни один технический маршрут не читает пользовательские данные.

## 7. Сквозные риски и фокус review

| Условие | Требуемое поведение | Где проверяется |
|---|---|---|
| Не тот DATABASE_URL у тестов | Отказ до соединения и подготовки БД | 0.2 / 0.4 |
| БД недоступна | Liveness 200, readiness 503, никаких реквизитов в ответе | 0.3 / 0.4 |
| Prod-конфигурация каркаса | Заглушки account/admin отсутствуют; бизнес-маршрутов нет | 0.3 / 0.4 |
| Пользователь без прав или с чужой компанией | Нет обхода membership, модульных прав и тарифа | Этап 1 |
| Два приложения пишут одну запись или повторяют команду | Согласованные блокировки, конфликт редактирования и дедупликация | Этап 3 |
