# МойСклад: сопоставление WB (и любой площадки) без модификаций в каталоге

## Задача

У «Вумджой ООО» (19621cff) на WB 200 листингов, в отчёте — 0 предложений (замер на проде 21.11.2026).
WB продаёт размер отдельным листингом, а в МойСкладе модификаций нет (0 из 1 403 товаров): каждый
размер — отдельный товар, размер «зашит» в артикул или название. Текущая политика для листинга с
размером требует модификацию с характеристикой размера, иначе SIZE_UNVERIFIABLE (43) или NO_MATCH (120).
Штрихкодов в МойСкладе нет (0 из 1 370), на WB — 227, у связанных листингов Ozon — 42.

Решения Владельца (21.11.2026):
- штрихкод — основание связи; остальные правила — запасные и штрихкод не перебивают;
- один товар МойСклада может быть связан одновременно с Ozon и WB (и с несколькими листингами);
- никаких правил под конкретную компанию (исключения «/Сырье» и т. п.) — только общие признаки.

## Результат

Правила в порядке силы; правило ниже работает, только если выше нет ни совпадения, ни противоречия.

| # | Правило (`matchedRules`) | Что совпадает | Автоприменение |
|---|---|---|---|
| 1 | `exact_barcode` (есть) | штрихкод листинга ∈ штрихкоды товара/модификации | да |
| 2 | `linked_barcode` (новое) | штрихкод листинга = штрихкод листинга **другой площадки**, уже связанного с товаром | да |
| 3 | существующие артикульные (`direct_article`, `parent_article_size`, `exact_code`, `wb_article_alias`) | как сейчас | да |
| 4 | `article_size` (новое) | артикул товара = артикул листинга + `-`/`_`/пробел + размер | да |
| 5 | `name_size` (новое) | у нескольких товаров один артикул, размер — токен в скобках названия «(L, …)», «(L)» | нет, только вручную |

- **Размер** сравнивается после нормализации: регистр, пробелы и кириллические буквы, которые пишутся
  так же, как латинские (А В Е К М Н О Р С Т Х → A B E K M H O P C T X). Транслитерации нет. Общая функция, без словарей под компанию.
- **Товар без модификации, но с размером в артикуле/названии** больше не SIZE_UNVERIFIABLE: размер
  подтверждён правилом 4 или 5. Без такого подтверждения — как сейчас.
- **Противоречие штрихкода:** у листинга и кандидата штрихкоды есть и не пересекаются, а артикул совпал →
  новый статус/причина `barcode_conflict` («Штрихкод расходится»), не READY. Связь по другой площадке
  указывает на один товар, а артикульные правила — на другой → AMBIGUOUS с причиной `cross_marketplace_conflict`.
- **Несколько кандидатов:** приоритет у кандидата, уже связанного с листингом любой площадки (сырьё и
  служебные товары с продажами не связаны — отсекаются сами). Если и так > 1 — AMBIGUOUS, выбор вручную.
- **Один товар — много листингов:** уже связанный с Ozon товар не исключается из кандидатов WB; закрепить тестом.
- **Недоступные листинги** (LISTING_UNAVAILABLE, 37 у «Вумджой ООО») — не в «Требует внимания», отдельная вкладка.
- **Автоприменение и пакет «Принять все»** берут только READY без `name_size`; строки `name_size` — в
  «Предложениях» с пометкой «размер по названию», принимаются отмеченными строками.
- `AutomaticMappingGuard::RULE_VERSION` → `identity_package_v3`: старые отчёты становятся устаревшими и
  пересчитываются сами (#3090), пакеты по старому отчёту отклоняются guard'ом.

Ожидание на «Вумджой ООО» (замер SQL на проде): `linked_barcode` 38, `article_size` 63, `name_size` 43;
объединение 119 из 200, из них 4 — противоречие «Ozon vs артикул» → вручную. Автоматически ≈ 72–76,
ещё ≈ 43 — «Предложения» для ручного принятия; ≈ 80 — ручной выбор (товара нет или артикул иной).
