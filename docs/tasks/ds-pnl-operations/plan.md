## Что строим

Плоский список **операций** документов ОПиУ компании: одна строка = одна `DocumentOperation`, а не документ.
Адрес `/documents/operations`, роут `document_operation_index` (GET). Вкладки раздела: «Документы ОПиУ» · «Операции» · «Удалённые»;
фильтры переходят между вкладками «Документы» и «Операции» в ссылке.

Колонки (1440): Дата · Документ (тип-ссылка на документ, №, описание в одну строку, «В документе N операций», если N > 1) ·
Статья ОПиУ · Проект / ЦФО (ЦФО — второй строкой) · Контрагент · Доход ₽ · Расход ₽ · «⋯».
≤1340 px — Статья, Проект/ЦФО, Контрагент сворачиваются в строку-мету под описанием (как 03-1280).
Полоса итога: «Найдено M операций · N документов», Доходы / Расходы / Результат по всей выборке, другие валюты — отдельной строкой
(как на вкладке документов). Пагинация 20/30/50 с фильтрами.

## Решения по разрыву макета и модели

| Макет | Решение | Почему |
|---|---|---|
| «Операция 1 из 3» | «В документе 3 операции» | у операций нет порядка: id — UUID v4, у коллекции нет `OrderBy`; номер «k» был бы случайным и не совпал бы со страницей документа |
| Чекбоксы строк | не делаем | массовые действия — открытый вопрос №3 отчёта |
| Меню «Изменить статью», «Изменить проект» | не делаем; в меню «Открыть документ» (edit) и «Просмотр» (show) | правка из списка — новая запись в ОПиУ (регистр, аудит), отдельная задача; вопрос в отчёт |
| ЦФО: мультивыбор со счётчиками, «ЦФО не указан» | одиночный выбор, как на вкладке документов | паттерн фильтров один на раздел; мультивыбор и счётчики — в отчёт |
| Пилюли «Статья ОПиУ», «Сумма» | делаем на обеих вкладках | «те же фильтры» (Stage 3 поручения); на вкладке документов — через EXISTS |
| Счётчики на всех вкладках | счётчик только у активной вкладки = «Найдено» | счётчик соседней вкладки — лишний запрос и другая семантика при фильтрах по операциям |
| Строк «10» | 20 / 30 / 50 | лимиты раздела и CLAUDE.md |

## Семантика фильтров на вкладке «Операции»

Значения операции «эффективные» — как в `PLRegisterUpdater`: проект `op.projectDirection ?? d.projectDirection`,
ЦФО `op.responsibilityCenterId ?? d.responsibilityCenterId`, контрагент `op.counterparty ?? d.counterparty`.
- период, тип, статус, номер — по документу; удалённые документы не входят;
- `q` — описание и номер документа, название статьи, эффективный контрагент, комментарий операции;
- проект, ЦФО, контрагент — по эффективному значению;
- направление «Доходы/Расходы» — по природе операции (на вкладке документов — так же, через EXISTS) (flow статьи, у статьи NONE — знак суммы), то есть ровно те строки,
  что попадают в колонку Доход/Расход итога;
- статья — `op.category = :id` (новый фильтр);
- сумма «от/до» — по модулю суммы операции (новый фильтр).
Операция без статьи в списке есть («Нужно указать статью»), в Доход/Расход не входит.

На вкладке «Документы» новые фильтры «Статья» и «Сумма» — «есть операция с этой статьёй / с суммой в диапазоне» (EXISTS).

## Деньги строки и итога

Правила — регистра ОПиУ и `DocumentPlContribution`: обычный документ — модуль операции в колонку её природы;
`marketplace_pl` — знак суммы статьи документа: при отрицательной сумме статьи (списания) вклад операции = −amount
(списание −X → X, сторно +X → −X). Сумма статьи — **полная** по документу, без фильтров списка (правка по ревью: по
отфильтрованным операциям одно сторно становилось расходом); итог = Σ вкладов найденных операций = сумма строк. Итог — агрегатными запросами в репозитории (без гидрации),
знаки строк страницы — одним сгруппированным запросом по документам страницы. Валюта — валюта основания ДДС, иначе RUB.

## Stage 1: бэкенд вкладки
Risk: HIGH-LOCAL (денежные итоги, новый запрос по операциям, IDOR через join документа)
Definition of Done:
- `DocumentListDTO`: `categoryId` (uuid), `amountFrom`/`amountTo` (неотрицательная десятичная строка, «1 000,50» → `1000.50`,
  мусор = не задан); `hasFilters()` учитывает их.
- `DocumentRepository`: фильтры статьи и суммы через EXISTS (список и итог вкладки документов).
- `DocumentOperationRepository`:
  - `paginateForList(string $companyId, DocumentListDTO $dto): Pagerfanta<DocumentOperation>` — join документа с
    `IDENTITY(d.company) = :companyId`, `d.deletedAt IS NULL`; fetch-join документа, его контрагента/проекта/основания,
    статьи, проекта и контрагента операции; **без** fetch-join `d.operations` (иначе коллекция документа неполная);
    порядок `d.date DESC, d.id, op.id`;
  - `summarizeForList(string $companyId, DocumentListDTO $dto): DocumentListTotalsDTO` — те же правила, что у вкладки документов;
  - `marketplaceCategorySigns(string $companyId, DocumentListDTO $dto, list<string> $documentIds)` и
    `countByDocuments(string $companyId, list<string> $documentIds)` — по одному запросу на страницу.
- Сервис `DocumentOperationPlContribution` (Finance/Application/Service, final readonly) — вклад строки по природе и знаку статьи;
  общая логика природы — `PlNatureResolver`.
- Контроллер `Finance/Controller/DocumentOperationIndexController` (final, `__invoke`, `priority` выше `/{id}` документа):
  активная компания до данных, DTO из запроса, страница, итог, знаки, счётчики, названия ЦФО батчем через Facade,
  списки проектов/ЦФО/статей для фильтров. Без бизнес-логики.
- Число запросов страницы не растёт с числом строк (тест); company-изоляция строк и итога (тест).
Work items:
- 1.1 — DTO + unit-тесты (статья, сумма: «1 000,50», «-5», «abc», «0»).
- 1.2 — фильтры статьи/суммы на вкладке документов + интеграционные тесты.
- 1.3 — запросы операций + интеграционные тесты: эффективные проект/ЦФО/контрагент, направление NONE по знаку,
  удалённый документ, чужая компания, стабильная пагинация, итог marketplace_pl (списание + сторно) = сумма строк.
- 1.4 — сервис вклада + unit-тесты всех веток; контроллер + функциональный тест 200/фильтры/IDOR.
Stage checks: `tests/Unit/Finance`, `tests/Integration/Finance`, `tests/Functional/Finance`, PHPStan и cs по изменённым файлам.
Reviewer focus: IDOR (company через join документа на каждом пути), неполные коллекции, суммы marketplace_pl, маршрут `/operations` vs `/{id}`.
