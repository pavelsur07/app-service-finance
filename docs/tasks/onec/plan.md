# onec: приём пакетов счетов на оплату и сырьё в S3

Задача — следующий этап после [PR #3124](https://github.com/pavelsur07/app-service-finance/pull/3124)
(подключение, токен, handshake, организации, политика версий уже на `master`).
Сейчас: принять части пакета `kind=invoices` от ВФ_Обмен, сохранить сырьё
в объектное хранилище, показать историю в кабинете. Нормализации нет.

Baseline: `phpunit tests/{Functional,Integration,Unit}/OneC` — 14 тестов,
80 проверок, зелёные (b97beafda, локальная pg+redis).

## Дизайн (одобрен Владельцем 26.11.2026)

**Результат.** Обработка шлёт часть пакета → сервер проверяет токен, оболочку
и совместимость, кладёт тело в хранилище, пишет строку `onec_package`,
отвечает `{accepted, package_id, part, status:"stored", duplicate}`. Владелец
видит в карточке подключения пакеты «частей N из parts_total», предупреждения
обработки и скачивает сырую часть.

**Решения.**

- Только `kind=invoices` (счета на оплату покупателям и от поставщиков).
  Другой `kind` → 422. Выписки, контрагенты — следующие этапы.
- Сырьё — через общий `Shared\Service\Storage\ObjectStorageInterface`,
  глобальный драйвер не трогаем. На проде `s3` (timeweb, регион `ru-1`,
  `docker-compose.prod.yml`, `x-php-env`). Путь
  `onec/{connection_id}/{package_id}/{part}-{sha256}.json.gz`: без даты, чтобы
  повтор попадал в тот же объект.
- Хэш — sha256 исходного тела до gzip. Клиент при повторе шлёт байт-в-байт то же
  тело (контракт). Тот же ключ, тот же хэш → прежний ответ с `duplicate:true`;
  другой хэш → 409 `package_conflict`.
- Ключ идемпотентности — unique `(connection_id, package_id, part)`. Порядок:
  проверка оболочки и согласованности с другими частями пакета → запись объекта
  (вне транзакции) → `INSERT … ON CONFLICT DO NOTHING RETURNING` → при
  конфликте чтение существующей строки и сравнение хэша. EntityManager не
  закрывается, параллельный повтор не даёт 500.
- Части одного пакета обязаны совпадать по `kind`, `period_from`, `period_to`,
  `include_open_outside_period`, `parts_total` → иначе 409 `package_conflict`.
- Подключение без рукопожатия или с другим `base_id` → 409 `base_conflict`;
  статус `error` (последнее рукопожатие `unsupported`) → 422 `unsupported`.
- Перевыпуск токена — новый хэш, старый сразу 401; у отключённого подключения
  перевыпуск возвращает статус `pending`. Отключение = отзыв: хэш заменяется
  случайным, статус `disabled`, старый токен → 401. Аудит обоих действий.
- Скачивание сырой части — владелец подключения или `ROLE_ADMIN`.
- Документы внутри части не разбираются, только `documents` — массив; число
  документов сохраняется.

**Расхождения с исходным ТЗ (и почему).**

- Формат ошибки — плоский `{"error","message"}`, как в опубликованном
  контракте handshake, а не `{"error":{…}}` из `site/src/CLAUDE.md`: контракт
  v1 уже у команды 1С, один формат на оба эндпоинта.
- Интерфейс — Twig, как остальной OneC и соседние модули, не React.
- После отключения — 401 (решение Владельца), код 403 `disabled` в контракте
  больше не выдаётся новыми отключениями.
- Тест «организация пропала из повторного handshake → помечена» уже есть
  (`HandshakeTest::testHandshakeBindsBaseAndPreservesMapping`), дублировать не
  нужно.

**Не делаем сейчас.** Нормализацию счетов, `onec:reprocess`, привязку
организаций к компаниям в UI и проверку ролей `CompanyMember` (только описание
в README), контрагентов, удаление старого сырья, профиль выгрузки.
