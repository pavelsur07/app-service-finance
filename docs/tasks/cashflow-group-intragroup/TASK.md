# Консолидированный ДДС: элиминация по парам и сверка внутригрупповых операций

Поручено Владельцем 25.11.2026. Продолжение задачи `cashflow-group-chart` (закрыта
17.11.2026): группа консолидации, эталон статей и отчёт `GET /finance/reports/cashflow/group`
уже на проде. Классификация — **Large** (меняется финансовая семантика отчёта, новая таблица,
миграция).

## Как сейчас

- Группа — `company_consolidation_member` (головная + участники),
  `ConsolidationGroupFacadeInterface`. Отчёт — `BuildCashflowGroupReport` +
  `CashflowGroupReportQuery`, шаблон `templates/cash/report/cashflow_group.html.twig`, xlsx.
- Внутригрупповая операция = `counterparties.inn` контрагента совпадает с `companies.inn`
  **другой** компании группы. Колонка «Внутригрупповые» = все такие операции;
  «Итого по группе» = сумма компаний минус **все** внутригрупповые.

## Проблема — подтверждена на выгрузках группы Максимедиа, 1–18.11.2026

Владелец выгрузил операции трёх компаний группы (Максимедиа, Информ-ТВ, Телегис) и
сверил вручную:

1. **Расхождение скрывается.** Информ-ТВ получил от Максимедиа 2 600 000 (13.11) и 150 000
   (17.11), а у Максимедиа встречных списаний нет: выписка ВТБ Максимедиа заканчивалась
   12.11. Текущий отчёт исключает и эти поступления → итог группы выглядит правдоподобно,
   хотя данных не хватает 2,75 млн, и итог не сходится с изменением остатков на счетах.
2. **Признак держится на ИНН контрагента, а у части контрагентов ИНН нет.** В выгрузках
   Информ-ТВ и Телегис контрагент «ООО "МАКСИМЕДИА"» без ИНН, у Максимедиа часть контрагентов
   названа строкой вида `7203489830, ООО "МАКСИМЕДИА"`. Такая операция не считается
   внутригрупповой → одна сторона исключается, другая нет → итог группы искажён.
3. **Не видно, какие счета отстают.** Выгрузки были на разные даты: ВТБ Максимедиа по 12.11,
   Сбер Максимедиа по 17.11, Информ-ТВ по 18.11, Телегис по 10.11.

Ожидаемо по выгрузкам (при полных ИНН): 12 внутригрупповых операций, 5 пар на 917 000,
2 поступления без пары на 2 750 000.

## Решение

Принцип МСФО-консолидации: исключаются **сверенные** внутригрупповые обороты, расхождения
показываются отдельно и разбираются, а не прячутся.

1. **Пары считаются при чтении**, детерминированно, без хранения автоматических пар и без
   подписки на события. Пара = списание компании X с контрагентом-компанией Y и поступление
   компании Y с контрагентом-компанией X:
   - суммы равны до копейки, валюта RUB;
   - `0 ≤ дата поступления − дата списания ≤ 5` календарных дней (константа). Поступление
     раньше списания автоматически не сопоставляется;
   - кандидатов несколько → минимальная разница дат, затем более ранняя дата, затем id.
     Жадно, одинаковый вход → одинаковые пары;
   - сопоставление только по сумме без признака контрагента запрещено: одинаковых сумм от
     внешних клиентов много.
   Почему при чтении: внутригрупповых операций за период десятки; `CashTransactionsChanged`
   не покрывает импорт и не предназначен для денежных последствий; хранимые авто-пары
   пришлось бы пересобирать при каждом изменении операций.
2. **Хранятся только ручные решения** — новая таблица (раздел «Модель»): «сопоставить
   вручную» и «разъединить авто-пару». Авто-алгоритм их уважает и никогда не перезаписывает.
3. **Элиминация только по парам.** Колонка «Внутригрупповые» → «Элиминация»: сумма пар
   (авто + ручных) с обратным знаком. «Итого по группе» = сумма компаний + элиминация со знаком.
   Внутригрупповые операции без пары остаются в итоге, строки помечаются ⚠, под отчётом —
   блок «Без пары: N операций, сумма» со ссылкой на сверку и строка «Итого без
   несопоставленных». Автопары определяются в окне [from − 10 дней; to + 10 дней],
   ручные пары учитываются без ограничения по датам. Если видна только одна нога пары,
   её сумма остаётся в итоге периода со статусом «в пути», ссылкой и датой встречной операции.
   Её не включают в «Без пары» и не помечают ⚠. Элиминация применяется при обеих ногах в периоде. Тогда итог группы = изменение суммы остатков компаний, а расхождение
   видно.
4. **Признак внутригрупповой операции не меняется — только ИНН.** Сопоставление по названию
   в отчёт не добавляем: два правила дают два ответа. Вместо этого сверка показывает
   **кандидатов на ИНН** и даёт проставить ИНН контрагенту одним действием:
   - контрагент компании группы без ИНН, чьё нормализованное название (`CounterpartyName`,
     та же нормализация, что у `PreviewCounterpartyNormalizeController`) совпадает с
     названием другой компании группы → предлагаем ИНН этой компании;
   - контрагент без ИНН, чьё название начинается с `^\d{10}(\d{2})?,\s*` и этот ИНН
     принадлежит другой компании группы → предлагаем этот ИНН.
   Запись — через Facade модуля Company (`Counterparty::assignTaxIds`); метода нет — добавить
   в `CounterpartyFacade` и `ARCHITECTURE.md`. Контрагент с ИНН собственной компании
   (переводы между своими счетами) кандидатом не является.
5. **Актуальность данных.** Для каждого активного RUB-счёта компаний группы — дата последней
   не удалённой операции. Блок над отчётом: «Данные по счетам», счёт показывается как
   «Компания · название · ****последние 4 цифры `accountNumber`» (у компаний группы счета
   называются одинаково). Подсветка, если последняя операция счёта отстаёт от самой поздней
   по группе больше чем на 3 дня. У операции без пары — подсказка, если у встречной компании
   есть счёт с последней операцией раньше даты операции: «Максимедиа · ВТБ ****1234 — данные
   по 12.11».

## Модель

`CashIntragroupDecision` (модуль Cash, таблица `cash_intragroup_decision`):

| Поле | Смысл |
|---|---|
| `id` | UUIDv7 из формы — он же ключ повтора |
| `company_id` | **головная** компания группы (граница tenant для IDOR) |
| `type` | enum `PAIR` (ручная пара) \| `UNPAIR` (отказ от авто-пары) |
| `outflow_transaction_id`, `inflow_transaction_id` | `cash_transaction` компаний группы |
| `created_by`, `created_at` | аудит |

- Внутри одной головной компании одна операция входит максимум в одно решение `PAIR`.
  Частичные уникальности: `(company_id, outflow_transaction_id) WHERE type = 'PAIR'` и
  `(company_id, inflow_transaction_id) WHERE type = 'PAIR'`. Третья уникальность —
  `(company_id, type, outflow_transaction_id, inflow_transaction_id)`.
- Решение применяется, только если `company_id` совпадает с текущей головной компанией
  (`headOf`) для компаний обеих операций. Новая голова не видит решения прежней ни в
  действующих, ни в устаревших. Прежние записи сохраняются. При возврате состава с прежней
  головной её решения снова применяются, если обе операции продолжают удовлетворять условиям.
- Отмена решения = удаление строки.
- Решение игнорируется, если транзакция удалена, сменила компанию вне группы, валюту или
  перестала быть внутригрупповой; такие решения сверка показывает как «устаревшие» с
  кнопкой удаления. Каскадов на `cash_transaction` нет.
- Валидация ручной пары (Action, под блокировкой группы `lockedHeadOf()` первой): обе
  транзакции в компаниях группы, разных компаниях, противоположных направлений, RUB, обе
  внутригрупповые по правилу ИНН, ни одна не состоит в другой `PAIR`. Суммы должны совпадать до копейки. При расхождении —
  отказ с ошибкой «Суммы не совпадают: 100,00 и 90,00. Пара возможна только при равных суммах».
  Даты могут различаться, включая поступление раньше списания: показать предупреждение и разрешить пару.
- Ручная пара сильнее авто: транзакции из ручных пар исключаются из авто-алгоритма. `UNPAIR`
  запрещает именно эту пару; транзакции остаются свободными для других кандидатов.

## Экраны

1. **Отчёт** `/finance/reports/cashflow/group` (Twig, как сейчас) и xlsx: колонка
   «Элиминация», ⚠ на строках с операциями без пары, блоки «Данные по счетам», «Деньги в пути (пара за границей периода)», «Без пары»,
   «Итого без несопоставленных». Drill-down ячейки «Элиминация» — список пар.
2. **Сверка** `GET /finance/reports/cashflow/group/reconciliation?from=&to=` (ссылка из
   отчёта):
   - контроль: Σ внутригрупповых поступлений, Σ выплат, разница = Σ операций без пары + Σ денег в пути
     со знаком; не сходится — ошибка на экране и ERROR в лог (это баг);
   - пары: дата/сумма/компания · счёт с обеих сторон, авто/ручная, «Разъединить»
     (авто → `UNPAIR`, ручная → удалить решение);
   - без пары: операция, подсказка про отставание данных, «Сопоставить вручную» (выбор из
     свободных встречных операций противоположного направления компании-контрагента, ±15
     дней, только равные до копейки суммы);
   - кандидаты на ИНН: компания · контрагент · предлагаемый ИНН · компания-владелец ИНН ·
     число операций → «Проставить ИНН»;
   - устаревшие решения → «Удалить».
   POST — `FINANCE_WRITE` + владелец всех компаний группы.

**Доступ** — как у текущего отчёта: владелец всех компаний группы, иначе 403 (роли — issue
#3054, вне этой задачи). Компания вне группы — пояснение, как сейчас.

## Не делаем

- Переводы между своими счетами одной компании (контрагент = своя компания): это
  `CashTransfer`. Связывание импортированных «пополнений своего счёта» в `CashTransfer` —
  отдельная задача.
- Сопоставление n:m (частичные оплаты), подтипы (реализация/заём), элиминацию в ОПиУ и
  Балансе, валюты кроме RUB (как сейчас — отдельно по компаниям).
- Сопоставление по названию контрагента в самом отчёте.
- Изменение отчёта ДДС отдельной компании.

группы; не внутригрупповая операция; чужая валюта; неравные суммы (в том числе разница в одну копейку).

**S7. Разъединение.** «Разъединить» #24↔#15 → обе без пары и после перезагрузки остаются без
пары; удалить решение → пара возвращается.

**S8. Идемпотентность.** Повторный POST с тем же id решения → одна строка, тот же результат.
Повтор «Проставить ИНН» → без изменений.

**S9. Доступ.** Не владелец одной из компаний — отчёт и сверка 403; POST без `FINANCE_WRITE`
— 403; id транзакции другой группы в ручной паре — отказ.

**S10. Регресс.** Отчёт ДДС отдельной компании не изменился. Тест «сумма по компаниям = сумма
их отчётов» остаётся; тест «итог = сумма минус внутригрупповые» заменяется на «итог = сумма
минус пары».

**S11. Граница периода.** Для выплаты 30.11 и встречного поступления 02.12 за ноябрь показать
пару как «в пути» у обеих компаний, дату и ссылку на встречную ногу. В сумму попадает только
ноябрьская выплата. Нет ⚠ и попадания в «Без пары». За ноябрь–декабрь идентификаторы той же
пары сохраняются, обе ноги элиминированы. Аналогично проверить декабрь отдельно и ручную пару
вне десятидневного окна. Контроль сверки учитывает нетто без пары и нетто в пути.

**S12. Смена головной компании.** У первой головы есть ручная пара. После смены головы решение
первой отсутствует в итогах и обоих списках решений новой группы. Новая голова сохраняет PAIR
по тем же операциям. После возврата прежней конфигурации снова применяется решение первой
головы, а обе записи сохраняются под своими company_id.

Тесты: unit — алгоритм пар (S2, ловушки, детерминизм), кандидаты на ИНН, нормализация;
integration — отчёт и сверка (S1–S7); functional — доступ (S9). Минимум — по `CLAUDE.md`.
