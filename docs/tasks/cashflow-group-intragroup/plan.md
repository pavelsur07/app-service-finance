## Stage 1. Автоматические пары, отчёт и экспорт

Риск HIGH-LOCAL. Перед первым рабочим пунктом зафиксировать базу в checkpoint. Критерии — S1–S5, S10 для автоматического расчёта, одинаковые суммы и структура в отчёте и XLSX.

1.1. Начать с тестов чистого алгоритма. Две встречные компании, RUB, равные суммы в копейках, интервал 0–5 календарных дней, жадный выбор по разнице, дате и ID, независимость от порядка входа. Запрещённая пара оставляет обе ноги доступными другим кандидатам.
1.2. Расширить CashflowGroupReportQuery и DTO. Сопоставлять операции целиком, разносить результат по строкам разбивки и прежнему дереву отчёта. Сохранить сумму колонок отдельных компаний, наследование group_code, некодированные статьи, отдельный учёт прочих валют. Операции без пары остаются в итоге.
1.3. На обезличенной фикстуре проверить контроль, последние даты по всем активным RUB-счетам, пустые счета, отставание строго более трёх дней, подсказки. Передать одинаковые данные в XLSX. Отсчёт для подсветки от самой поздней операции группы. В S3 таблица ТЗ заканчивается 17.11 у Беты, хотя ожидается 18.11. Для теста актуальности перенести внешнюю операцию #25 на 18.11, без изменения денег, контрагента и периода.

Статьи фикстуры из core.yaml — OP_IN_CUSTOMERS, INV_IN_INTEREST, OP_OUT_MARKETING, OP_OUT_SALARY, OP_OUT_TAX_OTHER, OP_OUT_OTHER и OP_IN_OTHER. У каждой ноги перевода статья соответствующего направления. Образцы — BuildCashflowGroupReportTest, CashTransactionBuilder, существующий CashflowGroupReportXlsxWriter. Проверки этапа — unit алгоритма, integration отчёта и контроль XLSX. Фокус ревью — знак элиминации, разбивки без двойного счёта, границы периодов, равные суммы от внешнего клиента, чужая валюта.

## Stage 2. Ручные решения и исправление ИНН

Риск HIGH-LOCAL. Критерии — S6–S9, устаревшие решения, адресная отмена и приоритет ручной пары.

2.1. Тесты модели, миграция cash_intragroup_decision, индексы и уникальности PAIR по каждой ноге и уникальность тройки. Builder и проверка схемы. Создатель и время решения сохраняются.
2.2. Сначала тесты действий, затем изменение внутри транзакции под lockedHeadOf активной компании. Перепроверять состав группы, владение и встречные ИНН. Повтор того же UUID и содержания возвращает исходный результат. Подмена ID либо содержания отклоняется. Для конфликтующих команд проверить гонку. При чтении недействительное решение возвращается в список устаревших.
2.3. Кандидаты по CounterpartyNameNormalizer и префиксу из ТЗ. ИНН берётся у проверенной встречной компании. Новый метод CounterpartyFacade сохраняет КПП, повтор с тем же ИНН без побочного эффекта. Две карточки с разными кавычками остаются отдельными. Обновить контракты в ARCHITECTURE.md.

Образцы — ConsolidationGroupFacadeInterface::lockedHeadOf, операции CashTransfer, Counterparty::assignTaxIds. Проверки — module integration Cash и Company, направленные тесты повторов, доступа и миграции. Фокус ревью — транзакционные границы, IDOR, повтор команды, устаревшие ссылки, конфликтующие ИНН. Внешнее ревью по размеру diff этапа.

## Открытые финансовые правила

- Ручная пара −100/+90 допускается по ТЗ. Полное исключение обеих ног изменит нетто группы на 10 ₽, а контроль из S4 перестанет сходиться. Требуется решение Владельца о сумме элиминации и представлении остатка.
- Одна нога за пределами выбранного периода. Требуется правило о том, в каком периоде обе ноги участвуют в элиминации и сверке. Проверить его на переходе месяца и границе S6 (поступление 17.11, выплата 19.11).
