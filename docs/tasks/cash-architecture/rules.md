# Пересмотр правил проекта

Дата: 2026-10-14. Правила, которые мешали улучшениям, найденным при аудите
модуля `Cash` (см. `plan.md`). Принцип: правило, которое нарушает большая часть
кода, не работает как правило — его либо переписывают под реальную практику,
либо закрепляют гейтом. Цифры — grep по `site/src` на дату документа.

Изменения внесены в `CLAUDE.md`, `PATTERNS.md` и шапку `ARCHITECTURE.md` тем же
PR, что добавил этот файл. Колонка «Статус» показывает, что внесено, а что

## Правила, которые не совпадали с реальностью

### 1. Список транспортов Messenger

- **Было:** «ровно один транспорт: `async_sync` / `async_pipeline` / `async_ads`».
- **Факт:** в `messenger.yaml` шесть транспортов: ещё `ingest_fetch`,
  `ingest_normalize`, `async_wb_finance`.
- **Чем мешало:** новое сообщение Ingestion или WB по правилу ушло бы не в тот
  транспорт.
- **Стало:** таблица всех шести транспортов в `CLAUDE.md` и `PATTERNS.md` §10,
  ссылка на таблицу воркеров в `ARCHITECTURE.md`.

### 2. «Query-класс возвращает `QueryBuilder`, не массив»

- **Факт:** 96 публичных методов Query возвращают массив, DTO или скаляр, 5 —
  `QueryBuilder`. При этом `PATTERNS.md` §6 сам называет Query инструментом для
  агрегаций и отчётов, которые через Pagerfanta не отдают.
- **Стало:** список для UI — `QueryBuilder`; агрегат и отчёт — readonly-DTO или
  `list<DTO>`; нетипизированный `array` в новом коде — нельзя.

### 3. «UUID v7 в конструкторе»

- **Факт:** в 41 сущности ID приходит в конструктор снаружи — для
  идемпотентности, дедупликации импорта и Builder'ов в тестах. Пример в
  `PATTERNS.md` §3 сам генерирует ID в Action.
- **Стало:** ID передаёт вызывающий код или генерирует конструктор при
  `?string $id = null`; переданный ID — `Assert::uuid()`.

## Правила, которые противоречили друг другу

### 4. «Бизнес-логика в Entity — только инварианты в конструкторе»

- **Факт:** 254 публичных метода сущностей — не геттеры и не сеттеры. Пример
  доменных событий в `PATTERNS.md` §20 (`Deal::changeStatus()`) и пример §11
  (`close()`, `reopen()`) сами нарушали правило; `ARCHITECTURE.md` называет
  `CashTransaction::replaceSplits()` точкой проверки инвариантов.
- **Чем мешало:** логика уезжала в сервисы по 800+ строк; Money и доменные
  события из `plan.md` по правилу некуда положить.
- **Стало:** Entity защищает инварианты в конструкторе и методах изменения
  состояния; внутри запрещены Repository, сервисы, Messenger, EntityManager и
  изменение других агрегатов.

### 5. «`flush()` только в Action» против «batch — `flush()` каждые N»

- **Факт:** `flush` в 85 файлах вне Action/Handler/Command, из них 14 —
  репозитории. Оба правила были в `CLAUDE.md`, выполнить их одновременно нельзя.
- **Почему важно:** в ORM 3 `flush()` сохраняет весь UnitOfWork — `flush` в
  сервисе сохраняет чужие незавершённые изменения.
- **Стало:** раздел «Транзакции» в `CLAUDE.md`: `flush` / `wrapInTransaction` —
  в Action, MessageHandler, консольной Command; пакетный сервис отдаёт порции,
  `flush` делает вызывающий код; Repository и сервисы — только
  `persist`/`remove`.
- **Осталось:** PHPStan-правило на `flush` — этап 4 `plan.md`.

### 6. «В Controller нет `try/catch`» и ошибки только в JSON

- **Факт:** 117 контроллеров рендерят Twig, 65 отдают JSON; 47
  `catch (\DomainException)` в контроллерах показывают flash — формально
  нарушение, по сути корректно.
- **Стало:** JSON-контроллер — без `try/catch`; HTML-контроллер может ловить
  конкретное доменное исключение для flash/ошибки формы;
  `catch (\Throwable)` ради flash — нельзя.
- **Осталось:** ветка в `ExceptionListener` для HTML-запросов (flash + redirect),
  после которой catch в HTML-контроллерах станет не нужен.

## Правила, которые мешали границам модулей и тестируемости

### 7. Facade `final` без интерфейса

- **Факт:** 24 Facade и 1 интерфейс (`MarketplaceAnalyticsFacadeInterface`).
  Моки final-фасадов держатся на `dg/bypass-finals`, а baseline считает каждый
  `createMock` на final-классе ростом.
- **Стало:** новый Facade — `{Name}FacadeInterface` + `final` реализация;
  потребители зависят от интерфейса.

### 8. Facade возвращает Entity

- **Факт:** фасады отдают `Company`, `Counterparty`, `ProjectDirection`,
  `Product`; поэтому `ModuleBoundaryRules` не может закрыть Entity (около 230
  записей по проекту).
- **Стало:** новые методы Facade возвращают DTO, Enum или скаляры; старые не
  переделываются без задачи.
- **Осталось:** PHPat-правило на Entity в сигнатурах новых методов.

## Процесс

### 9. Baseline при введении нового гейта

- **Факт:** baseline — 2334 записи. Новое правило в момент введения неизбежно
  добавляет записи и выглядит в CI как регресс; `[baseline-grow]` смешивает
  «новое нарушение» и «новое правило показало старые».
- **Стало:** новый гейт вводится одним PR вместе со своим baseline под
  `[baseline-grow]`, в описании — идентификатор правила и число записей; рост
  по другим идентификаторам в том же PR не допускается. Механизм CI не менялся.

### 10. `ARCHITECTURE.md` читать целиком

- **Факт:** 3861 строка; в разделах контрактов перемешана история этапов
  («Stage 7.6.2 connects…»). `AGENTS.md` уже говорил «только нужный раздел», а
  `CLAUDE.md` — нет.
- **Стало:** `CLAUDE.md` требует читать раздел затронутого модуля и нужные общие
  разделы; новая история этапов — только строкой в «Changelog».
- **Осталось:** перенести уже накопленную историю из разделов в «Changelog» —
  отдельная задача, текст большой и требует аккуратной сверки.

## Мета-правило

**Стало** (`CLAUDE.md`, «Правило без гейта — правило ревью»): правило либо
проверяется машинно, либо явно считается правилом ревью; правило, которое
нарушает больше половины кода, пересматривается отдельным PR, а не
игнорируется.

**Почему:** аудит показал, что правила с гейтом соблюдаются (strict_types,
границы Facade), а без гейта — уплыли (`flush`, логика в Entity, Query, ID в
конструкторе).
