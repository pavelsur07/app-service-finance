# Системный мониторинг интеграций

Статус: draft

Дата: 2026-07-25

Назначение: ТЗ для дизайн-демо и план последующей реализации

Основной пользователь: системный администратор (`ROLE_SUPER_ADMIN`)

## 1. Контекст

В системе есть несколько провайдеров и технических pipeline:

- Wildberries;
- Ozon Seller;
- Ozon Performance;
- Alfa Bank;
- Telegram;
- LLM;
- новые Ingestion pipeline;
- старые и ручные pipeline.

Просмотр каждого кабинета и каждой ошибки по отдельности неэффективен. Один
бизнес-источник также может обслуживаться несколькими техническими pipeline.
Например, финансовый отчёт Wildberries и Ozon Performance загружаются разными
модулями.

Нужен один административный раздел, который сначала показывает состояние всей
системы, затем позволяет провалиться в конкретную интеграцию, кабинет, запуск и
ошибку.

## 2. Цели

- Показать все типы интеграций на одном экране.
- Показать покрытие загрузки по всем активным кабинетам за выбранный день.
- Отдельно показывать количество затронутых кабинетов и количество событий
  ошибок.
- Выделять финальные ошибки, ошибки авторизации и пропущенные загрузки.
- Не считать временный retry финальной ошибкой.
- Не показывать неработающую или незапланированную интеграцию зелёной.
- Дать переход к конкретному кабинету, запуску, pipeline и endpoint.
- Не раскрывать токены, API-ключи и полные внешние payload.

## 3. Вне scope

- Автоматический перезапуск интеграции из интерфейса.
- Редактирование credentials.
- Просмотр полных request/response body.
- Замена существующих retry, cooldown, Messenger и cron-механизмов.
- Изменение финансовой семантики загружаемых данных.
- Production deploy, миграции и backfill.
- Отдельная аналитическая платформа, ClickHouse, Elasticsearch или новый
  observability-стек.
- Уведомления в Telegram/email в первой версии.

## 4. Термины

| Термин | Значение |
|---|---|
| Тип интеграции | Бизнес-тип данных: финансы, начисления, остатки, реклама, каталог, банк, уведомления, AI |
| Провайдер | Wildberries, Ozon Seller, Ozon Performance, Alfa Bank, Telegram, LLM |
| Pipeline | Технический процесс загрузки и обработки данных |
| Endpoint | Конкретный внешний HTTP endpoint |
| Кабинет | Подключение компании к внешнему провайдеру |
| Логический запуск | Одна загрузка для pipeline, кабинета и периода данных |
| Попытка | Один retry внутри логического запуска |
| Дата данных | День или период, за который запрашиваются данные |
| Операционный день | День фактического запуска и возникновения ошибки |
| Покрытие | Успешные и валидно пустые загрузки / ожидаемые загрузки |
| Затронутый кабинет | Уникальный кабинет, у которого есть актуальная проблема |
| Событие ошибки | Одна зафиксированная неуспешная попытка |

## 5. Главный пользовательский сценарий

1. Системный администратор открывает отчёт утром.
2. Видит общую картину по всем типам интеграций.
3. Замечает красную или жёлтую ячейку.
4. Открывает выбранный тип данных и провайдера.
5. Получает список проблемных компаний и кабинетов.
6. Открывает логический запуск.
7. Видит, на каком этапе и endpoint произошла ошибка.

## 6. Информационная архитектура

Нужно три уровня детализации:

```text
Все типы интеграций
    → тип данных + провайдер
        → компания + кабинет + pipeline
            → логический запуск + попытки + endpoint + ошибка
```

Первый экран не должен содержать отдельную строку для каждого endpoint или
кабинета.

## 7. Демо для дизайнера

### 7.1. Формат

Подготовить три связанных HTML-макета:

1. Общая сводка.
2. Детализация интеграции.
3. Детализация запуска.

Рекомендуемые файлы:

```text
site/screens/admin-integration-monitoring-overview.html
site/screens/admin-integration-monitoring-detail.html
site/screens/admin-integration-monitoring-run.html
```

Требования к демо:

- только фиктивные данные;
- desktop 1440 px, минимальная рабочая ширина 1280 px;
- существующий admin shell и UI Kit;
- без backend, БД и внешних API;
- без React и нового Vite entry;
- без новой UI-библиотеки;
- переходы между тремя макетами должны быть кликабельными;
- секреты и реальные названия клиентов не использовать.

## 11. Обязательные состояния макета

Дизайнер должен показать минимум по одному примеру:

1. Полностью успешно.
2. Выполняется.
3. Повторная попытка.
4. Частично успешно.
5. Финальная ошибка.
6. Ошибка авторизации.
7. Просрочено.
8. Валидный пустой результат.
9. Ручной запуск.
10. Реализовано, но не добавлено в расписание.
11. Не реализовано.
12. Нет активных кабинетов.
13. Loading.
14. Ошибка загрузки самого admin-отчёта.

Нельзя использовать один общий статус `Нет данных`. Следует различать:

- API успешно вернул 0 записей;
- загрузка ещё выполняется;
- загрузка не запускалась;
- ожидаемый запуск пропущен;
- нет активных кабинетов;
- ручной режим;
- загрузчик не реализован.

## 12. Визуальные требования

- Использовать существующий admin shell.
- Использовать существующие KPI, Card, Table, StatusPill, Filter chip,
  Empty state и Pagination из UI Kit.
- Статус всегда показывать цветом, текстом и иконкой/точкой.
- Красный использовать только для проблемы, требующей внимания.
- Жёлтый использовать для retry, partial и временной задержки.
- Зелёный использовать только для подтверждённого успешного результата.
- Серый использовать для ручного, отключённого и нереализованного режима.
- Все числовые значения в таблицах использовать с `tabular-nums`.
- Не вводить новые цвета, размеры и компоненты, если задача решается текущим
  UI Kit.
- Не использовать emoji-иконки.
- Длинные ошибки сокращать до одной строки и раскрывать по действию.
- Матрица и список проблем должны помещаться в основной сценарий без
  декоративных графиков.

показываются отдельные pipeline `MarketplaceAds` и `Ingestion Analytics`.

Публичные отчётные API и upload endpoint не следует смешивать с покрытием

### 13.5. Интеграции без загрузчика

- В enum объявлены `Яндекс.Маркет` и `СберМегаМаркет`, но HTTP-загрузчики не
  найдены.
- Для MoySklad есть конфигурация подключения, но загрузчик не найден.

Их нужно показывать как `Не реализовано`, а не как `Успешно`.

### 13.6. Расхождение расписания

Комментарий cron для Ozon realization говорит `10-е число`, но выражение
`0 6 5 * *` запускает команду пятого числа. При реализации каталога источником
истины должно быть явно согласованное расписание, а не комментарий.

## 14. Почему существующих таблиц недостаточно

Состояние сейчас распределено между:

- `MarketplaceFinancialReportSyncStatus` и историей ошибок;
- `Ingestion\SyncJob`;
- `InventorySnapshotSession`;
- `MarketplaceAds\AdLoadJob` и batch;
- `MarketplaceRawDocument`;
- `MarketplaceJobLog`;
- `Cash\ImportLog`;
- `Telegram\ImportJob`;
- обычными application logs.

У этих сущностей разные статусы, периоды, идентификаторы и детализация ошибок.
Постоянный отчёт через большой `UNION ALL` будет хрупким и усложнит добавление
новых интеграций.

## 15. Минимальная техническая архитектура

### 15.1. Модуль

Создать отдельный модуль:

```text
site/src/IntegrationMonitoring/
site/templates/admin/integration_monitoring/
site/tests/Integration/IntegrationMonitoring/
```

Модуль не управляет интеграциями и не меняет их поведение. Он только:

- содержит каталог;
- принимает события жизненного цикла запуска;
- хранит нормализованный статус;
- строит административный read model.

### 15.2. Каталог интеграций

Каталог хранить в PHP-коде, не в редактируемой таблице.

Для каждого pipeline определить:

- `integrationType`;
- `provider`;
- `pipelineCode`;
- человекочитаемое название;
- список стабильных `endpointCode`;
- режим: `scheduled`, `manual`, `disabled`, `not_implemented`;
- периодичность;
- SLA;
- источник списка ожидаемых кабинетов;
- считается ли пустой ответ успешным.

Каталог отвечает на вопрос «что должно работать», а журнал — «что фактически
произошло».

Не следует автоматически извлекать каталог из PHP-классов или cron-файла:
такой runtime-анализ будет хрупким и не сможет корректно описать бизнес-тип,
SLA и ручные режимы.

### 15.3. Хранилище

Для MVP достаточно двух таблиц.

#### `integration_runs`

Одна строка — один логический запуск pipeline для кабинета и периода данных.

Минимальные поля:

- `id`;
- `company_id`;
- `connection_ref`;
- `integration_type`;
- `provider`;
- `pipeline_code`;
- `data_from`;
- `data_to`;
- `status`;
- `expected_at`;
- `started_at`;
- `completed_at`;
- `records_count`;
- `attempts_count`;
- `last_error_code`;
- `last_error_message`;
- `last_http_status`;
- `correlation_id`;
- `created_at`;
- `updated_at`.

Уникальность логического запуска:

```text
company_id + connection_ref + pipeline_code + data_from + data_to
```

Это предотвращает создание нескольких «запусков» при Messenger retry.

#### `integration_error_events`

Append-only история попыток:

- `id`;
- `run_id`;
- `occurred_at`;
- `attempt`;
- `endpoint_code`;
- `http_method`;
- `error_class`;
- `error_code`;
- `http_status`;
- `retryable`;
- `final`;
- `message`;
- `response_excerpt`;
- `correlation_id`.

Отдельная таблица всех успешных HTTP-вызовов в MVP не нужна. Список доступных
endpoint берётся из каталога, а метрики запуска — из `integration_runs`.

### 15.4. Статусы запуска

Хранимые статусы:

```text
queued
running
retrying
success
empty
partial
failed
auth_failed
```

Вычисляемые состояния:

```text
missed
manual
not_scheduled
disabled
not_implemented
no_active_connections
```

Вычисляемые состояния не нужно сохранять в каждом запуске: они зависят от
каталога, расписания, текущего времени и наличия активных подключений.

### 15.5. Публичная граница модуля

Другие модули не должны напрямую создавать monitoring entity. Использовать
небольшой `IntegrationMonitoringFacade`:

- начать или зарегистрировать запуск;
- отметить retry;
- отметить успешное завершение;
- отметить валидный пустой результат;
- отметить partial/final/auth failure.

Facade принимает скаляры или DTO и не меняет retry-логику вызывающего pipeline.

### 15.6. Где записывать события

Запись выполнять на границах существующего логического pipeline:

- при старте handler;
- при получении retryable exception;
- при успешном терминальном завершении;
- при partial success;
- при final/auth failure.

Не нужно оборачивать глобальный Symfony HttpClient в первой версии. Глобальный
decorator не знает бизнес-период, кабинет и pipeline и добавит больше сложности,
чем пользы.

### 15.7. Вычисление покрытия

Для scheduled-интеграции:

```text
ожидалось = активные подходящие кабинеты
покрыто = success + empty
покрытие = покрыто / ожидалось
```

Правила:

- ручные интеграции исключаются из daily denominator;
- `empty` считается успехом только если это разрешено каталогом;
- `retrying` не считается финальной ошибкой, но ещё не считается покрытием;
- `missed` появляется после SLA, если ожидаемый запуск отсутствует;
- количество ошибок считается отдельно от количества затронутых кабинетов;
- день и SLA считать в `Europe/Moscow`;
- `data_from/data_to` не смешивать с `occurred_at`.

### 15.8. Группировка ошибок

Fingerprint ошибки:

```text
provider
+ endpoint_code
+ error_class
+ error_code
+ http_status
```

Свободный текст сообщения не должен быть единственным ключом: номера объектов,
UUID и даты создадут множество ложных уникальных групп.

### 15.9. Безопасность

- Все admin-контроллеры явно требуют `ROLE_SUPER_ADMIN`.
- Cross-company запросы допустимы только внутри этого защищённого модуля.
- Не отдавать endpoint credentials и query-параметры с секретами.
- Не хранить request body.
- Не хранить полный response body.
- `response_excerpt` ограничивать по длине и очищать от токенов/PII.
- В логах использовать `companyId`, `connectionRef`, `runId` и
  `correlationId`, но не API-ключи.

### 15.10. Read model и UI

- Агрегации и отчёты выполнять через DBAL Query-классы.
- Списки кабинетов, запусков и ошибок обязательно пагинировать через Pagerfanta.
- Первый экран рендерить server-side Twig.
- Фильтры передавать query-параметрами.
- Для первой версии использовать отдельные detail-страницы.
- React, SPA, charts и websocket не нужны.
- Автообновление можно добавить позже; для MVP достаточно кнопки `Обновить`.

## 18. Best practices

### Продуктовые

- Сначала показывать затронутые кабинеты, затем число событий ошибок.
- Считать покрытие только по ожидаемым scheduled-запускам.
- Не смешивать business date и фактическое время ошибки.
- Не считать `empty` ошибкой, если пустой день допустим.
- Показывать `missed`, даже если исключение не возникало.
- Ручные и нереализованные интеграции показывать нейтрально.
- Ошибки группировать по стабильному fingerprint.
- Приоритет определять по худшему актуальному статусу.

### Backend

- Один логический run на кабинет/pipeline/период.
- Retry хранить как попытки одного run.
- Error events делать append-only.
- Каталог хранить в коде.
- Межмодульную запись проводить только через Facade.
- Read model строить через DBAL.
- Списки пагинировать через Pagerfanta.
- Стабильные endpoint codes использовать вместо динамических URL.
- Не менять существующую retry-логику ради мониторинга.
- Ошибка записи мониторинга не должна скрывать исходную ошибку pipeline.

### Security

- Только `ROLE_SUPER_ADMIN`.
- Никаких API-ключей, токенов и request body.
- Response excerpt ограничивать и очищать.
- Не показывать signed download URL.
- Не использовать реальные данные клиентов в дизайнерских заглушках.

### Frontend

- Twig-first.
- Существующий UI Kit-first.
- StatusPill вместо цвета без текста.
- Отдельные страницы вместо сложного drawer в MVP.
- Query-параметры вместо client-side state manager.
- Кнопка обновления вместо websocket/polling в MVP.
- Никаких новых chart/UI-библиотек.
- Loading, empty, error и partial states проектировать сразу.

### Эксплуатация

- Использовать `Europe/Moscow` для SLA и операционного дня.
- Структурированно логировать `runId`, `companyId`, `connectionRef`,
  `pipelineCode` и `correlationId`.
- 429/timeout во время retry логировать как warning, а не как incident.
- Финальный неисправимый сбой логировать как error.
- Не строить алерт по накопленному историческому числу ошибок.
- Retention и автоматические алерты добавлять после измерения реального объёма.

## 19. Что не нужно усложнять

- Не создавать отдельный monitoring-adapter для каждого HTTP-клиента.
- Не вводить generic event bus только для мониторинга.
- Не хранить каждый успешный HTTP-вызов в отдельной таблице.
- Не делать динамический конструктор интеграций в admin.
- Не использовать runtime reflection для поиска endpoint.
- Не переносить существующие pipeline в новый модуль.
- Не переписывать старые status-таблицы.
- Не делать исторический backfill обязательным для запуска MVP.
- Не добавлять ClickHouse, Elasticsearch, Grafana или новую очередь.
- Не делать SPA.

## 20. Критерии приёмки результата

Пользователь должен:

1. За 5–10 секунд понять состояние интеграций.
2. Увидеть все типы интеграций без перехода по разделам.
3. Понять, где проблема: тип данных, provider, pipeline или кабинет.
4. Видеть количество затронутых кабинетов отдельно от количества ошибок.
5. Перейти к списку проблемных кабинетов.
6. Открыть запуск и увидеть endpoint и причину.
7. Отличить retry, final failure, valid empty и missed.
8. Не увидеть секреты или полный внешний payload.
9. Не получить зелёный статус для незапущенной интеграции.

## 21. Открытые решения перед реальной реализацией

Для демо эти вопросы не блокируют работу. Перед Stage 2 нужно подтвердить:

1. SLA для каждого scheduled pipeline.
2. Какие подключения входят в expected denominator.
3. Сколько хранить историю runs и errors.
4. Нужен ли исторический импорт из существующих status-таблиц.
5. Какие integration groups входят в первый production rollout.

Рекомендуемые значения по умолчанию:

- timezone: `Europe/Moscow`;
- manual-интеграции исключить из daily coverage;
- исторический backfill не делать в MVP;
- начать с WB Finance, Ozon Finance/Accrual и рекламы;
- retention определить после первого месяца измерения объёма.
