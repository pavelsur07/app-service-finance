# Воронка продаж Ozon и WB — план задачи

Статус: этапы 4 (Ozon) и 1 (WB) — код готов 18.11.2026, на проде с 18.11.2026 (#3060), ждут живой проверки; этап 5 — на проде 18.11.2026 (#3061, исправление #3064); этап 6 — на проде 18.11.2026 (#3063); этап 2 не нужен
(реклама WB уже грузится на master ресурсом `wb.ads.daily`); этап 3 не начат (нужна форма отказа WB кабинету без «Джема»).

Решение Владельца 18.11.2026: `/v1/analytics/data` грузим; кабинет, которому Ozon метрики не
отдаёт, пропускаем без ошибки. Поэтому этап 4 не ждёт проверки тарифа и сделан первым.

## 1. Задача

Собирать по каждому товару и дню воронку: показы → переходы в карточку → корзины → заказы → выкупы,
с разбивкой «всего / из поиска / из рекламы», по Ozon и WB.

Исходное состояние (проверено по коду 18.11.2026):

- `ozon-fetcher` грузит сырьём поисковую аналитику (`ozon.analytics.queries`, `.details`), рекламу
  (`ozon.ads.daily`, `ozon.ads.statistics`), заказы и возвраты. Общих показов, переходов и корзин нет.
- `wb-fetcher` грузит финансовые отчёты и рекламу (`wb.ads.daily`, с `/adv/v3/fullstats`). Воронки и
  поиска в нём нет.
- Нормализации воронки и экрана нет ни по одному маркетплейсу.

## 2. Что считаем результатом

1. В S3 каждый день появляется сырьё воронки по всем включённым кабинетам WB и Ozon, пропуски видны
   в витрине покрытия.
2. В БД Symfony есть дневная таблица воронки по товару с источником (всего / поиск / реклама),
   пересчитываемая из сырья идемпотентно.
3. Есть экран «Воронка» (отчёт R9): товар × ступени за период, конверсии между ступенями.
4. Документация сервисов описывает методы, лимиты, глубину и задержку по живым ответам, а не по
   спецификации.

## 3. Источники данных

| Ступень | WB | Ozon |
|---|---|---|
| Показы всего | нет в API | `/v1/analytics/data` — только Premium Plus (гипотеза, этап 0) |
| Переходы в карточку, корзины | `POST /api/analytics/v3/sales-funnel/products` | то же |
| Заказы, выкупы, отмены | тот же метод; итог — отчёт о реализации (уже грузится) | отправления и возвраты (уже грузятся) |
| Поиск: позиция, видимость, переходы, корзины, заказы | `search-report/*` — только «Джем» | `ozon.analytics.queries`, `.details` (уже грузятся) |
| Реклама: показы, клики, корзины, заказы | `GET /adv/v3/fullstats` | `ozon.ads.statistics` (уже грузится) |

Методы WB взяты из зеркала официальной OpenAPI-спецификации (обновлено 18.11.2026); портал WB
напрямую не открылся. Всё, что ниже помечено «гипотеза», подтверждается на этапе 0.

## 4. Этапы

Каждый этап — отдельный PR, начинается с тестов, заканчивается обновлением документации сервиса.
Включение — сначала кабинет 3f4d87cc, затем остальные после чистой ночи.

### Этап 0. Живые проверки (без кода)

Что делаем: по одному запросу на чтение к каждому методу, фиксируем форму ответа и ограничения.

- Ozon: тариф Premium у кабинетов; `/v1/analytics/data` с метриками воронки на кабинете с Premium Plus.
- WB воронка: принимает ли `sales-funnel/products` период в один день; пагинация; поля.
- WB токен: тип (персональный / базовый) и категории «Аналитика», «Продвижение» у каждого кабинета.
- WB «Джем»: ответ `search-report/*` на кабинете с подпиской и без неё.
- WB реклама: форма `/adv/v3/fullstats`; ходит ли Symfony к нему через общий лимитер.

Результат: факты в `services/wb-fetcher/docs/wb-api.md` и `services/ozon-fetcher/docs/ozon-api.md`;

### Этап 5. Нормализация в Symfony

Что делаем: дневная таблица воронки в новом модуле `MarketplaceFunnel`, перевод из сырья через канал фактов.

- Сервисы публикуют фактами `ozon.analytics.funnel` (запись = SKU дня) и `wb.analytics.funnel` (запись =
  карточка дня); день Ozon без тарифа — одна запись `…:unavailable`.
- Ключ `mfn_row`: компания, кабинет, день, товар (идентификатор маркетплейса), источник; первичный ключ в БД.
  Источник пока один — `total`; поиск и реклама добавляются строками с другим `source`.
- Пересчёт — замена дня под блокировкой, не дельта.
- Товар без листинга сохраняется с идентификатором маркетплейса; листинг находит экран (этап 6).
- Гейт 09:43 МСК: день с фактами не переведён; строки таблицы расходятся с переведённым.

Результат: таблица воронки заполнена за загруженный период по всем кабинетам с фактами.

Отклонения от плана: сущности — только схема (таблицы пишет DBAL, как у переводчиков), Builder не нужен;
гейт сверяет таблицу с контрольной суммой перевода, а не перечитывает сырьё; запросов чтения по компании
в модуле ещё нет — тест изоляции проверяет, что строки чужой компании не попадают в выборку.

- [x] Тест «повторный перевод дня → те же строки»; новая ревизия заменяет день (тест).
- [x] Тест изоляции компаний: строки чужой компании не видны.

## 5. Куда не лезем

- Легаси `Marketplace`, `Ingestion`, `MarketplaceAds`: загрузку рекламы WB из Symfony не переносим и
  не выключаем, отчёты на ней не трогаем.
- Уже работающие ресурсы `ozon-fetcher` и финансовые ресурсы `wb-fetcher` — без изменений.
- Экономика SKU, ОПиУ, сверки рекламы: воронка в них не подмешивается.
- Покупка подписок («Джем», Premium Plus) и ручная загрузка выгрузок из кабинета Ozon.
- Групповые отчёты WB (`grouped/history`), CSV-отчёты «Аналитика продавца», кластеры рекламы
  (`normquery`), плоская статистика v4 — только по отдельному запросу.
- Данные покупателей: в сырьё воронки они не попадают, проверяется на этапе 0.

## 6. Что проверяем на каждом этапе

- Лимиты: в установившемся режиме нет 429; общий с Symfony лимит не съедается сервисом.
- Потери: день, выпавший из окна истории, виден как пропуск, а не молча отсутствует.
- Идемпотентность: повтор задачи и рестарт сервиса не дают дублей и не теряют страницы.
- Секреты: токены и заголовки авторизации не попадают в журнал и сырьё.
- Деплой: после выката в журнале есть «Деплой завершён», контейнеры на новом образе.
- Наблюдение: первая ночь после включения каждого кабинета сверяется по витрине покрытия.

## 7. Риски

- Базовый токен WB даёт 2 запроса в час на воронку: догон истории на нём нереален — тип токена
  проверяется на этапе 0.
- Однодневный период в `sales-funnel/products` — гипотеза. Запасной путь — `products/history`
  (20 карточек на запрос, только последняя неделя): дороже по запросам и без догона истории.
- Выкупы WB дозревают дольше 30 дней: окончательные цифры берём из отчёта о реализации, воронка
  показывает состояние на дату перечитывания.
- Показов «всего» у WB нет: первая ступень общей воронки WB — переходы в карточку.

## 8. Решения Владельца

- Тариф Premium по кабинетам Ozon и наличие «Джема» по кабинетам WB (нужно для этапа 0).
- Ключи для живых проверок этапа 0 (только чтение).
