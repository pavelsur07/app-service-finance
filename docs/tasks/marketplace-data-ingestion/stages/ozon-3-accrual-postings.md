# Этап 3 (Ozon). Начисления по отправлениям — raw в `ozon-fetcher`

Риск: MEDIUM (новый ресурс сервиса и миграция его БД; БД Symfony, ОПиУ и загрузка Symfony не
затрагиваются). `stage_base_commit`: `4b590663b`. Ветка `feat/ozon-fetcher-accrual-postings`.
Поручение Владельца 21.10.2026: «Этап 3 — составь подробный план и приступай автономно». Общий план —
`../plan-ozon.md`.

## 1. Какую задачу решаем

Начисления by-day (уже в `ozon-fetcher`) отвечают на вопрос «что Ozon начислил за день». Для
юнит-экономики и недельного анализа нужен второй разрез — **«что Ozon начислил по каждому
отправлению»**: комиссия, логистика, возвраты конкретного заказа, даже если они пришли через недели.
Это даёт `POST /v1/finance/accrual/postings`.

**Уточнение к общему плану.** План считал, что Symfony этот метод грузит. Это не так: коннектор
Symfony на него бросает `LogicException` («require explicit posting_numbers»), вызывает его только
ручная команда-проба. Значит, этап 3 — **новые данные**, а не дублирование Symfony; переключать в
Symfony нечего.

## 2. Что известно о методе (живая проверка 21.10.2026, тестовый ключ Владельца, только чтение)

- Запрос: `{"posting_numbers": [...]}` — от 1 до 200 номеров; 201 → 400 `value must contain between 1
  and 200 items`. Даты в запросе нет, пагинации нет.
- Ответ: `{"posting_accruals": [{"posting_number": "...", "accruals": [...]}]}` — по элементу на
  каждый запрошенный номер, в том числе с пустым `accruals` (63 из 63, 88 из 88).
- Начисление: `type_id`, `accrued` (объект), `accrual_date`, `sku`, `quantity`, `seller_price`.
  До 8 начислений на отправление.
- Начисления появляются после доставки или отмены (у отмен — логистика) и копятся неделями: у
  отправлений 19.10 их ещё нет, у 01.10 даты начислений с 03.10.

## 3. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Ресурс | `ozon.finance.accrual-postings`, `period_key` — день МСК **создания отправлений** | тот же день, что у заказов: номера берутся из них, покрытие и перезагрузка — по дням |
| Откуда номера | из raw заказов `ozon.orders.fbo` и `ozon.orders.fbs` того же дня и кабинета (текущая загруженная ревизия), без запросов к Ozon | номера уже загружены; повторно читать списки — удвоить запросы |
| Как найти страницы заказов | новый столбец `fetch_task.content_pages` — sha256 страниц текущей ревизии через запятую, пишется при `done`; по sha256 — объект в `raw_object` → S3 | `content_hash` необратим, а страницы ревизии могут лежать в разных попытках (продолжение после сбоя); список хешей — техническое состояние (`services/AGENTS.md` §9), без денег и ПДн |
| Чтение S3 | `rawstore.Get(uri)` — GetObject + gunzip + проверка sha256 | неизменяемый raw, проверка целостности |
| Порции | номера дня FBO+FBS — без дублей, по возрастанию, по 200; страница = порция; курсор — `отпечаток списка:последний номер`; список изменился между попытками — день заново | детерминированные страницы → ревизии сравнимы; продолжение по чужому списку пропустило бы новый номер (ревью) |
| Проверка ответа | `posting_accruals` — массив; каждый номер ответа — из запроса; номеров в ответе ровно столько, сколько запрошено | живой ответ возвращает все; меньше — тихая потеря, это `invalid_response` |
| Заказы дня ещё не загружены | `not_ready`, повтор через час; также если ревизия заказов начата до конца дня (первая страница ревизии раньше полуночи МСК следующего дня, `content_started_at`); ревизия без списка страниц (до миграции) — заказы дня на перезагрузку | порядок без жёсткой связи задач; вчерашний день — только после ночного дочитывания заказов (ревью) |
| Пустой день (нет отправлений) | `done` с одной служебной страницей `{"posting_accruals": []}` без запроса к Ozon | покрытие видит день загруженным |
| Расписание | ensure — дни с `ORDERS_FROM` до **вчера** (сегодня начислений почти нет), низкий приоритет; раз в сутки перечитываются **45 дней** (`ACCRUAL_POSTINGS_DAYS`), обычный приоритет | начисления копятся неделями, возвраты — до месяца и дольше |
| Лимит | `/v1/finance/accrual/postings` — старт 0,2 запроса/с, пол 0,05, потолок 1 | лимит метода не опубликован; объём мал: крупный кабинет ≈ 5 запросов на день × 45 = 225 в сутки |
| Включение | Symfony: параметр `ozon_fetcher.accrual_postings_companies` (как у заказов): сначала `3f4d87cc`, затем `['*']`; ресурс выдаётся только кабинетам, которым выданы заказы | без заказов ресурсу нечего грузить |
| Снятый с кабинета ресурс | как у заказов — `resource_disabled`, в Ozon не ходит | единое правило |

## 5. Что считаем выполненной работой

По всем кабинетам Ozon в raw `ozon-fetcher` есть начисления по каждому отправлению с 18.10, раз в
сутки перечитываются последние 45 дней; ни одна порция не теряется молча (ответ сверяется с
запросом); задача не ходит в Ozon, пока заказы дня не загружены, и не ходит вовсе, если ресурс снят с
кабинета; загрузка заказов и финансов не замедлилась; гейты зелёные; ревью (отдельная сессия и Codex)
без BLOCKER/IMPORTANT.

## 7. Риски

- **Права S3-ключа сервиса на чтение** не проверены: если пользователь бакета только пишет, задачи
  уйдут в повтор `store` (WARNING) — видно на шаге с одним кабинетом, чинится правами бакета (Владелец).
- **Миграция БД сервиса** — аддитивный столбец с пустым значением по умолчанию, обратима
  (`DROP COLUMN`); старые `done`-задачи без `content_pages` — их дни дадут `not_ready` до ближайшей
  перезагрузки заказов (сегодня — каждый час, 30 дней — ночью), этого достаточно.
- **История до 18.10** не появится: номера берутся из заказов `ozon-fetcher`, а они грузятся с
  `ORDERS_FROM`. Сдвиг `ORDERS_FROM` назад (до M-2) — отдельным решением, если понадобится история.
