Symfony не затрагиваются). `stage_base_commit`: `416cfe566`. Ветка `feat/ozon-fetcher-products`.
Поручение Владельца 21.10.2026: «Этап 4 — составь подробный план и приступай автономно». Общий план —
`../plan-ozon.md`.

## 1. Какую задачу решаем

Связка «артикул продавца ↔ product_id ↔ SKU», баркоды, категория, название — основа сопоставления
заказов, начислений, остатков и рекламы с товарами. Symfony грузит её раз в сутки в 03:40
(`app:marketplace:ozon-listing-catalog:sync`, `RefreshOzonListingCatalogAction`): `/v3/product/list`
(все товары, `visibility: ALL`) → `/v3/product/info/list` порциями по `product_id`. По принципу плана
то же самое **дополнительно** грузит `ozon-fetcher`; Symfony не меняется.

## 2. Что известно о методах (живая проверка 21.10.2026, тестовый ключ Владельца, только чтение)

**`POST /v3/product/list`**
- Запрос: `{"filter": {"visibility": "ALL"}, "last_id": "", "limit": 1000}`; `limit` в `(0, 1000]`,
  1001 → 400 `code 3` `value must be inside range (0, 1000]`.
- Ответ: `{"result": {"items": [...], "total": N, "last_id": "...", "total_items": N}}`; товар —
  `product_id`, `offer_id`, `sku`, `archived`, `has_fbo_stocks`, `has_fbs_stocks`, `is_discounted`,
  `quants`.
- Пагинация — `last_id` (base64 `[product_id, product_id]`, keyset). **Последняя полная страница
  отдаёт непустой `last_id`** (60 из 60 и `last_id` ≠ ""); конец — следующая страница
  `items: []`, `last_id: ""`.

**`POST /v3/product/info/list`**
- Запрос: `{"product_id": [...]}` — до 1000; 1001 → 400 `no more than 1000 item(s)`; пустой
  массив → 400 `use either offer_id or product_id or sku`.
- Ответ: `{"items": [...]}` без `result`; товар — `id`, `offer_id`, `sku`, `sources`, `barcodes`,
  `name`, `description_category_id`, `type_id`, цены, `stocks`, `statuses`, `commissions`, … (39 полей).
- **Неизвестные `product_id` Ozon молча пропускает** (60 + 2 несуществующих → 60, 200).
- Объём: ≈ 3 КБ на товар (60 товаров — 185 КБ).

**Объём на проде** (листинги Ozon в Symfony, 21.10): 421 / 299 / 107 / 64 / 34 по кабинетам —
одна страница списка (+ пустая концевая) и одна порция подробностей на кабинет в сутки.

## 3. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Ресурсы | `ozon.products.list` (список) и `ozon.products.info` (подробности) — две задачи | разные методы и виды страниц; подробности зависят от списка так же, как начисления по отправлениям от заказов (этап 3) — тот же механизм `content_pages` + чтение raw; в покрытии видно, какая часть не загрузилась |
| `period_key` | день МСК **снимка** (дата загрузки); каждый день — новая задача | каталог — состояние на момент запроса, прошлое не догрузить; день без снимка виден в покрытии пропуском; ревизии дня сравнимы (как у остатков, этап 5) |
| Опоздавший снимок | задача за прошедший день в Ozon не ходит: `snapshot_missed` → `failed_permanent`, WARNING | иначе сегодняшний каталог лёг бы под вчерашней датой — тихая подмена данных |
| Расписание | ensure только **сегодня**, обычный приоритет, без перечитывания; первый проход планировщика после 00:00 МСК — задачи дня, исполняются сразу | раз в сутки, как Symfony; ночью — до загрузки Symfony в 03:40, общих лимитов метода не делят |
| Список | `last_id` до пустой страницы; каждая страница — в raw, включая концевую пустую; курсор задачи — `last_id`; непустая страница без `last_id` — `invalid_response` | конец списка Ozon сообщает только пустой страницей; детерминированный набор страниц → `unchanged` без новой ревизии |
| Проверка списка | `result` — объект; `items` — массив; `last_id` — строка; `total` — неотрицательное целое; непустая страница с уже виденным `last_id` → `invalid_response`; потолок 1000 страниц | как в Symfony: оборванный обход не должен выглядеть полным каталогом |
| Сверка с `total` | несовпадение числа товаров с `total` последней страницы — WARNING с числами, не ошибка | каталог может меняться во время обхода; повтор бы зациклился у активного продавца |
| Подробности: откуда id | `product_id` из raw списка того же дня и кабинета (текущая ревизия, `content_pages`), без дублей, по возрастанию, по 1000; страница = порция; курсор — `отпечаток списка:последний id`; список изменился — день заново | тот же приём, что этап 3: продолжение по чужому списку пропустило бы товар |
| Список дня не загружен | `catalog_not_loaded` → `not_ready`, повтор через 10 мин; подробности ставятся на минуту позже списка | список грузится за секунды |
| Переход суток во время загрузки | загрузка прерывается на полуночи МСК (дедлайн контекста по часам исполнителя) → `snapshot_missed` | страницы нового дня не ложатся под вчерашнюю дату (ревью) |
| Проверка подробностей | `items` — массив; каждый `id` ответа — из запроса и без повторов (иначе `invalid_response`); недостающие — WARNING с числом, не ошибка | Ozon молча пропускает удалённые товары (живая проверка), гонка удаления между запросами реальна |
| Пустой каталог | список — одна пустая страница, `done`; подробности — служебная страница `{"items": []}` без запроса | Ozon отвергает пустой `product_id`; покрытие видит день загруженным |
| Лимит | `/v3/product/list` и `/v3/product/info/list` — старт 0,2 запроса/с, пол 0,05, потолок 1 (общие значения по умолчанию) | 2–3 запроса на кабинет в сутки |
| Включение | Symfony: параметр `ozon_fetcher.products_companies` (как у заказов и начислений): сначала `3f4d87cc`, затем `['*']`; оба ресурса выдаются только с ключом seller | единое правило этапов |
| Снятый с кабинета ресурс | `resource_disabled`, в Ozon не ходит | как у заказов |

подробности по каждому товару списка; обход списка не обрывается молча; подробности запрошены для
всех `product_id` списка; снимок за прошедший день не подменяется сегодняшними данными; Symfony
грузит каталог как раньше; загрузка заказов и финансов не замедлилась; гейты зелёные; ревью

## 7. Риски

- **Объём raw**: подробности меняются ежедневно (цены, остатки в карточке) — новая ревизия в день,
  ≈ 3 КБ × товары; при 421 товаре ≈ 1,3 МБ в сутки до сжатия. Приемлемо; хранение — общая политика
  бакета.
- **Пропуск снимка** при простое сервиса весь день — невосстановим (как у Symfony); виден в покрытии.
- **Список дня упал окончательно** (`invalid_response`) — подробности до полуночи повторяются каждые
  10 мин (`catalog_not_loaded`) и закрываются `snapshot_missed`; сигнал — ERROR по списку. Ограничено
  сутками; ранний выход по статусу списка — если замер покажет вытеснение задач кабинета.
- **Изменение каталога между списком и подробностями** — новый товар попадёт в снимок следующего дня;
  удалённый — WARNING «недостающие».
