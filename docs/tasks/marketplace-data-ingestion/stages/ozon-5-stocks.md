# Этап 5 (Ozon). Остатки — снимки в `ozon-fetcher`

Риск: MEDIUM (два новых ресурса сервиса; миграций нет; БД Symfony и загрузка остатков Symfony не
затрагиваются). Ветка `feat/ozon-fetcher-stocks`. Поручение Владельца 22.10.2026: «Этап 5-7 — составь
подробный план для каждого этапа, чек-лист проверки готовности и приступай автономно». Общий план —
`../plan-ozon.md`.

## 1. Какую задачу решаем

Остатки — снимок «на сейчас»: истории в API нет, пропущенный снимок не восстановить. Symfony грузит их
раз в сутки в 04:05 (`app:inventory:ozon-daily-sync` → `SyncOzonInventorySnapshotHandler`,
`/v4/product/info/stocks`). По принципу плана то же самое **дополнительно** грузит `ozon-fetcher` —
в 05:00 МСК ежедневно и в воскресенье в 23:30 (отсечка недели, `spec-ozon.md` п. 9); Symfony не меняется.

## 2. Что известно о методе (живая проверка 22.10.2026, тестовый ключ Владельца, только чтение)

**`POST /v4/product/info/stocks`**
- Запрос: `{"filter": {"visibility": "ALL"}, "limit": 1000, "cursor": "..."}`; `limit` в `(0, 1000]`,
  1001 → 400 `code 3` `value must be inside range (0, 1000]`.
- Ответ: `{"items": [...], "total": N, "cursor": "...", "total_items": N}` — **без `result`**; товар —
  `product_id`, `offer_id`, `stocks[]` (`type` fbo/fbs/rfbs, `present`, `reserved`, `sku`,
  `shipment_type`, `warehouse_ids`).
- Пагинация — `cursor` (base64 keyset, как `last_id` списка товаров). **Последняя полная страница
  отдаёт непустой `cursor`**; конец — следующая страница `items: []`, `cursor: ""`.
- Битый курсор → 400 `code 3` `invalid last_id ...` — как у списка товаров (`stale_cursor`).
- Квота — `ratelimit-remaining: 49` на свежем окне; общая ли она для всех клиентов — на объёме
  снимка (1–2 запроса) не важно.

**Объём на проде** (Symfony `inventory_stock_snapshots`, 22.10): 231 / 145 / 72 / 60 SKU по кабинетам —
одна страница (+ пустая концевая) на снимок.

**Наблюдение по Symfony (не правим).** Symfony читает курсор из `result.last_id` и шлёт `last_id`
(`OzonInventoryClient.php`), а v4 отдаёт `cursor` в корне. Поэтому Symfony всегда читает только
первую страницу (до 1000 товаров). Сейчас у всех кабинетов товаров меньше 1000, данные полные;
у кабинета с > 1000 товаров остатки Symfony были бы неполными. Записано в итог этапа для Владельца.

## 3. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Ресурсы | `ozon.stocks` — ежедневный снимок 05:00; `ozon.stocks.week-close` — снимок воскресенья 23:30 | у снимков разное назначение (день / отсечка недели), пропуск каждого виден отдельно; ключ периода остаётся днём — контракт покрытия (`service-coverage` v1, карта Symfony) знает только `YYYY-MM-DD`, `YYYY-MM`, `ref`; ключ с часом (`snap:…THH` из `spec-ozon.md`) потребовал бы v2 контракта |
| `period_key` | день МСК снимка | как у каталога (этап 4) |
| Время | задача дня ставится с `RunAt` 05:00 МСК (`ozon.stocks`) и 23:30 МСК воскресенья (`ozon.stocks.week-close`); раньше — не исполняется | отсечка по `spec-ozon.md`; Symfony грузит в 04:05, к 05:00 его запросы завершены |
| Опоздавший снимок | после полуночи МСК задача за прошедший день в Ozon не ходит: `snapshot_missed` → `failed_permanent`, WARNING; загрузка, пересекающая полночь, прерывается (как `withinSnapshotDay` этапа 4) | пропуск не подменяется более поздним снимком (`spec-ozon.md` п. 9) |
| Снимок 05:00 опоздал (рестарт, сбой Ozon) | грузится в тот же день позже — это всё ещё снимок дня; время снимка видно по `fetched_at` страниц | лучше поздний снимок дня, чем пропуск; Symfony делает так же |
| Пагинация | `cursor` до пустой страницы; каждая страница — в raw, включая концевую пустую; курсор задачи — `cursor`; непустая страница без `cursor` — `invalid_response`; повтор курсора — `invalid_response`; потолок 1000 страниц | тот же приём, что список товаров |
| Проверка ответа | `items` — массив; у каждого товара `stocks` — массив; `cursor` — строка; `total` — неотрицательное целое | оборванный обход не должен выглядеть полным снимком |
| Сверка с `total` | несовпадение числа товаров с `total` — WARNING с числами; INFO «stocks snapshot read»: товаров, SKU в `stocks[]`, `total` | для сверки с Symfony без чтения raw |
| 400 на курсоре | `stale_cursor` → повтор с первой страницы (как заказы и список товаров) | курсор Ozon живёт ограниченно |
| Лимит | `/v4/product/info/stocks` — старт 0,2 запроса/с, пол 0,05, потолок 1, пауза 60 с | 2 запроса на снимок |
| Включение | Symfony: параметр `ozon_fetcher.stocks_companies`: сначала `3f4d87cc`, затем `['*']`; оба ресурса — только с ключом seller | единое правило этапов |
| Карта покрытия | две строки в `OPTIONAL_RESOURCES`: «Остатки: снимок 05:00» (день), «Остатки: отсечка недели» (день) | у отсечки недели в карте заполнены только воскресенья — остальные дни не считаются пропуском (строка «только при задачах», дни без задачи — пусто) |

## 4. Шаги

| Шаг | Что | Где |
|---|---|---|
| 5.1 | Клиент `FetchStocks` (страницы по курсору, проверки) | `internal/ozon/stocks.go` |
| 5.2 | Ресурсы в исполнителе: дедлайн суток, `snapshot_missed`, журнал числа товаров/SKU | `internal/executor/stocks.go`, `executor.go`, `outcome.go` |
| 5.3 | Планировщик: `ozon.stocks` на сегодня с `RunAt` 05:00, `ozon.stocks.week-close` в воскресенье с `RunAt` 23:30; лимиты | `internal/planner`, `internal/ratelimit` |
| 5.4 | Symfony: ресурсы в снимке кабинетов по параметру, строки карты покрытия; контракт, документы | `site/`, `services/_contracts`, `docs` |
| 5.5 | Деплой с одним кабинетом → проверка → все кабинеты | прод, только чтение |

## 5. Что считаем выполненной работой

По всем кабинетам Ozon в raw `ozon-fetcher` каждый день есть снимок остатков не раньше 05:00 МСК, по
воскресеньям — ещё и снимок 23:30; пропущенный снимок виден в покрытии и не подменяется поздним;
число SKU сопоставимо со снимком Symfony того же дня; гейты зелёные; ревью Codex без
BLOCKER/IMPORTANT.

## 7. Риски

- **Снимок 05:00 при простое сервиса** (деплой, сбой) берётся позже в тот же день — время снимка
  смещается; оценивается по `fetched_at`. Пропуск возможен, только если сервис лежит до полуночи.
- **Ключ дня для двух снимков разного времени**: если понадобится третий снимок в день — новый
  ресурс или контракт v2 покрытия.
