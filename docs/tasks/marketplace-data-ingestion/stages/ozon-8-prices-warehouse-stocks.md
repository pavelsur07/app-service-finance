# Этап 8 (Ozon). Цены и остатки по складам — снимки в `ozon-fetcher`

Риск: MEDIUM (два новых ресурса сервиса; миграций нет; БД Symfony и загрузки Symfony не
затрагиваются). Ветка `feat/ozon-fetcher-snapshots`. Поручение Владельца 24.10.2026: «Этап 8
разработай план». Общий план — `../plan-ozon.md`, требования — `../spec-ozon.md` §2 (группы 1 и 5),
§3 (приоритет 1).

## 1. Какую задачу решаем

Этапы 1–7 перенесли в `ozon-fetcher` всё, что Symfony грузит из Ozon. Этап 8 — первые **новые**
данные, которых нет нигде в системе:

- **цены** — базовая, со скидкой, маркетинговая (с соинвестом Ozon), минимальная, комиссии и индексы
  цен по каждому товару;
- **остатки по складам и кластерам Ozon** — доступно, в пути, в резерве, брак, возвраты, оборачиваемость.
  Этап 5 грузит остатки одной цифрой на SKU (как Symfony); для недельного анализа нужно, на каком
  складе товар и где его не хватает.

Оба — **снимки**: истории в API нет, пропущенный день потерян. Поэтому в ТЗ это приоритет 1.

## 2. Что известно о методах (живая проверка 24.10.2026, тестовый ключ Владельца, только чтение)

Кабинет тестового ключа — 60 товаров (`19621cff`).

**`POST /v5/product/info/prices`**
- Запрос: `{"cursor": "", "filter": {"visibility": "ALL"}, "limit": 1000}`; `limit` в `(0, 1000]`,
  1001 → 400 `code 3` `value must be inside range (0, 1000]`.
- Ответ: `{"items": [...], "cursor": "...", "total": N, "total_items": N}` — **без `result`**; товар —
  `product_id`, `offer_id`, `price{price, old_price, marketing_seller_price, min_price, net_price,
  retail_price, vat, currency_code, auto_action_enabled, …}`, `commissions{sales_percent_fbo/fbs/…,
  fbo_*_amount, fbs_*_amount}`, `marketing_actions{actions, current_period_from/to}`,
  `price_indexes{…}`, `acquiring`, `volume_weight`.
- Пагинация — как у остатков этапа 5: последняя полная страница отдаёт непустой `cursor`; конец —
  страница `items: []`, `cursor: ""` (60 товаров → 2 запроса).

**`POST /v1/analytics/stocks`**
- Запрос: `{"skus": ["…", …]}` — **от 1 до 100 SKU** (строки), 101 → 400 `code 3`
  `value must contain between 1 and 100 items, inclusive`; `{}` → 400. Пагинации нет.
- Ответ: `{"items": [...]}`; строка — SKU × склад: `sku`, `offer_id`, `name`, `warehouse_id`,
  `warehouse_name`, `cluster_id`, `cluster_name`, `macrolocal_cluster_id`, `placement_zone`,
  `available_stock_count`, `valid_stock_count`, `transit_stock_count`, `requested_stock_count`,
  `waiting_docs_stock_count`, `expiring_stock_count`, `stock_defect_stock_count`,
  `transit_defect_stock_count`, `excess_stock_count`, `other_stock_count`,
  `return_from_customer_stock_count`, `return_to_seller_stock_count`, `outbound_*`, `ads`,
  `ads_cluster`, `idc`, `idc_cluster`, `days_without_sales*`, `turnover_grade*`, `item_tags`.
- 60 SKU кабинета → 1350 строк по 49 SKU (11 SKU без строк — товар нигде не лежит).
- **Квота общая**: `ratelimit-remaining` между соседними запросами скачет 49 → 21 → 44 → 32 —
  ключ расходуют и другие клиенты (как у `accrual/postings`, этап 3).

**Почему не `/v2/analytics/stock_on_warehouses`.** Метод отвечает (offset-пагинация), но строка —
только `sku`, `warehouse_name`, `free_to_sell/promised/reserved_amount`: нет `warehouse_id`, кластера,
брака, транзита, оборачиваемости. `/v1/analytics/stocks` — новее и полнее; версию сверить с
документацией и каналом Ozon (шаг 8.1).

**Объём на проде** (SKU снимка этапа 5, 24.10): 239 / 140 / 72 / 60 → по 3 / 2 / 1 / 1 запросу
аналитики остатков и по 2 запроса цен на кабинет.

## 3. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Ресурсы | `ozon.prices` — снимок цен; `ozon.stocks.warehouses` — снимок остатков по складам | имена в ряду `ozon.stocks` |
| `period_key` | день МСК снимка | контракт покрытия v1, как этап 5 |
| Время | `ozon.prices` — `RunAt` 05:00 МСК; `ozon.stocks.warehouses` — с 05:00, после снимка `ozon.stocks` того же дня | конец недели — снимок понедельника 05:00 (решение 22.10, этап 5 §8) |
| Опоздавший снимок | как этап 5: в тот же день позже — допустимо; после полуночи — `snapshot_missed`, `failed_permanent`, WARNING; полночь посреди загрузки — прерывание (`withinSnapshot`) | пропуск не подменяется поздним (`spec-ozon.md` п. 9) |
| Цены: пагинация и проверки | `cursor` до пустой страницы, каждая страница в raw; непустая страница без курсора, повтор курсора — `invalid_response`; потолок страниц; `items` — массив, `cursor` — строка, `total` ≥ 0; 400 на курсоре — `stale_cursor` | тот же приём, что остатки этапа 5 (общий разбор страницы) |
| Остатки по складам: список SKU | SKU из raw снимка `ozon.stocks` **того же дня** (`stocks[].sku`, разбор этапа 5); снимок не загружен — `stocks_not_loaded`, `not_ready` 10 мин; пустой список — служебная страница без запроса, `done` | источник — уже загруженный raw, как кампании для отчётов этапа 7; один день — один набор товаров |
| Остатки по складам: порции | SKU по возрастанию, порции по 100; порция — одна страница raw; курсор задачи — `отпечаток списка SKU:индекс порции`; список изменился (перечитан снимок дня) — день заново | рестарт продолжает с порции; смена набора не смешивает два списка |
| Проверка ответа аналитики | `items` — массив; у строки есть `sku`; SKU строки входит в запрошенную порцию, иначе `invalid_response`; INFO «warehouse stocks read»: SKU запрошено, SKU в ответе, строк, складов | ответ без пагинации — защита от чужих данных и видимость полноты без чтения raw |
| Форма ответа | набор ключей верхнего уровня и строки сверяется с ожидаемым; новые поля — WARNING, raw сохраняется | `spec-ozon.md` п. 14 |
| Лимит | общая квота ключа (`SharedQuota`, как этап 3): `/v5/product/info/prices` и `/v1/analytics/stocks` — 0,2 запроса/с, 429 — пауза без снижения ставки и без сигнала шторма | квоту делят Symfony и другие клиенты; на снимок 2–5 запросов |
| Включение | Symfony: параметр `ozon_fetcher.snapshots_companies` (оба ресурса): сначала `3f4d87cc`, затем `['*']`; только с ключом seller; `ozon.stocks.warehouses` — только вместе с `ozon.stocks` | единое правило этапов; без снимка этапа 5 нет списка SKU |
| Карта покрытия | строки «Цены: снимок 05:00», «Остатки по складам: снимок 05:00» в `OPTIONAL_RESOURCES` | как у остальных этапов |

подменяется поздним; Symfony без новых 429; гейты зелёные; ревью Codex без BLOCKER/IMPORTANT;

## 7. Риски

- **Ответ аналитики без пагинации.** Если Ozon обрезает строки большого запроса, это не видно. Защита —
  порции по 100 SKU и число SKU в ответе в журнале; при подозрении — порции меньше (решение по замеру
  на `3f4d87cc`, 239 SKU).
- **Общая квота ключа.** 429 от чужой нагрузки — ожидаемо; снимок из 2–5 запросов укладывается в окно
  дня даже при паузах.
- **Аналитика остатков обновляется Ozon с задержкой** — снимок 05:00 может отражать состояние на
  ночь; для недельного анализа достаточно, сравнение со снимком этапа 5 (те же SKU, суммарно
  `available_stock_count` против `present − reserved` FBO) — в итоге этапа.
- **SKU без строк складов** — норма: `stocks[]` снимка этапа 5 содержит все SKU, включая нулевые;
  товар, который нигде не лежит, строк не даёт (проверка 24.10: 11 из 60).
