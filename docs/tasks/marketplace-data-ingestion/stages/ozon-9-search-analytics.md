# Этап 9 (Ozon). Поисковая аналитика по товарам (Premium) — raw в `ozon-fetcher`

Риск: MEDIUM (два новых ресурса сервиса; миграций нет; БД Symfony и загрузки Symfony не
затрагиваются). Ветка `feat/ozon-fetcher-search-analytics`. Поручение Владельца 24.10.2026: «делай
этапами, под каждый этап разрабатывай план, цель, что является результатом, чек-лист проверки
готовности этапа, действуй автономно». Общий план — `../plan-ozon.md`, требования — `../spec-ozon.md`
§2 (группа 1), §3 (приоритет 3).

## 1. Какую задачу решаем

ТЗ (группа 1) просит воронку по SKU: показы, переходы в карточку, корзины. В плане она шла как
`/v1/analytics/data` (метрики `hits_view*`, `session_view*`, `hits_tocart*`). **Живая проверка 24.10
показала: Ozon снял эти метрики** — запрос с любой из них получает 400 `deprecated metrics used`
(Premium у кабинетов включён, ключ тут ни при чём; так же у сторонних клиентов API). Метод отдаёт
только `ordered_units` и `revenue` — это уже есть в заказах (этап 1).

Замена, которую Ozon оставил в API, — **поисковая аналитика Premium**: по каждому SKU за день —
сколько уникальных покупателей видели товар в поиске, средняя позиция, сколько перешли в карточку,
конверсия в просмотр, GMV; и топ поисковых запросов по SKU. **История — около 33 дней** и уходит
по дню в сутки: что не загружено сейчас, потеряно. Поэтому этап — сразу после этапа 8.

## 2. Что известно о методах (живая проверка 24.10.2026, тестовый ключ Владельца, только чтение)

Кабинет тестового ключа — 60 SKU (`19621cff`), Premium включён.

**`POST /v1/analytics/product-queries`** — сводка по SKU
- Запрос: `{"date_from": "2026-10-20T00:00:00+03:00", "date_to": "2026-10-20T23:59:59+03:00",
  "skus": ["…"], "page": 0, "page_size": 1000}`; `skus` — **обязательно, 1–1000** (без них 400),
  `page_size` в `(0, 1000]`.
- Ответ: `{"items": [...], "total": N, "page_count": N, "analytics_period": {"date_from", "date_to"}}`;
  строка — `sku`, `name`, `offer_id`, `category`, `unique_search_users`, `position`,
  `unique_view_users` (строка!), `view_conversion`, `gmv`, `currency`. Только SKU с данными
  (60 запрошено → 34 строки).
- Данные — **по дням**: диапазон по UTC и по МСК за тот же день дают одно и то же, диапазон в час —
  пусто. День МСК передаём как `DT00:00:00+03:00`…`DT23:59:59+03:00`.
- **Задержка**: вчера (D−1) — 400 `There is no data for the specified period`, позавчера (D−2) — есть.
- **Глубина**: 24.10 самый ранний день с данными — 21.09 (D−33); 20.09 и раньше — тот же 400.

**`POST /v1/analytics/product-queries/details`** — топ запросов по SKU
- Запрос: как выше + `"limit_by_sku": 15` (в `(0, 15]`), `page_size` в `(0, 100]`.
- Ответ: `{"queries": [...], "total": N, "page_count": N, "analytics_period": {…}}`; строка — `sku`,
  `query`, `query_index`, `position`, `unique_search_users`, `unique_view_users`, `view_conversion`,
  `order_count`, `gmv`, `currency`. 60 SKU × до 15 запросов → 441 строка, 5 страниц по 100.
- Пагинация — `page` с 0 до `page_count − 1`.

**Квота**: `ratelimit-remaining` ~20 и скачет; у `/details` — свой предел «в секунду» (`You have
reached request rate limit per second` при запросах через 5 с подряд с другим методом) — квота
общая, `SharedQuota`.

**Объём на проде** (SKU снимка `ozon.stocks`): 239 / 140 / 72 / 60 → сводка — 1 запрос на день,
детализация — до 36 / 21 / 11 / 9 страниц на день; догон 33 дней у `3f4d87cc` ≈ 1200 запросов
(≈ 100 мин при 0,2 запроса/с, приоритет догона).

## 3. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Ресурсы | `ozon.analytics.queries` — сводка по SKU за день; `ozon.analytics.queries.details` — топ-15 запросов по SKU за день | две разные выдачи Ozon, разный объём и пагинация |
| `period_key` | день МСК данных | данные дневные |
| SKU | из raw снимка `ozon.stocks` **дня исполнения** (самый свежий загруженный снимок не старше сегодняшнего), по возрастанию, порции по 1000 | исторических снимков до 22.10 нет; товар без данных Ozon просто не вернёт |
| Свежесть | день грузится с D−2; D−1 и сегодня в Ozon не запрашиваются | данных нет до D−2 |
| Догон | с `DefaultQueriesFrom` = 2026-09-21 (самый ранний день 24.10), не глубже D−33; приоритет догона | история уходит, догон — сразу |
| Перечитывание | хвост: D−2…D−7 раз в сутки (`refresh`), ревизия при изменении | Ozon может досчитывать дни |
| «Нет данных за период» | день старше D−30 — `history_unavailable`, `failed_permanent`, WARNING (история ушла, видно в покрытии); младше — `not_ready` с повтором через 6 ч | не путать «ещё не посчитано» и «уже удалено» |
| Пагинация | `page` с 0; страница — raw; курсор — `отпечаток SKU:порция:страница`; `page_count` и число строк проверяются: страница с данными за пределом `page_count`, пустая страница до конца, повтор — `invalid_response`; потолок 1000 страниц | без тихой обрезки (`spec-ozon.md` п. 12) |
| Проверка ответа | `items`/`queries` — массив, у строки `sku` из порции; `analytics_period` совпадает с запрошенным днём | чужие данные и сдвиг периода не сохраняются молча |
| Форма ответа | набор полей сверяется с живой формой; расхождение — один WARNING, raw сохраняется (как этап 8) | `spec-ozon.md` п. 14 |
| Лимит | оба endpoint'а — `SharedQuota` 0,2 запроса/с, 429 — пауза | общая квота, предел в секунду |
| Включение | Symfony: `ozon_fetcher.search_analytics_companies` (оба ресурса), только вместе с `ozon.stocks`; сначала `3f4d87cc`, затем `['*']` | единое правило этапов; без снимка остатков нет SKU |
| Карта покрытия | строки «Поиск: сводка по товарам», «Поиск: запросы по товарам» | как у остальных этапов |

## 7. Риски

- **Глубина истории уходит по дню в сутки**: каждый день до включения — минус день истории. Включение
  на все кабинеты — сразу после проверки одного.
- **Ozon снимает метрики без анонса** (как воронку в `/v1/analytics/data`): снятие этих методов
  дойдёт как 400 — сработает общий `obsolete_endpoint` / `invalid_request` с ERROR.
- **SKU из сегодняшнего снимка для прошлых дней**: товар, удалённый с тех пор, в прошлые дни не
  попадёт. Для недельного анализа текущего ассортимента допустимо; записывается в итог.
