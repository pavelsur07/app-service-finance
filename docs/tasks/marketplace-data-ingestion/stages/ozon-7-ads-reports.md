# Этап 7 (Ozon). Реклама: статистика по товарам (асинхронные отчёты) — raw в `ozon-fetcher`

Риск: HIGH-LOCAL (асинхронный заказ отчётов на общем с Symfony аккаунте Performance; БД Symfony и
загрузка рекламы Symfony не затрагиваются). Ветка `feat/ozon-fetcher-ads-reports`. Зависит от
этапа 6 (клиент Performance, токен, слот рекламы, список кампаний и дневная статистика в raw).
Поручение Владельца 22.10.2026 — как у этапов 5–6. Решения по рекламе — `../plan-ozon.md`.

## 1. Какую задачу решаем

Расход, показы и клики в разрезе SKU внутри кампаний Ozon отдаёт только асинхронным отчётом
`/api/client/statistics`. Symfony заказывает их в 04:30 (вчера) и сверяет 14 дней с 06:10 до 23:40.
`ozon-fetcher` грузит те же отчёты **дополнительно** — в ночном окне, не отнимая у Symfony слоты
отчётов аккаунта.

## 2. Что известно (код Symfony, 22.10.2026)

- **Заказ:** `POST /api/client/statistics`, `{"campaigns": [≤ 10 id], "from": "…Z", "to": "…Z",
  "groupBy": "DATE"}`; день МСК D — `from = D−1T21:00:00Z`, `to = DT20:59:59Z`; ответ — `UUID`.
  Больше 10 кампаний → ошибка Ozon «Превышен лимит по количеству кампаний (максимум 10)». Диапазон —
  до 62 дней.
- **Статус:** `GET /api/client/statistics/{UUID}` → `state` (`NOT_STARTED`, `IN_PROGRESS`, `OK`,
  `ERROR`, …), `link`. По опыту Symfony опрос статуса лимитом не ограничен, ограничен заказ.
- **Скачивание:** `GET link` (относительный — от хоста Performance) или
  `/api/client/statistics/report?UUID=`; ответ — ZIP (CSV на кампанию) или один CSV.
- **Лимиты отчётов** (комментарии Symfony): у аккаунта не больше 1 активной выгрузки / 3 отчётов в
  очереди; превышение — 429 «Превышен лимит активных…». Под нагрузкой отчёт стоит в очереди Ozon
  30–90 мин, бывает до 2 ч; Symfony бросает отчёт через 3 ч.
- **Кампании:** Symfony берёт все кампании `advObjectType = SKU`, без фильтра по состоянию.

## 3. Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Ресурсы | `ozon.ads.statistics` — отчёт за **вчера** (имя ресурса — из контракта v1); `ozon.ads.statistics.tail` — отчёт диапазоном **14 дней до вчера**, `period_key` — день прохода | хвост одним диапазоном вместо 14 дневных отчётов (решение плана); ключ дня — контракт покрытия |
| Страница | один отчёт порции ≤ 10 кампаний = одна страница raw (тело как пришло, `content_type` ответа: zip/csv) | без разбора: нормализация — отдельный план |
| Кампании | `advObjectType = SKU` из raw `ozon.ads.campaigns` **дня исполнения** (этап 6), **только активные в периоде**: у кампании есть ненулевые показы, клики или расход в raw `ozon.ads.daily` за дни отчёта (живая форма 22.10: `rows[]` с `id`, `views`, `clicks`, `moneySpent`); статистика дня не загружена или форма незнакома — все SKU-кампании (как Symfony); по возрастанию id, порции по 10 | меньше отчётов — меньше слотов (решение плана); источник — уже загруженный raw, как номера отправлений этапа 3 |
| Кампаний нет | служебная страница без заказа, `done` | покрытие видит день загруженным |
| Зависимости не загружены | кампании дня исполнения не загружены → `ads_campaigns_not_loaded`, ожидание 30 мин с курсором; статистика дня — см. «Кампании» | порядок без жёсткой связи задач; задачи отчётов ставятся с 01:30 — после расхода и статистики (01:00) |
| Курсор | `отпечаток списка порций:индекс порции:UUID`; после рестарта — опрос **того же** UUID, без нового заказа; список кампаний изменился — день заново (`ads_campaigns_revised`) | слоты отчётов дефицитны |
| Окно заказа | новый отчёт заказывается только **00:30–04:00 МСК**; вне окна задача ждёт начала следующего окна (`report_window`); опрос и скачивание уже заказанного — в любое время | Symfony заказывает с 04:30 и днём; окно не отнимает его слоты (решение плана) |
| Один отчёт аккаунта | слот рекламы кабинета один (этап 6), задача держит его с заказа до скачивания: опрос внутри попытки каждые 30 с до 20 мин, затем `report_pending` (`not_ready` через 5 мин) **с сохранением UUID**; пока у кабинета есть задача рекламы с незавершённым UUID, другие задачи отчётов кабинета не заказывают | не больше 1 отчёта на аккаунт одновременно (решение плана) |
| 429 на заказ | не повторять подряд: задача ждёт начала **следующего** окна | общий лимит аккаунта с Symfony |
| Отчёт `ERROR` / пропал | `report_failed` → повтор с новым заказом через 30 мин в окне; 3 подряд — `failed_permanent` + ERROR | ошибка формирования на стороне Ozon |
| Отчёт не готов 3 ч | бросить UUID, заказать заново в следующем окне; WARNING | как Symfony (3 ч) |
| Лимитер | заказ — 1 запрос в 120 с на кабинет (пол = потолок); статус — 0,5 запроса/с; скачивание — 0,2 | разнос заказов как в Symfony (120 с) |
| Включение | Symfony: `ozon.ads.statistics`, `ozon.ads.statistics.tail` — компаниям `ozon_fetcher.ads_reports_companies` (из тех, кому выданы ресурсы этапа 6); `ozon.ads.statistics` перестаёт выдаваться всем performance-кабинетам; Go: отчёты планируются только кабинету с `ozon.ads.campaigns` и исполняются только при ресурсе в снимке | до этапа 7 сервис ресурс игнорировал; включение — как у остальных этапов |
| Карта покрытия | две строки в `OPTIONAL_RESOURCES`: «Реклама: отчёт по товарам», «Реклама: отчёт хвост 14 дней» | |

## 4. Шаги

| Шаг | Что | Где |
|---|---|---|
| 7.1 | Клиент: заказ, статус, скачивание (ZIP/CSV, ссылка относительная/абсолютная; Bearer — только на хост Performance) | `internal/ozonperf` |
| 7.2 | Исполнитель: кампании из raw, порции, курсор с UUID, окно заказа, опрос, исходы | `internal/executor` |
| 7.3 | Планировщик: вчера — ежедневно, хвост — раз в сутки; `RunAt` 00:30 | `internal/planner` |
| 7.4 | Symfony: гейт ресурсов, строки карты; контракт, документы | `site/`, `services/_contracts`, `docs` |
| 7.5 | Деплой с одним кабинетом → проверка ночного окна → все кабинеты | прод, только чтение |

## 5. Что считаем выполненной работой

По всем кабинетам с ключом Performance в raw `ozon-fetcher` каждую ночь — отчёты по товарам за вчера
и диапазон 14 дней, заказанные только в окне 00:30–04:00, не больше одного одновременно на
аккаунт; рестарт не порождает повторный заказ; загрузка Symfony в 04:30 и сверки днём без новых
429; гейты зелёные; ревью Codex без BLOCKER/IMPORTANT.

## 7. Риски

- **Окно 3,5 ч при очереди Ozon 30–90 мин**: у кабинета с десятками активных кампаний отчёты могут
  не уложиться в окно — остаток догружается следующей ночью (покрытие покажет `pending`). Если это
  постоянно — расширить окно до 04:20 или ужать хвост (решение по замеру).
- **Форма ответа статуса и ссылки** проверена только по коду Symfony; живая — на шаге «один кабинет».
- **Активные в периоде по `ozon.ads.daily`** зависят от формы ответа этапа 6; если в ней нет
  разреза по кампаниям — порции из всех SKU-кампаний (как Symfony), решение фиксируется в итоге этапа 6.
