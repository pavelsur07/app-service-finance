# План: загрузка данных Ozon в `ozon-fetcher` (Go)

Статус: **план на согласование**, 21.10.2026. Только **загрузка** (raw в S3 + журнал), без
нормализации. Детали требований — `spec-ozon.md`.

## Принцип

- Всё, что сейчас грузит из Ozon Symfony, **дополнительно** грузит `ozon-fetcher`.
- **Symfony не отключаем и не правим**: его загрузки, cron и отчёты работают как сейчас. Из Symfony
  меняется только список ресурсов, который сервис получает по кабинету, и подписи карты покрытия.
- Данные `ozon-fetcher` пока никто не читает; переключение потребителей на них — отдельный план
  после загрузки.
- Каждый ресурс включается так: код и тесты → **один кабинет** (`3f4d87cc`, малый объём) →
  проверка на проде → **все кабинеты** и догон истории.

### Реклама (этапы 6–7): решения

| Вопрос | Решение | Почему |
|---|---|---|
| Модуль или сервис | **модуль в `ozon-fetcher`**: пакет `internal/ozonperf` (клиент, токен), ресурсы `ozon.ads.*` | контракт `marketplace-connections` v1 уже считает кабинет = компания с ключами seller и performance и ресурсом `ozon.ads.statistics`; ядро (задачи, raw, журнал, покрытие) общее; отдельный сервис дублировал бы его без выигрыша |
| Очередь | одна `running`-задача на **(кабинет, API)**, а не на кабинет: миграция частичного уникального индекса `fetch_task_one_running_per_connection` | у Performance свой ключ и свои лимиты; отчёт готовится до 10 мин — в общем слоте он задерживал бы начисления и заказы |
| Лимитер | отдельный, по `client_id` Performance | лимиты Seller и Performance независимы |
| Токен | OAuth `client_credentials`, один на `client_id`, только в памяти, обновление за 5 мин до истечения; 401 → одно обновление токена, затем пауза рекламы кабинета (не всего кабинета) | как в Symfony (`TOKEN_TTL_SAFETY_MARGIN = 300`); `client_secret` сервис сейчас отбрасывает — начать держать в памяти |
| Что синхронно | кампании, расход по дням, дневная статистика по кампаниям (`/api/client/statistics/daily/json` — версию сверить) | без отчётов: не занимают слоты отчётов |
| Что асинхронно | статистика по товарам внутри кампаний (`/api/client/statistics` → опрос → скачивание) | только так Ozon отдаёт разрез SKU |
| Номер отчёта | UUID заказанного отчёта — в курсоре задачи; после рестарта — опрос того же отчёта, а не новый заказ | слоты отчётов дефицитны |
| Порции | ≤ 10 кампаний в отчёте; только кампании, активные в периоде | ограничение Ozon (`STATISTICS_BATCH_SIZE = 10` в Symfony); меньше отчётов |
| Хвост | вчера — ежедневно; 14 дней — раз в сутки ночью одним диапазоном на порцию | Ozon дописывает атрибуцию заказов задним числом; диапазон вместо 14 отчётов по дню |
| **Сосуществование с Symfony** | Go заказывает **не больше 1** отчёта на аккаунт одновременно и только в окне **00:30–04:00 МСК**; 429 на заказ отчёта → отложить до следующего окна, не повторять подряд | Symfony держит до 3 отчётов в работе на компанию (`MAX_IN_FLIGHT_PER_COMPANY`), грузит в 04:30 и сверяет 06:10–23:40; лимит одновременных отчётов у аккаунта общий — без окна Go отнимал бы слоты у рабочей загрузки |

## Риск, общий для всех этапов

Symfony и `ozon-fetcher` ходят в Ozon **с одним ключом**, лимит кабинета у них общий. Пока Symfony
не отключён, сервис на новых ресурсах держит RPS ниже обычного, а после каждого включения сверяем
429 у Symfony. Рост 429 — откат включения ресурса (убрать из списка ресурсов кабинета), не правка
Symfony.
