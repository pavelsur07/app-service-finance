# Handoff — module-access-roles

Модульные роли доступа: владелец компании раздаёт участникам доступ к группам модулей через
шаблоны ролей. Уровни `none | read | write`, `write ⊃ read`. Per-member override отклонён
владельцем — нестандартный доступ = копия шаблона.

Источник: owner brief в чате от 2026-08-05. План: `plan.md`. Отчёты: `stages/stage-1..5.md`.

**Внимание при генерации будущих миграций:** частичный функциональный индекс не выражается
атрибутами ORM, поэтому `schema:update --dump-sql` и `migrations:diff` предлагают
`DROP INDEX uniq_company_role_company_name`. Это ложное срабатывание, строку нужно удалять
из сгенерированной миграции. Деплой идёт через `migrations:migrate`.

## Изменения поведения, которые увидит пользователь

1. Участник без шаблона доступа теперь не имеет доступа ни к чему. Раньше `OPERATOR` без шаблона
   получал полный доступ (BC-fallback). Это был fail-open: обнуление `role_id` повышало права
   вместо снятия. На проде участников без шаблона нет — проверено read-only запросом.
2. Меню зависит от шаблона: у ограниченного шаблона разделы недоступных модулей скрыты.
3. Пункт «Отладка» переехал из «Компании и доступов» на верхний уровень меню.
4. Пять marketplace-эндпоинтов (Inventory snapshots, MarketplaceAds Ozon load/extract,
   MarketplaceAnalytics) больше не пускают пользователя с глобальной ролью `ROLE_COMPANY_OWNER`,
   если у него нет `marketplace:write` в активной компании.

## Что нашли ревью

24 итерации внешнего ревью суммарно. Главное:

**BLOCKER (Stage 4).** Пять marketplace-контроллеров стояли под `#[IsGranted('ROLE_COMPANY_OWNER')]`,
и это считалось гейтом строже модульного. Премисса неверна: роль объявлена в `role_hierarchy`
глобально и ставится на `User` при регистрации. Владелец компании A, будучи read-only участником
компании B, мог запускать в компании B загрузки и пересчёты.

**Self-escalation в плане (Stage 3).** План обещал заменить `assertOwner` на `module.admin.write`
для управления шаблонами. Участник с `admin:write` отредактировал бы свой шаблон и выдал себе
`finance:write`. Управление шаблонами осталось owner-only.

**Fail-open BC-fallback (Stage 3).** Снят, FK переведены на `RESTRICT`.

**Инвариант покрытия переписывался трижды (Stage 4).** Каждый раз ревью находило реальный
fail-open путь: проверка по атрибутам метода не видела invokable-контроллеров с class-level
`#[Route]`; ожидаемый модуль отбрасывался; `str_contains` считал гейтом закомментированный вызов;
`->isOwner(` — предикат — считался fail-closed проверкой. Итог: статический инвариант без эвристик
плюс поведенческий тест по 42 смешанным маршрутам.

## Риски

- Read-гейт fail-closed действует на все контроллеры: контроллер в новом неймспейсе без записи
  в `ModuleAccessMap` получит 403. Ловит `ControllerAccessCoverageTest` на CI.
- Ветка меняет вход в приложение (`/`) и раскладку дашбордов. Стоит прощёлкать вручную после деплоя.
- Миграция `Version20260811150000` меняет поведение FK. Удаление назначенного шаблона теперь
  отклоняется базой, а не только приложением.

## Follow-ups, сознательно вынесенные за scope

- Компанию с участниками нельзя удалить: `fk_company_members_company` объявлен `NO ACTION`,
  ORM участников не каскадит. Pre-existing дефект master, тестов на удаление компании не было.
- `$roleRepository->find($roleId)` на write-пути без валидации UUID: мусорная строка даст 500
  вместо 400. Company-принадлежность проверяется после, IDOR закрыт.
- `CompanyController::setActive` требует владельца, поэтому участник не может переключиться
  на компанию, где он участник. Pre-existing.
- Перевести 13 параметризованных смешанных маршрутов в `ModuleMixedRouteGateTest` на fixtures,
  чтобы требовать ровно 403 вместо «403 либо 404».
- Прогонять поведенческий тест по каждому разрешённому мутирующему методу, а не только POST.
- `src/Mcp/Application/Tool/CashCategoryUpsertTool.php` — нарушение порядка трейтов пришло
  с master, намеренно не тронуто.
