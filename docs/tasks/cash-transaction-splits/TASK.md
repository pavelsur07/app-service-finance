# TASK: разбивка транзакции ДДС на несколько категорий

**ID задачи:** `cash-transaction-splits`
**Ветка:** `agent/cash-transaction-splits` (от `master`)
**Владелец:** подтверждает решения D2–D4 и Production Gate A.

## Проблема

Одна `CashTransaction` может нести только одну категорию ДДС
(`cash_transaction.cashflow_category_id`). Платёж, покрывающий несколько статей
(аренда + реклама одним переводом), приходится либо относить целиком на одну статью,
либо не разносить вовсе.

## Scope

Ввести дочерние строки `cash_transaction_split` (категория + сумма) как единственный
источник правды о категоризации ДДС. Перевести всех потребителей на строки.
Дать UI разбивки. Удалить legacy-колонку отдельной задачей.

## Вне scope

- Per-split проект, ЦФО и комментарий — остаются на транзакции (см. plan.md, решение по ревью п.7).
- Разбивка транзакций в категориях с `allow_pl_document = true` — запрещена в v1 (решение D1).
- Автомэтч планового платежа на мультисплит — отключён в v1 (решение D2).
- Шаблоны разбивки, проценты в БД, история версий сплитов.
- Разбор 42% нераспределённых транзакций — отдельная задача, здесь не решается.

## Acceptance criteria

1. Транзакцию можно разбить на N категорий с разными суммами; сумма строк равна сумме транзакции.
2. Все отчёты, экспорт, ведомость, MCP-контракт и автоправила читают строки, не колонку.
3. Ни одна существующая операция не сломана: документы ОПиУ, платёжные планы и импорт
   работают как раньше — подтверждается сверкой до/после на реальных данных.
4. Изменение состава строк попадает в историю транзакции.
5. Backfill проверен per-transaction сверкой; расхождений нет.

## Ограничения

- Production-мутации только через Production Gate.
- Сырые production-суммы, ID компаний и категорий в репозиторные отчёты не попадают.
- Статический анализ — только через существующие `make`-таргеты (`make stan` в проекте нет).
