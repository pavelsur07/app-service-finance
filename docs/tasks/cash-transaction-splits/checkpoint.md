## Находки в ходе реализации

- **Девятый writer, которого не было в карте плана:** `CashTransactionAutoRuleController::applyOne` применяет правило и делает собственный flush. Подключён к синхронизатору.
- **Импорты трогать не пришлось:** три импорта создают транзакцию без категории, а строки зеркалят колонку включая её пустое состояние — инвариант держится по построению.
- **Баг, пойманный тестом:** пересоздание строки с той же категорией падало на `uniq_cts_tx_category` — Doctrine выполняет INSERT раньше DELETE в одном flush. Исправлено в корне: `replaceSplits()` переиспользует строку с совпадающей категорией. Это же чинит будущую форму мультиразбивки в Stage 4.
- **Инвариант «сумма строк = сумме транзакции» уточнён:** он применяется к непустому составу; «категории нет → строк нет» — легальное зеркало. Для D3/D4 в Stage 3 это означает LEFT JOIN, иначе транзакция без категории пропадёт из ведомости.

### Решения, принятые по ходу Stage 3

- Транзакция без категории строк не имеет → везде `LEFT JOIN` и
  `COALESCE(split.amount, t.amount)` там, где такие транзакции обязаны учитываться.
- `CashFacade` отдаёт массив `splits`; поле `category` заполняется только при одной
  строке, иначе `null` — одна категория из нескольких была бы ложью для интеграции.
- Потоковый экспорт переведён с `toIterable()` на `getArrayResult()`: Doctrine запрещает
  итерировать запрос с join коллекции. Потолок и путь апгрейда записаны в коде.
- Кандидатом в автоправило может быть только транзакция ровно с одной категорией.
- Тестовые данные: `CashTransactionBuilder` создаёт зеркальную строку — иначе фикстуры
  порождают состояние, которого в проде не существует.
