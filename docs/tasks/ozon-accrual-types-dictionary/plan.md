# ozon-accrual-types-dictionary — статьи Ozon by-day из справочника, без правки кода

> Статус: план, к работе не принят. Только модуль **Ingestion**. Marketplace
> (`OzonCostCategory`, `OzonAccrualServiceCategoryResolver`,
> `default_cost_mapping.yaml`), ОПиУ и Cash не трогаем.
> Предыдущая задача: `docs/tasks/ozon-accrual-type-mapping-fix/` (#2717).

## 1. Проблема

Новая услуга Ozon в by-day сегодня требует правки PHP: каталог
`OzonAccrualCategory` — статический список из 49 статей, 39 латинских кодов
Ozon из 126 в справочнике. Пока каталог не поправлен, строка получает
`ozon_unknown_<type_id>`, группу «Требует классификации» и `known=false`.
Название берётся из `name` («Неизвестная категория Ozon: AnalyticsPlus»), а
русское описание, которое Ozon уже присылает, не используется.

Прод 18.10.2026: из 126 типов справочника в by-day встретились 47.
Нераспознаны 2: 126 `AnalyticsPremium` и 127 `AnalyticsPlus` (с 01.10, по
2 строки). Как раз у них в справочнике пустой `description`.

Ручной путь уже есть: админка `/admin/ingestion/external-categories` →
`UpdateExternalCategoryMappingAction` (код, название, группа — свободный текст).
Но предложить там нечего: справочник не разобран, группы ниоткуда не берутся.

## 2. Что отдаёт Ozon и где группа

### `POST /v1/finance/accrual/types` (`ozon.finance.accrual-types`)

Грузится командой `app:ingestion:ozon-accrual:load-types` (ресурс
`ozon_finance_accrual_types`) раз в сутки в сырое хранилище. Структура
(фикстура `tests/Fixtures/Marketplace/Ozon/accrual_types.json`):

```json
{ "accrual_types": [
  { "id": 1,  "name": "Acquiring",       "description": "Эквайринг" },
  { "id": 29, "name": "LastMileCourier", "description": "Доставка до места выдачи" }
]}
```

| Поле | Что это | Свойства |
|---|---|---|
| `id` | `type_id`, тот же, что в by-day | стабилен |
| `name` | латинский код услуги | уникален → основа canonical code |
| `description` | русское название, как в кабинете | **не уникально**, у 126/127 пусто |

Группы, знака, типа операции (FBO/FBS) и признака «затрата/доход» **нет**.
Сейчас читается только `id → name` (`StoredOzonAccrualTypeNameResolver`),
`description` никто не читает.

### `POST /v1/finance/accrual/by-day` — то, что мы загружаем по дням

Строка — начисление (`accruals[]`):

| Поле | Значения | Что даёт для группы |
|---|---|---|
| `accrued_category` | `POSTING` / `ITEM` / `NON_ITEM` (+ `container_fees`) | уровень: отправление, товар, кабинет |
| `posting.delivery_schema` | `Fbo` / `Fbs` / … | схема работы |
| `posting.products[].commission.*` | `sale_amount`, `sale_commission`, `bonus`, `coinvestment`… | продажи и вознаграждение — без `type_id` |
| `posting.products[].delivery.services[]` | `{type_id, accrued}` | услуги по доставке отправления |
| `item_fees.fees[].fees[]` | `{type_id, accrued}` по SKU | услуги по товару (упаковка, возвраты) |
| `non_item_fee` | `{type_id, accrued}` | услуги кабинета (реклама, подписки, штрафы) |

Группы нет и здесь. Есть только **место**, где тип встретился. Это слабый
сигнал: `LastMileCourier` лежит в `delivery.services`, но в кабинете Ozon он
относится к «Услугам партнёров», а не к «Услугам доставки».

### Отчёт о реализации (`realization`) и снятый `transaction/list` v3

Реализация: `operation_type`, `services_amounts` по старым именам сервисов
(`MarketplaceServiceItemDelivToCustomer`…), без групп. v3 снят Ozon 09.09.2026.

### Где группа есть: xlsx «Детализация начислений» из кабинета

Группы в `OzonCostCategory.xlsxGroup` взяты из xlsx-отчёта кабинета
«Детализация начислений». Marketplace уже читает его для сверки
(`XlsxReaderService`, загружается пользователем вручную, по API его нет). Колонки
первого листа (строка 2 — заголовки):

| № | Поле | Пример / смысл |
|---|---|---|
| 0 | ID начисления | **не** `accrual_id` by-day (13–15 цифр против 11, Stage 0) |
| 1 | Дата | дата начисления |
| 2 | **Группа услуг** | «Услуги партнёров», «Услуги FBO»… — группа кабинета |
| 3 | **Тип начисления** | русское название услуги, ≈ `description` справочника |
| 4–7 | Артикул, SKU, товар, количество | по товару |
| 10–11 | Площадка, **схема работы** | FBO/FBS |
| 15 | Сумма | со знаком |

**Вывод:**
- В API-данных (справочник, by-day, реализация) группы нет. Из того, что
  Ingestion грузит автоматически, её можно только *предложить*.
- Точную группу даёт xlsx: пара «Тип начисления → Группа услуг». ID начисления с
  by-day не совпадает, а «Тип начисления» совпадает с `description` дословно лишь в
  16 парах из 37. Работает связка с by-day той же компании по (дата, SKU, |сумма|):
  на августе 3f4d87cc каждый тип начисления получил `type_id` (Stage 0).
- Ingestion этот xlsx сейчас не принимает, а у Marketplace файл временный
  (`TemporaryLocalFile`). Брать его из Marketplace нельзя (Marketplace не трогаем),
  поэтому загрузка xlsx в Ingestion — отдельный этап (Stage 3b), **основной источник
  группы** (решение Stage 0: наш каталог сам расходится с Ozon в 4 группах).

## 3. Решение

1. **Справочник — таблица Ingestion.** Каждый `load-types` раскладывает сырой
   ответ в `ingest_ozon_accrual_types`. Ozon-справочник общий, не компании, поэтому
   у сущности нет `companyId`. Новый, изменённый или пропавший тип виден сразу,
   без ожидания первой транзакции.
2. **Статистика использования из загруженных данных.** Таблица
   `ingest_ozon_accrual_type_usage`: `type_id × блок by-day (delivery / item_fee /
   non_item_fee / container) × delivery_schema`, число строк, первая и последняя
   дата. Пересчитывается после нормализации by-day. Это сигнал для группы и
   типа транзакции, а заодно список дней для обновления истории.
3. **Статья генерируется, а не пишется в коде.**

   | Поле | Правило |
   |---|---|
   | canonical code | есть статья в каталоге с этим `name` в `aliases` → её код (обратная совместимость); иначе `ozon_` + snake_case(`name`), пробелы и дефисы → `_`: `AnalyticsPlus` → `ozon_analytics_plus`, `Drop-Off Agent` → `ozon_drop_off_agent`. Пока тип не подтверждён, код вычисляется из текущего `name` при каждом разборе: если Ozon переименует тип, код у его строк сменится (ключ транзакции — нет). После подтверждения код закреплён маппингом |
   | canonical label | `description`; пусто → `name` |
   | canonical group | закрытый список групп (п. 4); без уверенной подсказки — «Требует классификации» |
   | transaction type | по блоку: `delivery`/`item_fee` → `FEE` (как сейчас); `non_item_fee` → `FEE`, если подсказка группы не говорит иное |
   | known | `true` только у статьи из каталога или подтверждённой человеком; сгенерированная — `false`, пока группа не подтверждена |

4. **Группы — закрытый справочник в БД.** `ingest_category_groups` с текущими
   группами каталога: Продажи, Возвраты, Вознаграждение Ozon, Услуги доставки,
   Услуги партнёров, Услуги FBO, Продвижение и реклама, Компенсации и
   декомпенсации (так у Ozon; в каталоге сейчас «Компенсации»), Другие услуги и
   штрафы, Требует классификации. Это группы кабинета Ozon. Свободный
   текст группы в админке заменяется выбором из списка.
5. **Подсказка группы — правила-данные, не код.** Таблица
   `ingest_category_group_rules` (`priority`, `match_field` = name|description,
   `pattern`, опционально блок by-day, `group_code`, `confidence`). Стартовый
   набор выводится из текущего каталога: «партнер» → Услуги партнёров,
   «склад|размещ|FBO» → Услуги FBO, «реклам|продвиж|отзыв|Premium» →
   Продвижение и реклама, «штраф|Defect» → Другие услуги и штрафы и т. д.
   `high` — группа заполняется сразу (`known` всё равно `false` до
   подтверждения), `medium/low` — только показывается в админке.
   **Приоритет группы:** ручной маппинг → группа Ozon из xlsx (Stage 3b) → группа
   каталога → правило → «Требует классификации». Группа из xlsx сильнее каталога:
   так данными исправляются 52, 74, 76 (Stage 0, п. 5).
6. **Порядок разбора:** маппинг компании → маппинг по умолчанию в БД →
   каталог в коде (теперь это курируемые исключения) → **статья из справочника** →
   `ozon_unknown_<id>` (только если типа нет даже в справочнике).
7. **История догоняется сама.** Новый тип — новый, его строки лежат в
   последних днях. Ночной `daily-maintenance --days-back=45` (05:15) обновит
   их после подтверждения. Долгий ремонт, как 18.10, не нужен.

### Что остаётся в коде

- Новое значение `TransactionType`.
- Услуги, где статья зависит от знака (`Compensation`).
- Коды, на которые уже завязаны маппинги (каталог `OzonAccrualCategory` не удаляется).

### Чего задача не решает

Путь в ОПиУ идёт через Marketplace (`OzonCostCategory.accrualTypeNames` и
`default_cost_mapping.yaml`). Новая услуга там по-прежнему станет
`ozon_unknown_<type_id>` и сработает гейт нераспознанных затрат. Это решается
отдельной задачей с согласия Владельца: Marketplace берёт статьи из Ingestion
через Facade.

## 4. Этапы

Каждый этап — отдельный Stage с регрессионными тестами; push и PR один на
handoff.

- **Задача:** подтвердить входные данные.
- **Результат:** `stages/stage-0.md`:

    сырых записей `ozon_finance_accrual_types`);

  - распределение `type_id × блок × delivery_schema` по by-day (из `source_data`);
  - сравнение текущих групп каталога со стартовыми правилами п. 5: сколько
    из 47 встреченных типов правила раскладывают верно;

- **Чек-лист:** [ ] версии справочника; [ ] покрытие правилами ≥ 90% встреченных

### Stage 3 — группы и подсказки

- **Задача:** закрытый список групп и правила подсказки из данных.
- **Результат:**
  - таблицы `ingest_category_groups`, `ingest_category_group_rules` с сидом

  - `ingest_ozon_accrual_type_usage` + пересчёт после нормализации by-day;
  - `OzonAccrualGroupSuggester`: правила по приоритету + блок by-day →

  - фабрика Stage 2 берёт группу у подсказчика (`high`) или ставит «Требует классификации».
- **Выполнено, когда:** unit-тесты на все ветки подсказчика; на фикстуре
  справочника результат совпадает с группами каталога у всех типов, где
  каталог их задаёт (кроме перечисленных в Stage 0 исключений).
- **Чек-лист:** [ ] группа маппинга валидируется по списку; [ ] правило без
  совпадений не ломает разбор; [ ] usage пересчитывается идемпотентно.

### Stage 3b — группы из xlsx «Детализация начислений» (основной источник)

- **Задача:** получить точную группу Ozon по типу из отчёта кабинета.
- **Результат:**
  - загрузка xlsx в Ingestion: новый ресурс `ozon_accrual_details_xlsx`, файл в
    сырое хранилище, как остальные источники;
  - разбор колонок 0/2/3/11/15 → таблица `ingest_ozon_accrual_type_groups`
    (`type_id`, `group`, `xlsx_type_name`, число строк, период, источник);
  - связь с by-day той же компании по (дата, SKU, |сумма в копейках|); строки без
    SKU — по (дата, |сумма|); несколько `type_id` на строку — голосование по всем
    строкам этого «Типа начисления»; доля однозначных совпадений < 80% → тип в
    очередь, группа не ставится. ID начисления не используется (≠ `accrual_id`);
  - подсказчик Stage 3 ставит группу из xlsx первой, с `confidence = high`.
- **Выполнено, когда:** тест на образце xlsx (обезличенном): пары группа ↔
  `type_id`; конфликт (один тип в двух группах) — в очередь, не перезапись.
- **Чек-лист:** [ ] связка по (дата, SKU, сумма) на 4 отчётах ≥ 95% строк; [ ] группа из xlsx
  совпадает с каталогом у типов, где каталог её задаёт; [ ] UI загрузки —
  то же ограничение, что в Stage 4 (страница в `src/Admin`), либо консольная
  команда `app:ingestion:ozon-accrual:import-details-xlsx`.

### Stage 4 — очередь подтверждения в админке

- **Выполнено, когда:** functional-тест: подтверждение → маппинг + аудит;

- **Из ревью Stage 3b:** загрузка отчёта в админке — только `ROLE_ADMIN`, актор

- **Чек-лист:** [ ] IDOR (маппинг компании — только своей); [ ] после

## 5. Риски

- **Смена кода у уже размеченных строк.** Каталог остаётся первым звеном, у
  47 встреченных типов код не меняется. Проверяется сверкой в Stage 2.
- **Неверная подсказка группы.** Сгенерированная статья `known=false` до
  подтверждения. Группа `high` видна в отчётах Ingestion сразу, но помечена
  как неподтверждённая; правила правятся данными без деплоя.
- **Ozon переименует `name`.** Код привязан к `type_id` через справочник:
  статья не меняется, в справочнике видно изменение `name` (INFO + аудит).
- **Расхождение с Marketplace.** Ingestion начнёт называть новые услуги, а ОПиУ
