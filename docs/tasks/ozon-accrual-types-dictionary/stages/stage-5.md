# Stage 5: мониторинг и handoff

## 1. Какую задачу решаем

Новый тип Ozon теперь сам получает статью, но остаётся неподтверждённым, пока
админ не нажмёт «Подтвердить». Нужно, чтобы это не терялось: сигнал в ночном
health-check и понятный runbook. Затем — полная проверка ветки и handoff.

## 2. Что будет результатом

- Ночной `daily-maintenance` (05:15): метрика `newOzonTypesAwaitingConfirmation` —
  типы справочника с неразобранными начислениями и неподтверждёнными категориями
  (очередь Stage 4 без «ждёт refresh»); WARNING `Ozon accrual types await admin
  confirmation`, если хоть один ждёт дольше 3 дней (по первой неразобранной строке),
  с перечнем `type_id`. Не ERROR: деньги не теряются, тип уже в очереди.
- Справочник: INFO о новых/изменённых/пропавших типах уже пишет
  `SyncOzonAccrualTypesAction` (Stage 1).
- `docs/ingestion/runbook.md` — раздел «Новый тип начисления Ozon»: где смотреть,
  как подтвердить, как загрузить отчёт, что делать со спором и когда ремонтировать
  историю.
- Handoff: полный набор тестов, PHPStan, CS, strict_types, финальное внутреннее
  ревью ветки, внешнее ревью (Codex), `handoff.md`, push + PR.

## 3. Что считаем выполненной работой

- Тест команды: метрика считается, WARNING при типе старше 3 дней, без него — нет.
- Полный `phpunit` зелёный; гейты зелёные; ревью без открытых BLOCKER/IMPORTANT.
- `handoff.md` с планом выкладки: 3 миграции (обратимы, только новые таблицы и сид),
  после деплоя — `sync-types` (запись через Владельца), импорт отчётов 3f4d87cc,
  сверка `daily-maintenance --dry-run`.
