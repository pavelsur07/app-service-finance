# Stage 3b: группы Ozon из xlsx «Детализация начислений»

## 1. Какую задачу решаем

В API Ozon группы нет; правила (Stage 3) — догадка. Точная группа есть в отчёте
кабинета «Детализация начислений» (xlsx). Stage 0 показал: ID начисления в отчёте ≠
`accrual_id` by-day, а «Тип начисления» ≠ `description` дословно, но связка с by-day
той же компании по (дата, SKU, |сумма|) даёт `type_id` для каждого типа начисления.
Ещё Stage 0 показал, что группы каталога расходятся с Ozon у 52, 74, 76.

## 2. Что будет результатом

- `OzonAccrualDetailsXlsxReader` (Infrastructure): OpenSpout, первый лист, строка 1 —
  период, строка 2 — заголовки; колонки ищутся **по названию** («Дата начисления»,
  «Группа услуг», «Тип начисления», «SKU», «Сумма итого, руб.»), а не по номеру;
  дата — Excel-серийная или `дд.мм.гггг`. Отдаёт DTO строк; без нужных колонок —
  доменное исключение.
- `OzonAccrualByDayTypeLookupQuery`: by-day компании за период → индекс
  `(дата, SKU, |сумма в копейках|) → type_id` (и `(дата, |сумма|)` для строк без SKU),
  DTO `OzonAccrualTypeLookup`.
- `ImportOzonAccrualDetailsAction(companyId, rows, dryRun)`: голосование по «Типу
  начисления» → `type_id`; у победителя ≥ 80% однозначных голосов и их не меньше
  `min(3, строк типа)` → `confirmed`, иначе `conflict`; группа отчёта → код
  закрытого списка по `label` или `ozon_label`. Результат — DTO по типам + список
  несопоставленных.
- Таблица `ingest_ozon_accrual_type_groups` (Entity `OzonAccrualTypeGroup`, глобальная:
  группа типа одна для всех продавцов): `type_id` (unique), `group_code`, `status`,
  `xlsx_type_name`, `xlsx_group_label`, `votes`, `rows_total`, `evidence_company_id`,
  `period_from`, `period_to`, `created_at`, `updated_at`. Новое подтверждение
  перезаписывает прежнее; смена группы — WARNING в лог.
- Резолвер: подтверждённая группа Ozon сильнее группы каталога, маппинга по
  умолчанию (без ручной правки) и подсказки. Не трогает ручной маппинг
  (`updated_by`) и маппинг компании. Меняется **только группа** — код, название,
  `known`, тип транзакции остаются (ключ не меняется).
- Команда `app:ingestion:ozon-accrual:import-details-xlsx --company-id= --file= [--dry-run]`.
- Сам файл не сохраняется (ни S3, ни БД): в таблицу идут только агрегаты.
  Персональные данные отчёта (названия товаров и т. п.) не хранятся.
- Миграция таблицы (обратима).

Не входит: загрузка через админку — Stage 4.

## 3. Что считаем выполненной работой

- Unit-тесты читателя на xlsx, собранном в тесте OpenSpout'ом (обезличенный):
  колонки по названию в другом порядке, серийная и текстовая дата, отсутствие колонки.
- Integration-тесты Action: by-day в БД + строки отчёта → `confirmed` с верной группой;
  неоднозначность (две суммы в один день) решается голосованием; мало голосов →
  `conflict`; группа вне списка → в несопоставленные; `dry-run` ничего не пишет;
  повторный импорт со сменой группы — перезапись.
- Integration-тест резолвера: группа Ozon переопределяет группу каталога (76 →
  «Услуги партнёров»), не трогает ручной маппинг и маппинг компании, не меняет тип
  транзакции и `known`.
- Тест команды (dry-run/execute, несуществующий файл).
- Гейты, миграция up/down/up, ревью.
