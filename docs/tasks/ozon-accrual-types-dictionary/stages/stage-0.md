# Stage 0: разведка на проде (read-only)

## 1. Какую задачу решаем

До кода подтвердить входные данные, на которых стоят Stage 1–3b:
- справочник `accrual/types` одинаков у всех кабинетов (одна глобальная таблица,
  а не по компаниям);
- сколько типов, у скольких пустой `description`, есть ли повторы `description`
  (влияет на label и на сопоставление с xlsx);
- где в by-day встречается каждый тип (блок, схема) — сигнал для группы и типа;
- насколько стартовые правила групп (plan.md п. 5) совпадают с группами каталога;
- можно ли связать xlsx «Детализация начислений» с by-day по `accrual_id`.

## 2. Что будет результатом

Раздел «Итог» ниже с цифрами и решениями:
1. версии справочника по кабинетам (sha256 из `storage_path`, дата загрузки);
2. последняя версия: число типов, без `description`, повторы `description`;
3. таблица прода `type_id × блок by-day × delivery_schema` со строками и датами;
4. прогон стартовых правил групп по справочнику (скрипт в scratchpad, не в коде):
   совпадения с группами каталога по 47 встреченным типам, расхождения списком;
5. решение по Stage 3b: есть ли на проде сохранённые xlsx «Детализации
   начислений»; если нет — пункт ждёт файл от Владельца, этапы 1–3 от него не зависят;
6. уточнения plan.md, если данные расходятся с допущениями.

## 3. Что считаем выполненной работой

- Все запросы — через `codex-psql-ro`, только SELECT; на проде ничего не меняется.
- Сырьё S3 wrapper'ы не отдают (память `prod-raw-s3-no-read-path`): содержимое
  справочника берём из фикстуры (126 типов) и сверяем версию прода по sha256/размеру;
  если версия прода отличается от фикстуры — фиксируем как риск Stage 1, а не гадаем.
- Цифры записаны в «Итог», выводы перенесены в plan.md.

### 5. xlsx «Детализация начислений» — решение по Stage 3b

- На проде xlsx не хранятся (`marketplace_ozon_reconciliation_*` — сверка по API,
  без файлов). Локально у Владельца есть 4 отчёта кабинета 3f4d87cc (июль, август,
  сентябрь ×2) в `docs/temp/` (не в git, персональные данные — в репозиторий не
  переносятся).
- Заголовки (строка 2): ID начисления, Дата начисления, **Группа услуг**, **Тип
  начисления**, Артикул, SKU, Название товара, Количество, Цена продавца, Дата
  принятия заказа…, Платформа продажи, Схема работы, Вознаграждение Ozon %, Индекс
  локализации %, Среднее время доставки, Сумма итого.
- **ID начисления ≠ `accrual_id` by-day**: 13–15 цифр против 11; 60 ID из xlsx — 0
  совпадений в `external_id`.
- **Связка по (дата, SKU, |сумма|) работает**: 15 из 15 строк «Логистика» нашлись в
  by-day 3f4d87cc; на всём августе каждый «Тип начисления» получил `type_id`
  (неоднозначность при совпадении суммы в один день — голосованием большинства).
- «Тип начисления» ≠ `description` дословно: однозначно по тексту сопоставляется
  16 пар из 37 (суффиксы «(ПВЗ)», «: отмена», «: Доставка до ПВЗ», другие
  формулировки) → сопоставлять по тексту нельзя, только по данным.
- Группы Ozon (xlsx) против нашего каталога:

  | type_id | Тип начисления (xlsx) | Группа Ozon | У нас сейчас |
  |---|---|---|---|
  | 76 StockInsurance | Страхование товара от массовых повреждений | Услуги партнёров | Другие услуги и штрафы |
  | 74 StarsMembership | Звёздные товары | Услуги партнёров | Продвижение и реклама |
  | 52 PremiumSubscription | Подписка Premium | Продвижение и реклама | Другие услуги и штрафы |
  | 17 Drop-Off Agent | Обработка отправления Drop-off партнёрами (ПВЗ) | Услуги партнёров | Услуги доставки (статья Ozon `ozon_drop_off`) |
  | 10, 25 | Компенсации… | «Компенсации и декомпенсации» | «Компенсации» (имя группы) |

- **Решение: Stage 3b — обязательный и основной источник группы**, а не опция:
  xlsx загружается в Ingestion, группа на `type_id` выводится связкой (дата, SKU,
  |сумма|) с by-day той же компании. Правила — запасной вариант для типов без xlsx.
  Один отчёт покрывает только типы, активные у кабинета (у 3f4d87cc — ~22 из 47),
  поэтому полезны отчёты крупных кабинетов.
