## Матрица сопоставления — техническое предложение

Все выборки ограничены companyId и accountId, только активные операции. Денежные значения сравниваются точно, без float. Дата соответствует существующему правилу дня UTC; направление проверяется явно, поскольку в текущем hash его нет. По согласованию владельца допускаются операции файлового импорта, банка и 1С.

| Ситуация | Результат |
|---|---|
| Совпадают реквизиты и текст после исключения технических отличий | unchanged, расходует одну квоту |
| Текущий hash совпал, но текст отличается регистром/пунктуацией | не терять изменение при нормализации: предложение вместо молчаливого skip |
| Единственный оставшийся кандидат с той же датой, направлением, суммой, валютой и совместимым номером | предложение с показом реквизитов; это не доказанная идентичность |
| У обеих сторон разные непустые номера | не сопоставлять как обновление |
| Номер отсутствует с одной стороны | только после распределения точных совпадений; при нескольких кандидатах конфликт |
| У кандидата явно другой контрагент | конфликт, не менять контрагента и не выбирать по похожести имени |
| Несколько возможных назначений строк операциям | конфликт для неоднозначной группы, не выбирать по UUID/порядку |
| Есть признаки той же операции, но отличается сумма | конфликт; не превращать в новую запись |
| Нет кандидатов и признаков конфликта | create по прежним правилам |
| Операция удалена после подтверждения | конфликт, без восстановления/create |

Распределять по всему файлу: точные совпадения раньше предложений. Сохранять количество законных одинаковых платежей; surplus одинаковых строк по прежним правилам допустим, но несколько строк с разными новыми описаниями на один ID — конфликт. Исторический soft-delete не переопределять глобально: явно выбранный ID удалённой операции обновлять нельзя, прежние правила повторного импорта удалённых строк покрыть регрессией.

Без внешнего устойчивого ID невозможно математически отличить новый похожий платёж от правки старого. UI должен показывать «возможное совпадение», реквизиты и требовать выбора; нельзя обещать автоматическую идентификацию любого файла. Обновления между указанными источниками согласованы владельцем; автоматическое подтверждение запрещено.

## Согласованные правила текста и источников

Пустой текст, включая одни технические пробелы, не очищает описание. При сравнении игнорировать пробелы по краям и техническую форму переносов строк; внутреннее форматирование сохранять, регистр и пунктуацию не сворачивать. Техническое равенство не должно вызывать UPDATE, аудит или предложение замены. Это сравнение отделено от эвристической нормализации текущего dedupe_hash.

Последующая синхронизация банка/1С не должна отменять подтверждённую замену. До реализации проверить пути записи описания в ImportBankStatementDayAction/ClientBank1CImportService и связанные контракты. Использовать существующую защиту, если она есть; иначе добавить минимальный механизм защиты и описать его хранение. Не изменять исходные payload, import_source и external_id ради защиты. Предпочтение варианту без миграции ниже относится к хранению плана; если для надёжной защиты описания потребуется отдельное поле, необходимость миграции обосновать в Stage 2 и актуализировать release-план. Не объявлять отсутствие миграции гарантированным.

Приёмка включает обновление описания операции каждого источника с последующим повтором банка/1С: подтверждённый текст сохраняется, количество операций и финансовые поля неизменны, исходные данные и внешние идентификаторы сохранены. Защиту проверить также при отсутствии изменений во входящей банковской операции.

## Хранение и объём

Предпочтительный вариант без миграции: неизменяемый план в существующем ObjectStorageInterface, привязанный к company/account/инициатору/fileHash/mappingHash и версии формата. В сессии — только ссылка/ID, не весь файл. В CashFileImportJob.options — ссылка и fingerprint подтверждённого плана, версия, инициатор, курсор выполненной пачки и агрегированные счётчики. Пагинация читает план; большие планы разбиваются на части. Отсутствующий объект или несовпавший fingerprint — отказ, не повторное построение с автоматическим подтверждением.

Подтверждённый план включает стабильные rowId (лист/номер строки), действие, transactionId, old/new description и fingerprint бизнес-реквизитов. Браузер передаёт только выбранные rowId и CSRF; сервер проверяет принадлежность и права. Подтверждение имеет стабильный jobId для защиты двойного клика, не новый UUID на каждый retry. Старые задания без версии плана сохраняют прежний путь выполнения.

Сначала использовать существующий индекс `idx_company_account_occurred(company_id, money_account_id, occurred_at)` и выборки диапазона дат порциями. Не делать запрос на строку или уникальный индекс по эвристическому hash. Новые индексы вводить только по замерам в реализации; на подготовке миграция не нужна.

## Транзакции, возобновление и stale preview

- Сохранить существующую сессионную блокировку импорта счёта; ручные правки дополнительно защищать блокировкой строки внутри транзакции и сравнением снимка.
- Перед записью проверять выбранный ID, компанию, счёт, активность, исходный текст и финансовые реквизиты.
- Курсор выполнения и счётчики в options сохранять в той же DB-транзакции, что изменения пачки. После rollback не продвигать курсор; после commit повтор не записывает аудит снова.
- Смешанный импорт не должен менять create-семантику и пересчёт остатков новых строк.
- Итоги обновлений показывать из задания, не перегружать смысл existing created/skippedDuplicates. У текущего ImportLog отдельного счётчика updated нет.
- Дедупликация должна учитывать текущие финансовые поля и текст после обновления. Один только пересчёт dedupe_hash недостаточен: старый файл обязан попасть в предложение/конфликт, а не create. Не переписывать external_id, import_source и rawData существующих операций.

## Обнаруженный побочный эффект

`CashTransactionAutoRulesSubscriber` реагирует на изменение description. Общий `AutoRuleDispatchGuard` подавляет также `AuditLogSubscriber::postUpdate`. Поэтому простое setDescription может изменить категории, а простое suppress — потерять аудит.

В Stage 2 требуется целевое решение: при импорте описаний подавить dispatch автоправил, сохранив ровно одну запись аудита с before/after и инициатором. Использовать существующие guard/AuditLog и транзакционный шаблон; не заводить параллельную систему аудита. Проверить фактическую запись audit в той же транзакции. Отдельный тест должен доказать одновременно отсутствие автокатегоризации и наличие аудита.
