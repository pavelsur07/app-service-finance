# Обновление описаний операций ДДС при повторном импорте

Статус: план, реализация не начата. Класс реализации: Large.

## Цель

При повторном импорте файла предлагать обновление описаний существующих операций ДДС. Обновлять только подтверждённые описания, не менять суммы и другие бизнес-поля, не создавать дубли.

## Текущее состояние

- `site/src/Cash/Service/Import/File/CashFileImportService.php`: описание входит в `dedupe_hash`, поэтому изменение текста может восприниматься как новая операция.
- Существующая дедупликация учитывает количество одинаковых операций и распределяет совпадения по всему файлу. Это поведение нужно сохранить.
- `site/src/Cash/Controller/Import/CashFileImportController.php`: предпросмотр нормализует первые 100 строк, но не определяет действия относительно базы.
- Интерфейс предпросмотра: `site/templates/cash/file_import_preview.html.twig`.
- Импорт выполняется через `CashFileImportJob` и `CashFileImportHandler`, с обработкой пачками и блокировкой по счёту.
- У задания есть JSON-поле `options`; пригодность для хранения подтверждённых действий необходимо оценить по объёму.
- Просмотренный обработчик поддерживает XLSX и CSV. Поддержка бинарного XLS не включена в задачу автоматически.

## Пользовательский сценарий

1. Загрузить файл и выбрать счёт.
2. Сопоставить колонки.
3. Получить анализ всего файла.
4. Просмотреть предложения «было → станет» и выбрать обновления.
5. Запустить импорт.
6. Получить фактический итог: создано, обновлено описаний, пропущено, конфликты и ошибки.

| Категория строки | Действие |
|---|---|
| Новая операция | Создать по существующим правилам |
| Существующая операция, описание совпадает | Пропустить |
| Найден кандидат, описание отличается | Предложить обновление после явного выбора |
| Несколько возможных соответствий | Конфликт, без автоматического обновления или создания |
| Некорректная строка | Показать ошибку |

Невыбранное обновление пропускается и не превращается в создание новой операции.

## Инварианты

- У существующей операции сохраняются ID, сумма, направление, дата, валюта, счёт, контрагент, статьи, распределения и связи с документами.
- Допускаются изменение описания и необходимые служебные изменения: время обновления, аудит, согласованное обновление данных дедупликации.
- Компания и счёт проверяются при анализе и исполнении.
- Одна существующая операция сопоставляется максимум одной строке файла.
- Несколько одинаковых реальных платежей не схлопываются в один.
- Если операция исчезла после предпросмотра, новая вместо неё не создаётся.
- Задание, обновляющее только описания, не запускает финансовые пересчёты и не меняет категории через автоматические правила.

## Сопоставление

1. Сначала распределить точные совпадения по существующим правилам.
2. Для оставшихся строк найти кандидатов без учёта описания, внутри компании и выбранного счёта.
3. Сравнить дату, сумму, направление и валюту.
4. Использовать номер документа и доступные сведения о контрагенте для уточнения.
5. Однозначные предложения показать пользователю с реквизитами; неоднозначные считать конфликтами.

Совпадение даты и суммы само по себе не доказывает идентичность операции. Без устойчивого идентификатора найденное соответствие остаётся предложением для подтверждения.

До реализации закрепить поведение при отсутствии номера документа, номере только с одной стороны, повторяющихся платежах, разных описаниях одной операции внутри файла, совпадающем номере с другой суммой, удалённых операциях и другом источнике импорта. При признаках существующей операции с другой суммой — конфликт без изменения суммы и автоматического создания.

## Серверный план импорта

- Анализировать весь файл; выводить результат страницами.
- Использовать общую логику сопоставления для предпросмотра и выполнения.
- Сохранять строку файла, ID операции, старое и новое описание, реквизиты сопоставления.
- Привязывать результат к компании, счёту, файлу и настройкам колонок.
- При смене этих параметров формировать новый результат.
- Хранить подтверждённые действия на сервере; проверять входные данные браузера.
- Оценить объём и выбрать существующее `options` либо обоснованное отдельное хранение. Не вводить миграцию без необходимости.

## Выполнение

Сохранить существующую очередь, пачки и блокировку импорта по счёту.

Для каждого подтверждённого обновления внутри транзакции:

1. Загрузить операцию с проверкой компании и счёта.
2. Проверить актуальность финансовых реквизитов и исходного описания.
3. При совпадении изменить описание и записать аудит и результат.
4. При изменении после предпросмотра показать конфликт, не затирать чужую правку.

Обеспечить идемпотентность:

- Повтор файла с новым описанием не создаёт дубль.
- Повторная доставка задания не повторяет обновление.
- Возобновление после сбоя учитывает выполненные действия.
- Повтор старого файла не создаёт дубль и не возвращает старое описание автоматически; возможное обратное изменение требует нового подтверждения.

## Интерфейс

Расширить существующий Twig-экран без общего редизайна:

- Сводка и фильтры: новые, без изменений, обновления, конфликты, ошибки.
- Реквизиты существующей операции и сравнение «было → станет».
- Выбор отдельных обновлений и всех доступных; по умолчанию обновления не выбраны.
- Количество создаваемых операций и выбранных обновлений перед запуском.
- Фактический итог, включая конфликты, возникшие после предпросмотра.

## Проверки

Перед изменениями запустить минимальные релевантные тесты импорта и записать baseline. Проблему воспроизвести регрессионным тестом, доказать красный результат на старом коде и зелёный на новом.

| Сценарий | Ожидаемый результат |
|---|---|
| Изменено описание | Тот же ID, новое описание, прежняя сумма |
| Обновление не выбрано | Операция неизменна |
| Повтор нового файла | Нет новых операций |
| Повтор старого файла | Нет дублей и автоматического возврата описания |
| Два одинаковых платежа | Оба сохраняются, соответствия не смешиваются |
| Несколько кандидатов | Конфликт без записи |
| Другая сумма предполагаемого совпадения | Сумма неизменна, конфликт виден |
| Правка после предпросмотра | Чужая правка не затирается |
| Удаление после предпросмотра | Операция не восстанавливается и не создаётся |
| Подмена компании, счёта, ID | Доступ запрещён |
| Повтор задания, сбой между пачками | Нет повторных изменений и дублей |
| Обновление после строки 100 | Найдено и доступно для подтверждения |

Дополнительно проверить неизменность остатков, распределений, связанных документов и отсутствие запроса к БД на каждую строку большого файла.

## Этапы

### Phase 0 — до кода

- Закрепить открытые бизнес-правила ниже в TASK.md.
- Прочитать релевантные разделы ARCHITECTURE.md, PATTERNS.md, CLAUDE.frontend.md и workflow templates.
- Найти 2–3 подходящих существующих примера предпросмотра, подтверждения и защиты от устаревшего результата.
- Уточнить контракт сопоставления и хранения, необходимость миграции и индексов.
- Запустить baseline; записать команды и результаты.
- Подготовить checkpoint.md, определить stage_base_commit и Definition of Done первого этапа.

### Stage 1 — backend: анализ и план действий

Риск HIGH-LOCAL. Реализовать сопоставление и серверный план, покрыть граничные случаи тестами. Definition of Done: анализ всего файла работает, предпросмотр ничего не изменяет, неоднозначность видна как конфликт.

### Stage 2 — backend: подтверждённое выполнение

Риск HIGH-LOCAL. Реализовать обновление, проверку актуальности, аудит, результаты и защиту от повторов. Definition of Done: меняется только описание и служебные данные; повтор и восстановление после сбоя не создают дубли.

### Stage 3 — frontend

Риск MEDIUM. Добавить сравнение, выбор, состояния загрузки/ошибки/пустого результата, итог и адаптивный вывод. Definition of Done: пользователь подтверждает конкретные изменения и видит фактический результат.

### Stage 4 — сквозная проверка и handoff

Проверить весь сценарий, выполнить полные gates и независимые ревью. Definition of Done: нет открытых BLOCKER/IMPORTANT, документация актуальна, PR готов к передаче.

На этапах — узкие и модульные проверки, саморевью, Stage Report, commit/push и обновление единственного Draft PR. Перед handoff: `make site-stan`, `make site-cs-check`, `make site-cs-strict-types`, `make site-test-unit`, `make site-test`; frontend-проверки по фактическим изменениям. Финальное внутреннее ревью — свежая сессия, внешнее — по external-review.md; дополнительное внешнее ревью HIGH-LOCAL этапа при diff более ~500 строк. Merge + deploy только по отдельному разрешению; при миграции учесть release.md.

## Согласованные решения

Владелец подтвердил 2026-11-06:

1. Пустое описание не очищает существующий текст (включая текст из одних технических пробелов).
2. Неоднозначные строки пропускаются с конфликтом, без автоматического создания операции и без ручного выбора кандидата в первой версии.
3. Содержательные изменения, включая регистр и пунктуацию, показываются для подтверждения. Пробелы по краям и технические различия переносов строк игнорируются при сравнении; внутреннее форматирование сохраняется.
4. Поддерживаются текущие XLSX/CSV; старый бинарный XLS в объём не входит.
5. Обновления разрешены для файлового импорта, банка и 1С. Источник, внешний ID и исходные данные сохраняются; последующая синхронизация не должна перезаписывать подтверждённое описание.
6. Все обновления — только по явному выбору; по умолчанию ничего не выбрано. Доступны отдельный выбор и «Выбрать все доступные».
