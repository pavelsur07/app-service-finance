# Stage 2 — подтверждённое обновление и защита описания

Статус: ТЗ, не реализовано. Риск: HIGH-LOCAL. Вход: план Stage 1.
`stage_base_commit`: записать перед началом. Backend отдельно от UI.

## Результат

Выбранные обновления выполняются ровно один раз и меняют только описание/служебные данные. Повтор файла, сообщения и банковской синхронизации не создаёт дубль и не отменяет подтверждённую правку.

## Что меняем

- `Cash/Application/StartCashFileImportJobAction.php` и Action подтверждения: проверка доступа, immutable selection, стабильный jobId на повтор подтверждения.
- `Cash/Entity/Import/CashFileImportJob.php`: версионированные options плана/выбора/прогресса, без изменения смысла старых jobs.
- `Cash/MessageHandler/Import/CashFileImportHandler.php`, `CashFileImportService.php`: исполнение плана, транзакции пачек, прогресс и результаты.
- `Cash/EventSubscriber/Transaction/CashTransactionAutoRulesSubscriber.php`, `Cash/EventSubscriber/Audit/AuditLogSubscriber.php`, существующий guard: лишь необходимая оркестрация audit без автокатегоризации. Не менять глобально поведение обычного редактирования.
- `Cash/Application/ImportBankStatementDayAction.php`, `Cash/Service/Import/ClientBank1CImportService.php` и существующие вызываемые пути: защита подтверждённого описания от перезаписи. Внешние API не вызывать, использовать fixtures.

## Work items

### 2.1 — подтверждение

Принимать planId/fingerprint, список выбранных rowId, CSRF и стабильный ключ подтверждения. Проверять текущие права, компанию, счёт, инициатора и принадлежность строк плану. Нельзя прислать произвольный transactionId/newDescription. Нельзя выбрать conflict/invalid/unchanged. Невыбранный update — skipped_by_user, никогда create. Повтор того же подтверждения возвращает то же задание; другая selection под тем же ключом отклоняется. Согласие из прошлой загрузки/профиля не наследуется.

### 2.2 — транзакции и прогресс

Сохранить блокировку по счёту. Под блокировкой строки проверить active/company/account и актуальность snapshot. Сравнивать ID, дату, направление, сумму, валюту, документ, контрагента и исходное описание; другие финансовые связи не менять. При stale/deleted — conflict, не fallback-create. Перепроверять create-решения против импортов, выполненных после preview: найденное новое совпадение не должно порождать дубль или несанкционированный update.

В одной транзакции фиксировать изменения пачки, аудит, курсор и счётчики. Сбой до commit откатывает всё, после commit повтор продолжает со следующего действия. Учитывать изменения состояния объекта job при detach/clear. Проверка равенства нового текста сама по себе не доказывает выполнение данным job — нужен его транзакционный прогресс. Ошибка хранения/неизвестная версия не запускает fallback с прежними предположениями.

Сводка: created, description_updated, unchanged, skipped_by_user, conflicts, invalid. Итоги не удваиваются на retry. Не подменять existing ImportLog.created числом обновлений. Старые jobs без версии плана работают прежним путём.

### 2.3 — финансовая неизменность и аудит

Обновлять описание и обоснованные служебные поля, сохранять rawData/importSource/externalId. Пересчёт dedupe_hash согласовать с новым matcher: повтор старого файла после update тоже не создаёт дубль. Только обновления описаний не пересчитывают остатки. Новые операции смешанного файла сохраняют прежние пересчёты.

Подавление автоправил локально ограничить этим сценарием, guard восстанавливать при исключениях. В той же транзакции сохранить ровно один UPDATE audit с before/after и инициатором. Учесть, что существующий guard подавляет аудит: явно доказать его сохранение тестом реальной БД, не только mock subscriber.

### 2.4 — восстановление и параллельность

Сценарии: повтор сообщения, двойной submit, оборванный processing, падение на границе пачки, два импорта одного счёта, ручное редактирование между preview и apply. В реальной конкуренции использовать два соединения/процесса, а не последовательные вызовы, маскирующие гонку. Старые версии задания не теряются после deploy.

### 2.5 — повтор банка/1С

Проследить все текущие записи description из банковского дневного импорта и 1С. Если существующий путь только пропускает совпадение, не переписывать его ради нового механизма: закрепить защиту тестом. Если путь перезаписывает текст — добавить минимальную устойчивую защиту, не записывать флаги в исходный банковский payload. Механизм и жизненный цикл документировать в design.md.

Если потребуется миграция: nullable/совместимый default для существующих операций, без массового изменения описаний/сумм; локальная миграция, rollback и совместимость старых workers проверяются. Прочитать release.md и включить отдельный production dispatch в handoff. Решение о необходимости схемы принять до изменения Entity; отсутствие миграции заранее не обещать. Изменение банковских финансовых правил вне scope.

## Тесты и проверки

B01–B15 и F01–F03 из acceptance.md; модульные тесты Cash; затронутые BankSync tests при изменениях вызывающего пути. Реальная БД обязательна для atomicity, audit, lock и idempotency. Финансовая регрессия Stage 1 должна стать зелёной.

## Приёмка этапа

- [ ] Один ID до/после, число операций неизменно для update-only, полный финансовый снимок равен.
- [ ] Пустой/невыбранный текст не меняет операцию.

- [ ] Прогресс и изменения атомарны; конфликт не становится create.
- [ ] Autocategorization не запускается; audit сохраняется с автором.
- [ ] Банк/1С не затирают подтверждённое описание, исходные данные сохранены.
- [ ] Старые задания, количественные совпадения и создание новых операций не сломаны.
