# MoySklad: выпуск и перенос существующих секретов

PR #2478, миграция `Version20260914143000`. Новые подключения сразу сохраняют зашифрованный токен. Существующие записи читают старый токен до отдельного переноса. Миграция не меняет прежние токены и финансовые данные; добавляет nullable account UUID, статусы/время проверок, version и encrypted-поля. Глобальный уникальный индекс account_id сохраняет привязку даже у отключённых подключений. Старые account_id остаются NULL до успешной проверки; дубли не объединяются автоматически.

## Одобрение и порядок

1. На handoff запросить `run the migration and deploy #2478`. Указать необратимый down и резервную копию moysklad_connections. Отдельно запросить ручное шифрование существующих секретов.
2. После одобрения выполнить штатный merge и release workflow по docs/workflow/release.md: migration dispatch, проверка схемы, deploy dispatch. До production-миграции подтвердить актуальную резервную копию таблицы и доступность восстановления. Секреты и дамп не скачивать в рабочую среду агента.
3. Проверить миграционный статус и доступность страницы через разрешённые read-only средства. Проверить Shared encryption key configuration без вывода значений. Не менять ключи/секреты в рамках задачи.
4. Перенос выполнять только после отдельного названного одобрения, для каждой компании отдельно. Ниже приведён аргумент приложения, а не разрешение выполнять произвольную SSH-команду:

```text
app:moysklad:encrypt-secrets --company=<company-uuid>
app:moysklad:encrypt-secrets --company=<company-uuid> --execute
```

Первый запуск всегда dry-run. Production доступ только через vf-prod-codex и разрешённые wrappers по docs/maintenance/prod-access.md. Если новый console command отсутствует в allowlist, не обходить ограничение: подготовить узкое разрешение владельцу либо передать ему точную команду. Изменение wrapper/прав не входит в обычное разрешение deploy/backfill.

## Контроль данных

До переноса записать агрегаты по каждой компании: количество подключений; количество непустых plaintext access/refresh токенов; количество заполненных encrypted-полей; количество bound account_id; распределения is_active/check_status. Значения токенов, ciphertext и payload не выводить. Проверить отсутствие дублирующихся non-NULL account_id. Сохранить контрольные идентификаторы и метаданные в защищённой production среде, без выгрузки секретов.

После execute сверить те же агрегаты: количество записей и привязки company/id/account/name/is_active/check_status/last_sync не изменились; plaintext очищен только у успешно проверенных записей, encrypted присутствует. Обработка атомарна для одной записи, не для всей компании: при ошибке предыдущие записи могли сохраниться. Повторный dry-run должен показать pending0, повторный execute — encrypted0. Колонка version у обработанных записей увеличивается ожидаемо. Идемпотентность, порча ciphertext и company isolation покрыты локальными тестами.

## Ошибка и восстановление

Команда прекращает обработку при ошибке, не печатает exception message/payload; диагностический лог содержит только класс/код исключения и companyId. Не исправлять данные SQL вручную без отдельного одобрения. После устранения причины повторный запуск безопасен.

Down намеренно необратим: удаление новых колонок потеряло бы зашифрованные секреты и привязки. До переноса схема совместима со старым кодом; после очистки plaintext откат на старый код нарушит доступ к секретам. Предпочтителен forward-fix. Восстановление резервной копии — отдельная согласованная операция с учётом записей, созданных после backup. Обычный code rollback после backfill недостаточен.

ALTER TABLE и создание уникального индекса могут блокировать таблицу; production-объём и время блокировки ещё не измерены. Подтвердить допустимое окно перед dispatch в рамках согласованного выпуска. В этой задаче production не читался и не изменялся.
