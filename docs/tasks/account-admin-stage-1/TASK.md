## 1. Цель

Пользователь входит в `account.vashfindir.ru` существующей учётной записью,
видит свою активную компанию и может выбрать другую доступную ему компанию.
Администратор входит в `admin.vashfindir.ru`; сервер разрешает доступ только
пользователям с системной ролью `ROLE_ADMIN`, включая иерархию `ROLE_SUPER_ADMIN`.
Старый интерфейс `app.vashfindir.ru` продолжает работать.

Результат — работающая авторизация и оболочки приложений с реальным контекстом.
Финансовые и административные бизнес-разделы пока остаются заглушками.

## 2. Подтверждённая исходная система

| Область | Факт и источник |
|---|---|
| Frontend | `apps/account/`, `apps/admin/`: React 19, Router, TypeScript, Vite, Vitest/MSW, Playwright; `/`, `/about`, клиентская 404 |
| Backend | Один Symfony в `site/`; `Company\Entity\User`, существующий password hasher/provider |
| Вход | `security.yaml`: form login `main` и отдельный `admin` с `context: admin`; ограничение 5 попыток / 15 минут |
| Сессии | `framework.yaml`: Redis, `cookie_secure: auto`, `cookie_samesite: lax`; явный `cookie_domain` в этом файле не задан |
| Компания | `ActiveCompanyService`: ключ `active_company_id`, владелец или активное членство; исключение удаляемых компаний; fallback на доступную компанию |
| Доступные компании | `CompanyFacade::listAccessibleCompaniesForUser()` и `userHasAccess()` уже реализованы |
| Права | `ModuleAccessResolver`, `ModuleAccessVoter`, `ModuleAccessSubscriber`; неизвестные контроллеры закрыты по умолчанию |
| HTTP-клиент | `site/packages/api`: JSON, cookies, CSRF, AbortSignal, нормализация ошибок; старый адаптер перенаправляет на `/login` |
| Публикация | Отдельные статические nginx-образы; Traefik Host/TLS; SPA-контейнеры без доступа к сети БД |

Не смешивать `Module::ADMIN` (права внутри компании) и системную `ROLE_ADMIN`.
Старый `CompanyController::setActive()` проверяет только владельца; напрямую
переносить его ограничения в новый кабинет нельзя. Новая операция использует
доступ владельца **или активного участника**, уже установленный общими сервисами.

## 3. Решение о сессиях

После подготовки документов владелец поручил приступить к реализации. Принят
рекомендованный вариант A; альтернативный B оставлен ниже для истории решения.

| Вариант | Поведение | Последствия |
|---|---|---|
| A — отдельные сессии, рекомендуется | Вход и выход отдельно в app, account и admin; учётные записи и пароли общие | Не требуется SSO; клиентская сессия не становится административной |
| B — общий вход app/account | После входа в один клиентский интерфейс второй узнаёт пользователя; admin отдельно | Потребуется отдельный дизайн обмена сессией/SSO, общего выхода и контекста компании; Stage 1 и Stage 4 этого плана нужно пересмотреть |

Общий cookie `Domain=.vashfindir.ru` не считается готовым решением SSO.
Переход на B потребует нового явного решения и пересмотра плана.

## 4. Границы

Входит: вход/выход, восстановление сессии после reload, CSRF, ограничение попыток,
профиль текущего пользователя, доступные/активная компания, отображение прав,
защищённые маршруты, состояния загрузки/ошибки/отсутствия компании/нет доступа,
same-origin API-маршрутизация, автоматические тесты, совместимость старого UI.

Не входит: регистрация, приглашения, сброс пароля, 2FA, OAuth/SSO, impersonation,
редактор ролей, управление пользователями/компаниями, отчёты и финансовые операции,
новый Symfony-проект `api/`, миграции, смена схемы БД, изменение workers/очередей,
прямой доступ браузера к сервисам `services/`. Существующие пароли не переносятся
и не пересчитываются отдельно. Новые зависимости по умолчанию не нужны.

## 5. Архитектура варианта A

### 5.1. Маршрутизация и граница хостов

| Браузерный origin | Путь | Обработчик |
|---|---|---|
| account | `/api/account/v1/*` | существующий site nginx → Symfony |
| admin | `/api/admin/v1/*` | существующий site nginx → Symfony |
| account/admin | SPA-страницы и `/assets/*` | соответствующий статический nginx |
| app | существующие пути | прежняя маршрутизация |

Traefik направляет **только** соответствующий API-префикс в backend, с явно
большим приоритетом, чем SPA-роутер; Host и HTTPS-признаки сохраняются. Префикс
не обрезается. Статические контейнеры остаются в `traefik-public`.

Запрещённые сочетания host/path возвращают 404: account → admin API, admin →
account API, app → новые SPA API. Произвольные legacy `/api/*`, `/admin/*`,
`/internal/*`, PHP-пути через новые домены не публикуются. API-ошибки никогда
не заменяются `index.html`. Ограничение проверяется и на HTTP-входе Symfony,
чтобы прямой запрос к backend не обходил правила Traefik.

Новые API не используют credentialed CORS. В `site/docker/common/nginx/conf.d/default.conf`
сейчас есть `Access-Control-Allow-Origin: *` и `Allow-Credentials: true`:
для новых путей исключить наследование этих заголовков без глобальной переделки
старого API. Проверять итоговые ответы после внутреннего перехода nginx к PHP.

### 5.2. Аутентификация и cookies

Два новых stateful firewall-контекста `spa_account`, `spa_admin` выбираются по
точному host и префиксу и стоят перед legacy `admin`/`main`. Они используют
существующий user provider и password hasher. Legacy-контексты не объединяются.

Обычный session cookie Symfony остаётся host-only: без `Domain`, `HttpOnly`,
`Secure` в production, `SameSite=Lax`, `Path=/`. Не вводить JWT, refresh token,
хранение авторизации в localStorage или чтение session ID из JavaScript.
После успешного входа session ID меняется средствами Symfony. Выход уничтожает
сессию текущего хоста и её cookie; другие интерфейсы остаются авторизованными.

На локальной машине нужны **разные имена хостов**, например account.localhost,
admin.localhost, app.localhost: cookies не разделяются портами. В Docker E2E —
разные сетевые aliases и явно разрешённые тестовые hosts; production принимает
только настроенные точные имена. Никакого wildcard для произвольного поддомена.

Использовать Symfony authenticator/Passport с PasswordCredentials и
CsrfTokenBadge; не писать ручную проверку хеша в контроллере. В admin после
проверки credentials требуется `isGranted('ROLE_ADMIN')`; пользователь без этой
роли не получает рабочую admin-сессию. Роль повторно проверяется для защищённых
запросов; снятие роли не оставляет доступ до следующего ручного входа.

Неверный email и неверный пароль имеют одинаковое сообщение. Сохранить минимум
существующее ограничение 5 попыток / 15 минут; тестировать также блокировку
корректного пароля после исчерпания лимита. Не логировать пароль, cookie, CSRF
или тела auth-запросов. Ошибки 401/403/429 не создают ложных ERROR-инцидентов.

### 5.3. CSRF и жизненный цикл

GET выдаёт CSRF-токены текущей сессии; каждый POST, включая login/logout/выбор
компании, требует `X-CSRF-Token`. Назначения токенов разделены: login, logout,
company selection, с префиксом контура. Токен другого контура/назначения/сессии
не подходит. Для mutation-запросов дополнительно проверяется соответствие
Origin текущему origin, при отсутствии — Referer; отсутствие обоих отклоняется.
Sibling-поддомены не считаются доверенными источниками. SameSite не заменяет CSRF.

После login/logout frontend сбрасывает токены и получает актуальные заново.
Истёкшая сессия на защищённом API даёт JSON 401 без HTML/302. Обработчик нового
приложения очищает контекст, отменяет запросы, открывает его `/login`. Сетевая
ошибка и 5xx не трактуются как выход. При 403 доступ не расширяется и повторный
вход не запускается циклически. POST автоматически не повторяется.

## 6. Предлагаемый контракт API v1

`P` — `/api/account/v1` или `/api/admin/v1`; различие endpoint-ов явно указано.
Все JSON-ответы, включая ошибки и CSRF, получают `Cache-Control: no-store`.

| Метод и путь | Доступ и запрос | Успешный ответ |
|---|---|---|
| `GET P/auth/csrf` | Анонимный, текущий host | 200 `{tokens:{login,logout,company_select?}}`; последнее поле только account |
| `POST P/auth/login` | JSON `{email,password}`, CSRF login | 204; frontend затем получает `P/session` |
| `POST P/auth/logout` | Авторизован, CSRF logout, без body | 204; повтор после выхода — 401, frontend считает выход завершённым |
| `GET P/session` | Авторизован, в admin дополнительно ROLE_ADMIN | 200 контекст ниже |
| `GET /api/account/v1/companies?page=1&perPage=50` | ROLE_USER | 200 `{data:[{id,name}],meta:{total,page,per_page,pages}}`, максимум 200, неверные параметры/страница — 422 |
| `POST /api/account/v1/active-company` | ROLE_USER, JSON `{targetCompanyId}`, CSRF company_select | 200 обновлённый account-контекст |

`targetCompanyId` — **цель переключения**, а не разрешение читать бизнес-данные
чужой компании. После серверной проверки доступа он сохраняется в сессию.
Остальные операции берут активную компанию только через `ActiveCompanyService`.

Account session: `{user:{id,email},active_company:{id,name}|null,
permissions:{finance,marketplace,deals,catalog,admin}}`.
Значения permissions: `none|read|write` из существующих Module/AccessLevel.
Список компаний не встраивается в session: он пагинируется отдельным запросом.
Admin session: `{user:{id,email},access:{admin:true}}`; списка всех компаний,
финансовых данных и имитации выбранного клиента нет. Entity целиком не выдаётся.

| Статус | error.code | Значение |
|---|---|---|
| 400 | `invalid_json` | Тело не является валидным JSON |
| 401 | `invalid_credentials` / `unauthenticated` | Ошибка login / нет сессии |
| 403 | `access_denied` / `csrf_invalid` / `origin_invalid` | Нет роли / CSRF / недоверенный источник |
| 404 | `not_found` | Чужая, удаляемая или отсутствующая целевая компания; запрещённый host/path |
| 405 | `method_not_allowed` | Неверный HTTP-метод |
| 415 | `unsupported_media_type` | Login/выбор компании с неподдерживаемым Content-Type |
| 422 | `validation_failed` | Поля, UUID, пагинация не прошли проверку |
| 429 | `too_many_attempts` | Лимит входа; заголовок Retry-After |
| 500 | `internal_error` | Общее сообщение без внутренних деталей |

Формат: `{"error":{"code":"…","message":"…"}}`. Ошибки валидатора,
authenticator, entry point и access-denied handler должны иметь один контракт.
Logout имеет пустое тело и допускает отсутствие Content-Type: существующий
transport устанавливает этот заголовок только при переданном body. Требования
CSRF и Origin к logout остаются обязательными.
Текущий общий transport превращает любой 401 в `ApiError(401,'unauthenticated')`:
это поведение сохраняется. Login-адаптер показывает «Неверный email или пароль»
для своего 401; глобальный expired-session handler не должен перехватывать login.

Account API документируется Nelmio по PATTERNS §19/25; существующий
`site/assets/api/schema.d.ts` обновляется генератором. Для SPA экспортировать
отдельную account area в `site/packages/api/src/generated/account-schema.d.ts`,
используя уже имеющийся openapi-typescript в контейнере site-frontend. Не тянуть
legacy frontend в apps. Admin endpoints остаются вне общей Nelmio-области по
текущему правилу admin API; их DTO/TS-контракт и JSON проверяются явными тестами.

## 7. Компания и права

1. Нулевое число компаний — успешный вход, `active_company:null`, все права none,
   экран «Нет доступных компаний». Кнопки создания компании в этом этапе нет.
2. Существующий корректный выбор сохраняется. При устаревшем выборе применяется
   поведение `ActiveCompanyService`: доступная компания или пустое состояние.
3. Пикер показывает владельческие и активные членства, без дублей и удаляемых
   компаний; стабильная сортировка name/id. По умолчанию 50 записей на страницу.
   Пустой список на page=1 возвращает 200 с data=[], total=0, pages=1;
   page>1 при пустом списке — 422.
4. Переключение на чужую/удаляемую/несуществующую компанию даёт одинаковый 404,
   не меняя прошлый выбор. Неактивное членство не даёт права переключения.
5. Права — проекция существующего resolver/voter, не новая RBAC-модель.
   Для обычного участника отсутствующий/чужой шаблон прав даёт none.
   Существующее правило владельца и членства ROLE_OWNER сохраняется: write
   во всех модулях независимо от шаблона; системной ROLE_ADMIN это не даёт.
6. При смене компании UI очищает прежний контекст, отменяет запросы; устаревший
   ответ не может вернуть данные прошлого выбора. Пока POST выполняется, новый
   выбор заблокирован. При неоднозначной сетевой ошибке перечитать session.
7. Вкладки одного account-origin разделяют серверную сессию. После фокуса вкладки
   контекст перепроверяется; backend всегда проверяет фактический текущий доступ.
   В этом этапе бизнес-запросов, требующих версионирования выбора, ещё нет.

## 8. Пользовательский интерфейс

Маршруты обоих приложений: `/login`, защищённая `/`, публичная `/about`, 404.
`/login` с действующей разрешённой сессией возвращает на `/`. Возврат после
входа допускается только на внутренний существующий маршрут этого SPA;
внешний URL, `//host`, API-путь или цикл login отвергается.

Форма: email, пароль, «Войти», видимые labels, autocomplete, состояние отправки,
единое сообщение неверных credentials, отдельные CSRF/network/429 состояния.
Показ пароля, регистрация и восстановление доступа не добавляются как фиктивные
действия. Валидатор браузера помогает UX, все проверки повторяются сервером.

```text
account: Ваш Финдир | Компания [доступный выбор] | email | Выйти
         Главная · О приложении
         Раздел находится в разработке

admin:   Ваш Финдир · Администрирование | email | Выйти
         Главная · О приложении
         Раздел находится в разработке
```

Состояния: начальная проверка сессии без показа чужих данных, anonymous,
authenticated, no-company, forbidden, retryable error. Все ошибки содержат
понятное действие (повторить, войти, выйти), без бесконечных редиректов.
На `/about` и 404 не нужны запросы к данным компаний. Session bootstrap запускается
при входе в `/login` или защищённую часть, а не принудительно на публичной странице.

Использовать finance kit и `@vashfindir/ui`. Общие visual-примитивы без auth-логики
живут в UI-пакете; session orchestration и маршруты — в соответствующем app.
Прямой fetch разрешён только transport-пакету. Секретов в Vite-переменных нет.
Клавиатура, focus, aria-live для ошибок, desktop/mobile без overflow обязательны.

## 9. Приёмка

| Набор | Наблюдаемый результат |
|---|---|
| Вход/выход | Реальные тестовые пользователи обоих контуров; reload сохраняет вход, logout убирает его, expired session возвращает login |
| Изоляция | Cookie одного хоста не отправляется другому; вход/выход в account не меняет app/admin; ROLE_COMPANY_OWNER не открывает admin |
| Права | ROLE_ADMIN и ROLE_SUPER_ADMIN входят; обычный пользователь получает отказ; снятие роли прекращает доступ |
| Компания | Owner/member/no-company; пагинация; переключение; чужой UUID; удаляемая компания; отозванное членство; права пересчитаны |
| Защита | CSRF, Origin, session fixation, единые invalid-credentials, rate limit, host/path matrix, запрет HTML вместо JSON |
| Frontend | MSW-сценарии 401/403/422/429/500/network/abort; устаревший ответ; необработанные запросы не уходят в сеть |
| E2E | Playwright в dev, preview и nginx production images; вход через реальный Symfony на изолированной тестовой БД, без подмены auth API |
| Совместимость | Старые login/admin login/company/member/module-access тесты и старый frontend остаются зелёными относительно baseline |
| Выпуск | Backend сначала, SPA после; public HTTPS и unauthenticated JSON acceptance; контейнеры healthy, корректные image SHA |

Production acceptance не создаёт пользователей и не меняет реальные компании.
Полные login/logout сценарии проходят на локальных/CI fixtures, не на production
credentials. Нужда в мутации production или миграции требует отдельного поручения.

## 10. Авторизация будущей реализации и источники

PR #2970 сохранил документы; последующее «приступай» разрешило реализацию
описанного варианта A, включая названные API-routing Traefik/nginx и CI E2E.
Это зафиксировано в checkpoint и сообщено в чате. Публикация auth-кода остаётся
отдельным решением merge + deploy для нового PR; ручных production-мутаций нет.

Технические основания: [Symfony 7.4 Security](https://symfony.com/doc/7.4/security.html)
для firewall/Passport/session authentication; [Symfony CSRF](https://symfony.com/doc/7.4/security/csrf.html)
для session-bound токенов; [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)
для host-only cookies и атрибутов. Конкретное поведение задаёт это ТЗ, а
совместимость определяется тестами текущего проекта.
