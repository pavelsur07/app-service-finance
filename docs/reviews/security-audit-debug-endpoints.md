# Анализ уязвимостей кода
## От самых простых к самым сложным

### Уровень 1: Информационные утечки и Debug-эндпоинты

#### 1.1 Debug-контроллеры с опасными операциями
**Файл:** `/workspace/site/src/MarketplaceAnalytics/Controller/Api/DebugRevenueReconciliationController.php`
**Уязвимость:** Контроллер позволяет выполнять DELETE-операции напрямую в БД
**Строки:** 61-68, 278-294
**Описание:** 
- Эндпоинт `/api/marketplace-analytics/debug/revenue-reconciliation` позволяет удалять дубликаты записей из БД
- При наличии токена пользователя с ролью `ROLE_COMPANY_USER` можно выполнить массовое удаление данных
- SQL-запрос использует параметризацию, но логика удаления может быть эксплуатирована при ошибке валидации

**Рекомендация:** Удалить debug-эндпоинты в production или защитить их дополнительным уровнем аутентификации (API key, IP whitelist)

#### 1.2 Массовое удаление данных
**Файлы:** 
- `DebugReprocessPeriodController.php` (строки 336-362)
- `DebugWipeRawDocumentsController.php` (строка 182)
- `DebugWipeCompanyDataController.php` (строки 209-228)

**Описание:** Несколько контроллеров выполняют массовые DELETE-операции:
```sql
DELETE FROM marketplace_sales WHERE company_id = :companyId AND ...
DELETE FROM marketplace_returns WHERE company_id = :companyId AND ...
DELETE FROM marketplace_costs WHERE company_id = :companyId AND ...
```

**Рекомендация:** Реализовать soft-delete вместо hard-delete, добавить аудит всех операций удаления

### Уровень 2: Потенциальные XSS уязвимости

#### 2.1 Отсутствие явного экранирования вывода
**Проблема:** В коде не найдено явного использования `htmlspecialchars()`, `htmlentities()` для пользовательских данных
**Риск:** Если данные из БД выводятся в шаблонах Twig без авто-экранирования, возможна XSS атака

**Рекомендация:** 
- Проверить все шаблоны Twig на использование `|raw` фильтра
- Убедиться, чтоTwig авто-экранирование включено по умолчанию
- Добавить Content-Security-Policy заголовки

---

### Уровень 3: Небезопасная работа с файлами

#### 3.1 Загрузка и обработка файлов
**Файл:** `/workspace/site/src/Cash/Controller/Import/Bank1CImportController.php`
**Строки:** 150, 249
**Описание:** 
```php
$rawContent = file_get_contents($uploadedFile->getPathname());
$handle = fopen('php://output', 'w');
```

**Риск:** 
- Недостаточная валидация загружаемых файлов
- Возможность загрузки вредоносных файлов

**Рекомендация:**
- Валидировать MIME-type и расширение файлов
- Использовать whitelist разрешённых типов
- Хранить файлы вне web-root директории

#### 3.2 Чтение произвольных файлов из хранилища
**Файл:** `/workspace/site/src/MarketplaceAnalytics/Controller/Api/DebugDownloadRawDocumentController.php`
**Строки:** 80-90
**Описание:** 
```php
$storagePath = $rawData['file_path'];
$stream = $this->storage->readStream($storagePath);
fpassthru($stream);
```

**Риск:** Если `$rawData['file_path']` контролируется пользователем, возможна атака Path Traversal

**Рекомендация:** Валидировать путь к файлу, использовать whitelist разрешённых путей

### Уровень 4: SQL Injection (потенциальные)

#### 4.1 Raw SQL запросы с параметризацией
**Файл:** `DebugRevenueReconciliationController.php` (строки 280-293)
**Описание:** 
```php
DELETE FROM marketplace_returns r
WHERE r.company_id = :companyId AND r.marketplace = 'ozon'
  AND r.return_date >= :periodFrom AND r.return_date <= :periodTo
```

**Статус:** ✅ Безопасно - используются параметризированные запросы

**Но есть риск:** Если в будущем код будет изменён и параметры будут конкатенироваться в SQL, возникнет уязвимость

**Рекомендация:** Использовать QueryBuilder или ORM вместо raw SQL там, где это возможно

### Уровень 5: Криптографические уязвимости

#### 5.1 Хранение API ключей
**Файл:** `/workspace/site/migrations/Version20260803200103.php`
**Описание:** Миграция добавляет шифрование для API ключей:
```php
$this->addSql('ALTER TABLE marketplace_connections ADD api_key_encrypted TEXT DEFAULT NULL');
$this->addSql('ALTER TABLE marketplace_connections ADD api_key_key_version VARCHAR(32) DEFAULT NULL');
```

**Статус:** ✅ Хорошо - используется шифрование

**Но проверить:** 
- Алгоритм шифрования (должен быть AES-256-GCM или аналогичный)
- Управление ключами шифрования (ротация, хранение)
- Старые plaintext ключи должны быть удалены после миграции

#### 5.2 Пароли пользователей
**Файл:** `/workspace/site/migrations/Version20250722151802.php`
**Описание:** 
```php
$this->addSql('CREATE TABLE "user" (... password VARCHAR(255) NOT NULL ...)');
```

**Рекомендация:** 
- Убедиться, что используется bcrypt или argon2id
- Проверить минимальную длину пароля
- Реализовать rate limiting для login endpoint

### Уровень 6: SSRF (Server-Side Request Forgery)

#### 6.1 HTTP запросы к внешним сервисам
**Поиск:** `curl`, `file_get_contents.*http`
**Результат:** Найдено только в контексте S3 storage (безопасно)

**Статус:** ✅ Низкий риск - внешние API вызовы используют фиксированные URL маркетплейсов

**Рекомендация:** 
- Валидировать любые пользовательские URL
- Использовать whitelist доменов
- Блокировать доступ к внутренним IP (127.0.0.1, 10.x.x.x, 192.168.x.x)

### Уровень 7: Deserialization уязвимости

#### 7.1 Использование serialize/unserialize
**Файл:** `/workspace/site/src/Cash/Message/EnqueueAutoRulesForRange.php`
**Описание:** 
```php
public function __unserialize(array $data): void
```

**Статус:** ⚠️ Средний риск - используется безопасный `__unserialize` вместо `unserialize()`

**Рекомендация:** 
- Никогда не использовать `unserialize()` на пользовательских данных
- Предпочитать JSON сериализацию
- Использовать Data Transfer Objects (DTO)

### Уровень 8: Бизнес-логика уязвимости

#### 8.1 Проверка прав доступа
**Файл:** Различные контроллеры
**Описание:** Используются аннотации `#[IsGranted('ROLE_COMPANY_USER')]`

**Риск:** 
- Недостаточно гранулярные роли
- Отсутствие проверки ownership на уровне объектов

**Рекомендация:** 
- Реализовать проверку ownership для каждого ресурса
- Добавить audit log для критических операций
- Использовать policy-based авторизацию

#### 8.2 Race Conditions
**Файл:** `/workspace/site/src/Deals/Service/DealNumberGenerator.php`
**Строки:** 40-43
**Описание:** 
```sql
INSERT INTO deals_deal_sequence (company_id, last_number)
... DO UPDATE SET last_number = deals_deal_sequence.last_number + 1
```

**Статус:** ✅ Хорошо - используется UPSERT для атомарности

**Но проверить:** Другие места с конкурентным доступом к общим ресурсам

### Уровень 9: Complex Attack Vectors

#### 9.1 Цепочка уязвимостей
**Сценарий атаки:**
1. Злоумышленник получает доступ к аккаунту пользователя с ролью `ROLE_COMPANY_USER`
2. Использует debug-эндпоинты для удаления критических данных
3. Эксплуатирует отсутствие аудита для сокрытия следов

**Митигация:**
- Удалить все debug-эндпоинты из production
- Реализовать двухфакторную аутентификацию
- Включить подробное логирование всех операций

#### 9.2 privilege escalation через сериализацию
**Сценарий:** Если сообщение очереди содержит сериализованные данные и обрабатывается с повышенными привилегиями

**Митигация:**
- Использовать только JSON для межсервисной коммуникации
- Валидировать схему сообщений
- Минимизировать привилегии воркеров очередей

## Рекомендации по приоритетам

### Немедленно (Critical):
1. Удалить или заблокировать debug-эндпоинты в production
2. Реализовать аудит всех destructive операций
3. Проверить конфигурацию CORS и CSRF защиты

### Краткосрочно (High):
1. Добавить валидацию загружаемых файлов
2. Реализовать granular access control
3. Включить rate limiting на критических эндпоинтах

### Среднесрочно (Medium):
1. Провести полный аудит криптографических примитивов
2. Реализовать Content-Security-Policy
3. Добавить мониторинг аномальной активности

### Долгосрочно (Low):
1. Регулярные security code review
2. Автоматизированное сканирование уязвимостей (SAST/DAST)
3. Security training для разработчиков
