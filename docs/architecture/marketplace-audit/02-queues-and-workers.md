# Marketplace Stage 0: очереди и workers

Источник истины для маршрутов — `site/config/packages/messenger.yaml:1-105`, для Compose workers — `docker-compose.prod.yml:239-367`. В production здесь **Redis Streams**, не RabbitMQ (`docker-compose.prod.yml:16-20,402-415`). `ingest_fetch` и `ingest_normalize` — отдельные имена transport, но используют **те же DSN, stream и consumer group**, что `async_sync` и `async_pipeline` (`site/config/packages/messenger.yaml:20-32`; `site/vendor/symfony/redis-messenger/Transport/Connection.php:33-46,331-334`). Фабрика Redis не использует `transport_name` для разделения (`site/vendor/symfony/redis-messenger/Transport/RedisTransportFactory.php:24-30`): sync/pipeline workers получают и Ingestion сообщения. Это свойство конфигурации; величина конкуренции и задержки неизвестна.

Отдельные Compose services дают по одному командному процессу на queue; фактические replica count, конкуренция и потребление ресурсов production не проверялись. `restart: always`, healthcheck и `stop_grace_period` заданы в Compose. У `async_ads` grace 120 с при заявленном polling до 10 минут (`docker-compose.prod.yml:343-360`): возможное прерывание/повтор требует теста, само по себе не доказывает потерю. Планировщик — supercronic (`docker-compose.prod.yml:423-432`). Read-only монитор `failed` запускается ежедневно; policy с порогами в `site/src/Shared/Messenger/FailedQueueHealthPolicy.php:30-52` и cron `docker/cron/app.cron:279-285`.

В routing ровно **20 классов семейства Marketplace/Ads/Analytics**: 6 sync, 11 pipeline и 3 ads (`site/config/packages/messenger.yaml:63-69,85-98,103-105`). Ingestion и Inventory идут по тем же физическим ресурсам; Ingestion `RunSyncChunkMessage` и `NormalizeRawRecordMessage` подтверждённо читаются sync/pipeline workers из общих stream/group. За счёт общего `async_pipeline` тяжёлый raw/ads/ingestion job **может** задерживать `CloseMonthStageMessage` и Cash/прочие DB jobs; реальную задержку доказывают queue age и runtime по типу.

Остальной routing на тех же ресурсах: `async_sync` принимает `BankImportMessage`, `CashFileImportMessage`, `SendRegistrationEmailMessage`, `SendPasswordChangedEmailMessage`, Symfony Mailer/Notifier `SendEmailMessage`, `ChatMessage`, `SmsMessage`, два `Sync*InventorySnapshotMessage` и три `Sync*MoySkladMessage`; `async_pipeline` принимает `ImportProductsMessage`, `ApplyAutoRulesForTransaction`, `EnqueueAutoRulesForRange`, `NormalizeInventorySnapshotMessage`. Их handler-ы живут в соответствующих `Cash`, `Company`, `Inventory`, `MoySklad`, `Catalog` и Symfony компонентах (`site/config/packages/messenger.yaml:70-82,93-99`). Для `RunSyncChunkMessage` и `NormalizeRawRecordMessage` см. отдельную строку карты выше (`messenger.yaml:79,100`). Это весь объявленный routing в данном файле; фактическая очередь `failed` может содержать старые классы вне текущего routing.

## Повторы, rolling deploy и совместимость

Отдельные status/unique guards есть у WB/Ozon raw и шагов, но это не общий exactly-once guarantee: статус дня меняется и следующий Message отправляется отдельными действиями (`site/src/Marketplace/MessageHandler/ProcessDayReportHandler.php:58-74`; `site/src/Marketplace/Wildberries/MessageHandler/SyncWbFinancialReportDayHandler.php:273-320`). Нужны тесты на crash между commit и dispatch, повтор и обратный порядок. `ProcessRawDocumentStepMessage::__unserialize()` учитывает старый payload без нового поля (`site/src/Marketplace/Message/ProcessRawDocumentStepMessage.php:28-32`); аналогичный guard есть у inventory import handler (`site/src/Marketplace/MessageHandler/ImportInventoryCostPriceHandler.php:77-80`). Все сообщения не признаны совместимыми автоматически.

Deploy workflow обновляет FPM, затем явно sync/pipeline/ads workers, затем делает общий `compose up`, включающий WB worker (`.github/workflows/deploy.yml:704-720`). Его drain/in-flight поведение и возраст старых `failed`/delayed сообщений исходники не подтверждают. FQCN Message нельзя удалять/переименовывать, пока сериализованные сообщения живут в Redis/failed (`ARCHITECTURE.md:373-375`). Перед сменой routing нужен тест старого payload в новом worker, нового payload в старом worker и drain обеих очередей. Future Financial Core задаёт собственные transport/DLQ и не должен быть продюсером в этой общей pipeline (`docs/financial-core/08-queue-topology.md`).
