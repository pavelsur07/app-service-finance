# Marketplace Stage 0: производительность и Raw Data

**Метод:** статический анализ PHP, Doctrine, миграций и Compose. Нагрузочных тестов, профилей PHP, `EXPLAIN ANALYZE`, размеров таблиц и production-метрик нет. «Факт» ниже означает реально видимый алгоритм/конфигурацию; «гипотеза» — его возможный вклад в задержку 3–4 кабинетов. Приоритет для замеров — не доказанный рейтинг bottleneck.

## Другие подтверждённые операции и смягчения

- Ozon by-day складывает все страницы дня в массив до записи JSON (`site/src/Marketplace/Ozon/Infrastructure/Api/OzonAccrualByDayClient.php:62-107`; `site/src/Marketplace/Ozon/MessageHandler/SyncOzonAccrualByDayHandler.php:180-275`). Есть предел 100 страниц (`OzonAccrualByDayClient.php:39-45`); дополнительный вызов service types на день (`SyncOzonAccrualByDayHandler.php:181-186`). API latency/size неизвестны.
- Ozon realization получает месячный ответ целиком через `toArray`, сохраняет raw и вычисляет hash списка строк (`site/src/Marketplace/Ozon/Infrastructure/Api/OzonRealizationFetcher.php:47-80`; `site/src/Marketplace/Ozon/MessageHandler/SyncOzonRealizationHandler.php:153-174,282-320`). Process action уже имеет bulk SKU lookup и `flush/clear` каждые 250 строк (`site/src/Marketplace/Ozon/Application/Action/ProcessOzonRealizationAction.php:143-169,223-267`).
- Ozon XLSX читает строки через OpenSpout, но собирает их в массив (`site/src/Marketplace/Application/Reconciliation/XlsxReaderService.php:33-86`). Ozon Performance ZIP/CSV также строит целые строки/массивы и сортирует строки (`site/src/Ingestion/Infrastructure/Api/Ozon/OzonPerformanceReportClient.php:487-648`). Это вторичные потоки, влияние на seller finance не установлено.
- Общая legacy обработка sales/returns режет строки чанками 500 и очищает EntityManager (`site/src/Marketplace/Application/ProcessMarketplaceRawDocumentAction.php:349-405`); WB sales заранее загружает listings/existing IDs (`site/src/Marketplace/Wildberries/Application/Processor/WbSalesRawProcessor.php:82-123`). Не следует утверждать, что все legacy handlers работают по одной записи без batching.
- Ozon by-day замена sales/returns выполняется транзакционно с advisory lock; закрытие месяца тоже одной транзакцией с lock (`site/src/Marketplace/Application/ProcessMarketplaceRawDocumentAction.php:215-247`; `site/src/Marketplace/Application/CloseMonthStageAction.php:66-101`). Это защита целостности, но может удерживать locks долго на большом дне; нужны lock wait и transaction duration.

## БД и узкие места по ресурсам

`marketplace_raw_documents.raw_data` — Doctrine JSON (`site/src/Marketplace/Entity/MarketplaceRawDocument.php:65-66`); в Ingestion raw хранится через `storage_path`, `hash`, `byte_size`, статус и отдельное gzip/NDJSON хранилище (`site/migrations/Version20260615160000.php:26-28`; `site/src/Ingestion/Infrastructure/Storage/RawNdjsonCodec.php:14-53`). У Ingestion есть unique `(company_id,source,resource_type,external_id,hash)`; latest lookup фильтрует внешний ID и сортирует по времени (`site/src/Ingestion/Repository/IngestRawRecordRepository.php:56-75`). Его индекс может оказаться достаточным через unique-prefix; менять его без плана `EXPLAIN ANALYZE` нельзя.

Потенциальные ресурсы: PHP CPU (hash/sort/JSON/normalizers), RAM (полный ответ и копии массивов), PostgreSQL I/O/WAL (перезапись raw JSON и per-row SELECT/UPSERT), Redis queue age/consumer count, внешний API rate limit. **RabbitMQ отсутствует в конфигурации**, поэтому его capacity и DLQ здесь не измеряются (`site/config/packages/messenger.yaml:5-50`; `docker-compose.prod.yml:16-20`).

## Минимальный план измерений

1. Получить 7–14 дней p50/p95/p99 по `provider × resource × stage × company` для rows/bytes, fetch, decode, append, store, normalize, close; ограничить cardinality и не писать payload.
2. Коррелировать Messenger enqueue/start/end/retry, Redis pending/oldest и worker CPU/RSS/OOM с периодами 3–4 кабинетов; отдельно sync/WB/pipeline/Ads/Ingestion.
3. Снять `pg_stat_statements`, WAL, TOAST/table/index bytes, lock waits/deadlocks и планы top queries на безопасной копии/штатном read-only доступе. Избегать `EXPLAIN ANALYZE` на тяжёлых production-запросах без отдельной оценки.
4. На тестовых обезличенных или синтетических страницах проверить профили WB append, WB canonical sort, NDJSON decode и per-row SQL. Зафиксировать суммы/hash до/после любой будущей оптимизации.
