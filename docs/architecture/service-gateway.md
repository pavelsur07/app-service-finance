# Шлюз и работа с сервисами

Правило для всех задач, где Symfony, фронт (клиентский UI, `admin.vashfindir.ru`)
и сервисы `services/` обмениваются данными. Решение Владельца 2026-10-18.
Правила самих сервисов (границы, хранение, pull-модель) — `services/AGENTS.md`;
этот документ — про то, **как с сервисами говорит остальная система**.

## 1. Главное правило

**Symfony — единственный шлюз к сервисам.** Фронт ходит только в Symfony;
Symfony обращается к сервисам по внутренней сети.

```
браузер → app/admin.vashfindir.ru → Symfony (шлюз, модуль ServiceGateway)
                                      ├─ своя БД и витрины
                                      └─ сервисы services/* по внутренней сети
```

| Слой | Делает | Не делает |
|---|---|---|
| Фронт | рисует ответы API Symfony | не знает адресов и токенов сервисов, не ходит в них |
| Шлюз (Symfony) | реестр сервисов, клиенты, права, таймауты, кеш, витрины, единые ошибки, аудит | не дублирует бизнес-логику сервисов |
| Сервис | свою работу и стандартные internal-endpoint'ы | не ходит в БД Symfony, не отдаёт UI, не публикуется наружу |

## 2. Обязательные правила

1. **Сервис не публикуется наружу.** Только внутренняя docker-сеть, без
   traefik-роутера. Исключение — только через `AGENTS.md` §3.3.
2. **Реестр сервисов — один источник правды** (`name`, внутренний `base_url`,
   ссылка на env с токеном, `capabilities`, версии контрактов, таймауты,
   `enabled`). Адрес и токен сервиса нигде, кроме реестра и env, не
   встречаются.
3. **Стандартный набор endpoint'ов у каждого сервиса:**

   | Endpoint | Назначение |
   |---|---|
   | `GET /health` | процесс жив |
   | `GET /ready` | готов: БД, хранилище, зависимости |
   | `GET /internal/status` | единая схема: версия, ошибки, очередь, последние успехи |
   | `GET /internal/coverage` | единая схема покрытия: компания, источник, тип данных, период, статус |
   | `POST /internal/<command>` | команда: `Idempotency-Key`, ответ 202 + id |
   | `GET /internal/<command>/{id}` | статус команды |

4. **Контракты — в `services/_contracts/<имя>/v<N>`.** Опубликованная версия
   неизменна; изменение — новая версия; шлюз принимает обе на время
   перехода. Ответ, не прошедший проверку схемы, — ошибка
   `contract_violation`, а не тихо принятые данные.
5. **Каждый вызов сервиса — с таймаутами** (connect и request). Повтор — только
   для безопасных запросов (GET и команды с `Idempotency-Key`), backoff +
   jitter. После серии сбоев — circuit breaker: сервис «недоступен» на время,
   шлюз отвечает сразу, не долбит упавший сервис.
6. **Чтение для экранов — через витрины в БД Symfony**, которые фоном
   (Messenger/cron) обновляются из сервисов. Экран не ждёт сервис и
   открывается при его недоступности; ответ несёт «данные на HH:MM» и
   признак `stale`. Синхронный вызов сервиса из запроса пользователя —
   только для детализации одной записи, с коротким таймаутом и кешем.
7. **Команды — асинхронно и идемпотентно:** права и аудит → сообщение
   Messenger → `POST /internal/<command>` с `Idempotency-Key` → UI опрашивает
   статус. Повтор нажатия или ретрай не создают дублей; при недоступном
   сервисе команда ждёт в очереди.
8. **Единые ошибки наружу** — формат `CLAUDE.md` «Обработка ошибок»
   (`{"error":{"code","message"}}`); коды шлюза: `service_unavailable`,
   `service_timeout`, `contract_violation`. Фронт не знает, какой сервис упал.
9. **Токен — свой у каждого сервиса и направления** («Symfony → сервис» и
   «сервис → Symfony» — разные). Значения — только GitHub secrets / env;
   ротация — одним деплоем. Сервис доверяет только шлюзу: пользовательские
   сессии в сервис не передаются.
10. **Права проверяет шлюз на сервере**, не только UI. Все команды админа —
    в аудит-лог: кто, что, когда, ответ сервиса.
11. **Сквозной `trace_id`:** шлюз генерирует и передаёт заголовком, сервис
    пишет его в логи и GlitchTip.
12. **Наблюдаемость сервиса:** свой проект GlitchTip (только ERROR), сигналы об
    аномалиях (как шторм 429 у ozon-fetcher), строка на экране «Сервисы»
    админки.

## 3. Подключение нового сервиса — чек-лист

- [ ] контракты в `services/_contracts`, стандартные endpoint'ы (§2.3)
- [ ] запись в реестре; токены (оба направления) — в GitHub secrets
- [ ] клиент в `ServiceGateway` + тест контракта на фикстурах
- [ ] compose-профиль, переключатель `<NAME>_ENABLED`, БД и роль создаёт деплой,
      гейты в CI по фильтру путей (образец — ozon-fetcher, `docs/maintenance/ozon-fetcher-prod.md`)
- [ ] свой проект GlitchTip, сигналы аномалий
- [ ] поэтапное включение (allowlist), откат переключателем

## 4. Текущее состояние против целевого

Документ описывает целевую схему. На 2026-10-18 по репозиторию:

| Целевое | Факт |
|---|---|
| модуль `ServiceGateway`, реестр сервисов | нет; единственный сервис (ozon-fetcher) связан напрямую: Symfony отдаёт `/internal/marketplace-connections`, сервис забирает |
| `/internal/status`, `/internal/coverage` | нет; у ozon-fetcher есть `/internal/fetch-status` (своя схема) |
| витрина `data_coverage`, экран «Сервисы» | нет |
| circuit breaker, `trace_id` между Symfony и сервисом | нет |
| токен на направление | один общий `INTERNAL_AUTH_TOKEN` для обоих направлений ozon-fetcher |
| сервис только во внутренней сети, свой GlitchTip, переключатель, bootstrap БД в деплое | **есть** (ozon-fetcher, PR #2706–#2713) |

Не выдавать целевое за существующее. Новый код со сервисами пишется по §2;
существующий ozon-fetcher приводится к нему отдельной задачей.

## 5. Когда выносить шлюз из Symfony

Отдельный шлюз (Traefik middleware, Kong, Envoy) — когда выполнено хотя бы
одно:
- фронт должен ходить в сервисы напрямую в реальном времени (стриминг,
  WebSocket, большие файлы);
- нагрузка шлюза мешает основному приложению;
- сервисов 5 и больше, и им нужна общая авторизация, rate-limit и журнал
  запросов вне PHP.

Решение о выносе — Владельца (`AGENTS.md` §3.3).
