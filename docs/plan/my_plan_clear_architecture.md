# Чистая архитектура в VashFinDir: анализ и план

Дата: 2026-10-08. Замеры сняты с `master` @ `cc020e22`.

## 1. Что такое чистая архитектура

Подход Роберта Мартина (Uncle Bob; статья 2012 года, книга 2017 года),
обобщающий гексагональную архитектуру (Ports & Adapters), Onion Architecture
и похожие идеи. Цель: бизнес-логика не зависит от фреймворка, базы данных, UI
и внешних сервисов.

### Правило зависимостей

```
┌─────────────────────────────────────────────┐
│  Frameworks & Drivers (Symfony, Doctrine,   │
│  PostgreSQL, HTTP-клиенты, UI)              │
│  ┌───────────────────────────────────────┐  │
│  │  Interface Adapters (контроллеры,     │  │
│  │  репозитории-реализации, презентеры)  │  │
│  │  ┌─────────────────────────────────┐  │  │
│  │  │  Use Cases (сценарии            │  │  │
│  │  │  приложения)                    │  │  │
│  │  │  ┌───────────────────────────┐  │  │  │
│  │  │  │  Entities (бизнес-правила)│  │  │  │
│  │  │  └───────────────────────────┘  │  │  │
│  │  └─────────────────────────────────┘  │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
          зависимости → только внутрь
```

Код внутреннего круга ничего не знает о внешних: не импортирует их классы,
не знает их имён и форматов данных.

### Слои

1. **Entities (домен).** Бизнес-правила и инварианты, которые существовали бы
   и без программы. Например: «сумма операции не может быть отрицательной».
2. **Use Cases (прикладной слой).** Сценарии вроде «импортировать выписку» или
   «пересчитать баланс». Управляют сущностями и задают нужные им интерфейсы
   (порты), например `TransactionRepositoryInterface`.
3. **Interface Adapters.** Переводят данные между форматом use case и внешним
   миром: контроллер разбирает HTTP-запрос в DTO, репозиторий реализует порт
   через Doctrine.
4. **Frameworks & Drivers.** Фреймворк, ORM, БД, очереди, внешние API —
   заменяемые «детали».

### Как внутренний слой вызывает внешний

Через инверсию зависимостей (DIP). Use case объявляет интерфейс, внешний слой
его реализует. Во время работы управление идёт наружу (use case обращается к
БД), но зависимость в исходном коде направлена внутрь: адаптер зависит от
интерфейса use case.

### Что это даёт

- **Тестируемость.** Бизнес-логика тестируется без БД и HTTP, на подменах портов.
- **Независимость от фреймворка.** Обновление Symfony или замена ORM не
  затрагивает правила.
- **Отложенные решения.** Выбор БД, очереди или внешнего API можно отложить.
- **Читаемость.** По структуре видно, что делает система, а не на чём она
  написана («screaming architecture»).

### Цена

- Больше кода: интерфейсы, DTO, мапперы.
- Для простого CRUD часто избыточно.
- Строгое разделение домена и ORM в PHP/Doctrine обычно смягчают: Entity
  остаётся Doctrine-сущностью, но бизнес-правила в ней только в виде
  инвариантов.

## 2. Как это устроено в проекте сейчас

Проект использует прагматичный вариант этих идей, а не каноническую схему:

| Идея чистой архитектуры | В проекте |
|---|---|
| Use Case | `Action`: `final`, `__invoke`, не знает о `Request`/`Response`, `flush()` только здесь |
| Interface Adapter (вход) | `Controller`: только HTTP in/out, без бизнес-логики |
| Граница модуля / порт | `Facade`: единственная точка входа между модулями, контракт через `Application/DTO` |
| Entity с инвариантами | Entity: только инварианты в конструкторе, без бизнес-логики |
| Правило зависимостей | Гейт `ModuleBoundaryRules`: нельзя импортировать чужие `Service/` и `Repository/`, нельзя ставить `#[ManyToOne]` на чужие Entity |

Главное отличие от канона: Doctrine-сущности и репозитории не отделены от
домена интерфейсами. Это осознанный компромисс ради меньшего объёма кода;
изоляция держится на уровне модулей, а не слоёв.

Основа уже хорошая: legacy-зона (`src/Entity`, `src/Service`,
`src/Repository`, `src/Controller`) пуста, модули с Facade есть, границы
проверяет `site/tests/Architecture/ModuleBoundaryRules.php`. Нужна не новая
архитектура, а точечные улучшения с машинной защитой от деградации.

## 4. Предложения (по убыванию пользы)

Принцип исполнения: не отдельный «большой рефакторинг», а правило «оставь код
чище» в задачах, которые и так трогают файл, плюс гейты с baseline, чтобы
новые нарушения не появлялись.

### 4.1. Бизнес-логика из контроллеров в Action — самый большой эффект

Крупнейшие контроллеры:

| Контроллер | Строк |
|---|---|
| `Telegram/Controller/TelegramWebhookController.php` | 1413 (30 методов) |
| `Marketplace/Controller/MarketplaceController.php` | 1048 |
| `Finance/Controller/PlReportPreviewController.php` | 745 |
| `Deals/Controller/DealController.php` | 708 |
| `Cash/Controller/Transaction/CashTransactionAutoRuleController.php` | 637 |

В 88 из 212 контроллеров напрямую используется `EntityManager` или
репозиторий; в 18 есть `persist()`/`flush()`, хотя по правилам `flush()`
допустим только в Action.

`TelegramWebhookController` по сути — роутер команд бота. Если превратить его
в диспетчер плюс отдельный Handler на каждую команду, его станет возможно
тестировать.

- [ ] PHPStan-правило: `persist()`/`flush()` в `*/Controller` запрещены
  (по образцу `RepositoryCompanyScopeRule`), baseline на текущие 18 файлов.
- [ ] `TelegramWebhookController` → диспетчер + Handler на каждую команду бота;
  тесты на Handler-ы.
- [ ] Остальные контроллеры из таблицы — выносить сценарий в Action при
  ближайшей задаче, затрагивающей файл.

### 4.2. Утечка чужих Entity между модулями

117 файлов импортируют Entity другого модуля:

- `Company\Entity` — 285 импортов. `Company`/`User` фактически общее ядро
  (shared kernel), это нормально.
- `Finance\Entity` — 28, `Cash\Entity` — 19. Это настоящая связность:
  например, Telegram-контроллер работает с `Cash\Entity\MoneyAccount` напрямую.

Гейт сейчас Entity не запрещает: по комментарию в
`ModuleBoundaryRules.php:46` Facade-ы возвращают Entity, а перевод на DTO
стоит около 230 записей.

- [ ] Зафиксировать в `ARCHITECTURE.md`: `Company`/`User` — shared kernel,
  импорт `Company\Entity` разрешён.
- [ ] Новые Facade-методы возвращают DTO/ID, не Entity.
- [ ] Постепенно перевести Facade-методы `Cash` и `Finance` на DTO
  (47 импортов).
- [ ] Когда счётчик снизится — включить запрет чужих Entity (кроме Company)
  в `ModuleBoundaryRules` с baseline.

### 4.3. Порты для внешних API

Самый большой файл проекта —
`MarketplaceAds/Infrastructure/Api/Ozon/OzonAdClient.php` (2356 строк).
API Ozon/WB меняются часто (пример — снятие `/v3/finance/transaction/list`
09.09.2026). Интерфейсов-портов в Domain/Application всего 21 — приём почти
не используется.

Use case зависит от интерфейса (например, `AdStatisticsProvider`),
возвращающего доменные DTO; Ozon-клиент реализует его и переводит формат Ozon
в доменный. Тогда смена версии API меняет только адаптер, Action тестируются
на фейке без HTTP-моков, а огромный клиент естественно делится на адаптеры.

- [ ] Ввести порт для статистики рекламы и адаптер Ozon за ним.
- [ ] Разделить `OzonAdClient` на адаптеры по группам методов.
- [ ] Action тестировать на фейк-реализации порта.

Порты — только для внешних систем, не для каждого репозитория.

### 4.4. Чистый домен для денежных расчётов

`Domain/` почти пуст: в Cash, самом денежном модуле, 1 файл на 200. Правила
расчётов лежат в `Cash/Service` (35 файлов) и размазаны по Builder/Action
Marketplace: `WbRawFinancialReportBuilder` (1160 строк),
`RefreshOrderStatusesAction` (1340 строк).

Для финансового продукта чистые Policy с unit-тестами на все ветки — лучшая
защита от регрессий вроде недавнего P0 с балансами в Cash; такие тесты
работают без БД за миллисекунды.

- [ ] Выносить формулы и классификацию (пересчёт балансов, разнесение затрат
  WB/Ozon, P&L-формулы) в Domain Policy без Doctrine/HTTP, с unit-тестами на
  все ветки.
- [ ] Низкий приоритет: убрать `Doctrine\ORM\Mapping` из
  `Shared/Domain/ValueObject/Money.php` (маппинг вынести в конфиг), чтобы
  Value Object не зависел от ORM.

### 4.5. Старые модули — к общему шаблону

Deals, Loan, Ai, Billing, Telegram устроены по-старому: `Service/` +
`Repository/`, без Facade. Тесты: Deals 5, Loan 0, Ai 1.

- [ ] Не рефакторить ради рефакторинга. При задаче по модулю — сначала Facade
  и тесты на затронутый сценарий, потом изменение.

## 5. Что не делать

- Отдельные доменные модели поверх Doctrine-Entity с маппингом туда-обратно:
  удвоит код без выгоды на текущем этапе продукта.
- Интерфейс на каждый репозиторий: порты нужны только для внешних систем.
- Отдельный проект «большого рефакторинга»: вместо него — «оставь код чище»
  плюс гейты с baseline (так уже ведётся PHPStan-baseline).

## 6. Порядок старта

1. PHPStan-правило против `persist`/`flush` в контроллерах (п. 4.1) —
   небольшая задача, сразу останавливает деградацию.
2. Разбор `TelegramWebhookController` на Handler-ы (п. 4.1) — самый большой и
   наименее тестированный файл.

## 7. Метрики прогресса

Пересчитывать при закрытии каждого пункта:

- контроллеров с `persist`/`flush` — цель 0;
- контроллеров > 500 строк — цель 0;
- импортов `Finance\Entity`/`Cash\Entity` из чужих модулей — цель 0;
- записей в PHPStan baseline — только вниз.
