# Техническое задание: выгрузка «строками» из сервиса для сверки ПЛАН-ФАКТ

**Проект:** VashFinDir (репозиторий `pavelsur07/app-service-finance`), модуль Marketplace
**Заказчик данных:** Лазарева — книга «ФМ», лист «РнП-(ПФ)»
**Версия ТЗ:** 1.1 (сверено с кодом репозитория 20.10.2026)
**Версия формата выгрузки:** 1.0

**Границы ТЗ.** Только выгрузка из сервиса. Загрузка в книгу, формулы «РнП-(ПФ)», плановые формулы и лист данных книги в ТЗ не входят и разрабатываются отдельно. Формат выгрузки при этом сделан удобным для машинной загрузки (плоская таблица, стабильные ключи).

---

## 1. Цель

Раз в неделю (и за любой другой период) получать из сервиса файл, в котором фактические данные предпросмотра ОПиУ по тегам лежат **строками** (одна строка — одна сумма), а не широкой таблицей «статья × колонки». Такой файл можно без разбора раскладывать по плану-факту: по периоду, каналу, тегу и статье.

## 2. Что уже есть в сервисе (основание)

| Что | Где |
|---|---|
| Сборка отчёта (только чтение, без `flush()`) | `Marketplace\Application\Action\BuildMarketplacePlPreviewAction(BuildMarketplacePlPreviewCommand(companyId, from, to, ?marketplace, ?tagIds))` → `MarketplacePlPreviewReport` |
| Фильтр запроса | `Marketplace\Application\PlPreview\PlPreviewFilter::fromQuery()`: `dateFrom`, `dateTo`, `marketplace`, `tags[]` / `tags_set=1`, `empty=1` |
| Текущая выгрузка (широкая) | `GET /marketplace/pl-preview/xlsx`, `PlPreviewXlsxController`, `Infrastructure\Export\PlPreviewXlsxExporter`; листы «ОПиУ по тегам», «Не попадёт в ОПиУ», «Исключено», «Сверка»; файл `pl-preview_<from>_<to>.xlsx` |
| Строка дерева ОПиУ | `Finance\Application\DTO\PlPreviewRow(id, ?code, name, level, type: PLCategoryType, format: PLValueFormat, values[columnKey])` |
| Колонки | `MarketplacePlPreviewColumn(key, label, kind: PlPreviewColumnKind)`: `tag` (`tag:<id>`), `common` («Общие / без тега»), `total` («Итого») |
| Покрытие и сверка | `costCoverage`, `costTotal`, `costReconciliationDelta`, `salesCoverage`, `unplaced`, `adReconciliation`, `warnings` в `MarketplacePlPreviewReport` |
| Каналы | `MarketplaceType`: `wildberries`, `ozon`, `yandex_market`, `sber_megamarket` (Lamoda в сервисе отсутствует) |
| Ограничения периода | `from ≤ to`, не длиннее 366 дней, иначе `MarketplacePlPreviewPeriodException`; даты по умолчанию — по Europe/Moscow |

### Важные свойства данных (они определяют формат)

1. **Строки отчёта — это дерево ОПиУ компании**, а не фиксированный список: набор и названия статей задаёт компания, `code` статьи может быть пустым. Поэтому стабильный ключ строки — `pl_code`, а при его отсутствии — `pl_category_id`.
2. **Теги — это теги листингов компании** (в вашем случае Off, Regular, Sale, Навол-скл-1 и т. д.), набор динамический. «Навол-скл-1» — обычный тег компании, не особая колонка. «Общие / без тега» — отдельная колонка (`common`): факты без листинга и листинги без единого тега.
3. **Теги пересекаются:** листинг с несколькими тегами входит полной суммой в каждый из них (`tagsOverlap`). Сумма колонок тегов + «Общие» может не равняться «Итого». Итог берётся только из колонки `total`.
4. **Реклама:** в колонках тегов — по рекламной статистике, в «Итого» — по учёту; остаток «учёт − статистика по листингам» попадает в «Общие». Расхождение учёта и статистики по WB — штатное свойство данных, отражённое в `adReconciliation`, а не ошибка выгрузки.
5. **Берутся все нормализованные строки периода**, проведённые в ОПиУ или нет. Понятия «период закрыт» в сервисе нет.
6. **Отнесение к периоду:** продажи — `sale_date`, возвраты — `return_date`, затраты — `cost_date`; «Реализация» Ozon входит в отчёт только если её документ целиком лежит внутри периода, иначе в `warnings` появляется предупреждение, а сумма в отчёт не попадает.
7. **СПП:** «Выручка без СПП» и «Выручка с СПП» определяются правилами маппинга продаж (`config/marketplace/default_sale_mapping.yaml`, `pl_code` `REV_NOT_SPP`, `REV_SPP_SALES`, `REV_RETURNS`, `REV_SPP_RETURNS`; источник суммы — `AmountSource`). Для Ozon `sale_gross` равен `total_revenue`.

## 3. Решение

Добавить **вторую выгрузку** рядом с существующей, не меняя её. Расчёт не дублируется: новая выгрузка вызывает `BuildMarketplacePlPreviewAction` (иначе возникнет расхождение с экраном и широкой выгрузкой) и только перекладывает результат в строки.

### 3.1. Состав изменений (слои по `CLAUDE.md`)

| Слой | Класс | Назначение |
|---|---|---|
| Controller | `Marketplace\Controller\PlPreviewRowsXlsxController` | Один action, `__invoke`, `GET /marketplace/pl-preview/rows-xlsx`, имя маршрута `marketplace_pl_preview_rows_xlsx`, `#[IsGranted(ModuleAccess::MARKETPLACE_READ)]`. Компания — через `ActiveCompanyService` до обращения к данным. Только HTTP in/out |
| Action | `Marketplace\Application\Action\BuildPlPreviewRowsExportAction` | Определяет каналы, вызывает `BuildMarketplacePlPreviewAction` по каждому каналу, возвращает `list<MarketplacePlPreviewReport>` (без `Request`/`Response`, без `flush()`) |
| Exporter | `Marketplace\Infrastructure\Export\PlPreviewRowsXlsxExporter` | Пишет xlsx (OpenSpout, как у `PlPreviewXlsxExporter`) |
| Docs | `ARCHITECTURE.md` | Раздел «Marketplace: предпросмотр ОПиУ по тегам» (текущее состояние) + строка в Changelog |

Параметры запроса — те же, что у `PlPreviewFilter` (`dateFrom`, `dateTo`, `marketplace`, `tags[]`, `tags_set`). Параметр `empty` игнорируется: выгрузка строками всегда содержит полную сетку (п. 4.2).

Ошибка периода — как в существующей выгрузке: flash `danger` и redirect на вкладку `marketplace_pl_preview_index` с тем же фильтром.

Имя файла: `pl-rows_<YYYY-MM-DD>_<YYYY-MM-DD>.xlsx`. Заголовки ответа — как у существующей выгрузки (`Content-Type` xlsx, `Cache-Control: no-store`).

### 3.2. Каналы

- Если параметр `marketplace` задан — выгружается только этот канал.
- Если не задан — выгружается каждый канал, по которому у компании есть SELLER-подключение и/или данные за период (способ определения — через репозиторий подключений, детали при реализации). Строки каналов не суммируются в файле: колонка `marketplace` всегда содержит конкретный канал, строк `all` в листе «Данные» нет.
- Контроль суммы каналов против общего расчёта (`marketplace = null`) — в листе «Паспорт» (п. 4.3).

## 4. Формат файла

Файл `.xlsx`, пять листов в фиксированном порядке: `Данные`, `Паспорт`, `Покрытие`, `Реклама`, `Предупреждения`.

Общие правила:
- Шапка в первой строке каждого листа; нет объединённых ячеек, пустых строк, итогов и подитогов.
- Текстовые значения (названия тегов, статей, категорий) — всегда текстовые ячейки (`StringCell`), как в `PlPreviewXlsxExporter::text()`: строка, начинающаяся с «=», не должна стать формулой.
- Числа — числовые ячейки; даты — ячейки даты (`yyyy-mm-dd`); момент выгрузки — дата-время.
- Названия статей без неразрывных пробелов-отступов (отступ передаёт `row_level`).
- Имена полей — латиницей в `snake_case` (стабильный контракт), русские подписи — в «Паспорте».

### 4.1. Лист «Данные»

Гранулярность: **канал × колонка (тег / общие / итого) × строка дерева ОПиУ**. Выводятся все строки дерева (`MarketplacePlPreviewReport::$rows`, независимо от `empty`), в том числе нулевые, — отсутствие строки означает ошибку выгрузки, а не нулевую сумму.

| № | Поле | Тип | Источник / правило |
|---|---|---|---|
| 1 | `period_from` | дата | `report->from` |
| 2 | `period_to` | дата | `report->to` (включительно) |
| 3 | `period_key` | текст | `YYYY-MM-DD_YYYY-MM-DD`, например `2026-10-12_2026-10-18` |
| 4 | `iso_week` | текст | `YYYY-Www`, заполняется только если период — ровно понедельник–воскресенье одной ISO-недели; иначе пусто |
| 5 | `marketplace` | текст | `MarketplaceType::value`: `ozon`, `wildberries`, … |
| 6 | `column_kind` | текст | `tag` / `common` / `total` (`PlPreviewColumnKind`) |
| 7 | `tag_id` | текст | UUID тега для `tag`, иначе пусто |
| 8 | `tag_name` | текст | Название тега; для `common` — «Общие / без тега»; для `total` — «Итого» |
| 9 | `pl_category_id` | текст | `PlPreviewRow::$id` |
| 10 | `pl_code` | текст | `PlPreviewRow::$code`, может быть пусто |
| 11 | `row_order` | целое | Порядковый номер строки в дереве (с 1) |
| 12 | `row_level` | целое | `PlPreviewRow::$level` |
| 13 | `row_name` | текст | `PlPreviewRow::$name` |
| 14 | `category_type` | текст | `PLCategoryType::value` как есть (например `LEAF_INPUT`, `SUBTOTAL`) |
| 15 | `value_format` | текст | `PLValueFormat`: `MONEY`, `QTY`, `PERCENT`, `RATIO` |
| 16 | `value` | число | `PlPreviewRow::$values[column_key]`; `MONEY`/`QTY` — до 2 знаков; `PERCENT` и `RATIO` — доля как есть (0,2773 = 27,73%), без округления до процентов |
| 17 | `generated_at` | дата-время | Момент выгрузки, Europe/Moscow |
| 18 | `format_ver` | текст | `1.0` |

**Знак `value`** — как в отчёте (знак строки документа ОПиУ после `is_negative`): расходы отрицательные, доходы положительные. Своих перекодировок знака выгрузка не делает.

**Ключ строки:** `period_key + marketplace + column_kind + tag_id + pl_category_id`. Дубли недопустимы.

**Порядок строк** детерминирован: канал (по значению enum) → колонки в порядке отчёта (теги, затем `common`, затем `total`) → `row_order`.

**Что брать потребителю.** Для первичных сумм — строки `category_type = LEAF_INPUT` и `value_format = MONEY|QTY`; остальные строки (подытоги, проценты, KPI) нужны для контроля, их можно пересчитать в книге. Для итогов по периоду и каналу использовать только `column_kind = total`.

### 4.2. Лист «Паспорт» (ключ — значение, одна пара на строку)

| Ключ | Значение |
|---|---|
| `format_ver`, `generated_at` | как в «Данные» |
| `period_from`, `period_to`, `period_key`, `iso_week` | как в «Данные» |
| `marketplaces` | список каналов через `;` |
| `tags` | список `<tag_id>=<tag_name>` через `;` (тот набор, что в файле) |
| `tags_overlap` | `1`, если `report->tagsOverlap` у какого-либо канала, иначе `0` |
| `rows_count` | число строк листа «Данные», а также `rows_count_<marketplace>` по каналам |
| `cost_total_<marketplace>` | `report->costTotal` |
| `cost_mapped_<marketplace>`, `cost_excluded_<marketplace>`, `cost_unmapped_<marketplace>` | `costTotalsByStatus()` |
| `cost_delta_<marketplace>` | `costReconciliationDelta` (ожидается 0) |
| `check_channels_vs_all_<pl_code или category_id>` | Для строк `total`: сумма каналов минус значение общего расчёта (`marketplace = null`). Предупреждающий контроль, не блокирующий: направление статьи в расчёте определяется по колонке «Итого» (`natureBaseColumn`), поэтому в редких случаях знак по каналу и по всем каналам может различаться |

### 4.3. Лист «Покрытие»

То, что не попало или может не попасть в ОПиУ (плоский вид листов «Не попадёт в ОПиУ», «Исключено»).

| Поле | Тип | Что |
|---|---|---|
| `period_key` | текст | как выше |
| `marketplace` | текст | канал |
| `section` | текст | `cost` (затраты, `costCoverage`), `sales` (`salesCoverage`), `unplaced` (`report->unplaced`) |
| `status` | текст | `cost`: `mapped` / `excluded` / `unmapped` (`PlPreviewCostStatus`); `sales`: `PlPreviewSalesKind` и признак правила; `unplaced`: `PlPreviewUnplacedReason` |
| `category_code` | текст | `costCategoryCode` или код статьи |
| `category_name` | текст | название категории / статьи |
| `rows_count` | целое | число строк (для `unplaced` пусто) |
| `amount` | число | `netAmount` / `amount` / сумма из `values['total']` |
| `has_active_mapping` | 0/1 | только для `sales` |

### 4.4. Лист «Реклама»

Плоский вид блока «Реклама: учёт и статистика» (`adReconciliation`).

| Поле | Тип |
|---|---|
| `period_key` | текст |
| `marketplace` | текст |
| `ads_ledger` | число (`ledger`, учёт) |
| `ads_statistics` | число (`statistics`) |
| `ads_on_listings` | число (`onListings`, на товарах) |
| `ads_unallocated` | число (`unallocated`, без товара) |
| `ads_difference` | число (`difference`, учёт − статистика) |

### 4.5. Лист «Предупреждения»

Поля: `period_key`, `marketplace`, `text` — по строке на каждое предупреждение `report->warnings` (ошибки формул дерева, неполная «Реализация» Ozon, нет проекта у подключения). Пустой лист (только шапка) допустим.

## 5. Правила и ограничения

1. **Период** — любые даты, `from ≤ to`, не более 366 дней. Недельная выгрузка запрашивается датами понедельник–воскресенье. Неделю на границе месяцев потребитель запрашивает двумя вызовами (до последнего дня месяца и с первого дня следующего).
2. **Файл — полный снимок периода.** При повторной выгрузке цифры могут измениться (корректировки площадок, перемаппинг). Потребитель заменяет все строки по ключу `period_key + marketplace` целиком. Признака «закрыто / предварительно» сервис не формирует; его назначает потребитель.
3. **Реализация Ozon.** Недельные периоды режут помесячный документ «Реализация» — он в недельную выгрузку не попадает, а в «Предупреждениях» появляется соответствующая запись. Потребитель обязан учитывать это при сверке с месячным планом (см. вопрос 2 в п. 8).
4. **Расчёт один:** Action вызывается без изменений; выгрузка не вводит своих формул сумм и знаков.
5. **Безопасность:** доступ по `ROLE_USER` + `ModuleAccess::MARKETPLACE_READ`; данные только активной компании (`getActiveCompany()` до запросов); `companyId` в файл не пишется; названия пользовательских тегов и статей пишутся текстом.
6. **Нагрузка:** число вызовов Action равно числу каналов (+1 для контроля «все каналы»); период ≤ 366 дней. Размер файла: ~ 40 строк дерева × (число тегов + 2) × число каналов на период.
7. Нет записи в БД, отметок у строк и документов ОПиУ.

## 6. Требования к реализации (по `CLAUDE.md` / `ARCHITECTURE.md`)

- `declare(strict_types=1)`; Controller, Action, Exporter — `final`; DTO — `final readonly`; constructor injection.
- Нет `flush()` и бизнес-логики в Controller; межмодульные вызовы только через Facade (`FinanceFacade` уже используется внутри `BuildMarketplacePlPreviewAction`).
- Тесты в том же этапе:
  - Action: happy-path (несколько каналов) и негативный (период `from > to` / длиннее 366 дней → `MarketplacePlPreviewPeriodException`);
  - Exporter: читает сгенерированный xlsx — заголовки, типы ячеек (числа числами, названия текстом, строка «=…» не формула), полнота сетки, детерминированный порядок, отсутствие дублей ключа;
  - Controller (functional, по образцу `PlPreviewControllerTest`, фикстура `PlPreviewFixture`): доступ, чужая компания не видна, ошибка периода → redirect.
- `ARCHITECTURE.md`: описать маршрут, Action и Exporter в разделе «Marketplace: предпросмотр ОПиУ по тегам»; строка в Changelog.
- Гейты: `make site-stan`, `make site-cs-check`, `make site-cs-strict-types`, `make site-test`; рост baseline не допускается.

## 7. Критерии приёмки

1. Для заданного периода и канала значения `column_kind = total` по каждой строке дерева совпадают с колонкой «Итого» существующей выгрузки `/marketplace/pl-preview/xlsx` с тем же фильтром (по строкам с учётом `empty=1`).
2. Значения `column_kind = tag` и `common` совпадают с соответствующими колонками существующей выгрузки.
3. Ни одна строка дерева не пропущена: `rows_count` в «Паспорте» равен числу строк «Данных»; нулевые значения присутствуют.
4. Сумма «Итого» по каналам равна общему расчёту (`marketplace = null`) либо расхождение объяснено в `check_channels_vs_all_*`.
5. Названия, начинающиеся с «=», в файле остаются текстом.
6. «Покрытие», «Реклама», «Предупреждения» совпадают с блоками существующей выгрузки («Не попадёт в ОПиУ», «Исключено», «Сверка») на той же фикстуре.
7. Приёмка на реальных периодах: выгрузить 01–04.10, 05–11.10, 12–18.10.2026 и сверить сумму каналов по `total` с присланными файлами `pl-preview_*.xlsx` (выручка, CM1, CM2, CM3, EBITDA).
8. Все гейты зелёные; тесты п. 6 написаны; `ARCHITECTURE.md` обновлён.

## 8. Открытые вопросы

1. **Строки `all`.** Достаточно ли выгружать только отдельные каналы с контролем в «Паспорте» или нужны и строки «все каналы» (риск двойного счёта у потребителя)? Рекомендация: только каналы.
2. **«Реализация» Ozon при недельных периодах.** Используется ли реализация в вашем учёте Ozon? Если да, недельный факт её не покажет (документ входит только целиком в период); нужно решение, как сверять такие недели — и нужна ли отдельная правка сервиса (например, отдельная строка предупреждения с суммой не вошедшей реализации).
3. **«Выручка с СПП» в 4–5 раз меньше «без СПП»** в присланных выгрузках. Вероятная причина — правила маппинга по каналам (`REV_SPP_*` заданы не для всех каналов или источников). После выгрузки с разбивкой по каналам будет видно, у какого канала разница; затем проверить правила маппинга.
4. **Нужны ли строки подытогов и процентов** в «Данных» или только первичные (`LEAF_INPUT`)? Рекомендация: все строки, потребитель фильтрует по `category_type` и `value_format`.
5. **Допустимо ли для выгрузки по умолчанию брать все каналы с SELLER-подключением**, или всегда требовать явный `marketplace`?
6. **Другие каналы.** Lamoda в `MarketplaceType` отсутствует; в выгрузку не попадёт, пока не появится в сервисе (отдельная задача).

## 9. Изменения относительно версии 1.0

- ТЗ сужено до выгрузки из сервиса; разделы про книгу, лист данных, формулы РнП и порядок загрузки удалены.
- Убраны выдуманные коды статей (`SALES_NOSPP`, `COGS_SALES` и т. п.): строки выгрузки соответствуют дереву ОПиУ компании и идентифицируются `pl_code` / `pl_category_id`; суммы не перекодируются.
- Убрана нормализация тегов `Склад` / `Общие`: теги — это теги компании как есть, «Общие / без тега» — колонка `common`, «Итого» — `total`.
- Убрано поле `status` («предварительно / закрыто»): сервис такого статуса не имеет, назначает потребитель. Добавлено правило «файл — полный снимок периода».
- Контроль «сумма блоков тегов = итог» заменён на правила пересечения тегов: итоги — только из `total`.
- Расхождение рекламы «учёт / статистика» описано как штатное (остаток уходит в «Общие»), а не как ошибка.
- Добавлены разбивка по каналам, предупреждения (в т. ч. по «Реализации» Ozon) и привязка к существующим классам и маршрутам.
- Lamoda исключена: в сервисе нет такого канала.
