# План: кабинеты и владельцы на /admin/users

**Класс:** Small/Medium (один модуль `Admin`, read-only к доменным данным, без миграций, без публичных контрактов).
**Риск:** MEDIUM.
**Дата согласования:** 2026-10-19.

## Цель

На странице `/admin/users` (`site/src/Admin/Controller/UserController.php`, шаблон `site/templates/admin/users/index.html.twig`):

- в таблице пользователей — колонка «Кабинеты»: имя + инн + бейдж «Владелец»/«Участник», у пользователей без кабинета — «Без кабинета»;
- фильтры (серверные, в GET): селект «Кабинет» (с опцией «— Без кабинета —») и тоггл «Только владельцы».

## Согласованные решения (best practices)

1. **Источник истины про владельца** — только `companies.user_id`. На зеркальное `CompanyMember role='OWNER'` в админке не опираться.
2. **Один пользователь = одна строка**: кабинеты в одной ячейке списком, не разворачивать в N строк (иначе ломается пагинация и KPI).
3. **Данные без N+1**: read-only query-класс по образцу `ExternalCategoryAdminQuery`; страница = 3 запроса (пользователи + собственные компании по IDs + активные членства по IDs), склейка в DTO в PHP.
4. **Фильтры серверные, в GET**: фильтрация на уровне SQL, состояние в URL (шареабельно), сброс `page` при смене фильтра, валидация whitelist'ом (`company` = UUID или `none`, `owners` = `1`). Членства учитываются только `status=ACTIVE`.
5. **UI на существующем ките админки**, без React и без picker_core: `.t-table`, `select.css`, `badge.css`; тоггл — ссылка на тот же роут с GET-параметром (прецедент: `MappingErrorListController`, `?all=`).
6. **Мультивыбора нет**; отдельного фильтра «по человеку-владельцу» нет (закрывается связкой селект + тоггл).
7. **Колонка «Кабинеты»**: ячейка — `name`, под ним мелким приглушённым `inn`, бейдж роли. `publicId` не показываем.
8. **KPI-ряд не трогаем**; сценарий «висячие пользователи» закрыт опцией «Без кабинета» в селекте.

## Этап 1 — Бэкенд: query-класс

- Новый read-only `UserAdminQuery`:
  - список пользователей с фильтрами на уровне SQL (company / none / owners-only) + Pagerfanta-пагинация (20/стр., как сейчас);
  - batch-загрузка: «собственные компании по IDs пользователей» (`companies.user_id IN`) + «активные членства по IDs» (`company_members.user_id IN`, join companies) → DTO «пользователь → кабинеты с флагом owner»;
  - список кабинетов для селекта (`id + name + inn`, по имени).
- Владелец определяется только по `companies.user_id`; членства — только `status=ACTIVE`.
- Валидация GET-параметров whitelist'ом.

## Этап 2 — Контроллер

- `UserController::renderUserIndex()`: читает и валидирует фильтры, передаёт в шаблон выбранные значения + DTO-строки страницы.
- `CreateAccountController` на 422 перерендеривает тот же метод — без GET-параметров поведение прежнее.

## Этап 3 — Шаблон

- Панель фильтров (form GET, сброс `page`): селект «Кабинет» (вкл. «— Без кабинета —») + тоггл-ссылка «Только владельцы».
- Колонка «Кабинеты» между «Email» и «Дата регистрации»: `name`, под ним мелким `inn`, бейдж «Владелец»/«Участник»; пусто → «Без кабинета».
- Пагинация уже прокидывает `app.request.query.all` — фильтры переживают переходы по страницам.

## Этап 4 — Тесты

Функциональные в `site/tests/Functional/Admin/` (новый `AdminUsersListTest`):

- колонка и бейдж «Владелец» у владельца, «Участник» у OPERATOR;
- фильтр по кабинету показывает и владельца, и участника; не показывает посторонних;
- «Без кабинета» и «Только владельцы»;
- сброс `page` при смене фильтра;
- 422-перерендер формы создания аккаунта зелёный.
