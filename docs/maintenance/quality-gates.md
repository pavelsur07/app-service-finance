# Гейты качества: устройство и история

Правила — `CLAUDE.md`, «Гейты качества». Здесь то, что нужно, когда гейт
красный или меняется CI.

## PHPStan

`make site-stan` — PHPStan level 8 по `site/src` и `site/tests`; исключения
перечислены в `site/phpstan.dist.neon`. Расширения читают контейнер из
`var/cache/test`, поэтому таргет сначала прогревает его сам. Таргета `make stan`
без префикса нет.

**Baseline** `site/phpstan-baseline.neon` — зафиксированный долг, а не свалка.
На момент внедрения (2026-08) в нём 3689 записей, из них 118 нарушений границ
модулей и 51 метод-запрос Repository без `companyId`. Рост блокирует
`site/bin/phpstan-baseline-guard.sh` в CI: сравнивается мультимножество
записей `(path, identifier, message)`, а не агрегаты, поэтому «удалил одну
старую, добавил одну новую» тоже ловится. Осознанный рост проводится меткой
`[baseline-grow]` в заголовке PR. Перегенерация начисто
`make site-stan-baseline` стирает ratchet и делает регресс неотличимым от долга.

Машинные правила поверх PHPStan:

- `site/tests/Architecture/ModuleBoundaryRules.php` — запрет зависеть от
  `Service/`, `Repository/`, `Application/` (кроме `Application/DTO`) и
  `Infrastructure/` чужого модуля; легаси-зона держится пустой.
- `site/tests/PHPStan/Rules/RepositoryCompanyScopeRule.php` — методы-запросы
  Repository без параметра компании; исключение `@companyScopeExempt <причина>`.
- `spaze/phpstan-disallowed-calls` — `dump`, `dd`, `var_dump`, `print_r`,
  `die`, `exit`; записей в baseline нет.

Известная ловушка тестов: `createMock` для `final` класса даёт
`property.unresolvableNativeType`, и пересечение `X&MockObject` не помогает —
подтипа у final быть не может. Дешевле изменить дизайн (вынести зависимость,
как в PR #2442), чем растить baseline.

## PHP CS Fixer

`make site-cs-check` — `@Symfony` + `@Symfony:risky` по `site/src` и
`site/tests`. Коммит `73a37a22` вычистил его целиком; на 2026-08-30 гейт
зелёный (`Found 0 of 2363`, exit 0, перепроверено с `--using-cache=no` —
тёплый кэш даёт ложную зелень).

`make site-cs-strict-types` сохранён отдельно, потому что даёт однозначный ответ
про одно правило: при красном `cs:check` по любой другой причине `exit 8` не
различает норму и регресс `declare_strict_types`. Вне охвата: три файла в
`site/config` и `site/public/index.php` (точки входа и конфиги) и
`site/migrations` (все 242 файла объявление имеют, но гейтом не покрыты).

Ветки, созданные до миграции на strict_types, перед `make site-cs-fix`
обновлять из `master`: иначе fixer массово допишет объявление в посторонний
diff, а это не форматирование — для скалярных вызовов включается строгая
проверка вместо приведения.

## Branch protection на `master`

Обязательные проверки заданы в защите ветки, а не в коде: `🔬 Static analysis`,
`🎨 PHP code style`, `🧪 Unit tests`. Красная — блокирует merge.
Integration- и functional-тесты остаются советующими.

**Имя job'а в `.github/workflows/deploy.yml` — контракт с защитой ветки.**
Переименовал job — обязательная проверка со старым именем больше не появится,
и PR встанет навсегда. Список обязательных проверок обновляется в том же PR,
что меняет имена.

**Матричный job обязательным сделать нельзя.** Проверено на docs-only PR #2388:
при требовании `🧪 Integration tests` и трёх `🧪 Functional tests N/3` PR
заблокировался навсегда. Когда матричный job пропускается по `if:`, GitHub
публикует один check с нераскрытым шаблоном `🧪 ${{ matrix.name }}`, а не три
раскрытых имени; требуемые контексты остаются `pending`. Чтобы сделать эти
тесты обязательными, матрицу нужно сначала развернуть в отдельные job'ы со
статическими именами.

Пропуск обычного job'а безопасен: workflow запускается на каждый PR
(`paths`-фильтра на уровне `on:` нет), check появляется всегда, а пропущенный
GitHub засчитывает как пройденный. Поэтому фронтенд-only и docs-only PR не
блокируются тремя обязательными проверками.

Защита не распространяется на админов. Аварийный обход существует, но
пользоваться им вместо починки — то же, что перегенерировать baseline вместо
исправления ошибки.
