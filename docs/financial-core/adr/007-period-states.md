# ADR-007: Состояния финансового периода OPEN / SOFT_CLOSED / CLOSED

- Статус: Принято (решение Владельца Q4, зафиксировано 2026-10-04)
- Контекст: `01 §8`, `03` (R-14), `04 §4`, `09`

## Контекст

Единственная блокировка — одна дата `Company::financeLockBefore`. Она не
различает «предварительно закрыт» и «закрыт», не применяется к записи
документов Finance/Loan и к импортам Cash, не оставляет аудита и не имеет
потока исправления.

## Решение

1. Период — календарный месяц компании. Таблица состояний
   `fincore_periods (company_id, period 'YYYY-MM', state, state_changed_at,
   state_changed_by)` и журнал `fincore_period_transitions (from, to, reason,
   actor, at)`. Нет записи ⇒ состояние выводится (п.6).
2. Состояния и поведение оркестратора:

   | Состояние | Обычные события (`effective_date` в периоде) | Adjustment-события |
   |---|---|---|
   | `OPEN` | проводятся | проводятся |
   | `SOFT_CLOSED` | **блокируются**: processing `blocked(period_soft_closed)`; не ошибка и не DLQ | допускаются при наличии причины и пользователя |
   | `CLOSED` | **блокируются**: `blocked(period_closed)` | допускаются только через явный correction/late-adjustment flow (п.3) с повышенным правом |

3. **Late-adjustment flow.** Событие `fincore.adjustment.posted` обязано
   содержать `reason`, `actor_user_id`, `original_event_id` (или `period`, если
   исправляется агрегат) и порождает запись аудита. Обычные события в закрытый
   период не «протискиваются»: их либо переводят в открытый период
   пере-датированием (новая ревизия с другой `effective_date`, решение
   бизнес-модуля), либо ждут открытия периода, либо оформляют корректировкой.
   Конкретная роль, имеющая право на корректировку `CLOSED`, определяется в
   Stage 3 по модели ролей `Company`.
4. **Переходы:** `OPEN → SOFT_CLOSED → CLOSED`; обратно только явно и с аудитом
   (`CLOSED → SOFT_CLOSED → OPEN`). Условие перехода в `CLOSED`: reconcile
   периода зелёный (нет событий без processing, нет `blocked`/`failed`
   processing за период, нулевые расхождения проверок периода).
5. **Replay соблюдает политику.** Replay события в периоде `SOFT_CLOSED/CLOSED`
   по умолчанию даёт `blocked`; запись возможна только как adjustment
   (`--as-adjustment --reason`), dry-run всегда показывает число блокируемых
   событий.
6. **Совместимость.** До cutover существующие модули продолжают читать
   `Company::financeLockBefore`. Эффективное состояние периода в ядре =
   более строгое из явного состояния и выведенного из `financeLockBefore`
   (период, целиком ≤ даты, считается `CLOSED`). Целевой моделью
   `financeLockBefore` не является; зависимость устраняется на Stage 10.
7. До Stage 5 legacy-писатели (Finance, Loan, импорты Cash) не
   проверяют состояния ядра; событие из такого писателя в закрытый период
   фиксируется, а проводка блокируется — расхождение видно в shadow-сверке.
   Stage 5 вводит `FinancialPeriodFacade::assertWritable()` для legacy-путей
   (закрывает R-14).

## Рассмотренные альтернативы

| Вариант | Почему отвергнут |
|---|---|
| Оставить `financeLockBefore` | не различает мягкое/жёсткое закрытие, нет аудита и корректировочного потока; решение Владельца |
| Автоперенос запрещённых событий в первый открытый день | молча меняет период относительно бизнес-факта; нарушает ADR-006 |
| Закрывать по компании целиком одной датой | лишает возможности закрывать месяц по готовности и открывать точечно |

## Последствия

+ предсказуемое поведение при поздних данных и replay; полный аудит корректировок;
− появляется состояние `blocked`, требующее мониторинга (`09 §4`, E-05);
− на переходный период два источника «закрытости» (ядро и `financeLockBefore`).
