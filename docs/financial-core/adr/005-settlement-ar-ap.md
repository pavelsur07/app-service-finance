# ADR-005: AR/AP — отдельный settlement-контур, не производная Cash

- Статус: Принято (решение Владельца Q1, зафиксировано 2026-10-04)
- Контекст: `02 §0`, `04 §5`, `06`, ADR-003, ADR-006

## Контекст

В коде нет Invoice, Bill, AR, AP, Prepayment: платёж — это `CashTransaction`
с контрагентом и категорией, связи «платёж → обязательство» нет, «кто кому
должен» не вывести (`02 §0`). Владелец решил: AR/AP входит в целевую
функциональность Financial Core.

## Решение

1. **Возникновение задолженности и движение денег — разные события.**

   ```text
   invoice issued   → RECOGNITION (доход) + SETTLEMENT (+AR)
   payment received → CASH (+)          + SETTLEMENT (−AR / аванс)      — доход не признаётся повторно
   bill received    → RECOGNITION (расход) + SETTLEMENT (+AP)
   vendor payment   → CASH (−)          + SETTLEMENT (−AP / аванс)
   ```

2. **Нормализованная семантика**, не привязанная к российским документам.
   Базовые понятия: `Receivable document` (Invoice), `Payable document` (Bill),
   `Payment`, `Allocation`, `Adjustment/Credit`, `Refund`. Акт, УПД, накладная и
   пр. — локальные первичные документы, из которых бизнес-модуль выводит
   нормализованное событие; тип локального документа хранится в
   `payload.source_document_type` и в расчётах не участвует.
3. **Граница ответственности.** Бизнес-модули (Stage 7 определяет их состав и
   раскладку в Phase 0) владеют первичными документами и платежами как
   state-based сущностями и публикуют события. Financial Core **не владеет**
   первичными документами; он владеет книгой `SETTLEMENT` и проекцией AR/AP.
   Модуль `Cash` остаётся источником банковских фактов и не хранит
   задолженность.
4. **Сценарии (обязательные для поддержки):**

   | Сценарий | События → эффект |
   |---|---|
   | Частичная оплата | `payment.allocated` на сумму < остатка: −AR/−AP на сумму аллокации |
   | Предоплата/аванс | `payment.received/made` без документа: CASH + SETTLEMENT на счёт аванса (`advance_received` / `advance_paid`); последующий `payment.allocated` переносит аванс в погашение документа без CASH-проводки |
   | Переплата | остаток платежа сверх документа остаётся авансом |
   | Возврат | `payment.refunded` с `causation_id` на платёж: обратные CASH + SETTLEMENT; доход не затрагивается |
   | Кредит-нота/скидка | `invoice.credit_issued`: RECOGNITION (уменьшение дохода) + SETTLEMENT (−AR) |
   | Отмена/сторно документа | `sales.invoice.cancelled` / `purchase.bill.cancelled`: сторно группы проводок исходного события (`06 §5`); при закрытом периоде — через adjustment-flow (ADR-007) |
5. **Инварианты** (`04 §4`): INV-10 (Revenue↔AR), INV-11 (Expense↔AP), INV-12
   (Σ аллокаций платежа ≤ суммы платежа; остаток документа = сумма − аллокации −
   кредиты). Эти условия — `balanced_within` соответствующих правил и
   reconcile-проверки A-01…A-03.
6. **Маркетплейс.** До миграции сохраняется текущая семантика (ADR-006);
   расчёты с маркетплейсом (выплаты, удержания как задолженность) **не
   вводятся** в Stage 4, а могут быть добавлены позже как отдельные правила и
   события поверх уже существующего `SETTLEMENT`.

## Рассмотренные альтернативы

| Вариант | Почему отвергнут |
|---|---|
| Выводить AR/AP из `CashTransaction` + `PaymentPlan` | нет документа-обязательства; платёж без документа неотличим от аванса; решение Владельца — отдельный контур |
| Хранить задолженность в Balance | Balance — журнал баланса; AR/AP нужен с детализацией по документу и контрагенту и с пересчётом из проводок |
| Привязать модель к российским документам (УПД/акт) | противоречит требованию нормализованной семантики |

## Последствия

+ «кто кому должен» вычисляется из проводок; платёж не создаёт доход повторно;
+ локализация документов — задача адаптеров, не ядра;
− новый бизнес-домен: модули, UI, API (Stage 7, backend и frontend отдельными Stage);
− курсовые разницы по валютным обязательствам не входят в первые Stage (ADR-008).
