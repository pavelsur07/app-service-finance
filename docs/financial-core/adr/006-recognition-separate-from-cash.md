# ADR-006: Признание отделено от денег; бизнес-модуль определяет факт, PostingRule — эффект

- Статус: Принято (решение Владельца Q2, зафиксировано 2026-10-04)
- Контекст: `02 §1–2`, `05 §4`, `06 §4,6`, ADR-005

## Контекст

Сегодня правила признания разные: Marketplace — конец отчётного периода;
Cash→P&L — дата оплаты (всегда `CASHFLOW_EXPENSE`, включая поступления);
Loan — дата платежа по графику; ручные документы — введённая дата. Единого
правила нет.

## Решение

1. Revenue и Expense признаются по **экономическому факту**, а не по движению
   денег. Дата оплаты не является универсальной датой признания.

   ```text
   Business fact → Financial Event (recognition) → RECOGNITION posting
   Payment       → Financial Event (payment)     → CASH posting + SETTLEMENT posting
   ```

2. **Границы ответственности:**
   - Бизнес-модуль определяет, **ЧТО произошло** и **в какой период это
     относится**: тип события, `occurred_at`, `effective_date`.
   - Financial Core определяет **финансовый эффект**: `PostingRule` переводит уже
     случившееся событие в проводки. Правило не определяет бизнес-факт, не читает
     источник и **не переопределяет `effective_date`**.
3. Три времени события: `occurred_at` (когда случилось), `effective_date` (в
   какой финансовый период относится), `recorded_at` (когда записано).
   `PostingRule` использует `effective_date`.
4. **Платёж не признаёт доход/расход.** Событие `payment.*` порождает только
   `CASH` и `SETTLEMENT`. Исключение — совместимость (п.5).
5. **Существующие потоки сохраняют текущую семантику как конкретные
   versioned-правила**, а не как универсальное правило системы:

   | Правило | Семантика | Статус |
   |---|---|---|
   | `marketplace_month_stage_v1` | признание на последний день отчётного периода маркетплейса (закрытие стадии) | сохраняется до миграции; не распространяется на другие источники |
   | `loan_schedule_v1` | признание процентов/комиссии на `dueDate` графика (событие `loan.payment.due`) | совместимость |
   | `legacy_cash_basis_v1` | признание по дате оплаты для расхода/дохода без первичного документа; срабатывает **только** на явное пользовательское событие `finance.document.created` (кнопка «создать документ из транзакции»), а не на сам факт проводки в Cash | совместимость; выводится из употребления, когда по операции есть Invoice/Bill |

   Любое изменение этих правил — новая `rule_version` и коррекция (`06 §5`).
6. **Следствие для Cash:** событие `cash.transaction.booked` порождает `CASH`
   (и, если известна привязка к документу, `SETTLEMENT`), но не `RECOGNITION`.
7. **Следствие для контракта события:** `effective_date` обязателен, задаётся
   продюсером; один бизнес-факт, у которого признание и оплата в разные даты,
   выражается **двумя событиями** (например, `loan.payment.due` и
   `cash.transaction.booked`), а не двумя датами в одном событии.

## Рассмотренные альтернативы

| Вариант | Почему отвергнут |
|---|---|
| Правило признания по дате оплаты для всех | противоречит решению Владельца; искажает периоды при отсрочке |
| Правило сам выбирает дату признания | смешивает определение факта с учётным эффектом; replay станет зависеть от логики правила, а не от события |
| Один универсальный «recognition date» в ядре | маркетплейс признаёт на конец периода, услуги — по факту оказания; универсальной даты нет |

## Последствия

+ детерминированный replay: результат зависит только от события и версии правила;
+ AR/AP возможны без двойного признания;
− продюсеры отвечают за корректный `effective_date`; нужен ревью на каждый
  новый тип события;
− legacy cash-basis правило временно сосуществует с economic-recognition.
