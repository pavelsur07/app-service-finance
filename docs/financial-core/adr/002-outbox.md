# ADR-002: Transactional Outbox с отдельным журналом событий

- Статус: Принято на Stage 0 (2026-10-04)
- Контекст: `03` (R-02, R-03), `04 §3`, `08`

## Контекст

Везде, где сегодня публикуются сообщения, запись в БД и `dispatch()` в Redis —
два независимых действия; между ними окно потери (G1–G8, C1–C2). Транспорт
бизнес-очередей — Redis (AOF everysec): потеря содержимого очереди необратима,
копии в БД нет. Единственная защита — sweeper'ы в части потоков (Ingestion, Ozon).

## Решение

1. Продюсер в **одной транзакции** с бизнес-данными записывает строку события
   (`fincore_events`) и строку доставки (`fincore_outbox`: `event_id`, `status`
   `pending|claimed|published`, `available_at`, `attempts`, `published_at`,
   `last_error`).
2. **Outbox Publisher** — отдельный процесс/команда: `SELECT … FOR UPDATE SKIP
   LOCKED LIMIT n` → claim → `dispatch(PostEventMessage)` вне транзакции →
   `published_at`. Гарантия — **at-least-once**; дубль допустим.
3. **Sweeper**: `pending/claimed` старше SLA и события `published` без processing
   старше SLA перепубликуются (E-01/E-02).
4. Брокер остаётся Redis; он перестаёт быть источником истины, поэтому его
   потеря — штатный восстановимый сбой.
5. `recordEvent()` не делает `flush()`; коммитит вызывающий Action — совпадает с
   правилом «flush только в Action».

## Рассмотренные альтернативы

| Вариант | Почему отвергнут |
|---|---|
| `doctrine_transaction` + `DispatchAfterCurrentBusStamp` | отправка после коммита, но сообщение уходит из памяти процесса: kill между commit и send теряет его; нет следа в БД |
| Doctrine Messenger-транспорт на том же подключении (сообщение в транзакции) | атомарно, но ack **удаляет** сообщение — нет журнала событий, lineage и replay; журнал всё равно пришлось бы вести отдельно |
| Только sweeper'ы по бизнес-таблицам (как сейчас в Ingestion) | работает на модуль, не даёт общего контракта; каждый модуль изобретает свой «pending» |
| Debezium/CDC | новая инфраструктура, несоразмерно |

## Последствия

+ атомарность «операция + факт», независимость от надёжности Redis;
+ единый паттерн вместо ad-hoc sweeper'ов;
− дополнительная запись на каждую операцию; нужен publisher-процесс и мониторинг
  возраста `pending` (прод-изменение — §3.3);
− задержка публикации = период опроса (цель ≤ 1–2 с при LISTEN/NOTIFY или короткий poll).

## Инварианты и проверки

INV-01, INV-03; E-01, E-02; тест «kill между commit и dispatch» (Stage 2/3).
