# ADR-003: Posting Orchestrator и односторонние проводки по книгам

- Статус: Принято на Stage 0 (2026-10-04); дополнено решениями Владельца Q3, Q2, Q4 (2026-10-04, п.6–8)
- Контекст: `06`, `07`, `04 §5`, ADR-005…008

## Контекст

Три контура (P&L, Cash, Balance) не связаны; P&L — изменяемый регистр, который
пересобирается delete+insert без блокировки и без сверки с источником (R-05).
Понятий AR/AP, Invoice, Bill нет. Нужно единое место, где факт превращается в
учётное воздействие детерминированно и повторяемо.

## Решение

1. **Posting Orchestrator** — единственный потребитель событий, создающий
   проводки. Для события подбирает `PostingRule` по `(event_type, event_version)`;
   правило — чистая функция `event → PostingDraft`.
2. Одно событие → 0..N групп (по правилу) → 1..M строк; всё в **одной транзакции
   на событие** вместе с `processing=done` и outbox-строками для проекций.
3. **Проводки односторонние со знаком, по книгам** `RECOGNITION`, `CASH`,
   `SETTLEMENT`; баланс-условия задаёт правило (`balanced_within`), а не схема.
   Решения Q1/Q3 приняты и полной двойной записи в ядре **не требуют**: AR/AP —
   отдельная книга `SETTLEMENT` (ADR-005), двусторонний контракт Balance
   закрывает adapter (п.6). Для правил, затрагивающих `SETTLEMENT`,
   кросс-книжные условия `balanced_within` обязательны (`06 §1`). Поля
   `account_code` и `balanced_within` сохраняют возможность перехода на двойную
   запись без смены схемы.
4. Проводки неизменяемы; исправление — сторно (`reverses_posting_id`, `UNIQUE`) +
   новая группа; смена правила = новая `rule_version` и replay.
5. Проекции (P&L, Cash, AR/AP) — **производные**, пересчитываемые из проводок по
   ключу агрегата; запись `ON CONFLICT DO UPDATE SET amount=<пересчитано>`, не дельта.
6. **Balance** получает данные из ядра автоматически, но ядро не пишет в его
   таблицы: поток `Financial Event → Orchestrator → Posting Group → Balance
   Intake Adapter → Balance operation`. `request_key = fincore:{posting_group_id}`
   (повтор не создаёт вторую операцию). Маппинг `posting/account/category →
   Balance account/article/dimension` — отдельная версионируемая конфигурация
   компании, не код Orchestrator. Первый режим — `draft/suggestion`, затем
   автоматический `post` после подтверждения маппинга. Balance остаётся
   отдельным ledger со своими инвариантами (равенство актива и пассива на
   документ, периоды); несбалансированный маппинг или закрытый период Balance
   → `blocked`/finding, не обход.
7. Правила версионируются, покрываются unit-тестами всех веток; результат
   записывается с `rule_code/rule_version` для аудита.
8. **Граница ответственности** (ADR-006): бизнес-модуль определяет, что
   произошло и `effective_date`; `PostingRule` определяет только финансовый
   эффект уже случившегося события, не переопределяя дату. **Состояние периода**
   (ADR-007) проверяет оркестратор до записи проводок, а не правило.

## Рассмотренные альтернативы

| Вариант | Почему отвергнут |
|---|---|
| Двойная запись «сразу» с планом счетов | придумывает бухгалтерский план без решения Владельца (AGENTS.md §3.4 п.1); нет AR/AP-данных |
| Расширить Balance как единый журнал | Balance — журнал баланса с жёсткими инвариантами (сумма актива = пассива на документ), его семантика не подходит для P&L/Cash |
| Каждый модуль сам пишет в проекции (как сейчас) | сохраняет R-05 и расхождения; нет общего replay |
| Проекции как SQL-views поверх проводок | допустимо для Stage 4 shadow, но не масштабируется на отчёты; решение по каждой проекции отдельно |

## Последствия

+ детерминированный, воспроизводимый учёт; причина любой суммы прослеживается до события;
+ shadow-сверка с legacy возможна без риска;
− правила нужно содержать и версионировать; сторно-коррекции увеличивают объём;
− односторонность требует reconcile-проверок вместо схемного гарантирования баланса.
