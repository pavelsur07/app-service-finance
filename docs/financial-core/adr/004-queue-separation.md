# ADR-004: Отдельные транспорты и DLQ для ядра, legacy-очереди не трогаем

- Статус: Принято на Stage 0 (2026-10-04)
- Контекст: `01 §3`, `08`

## Контекст

Сегодня: 4 Redis-транспорта + 2 алиаса на тех же стримах, общий `failed`
(пассивный, без алертов), один процесс на транспорт, общий Redis для очередей,
локов, кэша и сессий; `ingest_*` не изолированы от `async_*`. Смешивать
финансовое ядро с этими конвейерами — значит унаследовать R-03, R-10, R-21, R-22.

## Решение

1. Новые транспорты `fincore_events`, `fincore_projection`, `fincore_balance`,
   `fincore_reconcile` — отдельные стримы, отдельные воркеры, отдельные
   лимиты памяти; **один тип сообщения — один транспорт**.
2. Отдельный `fincore_failed` (Doctrine) как `failure_transport` каждого из них;
   запись DLQ дублируется структурированным статусом в
   `fincore_event_processing` (читаем причину без разбора сериализации).
3. Retry — по `08 §2`; `Recoverable` vs `Unrecoverable` — по CLAUDE.md.
4. Сообщения — скаляры/ID, `CompanyAwareMessage`, фильтр компании в воркере.
5. Legacy-очереди и маршрутизация **не меняются**; миграция потоков идёт по
   Stage 4–6 добавлением продюсеров, а не переносом consumer'ов.
6. Брокер ядра — Redis; надёжность даёт outbox (ADR-002), поэтому отдельный
   Redis-инстанс — опциональное решение Stage 3 (изоляция R-21), не предпосылка.
7. Порядок доставки не требуется (INV-15, `07 §4`) ⇒ горизонтальное
   масштабирование consumer'ов безопасно.

## Рассмотренные альтернативы

| Вариант | Почему отвергнут |
|---|---|
| Использовать `async_pipeline` | смешение с DB-heavy обработкой маркетплейсов, общий failed, нет изоляции отказов |
| Одна очередь на всё ядро | проекции и Balance intake имеют разные профили ошибок/ретраев; Balance-сбой не должен задерживать проводки |
| Doctrine-транспорт для всех очередей ядра | выше нагрузка на БД и нет ack-журнала; допустим для `fincore_failed` и, при необходимости, `fincore_reconcile` |
| RabbitMQ/Kafka | новая инфраструктура без доказанной потребности |

## Последствия

+ изоляция отказов, прозрачный DLQ и алерты по каждому контуру;
− новые воркеры и DSN в проде (§3.3), больше конфигурации и мониторинга;
− при одновременной работе legacy и ядра растёт нагрузка на Redis — наблюдать `maxmemory`.
